2. Thread — tạo, start vs run, lifecycle Hay hỏi phỏng vấn Junior+

Process có không gian bộ nhớ riêng; thread là đơn vị thực thi bên trong process. Các thread trong cùng process chia sẻ heap (object, static field) nhưng mỗi thread có stack riêng (biến local, lời gọi method). Chính vì chia sẻ heap nên mới sinh ra race condition — đây là khác biệt tư duy lớn nhất khi từ Node.js sang Java.

Ba cách tạo thread

// 1. implements Runnable - khuyen dung
Runnable r = () -> IO.println("chay bang Runnable");

// 2. Callable - co ket qua tra ve va nem duoc checked exception
Callable<Integer> c = () -> 42;

// 3. extends Thread - tranh dung: da ke thua Thread thi khong ke thua class khac duoc
class MyThread extends Thread {
    public void run() { IO.println("chay bang Thread"); }
}

Về mặt API, Runnable là một việc không trả về gì, còn Callable trả về kết quả và được chạy qua executor (Future). Trong code production hiện đại, bạn hiếm khi tự new Thread — hãy để ExecutorService quản lý (mục 8).

start() vs run() — câu hỏi mở màn kinh điển

public class ThreadBasics {
    public static void main() throws InterruptedException {
        Runnable job = () -> IO.println("chay trong: " + Thread.currentThread().getName());

        IO.println("main: " + Thread.currentThread().getName());
        job.run();
        Thread t = new Thread(job, "worker-1");
        t.start();
        t.join();
        IO.println("state sau join: " + t.getState());
    }
}
main: main
chay trong: main
chay trong: worker-1
state sau join: TERMINATED

job.run() chỉ là gọi method bình thường trên thread hiện tại (in ra main), còn start() mới tạo thread mới và để JVM gọi run() bên trong nó. Gọi start() lần thứ hai trên cùng thread ném IllegalThreadStateException. join() khiến thread gọi chờ thread kia kết thúc.

Interrupt & daemon

  • Interrupt là cơ chế hợp tác: t.interrupt() không dừng ngay mà chỉ đặt cờ. Nếu thread đang sleep/wait/join, nó nhận InterruptedException và cờ bị xóa. Bên trong catch, gọi lại Thread.currentThread().interrupt() để "trao cờ" lên trên — đừng nuốt im lặng.
  • Vòng lặp dài nên kiểm tra Thread.currentThread().isInterrupted() để thoát sớm; Thread.interrupted() vừa đọc vừa xóa cờ.
  • Daemon thread là thread nền: JVM sẽ thoát khi mọi non-daemon thread kết thúc, bất kể daemon còn chạy. Đặt bằng t.setDaemon(true) trước start(). Ví dụ điển hình: scheduled cleanup. Không dùng daemon cho việc quan trọng cần hoàn tất (ghi file, commit DB) — JVM có thể tắt bất ngờ.
Không có cách "kill" thread an toàn trong Java: Thread.stop() bị bỏ từ lâu vì để lại object trong trạng thái nửa vời. Muốn dừng: dùng cờ volatile + interrupt, hoặc Future.cancel(true).

3. Race condition & atomicity Hay hỏi phỏng vấn Production

Race condition xảy ra khi nhiều thread cùng đọc/ghi dữ liệu chia sẻ mà không đồng bộ, khiến kết quả phụ thuộc thứ tự thực thi — vốn không xác định. Phép count++ trông như một hành động nhưng thực chất là ba bước: đọc count → cộng 1 → ghi lại. Hai thread có thể đọc cùng giá trị cũ rồi cùng ghi đè nhau (lost update).

public class RaceCondition {
    static int count = 0;

    public static void main() throws InterruptedException {
        Runnable job = () -> {
            for (int i = 0; i < 100_000; i++) count++;
        };
        Thread t1 = new Thread(job);
        Thread t2 = new Thread(job);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        IO.println("count = " + count + " (ky vong 200000)");
    }
}
count = 129069 (ky vong 200000)   // mot lan chay - so nay thay doi moi lan

6 lần chạy thử trên máy soạn tài liệu cho: 129069, 141203, 115179, 133910, 106237, 134489 — không lần nào đủ 200000. Bug kiểu này rất khó tìm ở production vì đôi khi nó "đúng", chỉ sai dưới tải cao.

4. Visibility & Java Memory Model Hay hỏi phỏng vấn

Vì sao cần đồng bộ ngay cả khi chỉ một thread ghi? Mỗi CPU có cache riêng, JIT có thể giữ biến trong register, và compiler/CPU được phép đổi thứ tự lệnh miễn là với một thread đơn lẻ kết quả không đổi. Không có đồng bộ, thread này có thể không bao giờ thấy giá trị thread kia ghi.

public class VolatileStop {
    static volatile boolean running = true;

    public static void main() throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (running) {
                // vong lap nong - neu running khong volatile, JIT co the giu gia tri true mai mai
            }
            IO.println("worker dung");
        });
        worker.start();
        Thread.sleep(50);
        running = false;
        worker.join();
        IO.println("main ket thuc");
    }
}
worker dung
main ket thuc

Bỏ volatile đi, chương trình có thể treo vĩnh viễn: JIT nâng running ra khỏi vòng lặp (hoisting) vì không thấy nó bị thay đổi trong thread đó. Đây là bug kinh điển chỉ xuất hiện ở bản build tối ưu — bản debug lại chạy đúng.

happens-before — quy tắc thực dụng

JMM định nghĩa quan hệ happens-before: nếu thao tác A happens-before B thì mọi thay đổi bộ nhớ của A đều nhìn thấy ở B. Các cặp cần nhớ:

  • Trong cùng một thread, mọi thao tác theo thứ tự chương trình.
  • Ghi vào volatile happens-before lần đọc volatile tiếp theo cùng biến.
  • Nhả monitor (unlock/ra khỏi synchronized) happens-before vào monitor tiếp theo (mở khóa kế tiếp).
  • Thread.start() happens-before mọi thao tác trong thread mới; mọi thao tác trong thread happens-before join() trả về.
  • Ghi final field trong constructor happens-before đọc field đó qua tham chiếu được công bố an toàn (JLS 17.5).
  • Gửi task vào executor happens-before task bắt đầu chạy; task kết thúc happens-before Future.get() trả về.
volatile chỉ giải quyết visibility, không giải quyết atomicity. volatile int count; count++; vẫn mất dữ liệu y như mục 3. Chỉ dùng volatile cho: cờ bật/tắt, trạng thái một chiều, hoặc biến chỉ một thread ghi và nhiều thread đọc (theo mô hình one-writer).

Khái niệm liên quan là safe publication: đưa object đã khởi tạo xong cho thread khác thấy. Các cách an toàn: static final khởi tạo trong static block, volatile reference, gán qua AtomicReference, hoặc đặt vào collection concurrent. Nếu không, thread khác có thể thấy object ở trạng thái nửa vời (thấy reference trước khi thấy field đã gán).

5. synchronized — khóa đúng cách Hay hỏi phỏng vấn Junior+

synchronized khóa theo một monitor object: một thread vào được thì thread khác phải chờ. Nó đảm bảo đồng thời atomicity (trọn khối như một hành động) và visibility (khi ra khỏi khối, mọi thay đổi được đẩy ra bộ nhớ chính; khi vào khối, cache được làm mới).

public class SynchronizedCounter {
    static int count = 0;

    static synchronized void tang() {
        count++;
    }

    public static void main() throws InterruptedException {
        Runnable job = () -> {
            for (int i = 0; i < 100_000; i++) tang();
        };
        Thread t1 = new Thread(job);
        Thread t2 = new Thread(job);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        IO.println("count = " + count);
    }
}
count = 200000

Khóa vào đối tượng nào?

  • synchronized trên method instance → khóa this.
  • static synchronized → khóa object Class của class đó.
  • synchronized (obj) { ... } → khóa đúng object obj. Đây là dạng linh hoạt nhất — luôn khóa cùng một object đã tạo sẵn, không tạo mới trong method.

Lỗi phổ biến: tạo object khóa mới mỗi lần gọi, khiến mỗi thread khóa một monitor khác nhau và synchronized trở nên vô dụng:

public class BadLock {
    static int count = 0;

    static void tang() {
        Object lock = new Object();
        synchronized (lock) {
            count++;
        }
    }

    public static void main() throws InterruptedException {
        Runnable job = () -> {
            for (int i = 0; i < 100_000; i++) tang();
        };
        Thread t1 = new Thread(job);
        Thread t2 = new Thread(job);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        IO.println("count = " + count + " (ky vong 200000)");
    }
}
count = 150497 (ky vong 200000)   // mot lan chay - van nho hon 200000
Đừng khóa trên object "của người khác": tránh synchronized ("literal"), trên Integer/Boolean boxed (có cache!), hay trên object public mà code khác cũng khóa — dễ deadlock ngoài ý muốn. Tạo một private final Object lock = new Object(); riêng.

wait / notify — và vì sao nên tránh

wait()/notify() cho phép thread chờ điều kiện trong khi đã nhả monitor, nhưng dễ dùng sai: phải gọi trong synchronized, phải chờ bằng while (không phải if) vì có thể thức dậy giả (spurious wakeup), và notify chỉ đánh thức một thread bất kỳ. Code hiện đại nên dùng BlockingQueue, CountDownLatch (mục 12) hoặc Lock + Condition (mục 6) thay vì tự viết wait/notify.

Góc production: khóa synchronized càng rộng càng dễ nghẽn. Nguyên tắc: khóa ít và ngắn — không gọi IO, không gọi callback/network bên trong khối khóa. Trước JDK 24, synchronized gây pinning virtual thread; JEP 491 (JDK 24) đã xử lý — chi tiết ở mục 10.

6. Lock, ReentrantLock, Condition Junior+ Production

ReentrantLock là bản nâng cấp của synchronized khi bạn cần thứ mà monitor không có: thử khóa không chờ (tryLock), chờ có timeout, ngắt được khi đang chờ (lockInterruptibly), công bằng (fairness), hoặc nhiều hàng chờ điều kiện (Condition).

import java.util.concurrent.locks.ReentrantLock;

public class LockDemo {
    static int count = 0;
    static final ReentrantLock lock = new ReentrantLock();

    public static void main() throws InterruptedException {
        Runnable job = () -> {
            for (int i = 0; i < 100_000; i++) {
                lock.lock();
                try {
                    count++;
                } finally {
                    lock.unlock();
                }
            }
        };
        Thread t1 = new Thread(job);
        Thread t2 = new Thread(job);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        IO.println("count    = " + count);
        IO.println("isLocked = " + lock.isLocked());
    }
}
count    = 200000
isLocked = false
Luôn unlock() trong finally. Khác với synchronized (JVM tự nhả khi ra khỏi block hoặc khi exception), Lock phải nhả tay — quên finally là treo cả hệ thống.

tryLock — chống chờ vô hạn

import java.util.concurrent.locks.ReentrantLock;

public class TryLockDemo {
    static final ReentrantLock lock = new ReentrantLock();

    public static void main() throws InterruptedException {
        lock.lock();
        Thread worker = new Thread(() ->
            IO.println("worker tryLock khi main dang giu: " + lock.tryLock()));
        worker.start();
        worker.join();
        IO.println("main nha lock");
        IO.println("main tryLock lai sau khi nha    : " + lock.tryLock());
        lock.unlock();
    }
}
worker tryLock khi main dang giu: false
main nha lock
main tryLock lai sau khi nha    : true

Reentrant nghĩa là cùng một thread có thể khóa lồng nhiều lần (đếm số lần giữ), phải unlock() đúng số lần. tryLock() trả false ngay lập tức nếu không lấy được; bản có tham số tryLock(time, unit) chờ tối đa bao lâu. Đây là công cụ chính để phá deadlock: nếu không lấy được khóa trong thời gian cho phép, chủ động bỏ và thử lại/thất bại sạch sẽ thay vì treo mãi.

7. Atomic, CAS & LongAdder Hay hỏi phỏng vấn Junior+

Các lớp java.util.concurrent.atomic giải bài toán read-modify-write cho một biến mà không cần khóa, dựa trên lệnh phần cứng CAS (Compare-And-Set): "nếu giá trị hiện tại vẫn là A thì đổi thành B; nếu không, trả về thất bại". Thất bại thì vòng lặp thử lại với giá trị mới.

import java.util.concurrent.atomic.AtomicInteger;

public class AtomicCounter {
    static AtomicInteger count = new AtomicInteger();

    public static void main() throws InterruptedException {
        Runnable job = () -> {
            for (int i = 0; i < 100_000; i++) count.incrementAndGet();
        };
        Thread t1 = new Thread(job);
        Thread t2 = new Thread(job);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        IO.println("count = " + count.get());
    }
}
count = 200000

incrementAndGet() là một thao tác CAS trọn vẹn nên luôn đúng. Ngoài ra còn getAndIncrement(), addAndGet(n), updateAndGet(fn), accumulateAndGet(n, fn).

  • Chọn lớp: AtomicInteger/AtomicLong (đếm, id), AtomicBoolean (cờ), AtomicReference (object/trạng thái), AtomicIntegerArray/AtomicLongArray (mảng).
  • LongAdder (và LongAccumulator) cho counter contention cao: chia thành nhiều cell để giảm tranh chấp, cộng lại khi sum(). Nhanh hơn AtomicLong khi hàng nghìn thread cùng tăng, nhưng sum() không phải ảnh chụp nhất quán tức thời — phù hợp metrics.
  • Bẫy ABA: giá trị đổi A → B → A khiến CAS tưởng chưa từng thay đổi. Hiếm gặp, nhưng với cấu trúc lock-free phức tạp hãy dùng AtomicStampedReference (kèm số phiên bản).
  • Atomic không thay được khóa khi cần cập nhật nhiều biến liên quan trong một thao tác nhất quán — lúc đó vẫn cần synchronized/Lock.

8. ExecutorService, Future & thread pool Hay hỏi phỏng vấn Production

Tự tạo thread cho từng việc là phản pattern: thread tạo/hủy tốn kém, số lượng không giới hạn làm sập hệ thống. ExecutorService tách "việc cần chạy" khỏi "ai chạy và chạy bao nhiêu", cho phép hàng đợi, giới hạn thread, và thu thập kết quả qua Future.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class ExecutorDemo {
    public static void main() throws Exception {
        try (ExecutorService pool = Executors.newFixedThreadPool(3)) {
            Future<Integer> f1 = pool.submit(() -> {
                Thread.sleep(30);
                return 21;
            });
            Future<Integer> f2 = pool.submit(() -> 2);
            IO.println("f1  = " + f1.get());
            IO.println("f2  = " + f2.get());
            IO.println("tong = " + (f1.get() + f2.get()));
        }
        IO.println("pool da dong");
    }
}

f2  = 2
tong = 23
pool da dong

Từ Java 19, ExecutorService là AutoCloseable: dùng try-with-resources để tự động close() (chờ task đang chạy xong rồi dừng) — gọn hơn shutdown() + awaitTermination() thủ công.

Future — lấy kết quả, và cái bẫy nuốt exception

import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;

public class FutureTimeout {
    public static void main() throws Exception {
        try (ExecutorService pool = Executors.newSingleThreadExecutor()) {
            Future<String> f = pool.submit(() -> {
                Thread.sleep(200);
                return "xong";
            });
            try {
                IO.println(f.get(50, TimeUnit.MILLISECONDS));
            } catch (TimeoutException e) {
                IO.println("het thoi gian cho - future van chay");
                f.cancel(true);
            }

            Future<?> loi = pool.submit(() -> {
                throw new IllegalStateException("bug trong task");
            });
            try {
                loi.get();
            } catch (ExecutionException e) {
                IO.println("bat duoc: " + e.getCause().getMessage());
            }
        }
    }
}

  • get() block đến khi xong — đừng gọi trong vòng lặp tuần tự nếu muốn song song; luôn cân nhắc get(timeout, unit).
  • Exception trong task bị bọc vào ExecutionException — phải get() mới thấy; submit() một task ném lỗi mà không bao giờ gọi get() là nuốt lỗi im lặng. execute() thì ngược lại: exception in thẳng ra UncaughtExceptionHandler và in stderr.

9. CompletableFuture Hay hỏi phỏng vấn Production

Future chỉ cho lấy kết quả bằng get() (block). CompletableFuture (Java 8) thêm khả năng ghép nối như Promise: biến đổi, kết hợp, xử lý lỗi — tương đương .then() của Node.js.

import java.util.concurrent.CompletableFuture;

public class CompletableFutureDemo {
    static String goiApi(String ten) {

                        .join();

            .supplyAsync(() -> "10")
            .thenApply(Integer::parseInt)
            .thenApply(n -> n * 2)
            .thenAccept(n -> IO.println("chain: " + n))
            .join();
    }
}

10. Virtual threads, Scoped Values & structured concurrency Production

Virtual thread (chính thức từ Java 21, JEP 444) là thread do JVM quản lý, nhẹ hơn thread hệ điều hành hàng nghìn lần: có thể tạo hàng triệu. Khi virtual thread gặp thao tác blocking (IO, sleep, chờ lock), JVM tháo nó ra khỏi carrier thread và dùng carrier chạy việc khác — nên code blocking truyền thống vẫn scale.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class VirtualThreadsDemo {
    public static void main() throws Exception {
        Thread vt = Thread.ofVirtual().name("vt-", 1).start(() ->
            IO.println("virtual? " + Thread.currentThread().isVirtual()
                       + " | ten: " + Thread.currentThread().getName()));
        vt.join();

        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            Future<String> f = pool.submit(() -> {
                Thread.sleep(50);
                return "xong, virtual=" + Thread.currentThread().isVirtual();
            });
            IO.println(f.get());
        }
    }
}
virtual? true | ten: vt-1
xong, virtual=true
  • Dùng khi: server xử lý nhiều request blocking (HTTP client, JDBC, đọc file) — thay thế thread pool lớn. Mỗi request một virtual thread là mô hình đơn giản nhất.
  • Không dùng khi: CPU-bound (virtual thread không nhanh hơn platform thread cho tính toán); không pool virtual thread (tạo mới là rẻ, pool chỉ tổ tốn).
  • Pinning: virtual thread bị "ghim" vào carrier khi chạy native code/JNI/FFM. Trước JDK 24, synchronized cũng gây pinning; JEP 491 (JDK 24) đã bỏ pinning cho monitor — trên JDK 25 bạn không cần thay synchronized bằng ReentrantLock chỉ vì virtual thread nữa.
  • ThreadLocal: mỗi virtual thread có ThreadLocal riêng — hàng triệu thread nghĩa là hàng triệu bản sao; cân nhắc ScopedValue. Đặc biệt cảnh giác khi chạy virtual thread trong thread pool kế thừa ThreadLocal.

Scoped Values (chính thức JDK 25, JEP 506)

ScopedValue là cách chia sẻ dữ liệu bất biến theo ngữ cảnh request (user, traceId, tenant) mà không cần truyền tham số qua mọi hàm. Khác ThreadLocal: chỉ đọc được trong scope, tự giải phóng, an toàn với virtual threads.

    public static void main() {
        ScopedValue.where(USER, "an").run(() -> {
            IO.println("trong scope : " + USER.get());
            IO.println("isBound     : " + USER.isBound());
        });
        IO.println("ngoai scope : " + USER.isBound());
    }
}

ngoai scope : false
Thread mới không tự thừa hưởng binding. Đọc ScopedValue từ một thread start() độc lập ngoài scope sẽ ném NoSuchElementException. Binding chỉ truyền xuống subtask trong StructuredTaskScope; muốn truyền context sang thread tự tạo, hãy truyền tham số hoặc chạy task trong scope phù hợp.

Structured concurrency — preview

Ý tưởng: một task tách thành nhiều subtask phải cùng sống trong một scope — subtask nào lỗi hoặc bị hủy thì cả nhóm được dọn dẹp, không để thread rò rỉ.

import java.util.concurrent.*;

public class StructuredDemo {
    static String goiApi(String ten) throws InterruptedException {

        return ten + "@api";

    public static void main() throws Exception {
        try (var scope = StructuredTaskScope.open()) {
            var user = scope.fork(() -> goiApi("user"));
            var order = scope.fork(() -> goiApi("order"));
            scope.join();
            IO.println(user.get() + " + " + order.get());
        }
    }
}

11. Deadlock, livelock & starvation Hay hỏi phỏng vấn Production

Deadlock xảy ra khi hai thread mỗi bên giữ một khóa và chờ khóa của bên kia — vòng tròn chờ vĩnh viễn. Điều kiện Coffman gồm 4 yếu tố, phá một yếu tố là phá được deadlock:

  1. Mutual exclusion — tài nguyên chỉ một thread dùng tại một thời điểm.
  2. Hold and wait — đang giữ khóa này lại chờ khóa khác.
  3. No preemption — không ai cướp được khóa.
  4. Circular wait — có vòng tròn chờ.
public class DeadlockDemo {
    static final Object A = new Object();
    static final Object B = new Object();

    public static void main() throws InterruptedException {
        Thread t1 = new Thread(() -> {
            synchronized (A) {
                try { Thread.sleep(50); } catch (InterruptedException e) { return; }
                synchronized (B) { IO.println("t1 lay duoc B"); }
            }
        }, "t1");
        Thread t2 = new Thread(() -> {
            synchronized (B) {
                try { Thread.sleep(50); } catch (InterruptedException e) { return; }
                synchronized (A) { IO.println("t2 lay duoc A"); }
            }
        }, "t2");
        t1.setDaemon(true);
        t2.setDaemon(true);
        t1.start();
        t2.start();
        Thread.sleep(300);
        IO.println("t1 state: " + t1.getState());
        IO.println("t2 state: " + t2.getState());
        IO.println("ca hai BLOCKED: deadlock");
    }
}
t1 state: BLOCKED
t2 state: BLOCKED
ca hai BLOCKED: deadlock

Trong thực tế chương trình sẽ treo (t1/t2 là daemon ở đây để ví dụ tự thoát). Chẩn đoán bằng thread dump: jcmd <pid> Thread.print hoặc jstack <pid>; JVM còn tự phát hiện và in dòng Found one Java-level deadlock kèm chuỗi chờ.

Cách phòng tránh

  • Thứ tự khóa cố định: mọi nơi đều khóa A rồi B, không nơi nào ngược lại. Đặt tên/so sánh id để sắp thứ tự khóa nếu là object động.
  • tryLock có timeout thay vì chờ vô hạn: không lấy được thì nhả hết và thử lại — phá "hold and wait".
  • Giảm khóa lồng nhau: một khóa duy nhất, hoặc dùng cấu trúc concurrent có sẵn thay vì tự khóa nhiều tầng.
  • Không gọi code "ngoài" khi đang giữ khóa (callback, network, listener) — nguồn deadlock phổ biến ở production.
  • Bất biến & không chia sẻ là cách tốt nhất: message passing/queue thay vì khóa chung.

Livelock: các thread vẫn chạy nhưng cứ "nhường nhau" mãi, không tiến triển (hai người nhường nhau ở hành lang). Starvation: một thread mãi không được cấp tài nguyên vì thread khác luôn giành mất — thường do ưu tiên hoặc khóa không công bằng. Cả hai đều cần thiết kế lại luồng phối hợp, không chỉ thêm timeout.

Producer–Consumer với BlockingQueue

import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;

public class ProducerConsumer {
    public static void main() throws InterruptedException {
        BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(3);

        Thread producer = new Thread(() -> {
            try {
                for (int i = 1; i <= 5; i++) {
                    queue.put(i);
                    IO.println("san xuat: " + i);
                }
                queue.put(-1);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "producer");

        Thread consumer = new Thread(() -> {
            try {
                while (true) {
                    int v = queue.take();
                    if (v == -1) break;
                    IO.println("tieu thu: " + v);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "consumer");

        producer.start();
        consumer.start();
        producer.join();
        consumer.join();
        IO.println("xong");
    }
}

Không nên dùng parallel stream khi: task có IO/DB/HTTP (chặn carrier của common pool, ảnh hưởng toàn bộ ứng dụng); có side-effect (ghi list, tăng biến — race condition); dữ liệu nhỏ (overhead chia việc lớn hơn lợi ích); cần thứ tự (phải dùng forEachOrdered, mất lợi thế); hoặc đang ở trong một parallel stream khác (nested). Muốn đo lợi thật, hãy benchmark bằng JMH — đừng đoán. Với task IO, virtual threads + cấu trúc tuần tự thường tốt hơn.

Liên hệ: Stream API cơ bản và bẫy parallel nằm ở 3.8 Stream API; nguyên tắc chung: đo trước, song song hóa sau.

15. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Process và thread khác nhau thế nào? Java thread chia sẻ gì?
Process là chương trình đang chạy với không gian địa chỉ riêng; thread là đơn vị thực thi trong process. Các thread cùng process chia sẻ heap, static field, code, nhưng mỗi thread có stack riêng (biến local, call frame) và chương trình con. Chính việc chia sẻ heap tạo ra nhu cầu đồng bộ.
Câu 2. start() và run() khác gì? Gọi start() hai lần thì sao?
run() chỉ là lời gọi method bình thường trên thread hiện tại. start() tạo thread mới và JVM gọi run() bên trong nó. Gọi start() lần hai trên cùng thread ném IllegalThreadStateException; còn gọi run() nhiều lần vẫn bình thường.
Câu 3. Kể 6 trạng thái của thread.
NEW, RUNNABLE, BLOCKED (chờ monitor synchronized), WAITING (wait/join/park vô hạn), TIMED_WAITING (sleep/wait/join có thời hạn), TERMINATED. Chú ý RUNNABLE bao gồm cả thread đang chờ IO ở tầng OS — không có trạng thái "blocked on IO" riêng.
Câu 4. Race condition là gì? Vì sao count++ không an toàn?
Race condition là kết quả phụ thuộc thứ tự thực thi không xác định của nhiều thread. count++ gồm đọc – cộng – ghi, không nguyên tử; hai thread có thể cùng đọc giá trị cũ rồi cùng ghi đè (lost update). Sửa: synchronized, Atomic, hoặc không chia sẻ state.
Câu 5. volatile đảm bảo gì? Có thay được synchronized không?
volatile đảm bảo visibility (ghi/đọc đi thẳng bộ nhớ chính, có happens-before giữa lần ghi và lần đọc sau) và chặn reordering quanh nó. Nó không đảm bảo atomicity: volatile count++ vẫn mất cập nhật. Dùng cho cờ hiệu, one-writer-many-readers; không dùng thay khóa cho compound action.
Câu 6. happans-before là gì? Kể vài cặp quy tắc.
Là quan hệ đảm bảo thay đổi bộ nhớ của thao tác A được thread thực hiện B nhìn thấy. Các cặp hay dùng: thứ tự chương trình trong một thread; ghi volatile → đọc volatile sau; unlock monitor → lock monitor sau; start() → code trong thread mới; code trong thread → join() trả về; final field → đọc qua reference được công bố an toàn.
Câu 7. synchronized khóa vào đối tượng nào?
Method instance khóa this; static synchronized khóa object Class; block khóa object trong ngoặc. Nó reentrant (cùng thread khóa lồng được). Đừng khóa String/boxed literal hay object public dùng chung vì dễ deadlock và ảnh hưởng ngoài phạm vi kiểm soát.
Câu 8. synchronized và ReentrantLock khác nhau gì? Khi nào chọn Lock?
Lock linh hoạt hơn: tryLock (không chờ hoặc timeout), lockInterruptibly, fairness, nhiều Condition. Bù lại phải nhả tay trong finally. Mặc định dùng synchronized; chuyển sang Lock khi cần timeout/ngắt/công bằng hoặc phá deadlock.

Nâng cao (Junior+)

Câu 9. CAS là gì? Vì sao Atomic nhanh hơn synchronized?
CAS (compare-and-set) là lệnh phần cứng: "nếu giá trị còn là A thì đổi thành B, ngược lại báo thất bại". Atomic dùng vòng lặp CAS nên không cần khóa hệ điều hành, giảm chi phí context switch — nhanh hơn khi contention thấp. Contention cao thì CAS quay vòng nhiều; lúc đó LongAdder hoặc khóa có thể tốt hơn.
Câu 10. ABA problem là gì?
Giá trị đổi A → B → A khiến CAS tưởng "chưa từng thay đổi" và thực hiện nhầm. Với dữ liệu phức tạp (stack/queue lock-free), dùng AtomicStampedReference để kèm số phiên bản, hoặc dùng GC + immutable node như các collection sẵn có.
Câu 11. Vì sao không nên dùng Executors.newFixedThreadPool trong production?
Nó dùng queue không giới hạn: khi task đến nhanh hơn xử lý, queue phình đến OOM và thời gian chờ tăng vô hạn mà không có tín hiệu. Production nên tự tạo ThreadPoolExecutor với queue có biên và RejectedExecutionHandler phù hợp (fail fast hoặc CallerRuns để backpressure).
Câu 12. submit() khác execute() thế nào về exception?
execute(Runnable) ném exception ra UncaughtExceptionHandler (in stderr, thread có thể chết). submit(...) bọc exception vào Future — nếu không gọi get() thì lỗi bị nuốt im lặng. Đây là lỗi production rất hay gặp khi submit mà không theo dõi Future.
Câu 13. Kích thước thread pool nên chọn thế nào?
CPU-bound: ~ số core. IO-bound: cores × (1 + wait/compute), rồi đo và chỉnh. Tuyệt đối không chọn số "to cho chắc": quá nhiều thread gây context switch và OOM. Với blocking IO thuần, virtual thread thường thay thế công thức này tốt hơn.
Câu 14. Deadlock là gì và phòng tránh thế nào?
Hai hay nhiều thread chờ khóa của nhau theo vòng tròn. Phòng tránh: khóa theo thứ tự cố định; dùng tryLock(timeout); giảm khóa lồng nhau; không gọi callback/IO khi đang giữ khóa; ưu tiên immutable/không chia sẻ. Chẩn đoán bằng thread dump (jcmd Thread.print/jstack).
Câu 15. ConcurrentHashMap khác HashMap và synchronizedMap thế nào?
ConcurrentHashMap an toàn đa luồng bằng khóa mịn/CAS, không nhận null, iterator weakly consistent (không ném CME) và các thao tác ghép như computeIfAbsent/merge là atomic. Collections.synchronizedMap chỉ khóa từng method — thao tác ghép vẫn race và duyệt vẫn phải tự đồng bộ.
Câu 16. Future vs CompletableFuture?
Future chỉ cho get() blocking và không ghép nối được. CompletableFuture hỗ trợ pipeline phi blocking: thenApply/thenCompose/thenCombine, allOf/anyOf, xử lý lỗi exceptionally/handle, timeout orTimeout. Lưu ý mặc định chạy trên common ForkJoinPool — truyền executor riêng cho task blocking.

Production

Câu 17. Virtual thread khác platform thread? Khi nào dùng?
Virtual thread do JVM lập lịch, cực nhẹ (hàng triệu được), tự nhường carrier khi blocking IO. Dùng cho workload blocking IO (HTTP, DB, file) để thay thread pool lớn. Không có lợi cho CPU-bound; không pool virtual thread; trước JDK 24 synchronized gây pinning (JEP 491 đã sửa ở JDK 24+), còn pinning khi chạy native/JNI/FFM.
Câu 18. ScopedValue khác ThreadLocal ở đâu?
ScopedValue bất biến, giới hạn trong một scope (where(...).run(...)), tự giải phóng khi hết scope và thân thiện với virtual thread (không cần copy hàng triệu bản). ThreadLocal mutable, gắn vòng đời thread, phải remove() trên thread pool. ScopedValue chỉ chia sẻ đọc; muốn truyền vào thread tách rời phải dùng StructuredTaskScope hoặc tham số.
Câu 19. Vì sao iterator của ConcurrentHashMap không ném ConcurrentModificationException?
Nó là weakly consistent: hoạt động trên ảnh chụp tại thời điểm duyệt, có thể thấy hoặc không thấy thay đổi đồng thời, nhưng không bao giờ ném CME và không bị kẹt. Ngược lại, fail-fast iterator của HashMap phát hiện modification count thay đổi và ném CME. Không có nghĩa là size() chính xác tức thời — size() là ước lượng.
Câu 20. Parallel stream dùng chung gì, khi nào nên tránh?
Dùng common ForkJoinPool (mặc định ~ số core - 1). Tránh khi: task blocking IO (chiếm carrier, ảnh hưởng cả app), có side-effect/state chia sẻ, dữ liệu nhỏ, cần đảm bảo thứ tự, hoặc nested parallel. Chỉ dùng cho CPU-bound thuần túy với dữ liệu lớn và đã benchmark bằng JMH.

16. Bài tập đoán output

Đoán kết quả (hoặc kết luận "không xác định") trước khi mở đáp án. Các bài race/thread có thể chạy ra kết quả khác nhau — mục tiêu là giải thích vì sao.

Bài 1. Hai thread cùng tăng một biến AtomicInteger 1000 lần mỗi bên. Kết quả?

Luôn bằng 2000. incrementAndGet() là một thao tác CAS nguyên tử; không có lost update.

Bài 2. Hai thread cùng tăng một biến volatile int 1000 lần mỗi bên. Kết quả?

Thường nhỏ hơn 2000 và thay đổi mỗi lần chạy. volatile chỉ đảm bảo visibility, không đảm bảo atomicity của read-modify-write. Sửa bằng AtomicInteger hoặc khóa.

Bài 3. static synchronized và method synchronized thường có khóa cùng nhau không?

Không. static synchronized khóa object Class, còn method instance khóa this — hai monitor khác nhau nên hai thread có thể vào đồng thời một bên static, một bên instance.

Bài 4. ReentrantLock được khóa hai lần bởi cùng thread, chỉ unlock() một lần. Lock còn bị giữ không?

Còn. Lock reentrant đếm số lần giữ; phải unlock() đúng hai lần. Thiếu một lần thì thread khác không bao giờ vào được.

Bài 5. Task ném exception, gọi submit() rồi không bao giờ get(). Điều gì xảy ra?

Exception nằm im trong Future — không log, không ai biết task đã thất bại. Đây là lỗi nuốt exception kinh điển. execute() thì in stack trace qua UncaughtExceptionHandler.

Bài 6. Future.get(50, MILLISECONDS) khi task cần 200ms — task có bị hủy không?

Không. get chỉ ném TimeoutException; task vẫn chạy tới hết. Muốn hủy phải gọi future.cancel(true) và task phải hợp tác với interrupt.

Bài 7. IntStream.rangeClosed(1, 5).parallel().forEach(...) in theo thứ tự nào?

Không xác định — có thể là 3 2 4 1 5 hoặc bất kỳ hoán vị nào (một lần chạy của tài liệu ra 3 2 4 1 5). Muốn đúng thứ tự dùng forEachOrdered (đánh đổi mất một phần song song).

Bài 8. Thread pool 1 thread, chạy task A submit task B rồi A.get() trên B. Chuyện gì xảy ra?

Deadlock: B nằm trong queue chờ thread duy nhất, mà thread đó (đang chạy A) lại chờ B. Không bao giờ xong. Tránh chờ task con bên trong task cha cùng pool; dùng thenCompose/tách pool hoặc thiết kế lại.

Bài 9. ThreadLocal set ở request 1, request 2 chạy lại trên cùng thread pool — đọc được gì?

Vẫn thấy giá trị của request 1 nếu không remove(), vì thread được tái sử dụng. Vừa rò rỉ bộ nhớ vừa có thể lộ dữ liệu người dùng. Luôn try/finally { tl.remove(); }.

Bài 10. Hai thread khóa A rồi B, và B rồi A. Kết quả?

Deadlock nếu mỗi bên giữ được khóa đầu trước khi xin khóa thứ hai (như ví dụ mục 11: cả hai BLOCKED). Sửa bằng thứ tự khóa cố định hoặc tryLock timeout.

Bài 11. ConcurrentHashMap.computeIfAbsent có thread-safe không? Còn get() rồi put()?

computeIfAbsent atomic — chỉ một thread tính giá trị cho mỗi key. Còn cặp get() + put() là check-then-act, hai thread có thể cùng thấy null và tạo/cập nhật chồng nhau. Dùng putIfAbsent/computeIfAbsent/merge.

Bài 12. Trên JDK 25, virtual thread gọi synchronized rồi blocking lâu có làm pinning carrier không?

Không còn từ JDK 24 (JEP 491) — monitor không còn ghim virtual thread. Pinning hiện chỉ xảy ra khi chạy native/JNI/FFM (hoặc class initializer) trong thân virtual thread. Trên JDK 21–23 thì có, nên tài liệu cũ thường khuyên thay bằng ReentrantLock.
