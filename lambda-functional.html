Lambda & Functional interfaces — hành vi như dữ liệu

Lambda (Java 8, 2014) cho phép bạn truyền hành vi như một giá trị: ds.sort(Comparator.comparingInt(String::length)) thay cho cả một class. Lambda không đứng một mình — nó luôn là implementation của một functional interface (interface có đúng một abstract method). Nắm chắc cặp đôi này là điều kiện để hiểu Comparator, callback, xử lý sự kiện, Optional và Stream API. Trang này đi từ anonymous class, SAM, target typing, closure tới invokedynamic và các bẫy production — mọi output đều chạy thật trên JDK 25.

2. Từ anonymous class đến lambda Hay hỏi phỏng vấn

Trước Java 8, muốn truyền hành vi vào method, bạn phải viết một class (hoặc anonymous class) implement interface. Cùng một logic "chuẩn hoá chuỗi" dưới đây được viết ba cách: anonymous class → lambda → method reference. Chạy java BaCachDemo.java:

@FunctionalInterface
interface ChuyenDoi {
    String ap(String s);
}

public class BaCachDemo {
    static String chuanHoa(String s) {
        return s.trim().toUpperCase();
    }

    static void inKetQua(String nhan, ChuyenDoi cd, String input) {
        IO.println(nhan + ": " + cd.ap(input));
    }

    public static void main() {
        inKetQua("anonymous ", new ChuyenDoi() {
            @Override public String ap(String s) {
                return s.trim().toUpperCase();
            }
        }, "  java  ");

        inKetQua("lambda    ", s -> s.trim().toUpperCase(), "  java  ");

        inKetQua("method ref", BaCachDemo::chuanHoa, "  java  ");
    }
}

Lambda là gì? Là biểu thức (thamSo) -> than đại diện cho implementation của một functional interface. Nó không phải "function pointer" hay "hàm tự do": Java vẫn là ngôn ngữ nominal — muốn truyền hành vi, phải có một interface làm hợp đồng. Vì vậy mỗi lambda luôn gắn với một target type (mục 5).

Method reference không phải "cú pháp thứ ba của lambda" mà là dạng viết tắt khi thân lambda chỉ chuyển tiếp tham số cho một method. Ba cách trên là ba cách tạo implementation — không có cách nào tạo ra method mới ngoài class.
Về instance: lambda có capture (dùng biến ngoài hoặc this) tạo object mỗi lần đi qua biểu thức; lambda không capture thường được JVM cache lại. Bound reference obj::method cũng là dạng capture (giữ obj), còn TenClass::staticMethod và unbound TenClass::instanceMethod không giữ object nào.

3. Functional interface & @FunctionalInterface Hay hỏi phỏng vấn Junior+

Functional interface (giao diện chức năng) là interface có đúng một abstract method — gọi là SAM (Single Abstract Method). Chính SAM này là "kiểu" của lambda. Đã học ở 2.5 Abstract vs Interface — mục 9; dưới đây là những điểm mà mục này khai thác sâu.

Annotation @FunctionalInterface là tuỳ chọn, nhưng nên dùng: nó biến việc "lỡ thêm abstract method thứ hai" thành lỗi compile ngay lập tức và tài liệu hoá ý định thiết kế. Interface con của một functional interface mà không thêm abstract method mới vẫn là functional interface và vẫn gắn được annotation:

@FunctionalInterface
interface ChuyenDoi {
    String ap(String s);
}

// Khong them abstract method moi - SAM duoc ke thua
@FunctionalInterface
interface ChuyenDoiHoa extends ChuyenDoi {
}

public class FunctionalChildDemo {
    public static void main() {
        ChuyenDoiHoa cd = s -> s.toUpperCase();
        IO.println(cd.ap("java"));
    }
}
JAVA

Những thứ không tính vào SAM (vì vậy interface vẫn functional):

  • default method — interface vẫn functional dù có bao nhiêu default (xem default method). Predicate.and, Function.andThen chính là các default method này.
  • static và private method (Java 9+).
  • Abstract method trùng chữ ký với public method của Object như equals(Object), hashCode(). Nhờ đó Comparator<T> — khai báo cả compare lẫn equals — vẫn là functional interface.

Hai lỗi compiler kinh điển khi interface không còn SAM. Lỗi thứ nhất — annotation phát hiện sớm:

Lỗi thứ hai — khi gán lambda, thông báo nhắc thẳng "không phải functional interface":

Lambda chỉ implement được interface một abstract method. Cần hai method trở lên thì phải dùng anonymous class, class có tên, hoặc tách thành hai interface nhỏ (Interface Segregation — mục 10). Không thể "ép" bằng cast: cast chỉ chọn target type, không làm interface hết hai method.

Generic chỉ chứa reference type, nên Predicate<Integer> phải boxing/unboxing mỗi lần gọi. Với vòng lặp nóng hoặc IntStream, JDK có sẵn các biến thể primitive:

4.2 Biến checked exception thành unchecked

Vì Supplier/Function/Consumer không khai báo checked exception, lambda có gọi IOException… sẽ không compile. Helper "unchecked" bọc lại thành RuntimeException (giữ nguyên cause) là mẫu rất phổ biến khi làm việc với file/IO trong pipeline:

import java.io.IOException;
import java.util.function.Supplier;

@FunctionalInterface
interface Thunk<T> {
    T get() throws Exception;
}

static <T> Supplier<T> unchecked(Thunk<T> thunk) {
    return () -> {
        try {
            return thunk.get();
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    };
}

void main() {
    Supplier<String> ok = unchecked(() -> "gia tri");
    IO.println(ok.get());

    Supplier<String> loi = unchecked(() -> {
        throw new IOException("mat ket noi");
    });
    try {
        loi.get();
    } catch (RuntimeException e) {
        IO.println(e.getClass().getSimpleName() + " <- "
                + e.getCause().getClass().getSimpleName() + ": " + e.getCause().getMessage());
    }
}

Chỉ dùng unchecked ở biên hệ thống (đọc file, gọi API) nơi bạn kiểm soát ngữ cảnh; nó làm mất kiểm tra checked ở compile nên đừng lạm dụng. Ngược lại, chọn Callable khi SAM có khai báo checked exception — như snippet phía trên.

5.1 Target typing — lambda không có kiểu độc lập

Cùng một lambda có thể mang nhiều nghĩa khác nhau tuỳ ngữ cảnh. Trình biên dịch nhìn target type (kiểu bên trái phép gán, kiểu tham số method, kiểu trả về) để quyết định SAM nào được implement — cơ chế này gọi là target typing:

import java.util.function.Function;
import java.util.function.IntUnaryOperator;

void main() {
    // Hai lambda giong het nhau ve chu, chi khac target type
    IntUnaryOperator u = x -> x + 1;              // int -> int
    Function<Integer, Integer> f = x -> x + 1;    // Integer -> Integer
    IO.println(u.applyAsInt(4));                  // 5
    IO.println(f.apply(4));                       // 5
    IO.println(u.getClass() == f.getClass());     // false
}

false

Cùng một thân x -> x + 1 nhưng u là implementation của IntUnaryOperator (không boxing), còn f là của Function<Integer,Integer> (có boxing) — hai class runtime khác nhau. Lambda không có kiểu riêng, "nghĩa" của nó do target type quyết định.

Vì cần target type, var một mình không đủ ngữ cảnh — đây là lỗi rất hay gặp khi viết nhanh:

Sửa bằng cách khai báo kiểu functional interface tường minh: Function<String, Integer> f = s -> s.length();. Cũng vì target typing, hai overload mà cả hai đều "vừa khớp" lambda sẽ gây mơ hồ — đặc biệt khi thân lambda là một statement expression như lời gọi method void:

5.2 Lambda không tạo scope mới — và this trỏ object bao ngoài

Thân lambda không phải một scope mới cho tên biến: tham số lambda dùng chung "không gian tên" với method bao ngoài, nên không được trùng tên với biến local/parameter ở ngoài:

ScopeLambdaErr.java:7: error: variable ten is already defined in method main()
            String ten = "lambda";
                   ^
1 error

Còn this trong lambda là object bao ngoài (lexical this), khác hẳn anonymous class — nơi this là object vô danh:

public class ThisLambdaDemo {
    String ten = "outer";

    void chayLambda() {
        Runnable r = () -> IO.println("lambda this    : " + this.ten);
        r.run();
    }

    void chayAnon() {
        Runnable r = new Runnable() {
            String ten = "inner";

            @Override public void run() {
                IO.println("anonymous this : " + this.ten);
                IO.println("Outer.this.ten : " + ThisLambdaDemo.this.ten);
            }
        };
        r.run();
    }

    public static void main() {
        ThisLambdaDemo demo = new ThisLambdaDemo();
        demo.chayLambda();
        demo.chayAnon();
    }
}

anonymous this : inner

Một vài luật đáng nhớ khác của thân lambda:

  • return trong block lambda là return khỏi lambda, không phải khỏi method bao ngoài.
  • Không dùng được break/continue trỏ ra vòng lặp bên ngoài lambda; muốn điều khiển vòng lặp thì đặt lambda trong vòng lặp.
  • Lambda không có tham số kiểu generic riêng (không viết được <T> (T x) -> ...); generic hóa bằng method bao ngoài hoặc target type generic.
  • Checked exception chỉ được ném nếu SAM khai báo (Callable.call được, Runnable.run thì không).

6. Closure & effectively final Hay hỏi phỏng vấn

Lambda "đóng" (closure) các biến từ scope bao ngoài: tham số method, biến local, field của this, static field. Với biến local/parameter, JLS bắt buộc chúng phải final hoặc effectively final — nghĩa là được gán đúng một lần và không đổi giá trị sau đó (xem Biến trong Java — mục 10 final chuyên sâu). Gán lại một lần cũng đủ vi phạm:

6.1 Muốn "biến đổi" trong lambda thì làm sao?

Ba cách thực dụng, xếp theo mức độ khuyến khích:

  1. Thiết kế lại — trả giá trị từ lambda (Supplier/Function) thay vì side effect; gom state vào một object/record có field.

9.1 Strategy bằng lambda — thay cả một class

Strategy là pattern đổi thuật toán lúc chạy. Nếu interface chỉ một method, mỗi "chiến lược" chỉ là một lambda — không cần class con, không cần factory phức tạp (xem 2.4 Polymorphism — mục 8 và 2.8 SOLID & Patterns — mục 10):

record DonHang(String ma, long tongTien) {

@FunctionalInterface

Callback chỉ là một functional interface được gọi lại sau này; danh sách listener chỉ là List<Consumer<T>>. Nhờ lambda, đăng ký listener gọn hơn hẳn anonymous class:

import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;

public class CallbackDemo {
    static final List<Consumer<String>> langNghe = new ArrayList<>();

        langNghe.add(c);

    static void phatSuKien(String ma) {
        for (Consumer<String> c : langNghe) {
            c.accept(ma);
        }

    public static void main() {
        dangKy(ma -> IO.println("email: da gui xac nhan " + ma));
        dangKy(ma -> IO.println("sms  : da gui " + ma));

11. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Lambda expression là gì? Vì sao Java cần functional interface đi kèm?
Lambda là biểu thức (thamSo) -> than biểu diễn implementation của một functional interface. Java là ngôn ngữ nominal: muốn truyền hành vi phải có một kiểu có tên làm hợp đồng, nên lambda luôn cần target type là functional interface. Nó không phải hàm tự do như JavaScript.
Câu 2. Functional interface là gì? @FunctionalInterface có bắt buộc không? Cách đếm abstract method?
Là interface có đúng một abstract method (SAM). Annotation không bắt buộc — interface một abstract method vẫn dùng lambda được — nhưng nên ghi để compiler chặn khi lỡ thêm method thứ hai. Không tính vào SAM: default, static, private method, và abstract method trùng public method của Object (equals, hashCode, toString). Vì vậy Comparator (compare + equals) vẫn functional.
Câu 3. Lambda khác anonymous class ở những điểm nào?
Lambda ngắn hơn; không sinh file class riêng lúc compile (dùng invokedynamic sinh lúc runtime, thường nhẹ hơn); this trỏ object bao ngoài; không có field/state riêng; không tạo scope mới cho tên biến; chỉ implement được đúng một abstract method. Anonymous class phù hợp khi cần state riêng, nhiều method, hoặc implement abstract class.
Câu 4. Vì sao biến local capture phải "effectively final"? Muốn thay đổi giá trị trong lambda thì làm sao?
Lambda capture giá trị của biến local tại thời điểm tạo; biến local nằm trên stack và có thể biến mất khi method kết thúc. Nếu cho phép gán lại, lambda và biến gốc sẽ lệch giá trị, gây bug khó truy. Vì vậy JLS yêu cầu final hoặc effectively final (gán đúng một lần, không đổi). Muốn thay đổi: dùng field, mảng một phần tử int[] dem = {0};, hoặc AtomicInteger; tốt nhất là thiết kế lại để lambda trả giá trị thay vì side effect.
Câu 5. Lambda đọc biến local và field khác nhau thế nào?
Local được capture theo giá trị tại lúc tạo lambda (không đổi được vì effectively final). Field/static không bị ràng buộc đó: lambda giữ this (hoặc class) và đọc field tại thời điểm gọi. Ví dụ: local base = 10 rồi đổi field heSo thành 10 — lambda dùng base vẫn ra 11, còn n * heSo ra 50.
Câu 6. Lambda có tạo scope mới không? Có được khai báo biến trùng tên local bên ngoài không?
Không tạo scope mới cho tên biến. Tham số lambda và biến local trong thân lambda dùng chung không gian tên với method bao ngoài, nên khai báo trùng tên biến local/parameter bên ngoài là lỗi variable ... is already defined. Anonymous class thì ngược lại: có scope riêng và được phép shadow.
Câu 7. this trong lambda trỏ vào đâu? Trong static context thì sao?
Trỏ vào object bao ngoài (lexical this) — cùng object với method chứa lambda. Anonymous class dùng this cho chính object vô danh, muốn outer phải viết TenClass.this. Nếu lambda được tạo trong static context thì không có this; chỉ dùng được static member.
Câu 8. Target typing là gì? Vì sao var f = x -> x + 1; không compile? Gặp "reference to ... is ambiguous" thì sửa sao?
Target typing là việc kiểu của lambda được suy ra từ ngữ cảnh (biến được gán, tham số method, kiểu trả về). var không cung cấp ngữ cảnh nên javac báo "lambda expression needs an explicit target-type"; sửa bằng cách khai báo kiểu functional interface tường minh. Ambiguous xảy ra khi hai overload đều vừa khớp lambda — đặc biệt khi thân lambda là statement expression (s -> IO.println(s) khớp cả Consumer lẫn Function); sửa bằng cast target type (Consumer<String>) s -> IO.println(s), hoặc tốt hơn là đổi tên/tách method để tránh overload mơ hồ.

Nâng cao (Junior+)

Câu 9. Kể 4 loại method reference. Khi nào dùng thay lambda?
(1) static: Integer::parseInt; (2) instance của object cụ thể: System.out::println; (3) instance của tham số tuỳ ý: String::length (tham số đầu thành receiver); (4) constructor: ArrayList::new. Dùng khi thân lambda chỉ chuyển tiếp đúng một method, không thêm logic — method reference ngắn và thể hiện ý định rõ hơn. Còn super::method là dạng bổ sung ít gặp.
Câu 10. Phân biệt Runnable, Callable, Supplier.
Runnable.run(): void — không tham số, không kết quả, không checked exception. Callable<V>.call(): V — không tham số, có kết quả, được ném checked exception (dùng với ExecutorService.submit). Supplier<T>.get(): T — không tham số, có kết quả, không checked exception (dùng cho lazy value, orElseGet, factory).
Câu 11. Phân biệt Function vs UnaryOperator, Predicate vs Consumer?
UnaryOperator<T> là Function<T,T> — vào/ra cùng kiểu. BinaryOperator<T> là BiFunction<T,T,T>. Predicate.test trả boolean; Consumer.accept trả void (chỉ side effect). Chọn interface sát nghĩa nhất để người đọc và framework hiểu ý định.
Câu 12. Primitive functional interface (IntPredicate, ToIntFunction…) để làm gì?
Tránh boxing/unboxing cho int/long/double. Generic không nhận primitive nên Predicate<Integer> phải bọc/mở hộp mỗi lần gọi — tốn kém trong vòng lặp nóng hoặc Stream primitive. Bản primitive có tên method riêng (applyAsInt, getAsInt) và không compose được với bản generic.
Câu 13. Predicate.and và Function.andThen khác gì? Có short-circuit không?
Predicate.and/or short-circuit như &&/||: vế phải không chạy nếu vế trái đã quyết định. Function.andThen chạy hàm này rồi hàm kia, không có khái niệm short-circuit; compose là bản ngược — chạy tham số trước. Có thể verify short-circuit bằng cách đặt side-effect (in log) trong từng predicate.
Câu 14. Lambda có chậm không? invokedynamic và LambdaMetafactory hoạt động thế nào?
javac biến thân lambda thành private method và phát invokedynamic; JVM gọi bootstrap LambdaMetafactory để tạo implementation một lần cho mỗi call site (link), sau đó tái sử dụng. Lambda không capture thường được cache; lambda capture tạo object (có thể được JIT loại bỏ nhờ escape analysis). Sau khi JIT inline, chi phí gần như gọi method thường — lambda không chậm như nhiều người tưởng. Chỉ cân nhắc trong hot path tạo lambda capture với tần suất cực lớn.
Câu 15. Có serialize lambda được không? Cần cảnh báo gì?
Được, nếu target type kế thừa Serializable (hoặc cast giao (Runnable & Serializable)). Nhưng: captured value phải serializable, nếu không sẽ NotSerializableException lúc chạy; class sinh ra là hidden class (từ Java 15) tên dạng Foo$$Lambda/0x... — không ổn định giữa các lần chạy/build, không xuất hiện trên classpath nên deserialize có thể thất bại; code không portable. Vì vậy đừng lưu lambda vào DB/session lâu dài — dùng class có tên hoặc enum cho chiến lược cần bền vững.
Câu 16. Lambda tự gọi chính nó (đệ quy) được không? Làm sao gọi code ném checked exception trong Supplier?
Đệ quy được nhờ holder mảng một phần tử: IntUnaryOperator[] f = new IntUnaryOperator[1]; f[0] = n -> ... f[0].applyAsInt(n - 1) ... — mảng effectively final nhưng phần tử gán được. Vẫn chịu giới hạn stack. Với checked exception: Supplier/Function không khai báo checked nên phải bọc bằng helper unchecked(() -> ...) trả RuntimeException giữ cause; nếu muốn ném thẳng checked hãy dùng Callable (SAM có throws Exception).
Câu 17. Class sinh ra cho lambda tên gì? Vì sao stack trace khó đọc và cách khắc phục?
Từ Java 15 nó là hidden class, tên dạng TenClass$$Lambda/0x... (các JDK 15–22 từng in thêm số thứ tự $N): không load được bằng tên, không có trên classpath, không ổn định giữa các lần chạy. Stack trace hiện frame private lambda$main$0 thay vì code bạn viết. Khắc phục: tách thân lambda thành method có tên rồi dùng method reference (this::tinhPhi), log kèm tên nghiệp vụ; kiểm tra bằng getClass().isHidden() và getName().contains("$$Lambda"). Không dùng tên class lambda cho logic.

  • Kể tên được 6 interface lõi và nói khi nào dùng bản primitive.
  • Giải thích invokedynamic ở mức phỏng vấn: link một lần, cache, capture tạo object.
  • Nêu được cảnh báo serializable lambda (captured value + hidden class $$Lambda không ổn định).
  • Viết được lambda đệ quy qua holder và helper unchecked cho checked exception.
  • Biết debug lambda: hidden class, frame lambda$..., mẹo tách method có tên.
  • Đọc được 6 thông báo lỗi trong bảng phía trên và biết cách sửa từng lỗi.
