1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Phân biệt hai khái niệm hay bị gộp chung:

  • Design principle (nguyên tắc thiết kế) — lời khuyên bậc cao, không có code cụ thể. SOLID, DRY, KISS, YAGNI là ví dụ. Bạn "hiểu và áp dụng", không "cài đặt".
  • Design pattern (mẫu thiết kế) — giải pháp cụ thể, đã được đặt tên, mô tả quan hệ giữa các class/object để giải một vấn đề lặp lại. Singleton, Factory, Builder, Strategy, Observer... là ví dụ. Bạn "nhận diện và chọn dùng".

Bộ pattern nổi tiếng nhất là của "Gang of Four" (GoF, 1994) với 23 mẫu, chia làm 3 nhóm. Không cần học hết 23 — cần biết nhóm nào tồn tại để tra cứu:

NhómGiải quyết việc gìVí dụ tiêu biểu
Creational (khởi tạo)Cách tạo object linh hoạt, che giấu chi tiết khởi tạoSingleton, Factory Method, Abstract Factory, Builder, Prototype
Structural (cấu trúc)Ghép các object/class thành cấu trúc lớn hơnAdapter, Decorator, Proxy, Facade, Composite
Behavioral (hành vi)Cách object giao tiếp, phân chia trách nhiệm, thuật toánStrategy, Observer, Template Method, Chain of Responsibility, Command
Pattern là công cụ, không phải mục tiêu. Lỗi phổ biến của người mới học pattern là thấy vấn đề nào cũng muốn "dán" pattern vào: thêm interface khi chỉ có một implementation, thêm factory cho một constructor, thêm abstract class cho hai class chưa chắc thay đổi. Kết quả là code khó đọc hơn, nhiều file hơn, mà chẳng giải quyết vấn đề thực tế nào. Nguyên tắc thực dụng: chỉ dùng pattern khi bạn đã thấy vấn đề nó giải quyết đang thật sự xảy ra (rule of three — đến lần thứ ba lặp lại mới trừu tượng hoá).

Mức độ bắt buộc của chủ đề 2.8 (phỏng vấn: rất cao · production: bắt buộc):

  • Phải làm được — nhận diện và sửa vi phạm SRP, OCP, LSP, ISP, DIP ở đoạn code nhỏ; viết singleton bằng enum và holder; viết builder cho lớp nhiều tham số; dùng strategy qua interface + lambda; viết simple factory; dùng observer/listener; giải thích constructor injection và lợi ích test.
  • Phải hiểu — vì sao DIP dẫn tới testability; vì sao LSP/ISP là về hợp đồng chứ không phải cú pháp; vì sao singleton bị coi là anti-pattern; vì sao over-engineering còn tệ hơn thiếu pattern.
  • Nhận biết — pattern mà Spring/JDK dùng sẵn: @Bean (Factory), AOP (Proxy/Decorator), JdbcTemplate (Template Method), ApplicationEvent (Observer), Comparator (Strategy); abstract factory, prototype, visitor chỉ cần biết tên + ý tưởng.

Cách học hiệu quả nhất:

  1. Với mỗi nguyên tắc: đọc định nghĩa → đoán xem đoạn code mẫu vi phạm ở đâu → đọc cách sửa. Đoán trước, xem sau.
  2. Làm mục Bài tập đoán output trước, chỉ mở đáp án sau khi đã đoán.
  3. Tự hỏi "đoạn code này có mùi gì?" thay vì "đoạn code này nên dùng pattern gì?". Pattern là câu trả lời, vấn đề mới là câu hỏi.
  4. Ôn nhanh bảng trong Cheat sheet trước buổi phỏng vấn.
Ví dụ dùng IO.println(...) — cách viết gọn của JDK 25 (JEP 512), tương đương System.out.println(...). Các file không khai báo class bao ngoài là compact source file: lưu thành TenFile.java rồi chạy java TenFile.java là được.

Middleware của Express là ví dụ dễ thấy nhất của Chain of Responsibility — chạy thật bằng Node v22:

// middleware chain ~ chain of responsibility
const middlewares = [
  (req, next) => { console.log("1. log:", req.url); next(); },
  (req, next) => { console.log("2. xac thuc nguoi dung"); next(); },
  (req, next) => { console.log("3. xu ly don hang"); },
];

function chayChuoi(req) {
  let i = 0;
  function next() {
    if (i < middlewares.length) middlewares[i++](req, next);
  }
  next();
}

chayChuoi({ url: "/don-hang" });
// 1. log: /don-hang
// 2. xac thuc nguoi dung
// 3. xu ly don hang

Còn module cache của Node chính là singleton: hai lần require cùng module trả về đúng một object, nên state chia sẻ với nhau:

// counter.cjs
let count = 0;
module.exports = {
  tang() { return ++count; },
  dem()  { return count; },
};

// main.cjs
const a = require("./counter.cjs");
const b = require("./counter.cjs");
console.log("a === b:", a === b);  // a === b: true
a.tang();
console.log("b.dem():", b.dem());  // b.dem(): 1
Điểm khác biệt lớn: Node "tha" cho bạn dùng object/closure/hàm tự do, còn Java ép mọi thứ vào class/interface — nhờ vậy pattern hiện ra rõ ràng hơn trong code Java, nhưng cũng dễ bị lạm dụng hơn. Đừng biến Java thành JavaScript bằng cách nhồi mọi thứ vào static.

2. S — Single Responsibility Hay hỏi phỏng vấn

Phát biểu: một class chỉ nên có một lý do để thay đổi (one reason to change) — nghĩa là chỉ phục vụ một "trục thay đổi" (axis of change) hoặc một nhóm người quan tâm (stakeholder).

Ví dụ đời thường: một nhân viên vừa bán hàng, vừa giao hàng, vừa làm kế toán. Mỗi khi chính sách giao hàng đổi, chính sách thuế đổi, hay quy trình bán đổi — đều phải sửa cùng một người. Tách vai ra thì mỗi thay đổi chỉ ảnh hưởng đúng chỗ của nó.

Đoạn code sau vi phạm SRP vì class Order đảm nhận 3 việc: tính tiền (nghiệp vụ), gửi hóa đơn (thông báo) và ghi log (hạ tầng):

import java.math.BigDecimal;

public class Order {
    private final BigDecimal donGia;
    private final int soLuong;
    private final String email;

    Order(BigDecimal donGia, int soLuong, String email) {
        this.donGia = donGia;
        this.soLuong = soLuong;
        this.email = email;
    }

    BigDecimal xuLyDon() {
        BigDecimal tong = donGia.multiply(BigDecimal.valueOf(soLuong));
        IO.println("Gui hoa don toi " + email + ": " + tong);    // Gui hoa don toi an@example.com: 240000
        IO.println("LOG: don hang cua " + email + " = " + tong);  // LOG: don hang cua an@example.com = 240000
        return tong;
    }

    public static void main() {
        Order don = new Order(new BigDecimal("120000"), 2, "an@example.com");
        IO.println("Tong tien: " + don.xuLyDon());                // Tong tien: 240000
    }
}

Ba lý do để Order phải sửa: quy tắc tính tiền đổi, mẫu email đổi, định dạng log đổi. Mỗi lần như vậy đều phải mở lại class nghiệp vụ và chạy lại toàn bộ test của nó — dù nghiệp vụ không hề sai.

Tách ra: Order chỉ còn tính tiền, không in ấn gì cả. Việc gửi thông báo nhường cho thành phần chuyên trách (mục Factory sẽ có NotificationFactory), việc ghi log nhường cho logging framework. Caller ghép chúng lại:

import java.math.BigDecimal;

public class Order {
    private final BigDecimal donGia;
    private final int soLuong;

    Order(BigDecimal donGia, int soLuong) {
        this.donGia = donGia;
        this.soLuong = soLuong;
    }

    BigDecimal tinhTien() {
        return donGia.multiply(BigDecimal.valueOf(soLuong));
    }

    public static void main() {
        Order don = new Order(new BigDecimal("120000"), 2);
        BigDecimal tong = don.tinhTien();
        IO.println("Tong tien: " + tong);  // Tong tien: 240000
    }
}

Hiểu đúng, kẻo cực đoan: SRP không có nghĩa "mỗi class một method". Một class có 10 method vẫn đúng SRP nếu tất cả cùng phục vụ một trục thay đổi (ví dụ Order có tinhTien, themSanPham, apDungCoupon đều là nghiệp vụ đơn hàng). Tiêu chí thực dụng: mô tả class bằng một câu không có chữ "và". Nếu phải viết "class này tính tiền và gửi email và ghi log", hãy tách.

Đừng tách class chỉ để "cho đẹp". Tách quá sớm cũng là over-engineering: mỗi class nhỏ thêm một file, một chỗ phải điều hướng khi debug. Tách khi lý do thay đổi thứ hai thực sự xuất hiện.

3. O — Open/Closed Hay hỏi phỏng vấn

Phát biểu: module nên mở cho việc mở rộng (open for extension) và đóng với việc sửa đổi (closed for modification) — thêm tính năng mới bằng cách thêm code mới, hạn chế tối đa sửa code cũ đã chạy ổn và đã có test.

Đoạn code tính chiết khấu theo loại khách sau sẽ phải sửa mỗi khi có loại khách mới — mỗi lần sửa lại có nguy cơ làm hỏng nhánh cũ:

import java.math.BigDecimal;

public class Order {
    static BigDecimal apDungChietKhau(BigDecimal tong, String loaiKhach) {
        if (loaiKhach.equals("vang")) {
            return tong.multiply(new BigDecimal("0.95"));
        } else if (loaiKhach.equals("bach kim")) {
            return tong.multiply(new BigDecimal("0.90"));
        } else if (loaiKhach.equals("thuong")) {
            return tong;
        } else {
            throw new IllegalArgumentException("Loai khach la: " + loaiKhach);
        }
    }

    public static void main() {
        IO.println(apDungChietKhau(new BigDecimal("100000"), "vang"));  // 95000.00
    }
}

Cách viết "đóng với sửa đổi": biến mỗi quy tắc thành dữ liệu — một entry trong Map, value là hàm nhận tổng tiền và trả về tiền sau chiết khấu:

import java.math.BigDecimal;
import java.util.Map;
import java.util.function.UnaryOperator;

public class Order {
    static final Map<String, UnaryOperator<BigDecimal>> CHIET_KHAU = Map.of(
            "thuong", tong -> tong,
            "vang", tong -> tong.multiply(new BigDecimal("0.95")),
            "bach kim", tong -> tong.multiply(new BigDecimal("0.90")));

    static BigDecimal apDungChietKhau(BigDecimal tong, String loaiKhach) {
        UnaryOperator<BigDecimal> quyTac = CHIET_KHAU.get(loaiKhach);
        if (quyTac == null) {
            throw new IllegalArgumentException("Loai khach la: " + loaiKhach);
        }
        return quyTac.apply(tong);
    }

    public static void main() {
        IO.println(apDungChietKhau(new BigDecimal("100000"), "vang"));      // 95000.00
        IO.println(apDungChietKhau(new BigDecimal("100000"), "bach kim"));  // 90000.00
    }
}

Thêm loại khách mới giờ chỉ là thêm một dòng vào map — không đụng vào logic đang chạy. Nhánh equals đã biến mất, cũng không còn rủi ro quên else.

Cách cổ điển của OCP là interface + đa hình: định nghĩa một interface, mỗi quy tắc là một implementation, thêm quy tắc mới là thêm class mới. Đó chính là pattern Strategy ở mục 10. Map-of-lambda ở trên chỉ là bản gọn của cùng ý tưởng khi mỗi quy tắc chỉ có một biểu thức. Xem thêm 2.4 Polymorphism.

OCP không cấm sửa code. Sửa bug, đổi hành vi sai vẫn phải sửa bình thường. Điều cần hạn chế là: mỗi lần thêm tính năng phải mở file cũ ra sửa và test lại toàn bộ. Nếu dữ liệu chỉ có đúng 2-3 nhánh cố định, một switch rõ ràng còn dễ đọc hơn cả map lẫn interface.

4. L — Liskov Substitution Hay hỏi phỏng vấn

Phát biểu (Barbara Liskov, 1987): nếu S là subtype của T, thì object kiểu S phải thay thế được object kiểu T mà không làm hỏng tính đúng đắn của chương trình. Nói đơn giản: code đang dùng cha thì khi truyền con vào phải chạy đúng y như trước, không bất ngờ.

Ví dụ kinh điển: Bird có fly(), nhưng Penguin kế thừa lại không bay được. Cách "sửa" tệ nhất là override để ném lỗi:

class Bird {
    void fly() {
        IO.println("Bay tren troi");
    }
}

class Penguin extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException("Canh cut khong bay duoc");
    }
}

void main() {
    Bird chim = new Penguin();
    try {
        chim.fly();
    } catch (UnsupportedOperationException e) {
        IO.println("Vi pham LSP: " + e.getMessage());  // Vi pham LSP: Canh cut khong bay duoc
    }
}

Code viết theo kiểu "chim nào cũng bay" sẽ vỡ khi nhận Penguin. Dấu hiệu vi phạm LSP rất dễ nhận ra: override rồi ném UnsupportedOperationException, hoặc trong thân method phải instanceof để xử lý riêng từng subtype. Cách sửa: đừng cho Penguin kế thừa Bird; tách interface FlyingBird chỉ dành cho loài bay được, hoặc mô hình hóa hành vi bay thành một khả năng riêng (composition).

Ví dụ thứ hai hay gặp trong phỏng vấn: Square kế thừa Rectangle — nghe rất "hình học", nhưng sai về hợp đồng:

class Rectangle {
    protected int width;
    protected int height;

    void setWidth(int width) {
        this.width = width;
    }

    void setHeight(int height) {
        this.height = height;
    }

    int area() {
        return width * height;
    }
}

class Square extends Rectangle {
    @Override
    void setWidth(int width) {
        this.width = width;
        this.height = width;
    }

    @Override
    void setHeight(int height) {
        this.width = height;
        this.height = height;
    }
}

void main() {
    Rectangle r = new Square();
    r.setWidth(5);
    r.setHeight(4);
    IO.println("Dien tich mong doi 20, thuc te " + r.area());  // Dien tich mong doi 20, thuc te 16
}

Vì sao vi phạm? Hợp đồng ngầm của Rectangle là: setWidth và setHeight độc lập với nhau — gọi cái này không được đổi cái kia. Square buộc hai cạnh bằng nhau nên đã phá hợp đồng đó. Code viết trên Rectangle (tính diện tích sau khi set hai cạnh) không thể biết mình đang nhận Square, nên kết quả sai âm thầm: mong đợi 20, nhận 16. Đây là lý do LSP nói về hợp đồng hành vi, không phải quan hệ "is-a" ngoài đời. Cách sửa: Square và Rectangle cùng implement interface Shape bất biến (mỗi shape tự tính diện tích), hoặc tạo Square từ đầu chứ không kế thừa.

Tóm tắt luật chơi khi override (xem thêm 2.3 Inheritance): không được siết chặt hơn điều kiện đầu vào (precondition), không được nới lỏng hơn điều kiện đầu ra (postcondition), không được phá invariant của cha, và không được ném checked exception mới ngoài danh sách cha cho phép.

5. I — Interface Segregation Hay hỏi phỏng vấn

Phát biểu: client không nên bị ép phụ thuộc vào những method mà nó không dùng. Thay vì một interface "ôm đồm", hãy chia thành nhiều interface nhỏ theo nhu cầu của từng nhóm client.

Ví dụ: interface máy văn phòng gộp cả in, scan, fax. Một máy in giá rẻ buộc phải implement cả ba, và phải "giả vờ" với hai method không có:

interface Machine {
    void print(String document);
    void scan(String document);
    void fax(String document);
}

void main() {
    Machine mayIn = new Machine() {
        public void print(String document) {
            IO.println("In: " + document);  // In: hoa don
        }

        public void scan(String document) {
            throw new UnsupportedOperationException("May in don gian khong scan duoc");
        }

        public void fax(String document) {
            throw new UnsupportedOperationException("May in don gian khong fax duoc");
        }
    };

    mayIn.print("hoa don");
    try {
        mayIn.scan("hop dong");
    } catch (UnsupportedOperationException e) {
        IO.println("Loi: " + e.getMessage());  // Loi: May in don gian khong scan duoc
    }
}

Tách interface theo nhu cầu — ai cần gì dùng nấy. Class in đơn giản chỉ cần một method, thậm chí dùng luôn lambda vì interface chỉ có một method:

interface Printer {
    void print(String document);
}

void main() {
    Printer mayIn = document -> IO.println("In: " + document);
    mayIn.print("hoa don");  // In: hoa don
}

Lợi ích thực tế: code phụ thuộc ít method hơn thì dễ mock khi test, ít phải implement "method giả", và không có nguy cơ gọi nhầm method mà implementation không hỗ trợ. JDK cũng theo nguyên tắc này: DataInput và DataOutput tách riêng đọc/ghi; các functional interface như Consumer, Supplier, Predicate mỗi cái chỉ một method thay vì một interface "làm mọi thứ".

Đừng tách interface chỉ vì muốn mỗi interface một method. ISP nói về client: nếu mọi client đều dùng đủ cả 5 method của interface, giữ nguyên một interface là hợp lý. Interface thuộc về người gọi, không thuộc về người viết. Xem thêm 2.5 Abstract class vs Interface.

6. D — Dependency Inversion Hay hỏi phỏng vấn

Phát biểu: (1) module cấp cao không nên phụ thuộc module cấp thấp — cả hai nên phụ thuộc abstraction; (2) abstraction không nên phụ thuộc chi tiết — chi tiết phụ thuộc abstraction.

Ví dụ kinh điển: OrderService xử lý nghiệp vụ (cấp cao) không nên biết database cụ thể (cấp thấp). Nó chỉ cần biết interface OrderRepository; còn implementation là MySQL, memory hay mock test đều được:

import java.util.Optional;

interface OrderRepository {
    Optional<Order> findById(long id);
}

record Order(long id, String customer) {
    static final OrderRepository IN_MEMORY = id -> id == 42
            ? Optional.of(new Order(42, "Nguyen Van An"))
            : Optional.empty();
}

class OrderService {
    private final OrderRepository repository;

    OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    String tenKhach(long id) {
        return repository.findById(id)
                .map(Order::customer)
                .orElse("khong tim thay");
    }
}

void main() {
    OrderService service = new OrderService(Order.IN_MEMORY);
    IO.println(service.tenKhach(42));  // Nguyen Van An
    IO.println(service.tenKhach(99));  // khong tim thay
}

Chiều phụ thuộc đã bị đảo: trước đây OrderService biết MySQLOrderRepository, giờ cả hai cùng biết OrderRepository. Khi test, bạn truyền repository giả trong bộ nhớ — không cần database, không cần Spring context. Đây là lý do số một khiến DIP là nguyên tắc được đánh giá cao trong phỏng vấn.

DI khác DIP thế nào?

  • DIP là nguyên tắc thiết kế: phụ thuộc vào abstraction. Nó nói về hướng mũi tên phụ thuộc trong code.
  • DI (Dependency Injection) là kỹ thuật hiện thực: dependency được truyền từ bên ngoài vào thay vì tự tạo bên trong. Có 3 kiểu: constructor injection, setter injection, field injection.
  • DI giúp thực thi DIP, nhưng inject một class cụ thể vẫn vi phạm DIP. Ví dụ constructor nhận MySQLOrderRepository (concrete) thì có DI nhưng không có DIP.

7. Singleton — một instance duy nhất Hay hỏi phỏng vấn

Mục đích: đảm bảo một class chỉ có đúng một instance trong toàn chương trình và cung cấp điểm truy cập toàn cục cho instance đó. Hay dùng cho: cấu hình, connection pool, cache, logger. Đây là pattern dễ cài sai nhất trong đa luồng nên phỏng vấn rất thích hỏi.

public final class AppConfig { private AppConfig() { } static AppConfig getInstance() { ... } }

Cách 1 — eager (tạo sẵn)

Instance được tạo ngay khi class được nạp. JVM đảm bảo class chỉ khởi tạo một lần nên thread-safe sẵn, nhưng instance tồn tại kể cả khi chưa ai dùng:

public class AppConfig {
    static final AppConfig INSTANCE = new AppConfig();

    private AppConfig() {
    }

    String get(String key) {
        return "gia tri cua " + key;
    }

    public static void main() {
        AppConfig cauHinh = AppConfig.INSTANCE;
        IO.println(cauHinh.get("db.url"));              // gia tri cua db.url
        IO.println("Chi mot object? " + (AppConfig.INSTANCE == cauHinh));  // Chi mot object? true
    }
}

Constructor private chặn mọi nơi khác tạo instance — thử new sẽ bị compiler chặn ngay:

AppConfigDemo.java:7: error: AppConfig() has private access in AppConfig
        new AppConfig();
        ^
1 error

Cách 2 — lazy holder (khuyến nghị cho class thường)

Muốn vừa lazy (khi nào gọi lần đầu mới tạo) vừa thread-safe mà không cần synchronized? Dựa vào luật khởi tạo class của JVM: class chỉ được khởi tạo khi có ai đó truy cập lần đầu, và việc khởi tạo class đã được JVM đồng bộ hoá:

public class AppConfig {
    private AppConfig() {
    }

    private static class Holder {
        static final AppConfig INSTANCE = new AppConfig();
    }

    static AppConfig getInstance() {
        return Holder.INSTANCE;
    }

    public static void main() {
        IO.println("Cung mot object? " + (AppConfig.getInstance() == AppConfig.getInstance()));
        // Cung mot object? true
    }
}

Cách 3 — double-checked locking với volatile

Cách này từng sai trong lịch sử Java: thiếu volatile, một thread có thể thấy instance != null nhưng object chưa được khởi tạo xong (do CPU/JIT tái sắp xếp thao tác ghi). Từ Java 5, thêm volatile là đúng — nhưng nếu không hiểu rõ JMM, hãy dùng holder hoặc enum:

public class AppConfig {
    private static volatile AppConfig instance;

    private AppConfig() {
    }

    static AppConfig getInstance() {
        if (instance == null) {                  // kiem tra lan 1: nhanh, khong khoa
            synchronized (AppConfig.class) {
                if (instance == null) {          // kiem tra lan 2: bat buoc
                    instance = new AppConfig();
                }
            }
        }
        return instance;
    }

    public static void main() {
        IO.println("Cung mot object? " + (AppConfig.getInstance() == AppConfig.getInstance()));
        // Cung mot object? true
    }
}

Cách 4 — enum (ngắn và an toàn nhất)

JVM đảm bảo mỗi enum constant chỉ được khởi tạo một lần, thread-safe; enum còn chống được cả reflection lẫn serialization phá vỡ singleton. Đây là cách được Effective Java khuyến nghị:

public enum AppConfig {
    INSTANCE;

    private int soLanDoc = 0;

    String get(String key) {
        soLanDoc++;
        return key + " = gia tri (lan doc " + soLanDoc + ")";
    }

    public static void main() {
        IO.println(AppConfig.INSTANCE.get("db.url"));   // db.url = gia tri (lan doc 1)
        IO.println(AppConfig.INSTANCE.get("db.user"));  // db.user = gia tri (lan doc 2)
    }
}

Hai dòng output cho thấy state dùng chung: lần gọi thứ hai thấy soLanDoc đã tăng — đúng như một singleton.

Vì sao singleton bị coi là anti-pattern?

  • Global state — bất kỳ code nào cũng sửa được state dùng chung; bug ở xa rất khó lần ra.
  • Khó test — không thể thay instance thật bằng fake, test phụ thuộc thứ tự chạy, singleton giữ state giữa các test.
  • Che giấu dependency — đọc constructor không biết class cần gì; dependency nằm sâu trong thân method.
  • Race condition — nếu singleton có state mutable mà không đồng bộ, đây là bãi mìn trong đa luồng.
Spring singleton bean khác gì? Spring mặc định mỗi bean là một instance trong application context, nhưng: (1) container quản lý vòng đời, không cần private constructor/static INSTANCE; (2) có thể đổi scope thành prototype, request, session; (3) test dễ vì có thể inject bean giả. Vì vậy câu "đừng dùng singleton" nên hiểu là "đừng tự viết singleton + global state; hãy để DI container quản lý".

8. Factory — tạo object theo nhu cầu Junior+

Vấn đề: khi chỗ sử dụng phải quyết định tạo implementation nào (theo config, theo input, theo môi trường), code sẽ rải rác các chuỗi new EmailNotifier()/new SmsNotifier() kèm if/else/switch lặp lại. Thêm kênh mới phải sửa nhiều nơi.

Simple factory gom việc chọn implementation vào một chỗ. Ở đây sản phẩm là Consumer<String> — interface sẵn có của JDK, chỉ một method, nên dùng lambda thay cho class:

import java.util.function.Consumer;

public class NotificationFactory {
    static Consumer<String> create(String channel) {
        return switch (channel) {
            case "email" -> message -> IO.println("[EMAIL] " + message);
            case "sms" -> message -> IO.println("[SMS] " + message);
            default -> throw new IllegalArgumentException("Kenh khong ho tro: " + channel);
        };
    }

    public static void main() {
        Consumer<String> thongBao = NotificationFactory.create("email");
        thongBao.accept("Don hang DH-42 da duoc xu ly");  // [EMAIL] Don hang DH-42 da duoc xu ly

        NotificationFactory.create("sms").accept("OTP cua ban la 123456");  // [SMS] OTP cua ban la 123456

        try {
            NotificationFactory.create("zalo");
        } catch (IllegalArgumentException e) {
            IO.println("Loi: " + e.getMessage());  // Loi: Kenh khong ho tro: zalo
        }
    }
}

Bản cổ điển của ví dụ này sẽ có interface Notifier và hai class EmailNotifier, SmsNotifier. Vì mỗi sản phẩm chỉ hành xử như một hàm một tham số, dùng Consumer<String> + lambda giúp bỏ hẳn hai file class mà vẫn giữ đúng tinh thần factory. Nếu sản phẩm có state hoặc nhiều method, tạo interface riêng và class thật như bình thường.

Phân biệt ba mức độ:

  • Simple factory (ví dụ trên) — một method tĩnh trả về sản phẩm theo tham số. Không phải pattern GoF chính thức nhưng dùng nhiều nhất trong thực tế.
  • Factory method — creator khai báo method trừu tượng create(), các subclass quyết định sản phẩm cụ thể. JDK: Collection.iterator(), NumberFormat.getInstance(), Executors.newFixedThreadPool().
  • Abstract factory — "nhà máy của các nhà máy", tạo cả một họ sản phẩm liên quan (ví dụ UI theme sáng/tối tạo Button + Checkbox đồng bộ). Chỉ cần nhận biết tên; code Java thường ít tự viết.
Đừng để factory trả null. Ví dụ trên ném IllegalArgumentException với message rõ ràng — caller biết ngay mình truyền sai. Nếu factory trả null, lỗi sẽ nổ ở tận nơi khác với stack trace khó hiểu. Trường hợp "có thể không có" thì trả Optional (học ở 3.7 Optional).

9. Builder — constructor quá dài Production

Vấn đề: constructor nhiều tham số, phần lớn là tùy chọn, lại có các tham số cùng kiểu nằm cạnh nhau — gọi hàm kiểu gì cũng khó đọc và dễ truyền nhầm:

// Khong dung builder: doc khong biet tham so nao la gi, de truyen nham
new Order("Nguyen Van An", "123 Le Loi, Q1", "COD", true, null, 2, "giao gap");

Builder thay thế bằng chuỗi method có tên, mỗi method trả về chính builder để gọi tiếp, cuối cùng build() tạo ra sản phẩm bất biến (record):

import java.util.ArrayList;
import java.util.List;

record Order(String customer, List<String> items, String coupon, boolean express) {
}

class OrderBuilder {
    private String customer = "khach le";
    private final List<String> items = new ArrayList<>();
    private String coupon;
    private boolean express;

    OrderBuilder customer(String customer) {
        this.customer = customer;
        return this;
    }

    OrderBuilder addItem(String item) {
        items.add(item);
        return this;
    }

    OrderBuilder coupon(String coupon) {
        this.coupon = coupon;
        return this;
    }

    OrderBuilder express() {
        this.express = true;
        return this;
    }

    Order build() {
        return new Order(customer, List.copyOf(items), coupon, express);
    }
}

void main() {
    Order don = new OrderBuilder()
            .customer("Nguyen Van An")
            .addItem("Ao thun")
            .addItem("Quan jean")
            .express()
            .build();
    IO.println(don);
    // Order[customer=Nguyen Van An, items=[Ao thun, Quan jean], coupon=null, express=true]

    IO.println(new OrderBuilder().build());
    // Order[customer=khach le, items=[], coupon=null, express=false]
}

Builder giải quyết 4 việc cùng lúc: thay "named arguments" mà Java không có, cho giá trị mặc định, validate tập trung trong build() (ví dụ chặn đơn rỗng), và giữ sản phẩm Order bất biến — ai đó cầm Order không thể sửa nữa.

Điểm cần chú ý: List.copyOf(items) tạo bản sao bất biến, nên builder sửa tiếp cũng không ảnh hưởng object đã build. Đây là chi tiết nhiều người quên khiến đơn hàng "tự nhiên" thay đổi sau khi build.

JDK cũng đầy builder: StringBuilder, Stream.builder(), HttpRequest.newBuilder(), LocalDate thì không cần vì bất biến với method tên rõ nghĩa. Lombok @Builder sinh ra code tương tự thế này — chỉ cần biết tên, không cần viết tay.

Đừng dùng builder cho mọi thứ. Hai tham số thì new Order(donGia, soLuong) gọn hơn hẳn builder 30 dòng. Chỉ chuyển sang builder khi có khoảng 4+ tham số, phần lớn tùy chọn, hoặc khi cần validate trước khi tạo object.

10. Strategy & Observer Hay hỏi phỏng vấn

Strategy (chiến lược): đóng gói một họ thuật toán có thể thay thế cho nhau lúc chạy. Code gọi chỉ làm việc với interface, không cần biết thuật toán cụ thể.

Cách tồi là if/else theo phương thức thanh toán ngay trong checkout: thêm ví điện tử mới phải sửa method đã chạy ổn. Cách Strategy: Order giữ một PaymentStrategy và đổi được bất cứ lúc nào:

import java.math.BigDecimal;

interface PaymentStrategy {
    void pay(BigDecimal amount);
}

class Order {
    private PaymentStrategy payment;

    void doiCachThanhToan(PaymentStrategy payment) {
        this.payment = payment;
    }

    void checkout(BigDecimal amount) {
        if (payment == null) {
            throw new IllegalStateException("Chua chon cach thanh toan");
        }
        payment.pay(amount);
    }
}

void main() {
    Order don = new Order();

    // Java 8 truoc lambda: anonymous class - van la mot implementation cua interface
    don.doiCachThanhToan(new PaymentStrategy() {
        public void pay(BigDecimal amount) {
            IO.println("VNPay: -" + amount + " VND");
        }
    });
    don.checkout(new BigDecimal("250000"));  // VNPay: -250000 VND

    // Tu Java 8: lambda thay ca class implementation khi interface chi co 1 method
    don.doiCachThanhToan(amount -> IO.println("Momo: -" + amount + " VND"));
    don.checkout(new BigDecimal("120000"));  // Momo: -120000 VND

    don.doiCachThanhToan(amount -> IO.println("Tien mat: -" + amount + " VND"));
    don.checkout(new BigDecimal("50000"));   // Tien mat: -50000 VND
}

Vì PaymentStrategy chỉ có một method (functional interface), mỗi lambda chính là một implementation — không cần tạo hàng loạt class nhỏ. Nếu thuật toán có state hoặc nhiều method, hãy tạo class thật implements PaymentStrategy. Strategy chính là DIP áp cho tầng thuật toán: code cấp cao (Order) chỉ biết abstraction. Lambda sẽ học kỹ ở 3.6 Lambda & Functional interfaces.

Observer (quan sát): subject giữ danh sách observer, khi state đổi thì thông báo cho tất cả. Đây là nền tảng của event listener, pub/sub, và Spring ApplicationEvent. Ví dụ: Order cho đăng ký PriceObserver để nhận thông báo mỗi khi tổng tiền thay đổi:

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

interface PriceObserver {
    void onPriceChanged(BigDecimal oldValue, BigDecimal newValue);
}

class Order {
    private BigDecimal tongTien;
    private final List<PriceObserver> observers = new ArrayList<>();

    Order(BigDecimal tongTien) {
        this.tongTien = tongTien;
    }

    void addObserver(PriceObserver observer) {
        observers.add(observer);
    }

    void capNhatTong(BigDecimal moi) {
        BigDecimal cu = tongTien;
        tongTien = moi;
        for (PriceObserver observer : observers) {
            observer.onPriceChanged(cu, moi);
        }
    }
}

void main() {
    Order don = new Order(new BigDecimal("250000"));
    don.addObserver((cu, moi) -> IO.println("Email: tong tien doi tu " + cu + " thanh " + moi));
    don.addObserver((cu, moi) -> IO.println("LOG: " + cu + " -> " + moi));

    don.capNhatTong(new BigDecimal("270000"));
    // Email: tong tien doi tu 250000 thanh 270000
    // LOG: 250000 -> 270000
}

13. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Design pattern là gì? GoF chia pattern thành mấy nhóm?
Design pattern là giải pháp điển hình, đã được đặt tên, cho một vấn đề thiết kế lặp lại — nó mô tả quan hệ giữa các class/object, không phải thư viện code dán vào là chạy. GoF chia 23 mẫu thành 3 nhóm: creational (khởi tạo object: Singleton, Factory, Builder), structural (ghép cấu trúc: Adapter, Decorator, Proxy) và behavioral (hành vi: Strategy, Observer, Template Method, Chain of Responsibility).
Câu 2. SOLID là gì? Kể tên 5 nguyên tắc kèm một câu mô tả.
S — Single Responsibility: một class một lý do để thay đổi. O — Open/Closed: mở cho mở rộng, đóng với sửa đổi. L — Liskov Substitution: subtype thay thế được cha mà không phá chương trình. I — Interface Segregation: interface nhỏ theo nhu cầu client. D — Dependency Inversion: phụ thuộc abstraction, không phụ thuộc concrete.
Câu 3. SRP hiểu đúng thế nào? Có phải "mỗi class một method"?
Không. SRP là "một lý do để thay đổi" — một class có thể có nhiều method miễn tất cả cùng phục vụ một trục thay đổi/nhóm stakeholder. Tiêu chí thực dụng: mô tả class bằng một câu không có chữ "và". Nếu phải nói "class này tính tiền và gửi email và ghi log" thì nên tách.
Câu 4. OCP nghĩa là gì? Có phải cấm sửa code?
OCP nghĩa là thêm tính năng mới nên làm bằng cách thêm code mới (class mới, implementation mới, entry mới) thay vì sửa nhánh if/else cũ đã chạy ổn và đã test. Nó không cấm sửa bug hay sửa hành vi sai. Nếu chỉ có 2-3 nhánh cố định, switch đơn giản còn dễ đọc hơn trừu tượng hoá.
Câu 5. Phát biểu nguyên tắc Liskov (LSP)?
Nếu S là subtype của T thì object kiểu S phải thay thế được object kiểu T mà không làm hỏng tính đúng đắn của chương trình. Cụ thể khi override: không siết chặt precondition, không nới lỏng postcondition, giữ nguyên invariant, không ném checked exception mới ngoài danh sách cha cho phép.
Câu 6. Vì sao Square kế thừa Rectangle bị coi là vi phạm LSP?
Vì hợp đồng của Rectangle là setWidth và setHeight độc lập với nhau. Square buộc hai cạnh bằng nhau nên phá hợp đồng đó: code viết trên Rectangle gọi setWidth(5); setHeight(4) mong đợi diện tích 20 nhưng nhận 16. Đây là lỗi âm thầm, không exception. Cách sửa: cho cả hai cùng implement một interface Shape bất biến, hoặc dùng composition thay vì kế thừa.
Câu 7. ISP là gì? Lợi ích thực tế?
Client không nên bị ép phụ thuộc method nó không dùng; chia interface lớn thành nhiều interface nhỏ theo nhu cầu client. Lợi ích: không phải implement method "giả" rồi ném UnsupportedOperationException, dễ mock khi test, giảm coupling. Ví dụ JDK: DataInput/DataOutput tách riêng; Consumer/Supplier/Predicate mỗi cái một method.
Câu 8. Nguyên tắc Dependency Inversion nói gì?
Module cấp cao không phụ thuộc module cấp thấp; cả hai phụ thuộc abstraction. Abstraction không phụ thuộc chi tiết; chi tiết phụ thuộc abstraction. Ví dụ: OrderService (nghiệp vụ) không biết MySQL, chỉ biết interface OrderRepository; ai cài đặt interface đó là chuyện của tầng hạ tầng.
Câu 9. DI và DIP khác nhau thế nào?
DIP là nguyên tắc thiết kế (phụ thuộc abstraction); DI là kỹ thuật truyền dependency từ ngoài vào (constructor/setter/field). DI giúp thực thi DIP nhưng không đảm bảo DIP: constructor nhận thẳng MySQLOrderRepository là có DI mà vẫn vi phạm DIP.
Câu 10. Vì sao nên ưu tiên constructor injection?
Dependency là bắt buộc nên object không bao giờ ở trạng thái thiếu; field có thể final (immutable); tạo object trong test chỉ cần gọi constructor, không cần container/reflection; đọc constructor là biết ngay class phụ thuộc gì. Setter/field injection chỉ hợp lý cho dependency tùy chọn.

Nâng cao (Junior+)

Câu 11. Singleton là gì? Kể các cách cài đặt.
Đảm bảo một class chỉ có một instance và có điểm truy cập toàn cục. Các cách: (1) eager static final INSTANCE; (2) lazy + synchronized; (3) lazy holder (static nested class) — lazy + thread-safe không cần khoá; (4) double-checked locking + volatile; (5) enum INSTANCE — ngắn và an toàn nhất. Khác static class: singleton là object thật, có thể implements interface, thay thế/mock được, kiểm soát được thời điểm khởi tạo.
Câu 12. Double-checked locking vì sao bắt buộc có volatile?
Vì instance = new AppConfig() không phải một thao tác nguyên tử: cấp phát bộ nhớ, chạy constructor, gán reference. Nếu thiếu volatile, CPU/JIT có thể tái sắp xếp khiến thread khác thấy reference khác null trong khi object chưa khởi tạo xong (partially constructed object) rồi dùng luôn — lỗi cực khó tái hiện. volatile cấm tái sắp xếp và đảm bảo visibility. Nếu không tự tin, dùng holder hoặc enum.
Câu 13. Enum singleton có gì hay?
JVM đảm bảo mỗi enum constant chỉ được khởi tạo một lần nên thread-safe sẵn; enum chống reflection (constructor enum bị chặn) và serialization luôn trả cùng instance — hai lỗ hổng kinh điển của singleton class. Code ngắn nhất, không cần synchronized. Nhược điểm: không lazy theo nghĩa tuyệt đối (khởi tạo khi class được dùng) và không thể kế thừa class khác.
Câu 14. Khi nào KHÔNG nên dùng singleton?
Khi đối tượng có state mutable dùng chung (dễ race, bug khó tái hiện); khi cần mock/thay thế trong test; khi singleton chỉ để tiện gọi ở mọi nơi thay vì truyền dependency rõ ràng; khi framework đã có DI container quản lý vòng đời (Spring bean). Quy tắc: dùng DI trước, singleton tự viết là phương án cuối.
Câu 15. Builder giải quyết vấn đề gì? Khi nào không nên dùng?
Giải quyết telescoping constructor: nhiều tham số, phần lớn tùy chọn, khó đọc và dễ truyền nhầm. Builder cho named arguments, giá trị mặc định, validate trong build(), và giữ sản phẩm bất biến. Không nên dùng khi chỉ 2-3 tham số — constructor hoặc record gọn hơn nhiều.
Câu 16. Strategy thay thế if/else thế nào? Khi nào vẫn nên giữ if/else?
Thay vì if/else chọn thuật toán trong method, đưa từng thuật toán vào một implementation của interface chung, context chỉ gọi interface và đổi được lúc chạy. Khi chỉ có 2-3 nhánh đơn giản, không có nhu cầu đổi lúc chạy, if/else/switch dễ đọc hơn. Dấu hiệu cần Strategy: nhánh tăng liên tục, mỗi nhánh có logic riêng, muốn test từng nhánh độc lập.
Câu 17. Simple factory khác factory method thế nào? Vì sao factory không nên trả null?
Simple factory: một method tĩnh nhận tham số rồi tự quyết định sản phẩm (thường dùng switch). Factory method: creator khai báo method trừu tượng để subclass quyết định sản phẩm — mở rộng bằng cách thêm subclass creator. Factory không nên trả null vì caller sẽ NPE ở nơi khác, stack trace khó lần; hãy ném exception có message hoặc trả Optional.
Câu 18. Observer pattern là gì? Cho ví dụ.
Subject giữ danh sách observer; khi state đổi thì thông báo cho tất cả observer (quan hệ 1-n). Ví dụ: PriceObserver nhận thông báo khi giá đổi, addEventListener trên DOM, EventEmitter trong Node, Spring ApplicationEvent/@EventListener. Lưu ý remove listener để tránh leak và cô lập exception từng observer.
Câu 19. Spring dùng những pattern nào? Kể tên kèm ví dụ.
DI/DIP (constructor injection), Factory (@Bean, BeanFactory), Singleton (bean scope mặc định), Builder (RestClient.builder()), Proxy/Decorator (AOP @Transactional), Template Method (JdbcTemplate), Observer (ApplicationEventPublisher), Strategy (PasswordEncoder, Comparator), Chain of Responsibility (filter chain, interceptor), Adapter (HandlerAdapter).
Câu 20. Spring singleton bean khác GoF singleton ở đâu?
Spring singleton là một instance trong application context, không phải một instance trong JVM: hai context khác nhau có hai bean; có thể đổi scope thành prototype/request/session. Class không cần private constructor hay static INSTANCE, vòng đời do container quản lý, dễ inject fake khi test. GoF singleton là biến static toàn cục thật sự.
Câu 21. Làm sao nhận diện khi nào cần pattern?
Bắt đầu từ "mùi" của code chứ không phải từ pattern: if/else/switch dài theo type, constructor dài, new rải rác, khó viết unit test vì dính chặt vào implementation, global state khó kiểm soát, đăng ký nhận sự kiện thủ công. Mỗi mùi ánh xạ tới một pattern. Thực dụng: rule of three — đến lần thứ ba lặp lại cấu trúc tương tự mới trừu tượng hoá.
Câu 22. Có phải càng nhiều pattern càng tốt? Làm sao tránh over-engineering?
Không. Pattern là công cụ giao tiếp và giảm chi phí thay đổi, không phải tiêu chí chất lượng. Tránh bằng cách: hỏi "vấn đề thật đang gặp là gì?", ưu tiên code đơn giản chạy được, chỉ trừu tượng khi có ít nhất hai biến thể thật (hoặc lần thay đổi thứ ba), và đọc lại code của mình sau vài ngày — nếu khó hiểu hơn code cũ thì pattern đang bị lạm dụng.

import java.util.List;

interface PriceObserver {
    void onPriceChanged(BigDecimal oldValue, BigDecimal newValue);
}

class Order {
    private BigDecimal tongTien;
    private final List<PriceObserver> observers = new ArrayList<>();

    Order(BigDecimal tongTien) {
        this.tongTien = tongTien;
    }

    void addObserver(PriceObserver observer) {
        observers.add(observer);
    }

    void capNhatTong(BigDecimal moi) {
        BigDecimal cu = tongTien;
        tongTien = moi;
        for (PriceObserver observer : observers) {
            observer.onPriceChanged(cu, moi);
        }
    }
}

void main() {
    Order don = new Order(new BigDecimal("100000"));
    don.addObserver((cu, moi) -> IO.println("A: " + cu + " -> " + moi));
    don.addObserver((cu, moi) -> IO.println("B: " + cu + " -> " + moi));
    don.capNhatTong(new BigDecimal("120000"));
    don.capNhatTong(new BigDecimal("150000"));
}

In ra 4 dòng — mỗi lần cập nhật, cả hai observer đều được gọi theo thứ tự đăng ký:

A: 100000 -> 120000
B: 100000 -> 120000
A: 120000 -> 150000
B: 120000 -> 150000

Đây là Observer: subject không cần biết observer nào làm gì, chỉ phát thông báo. Lưu ý thứ tự gọi là thứ tự thêm vào danh sách — đừng thiết kế phụ thuộc vào thứ tự này nếu không cần.

1 — Builder (nhiều tham số tùy chọn, sản phẩm bất biến). 2 — Strategy (họ thuật toán thay thế lúc chạy, test độc lập). 3 — Observer (một sự kiện, nhiều nơi nhận, tránh Order biết hết các bên). 4 — Singleton (một instance duy nhất; hoặc tốt hơn là bean do DI container quản lý). 5 — Simple factory (gom logic chọn implementation vào một chỗ, không trả null). Điểm chung: chọn pattern theo vấn đề, không theo danh sách cho đẹp.

Checklist tự đánh giá trước phỏng vấn

  • Phát biểu được 5 nguyên tắc SOLID bằng một câu mỗi nguyên tắc, không cần nhìn tài liệu.
  • Giải thích SRP đúng: "một lý do để thay đổi", không phải "mỗi class một method".
  • Đưa được ví dụ OCP bằng interface/map và nói rõ khi nào vẫn nên dùng switch.
  • Giải thích được vì sao Square/Rectangle vi phạm LSP, kèm kết quả số cụ thể (20 vs 16).
  • Chỉ ra dấu hiệu vi phạm LSP: override ném UnsupportedOperationException, phải instanceof.
  • Giải thích ISP bằng ví dụ Machine print/scan/fax hoặc JDK DataInput/DataOutput.
  • Phân biệt DIP (nguyên tắc) và DI (kỹ thuật); nêu 3 kiểu injection và vì sao ưu tiên constructor.
  • Viết được singleton bằng enum, lazy holder, DCL + volatile — và biết cái nào nên chọn.
  • Giải thích vì sao singleton bị coi là anti-pattern và Spring bean khác gì.
  • Viết được simple factory trả interface, ném exception khi input sai, không trả null.
  • Viết được builder cho record, có giá trị mặc định và snapshot bằng List.copyOf.
  • Viết được strategy bằng interface + lambda, giải thích khi nào if/else vẫn tốt hơn.
  • Viết được observer đơn giản và kể tên ứng dụng thật (event listener, ApplicationEvent).
  • Kể được ít nhất 6 pattern Spring dùng sẵn kèm ví dụ annotation/class.
  • Trả lời được "càng nhiều pattern càng tốt không?" với lập luận chống over-engineering.
