1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Object là class cha ngầm của mọi class trong Java. Không cần extends Object, bạn vẫn có sẵn ba method quan trọng nhất:

  • equals(Object) — định nghĩa "hai object này có bằng nhau về giá trị không". Mặc định Object chỉ so địa chỉ (identity), giống hệt toán tử ==.
  • hashCode() — trả về một số nguyên đại diện cho object, là "mã bucket" để HashMap/HashSet tìm nhanh. Mặc định là hash định danh: thường khác nhau giữa các object nhưng không được đảm bảo — vẫn có thể va chạm.
  • toString() — mô tả object dạng chuỗi, dùng khi log, debug hoặc nối chuỗi. Mặc định cho ra thứ khó đọc kiểu Point@b59d31.

Vì sao chủ đề này quan trọng? Ba lý do thực chiến: (1) HashMap, HashSet, dedupe danh sách, Set.contains đều xây trên equals + hashCode; viết sai thì dữ liệu "biến mất" một cách vô hình. (2) Log/debug và thông báo lỗi test dựa vào toString; thiếu nó, bạn chỉ thấy địa chỉ bộ nhớ. (3) Đây là câu hỏi phỏng vấn kinh điển, xuất hiện ở gần như mọi buổi phỏng vấn Java từ junior trở lên.

Mức độ bắt buộc của chủ đề 2.6 (phỏng vấn: rất cao · production: bắt buộc):

  • Phải làm được — viết bộ ba equals/hashCode/toString đúng chuẩn; dùng Objects.equals, Objects.hash; xử lý field null, mảng, BigDecimal; dùng record cho value object; viết test kiểm tra hợp đồng.
  • Phải hiểu — 5 tính chất của equals; 3 điều khoản của hashCode; vì sao phải override cả hai cùng lúc; chuỗi hash → bucket → equals của HashMap; vì sao key phải bất biến; getClass vs instanceof.
  • Nhận biết — bẫy scale của BigDecimal; bẫy cache của wrapper; mảng dùng Arrays.equals; Lombok @EqualsAndHashCode(callSuper = true); entity JPA với id sinh tự động; hash của record có thể khác giữa các lần chạy JVM.

Cách học hiệu quả nhất:

  1. Đoán output của ví dụ trước khi nhìn comment kết quả.
  2. Làm mục Bài tập đoán output trước, chỉ mở đáp án sau khi đã đoán.
  3. Ôn nhanh bằng Cheat sheet trước buổi phỏng vấn.
  4. Gặp câu lạ, tra ở mục Interview Q&A.
Ví dụ dùng IO.println(...) — cách viết gọn của JDK 25 (JEP 512), tương đương System.out.println(...) mà bạn sẽ thấy trong đề phỏng vấn và tài liệu cũ. Mọi ví dụ trong trang chạy được bằng java TenFile.java.

Góc Node.js — nhìn nhanh

Trong JavaScript, hai object có cùng nội dung vẫn không bằng nhau vì phép so sánh object luôn theo reference:

// JavaScript (Node 22)
const a = { sku: "SKU-1" };
const b = { sku: "SKU-1" };

console.log(a === b);                                  // false
console.log(JSON.stringify(a) === JSON.stringify(b)); // true
console.log(JSON.stringify({ x: 1, y: 2 }) ===
            JSON.stringify({ y: 2, x: 1 }));           // false - bay thu tu key

Java mặc định giống hệt ===: equals của Object cũng so reference. Khác biệt là Java cho bạn override equals để đổi ngữ nghĩa sang so giá trị, và HashMap/HashSet tự động dùng ngữ nghĩa đó. JavaScript không override được toán tử, nên phải gọi hàm so sánh thủ công: tự viết, JSON.stringify, lodash isEqual, hay util.isDeepStrictEqual của Node. Chi tiết đầy đủ ở mục 14.

Mặc định, Object.toString() trả về chuỗi theo công thức: tên class + @ + hash code dạng hex. Chạy thật file Point.java:

public class Point {
    int x;
    int y;

    Point(int x, int y) {
        this.x = x;
        this.y = y;

    public static void main() {
        Point p = new Point(3, 4);
        IO.println(p);
        IO.println("p = " + p);
        IO.println(p.getClass().getName() + "@" + Integer.toHexString(p.hashCode()));
    }

Dòng cuối chính là công thức mặc định được viết tường minh. Số b59d31 là hash định danh — có thể khác khi chạy lại hoặc trên JVM khác, đừng bao giờ ghi nhớ hay parse nó.

Vấn đề: Point@b59d31 không cho bạn biết toạ độ là (3, 4). Override toString để log/debug đọc được ngay:

final class Product {
    private final String name;
    private final long price;

    Product(String name, long price) {
        this.name = name;
        this.price = price;
    }

    @Override
    public String toString() {
        return "Product{name='" + name + "', price=" + price + "}";
    }
}

void main() {
    Product p = new Product("Ao thun", 199_000);
    IO.println(p);
    IO.println("Chi tiet: " + p);
}
Product{name='Ao thun', price=199000}
Chi tiet: Product{name='Ao thun', price=199000}

record tự sinh toString

Với record, bạn không phải viết gì — JDK tự sinh toString dạng TenRecord[field=value, ...]:

record Point(int x, int y) {}

record Product(String sku, long price) {}

void main() {
    IO.println(new Point(3, 4));
    IO.println(new Product("SKU-1", 199_000));
}
Point[x=3, y=4]
Product[sku=SKU-1, price=199000]

Quy ước khi viết toString

  • Ngắn gọn, đủ field nhận diện — thường là tên class + các field chính, không cần in toàn bộ object graph.
  • Format ổn định — đừng đổi format liên tục vì log cũ và thông báo test sẽ khó so; nhưng cũng đừng parse toString bằng code (nhất là toString của record — JDK ghi rõ format có thể thay đổi).
  • Không chứa dữ liệu nhạy cảm — mật khẩu, token, số thẻ, email... Ghi log object là ghi cả chuỗi này ra file/console:
@Override
public String toString() {
    return "User{email=" + email + ", password=" + password + "}"; // RO RI MAT KHAU
}

@Override
public String toString() {
    return "User{id=" + id + ", email=" + email + "}"; // an toan hon
}
Cẩn thận với lazy loading: nếu toString chạm vào quan hệ JPA lười tải (ví dụ order.getItems()), ghi log có thể kéo cả bảng dữ liệu (N+1 query) hoặc ném LazyInitializationException. Chỉ in state thật sự cần, hoặc dùng DTO cho log. IDE (IntelliJ, VS Code) có generate sẵn — xem mục 11.

3. == vs equals Hay hỏi phỏng vấn

Hai toán tử trông giống nhau nhưng đo hai thứ khác nhau:

  • == so giá trị với primitive (int, boolean, char...); riêng float/double theo luật số học đặc biệt (NaN != NaN, +0.0 == -0.0). Với object, == so địa chỉ / reference: hai biến == nhau khi cùng trỏ vào một object.
  • equals là một method. Bản gốc trong Object viết đúng một dòng: return this == obj; — tức mặc định cũng là identity. Sức mạnh chỉ đến khi bạn override nó để so nội dung.
final class Product {
    final String name;

    Product(String name) {
        this.name = name;
    }
}

void main() {
    Product a = new Product("Ao thun");
    Product b = new Product("Ao thun");
    Product c = a;

    IO.println("a == b        : " + (a == b));
    IO.println("a.equals(b)   : " + a.equals(b));
    IO.println("a == c        : " + (a == c));

    String s1 = "java";
    String s2 = "java";
    String s3 = new String("java");
    IO.println("s1 == s2      : " + (s1 == s2));
    IO.println("s1 == s3      : " + (s1 == s3));
    IO.println("s1.equals(s3) : " + s1.equals(s3));
}
a == b        : false
a.equals(b)   : false
a == c        : true
s1 == s2      : true
s1 == s3      : false
s1.equals(s3) : true

Đọc kết quả: Product chưa override equals nên hai sản phẩm cùng tên vẫn "khác nhau" — đúng như === trong JS. Với String: hai literal cùng nội dung được chia sẻ trong string pool nên s1 == s2 là true (may mắn), nhưng new String(...) tạo object mới nên s1 == s3 là false. Khi nào cần value equality? Khi object đại diện cho một giá trị trong nghiệp vụ — mã sản phẩm, toạ độ, số tiền, đơn hàng — chứ không phải một thực thể có danh tính riêng. Lúc đó hãy override equals (và hashCode), hoặc dùng record để JDK làm giúp.

4. Hợp đồng equals — 5 tính chất Hay hỏi phỏng vấn

Javadoc của Object.equals quy định equals phải là một quan hệ tương đương (equivalence relation) với 5 tính chất. Phỏng vấn gần như luôn hỏi điều này:

  1. Reflexive — x.equals(x) luôn true.
  2. Symmetric — x.equals(y) bằng y.equals(x). Không bao giờ có chuyện một chiều.
  3. Transitive — nếu x.equals(y) và y.equals(z) thì x.equals(z).
  4. Consistent — gọi nhiều lần cho cùng kết quả, miễn là state dùng để so không đổi. Đừng để equals phụ thuộc thời gian, ngẫu nhiên, DNS, hay field bị mutate.
  5. Non-nullity — x.equals(null) phải trả false, không được ném NullPointerException.

Vi phạm symmetric — ví dụ chạy thật

Lớp cha dùng instanceof, lớp con thêm state và dùng getClass() — thế là equals một chiều:

class Point {
    final int x;
    final int y;

    Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point p)) return false;
        return x == p.x && y == p.y;
    }
}

void main() {
    Point p = new Point(1, 2);
    Point cp = new Point(1, 2) {
        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (o == null || getClass() != o.getClass()) return false;
            return super.equals(o);
        }
    };

    IO.println("p.equals(cp)     : " + p.equals(cp));
    IO.println("cp.equals(p)     : " + cp.equals(p));
    IO.println("vi pham symmetry : " + (p.equals(cp) != cp.equals(p)));
}
p.equals(cp)     : true
cp.equals(p)     : false
vi pham symmetry : true

Đây không phải tình huống hiếm gặp — chính JDK mắc lỗi này. java.sql.Timestamp kế thừa java.util.Date và thêm field nanos. Javadoc của Timestamp ghi rõ: "Timestamp.equals(Object) never returns true when passed an object that isn't an instance of Timestamp... not symmetric with respect to Date.equals". Chạy thật (nanos bằng 0):

import java.sql.Timestamp;
import java.util.Date;

void main() {
    Date date = new Date(1_000_000_000_000L);
    Timestamp ts = new Timestamp(1_000_000_000_000L);

    IO.println("date.equals(ts) : " + date.equals(ts));
    IO.println("ts.equals(date) : " + ts.equals(date));
}
date.equals(ts) : true
ts.equals(date) : false
Bài học từ Effective Java: không thể vừa mở rộng một class có equals theo giá trị, vừa giữ đúng hợp đồng equals — trừ khi chấp nhận bỏ qua state của lớp con (mà như thế thì equals cũng vô nghĩa). Cách an toàn: ưu tiên composition hơn inheritance cho value object, hoặc chặn hẳn việc kế thừa bằng final. Nếu buộc phải thiết kế class cha cho phép kế thừa, idiom canEqual giữ được symmetry: equals của cha kiểm tra o instanceof Cha && ((Cha) o).canEqual(this), mỗi lớp con override canEqual để chỉ nhận đúng lớp mình (Effective Java, item 10).

5. Viết equals đúng — từng bước Junior+

public boolean equals(Object o)

Chữ ký bắt buộc nhận Object. Công thức 5 bước, làm đúng thứ tự:

  1. if (this == o) return true; — fast path, cũng xử lý luôn trường hợp x.equals(x).
  2. if (o == null || getClass() != o.getClass()) return false; — loại null và sai class trước khi cast.
  3. Cast: Product other = (Product) o;
  4. So từng field: primitive dùng ==; object dùng Objects.equals(a, b) (null-safe); mảng dùng Arrays.equals/Arrays.deepEquals; double/float dùng Double.compare/Float.compare.
  5. @Override trên method để compiler kiểm tra chữ ký, và override hashCode theo cùng bộ field (mục 7).
import java.util.Objects;

final class Product {
    private final String sku;
    private final String name;
    private final long price;

    Product(String sku, String name, long price) {
        this.sku = sku;
        this.name = name;
        this.price = price;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) {
            return true;
        }
        if (o == null || getClass() != o.getClass()) {
            return false;
        }
        Product other = (Product) o;
        return price == other.price
                && Objects.equals(sku, other.sku)
                && Objects.equals(name, other.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(sku, name, price);
    }
}

void main() {
    Product a = new Product("SKU-1", "Ao thun", 199_000);
    Product b = new Product("SKU-1", "Ao thun", 199_000);
    Product c = new Product("SKU-1", "Ao thun", 250_000);

    IO.println("a == b      : " + (a == b));
    IO.println("a.equals(b) : " + a.equals(b));
    IO.println("a.equals(c) : " + a.equals(c));
    IO.println("hash a      : " + a.hashCode());
    IO.println("hash b      : " + b.hashCode());
    IO.println("hash c      : " + c.hashCode());
}
a == b      : false
a.equals(b) : true
a.equals(c) : false
hash a      : 949354521
hash b      : 949354521
hash c      : 949405521

Chú ý Objects.equals(sku, other.sku): nếu sku là null, cả hai phía null vẫn cho true, một phía null cho false — không ném NPE. Nếu tự viết sku.equals(other.sku) bạn phải tự chống null bằng tay.

Bẫy chữ ký: equals(Product) chỉ là overload

Nếu bạn quên @Override và viết tham số kiểu cụ thể, compiler coi đó là một method mới — nó không override Object.equals:

EqualsSignatureErr.java:8: error: method does not override or implement a method from a supertype
    @Override
    ^
1 error

Bỏ @Override thì code compile được nhưng hành vi rất quái — tuỳ kiểu tĩnh của biến gọi mà chọn overload hay Object.equals:

final class Product {
    final String sku;

    Product(String sku) {
        this.sku = sku;
    }

    public boolean equals(Product other) { // THIEU @Override, sai kieu tham so
        return sku.equals(other.sku);
    }
}

void main() {
    Product a = new Product("SKU-1");
    Product b = new Product("SKU-1");
    Object c = a;

    IO.println("a.equals(b)          : " + a.equals(b));
    IO.println("c.equals(b)          : " + c.equals(b));
    IO.println("a.equals((Object) b) : " + a.equals((Object) b));
}
a.equals(b)          : true
c.equals(b)          : false
a.equals((Object) b) : false

Nguy hiểm nhất là khi object của bạn nằm trong HashSet: collection luôn gọi qua kiểu Object, nên overload của bạn bị bỏ qua hoàn toàn. Luôn có @Override và tham số Object.

So sánh double: price == other.price sai với NaN vì NaN != NaN — hai object cùng chứa NaN sẽ không equal, phá tính reflexive. Dùng Double.compare(price, other.price) == 0: nó coi NaN bằng nhau và phân biệt -0.0 với 0.0 (còn == thì coi hai giá trị này bằng nhau). Với BigDecimal, nhớ bẫy scale ở mục 10.

6. record — value object làm sẵn Production

Record tự sinh constructor, accessor, equals, hashCode, toString dựa trên danh sách component. Với value object, đây là cách viết ít code và ít bug nhất:

record Point(int x, int y) {}

record Product(String sku, long price) {}

void main() {
    Point p1 = new Point(1, 2);
    Point p2 = new Point(1, 2);
    Product a = new Product("SKU-1", 199_000);
    Product b = new Product("SKU-1", 199_000);

    IO.println("p1 == p2           : " + (p1 == p2));
    IO.println("p1.equals(p2)      : " + p1.equals(p2));
    IO.println("hash p1 == hash p2 : " + (p1.hashCode() == p2.hashCode()));
    IO.println("p1                 : " + p1);
    IO.println("a.equals(b)        : " + a.equals(b));
    IO.println("a                  : " + a);
}
p1 == p2           : false
p1.equals(p2)      : true
hash p1 == hash p2 : true
p1                 : Point[x=1, y=2]
a.equals(b)        : true
a                  : Product[sku=SKU-1, price=199000]

Record là final và bất biến (component là private final) nên cực hợp làm key của HashMap/HashSet: không ai sửa được field sau khi put. Javadoc Record.hashCode nói rõ: thuật toán hash cụ thể không được đảm bảo và có thể khác giữa các lần chạy JVM, kể cả khi hash của các component không đổi — đừng lưu hash của record xuống DB hay cache ngoài tiến trình.

Bẫy record chứa mảng: equals của record so từng component bằng Objects.equals, mà Objects.equals(int[], int[]) là so reference — hai mảng cùng nội dung vẫn khác nhau:

    Product b = new Product("SKU-1", new int[]{38, 39});

    IO.println("a.hashCode == b : " + (a.hashCode() == b.hashCode()));

Muốn record chứa nhiều giá trị, dùng List bất biến (List.copyOf) thay vì mảng, hoặc tự override equals/hashCode với Arrays.equals/Arrays.hashCode.

7. Hợp đồng hashCode Hay hỏi phỏng vấn

public int hashCode()

Javadoc Object.hashCode có đúng 3 điều khoản:

  1. Consistent trong một lần chạy — cùng một object, gọi hashCode() nhiều lần phải cho cùng kết quả, miễn là field dùng để tính hash không đổi. Giữa các lần chạy JVM khác nhau thì không cần giống nhau.
  2. Equal objects → equal hash codes — nếu a.equals(b) thì a.hashCode() == b.hashCode(). Đây là điều khoản bắt buộc, không phải "nên".
  3. Unequal objects có thể trùng hash — không bắt buộc khác nhau, nhưng hash càng rải đều thì HashMap càng nhanh. Trùng hash gọi là collision, hoàn toàn bình thường.

Mặc định Object.hashCode() là identity hash — gắn với danh tính object, không phải địa chỉ bộ nhớ thật (JVM có thể di chuyển object mà hash không đổi). Hai object khác nhau thường có hash khác nhau nhưng không được đảm bảo — va chạm vẫn có thể xảy ra; con số cụ thể cũng không được hứa và không ổn định giữa các lần chạy. Muốn lấy identity hash kể cả khi class đã override hashCode(), dùng System.identityHashCode(obj).

Objects.hash và cái bẫy một tham số

Objects.hash(a, b, c) tiện và null-safe, nhưng nó thực chất là Arrays.hashCode(new Object[]{...}) — tức luôn "trộn" mảng theo công thức bắt đầu bằng 31. Hệ quả: với đúng một tham số, kết quả không bằng hashCode của object đó:

import java.util.Objects;

void main() {
    String sku = "SKU-1";
    IO.println("sku.hashCode()        : " + sku.hashCode());
    IO.println("Objects.hash(sku)     : " + Objects.hash(sku));
    IO.println("Objects.hashCode(sku) : " + Objects.hashCode(sku));
    IO.println("Objects.hash == hash  : " + (Objects.hash(sku) == sku.hashCode()));
}
sku.hashCode()        : 78969697
Objects.hash(sku)     : 78969728
Objects.hashCode(sku) : 78969697
Objects.hash == hash  : false

Nếu class chỉ có một field và bạn muốn hashCode() trả thẳng hash của field, dùng Objects.hashCode(field) (trả 0 cho null). Dùng Objects.hash cho từ 2 field trở lên là chuẩn; chỉ cần nhớ nó không phải "hash của một field" và mỗi lần gọi nó tạo một Object[] — trong hot path nên tự trộn 31 * result + hash để tránh cấp phát.

Bộ field trong hashCode phải khớp equals: field nào equals bỏ qua thì hashCode cũng phải bỏ qua, và ngược lại field nào equals dùng thì hashCode phải dùng. Lệch nhau phá điều khoản 2 — đây là bug phổ biến nhất của chủ đề này, xem mục 8.

9. HashMap / HashSet hoạt động thế nào Hay hỏi phỏng vấn

Ở mức giới thiệu đủ để hiểu hợp đồng, một lần map.get(key) đi qua 4 bước:

  1. Gọi key.hashCode().
  2. Trộn bit: h ^ (h >>> 16) (spread) để các bit cao tham gia vào index.
  3. Chọn bucket: (n - 1) & spread, với n là số bucket (mặc định 16).
  4. Đi trong bucket, dùng equals để tìm đúng key. Tìm thấy → trả value; không → trả null.
void main() {
    String key = "Aa";
    int h = key.hashCode();
    int spread = h ^ (h >>> 16);

    IO.println("hash          : " + h);
    IO.println("spread        : " + spread);
    IO.println("bucket (n=16) : " + (spread & 15));
    IO.println("bucket (n=32) : " + (spread & 31));
}
hash          : 2112
spread        : 2112
bucket (n=16) : 0
bucket (n=32) : 0

Collision là bình thường

"Aa" và "BB" có cùng hash 2112 — một ví dụ nổi tiếng. Cả hai vào bucket 0, nhưng equals là false, nên cả hai vẫn được giữ:

import java.util.HashSet;
import java.util.Set;

    IO.println("\"Aa\".hashCode() : " + "Aa".hashCode());

    Set<Product> set = new HashSet<>();

"BB".hashCode() : 2112
"Aa".equals("BB"): false

Năm object cùng hash nhưng vẫn nằm đủ 5 phần tử vì equals khác nhau. Trong OpenJDK hiện tại, bucket 8 phần tử vẫn là danh sách liên kết; chỉ khi thêm phần tử thứ 9 vào bucket đang có ≥ 8 node và capacity của map đạt tối thiểu 64 (MIN_TREEIFY_CAPACITY) thì bucket mới chuyển từ danh sách liên kết sang cây đỏ-đen để tra cứu nhanh hơn (khoảng O(log n) thay vì O(n) cho bucket đó); nếu capacity còn nhỏ hơn 64 thì map resize (tăng gấp đôi) thay vì treeify. Chi tiết đầy đủ (kể cả untreeify khi xóa) ở Collections — mục 5.

HashSet.add dùng hash + equals để dedupe; HashMap.put với key đã tồn tại (equals) chỉ ghi đè value, không thêm entry mới. Lưu ý: thứ tự in của HashMap/HashSet phụ thuộc hash, capacity và không được đảm bảo — output trên là một lần chạy thật với JDK 25, đừng viết code dựa vào thứ tự đó. Capacity mặc định 16, load factor 0.75: khi số entry vượt 16 × 0.75 = 12, map nhân đôi số bucket và phân bố lại. Chi phí trung bình của get/put là O(1). Đây là kiến thức nền; phần tối ưu sâu (capacity, load factor, va chạm hash) thuộc GĐ3.

BigDecimal — equals so cả scale

BigDecimal.equals yêu cầu cùng giá trị và cùng scale, còn compareTo chỉ so giá trị. Vì vậy 1.0 và 1.00 là equal theo compareTo nhưng unequal theo equals — kéo theo hash khác nhau:

import java.math.BigDecimal;
import java.util.HashSet;
import java.util.Set;
import java.util.TreeSet;

void main() {
    BigDecimal a = new BigDecimal("1.0");
    BigDecimal b = new BigDecimal("1.00");

    IO.println("a.equals(b)         : " + a.equals(b));
    IO.println("a.compareTo(b) == 0 : " + (a.compareTo(b) == 0));
    IO.println("a.hashCode()        : " + a.hashCode());
    IO.println("b.hashCode()        : " + b.hashCode());

    Set<BigDecimal> hash = new HashSet<>();
    hash.add(a);
    hash.add(b);
    IO.println("HashSet size        : " + hash.size());

    tree.add(a);
    tree.add(b);
    IO.println("TreeSet size        : " + tree.size());

a.compareTo(b) == 0 : true
a.hashCode()        : 311
b.hashCode()        : 3102

Hệ quả: cùng là 1 đồng nhưng HashSet giữ 2 phần tử, TreeSet giữ 1. Nghiệp vụ tiền tệ nên so bằng compareTo(...) == 0. Nếu buộc dùng làm key, hãy chuẩn hoá scale trước (stripTrailingZeros() hoặc quy định mọi giá trị cùng scale như setScale(2)).

Quy tắc nhất quán compareTo ↔ equals: Javadoc của Comparable khuyến nghị mạnh (x.compareTo(y) == 0) == x.equals(y). Khi vi phạm, hai collection "nhìn" dữ liệu khác nhau: TreeSet/TreeMap dùng compareTo nên coi 1.0 và 1.00 là một, còn HashSet/HashMap dùng equals + hashCode nên giữ cả hai — đúng như ví dụ BigDecimal phía trên.

String.equals so nội dung, String.hashCode có công thức ổn định (s[0]*31^(n-1) + ...) nên rất hợp làm key. Wrapper (Integer, Long...) cũng so giá trị, nhưng nhớ bẫy cache: Integer.valueOf cache sẵn từ -128 đến 127 theo JLS, ngoài khoảng đó mỗi lần boxing có thể tạo object mới:

Vì vậy == đôi khi đúng với số nhỏ và sai với số lớn — không bao giờ dùng == để so wrapper, luôn dùng equals.

Lombok

Lombok sinh bộ ba bằng annotation, code ngắn hơn nhiều — nhưng cần dependency nên ví dụ dưới đây không chạy trong môi trường thuần của trang này:

Ba cảnh báo Lombok: (1) Kế thừa mà quên callSuper = true thì equals/hashCode của lớp con bỏ qua state lớp cha — sai hợp đồng. (2) @EqualsAndHashCode mặc định gom mọi field non-static, non-transient — với entity JPA, field id là null trước khi persist nên nhiều entity "mới" sẽ equal nhau; quan hệ lười tải cũng có thể bị equals chạm vào. (3) Entity JPA tốt nhất dùng business key (mã đơn hàng, sku) hoặc viết equals/hashCode thủ công theo id.

Value object trong production

  • Giá trị thuần (toạ độ, tiền tệ, mã sản phẩm, DTO) → record; hết bug quên hashCode.
  • Key của HashMap/HashSet → phải bất biến; không dùng entity mutable có id sinh tự động.
  • Class có equals theo giá trị mà muốn yên tâm về symmetry → để final hoặc dùng composition thay vì kế thừa.
  • Đừng đưa field "phái sinh"/cache/logger vào equals — chỉ field định danh giá trị.

Giống tinh thần "kiểm thử method ngay khi viết" ở 1.5 Methods, hãy kiểm tra hợp đồng bằng các ca cố định trước khi tin vào class của mình. Điểm khác: equals/hashCode có hợp đồng hình thức trong Javadoc Object, nên test không phải "chạy thử vài ca" mà phải phủ đúng các tính chất.

12.2 Test thuần Java — assert + main

Chưa cần thư viện, chỉ cần một method check như "assert tự chế". Bộ test thủ công chạy thật:

import java.util.Objects;

    final String sku;
    final long price;

    Product(String sku, long price) {
        this.sku = sku;
        this.price = price;

    @Override

        if (this == o) return true;

    }

    @Override
    public int hashCode() {
        return Objects.hash(sku, price);
    }
}

}

15. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Hợp đồng equals gồm những tính chất nào?
Năm tính chất: reflexive (x.equals(x) true), symmetric (x.equals(y) == y.equals(x)), transitive (x=y, y=z ⇒ x=z), consistent (kết quả ổn định nếu state không đổi), và non-nullity (x.equals(null) trả false, không ném NPE). Nói cách khác equals phải là quan hệ tương đương trên các object.
Câu 2. == và equals khác nhau thế nào?
== so giá trị với primitive và so reference với object. equals mặc định trong Object cũng so reference (return this == obj;), nhưng có thể override để so giá trị. Vì vậy với object chưa override, hai khái niệm giống nhau; sau khi override, equals là "so nội dung" còn == vẫn là "cùng một object".
Câu 3. Mặc định Object cho ta những gì ở ba method này?
equals so identity (this == obj); hashCode trả identity hash — khác nhau giữa các object khác nhau nhưng không hứa con số cụ thể và có thể khác giữa các lần chạy JVM; toString trả getClass().getName() + "@" + Integer.toHexString(hashCode()), ví dụ Point@b59d31.
Câu 4. Vì sao nên override toString?
Để log, debugger và thông báo lỗi test hiển thị dữ liệu có nghĩa thay vì Product@1b6d3586. Nối chuỗi ("x=" + obj) cũng tự gọi toString. Record tự sinh sẵn theo dạng Product[sku=SKU-1, price=199000]. Lưu ý không đưa dữ liệu nhạy cảm vào và đừng parse output của toString bằng code.
Câu 5. Vì sao override equals thì phải override hashCode?
Vì điều khoản 2 của hashCode: object equal phải có hash bằng nhau. HashMap/HashSet tìm bucket bằng hashCode trước rồi mới so equals. Nếu equal mà hash khác, hai object rơi vào hai bucket khác nhau và collection "không nhìn thấy" nhau dù equals trả true.
Câu 6. Chỉ override equals mà quên hashCode thì chuyện gì xảy ra?
HashSet.add hai object equal sẽ giữ cả hai (size 2), contains/get bằng object equal khác trả về false/null — dù bản thân a.equals(b) là true. Đây là bug kinh điển; xem demo đầy đủ ở mục 8.
Câu 7. Chỉ override hashCode mà không equals thì sao?
Không dedupe được: equals vẫn theo identity nên hai object cùng nội dung vẫn bị coi là khác nhau, HashSet giữ cả hai. Nếu hashCode trả cùng một giá trị cho mọi object, chúng dồn vào một bucket → tìm kiếm chậm dần. Hợp đồng không bị vi phạm (unequal được phép trùng hash), nhưng class vô dụng về mặt value equality.
Câu 8. record tự sinh gì và equals của nó có đúng hợp đồng không?
Record tự sinh constructor, accessor, equals, hashCode, toString dựa trên các component, và equals tuân đủ 5 tính chất. Bẫy: component là mảng thì so reference (Objects.equals trên mảng), component mutable thì record vẫn có thể bị mutate; hash của record không được đảm bảo giống nhau giữa các lần chạy JVM.
Câu 9. Hai object không equals có thể cùng hashCode không?
Có, gọi là collision và hoàn toàn hợp lệ — ví dụ "Aa" và "BB" đều có hash 2112. Vì không gian hash chỉ 32 bit nên không thể đảm bảo khác nhau cho mọi object. Collision chỉ ảnh hưởng hiệu năng (bucket dài), tính đúng đắn do equals quyết định.
Câu 10. hashCode có phải giống nhau giữa các lần chạy chương trình không?
Không. Hợp đồng chỉ yêu cầu consistent trong một lần thực thi khi state không đổi. Object.hashCode (identity hash) và hash của record có thể khác giữa các lần chạy. Ngoại lệ: các class như String, Integer có công thức hash được đặc tả nên ổn định. Vì vậy đừng lưu hash vào DB/file rồi so sánh ở lần chạy sau.

Junior+

Câu 11. Trong equals nên dùng getClass hay instanceof?
Nếu class final/record, cả hai tương đương. Nếu mở kế thừa: getClass bảo vệ symmetry (chỉ cùng class chính xác mới equal) nhưng lớp con thêm field sẽ không bao giờ bằng lớp cha; instanceof cho lớp con bằng lớp cha nếu field chung khớp, dễ vỡ symmetry nếu lớp con thêm state và override equals — đúng như Timestamp vs Date. Effective Java khuyên ưu tiên composition hơn kế thừa cho value object.
Câu 12. Cho ví dụ vi phạm tính symmetric.
Kinh điển trong JDK: Timestamp kế thừa Date và thêm nanos; date.equals(ts) là true còn ts.equals(date) là false — javadoc của Timestamp thừa nhận điều này. Tự tạo cũng dễ: lớp cha dùng instanceof, lớp con thêm field và dùng getClass → một chiều. Demo chạy thật ở mục 4.
Câu 13. Vì sao dùng object mutable làm key HashMap rất nguy hiểm?
Vì HashMap chọn bucket theo hash tại thời điểm put. Sửa field tham gia tính hash sau đó làm hash đổi, entry nằm ở bucket cũ nhưng get lại tìm ở bucket mới → trả null dù entry vẫn còn (value vẫn thấy qua containsValue/duyệt map). Cách phòng: key bất biến (record/String/wrapper), hoặc remove trước khi sửa và put lại.
Câu 14. Objects.equals và Objects.hash có gì hay, có bẫy gì?
Objects.equals(a, b) null-safe: cả hai null → true, một null → false, không NPE. Objects.hash(...) gọn cho nhiều field nhưng thực chất là Arrays.hashCode(new Object[]{...}); bẫy: với đúng một tham số, Objects.hash(sku) != sku.hashCode() (nó cộng thêm 31). Muốn hash của một field, dùng Objects.hashCode(field).
Câu 15. BigDecimal khác nhau thế nào giữa equals và compareTo?
equals yêu cầu cùng giá trị và cùng scale nên new BigDecimal("1.0").equals(new BigDecimal("1.00")) là false; compareTo(...) == 0 là true. Hash của hai object cũng khác nên HashSet giữ 2 phần tử trong khi TreeSet giữ 1. Nghiệp vụ tiền nên so compareTo; làm key thì chuẩn hoá scale trước.
Câu 16. So sánh hai mảng trong Java thế nào cho đúng?
Không dùng == hay equals (mảng không override, luôn so reference → false). Dùng Arrays.equals(a, b) cho mảng một chiều và Arrays.deepEquals(a, b) cho mảng lồng nhau; hash bằng Arrays.hashCode/Arrays.deepHashCode. Tốt nhất là tránh dùng mảng làm key/field của value object.
Câu 17. Vì sao so String phải dùng equals? Vì sao Integer a == b lúc đúng lúc sai?
String literal cùng nội dung được chia sẻ trong string pool nên == đôi khi true, nhưng chuỗi tạo động (new String, nối chuỗi, substring) là object mới nên == false. Wrapper có cache -128..127 theo JLS: Integer 127 == 127 true, 128 == 128 false. Quy tắc: luôn equals/Objects.equals cho mọi object.
Câu 18. Vì sao enum so sánh bằng == là an toàn?
Mỗi hằng enum là một singleton do JVM tạo đúng một lần, nên reference là duy nhất cho mỗi hằng. Enum.equals được final và bên trong dùng ==. Dùng == còn an toàn null (trả false thay vì NPE) và nhanh hơn gọi method — đây là ngoại lệ được khuyến nghị của quy tắc "so object bằng equals".
Câu 19. Vì sao phải viết equals(Object) mà không phải equals(Product)?
Vì equals được khai báo trong Object với tham số Object; viết tham số cụ thể chỉ tạo overload mới, không override. Collection và framework luôn gọi qua kiểu Object nên method của bạn bị bỏ qua. Luôn dùng @Override để compiler báo lỗi nếu chữ ký sai (xem mục 5).
Câu 20. a.equals(null) có ném lỗi không? null.equals(a) thì sao?
a.equals(null) phải trả false theo hợp đồng (implementation đúng kiểm tra o == null trước khi cast). Nhưng null.equals(a) ném NullPointerException vì bạn gọi method trên reference null. Vì vậy: dùng Objects.equals(a, b), hoặc đặt hằng số/giá trị chắc chắn khác null ở bên trái như "ADMIN".equals(role).
Câu 21. Lombok @EqualsAndHashCode có bẫy gì?
Ba bẫy chính: (1) class kế thừa mà quên callSuper = true thì equals/hashCode bỏ qua state lớp cha — sai hợp đồng; (2) mặc định gom mọi field non-static/non-transient, kể cả field cache hoặc quan hệ lười tải; (3) entity JPA với id sinh tự động: id là null trước khi persist nên mọi entity mới equal nhau — nên viết tay theo business key hoặc id.

Production

Câu 22. Chọn field nào để đưa vào equals/hashCode?
Chọn đúng những field định danh giá trị của object (sku, toạ độ, số tiền…), bất biến và ổn định. Hai method phải dùng cùng một bộ field — thứ tự field chỉ làm đổi giá trị hash chứ không ảnh hưởng tính đúng đắn. Loại bỏ field phái sinh (tính lại được), field cache/logger, field thay đổi theo thời gian (lastUpdated, viewCount). Với entity, dùng business key hoặc id; tránh id sinh tự động còn null.
Câu 23. toString có được chứa dữ liệu nhạy cảm không? Có nên gọi DB trong toString?
Không nên chứa mật khẩu, token, số thẻ, thông tin cá nhân — log bị ghi ra file, console, hệ thống log tập trung, rất khó thu hồi. Cũng không nên để toString kích hoạt lazy loading (gọi quan hệ JPA) vì dễ gây N+1 query hoặc LazyInitializationException. toString chỉ nên đọc state đơn giản, đã che dữ liệu nếu cần.
Câu 24. Khi nào nên dùng record thay vì tự viết bộ ba method?
Khi object là value object/DTO bất biến và các component không phải mảng/mutable object — record cho code ngắn nhất, đúng hợp đồng nhất, tự cập nhật khi thêm component. Không phù hợp khi cần mutable state, constructor rỗng (framework cũ), hoặc class có hành vi phức tạp kiểu entity JPA — lúc đó viết class thường (hoặc dùng Lombok cẩn thận). Nhớ hash của record có thể khác giữa các lần chạy JVM nên đừng lưu lại.

Checklist tự đánh giá trước phỏng vấn
