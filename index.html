2. Cú pháp khai báo

[modifier] type variableName = value;

Ba thành phần, theo đúng thứ tự:

  • type — kiểu dữ liệu (int, String, BigDecimal...). Bắt buộc.
  • variableName — tên bạn tự đặt, theo quy tắc camelCase. Bắt buộc.
  • = value — giá trị ban đầu. Có thể bỏ, gán sau cũng được.
public class VariablesDemo {
    public static void main() {
        // Khai báo và gán giá trị ngay
        String ten = "Nguyen Van An";
        int tuoi = 25;
        double diemTrungBinh = 8.75;
        char xepLoai = 'A';
        boolean dangLamViec = true;

        IO.println(ten);            // Nguyen Van An
        IO.println(tuoi);           // 25
        IO.println(diemTrungBinh);  // 8.75
        IO.println(xepLoai);        // A
        IO.println(dangLamViec);    // true
    }
}
Ví dụ dùng IO.println(...) — cách viết gọn của JDK 25 (JEP 512), tương đương System.out.println(...) mà bạn sẽ thấy trong đề phỏng vấn và tài liệu cũ.

Quy tắc đặt tên (Identifiers)

  • Được dùng: chữ cái, chữ số, dấu gạch dưới _ và $. Không bắt đầu bằng chữ số.
  • Không được trùng từ khóa: class, int, static, final, new...
  • Phân biệt hoa thường: age và Age là hai biến khác nhau.
  • Quy ước: biến camelCase (userId), hằng số UPPER_SNAKE_CASE (MAX_SIZE), class PascalCase (UserService).
  • Tên phải có nghĩa: retryCount tốt hơn x; tránh tmp, data1, data2.

Field (biến khai báo trong class) được Java gán mặc định. Còn biến local không có giá trị mặc định — phải gán trước khi dùng, nếu không compiler chặn ngay. Đây là câu hỏi phỏng vấn rất hay gặp.

4. Literals — cách viết giá trị

Literal là giá trị viết thẳng trong code — không qua biến, không qua constructor. Java quy định chặt cách viết từng nhóm literal, và vài bẫy ở đây từng gây bug production thật: số có 0 ở đầu bị hiểu là hệ 8, hằng số vượt int mà quên hậu tố L, \uXXXX chạy trước cả comment... Mục này đi từng nhóm, output đều chạy thật trên JDK 25.

    public static void main() {

        int hex = 0xFF;               // he 16  -> 255

        IO.println("hex : " + hex);   // hex : 255

  • int là kiểu mặc định của literal số nguyên; thêm L để thành long.
  • 1.5 mặc định là double; thêm f/F để thành float. Hậu tố D/d cho double là tuỳ chọn, viết để rõ ý.
  • Hậu tố long nên viết hoa L — chữ thường l nhìn như số 1: 10l trông giống 101.

4.2 Underscore — chỉ được nằm giữa hai chữ số

Từ Java 7, bạn được chèn _ để nhóm chữ số. Luật duy nhất: underscore phải nằm giữa hai chữ số. Trong bốn hệ đếm, trước hậu tố, giữa các chữ số của phần thập phân — tất cả đều hợp lệ:

public class UnderRules {
    public static void main() {
        int a = 1__0;                       // nhieu gach lien tiep: HOP LE
        double d = 1_0.0_1;                 // giua cac chu so: OK
        int e = 0x7fff_ffff;                // trong hex: OK
        float g = 1_0f;                     // truoc hau to: OK
        long h = 1_000_000L;                // truoc L: OK
        int big = 2_1_4_7_4_8_3_6_4_7;

        IO.println("a   : " + a);    // a   : 10
        IO.println("d   : " + d);    // d   : 10.01
        IO.println("e   : " + e);    // e   : 2147483647
        IO.println("g   : " + g);    // g   : 10.0
        IO.println("h   : " + h);    // h   : 1000000
        IO.println("big : " + big);  // big : 2147483647
    }
}

Ba vị trí sai kinh điển: cuối số, ngay sau tiền tố hệ đếm, và cạnh dấu chấm thập phân — javac 25 báo đủ ba lỗi:

Từ Java 22, gạch dưới đơn _ còn là "unnamed variable": int _ = 5; khai báo được nhưng không được đọc (lỗi underscore not allowed here).

4.3 Ba bẫy số nguyên: 09, 2147483648, 0x80000000

09 sai vì hệ 8 chỉ có chữ số 0–7 — literal hỏng ngay từ bước lexer, chưa tới phần kiểu:

LitZeroNine.java:3: error: illegal digit in an octal literal

Hằng số thập phân vượt Integer.MAX_VALUE cũng bị chặn, dù biến nhận là long — vì literal được định kiểu trước khi gán:

LitDecimalOverflow.java:3: error: integer number too large
        long x = 2147483648;
                 ^
1 error

Sửa bằng hậu tố: long x = 2147483648L;. Thú vị ở chỗ literal hex/binary/bát phân không chịu luật này — chúng biểu diễn bit pattern 32 bit theo bù hai, nên 0x80000000 là literal int hợp lệ và chính bằng Integer.MIN_VALUE:

public class LitHexMin {
    public static void main() {
        int x = 0x80000000;
        IO.println("x           : " + x);                            // x           : -2147483648
        IO.println("x == MIN    : " + (x == Integer.MIN_VALUE));      // x == MIN    : true
        IO.println("0xFFFFFFFF  : " + 0xFFFFFFFF);                    // 0xFFFFFFFF  : -1
        IO.println("0b111...    : " + 0b11111111111111111111111111111111); // 0b111...    : -1
    }
}
Nhớ nhanh: literal thập phân là giá trị có dấu (tối đa 2147483647); literal hex/binary/octal là bit pattern (tối đa 32 bit, đọc theo bù hai). Đây là lý do 0x80000000 qua được còn 2147483648 thì không.

4.4 Số thực — dấu chấm, ký pháp khoa học, hex float

double nhận cả dạng thiếu phần nguyên (.5), ký pháp khoa học (1e3, 1e-3), cả hex float (0x1.8p1 = 1.5 × 21 = 3.0). Nhưng literal có dấu chấm mặc định là double, muốn ra float phải thêm hậu tố:

public class LitReal {
    public static void main() {
        double a = .5;
        double b = 1e3;
        double c = 0x1.8p1;
        float d = 0x1.8p1f;
        double e = 1e-3;
        double g = 1_000.5_5;

        IO.println("a : " + a);   // a : 0.5
        IO.println("b : " + b);   // b : 1000.0
        IO.println("c : " + c);   // c : 3.0
        IO.println("d : " + d);   // d : 3.0
        IO.println("e : " + e);   // e : 0.001
        IO.println("g : " + g);   // g : 1000.55
    }
}

4.5 char — một ký tự là một con số

char viết nháy đơn, chứa escape sequence, và tham gia tính toán như int (numeric promotion — mục 8):

public class LitChar {
    public static void main() {
        char newline = '\n';
        char tab = '\t';
        char single = '\'';
        char backslash = '\\';
        char a = '\u0041';
        char c = 'a';
        c++;

        IO.println("newline  : " + (int) newline);   // newline  : 10
        IO.println("tab      : " + (int) tab);       // tab      : 9
        IO.println("single   : " + single);          // single   : '
        IO.println("backslash: " + backslash);       // backslash: \
        IO.println("unicode  : " + a);               // unicode  : A
        IO.println("c        : " + c);               // c        : b
        IO.println("c + 1    : " + (c + 1));         // c + 1    : 99
        IO.println("(char)   : " + (char) (c + 1));  // (char)   : c
    }
}

Unicode escape chạy TRƯỚC lexer. \uXXXX được dịch thành ký tự thật ở một bước tiền xử lý, trước khi compiler hiểu comment/chuỗi (JLS 3.3). Hệ quả: \u000a (xuống dòng) cắt đứt comment và "thả" phần code phía sau ra ngoài:

public class LitUnicodeTrap {
    public static void main() {
        // comment \u000a IO.println("dong nay bi lo ra");
        IO.println("ket thuc");
    }
}

Sau tiền xử lý, dòng comment bị cắt tại \u000a thành hai dòng, nên lệnh IO.println kia trở thành code thật. Chương trình in hai dòng:

4.6 String, text block, null và boolean

String viết nháy kép (là object, không phải primitive — xem mục 14); null là literal duy nhất của reference rỗng; boolean chỉ có đúng hai literal true/false — khác JS, nơi mọi giá trị truthy/falsy đều dùng được trong điều kiện:

public class LitString {
    public static void main() {
        String quote = "Noi dung \"trong nhay kep\"";
        String path = "C:\\Users\\an";
        boolean ok = true;
        boolean off = false;
        String nothing = null;
        String block = """
                dong 1
                dong 2""";

        IO.println(quote);      // Noi dung "trong nhay kep"
        IO.println(path);       // C:\Users\an
        IO.println(ok);         // true
        IO.println(off);        // false
        IO.println(nothing);    // null
        IO.println(block);
        // dong 1
        // dong 2
    }
}
Text block dùng ba nháy kép, giữ nguyên xuống dòng (Java 15+). Cú pháp đầy đủ, stripIndent, nối dòng bằng \... ở Strings — mục 5. Bộ escape của chuỗi/ký tự: \t \b \n \r \f \' \" \\ và octal escape ('\101' = 'A') — rất hiếm dùng.

  • Hệ bát phân: JS hiện đại viết 0o17; dạng cũ 017 chỉ chạy ở sloppy mode — trong ESM/strict ném SyntaxError: Octal literals are not allowed in strict mode.

5. Gán, ghi đè, khai báo trước

Khai báo trước rồi gán sau là chuyện thường ngày. Nhưng Java có ba chi tiết mà JS không có: phép gán là một biểu thức trả về giá trị (nên gán dây chuyền được), compiler kiểm tra definite assignment (không có undefined), và thứ tự đánh giá hai vế được quy định chặt chẽ.

5.1 Gán là biểu thức — nó trả về giá trị

public class AssignExpr {
    public static void main() {
        int b;
        int a = b = 3;                  // (b = 3) tra ve 3, roi gan cho a
        IO.println("a = " + a);          // a = 3
        IO.println("b = " + b);          // b = 3

        int x, y, z;
        x = y = z = 7;                   // gan day chuyen
        IO.println("x y z = " + x + " " + y + " " + z);   // x y z = 7 7 7

        double d;
        int i;
        d = i = 5;                       // i = 5 tra ve int, widening sang double
        IO.println("d = " + d);          // d = 5.0
        IO.println("i = " + i);          // i = 5
    }
}

Biểu thức gán có kiểu và giá trị của biến bên trái — nên d = i = 5 hợp lệ (giá trị int 5 được widening sang double), còn int i = d = 5.0 thì lỗi. Lần gán sau không cần ghi lại kiểu vì kiểu đã cố định từ lúc khai báo, và không thể gán String vào biến int.

5.2 Definite assignment — local phải gán trước khi đọc

Khác JS (biến chưa gán đọc ra undefined), Java chặn ngay lúc compile. Compiler phân tích mọi nhánh if/else, vòng lặp, switch để chắc chắn biến local đã có giá trị trên mọi đường đi tới chỗ đọc:

DefAssignError.java:4: error: variable x might not have been initialized
        IO.println(x);
                   ^
1 error

Field thì ngược lại — luôn có giá trị mặc định. Biến final blank cũng theo luật definite assignment: phải gán đúng một lần trên mọi nhánh trước khi dùng:

public class DefAssignFlow {
    static int field;
    static boolean flag;
    static String name;

    public static void main() {
        IO.println("field int    : " + field);   // field int    : 0
        IO.println("field boolean: " + flag);    // field boolean: false
        IO.println("field String : " + name);    // field String : null

        int n;
        int mode = 1;
        if (mode > 0) {
            n = 10;
        } else {
            n = 20;
        }

    }

5.4 Thứ tự đánh giá — trái trước, phải sau

Với phép gán vào mảng, Java đánh giá tham chiếu mảng và chỉ số trước, rồi mới tính vế phải:

import java.util.Arrays;

public class AssignEvalOrder {
    public static void main() {
        int[] arr = {10, 20, 30};
        int i = 0;
        arr[i] = i++;
        IO.println("arr = " + Arrays.toString(arr));  // arr = [0, 20, 30]
        IO.println("i   = " + i);                     // i   = 1

        int[] a = {1, 2, 3};
        int j = 0;
        a[j] = ++j;
        IO.println("a   = " + Arrays.toString(a));    // a   = [1, 2, 3]
        IO.println("j   = " + j);                     // j   = 1
    }
}

Ở arr[i] = i++, chỉ số lấy i = 0 trước; vế phải i++ trả về 0 rồi mới tăng i lên 1 → arr[0] = 0, i = 1. Còn a[j] = ++j cũng lấy chỉ số 0 trước, nhưng vế phải tăng j lên 1 rồi trả 1 → a[0] = 1, mảng không đổi. Bẫy này hay xuất hiện trong đề phỏng vấn; code production đừng viết i++ chung dòng với việc dùng i.

Chốt gọn: gán là biểu thức trả về giá trị (a = b = 3 chạy được) → local bắt buộc definitely assigned trước khi đọc; field có default; blank final gán đúng một lần trên mọi nhánh → gán được khi widening/boxing/hằng số vừa khoảng; compound assignment ngầm ép kiểu (s += 1, i += 2.5) → vế trái của phép gán mảng được đánh giá trước: arr[i] = i++ cho arr[0] = 0, i = 1.

6. Scope & vòng đời biến

Scope trả lời "biến này nhìn thấy được ở đâu"; vòng đời trả lời "nó sống đến bao giờ". Hai chuyện khác nhau: ra khỏi scope chưa chắc object bị xoá — GC chỉ thu hồi khi không còn ai tham chiếu tới. Mục này tách rõ ba loại biến, các tầng scope và đường đi trong bộ nhớ.

6.1 Ba loại biến

  • Biến local — khai báo trong method hoặc block { }, chỉ sống trong phạm vi đó. Hết method/block là biến "chết".
  • Field (instance variable) — khai báo trong class, mỗi object có một bản riêng, sống theo object.
  • Static field — dùng chung cho mọi object của class, sống theo class. Kèm final thành hằng số.
public class User {
    private String name;                          // field: mỗi object có bản riêng
    private static int userCount = 0;             // static: dùng chung mọi object
    public static final int MAX_NAME_LEN = 100;   // hằng số

    User(String name) {
        this.name = name;
        userCount++;
    }

    void rename(String newName) {
        String trimmed = newName.trim();          // local: chỉ sống trong method này
        this.name = trimmed;
    }
}

6.2 Block scope — sống trong cặp ngoặc nhọn

Biến khai báo trong { } chỉ thấy trong block đó; biến vòng lặp for (int k = ...) chỉ sống trong vòng lặp. In inner hay k ra ngoài là lỗi cannot find symbol:

public class ScopeBlock {
    public static void main() {
        int outer = 1;
        {
            int inner = 2;
            IO.println("trong block: " + outer + ", " + inner);   // trong block: 1, 2
        }
        IO.println("ngoai block: " + outer);                     // ngoai block: 1

        for (int k = 0; k < 2; k++) {
            int step = k * 10;
            IO.println("for: " + k + " -> " + step);              // for: 0 -> 0
        }                                                         // for: 1 -> 10
    }
}

6.3 for-each và switch case — hai chỗ dễ sập bẫy

Vòng for-each tạo một biến mới mỗi vòng lặp; gán vào nó không sửa mảng gốc:

import java.util.Arrays;

public class ScopeForEach {
    public static void main() {
        int[] nums = {1, 2, 3};
        for (int n : nums) {
            n = n * 10;
            IO.println("n = " + n);   // n = 10
        }                             // n = 20
                                      // n = 30
        IO.println("mang = " + Arrays.toString(nums));   // mang = [1, 2, 3]
    }
}

Với switch kiểu cũ, các case chia sẻ cùng một scope — khai báo trùng tên ở hai case là lỗi, dù hai case không bao giờ chạy cùng nhau:

Cách sửa: bọc mỗi case trong { } để tạo scope riêng — hoặc dùng switch mũi tên -> (Java 14+), mỗi nhánh đã là một scope:

6.4 Shadowing — che tên, nhưng có giới hạn

Local được phép trùng tên field; muốn chỉ field thì dùng this.:

public class ScopeShadow {
    int value = 100;

    void run() {
        IO.println("field      : " + value);        // field      : 100
        int value = 5;
        IO.println("local      : " + value);        // local      : 5
        IO.println("this.field : " + this.value);   // this.field : 100
    }

    public static void main() {
        new ScopeShadow().run();
    }
}

Nhưng local không được trùng local khác đang còn hiệu lực — kể cả trong block con (khác C/C++), kể cả khi local ngoài không được dùng lại:

ScopeRedeclareError.java:5: error: variable x is already defined in method main()
            int x = 2;
                ^
1 error

Lambda nằm trong scope của method chứa nó, nên khai báo biến trong thân lambda cũng không được trùng:

ScopeLambdaError.java:5: error: variable x is already defined in method main()
            int x = 2;
                ^

Khác Java, JS cho phép shadowing kiểu { let x = 1; { let x = 2; } }. Sang Java, thói quen đặt tên local trùng nhau sẽ bị compiler chặn — hãy coi đó là tính năng: mỗi tên chỉ mang một nghĩa trong cùng method.

6.5 Vòng đời — stack, heap và GC reachability

Biến local nằm trên stack theo frame của method; hết method là frame bị pop. Nhưng object trên heap chỉ bị GC thu hồi khi không còn tham chiếu — nếu object đã được nhét vào list/field, nó vẫn sống dù biến local biến mất:

import java.util.ArrayList;
import java.util.List;

public class ScopeLife {
    static List<String> store = new ArrayList<>();

    static void addLocal() {
        String s = new String("giu boi store");
        store.add(s);
        IO.println("trong method: " + s);   // trong method: giu boi store
    }

    public static void main() {
        addLocal();
        IO.println("ngoai method: " + store);      // ngoai method: [giu boi store]
        IO.println("size        : " + store.size()); // size        : 1
    }
}

Ngược lại, local bị lambda/anonymous class capture sẽ được "chuyển" sang heap để sống lâu hơn method — cũng là lý do biến capture phải final/effectively final (mục 10.5):

public class ScopeCapture {
    interface Counter {
        int inc();
        int value();
    }

    static Counter makeCounter() {
        int[] count = {0};
        return new Counter() {
            public int inc() {
                return ++count[0];
            }

            public int value() {
                return count[0];
            }
        };
    }

    public static void main() {
        Counter c = makeCounter();
        c.inc();
        c.inc();
        c.inc();
        IO.println("count = " + c.value());   // count = 3
    }
}
Vẽ nhanh: local primitive + reference → stack frame; object → heap; field → heap theo object; static → heap theo class. GC chỉ quan tâm "còn reachable từ root (stack, static...) không", không quan tâm biến đã ra khỏi scope hay chưa. Chi tiết ở mục 7.

7. Stack vs Heap & pass-by-value Hay hỏi phỏng vấn Junior+

Hiểu chỗ này thì mọi câu hỏi "biến lưu ở đâu", "truyền tham số thế nào" đều giải được. JVM chia bộ nhớ thành hai vùng chính:

  • Stack — mỗi thread có stack riêng. Chứa biến local primitive (int x = 5 lưu thẳng số 5) và địa chỉ của object. Tổ chức theo kiểu LIFO như chồng đĩa; nhanh, nhỏ; hết thì StackOverflowError.
  • Heap — dùng chung cho mọi thread. Chứa object thật (new ArrayList<>(), String...). Lớn; được Garbage Collector dọn dẹp; hết thì OutOfMemoryError.

Câu hỏi phỏng vấn kinh điển: "Java truyền tham số theo giá trị hay tham chiếu?" — Trả lời: luôn theo giá trị. Nhưng với object, giá trị được truyền là bản sao của địa chỉ, nên bạn sửa được nội dung object, mà gán lại reference bên trong method thì bên ngoài không đổi.

public class PassByValueDemo {

9. Tràn số Hay hỏi phỏng vấn Production

Số nguyên Java biểu diễn theo bù hai (two's complement) với số bit cố định: int 32-bit, long 64-bit. Khi kết quả vượt khỏi khoảng biểu diễn, Java không ném exception mà quay vòng (wraparound) âm thầm — bug rất khó tìm vì kết quả vẫn là một số "trông bình thường". Riêng float/double theo IEEE 754 có hành vi khác hẳn (mục 9.5).

9.1 Wraparound — quay vòng ở hai đầu mút

Cộng 1 vào Integer.MAX_VALUE không báo lỗi mà nhảy sang Integer.MIN_VALUE. Phép chia cho -1 và abs cũng có "góc chết":

IO.println("MIN / -1      : " + (min / -1));     // -2147483648
IO.println("MIN % -1      : " + (min % -1));     // 0
IO.println("-MIN          : " + (-min));         // -2147483648
IO.println("Math.abs(MIN) : " + Math.abs(min));  // -2147483648

IO.println("1e6 * 1e6     : " + (1_000_000 * 1_000_000)); // -727379968

int x = max;
x += 1;
IO.println("x += 1        : " + x);              // -2147483648

9.2 Phát hiện & chống tràn bằng Math.*Exact

Từ Java 8, nhóm method …Exact kiểm tra trước khi tính và ném ArithmeticException đúng lúc thay vì để tràn âm thầm. Message chỉ có hai dạng: "integer overflow" (phép int) và "long overflow" (phép long):

    Math.addExact(Integer.MAX_VALUE, 1);
} catch (ArithmeticException e) {
    IO.println("int  : " + e.getMessage());   // int  : integer overflow
}

try {
    Math.addExact(Long.MAX_VALUE, 1L);
} catch (ArithmeticException e) {
    IO.println("long : " + e.getMessage());   // long : long overflow
}

Nếu cần thông báo lỗi nghiệp vụ thay vì exception chuẩn, tự kiểm tra trước khi cộng — chỉ cần xét khi hai số cùng dấu:

static long addSafely(long a, long b) {
    if (a > 0 && b > 0 && a > Long.MAX_VALUE - b) {
        throw new ArithmeticException("long overflow");
    }
    if (a < 0 && b < 0 && a < Long.MIN_VALUE - b) {
        throw new ArithmeticException("long underflow");
    }
    return a + b;
}

IO.println("2 + 3   : " + addSafely(2, 3));   // 5

Cách dùng đúng: bọc ở biên (tính tiền, phân trang, timestamp, chỉ số mảng) rồi để exception nổi lên tầng xử lý lỗi — đừng nhồi try/catch khắp nơi. …Exact chỉ chậm hơn phép thường một chút, đổi lại là tính đúng đắn.

9.3 Bug kinh điển: binary search, thời gian, giai thừa

Bug nổi tiếng nhất của wraparound nằm trong chính JDK: java.util.Arrays.binarySearch tính mid = (lo + hi) / 2. Khi lo + hi vượt Integer.MAX_VALUE (mảng cỡ hơn 230 phần tử), tổng tràn thành số âm → tìm kiếm sai. Bug tồn tại gần 9 năm trong JDK trước khi Joshua Bloch phát hiện năm 2006; bản sửa dùng dịch phải không dấu:

int lo = 1_000_000_000;
int hi = 2_000_000_000;

IO.println("(lo + hi) / 2  : " + (lo + hi) / 2);           // -647483648
IO.println("lo+(hi-lo)/2   : " + (lo + (hi - lo) / 2));     // 1500000000
IO.println("(lo + hi) >>> 1: " + ((lo + hi) >>> 1));        // 1500000000

Vì sao >>> sửa được? Tổng trong bù hai vẫn đúng theo modulo 232, chỉ bit dấu sai; dịch phải không dấu coi 32 bit đó là số không âm nên ra đúng trung bình cộng (với lo, hi ≥ 0).

Hai ca "đời thường" hơn cũng là tràn int khi tính thời gian và khi ép kiểu ngầm:

IO.println("30 ngay int ms : " + (1000 * 60 * 60 * 24 * 30));  // -1702967296
IO.println("30 ngay long ms: " + (1000L * 60 * 60 * 24 * 30)); // 2592000000
IO.println("1 nam int ms   : " + (1000 * 60 * 60 * 24 * 365));  // 1471228928
IO.println("1 nam long ms  : " + (1000L * 60 * 60 * 24 * 365)); // 31536000000

long now = System.currentTimeMillis();
long bad = now + 30 * 24 * 3600 * 1000;
long good = now + 30L * 24 * 3600 * 1000;
IO.println("bad  < now     : " + (bad < now));    // true  - "30 ngay sau" lai o qua khu
IO.println("good > now     : " + (good > now));   // true
IO.println("delta bad      : " + (bad - now));    // -1702967296
IO.println("delta good     : " + (good - now));   // 2592000000

long dan = 1 * 1000 * 1000 * 1000 * 5;          // int * int -> tran roi moi rong ra long
IO.println("int * int      : " + dan);           // 705032704
long dung = 1L * 1000 * 1000 * 1000 * 5;        // 1L keo ca bieu thuc sang long
IO.println("1L bat dau     : " + dung);          // 5000000000

Chỉ cần một toán hạng long (30L, 1000L, 1L) là cả biểu thức được promote sang long. Còn giai thừa là ví dụ kinh điển cho thấy tràn có thể ra số dương nhưng sai:

static int factorialInt(int n) {
    int r = 1;
    for (int i = 2; i <= n; i++) r *= i;
    return r;
}

IO.println("int 12!        : " + factorialInt(12));   // 479001600
IO.println("int 13!        : " + factorialInt(13));   // 1932053504 (sai!)

13! = 6 227 020 800 vượt Integer.MAX_VALUE, nhưng kết quả tràn lại ra 1932053504 — một số dương "hợp lệ" nên không ai nghi ngờ. Dùng long chỉ đẩy biên lên: đúng đến 20!, hỏng từ 21!; cần hơn nữa thì dùng BigInteger.

9.4 Unsigned — đối xử 32/64 bit như số không dấu

Java không có kiểu unsigned int, nhưng từ Java 8 có sẵn nhóm method tĩnh coi dãy bit là số không dấu — hữu ích khi làm việc với hash, checksum, giao thức, địa chỉ IPv4. Đừng tự viết lại bằng tay:

int a = -1;   // 0xFFFFFFFF

IO.println("toUnsignedString : " + Integer.toUnsignedString(a));          // 4294967295
IO.println("toUnsignedLong   : " + Integer.toUnsignedLong(a));            // 4294967295
IO.println("parseUnsignedInt : " + Integer.parseUnsignedInt("4294967295")); // -1
IO.println("divideUnsigned   : " + Integer.divideUnsigned(-1, 2));        // 2147483647
IO.println("remainderUnsigned: " + Integer.remainderUnsigned(-1, 2));     // 1
IO.println("compareUnsigned  : " + Integer.compareUnsigned(-1, 1));       // 1

IO.println("-1 >> 1          : " + (-1 >> 1));     // -1
IO.println("-1 >>> 1         : " + (-1 >>> 1));    // 2147483647
IO.println("Long -1 unsigned : " + Long.toUnsignedString(-1L));  // 18446744073709551615
  • >> (số học) giữ nguyên bit dấu nên -1 >> 1 vẫn là -1; >>> (luận lý) đổ 0 vào bên trái.
  • compareUnsigned(-1, 1) trả 1 vì -1 là 4294967295 không dấu, lớn hơn 1 — trái ngược hoàn toàn với so sánh có dấu.
  • parseUnsignedInt("4294967296") vẫn ném NumberFormatException vì vượt 32 bit; class Long có bộ method tương tự (compareUnsigned, divideUnsigned, parseUnsignedLong…).
  • Khi nào dùng: hiển thị/so sánh hash 32-bit, checksum CRC32, IP & port trong giao thức mạng, thuật toán bit. Tính toán nghiệp vụ thông thường hãy giữ long/BigInteger cho rõ nghĩa.

9.5 float/double: tràn ra Infinity, không wraparound

Số dấu phẩy động theo IEEE 754 không quay vòng. Vượt giới hạn → vô cực; quá nhỏ → mất dần về 0; phép toán với NaN sinh NaN (lan truyền):

double big = Double.MAX_VALUE;
IO.println("MAX * 2      : " + big * 2);            // Infinity
IO.println("MIN / 2      : " + Double.MIN_VALUE / 2); // 0.0
IO.println("1.0 / 0      : " + 1.0 / 0);            // Infinity
IO.println("-1.0 / 0     : " + -1.0 / 0);           // -Infinity

double nan = 0.0 / 0.0;
IO.println("0.0 / 0.0    : " + nan);              // NaN
IO.println("NaN + 1      : " + (nan + 1));        // NaN
IO.println("NaN == NaN   : " + (nan == nan));      // false
IO.println("NaN != NaN   : " + (nan != nan));      // true
IO.println("isNaN        : " + Double.isNaN(nan)); // true
  • Khác biệt cốt lõi với số nguyên: 1 / 0 (int) ném ArithmeticException: / by zero, còn 1.0 / 0 trả Infinity.
  • NaN không bằng chính nó: mọi so sánh ==, <, > với NaN đều false. Vì vậy đừng viết x == Double.NaN — dùng Double.isNaN(x).
  • Underflow: Double.MIN_VALUE là số dương nhỏ nhất biểu diễn được; chia đôi nữa thành 0.0 — mất chính xác âm thầm nhưng khác hẳn wraparound của int.

9.6 Production: chọn long, dùng Exact, để ý biên

  • ID & timestamp luôn long: System.currentTimeMillis() cỡ 1,7×1012 đã vượt xa int (~2,1 tỷ). Đây là lý do AtomicLong, Instant.getEpochSecond()… đều dùng long.
  • Tiền dùng long theo đơn vị nhỏ nhất hoặc BigDecimal (mục 13) — không dùng int/double.
  • Chỗ nhạy cảm dùng Math.*Exact: cộng dồn số lượng lớn, nhân giá × số lượng, chỉ số suy ra từ input người dùng. Ở biên API, validate đầu vào để tránh cả tràn lẫn underflow.
  • Số vượt long (mã giao dịch, hash 128-bit, giai thừa lớn) → BigInteger; số nguyên > 253 truyền sang JavaScript nên serialize dạng String (xem Data Types — 13.2) vì JS chỉ chính xác tới Number.MAX_SAFE_INTEGER.
  • Không "kiểm tra sau": sau khi tràn, kết quả có thể ngược dấu hoặc vẫn cùng dấu (như 13! ở trên). Chỉ kiểm tra trước hoặc dùng …Exact mới chắc.

Góc Node.js

JS chỉ có một kiểu số thường — number = double 64-bit — nên mọi bẫy về độ chính xác nằm chung một chỗ:

// JavaScript (Node 22)
console.log(Number.MAX_SAFE_INTEGER);       // 9007199254740991
console.log(2 ** 53 === 2 ** 53 + 1);       // true
console.log(9007199254740993);              // 9007199254740992
console.log(0.1 + 0.2);                     // 0.30000000000000004

console.log(1n + 2n);                       // 3n
try {
  const mixed = 1n + 1;
} catch (e) {
  console.log(e.message);
  // Cannot mix BigInt and other types, use explicit conversions
}

console.log((2147483647 + 1) | 0);          // -2147483648
console.log((-1) >>> 0);                    // 4294967295
  • Số nguyên chính xác tới Number.MAX_SAFE_INTEGER = 253 − 1 = 9007199254740991. Từ 253 trở đi, 2 ** 53 === 2 ** 53 + 1 là true — không lỗi nào được ném.
  • Số nguyên lớn dùng BigInt (1n + 2n). Trộn BigInt với Number ném TypeError: Cannot mix BigInt and other types, use explicit conversions — phải đổi kiểu tường minh.
  • Phép bitwise của JS (&, |, >>) ép về int 32-bit có dấu và wraparound y như Java: (2147483647 + 1) | 0 ra -2147483648. Riêng >>> trả số 32-bit không dấu ((-1) >>> 0 = 4294967295).
Chốt gọn: int tràn thì quay vòng âm thầm (MAX+1 = MIN; MIN / -1 = MIN; abs(MIN) vẫn âm) → tính thời gian/nhân số lớn nhớ hậu tố L hoặc dùng Math.*Exact → binary search sửa bằng (lo + hi) >>> 1 → float/double tràn ra Infinity/NaN chứ không quay vòng → production: long cho ID/timestamp/tiền, …Exact ở chỗ nhạy cảm.

10. final chuyên sâu Hay hỏi phỏng vấn

final khoá việc gán lại, nhưng phạm vi ảnh hưởng khác nhau tuỳ nơi đặt: biến, reference, field, method, class. Mục này đi qua từng ngữ cảnh, bảo đảm bộ nhớ (JMM) của final field, quy tắc capture trong lambda và niềm tin sai lầm rằng "final làm code nhanh hơn".

10.1 final variable — gán đúng một lần

final trên biến nghĩa là gán đúng một lần; gán lần thứ hai là lỗi compile. Áp dụng cho cả field, local và tham số method. Biến local blank final (chưa gán ngay) phải được gán trên mọi nhánh trước khi dùng — compiler kiểm tra "definite assignment":

final int max = 10;
IO.println("max = " + max);   // 10

final int n;
int flag = 1;
if (flag > 0) {
    n = 10;
} else {
    n = 20;
}
IO.println("n = " + n);       // 10

for (final int i : new int[]{1, 2, 3}) {
    IO.println(i);
}
// 1
// 2
// 3

Gán lại biến local final:

FinalLocal.java:4: error: cannot assign a value to final variable max
        max = 20;
        ^
1 error

Tham số cũng final được — hữu ích để compiler chặn việc vô tình gán đè giá trị đầu vào:

FinalParam.java:3: error: final parameter times may not be assigned
        times = times - 1;
        ^
1 error

Field blank final phải được gán đúng một lần trong mọi constructor (hoặc initializer). Bỏ sót — compiler chặn:

BlankFinal.java:2: error: variable url not initialized in the default constructor
    private final String url;
                         ^
1 error

Gán hai lần — dù cả hai đều nằm trong constructor — cũng bị chặn:

FinalTwice.java:6: error: variable url might already have been assigned
        url = "b";
        ^
1 error
public class Connection {
    private final String url;      // blank final

    Connection(String url) {
        this.url = url;            // gan dung 1 lan
    }
}
Từ JDK 25 (JEP 513 — Flexible Constructor Bodies), bạn được chạy validate và gán blank final field ngay trước super(...), miễn field khai báo trong class hiện tại và chưa có initializer: if (v < 0) throw ...; value = v; super("ok");. Trước JDK 25 mọi câu lệnh phải nằm sau lời gọi constructor. Chi tiết ở Classes & Objects — mục 3.

10.2 final reference ≠ immutable object

final khoá biến tham chiếu, không khoá nội dung object mà nó trỏ tới — câu phỏng vấn kinh điển và cũng là lỗi thực chiến:

final List<String> list = new ArrayList<>();
list.add("java");                                  // OK - noi dung doi duoc
list.add("spring");
IO.println("final List add duoc : " + list);        // [java, spring]

final int[] arr = {1, 2, 3};
arr[0] = 99;                                       // OK - phan tu doi duoc
IO.println("final int[] sua duoc: " + Arrays.toString(arr)); // [99, 2, 3]

// list = new ArrayList<>();  // LOI: cannot assign a value to final variable list

Muốn bất biến thật sự thì phải khoá nội dung, không chỉ khoá biến. List.of(...) và List.copyOf(...) tạo list immutable; mọi lệnh sửa đều ném UnsupportedOperationException:

List<String> immutable = List.of("a", "b");
try {
    immutable.add("c");
} catch (UnsupportedOperationException e) {
    IO.println("List.of add         : UnsupportedOperationException");
}

List<String> copied = List.copyOf(list);
IO.println("List.copyOf         : " + copied); // [java, spring]
Bất biến nông (shallow): List.of chỉ khoá cấu trúc list; phần tử bên trong nếu là object mutable thì vẫn sửa được ruột. Muốn sâu, phần tử cũng phải immutable (xem 5 bước tạo immutable class), và cẩn thận getter trả về mảng/collection nội bộ. JS cũng y hệt với Object.freeze nông.

10.3 final field và Java Memory Model (JMM)

Ngoài ý nghĩa "không gán lại", final field còn có bảo đảm bộ nhớ (JLS 17.5): field được "đóng băng" khi constructor kết thúc. Một thread đọc được tham chiếu object sau khi object khởi tạo xong sẽ thấy đúng giá trị final field, kể cả khi object bị chia sẻ kiểu "ẩu" giữa các thread. Field không final không có bảo đảm này — có thể thấy giá trị mặc định 0/null.

Đây là nền tảng của class immutable: field quan trọng nên là private final và gán trong constructor. Lưu ý freeze chỉ áp dụng cho chính field final; để an toàn toàn phần khi chia sẻ (đặc biệt với mảng/collection bên trong), hãy publish qua static initializer, volatile, synchronized hoặc concurrent collection.

Bẫy compile-time constant: hằng static final kiểu nguyên thủy/String khởi tạo bằng constant expression được javac inline thẳng vào nơi dùng. Hệ quả: đọc nó không kích hoạt static block của class khai báo, và đổi hằng phải recompile cả phía client — chi tiết ở Classes & Objects — mục 5.3:

class ConstHolder {
    static final int MAX = 100;                        // compile-time constant
    static {
        IO.println("ConstHolder initialized");
    }
}

class InitHolder {
    static final long START = Long.parseLong("20");    // khong phai constant expression
    static {
        IO.println("InitHolder initialized");
    }
}

public class FinalJmm {
    public static void main() {
        IO.println("MAX = " + ConstHolder.MAX);
        IO.println("START = " + InitHolder.START);
        // In ra:
        // MAX = 100
        // InitHolder initialized
        // START = 20
    }
}

10.4 final method, final class & sealed

final trên method chặn override; trên class chặn kế thừa. Cả hai đều là lỗi compile, không phải cảnh báo:

FinalOverride.java:8: error: run() in ChildMethod cannot override run() in ParentMethod
    void run() {
         ^
  overridden method is final
1 error
FinalExtend.java:4: error: cannot inherit from final BaseClass
class SubClass extends BaseClass {
                       ^
1 error

Nhiều class quen thuộc đã final sẵn: String, toàn bộ wrapper (Integer, Long…), record. enum cũng không thể bị kế thừa (enum có constant-specific body chỉ mở cho chính các constant đó; từ Java 17 được mô tả là implicitly sealed).

Vì sao String final? Nếu cho phép subclass, kẻ tấn công có thể tạo EvilString "trông như String" rồi thay hành vi equals/hashCode — phá mọi HashMap, kiểm tra bảo mật, đường dẫn file, class loading. Thêm nữa String bất biến nên hashCode được cache và an toàn khi chia sẻ giữa các thread/String pool.

Thay thế hiện đại — sealed: final đóng cứng hoàn toàn; nếu chỉ muốn "đúng danh sách con này được kế thừa" thì dùng sealed ... permits .... Chi tiết ở Enum, nested & sealed — mục 10.

10.5 Effectively final — vì sao lambda bắt buộc?

Lambda và anonymous class chỉ bắt (capture) biến local là final hoặc effectively final (gán đúng một lần, không đổi sau đó). Gán lại là lỗi compile — errblock dưới đây là output thật của javac 25:

FinalCapture.java:5: error: local variables referenced from a lambda expression must be final or effectively final
        Runnable r = () -> IO.println(count);
                                      ^
1 error

Tại sao Java bắt buộc? Biến local nằm trên stack và biến mất khi method kết thúc, còn lambda có thể sống lâu hơn (được trả về, chạy ở thread khác). Java không giữ "ô nhớ" của biến — nó copy giá trị vào lambda ngay lúc tạo. Nếu cho phép biến đổi sau đó, lambda giữ bản chụp cũ, gây hiểu nhầm kiểu closure của JS. Bắt buộc final/effectively final biến quy tắc "chụp giá trị" thành rõ ràng: biến không đổi thì bản chụp luôn đúng.

Đối chiếu JS: closure JS bắt binding (sống), nên vòng lặp var nổi tiếng in ra giá trị cuối; Java bắt giá trị nên vấn đề đó không tồn tại. Khi thật sự cần bộ đếm sửa được, dùng "hộp" một ô — biến tham chiếu không đổi nhưng ruột đổi được:

int[] count = {0};                 // bien count khong doi
Runnable r = () -> count[0]++;     // nhung phan tu doi duoc
r.run();
r.run();
IO.println("count = " + count[0]); // count = 2

10.6 "final cho nhanh hơn" — niềm tin cần bỏ

Nhiều người tin thêm final để JIT dễ tối ưu. Trên HotSpot hiện đại, JIT dùng class hierarchy analysis + profile để inline cả method không final; khi class mới được nạp làm mất tính đúng, nó deoptimize rồi biên dịch lại. Vì vậy đánh dấu final cho method/class hầu như không tạo khác biệt đo được về tốc độ.

Giá trị thật của final là ngữ nghĩa và an toàn: (1) chặn gán lại/override/extends ngoài ý muốn, (2) tự tài liệu hoá "giá trị này không đổi", (3) bảo đảm JMM cho final field (mục 10.3). Muốn tối ưu thật, hãy đo bằng JMH và tập trung vào thuật toán/bộ nhớ.

Ngoại lệ "có thật" về hiệu năng: static final hằng số constant expression được javac inline ngay lúc compile (constant folding) — nhưng đó là việc của compiler, không phải JIT, và kèm hệ quả phải recompile client khi đổi giá trị (mục 10.3).

Góc Node.js

  • Java không có từ khoá const (nó là từ khoá dự trữ, không dùng được) — dân JS mới sang hay viết nhầm; dùng final.
  • const giống final ở chỗ khoá binding: const o = {}; o.x = 1; hợp lệ, còn o = {} ném TypeError: Assignment to constant variable.. Java cũng y hệt: final List vẫn add được.
  • Object.freeze chỉ khoá một lớp (nông): sloppy mode bỏ qua im lặng khi gán vào object đã freeze, strict mode/ESM ném TypeError: Cannot assign to read only property 'x'. Muốn sâu phải freeze đệ quy — tương tự giới hạn "shallow" của List.of.
  • TypeScript as const/readonly chỉ kiểm tra lúc biên dịch; runtime không khoá gì — khác final của Java vì được enforce ở bytecode và JMM.
  • JS không có final method/class; muốn "đóng" phải dựa vào convention/private field #. Java có final/sealed ở tầng ngôn ngữ.
Chốt gọn: final = gán 1 lần (local/param/field; blank final gán trong constructor) → không làm object bất biến (dùng List.of/List.copyOf) → final field có bảo đảm JMM khi publish → chặn override/extends, sealed là lựa chọn mở hơn → lambda chỉ bắt biến final/effectively final vì Java copy giá trị → đừng dùng final để "tối ưu tốc độ".

11. var (Java 10+) Production

var để compiler tự suy kiểu cho biến local — nhìn như let của JS nhưng bản chất ngược lại: vẫn là static typing, kiểu chốt cứng lúc compile và không bao giờ đổi. var chỉ tiết kiệm việc gõ tên kiểu, không làm Java thành ngôn ngữ động.

11.1 Suy kiểu local — var làm gì

import java.util.ArrayList;

public class VarBasics {
    public static void main() {
        var name = "An";
        var count = 10;
        var list = new ArrayList<String>();
        list.add("java");

        IO.println(name.getClass().getSimpleName());   // String
        IO.println(count);                             // 10
        IO.println(list);                              // [java]
        IO.println(list.getClass().getSimpleName());   // ArrayList
    }
}

12. Wrapper & autoboxing chuyên sâu Hay hỏi phỏng vấn Junior+

Mỗi primitive có một lớp vỏ object (wrapper): int → Integer, long → Long, double → Double… Wrapper cần thiết vì generics và collections chỉ chứa reference (List<Integer> không thể là List<int>), vì cho phép null (cột DB nullable, field JSON vắng mặt), và vì cần object cho reflection/API. Đổi lại: tốn bộ nhớ hơn, thêm một tầng method và đầy bẫy.

12.1 Cơ chế: valueOf, intValue và autoboxing

Autoboxing/unboxing là "đường tắt" do compiler sinh ra: Integer b = 10; thực chất là Integer.valueOf(10); int c = b; là b.intValue() (kèm kiểm tra null ngầm). Viết tường minh cũng được và rõ ràng hơn ở chỗ nhạy cảm:

Integer a = Integer.valueOf(10);   // nen dung - di qua cache
Integer b = 10;                    // autobox - y het valueOf
int c = b.intValue();              // unbox tuong minh

IO.println("valueOf : " + a);   // 10
IO.println("autobox : " + b);   // 10
IO.println("intValue: " + c);   // 10

Phân biệt hai nhóm API hay bị lẫn: Integer.parseInt("10") trả int; Integer.valueOf("10") trả Integer. Còn new Integer(10) bị đánh dấu @Deprecated(since = "9") vì luôn tạo object mới, bỏ qua cache — javac chỉ cảnh báo (không chặn), nên code cũ vẫn chạy. Bật -Xlint:deprecation sẽ thấy rõ:

WrapperNew.java:3: warning: [deprecation] Integer(int) in Integer has been deprecated
        Integer x = new Integer(10);
                    ^
1 warning

12.2 Cache — vì sao == "đôi khi đúng"

Wrapper không phải lúc nào cũng tạo object mới. Integer.valueOf trả instance từ cache cho khoảng -128..127; ngoài khoảng mới tạo mới. Vì vậy hai biến cùng giá trị có thể là cùng object (== true) hoặc khác object (== false) tuỳ giá trị — cực kỳ dễ sinh bug:

Integer a = 127, b = 127;
Integer c = 128, d = 128;

IO.println("127 == 127   : " + (a == b));  // true
IO.println("128 == 128   : " + (c == d));  // false
IO.println("128 equals   : " + c.equals(d)); // true

Integer m = 1000, n = 1000;
IO.println("1000 == 1000 : " + (m == n)); // false

12.3 Bẫy so sánh & NullPointerException

Ba nhóm bẫy thường gặp: so sánh khác kiểu, unbox null, và unbox ngầm trong điều kiện/ternary:

Integer a = null;
Integer b = 1;

IO.println("null == 1     : " + (a == b)); // false - so reference, KHONG unbox

try {
    IO.println(a == 1);                    // unbox a -> chan
} catch (NullPointerException e) {
    IO.println("a == 1        : NullPointerException");
}

IO.println("1 equals 1L   : " + Integer.valueOf(1).equals(Long.valueOf(1))); // false
IO.println("Objects.equals: " + Objects.equals(a, b)); // false - null-safe

try {
    int c = true ? a : 0;                  // ternary ep ve int -> unbox a
    IO.println(c);
} catch (NullPointerException e) {
    IO.println("true ? a : 0  : NullPointerException");
}

IO.println("false ? a : 0 : " + (false ? a : 0)); // 0 - nhanh false khong cham a
  • a == b khi cả hai là wrapper chỉ so reference — null == 1 trả false mà không ném. Nhưng chỉ cần một bên là primitive (a == 1) là compiler chèn unbox → NPE.
  • Integer.valueOf(1).equals(Long.valueOf(1)) là false: equals kiểm tra đúng class trước khi so giá trị. Tương tự, Integer.compare(1, 2L) thậm chí không compile vì khác kiểu tham số.
  • Ternary true ? a : 0 bị ép về int chung nên unbox trước khi chọn; đổi điều kiện thành false thì nhánh 0 được chọn và không đụng tới a. Đừng để logic unbox phụ thuộc vào nhánh ternary.
  • An toàn nhất: kiểm tra null trước, dùng Objects.equals(a, b), hoặc Objects.requireNonNull ở biên rồi mới tính bằng primitive.

12.4 Overload resolution — 3 pha chọn method

Khi có nhiều overload, javac chọn theo 3 pha theo thứ tự, dừng ngay khi pha nào tìm được method phù hợp nhất:

  1. Pha 1 — strict invocation: chỉ widening primitive/reference, không boxing/unboxing, không varargs.
  2. Pha 2 — loose invocation: cho phép boxing/unboxing (vẫn không varargs).
  3. Pha 3 — variable arity: mới xét method varargs (int...).
static void f(int x)     { IO.println("f(int)"); }
static void f(Integer x) { IO.println("f(Integer)"); }
static void f(Object x)  { IO.println("f(Object)"); }
static void f(long x)    { IO.println("f(long)"); }

static void g(Integer x) { IO.println("g(Integer)"); }
static void g(Object x)  { IO.println("g(Object)"); }

f(1);                   // f(int)      - pha 1, khop chinh xac
f(Integer.valueOf(1));  // f(Integer)  - pha 1, khop chinh xac
f(1L);                  // f(long)     - pha 1, khop chinh xac

short s = 1;
f(s);                   // f(int)      - pha 1, widening thang boxing

g(1);                   // g(Integer)  - pha 2, boxing; Integer cu the hon Object
g(1L);                  // g(Object)   - pha 2, Long khong match Integer

Bài học: widening primitive thắng boxing (f(short) chọn f(int), không chọn f(Integer)), và trong pha 2 kiểu "cụ thể hơn" thắng. Với null, luật "cụ thể hơn" cũng áp dụng — điều này bác bỏ một câu hỏi phỏng vấn hay được truyền miệng sai:

static void m(Object x)  { IO.println("m(Object)"); }
static void m(Integer x) { IO.println("m(Integer)"); }

m(null);              // m(Integer) - Integer cu the hon Object
m((Object) null);     // m(Object)  - ep kieu de chi ro
m((Integer) null);    // m(Integer)

Chỉ khi các overload không có quan hệ subtype thì null mới gây mơ hồ — ví dụ m(String) và m(Integer):

Ambiguous2.java:6: error: reference to m is ambiguous
        m(null);
        ^
  both method m(String) in Ambiguous2 and method m(Integer) in Ambiguous2 match
1 error
Ghi chú phỏng vấn: nếu bị hỏi "có m(Object) và m(Integer), gọi m(null) có ambiguous không?" — câu trả lời đúng là không: chọn m(Integer); muốn bản Object phải ép kiểu m((Object) null). Ambiguous thật sự xảy ra khi các kiểu không liên quan nhau (như String vs Integer). Cứ dẫn JLS 15.12.2 kèm ví dụ chạy được.

12.5 Hiệu năng: đừng box trong vòng lặp nóng

Mỗi lần autobox ngoài cache là một lần cấp phát object. Trong vòng lặp lớn, điều này tạo hàng triệu object rác cho GC. Ví dụ xấu kinh điển là biến tích luỹ kiểu wrapper:

Long sum = 0L;                 // XAU
for (int i = 0; i < 1_000_000; i++) {
    sum += i;                  // moi vong: unbox, cong, roi box lai object moi
}

long total = 0L;               // TOT
for (int i = 0; i < 1_000_000; i++) {
    total += i;                // chi phep cong primitive
}

Đo nhanh trên máy tác giả (JDK 25, 10 triệu vòng, không dùng JMH): bản Long mất ~30–45 ms còn bản long ~3–5 ms — con số chỉ minh hoạ xu hướng, phụ thuộc máy và JIT. Cùng tinh thần, với collection số hãy dùng primitive stream (IntStream, LongStream): IntStream.range(0, n).sum() không box từng phần tử; mapToInt/mapToLong để thoát khỏi Stream<Integer>.

12.6 Production: chọn primitive hay wrapper

  • DTO/entity nullable → wrapper (Integer age, Long parentId): null mang nghĩa "không có giá trị", phân biệt với 0. Nhưng phải kiểm tra null trước khi tính toán.
  • Bộ đếm, tổng, chỉ số → primitive (long total, int count): nhanh hơn, không có nguy cơ NPE do unbox ngầm.
  • Không dùng == cho wrapper: dùng equals/Objects.equals cho nullable, Integer.compare khi chắc chắn không null — tránh cả bug cache lẫn NPE.
  • Unbox ở biên: nhận wrapper, Objects.requireNonNull(x, "x") một lần rồi tính bằng primitive. Giá trị "có thể vắng" nên trả Optional (lộ trình 3.7) thay vì trả null.
  • Hiệu năng: tránh wrapper làm accumulator trong vòng lặp nóng; dùng primitive stream; chỉ giữ wrapper khi thật cần null/generic.

Góc Node.js

  • JS có hai toán tử so sánh: == ép kiểu (1 == "1" là true), === không ép. Java không có ===; == trên primitive so giá trị, trên reference so địa chỉ — và compiler chặn ngay nếu hai kiểu không so sánh được với nhau.
  • new Number(1) === 1 là false (object vs primitive) nhưng new Number(1) == 1 là true — họ hàng với bẫy cache wrapper của Java. Dân JS chuyên nghiệp gần như không bao giờ dùng new Number/Boolean/String.
  • Boolean(0) là false, nhưng Boolean(new Boolean(false)) là true vì object luôn truthy — thêm một bẫy "wrapper" quen thuộc.
  • JS không có wrapper cho mục đích generics (array chứa mọi thứ) nên không có "autobox trong vòng lặp"; bù lại number là double nên dính bẫy chính xác số (mục 9.5 và 13).
Chốt gọn: wrapper = object hoá primitive, cần cho collection/generics/null → autobox = valueOf/intValue, constructor deprecated → cache -128..127 khiến == "đôi khi đúng": luôn equals/compare → unbox null nổ NPE (kể cả trong ternary/điều kiện) → overload chọn theo 3 pha, widening thắng boxing → đừng box trong vòng lặp nóng → DTO nullable dùng wrapper, bộ đếm dùng primitive.

13. BigDecimal chuyên sâu Hay hỏi phỏng vấn Production

double (học ở mục 3) chỉ hợp với tính toán khoa học; với tiền bạc, mọi hệ thống production đều dùng BigDecimal. Mục này giải thích vì sao và các bẫy khi dùng nó.

13.1 Vì sao "số thập phân nhị phân" là vấn đề

double/float lưu theo chuẩn IEEE 754: giá trị = ±m × 2e, nên chỉ biểu diễn chính xác được các số dạng k/2ⁿ (0.5, 0.25, 0.125…). Còn 0.1 = 1/10 khi viết ở hệ nhị phân là số vô hạn tuần hoàn — giống như 1/3 trong hệ thập phân — nên buộc phải lưu xấp xỉ. Bằng chứng:

IO.println(0.1 + 0.2);   // 0.30000000000000004

double d = 0;
for (int i = 0; i < 10; i++) d += 0.1;
IO.println("0.1 cong 10 lan         = " + d);   // 0.9999999999999999

double e = 0;
for (int i = 0; i < 1_000_000; i++) e += 0.01;
IO.println("0.01 cong 1.000.000 lan = " + e);   // 10000.000000171856

IO.println(new BigDecimal(0.1));
// 0.1000000000000000055511151231257827021181583404541015625

IO.println(0.1);   // 0.1  <- nhin nhu dung!
Điều hiểm: IO.println(0.1) vẫn in ra 0.1 — Java in số ngắn nhất mà đọc lại vẫn ra đúng double đó (shortest round-trip). Vì vậy sai số bị che: nhìn thì đẹp, cộng dồn mới lộ. Tiền cần chính xác tuyệt đối, nên ta dùng BigDecimal.

13.2 BigDecimal lưu gì

Không lưu nhị phân mà lưu unscaledValue × 10-scale: 19.99 = unscaled 1999, scale 2. Nhờ vậy nó biểu diễn số thập phân chính xác, và scale là một phần dữ liệu — gốc của bẫy equals ở mục 13.6:

BigDecimal gia = new BigDecimal("19.99");
IO.println(gia.unscaledValue());   // 1999
IO.println(gia.scale());           // 2

13.3 Tạo bằng chuỗi — đừng truyền double

new BigDecimal("199000")     // 199000
new BigDecimal(19.99)        // 19.989999999999998436805981327779591083526611328125
new BigDecimal("19.99")      // 19.99
BigDecimal.valueOf(0.1+0.2)  // 0.30000000000000004
  • Truyền double vào là mang sẵn sai số rồi phơi ra đủ 55 chữ số — không phải BigDecimal "tránh" được lỗi, mà kế thừa nguyên lỗi.
  • BigDecimal.valueOf(double) chỉ dùng Double.toString nên "đỡ tệ" cho 19.99, nhưng vẫn xuất phát từ double: 0.1 + 0.2 vẫn ra 0.30000000000000004. Chỉ dùng khi double đó chắc chắn exact — ví dụ số nguyên nhỏ (new BigDecimal(199000.0) = đúng 199000 vì < 253).
  • Với tiền, cứ truyền String.

13.4 Cộng trừ nhân chia bằng method — và nhớ immutable

BigDecimal immutable: mọi phép tính trả object mới, không sửa object cũ. Quên gán lại là bug im lặng:

BigDecimal total = new BigDecimal("100");
total.add(new BigDecimal("50"));          // khong gan -> total van 100
total = total.add(new BigDecimal("50"));  // dung -> total = 150

BigDecimal a = new BigDecimal("0.10").add(new BigDecimal("0.20"));
BigDecimal m = new BigDecimal("0.10").multiply(new BigDecimal("0.20"));
IO.println(a + " (scale " + a.scale() + ")");   // 0.30 (scale 2)
IO.println(m + " (scale " + m.scale() + ")");   // 0.0200 (scale 4)

BigDecimal gia = new BigDecimal("199000.50");
BigDecimal thue = gia.multiply(new BigDecimal("0.08")).setScale(2, RoundingMode.HALF_UP);
IO.println(thue);   // 15920.04

Scale lan truyền theo phép tính: cộng/trừ lấy max scale hai bên; nhân lấy tổng scale hai bên. Vì vậy hãy chuẩn hoá scale trước khi so sánh/lưu trữ (mục 13.7).

13.5 divide() không chia hết → ArithmeticException

BigDecimal "không chịu" làm tròn ngầm: phép chia vô hạn (1/3) mà không nói rõ độ chính xác sẽ ném exception. Đây là chỗ bắt buộc phải khai báo scale kèm RoundingMode ngay trong code:

new BigDecimal("1").divide(new BigDecimal("3"));
// ArithmeticException: Non-terminating decimal expansion; no exact representable decimal result.

new BigDecimal("1").divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP);   // 0.33
new BigDecimal("1").divide(new BigDecimal("3"), 8, RoundingMode.HALF_UP);   // 0.33333333
new BigDecimal("1").divide(new BigDecimal("3"), MathContext.DECIMAL128);
// 0.3333333333333333333333333333333333
new BigDecimal("1000000").divide(new BigDecimal("3"), 0, RoundingMode.HALF_UP); // 333333
Chia hoá đơn 1.000.000đ cho 3 người là ví dụ kinh điển: mỗi người 333.333đ, dư 1đ — cần quy tắc kế toán cho phần lẻ (cộng vào người đặt, hoặc ghi vào tài khoản chênh lệch).

13.6 equals vs compareTo — bẫy scale

BigDecimal a = new BigDecimal("1.0");
BigDecimal b = new BigDecimal("1.00");

a.equals(b);              // false  - scale 1 vs 2
a.compareTo(b) == 0;      // true   - cung gia tri

Set<BigDecimal> hash = new HashSet<>(); hash.add(a); hash.add(b);   // size 2
Set<BigDecimal> tree = new TreeSet<>(); tree.add(a); tree.add(b);   // size 1

equals() so cả value lẫn scale; compareTo() chỉ so giá trị. Hệ quả nặng hơn bạn tưởng:

  • HashSet/HashMap coi 1.0 và 1.00 là 2 phần tử (hashCode tính theo unscaled + scale).
  • TreeSet/TreeMap coi là 1 (compareTo = 0) — vì compareTo không consistent với equals (Javadoc ghi rõ).

Quy tắc: so tiền bằng compareTo(...) == 0; nếu dùng làm key/Set thì setScale chuẩn hoá ngay từ đầu.

13.7 setScale & RoundingMode — làm tròn ở biên

new BigDecimal("2.675").setScale(2);
// ArithmeticException: Rounding necessary

new BigDecimal("2.675").setScale(2, RoundingMode.HALF_UP);   // 2.68
new BigDecimal("2.5").setScale(0, RoundingMode.HALF_UP);     // 3
new BigDecimal("2.5").setScale(0, RoundingMode.HALF_EVEN);   // 2
new BigDecimal("199999").setScale(0, RoundingMode.HALF_UP);  // 199999
  • setScale(2) trần: nếu phải làm tròn thì ném exception — tốt, để bắt lỗi sớm. Muốn làm tròn phải chỉ định mode.
  • HALF_UP (≥ 5 lên) là chuẩn kế toán thông dụng ở VN; HALF_EVEN (banker's) là chuẩn của IEEE/tài chính phương Tây. Chọn một quy tắc thống nhất cho toàn hệ thống và ghi rõ trong code/tài liệu.
  • Làm tròn một lần ở bước cuối (khi lưu DB / trả API), không làm tròn giữa chừng rồi tính tiếp — sai số sẽ nhân lên.
  • Scale theo loại tiền (ISO 4217): VND là 0 chữ số thập phân, USD là 2. Đừng hardcode 2 cho VND.
  • Mẹo: RoundingMode.UNNECESSARY để "khẳng định" giá trị không cần làm tròn — nếu có, nó ném exception và bạn phát hiện sai sót.

13.8 Hai bẫy production

new BigDecimal("1E+3").toString();             // 1E+3   <- ky phap khoa hoc

  • Nếu cần tốc độ và là hệ thống nội bộ, phương án thay thế hoàn toàn hợp lệ là long theo đơn vị nhỏ nhất (đồng/xu).

Góc Node.js

  • JS chỉ có một kiểu số number = double, không có BigDecimal built-in; BigInt chỉ dành cho số nguyên (BigInt(0.1) ném RangeError).

14. String & biến Hay hỏi phỏng vấn

Góc nhìn của mục này là biến và tham chiếu: String là reference type bất biến, biến giữ địa chỉ chứ không giữ ruột chuỗi. Hiểu điều đó là giải được mọi câu "nối chuỗi tốn gì", "vì sao switch String chạy được". Phần method/format/regex để doc riêng Strings chuyên sâu (1.7).

14.1 s += "b" tạo object mới, biến đổi trỏ chứ không đổi ruột

public class StrMutation {
    public static void main() {
        String pooled = "ab";
        String s = "a";
        s += "b";
        IO.println("s           : " + s);                    // s           : ab
        IO.println("s == pooled : " + (s == pooled));        // s == pooled : false
        IO.println("s.equals    : " + s.equals(pooled));     // s.equals    : true
        IO.println("noi hang    : " + ("a" + "b" == pooled)); // noi hang    : true

        String t = "a";
        t = t + "b";
        IO.println("t == pooled : " + (t == pooled));        // t == pooled : false
    }
}

s += "b" tương đương s = s + "b": đọc object "a", tạo object "ab" mới trên heap, rồi gán địa chỉ mới vào s. Object "a" không bị sửa — nó còn nằm trong pool cho người khác dùng. Vì thế s == pooled là false: chuỗi nối lúc runtime không tự vào pool. Khác hẳn "a" + "b" là hằng số biên dịch được ghép sẵn trong pool (dòng cuối in true).

14.2 Pool & intern — góc nhìn tham chiếu

Java có String pool — vùng nhớ chứa các chuỗi literal để tái sử dụng. Hai literal giống nhau là cùng một object; new String tạo object ngoài pool; intern() đưa chuỗi về pool:

String s1 = "java";
String s2 = "java";
String s3 = new String("java");
String s4 = s3.intern();          // dua ve pool

IO.println("s1 == s2        : " + (s1 == s2));      // s1 == s2        : true
IO.println("s1 == s3        : " + (s1 == s3));      // s1 == s3        : false
IO.println("s1 == s4        : " + (s1 == s4));      // s1 == s4        : true
IO.println("s1.equals(s3)   : " + s1.equals(s3));  // s1.equals(s3)   : true
  • Quy tắc bất di bất dịch: so sánh chuỗi luôn dùng .equals(), không dùng ==.
  • Gán s3 = s3.intern() cũng chạy được — nhưng đừng lạm dụng: intern() có chi phí tra cứu và giữ chuỗi sống lâu trong pool.
  • Chi tiết cơ chế pool, equals/hashCode của String và Unicode tiếng Việt ở Strings — mục 3 và mục 7.

14.3 Bẫy null — "null" là một chuỗi thật

Phép nối chuỗi không ném NPE với null — nó chuyển null thành bốn ký tự null. Đây là nguồn bug âm thầm: dữ liệu thiếu biến thành chữ "null" trông như dữ liệu thật:

public class StrNull {
    public static void main() {
        String s = null;
        s += "x";
        IO.println(s);                    // nullx
        IO.println("gia tri: " + s);      // gia tri: nullx
        IO.println("" + null + null);     // nullnull

}
Vì lý do này, đừng dựa vào + để "che" null. Ở biên nhận dữ liệu (JSON, DB, form), hãy validate/Objects.requireNonNull trước khi nối, hoặc dùng String.valueOf(s) khi muốn rõ ý "null thành chuỗi".

14.4 switch trên String hoạt động thế nào (Java 7+)

Java 7 cho switch trên String. Bên dưới compiler làm hai bước: lấy hashCode() để nhảy nhanh tới nhóm case, rồi so equals() để chốt. Chạy thử với một String tạo bằng new (ngoài pool) vẫn khớp bình thường:

public class StrSwitch {
    public static void main() {
        String key = new String("b");
        switch (key) {
            case "a" -> IO.println("nhanh a");   // khong in
            case "b" -> IO.println("nhanh b");   // nhanh b
            default  -> IO.println("khac");
        }

        String upper = "B";
        IO.println("equals          : " + upper.equals("b"));            // equals          : false
        IO.println("equalsIgnoreCase: " + upper.equalsIgnoreCase("b"));  // equalsIgnoreCase: true
    }
}

14.5 Nối chuỗi trong vòng lặp — String vs StringBuilder

Mỗi phép += tạo một object mới; trong vòng lặp N lần là N object rác cho GC. StringBuilder giữ một buffer và append tại chỗ:

public class StrBuilder {
    public static void main() {
        String s = "";
        for (int i = 1; i <= 5; i++) {
            s += i;                       // moi vong tao mot String moi
        }
        IO.println("noi +   : " + s);     // noi +   : 12345

        StringBuilder sb = new StringBuilder();
        for (int i = 1; i <= 5; i++) {
            sb.append(i);                 // them vao cung mot buffer
        }
        IO.println("builder : " + sb);    // builder : 12345
    }
}

Quy tắc thực dụng: một biểu thức + đơn lẻ thì cứ viết thoải mái (compiler đã tối ưu từ Java 9); nối trong for/while hoặc build động thì dùng StringBuilder — chi tiết capacity, StringBuffer và invokedynamic ở Strings — mục 8.

15.3 Thread-safety: static mutable là bẫy lớn Junior+

Node.js chạy một luồng nên ít gặp. Java đa luồng thật, và count++ không phải một phép tính — nó là đọc → cộng → ghi, nên hai thread có thể ghi đè nhau:

public class RaceDemo {
    static int count = 0;                            // NGUY HIEM
    static final AtomicLong atomicCount = new AtomicLong();

    static void tang() {
        for (int i = 0; i < 200_000; i++) {
            count++;                                 // race condition
            atomicCount.incrementAndGet();           // an toan
        }
    }

    public static void main() throws InterruptedException {
        Thread t1 = new Thread(RaceDemo::tang);
        Thread t2 = new Thread(RaceDemo::tang);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        IO.println("int    : " + count + " (ky vong 400000)");
        IO.println("atomic : " + atomicCount + " (luon dung 400000)");
    }
}

Một lần chạy thật:

int    : 298949 (ky vong 400000)
atomic : 400000 (luon dung 400000)
  • int cho kết quả sai và mỗi lần chạy một khác — đó là race condition.
  • AtomicLong dùng cơ chế CAS (compare-and-swap) nên luôn đúng, hiệu năng tốt hơn synchronized cho counter.
  • volatile chỉ đảm bảo các thread nhìn thấy giá trị mới nhất, không đảm bảo ++ an toàn. Câu chốt phỏng vấn: volatile cho visibility, atomic cho cả visibility lẫn atomicity.
  • Nguyên tắc: hạn chế tối đa static mutable; cần đếm thì dùng AtomicLong.

Java không có hàm deep copy dựng sẵn kiểu structuredClone() của JS. Cách production hay dùng nhất là copy constructor / factory tự viết — rõ ràng và kiểm soát được từng field:

    List<String> items;

        this.items = items;

    Order(Order other) {                       // copy constructor: deep
        this.code = other.code;
        this.items = new ArrayList<>(other.items);
    }
}

Order o1 = new Order("DH1", new ArrayList<>(List.of("Ao")));
Order o2 = new Order(o1);
o2.items.add("Quan");

// deep copy    : o1=[Ao] | o2=[Ao, Quan]

Serialization round-tripCóChậm, cần Serializable, không giữ identity — chỉ dùng khi bất đắc dĩ
JSON round-trip (Jackson)CóTiện khi đã có DTO; mất kiểu đặc biệt (Date, Map, identity)
Thiết kế immutable (record + List.copyOf)Không cần copyCách được khuyến nghị nhất trong production

Bẫy: bất biến của record chỉ là nông

record OrderRecord(String code, List<String> items) {}

OrderRecord r1 = new OrderRecord("DH2", new ArrayList<>(List.of("Giay")));
r1.items().add("Dep");                    // record KHONG bao ve list ben trong!
IO.println("record       : " + r1.items());   // [Giay, Dep]

int[][] grid = {{1, 2}, {3, 4}};
int[][] gridClone = grid.clone();         // clone() cung la shallow
gridClone[0][0] = 99;
IO.println("clone 2D     : " + Arrays.deepToString(grid)); // [[99, 2], [3, 4]]
Muốn immutable thật: class/record phải copy phòng thủ khi nhận và khi trả field mutable — constructor làm this.items = List.copyOf(items), getter trả List.copyOf(items). Chi tiết defensive copy sẽ gặp lại ở doc Encapsulation & Immutability (mục 2.2).

Góc Node.js

  • {...obj}, [...arr], Object.assign của JS là shallow — giống new ArrayList<>(list).
  • structuredClone() là deep copy dựng sẵn (trừ function/class method) — Java không có tương đương, phải viết copy constructor hoặc dùng round-trip.
  • JSON.parse(JSON.stringify(obj)) là deep "giả": mất Date, Map, Set, undefined — giống hạn chế của JSON round-trip bên Java.

18. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Kể tên 8 kiểu nguyên thủy của Java.
byte (8-bit), short (16-bit), int (32-bit), long (64-bit), float (32-bit), double (64-bit), char (16-bit UTF-16), boolean. Mọi thứ khác là reference type. Java không phải pure OOP chính vì còn 8 primitive.
Câu 2. Biến local khác field thế nào về giá trị mặc định?
Field được gán mặc định (0, 0.0, false, '\u0000', null). Biến local không có mặc định — dùng khi chưa gán bị lỗi compile "variable might not have been initialized".
Câu 3. int và Integer khác nhau thế nào?
int là primitive, luôn có giá trị, không null, nhanh và nhẹ. Integer là wrapper object: cho phép null, dùng được trong collections/generics. So sánh Integer bằng == là so địa chỉ — phải dùng .equals().
Câu 4. final dùng để làm gì? Có giống const của JS không?
Giống ở chỗ khoá gán lại. Khác: final chỉ khoá biến trỏ tới object, nội dung object vẫn sửa được (final List vẫn add() được). Java không có từ khóa const.
Câu 5. == và equals() khác nhau thế nào?
== so giá trị với primitive, so địa chỉ (cùng object hay không) với reference. equals() so nội dung, với điều kiện class đó override (String, wrapper, record... đều override sẵn). So sánh String/wrapper luôn dùng .equals().
Câu 6. char và String khác nhau thế nào?
char là primitive 16-bit, bản chất là một con số Unicode, viết nháy đơn 'a', tham gia tính toán như số. String là object bất biến, viết nháy kép "a", là chuỗi ký tự.
Câu 7. Autoboxing / unboxing là gì? Cho ví dụ.
Autoboxing là tự động bọc primitive thành wrapper (Integer x = 5), unboxing là ngược lại (int y = x). Compiler chèn Integer.valueOf()/intValue(). Cần vì collections như List<Integer> chỉ chứa object.
Câu 8. Vì sao không nên dùng double/float cho tiền?
Số thực nhị phân IEEE 754 không biểu diễn chính xác số thập phân: 0.1 + 0.2 = 0.30000000000000004. Sai số tích lũy qua nhiều giao dịch. Tiền tệ luôn dùng BigDecimal và tạo bằng chuỗi.
Câu 9. Khi nào dùng long thay int?
Khi giá trị có thể vượt ~2,1 tỷ: ID auto-increment lớn, snowflake ID, timestamp milli/micro giây, kích thước file. Production mặc định ID và timestamp là long.
Câu 10. var là gì? Nó có biến Java thành ngôn ngữ kiểu động không?
Không. var (Java 10) chỉ là suy luận kiểu local — compiler chốt kiểu ngay lúc compile, sau đó không đổi được. Chỉ dùng cho biến local và bắt buộc có giá trị khởi tạo.

Nâng cao (Junior+)

Câu 11. Integer cache là gì? Vì sao 128 == 128 là false?
Autoboxing gọi Integer.valueOf(), method này cache sẵn các giá trị -128 → 127. Trong khoảng đó hai biến trỏ cùng object nên == true; ngoài khoảng tạo object mới nên == false. Long, Short... cũng có cache tương tự.
Câu 12. Unboxing một Integer đang null thì xảy ra gì?
NullPointerException ngay tại dòng đó, vì compiler chèn x.intValue() — gọi method trên null. Rất hay gặp khi đọc cột DB nullable; phải kiểm tra null trước hoặc dùng Optional.
Câu 13. Stack và Heap khác nhau thế nào? Biến được lưu ở đâu?
Stack: mỗi thread một cái, chứa biến local primitive và địa chỉ object, LIFO, nhanh, tràn thì StackOverflowError. Heap: dùng chung, chứa object thật, do GC quản lý, hết thì OutOfMemoryError. Biến static gắn với class, không thuộc object.
Câu 14. Java pass-by-value hay pass-by-reference?
Luôn pass-by-value. Với object, giá trị được copy là địa chỉ, nên method sửa được nội dung object (add vào list) nhưng gán lại reference (new list) thì bên ngoài không đổi.
Câu 15. String pool / intern là gì?
Pool là vùng nhớ chứa các String literal để tái sử dụng. "java" == "java" là true vì cùng nằm trong pool. new String("java") tạo object mới ngoài pool nên == false; intern() đưa chuỗi về pool.
Câu 16. Numeric promotion là gì? Vì sao 'a' + 1 trả về int?
Khi tính toán, byte/short/char được nâng lên int trước, kết quả cũng là int. Nên 'a' + 1 = 98 (int), muốn thành ký tự 'b' phải ép (char).
Câu 17. Vì sao byte b = 10; b += 5; chạy được mà b = b + 5; không?
Compound assignment (+=) có ngầm ép kiểu do JLS quy định — tương đương b = (byte)(b + 5). Còn b + 5 là int, gán vào byte cần ép tường minh, nếu không compiler báo possible lossy conversion from int to byte.
Câu 18. Tràn số nguyên là gì? Math.addExact để làm gì?
Vượt giới hạn kiểu thì giá trị quay vòng (wraparound) và không có exception: Integer.MAX_VALUE + 1 = -2147483648. Math.addExact/multiplyExact ném ArithmeticException (message integer overflow) để phát hiện sớm.
Câu 19. Blank final là gì?
Biến final khai báo không có giá trị, được gán đúng một lần trong constructor. Mỗi object có giá trị riêng nhưng bất biến sau khi tạo — dùng cho dependency injection, config của object.
Câu 20. final với một List — nội dung có sửa được không?
Được. final chỉ khoá việc gán lại biến, còn list.add() sửa nội dung object vẫn bình thường. Muốn bất biến thật dùng List.of()/List.copyOf() hoặc immutable object.
Câu 21. Effectively final là gì?
Biến local không khai báo final nhưng chỉ được gán đúng một lần — compiler coi như final, cho phép dùng trong lambda/anonymous class. Gán lại lần nữa là lỗi "must be final or effectively final".
Câu 22. volatile khác AtomicLong thế nào?
volatile đảm bảo visibility (thread khác thấy giá trị mới) nhưng ++ vẫn là read-modify-write nên không atomic. AtomicLong dùng CAS đảm bảo cả visibility lẫn atomicity — đúng cho counter.
Câu 23. Vì sao biến static mutable nguy hiểm trong đa luồng?
Static mutable là state dùng chung giữa mọi thread. count++ gồm đọc → cộng → ghi, hai thread xen kẽ sẽ mất cập nhật (race condition) — kết quả mỗi lần chạy một khác. Cách xử lý: tránh static mutable, dùng AtomicLong, synchronized, hoặc chỉ dùng static final immutable.
Câu 24. BigDecimal.equals() khác compareTo()? divide() có thể ném gì?
equals() so cả giá trị lẫn scale nên 1.0 ≠ 1.00; compareTo() so giá trị, trả 0 khi bằng. divide() với phép chia vô hạn (1/3) mà không truyền scale + RoundingMode sẽ ném ArithmeticException: Non-terminating decimal expansion.
Câu 25. Enum có field/method để làm gì? Sao không dùng String constant?
Enum giới hạn đúng tập giá trị hợp lệ (type-safe), gõ sai là lỗi compile; có thể gắn nhãn, giá trị, method riêng cho từng hằng. String constant không giới hạn giá trị, dễ typo, so sánh phải equals — không nên dùng cho trạng thái nghiệp vụ.
Câu 26. Vì sao 1000 * 60 * 60 * 24 * 365 cho kết quả sai? Sửa thế nào?
Vì là phép nhân int: 1000 * 60 * 60 * 24 * 365 = 31.536.000.000, vượt 2,1 tỷ nên tràn trước khi gán vào biến long (nếu có) — kết quả sai là 1471228928. Sửa: 1000L * 60 * 60 * 24 * 365 — bắt đầu bằng long để cả biểu thức tính theo long, ra 31536000000.
Câu 27. static final field khác final field thế nào?
final field: mỗi object một bản, không đổi sau khi tạo. static final: một bản duy nhất dùng chung cho cả class — đây mới là "hằng số" theo đúng nghĩa, tên viết UPPER_SNAKE_CASE.
Câu 28. Shallow copy và deep copy khác nhau thế nào?
Shallow copy tạo object vỏ mới nhưng các field reference vẫn trỏ object cũ (new ArrayList<>(list)). Deep copy tạo luôn object con mới, sửa bản copy không ảnh hưởng gốc (copy constructor tự viết). Mọi cách copy có sẵn trong JDK (clone, Arrays.copyOf, List.copyOf) đều là shallow.
Câu 29. Java có sẵn hàm deep copy như structuredClone() của JS không? Làm sao deep copy?
Không có. Cách production: viết copy constructor/factory method copy từng field (khuyến nghị); hoặc serialization/JSON round-trip (chậm, mất kiểu, không giữ identity). Object.clone() mặc định chỉ shallow. Cách tốt nhất vẫn là thiết kế bất biến để không cần deep copy.
Câu 30. Record có bất biến sâu không?
Không. Record chỉ khoá việc gán lại field; nếu record chứa List, Map hay object mutable thì nội dung đó vẫn sửa được (r.items().add(...) chạy bình thường). Muốn bất biến thật phải copy phòng thủ trong constructor và getter: List.copyOf(items).
