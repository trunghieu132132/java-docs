Inheritance — kế thừa trong Java

Kế thừa (inheritance) cho phép một class thừa hưởng field và method từ class khác, biến quan hệ đời thường "Dog là một Animal" (is-a) thành code thật: class Dog extends Animal. Đây là cơ chế đứng sau polymorphism, abstract class, exception hierarchy và gần như toàn bộ thư viện JDK. Nhưng kế thừa cũng là công cụ bị lạm dụng nhiều nhất — trang này không chỉ dạy cách viết extends, mà còn dạy khi nào không nên dùng, cùng các bẫy khởi tạo và override mà phỏng vấn Junior+ rất hay hỏi.

1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Hai thuật ngữ bạn sẽ gặp suốt:

  • Superclass (lớp cha, base class) — class bị kế thừa, giữ phần chung: Animal.
  • Subclass (lớp con, derived class) — class đi kế thừa, thêm phần riêng: Dog. Java dùng từ khoá extends ("mở rộng").

Ví dụ đời thường: "Xe máy là một phương tiện", "hóa đơn VAT là một hóa đơn", "Dog là một Animal". Quan hệ đọc là "is-a" (là một). Ngược lại, "Xe máy có một động cơ" là quan hệ has-a — đó là composition, học ở mục 9. Chọn nhầm is-a/has-a là lỗi thiết kế phổ biến nhất của người mới.

Ba sự thật quan trọng của Java mà bạn phải nhớ:

  • Đơn kế thừa: một class chỉ extends đúng một class. Không có "đa kế thừa class" như C++. Muốn nhiều "kiểu" thì dùng interface (học ở 2.5 Abstract class vs Interface).
  • Mọi class đều là con cháu của Object: viết hay không viết extends Object thì Object vẫn là gốc (mục 8).
  • Kế thừa là bắc cầu: Dog extends Animal, Animal extends Object — Dog thừa hưởng cả chuỗi.

Mức độ bắt buộc của chủ đề 2.3 (phỏng vấn: rất cao · production: bắt buộc):

  • Phải làm được — viết extends đúng; gọi super(args) và super.method(); override kèm @Override; phân biệt override / overload / hiding; chọn composition khi quan hệ không phải is-a; dự đoán được thứ tự khởi tạo cha/con.
  • Phải hiểu — constructor không được thừa hưởng; compiler tự chèn super(); quy tắc visibility/return type/exception khi override; static binding vs dynamic dispatch; vì sao gọi method overridable trong constructor là bẫy; LSP.
  • Nhận biết — sealed class (JDK 17+), JEP 513 Flexible Constructor Bodies (JDK 25), diamond problem, "favor composition over inheritance".

Cách học hiệu quả nhất:

  1. Đoán output của ví dụ trước khi nhìn comment kết quả.
  2. Làm mục Bài tập đoán output trước, chỉ mở đáp án sau khi đã đoán.
  3. Ôn nhanh bằng Cheat sheet trước buổi phỏng vấn.
  4. Gặp câu lạ, tra ở mục Interview Q&A.
Ví dụ dùng IO.println(...) — cách viết gọn của JDK 25 (JEP 512) — và dạng class đầy đủ chạy bằng java TenFile.java. Kết quả chạy thật in ngay bên dưới mỗi ví dụ. Code production vẫn dùng public static void main(String[] args) như bạn thấy trong đề phỏng vấn.

Góc Node.js — prototype chain vs class extends

Nếu bạn đến từ JS/Node, kế thừa không còn xa lạ — nhưng cơ chế bên dưới khác hẳn. JavaScript không có "class" thật: class ... extends chỉ là cú pháp đường (syntactic sugar) trên prototype chain. Mỗi object có một liên kết ẩn [[Prototype]]; khi truy cập dog.speak(), engine dò theo chuỗi prototype cho tới khi tìm thấy. Java không có prototype: class được biên dịch cố định, method được gọi qua bảng ảo (virtual dispatch) do JVM quản lý.

Đoạn JS dưới đây cho kết quả y hệt phiên bản Java ở mục 2:

// JavaScript - chi de so sanh, KHONG phai Java
class Animal {
  constructor(name) {
    this.name = name;
  }
  speak() {
    console.log(this.name + " phat ra am thanh...");
  }
}

class Dog extends Animal {
  speak() {
    console.log(this.name + ": Gau gau!");
  }
}

new Dog("Milu").speak();   // Milu: Gau gau!
Điểm dễ nhầm nhất: trong JS, method "override" thực chất là gán một property mới lên prototype của lớp con; trong Java, override là ghi đè entry trong bảng method của class — compiler kiểm tra chặt (signature, visibility, return type, exception) nên sai sẽ lỗi ngay khi compile, không đợi tới lúc chạy.

2. Cú pháp extends & từ khoá super Junior+

[modifier] class TenCon extends TenCha { ... }

Trong thân class con, super có ba dạng dùng, ý nghĩa khác nhau:

super(args);     // gọi constructor của lớp cha
super.method(args);     // gọi bản method của lớp cha (không dispatch)
this(args);     // gọi constructor khác của CHÍNH class này

Ví dụ nền tảng — Dog thừa hưởng name() và speak() từ Animal, override speak(), rồi gọi bản gốc qua super.speak():

class Animal {
    private final String name;

    Animal(String name) {
        this.name = name;
    }

    String name() {
        return name;
    }

    void speak() {
        IO.println(name + " phat ra am thanh...");
    }
}

public class Dog extends Animal {
    Dog(String name) {
        super(name);
    }

    @Override
    void speak() {
        IO.println(name() + ": Gau gau!");
    }

    void showAll() {
        super.speak();
        speak();
    }

    public static void main() {
        Dog dog = new Dog("Milu");
        dog.speak();
        dog.showAll();
    }
}
Milu: Gau gau!
Milu phat ra am thanh...
Milu: Gau gau!

Ba điều rút ra từ ví dụ:

  • Dog không khai báo name nhưng vẫn có, vì field private final String name nằm ở Animal. Field private vẫn thuộc về object con — chỉ là code con không truy cập trực tiếp được (đó là encapsulation, không phải "không thừa hưởng").
  • super.speak() gọi thẳng bản của cha; còn speak() trong showAll() vẫn dispatch tới bản của Dog dù code nằm ở đâu.
  • Dog(String name) { super(name); } — constructor con bắt buộc lo việc gọi constructor cha (xem quy tắc bên dưới).

Constructor khi kế thừa — 4 quy tắc

  1. Constructor không được thừa hưởng. Animal(String) không tự trở thành constructor của Dog; mỗi class phải tự khai báo constructor của mình. Vì vậy new Dog() trong khi Dog chỉ có Dog(String) là lỗi compile.
  2. Không gọi tường minh thì compiler tự chèn super() (constructor cha không tham số) vào đầu constructor con. Nếu lớp cha không có constructor no-arg, bạn buộc phải gọi super(args) — nếu không sẽ lỗi compile:

}

class Animal {

    String name() {
        return name;
    }

Ngoại lệ duy nhất được phép: gán field của chính class (field không có initializer) trước super() — kỹ thuật JEP 513 giới thiệu để field của con đã đúng ngay cả khi method override bị gọi từ constructor cha (xem mục 14):

class Animal {
    Animal() {
        IO.println("Animal()");
    }
}

public class Dog extends Animal {
    private final int age;

    Dog(int age) {
        this.age = age;
        IO.println("gan age truoc super()");
        super();
        IO.println("age = " + this.age);
    }

    public static void main() {
        new Dog(3);
    }
}

Đừng lạm dụng prologue. Code trước super() chỉ nên là validate tham số, tính toán thuần tuý, hoặc gán field. Mọi thứ phức tạp nên nằm sau super(). Phỏng vấn vẫn hỏi theo luật cũ "super phải là câu đầu tiên" — hãy trả lời kèm ngữ cảnh JDK 25 (JEP 513) để ghi điểm.

3. Thứ tự khởi tạo cha/con đầy đủ Hay hỏi phỏng vấn

Đây là câu hỏi kinh điển: khi chạy new Dog(), code nào chạy trước? Câu trả lời đúng phải kể đủ 6 bước, và phân biệt rõ static (chạy một lần khi class được nạp) với instance (chạy mỗi lần tạo object):

  1. static initializer của lớp cha — khi class con được nạp lần đầu, JVM nạp và khởi tạo lớp cha trước (cha trước con).
  2. static initializer của lớp con.
  3. instance field + instance initializer của lớp cha, theo thứ tự xuất hiện trong file.
  4. thân constructor lớp cha.
  5. instance field + instance initializer của lớp con, theo thứ tự xuất hiện.
  6. thân constructor lớp con.

Ví dụ chạy thật dưới đây in đúng thứ tự đó. Chú ý: vì main nằm trong Dog, hai dòng static của cha/con in ra trước cả khi thân main chạy — nhưng vẫn đúng thứ tự cha trước con:

class Animal {
    static {
        IO.println("1. static initializer Animal");
    }

    int animalField = initAnimalField();

    int initAnimalField() {
        IO.println("3. instance field Animal");
        return 10;
    }

    Animal(String name) {
        IO.println("4. constructor Animal");
    }
}

public class Dog extends Animal {
    static {
        IO.println("2. static initializer Dog");
    }

    int value = 42;

    {
        IO.println("5. instance initializer Dog");
    }

    Dog(String name) {
        super(name);
        IO.println("6. constructor Dog");
    }

    public static void main() {
        Dog dog = new Dog("Milu");
        IO.println("dog.value = " + dog.value);
    }
}

Ghi nhớ bằng một câu: static cha → static con → instance cha → constructor cha → instance con → constructor con. Hệ quả thực chiến: mọi field của lớp con lúc constructor cha chạy vẫn còn giá trị mặc định (0, null, false). Nếu constructor cha gọi một method bị override ở con, method đó sẽ đọc phải field chưa khởi tạo — xem mục 14.

Các lần new Dog() sau chỉ chạy bước 3–6; static initializer chỉ chạy đúng một lần cho mỗi class loader. Bạn có thể tự kiểm chứng bằng cách thêm dòng new Dog("Milu"); thứ hai trong main.

4. Method overriding & @Override Hay hỏi phỏng vấn

Override = lớp con định nghĩa lại một instance method của lớp cha với đúng signature (tên + danh sách kiểu tham số). Khác overload (cùng class, khác tham số), override xảy ra giữa cha và con và được quyết định lúc chạy (dynamic dispatch).

Annotation @Override không bắt buộc về mặt cú pháp, nhưng gần như luôn nên viết: compiler sẽ báo lỗi nếu bạn tưởng đang override mà thực ra không phải (sai tên, sai tham số, method cha là private/static...).

class Animal {
    Number makeSound() {
        IO.println("Animal sound");
        return 0;
    }

    String speak() {
        return "Animal speaks";
    }
}

public class Dog extends Animal {
    @Override
    Integer makeSound() {
        IO.println("Dog sound");
        return 1;
    }

    @Override
    String speak() {
        return "Dog speaks: Gau gau!";
    }

    public static void main() {
        Animal animal = new Dog();
        IO.println(animal.speak());
        IO.println(animal.makeSound().getClass().getSimpleName());
    }
}
Dog speaks: Gau gau!
Dog sound
Integer

Quan sát: biến animal có kiểu Animal nhưng animal.speak() gọi bản của Dog — đó chính là polymorphism (2.4). makeSound() minh hoạ covariant return type: lớp con được trả về kiểu hẹp hơn (Integer thay vì Number); compiler sinh "bridge method" để JVM vẫn dispatch đúng.

5. static: hiding chứ không phải override Hay hỏi phỏng vấn

Static method không tham gia dynamic dispatch. Nếu lớp con khai báo method static trùng signature với static method của cha, đó là hiding (che khuất): gọi method nào phụ thuộc vào kiểu của reference lúc compile, không phải object thật:

class Animal {
    static void info() {
        IO.println("Animal.info() - static");
    }
}

public class Dog extends Animal {
    static void info() {
        IO.println("Dog.info() - hiding, khong phai override");
    }

    public static void main() {
        Animal animal = new Dog();
        animal.info();

        Dog dog = new Dog();
        dog.info();

        ((Animal) dog).info();
    }
}
Animal.info() - static
Dog.info() - hiding, khong phai override
Animal.info() - static

Dù object thật là Dog, animal.info() vẫn gọi Animal.info() vì kiểu reference là Animal. Đây là lý do static method không thể là "polymorphism".

Không được trộn static của cha với instance của con (và ngược lại) — compiler chặn cả hai chiều:

    static void info() {
        IO.println("Animal.info()");

}

public class Dog extends Animal {
    void info() {
        IO.println("Dog.info()");
    }

    public static void main() {
    }
}

9. Composition vs inheritance Production

Nguyên tắc nổi tiếng (Effective Java, Item 18): "Favor composition over inheritance" — ưu tiên composition thay vì kế thừa. Kế thừa chỉ đúng khi quan hệ is-a thật sự và class cha được thiết kế để cho kế thừa; còn nếu bạn chỉ muốn tái dùng code thì composition gần như luôn thắng.

Ví dụ kinh điển: viết stack bằng cách kế thừa ArrayList. Nghe "tiết kiệm" vì được tặng miễn phí add, remove, size... nhưng chính món quà đó phá vỡ invariant LIFO của stack:

import java.util.ArrayList;

public class BadStack<E> extends ArrayList<E> {
    void push(E e) {
        add(e);
    }

    E pop() {
        return remove(size() - 1);
    }

    public static void main() {
        BadStack<String> stack = new BadStack<>();
        stack.push("a");
        stack.push("b");
        stack.add(0, "chen vao giua");
        IO.println(stack);
        IO.println("pop -> " + stack.pop());
    }
}
[chen vao giua, a, b]
pop -> b

Người dùng stack có thể gọi thẳng add(0, ...), remove(0), set(...) — stack không còn là stack. Tệ hơn: mọi thay đổi của ArrayList trong tương lai đều có thể ảnh hưởng tới BadStack mà bạn không kiểm soát. Trong JDK thật, java.util.Stack extends Vector cũng mắc lỗi thiết kế y hệt và được khuyến cáo dùng ArrayDeque thay thế.

Bản đúng dùng composition + delegation: giữ một Deque bên trong và chỉ lộ đúng API của stack:

import java.util.ArrayDeque;
import java.util.Deque;

public class GoodStack<E> {
    private final Deque<E> data = new ArrayDeque<>();

    void push(E e) {
        data.addLast(e);
    }

    E pop() {
        return data.removeLast();
    }

    E peek() {
        return data.getLast();
    }

    int size() {
        return data.size();
    }

    public static void main() {
        GoodStack<String> stack = new GoodStack<>();
        stack.push("a");
        stack.push("b");
        IO.println("size = " + stack.size());
        IO.println("pop  = " + stack.pop());
        IO.println("peek = " + stack.peek());
    }
}
size = 2
pop  = b
peek = a

Giờ không ai chèn được vào giữa stack: API công khai chỉ có push, pop, peek, size. Bên trong đổi từ ArrayDeque sang cấu trúc khác cũng không ảnh hưởng người dùng.

10. LSP — nguyên lý thay thế Production

Liskov Substitution Principle (LSP): chỗ nào code cần lớp cha thì phải thay được bằng object của lớp con mà chương trình vẫn đúng. Nói cách khác: lớp con không được làm điều mà người dùng lớp cha không ngờ tới. Kế thừa là một lời hứa — vi phạm LSP là phá lời hứa đó.

class Bird {
    void fly() {
        IO.println("Dang bay...");
    }
}

public class Penguin extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException("Chim canh cut khong bay duoc");
    }

    static void choChimBay(Bird bird) {
        bird.fly();
    }

    public static void main() {
        choChimBay(new Bird());

        try {
            choChimBay(new Penguin());
        } catch (UnsupportedOperationException e) {
            IO.println("Loi LSP: " + e.getMessage());
        }
    }
}
Dang bay...
Loi LSP: Chim canh cut khong bay duoc

Hàm choChimBay(Bird) được viết dựa trên giả định "Bird nào cũng bay". Penguin là Bird nhưng ném lỗi — mọi call site cũ bị phá. Cách sửa đúng: đừng đặt fly() ở Bird; tách interface Flyable cho các loài bay được, còn Penguin chỉ là Bird (interface học ở 2.5).

Dấu hiệu code đang vi phạm LSP:

  • Override mà ném UnsupportedOperationException, hoặc biến method thành no-op rỗng.
  • Code khách hàng phải instanceof/ép kiểu để xử lý riêng từng lớp con.
  • Lớp con làm yếu precondition (nhận ít hơn), làm mạnh postcondition (trả về ít hơn) so với cha.
  • Comment kiểu "phải gọi method X trước khi gọi Y" chỉ đúng với một lớp con.

LSP là chữ L trong SOLID — xem thêm ở 2.8 SOLID & design patterns. Nhớ câu thần chú: kế thừa không phải để tái dùng code, mà để thay thế được (substitutability).

11. instanceof & cast (giới thiệu) Junior+

Vì lớp con là một dạng của lớp cha, gán con cho biến kiểu cha luôn an toàn — gọi là upcast, không cần ép kiểu:

Ví dụ 2 — equals thêm state ở lớp con gây bất đối xứng

import java.util.Objects;

class Animal {
    protected final String name;

    Animal(String name) {
        this.name = name;
    }

    @Override
    public boolean equals(Object o) {
        if (o instanceof Animal other) {
            return name.equals(other.name);
        }
        return false;
    }

    @Override
    public int hashCode() {
        return name.hashCode();
    }
}

public class Dog extends Animal {
    private final String breed;

    Dog(String name, String breed) {
        super(name);
        this.breed = breed;
    }

    @Override
    public boolean equals(Object o) {
        if (o instanceof Dog other) {
            return super.equals(o) && breed.equals(other.breed);
        }
        return false;
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, breed);
    }

    public static void main() {
        Animal a = new Animal("Milu");
        Dog d = new Dog("Milu", "Poodle");
        IO.println("a.equals(d) = " + a.equals(d));
        IO.println("d.equals(a) = " + d.equals(a));
        IO.println("a.hashCode() == d.hashCode() = " + (a.hashCode() == d.hashCode()));
    }
}
a.equals(d) = true
d.equals(a) = false
a.hashCode() == d.hashCode() = false

a.equals(d) là true nhưng d.equals(a) là false — vi phạm tính đối xứng (symmetry); kèm theo đó hai object "bằng nhau" lại có hashCode khác nhau. Contract yêu cầu x.equals(y) thì y.equals(x), và equals thì hashCode phải bằng nhau. Cách xử lý chuẩn (dùng composition thay vì kế thừa, hoặc chấp nhận không so được hai chiều) sẽ học kỹ ở 2.6 equals / hashCode / toString.

Cơ bản

Câu 1. Kế thừa là gì? extends làm gì?
Kế thừa cho phép lớp con (subclass) thừa hưởng field và method của lớp cha (superclass), tạo quan hệ is-a. class Dog extends Animal nghĩa là Dog có mọi thành viên không-private của Animal, dùng được chúng như của mình, và có thể override để thay đổi hành vi. Java chỉ cho đơn kế thừa class.
Câu 2. Vì sao Java không cho đa kế thừa class? Diamond problem là gì?
Đa kế thừa class tạo ra "diamond problem": nếu A có method x(), B và C đều extends A và override x(), thì D extends B, C gọi x() theo bản nào? Java chọn đơn kế thừa cho class để tránh nhập nhằng, nhưng cho phép implements nhiều interface. Với interface có default method, nếu xung đột xảy ra, compiler buộc lớp con override để chọn cách giải quyết.
Câu 3. Constructor có được thừa hưởng không? Vì sao?
Không. Constructor không phải thành viên (member) nên không được thừa hưởng; mỗi class phải tự khai báo constructor của mình. Tên constructor trùng tên class nên về bản chất cũng không thể thừa hưởng sang class tên khác. Constructor con bắt buộc gọi trực tiếp hoặc gián tiếp constructor cha qua super(...).
Câu 4. Nếu constructor không gọi super(...) thì chuyện gì xảy ra? Khi nào lỗi?
Compiler tự chèn super() (không tham số) vào đầu constructor. Nếu lớp cha không có constructor no-arg, chương trình lỗi compile: "constructor Animal in class Animal cannot be applied to given types". Lúc đó bạn buộc phải gọi tường minh super(args).
Câu 5. this(...) và super(...) khác nhau thế nào? Gọi cả hai trong một constructor được không?
super(...) gọi constructor lớp cha; this(...) gọi constructor khác cùng class (constructor chaining). Không được gọi cả hai trong cùng constructor — compiler báo "redundant explicit constructor invocation" hoặc lỗi tương tự. Từ JDK 25 (JEP 513), câu lệnh không đụng this được phép đứng trước lời gọi constructor, nhưng điều này không thay đổi việc chỉ được gọi tối đa một constructor khác.
Câu 6. Override và overload khác nhau thế nào?
Override: lớp con định nghĩa lại method của cha với cùng signature; quyết định lúc chạy theo object thật. Overload: nhiều method cùng tên khác danh sách tham số (thường trong cùng class); quyết định lúc compile theo kiểu tham số. Override có ràng buộc return type covariant, visibility không giảm, exception không mở rộng — overload không có các ràng buộc này.
Câu 7. @Override có bắt buộc không? Vì sao nên dùng?
Không bắt buộc — code vẫn compile nếu thiếu. Nhưng nên luôn viết: compiler kiểm tra method đó thật sự override một method cha/interface, nhờ đó bắt được lỗi sai tên, sai tham số, method cha private/static... Nếu không, bạn có thể vô tình tạo overload mới và method cũ không bao giờ được gọi.
Câu 8. Khi override, quy tắc về return type, visibility, exception là gì?
Return type: giống hoặc covariant (kiểu con). Visibility: không được giảm, chỉ được tăng. Checked exception: không được ném rộng hơn method cha (có thể hẹp hơn hoặc bỏ); unchecked exception không bị hạn chế. Thêm nữa, không override được private, static, final; constructor không tính là override.
Câu 9. static method có override được không? Hiện tượng đó gọi là gì?
Không. Nếu lớp con khai báo static method trùng signature, đó là hiding (che khuất), không phải override. Method được chọn theo kiểu reference lúc compile, không theo object thật. Ví dụ biến Animal animal = new Dog(); animal.info(); vẫn gọi Animal.info() dù object là Dog.
Câu 10. Private method trùng tên ở lớp con — có phải override không?
Không. Private method không được thừa hưởng nên lớp con khai báo cùng tên chỉ là một method mới, không liên quan gì tới method cha. Method private của cha được bind tĩnh (early binding): nếu code trong class cha gọi nó, luôn chạy bản của cha dù object thật là lớp con.

Nâng cao (Junior+)

Câu 11. Trình bày đầy đủ thứ tự khởi tạo khi tạo một object lớp con.
(1) static initializer lớp cha → (2) static initializer lớp con → (3) instance field/initializer của cha → (4) thân constructor cha → (5) instance field/initializer của con → (6) thân constructor con. Phần static chỉ chạy lần đầu class được nạp; phần instance chạy mỗi lần new. Vì vậy field của con luôn có giá trị mặc định khi constructor cha đang chạy.
Câu 12. Vì sao không nên gọi method overridable trong constructor?
Vì constructor cha chạy trước khi field của con được khởi tạo. Nếu method bị con override được gọi từ constructor cha, bản của con chạy khi mọi field riêng của con còn là 0/null — bug rất khó tìm. Giải pháp: chỉ gọi method private/final/static trong constructor, hoặc dùng prologue JEP 513 để gán field con trước super().
Câu 13. Mọi class có kế thừa Object không? Interface thì sao?
Mọi class — kể cả class không viết extends, record, enum, mảng — đều có Object ở gốc. Interface không extends Object, nhưng mọi object thực hiện interface vẫn là Object; biến kiểu interface vẫn gọi được các method của Object như toString(), equals(). Một interface có thể extends nhiều interface khác.
Câu 14. Upcast và downcast là gì? Khi nào ClassCastException xảy ra?
Upcast: gán object con cho biến kiểu cha — luôn an toàn, tự động (Animal a = new Dog()). Downcast: ép biến kiểu cha về kiểu con ((Dog) a) — cần thiết khi muốn dùng API riêng của con. Nếu object thật không phải kiểu đích (hoặc lớp con của nó), JVM ném ClassCastException lúc chạy. Luôn kiểm tra bằng instanceof trước khi cast.
Câu 15. final method, final class, final field khác nhau thế nào? Cho ví dụ JDK.
final method: lớp con không override được. final class: không class nào extends được — ví dụ String, Integer, mọi record. final field/biến: gán một lần, không đổi được. Cả ba đều là công cụ thiết kế để nói rõ "phần này cố ý bất biến"; String final giúp bất biến và dùng chung an toàn trong string pool.
Câu 16. Khi nào dùng composition thay vì kế thừa? "Favor composition over inheritance" nghĩa là gì?
Kế thừa chỉ đúng khi quan hệ is-a thật và lớp cha được thiết kế ổn định cho việc kế thừa. Nếu mục đích chỉ là tái dùng code, hoặc quan hệ thực ra là has-a, hãy dùng composition: giữ object của class khác làm field và ủy quyền (delegation) các method cần thiết. Composition lỏng hơn, che giấu nội bộ tốt hơn, ít bị ảnh hưởng khi class kia thay đổi. Ví dụ kinh điển: đừng cho Stack extends ArrayList, hãy cho Stack chứa một Deque.
Câu 17. LSP (Liskov Substitution Principle) là gì? Cho ví dụ vi phạm.
Mọi nơi dùng lớp cha phải thay được bằng object lớp con mà chương trình vẫn đúng. Ví dụ vi phạm: Bird có fly(), Penguin extends Bird nhưng fly() ném UnsupportedOperationException — code viết cho Bird sẽ vỡ khi nhận Penguin. Cách sửa: tách interface Flyable cho loài bay được, đừng nhét hành vi không phổ quát vào lớp cha.
Câu 18. Vì sao Stack extends ArrayList là thiết kế sai?
Vì stack là LIFO, còn ArrayList cho phép chèn/xóa/sửa ở bất kỳ vị trí nào. Kế thừa khiến stack thừa hưởng add(index, e), remove(index), set(...) — người dùng có thể phá invariant LIFO. Ngoài ra stack phụ thuộc vào mọi thay đổi tương lai của ArrayList. Trong JDK, java.util.Stack extends Vector là ví dụ lịch sử của lỗi này; cách đúng là composition với ArrayDeque.
Câu 19. Override equals ở lớp con mà thêm field mới có vấn đề gì?
Gây bất đối xứng: với Animal so theo name và Dog so thêm breed, có thể a.equals(d) == true nhưng d.equals(a) == false — vi phạm contract đối xứng; hashCode cũng có thể khác nhau dù equals nói bằng nhau. Cách tránh: không thêm field mới vào equals của lớp con (chấp nhận so theo cha), hoặc dùng composition thay vì kế thừa, hoặc dùng getClass() thay instanceof (giữ được đối xứng, nhưng object lớp con sẽ không bao giờ bằng object lớp cha — mỗi cách đều có đánh đổi). Chi tiết ở 2.6.
Câu 20. sealed class là gì? Dùng khi nào?
sealed (Java 17+) giới hạn tập class/interface được phép kế thừa qua danh sách permits; các lớp con phải final, sealed tiếp, hoặc non-sealed. Dùng cho domain model đóng (ví dụ cây lệnh thanh toán, trạng thái đơn hàng) để compiler kiểm tra đủ nhánh khi dùng switch pattern matching. Nó là điểm giữa "mở hoàn toàn" và final.

Bài 13. equals bất đối xứng khi lớp con thêm state 
import java.util.Objects;

class Animal {
    protected final String name;

    Animal(String name) {
        this.name = name;
    }

    @Override
    public boolean equals(Object o) {
        if (o instanceof Animal other) {
            return name.equals(other.name);
        }
        return false;
    }

    @Override
    public int hashCode() {
        return name.hashCode();
    }
}

public class Dog extends Animal {
    private final String breed;

    Dog(String name, String breed) {
        super(name);
        this.breed = breed;
    }

    @Override
    public boolean equals(Object o) {
        if (o instanceof Dog other) {
            return super.equals(o) && breed.equals(other.breed);
        }
        return false;
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, breed);
    }

    public static void main() {
        Animal a = new Animal("Milu");
        Dog d = new Dog("Milu", "Poodle");
        IO.println(a.equals(d));
        IO.println(d.equals(a));
        IO.println(a.hashCode() == d.hashCode());
    }
}
In ra true, false, false. Animal.equals chấp nhận mọi Animal (kể cả Dog) nên a.equals(d) là true; Dog.equals chỉ chấp nhận Dog nên d.equals(a) là false — vi phạm đối xứng. Tệ hơn, hashCode của hai object "bằng nhau" (theo một chiều) lại khác nhau. Giải pháp thường dùng: không thêm field mới vào equals của lớp con, hoặc dùng composition.

Checklist tự đánh giá trước phỏng vấn

  • Viết được class Con extends Cha kèm constructor gọi super(args) mà không cần tra cứu.
  • Kể đúng 6 bước thứ tự khởi tạo cha/con và phân biệt static với instance.
  • Giải thích được vì sao constructor không được thừa hưởng.
  • Nêu đủ 4 quy tắc override: signature, covariant return, visibility, checked exception.
  • Phân biệt override / overload / hiding và cho ví dụ mỗi loại.
  • Giải thích vì sao static method không dispatch theo object thật.
  • Trả lời được private method trùng tên ở con có phải override không (không).
  • Giải thích bẫy gọi method overridable trong constructor kèm ví dụ field = 0.
  • Phân biệt upcast và downcast, biết khi nào ClassCastException.
  • Nêu được lý do Stack extends ArrayList sai và cách sửa bằng composition.
  • Phát biểu LSP và một ví dụ vi phạm (Bird/Penguin).
  • Giải thích vì sao thêm state vào equals ở lớp con gây bất đối xứng.
  • Biết JEP 513 thay đổi quy tắc constructor của JDK 25 thế nào.
