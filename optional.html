Optional — container có thể không có giá trị

Optional<T> là một cái hộp: hoặc chứa đúng một giá trị khác null, hoặc rỗng. Nó giúp Java nói rõ ý định "có thể không có kết quả" ngay trong kiểu trả về của method, thay vì trả null rồi hy vọng người gọi nhớ kiểm tra. Trang này đi từ vấn đề null, các API cốt lõi (of, map, flatMap, orElse…), tới best practices và góc nhìn Node.js.

2. Vấn đề null & Optional là gì

Năm 1965, Tony Hoare đưa null vào ngôn ngữ ALGOL W và sau này gọi đó là "sai lầm tỷ đô" (billion-dollar mistake): hệ thống ngôn ngữ không ép ai kiểm tra null, nên hàng triệu chương trình sập vì truy cập vào thứ không tồn tại. Java thừa hưởng nguyên xi vấn đề đó.

Điều tệ nhất của null trong Java không phải là nó tồn tại, mà là trình biên dịch không hề cảnh báo. Mọi reference type đều nhận null; đọc tài liệu method cũng không nói rõ nó có thể trả null hay không:

record User(String name) {}

public class HelpfulNpe2 {
    public static void main() {
        User u = new User(null);
        IO.println(u.name().length());
    }
}
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.length()" because the return value of "User.name()" is null
	at HelpfulNpe2.main(HelpfulNpe2.java:6)

Dòng message dài kia là JEP 358 — Helpful NullPointerExceptions, bật mặc định từ JDK 15: thay vì chỉ có NullPointerException trần, JVM mô tả chính xác cái gì null và method nào trả về null. Muốn hiểu thêm về NPE và các RuntimeException khác, xem 3.1 Exceptions.

null len lỏi vào code qua rất nhiều cửa:

  • API/DB trả "không tìm thấy" bằng null thay vì báo lỗi rõ ràng.
  • Map.get(key) trả null khi key không tồn tại.
  • Field chưa được gán; tham số truyền vào là null.
  • Autoboxing: Integer i = null; int x = i; nổ ngay chỗ unbox (xem Biến trong Java — mục 12).

Văn hóa Java hiện đại thay đổi cách tiếp cận: đừng trả null khi "không có kết quả" — hãy trả Optional. Javadoc của Optional định nghĩa: "A container object which may or may not contain a non-null value" — một hộp hoặc chứa một giá trị khác null, hoặc rỗng.

Optional không phải "nullable type" của Java. Nó không thay thế mọi null check trong ngôn ngữ, không phải annotation @Nullable, và không làm compiler ép bạn kiểm tra. Nó chỉ là một quy ước API: method trả Optional nghĩa là "tôi có thể không có kết quả, hãy xử lý bằng API của tôi".

3. Tạo Optional: of, ofNullable, empty

Có đúng ba cách tạo, và chọn sai cách là nguồn bug phổ biến:

Optional<T> of(T value)  ·  Optional<T> ofNullable(T value)  ·  Optional<T> empty()
APIDùng khiHành vi với null
Optional.of(v)Chắc chắn 100% v != nullNém NullPointerException ngay lập tức (fail fast)
Optional.ofNullable(v)v có thể null (Map.get, field, API)Trả Optional.empty()
Optional.empty()Muốn thể hiện "chắc chắn không có giá trị"Chính là giá trị rỗng

Optional.of(null) ném NPE tại thời điểm chạy, ngay dòng đó — đây là hành vi có chủ đích (fail fast). Chạy thật file dưới đây sẽ thấy stack trace chính xác:

import java.util.Optional;

public class OfNull {
    public static void main() {
        Optional<String> ten = Optional.of(null);
        IO.println(ten);
    }
}
Exception in thread "main" java.lang.NullPointerException
	at java.base/java.util.Objects.requireNonNull(Objects.java:220)
	at java.base/java.util.Optional.of(Optional.java:113)
	at OfNull.main(OfNull.java:5)

Stack trace chỉ rõ Optional.of gọi Objects.requireNonNull. Còn với nguồn có thể null, đúng vũ khí là ofNullable:

import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

public class OptionalCreate {
    public static void main() {
        Optional<String> co = Optional.of("Java");
        IO.println(co);   // Optional[Java]

        Optional<String> rong = Optional.empty();
        IO.println(rong);   // Optional.empty

        String giaTri = null;
        Optional<String> coThe = Optional.ofNullable(giaTri);
        IO.println(coThe);   // Optional.empty

        Map<String, String> config = new HashMap<>();
        config.put("lang", "Java");
        Optional<String> lang = Optional.ofNullable(config.get("missing"));
        IO.println(lang);   // Optional.empty

        Optional<Optional<String>> longNhau = Optional.of(Optional.empty());
        IO.println(longNhau);   // Optional[Optional.empty]  <- long Optional, tranh dung
    }
}

Bốn quy tắc vàng khi tạo:

  1. Biến kiểu Optional không bao giờ được là null. "Optional rỗng" là Optional.empty(), không phải null. Nếu biến Optional của bạn null thì chính bạn đã tạo ra bug khó chịu gấp đôi: người gọi vừa phải kiểm tra rỗng, vừa phải phòng null.
  2. Không so sánh Optional với null. opt == null luôn false với Optional hợp lệ, còn opt.equals(null) cũng false. Cả hai cách đều vô nghĩa — hãy dùng isEmpty()/isPresent().
  3. Không lồng Optional trong Optional. Optional<Optional<T>> hợp lệ về mặt kiểu nhưng gần như luôn là dấu hiệu dùng sai map (đúng ra là flatMap — mục 6).
  4. Nguồn có thể null thì dùng ofNullable — đặc biệt là Optional.ofNullable(map.get(k)), thay vì Optional.of(map.get(k)) dễ nổ khi miss key.

Vài thuộc tính cần biết để không "đoán mò" (chạy thật và in ra):

import java.io.Serializable;
import java.util.Optional;

public class OptionalMicro {
    public static void main() {
        Optional<String> e = Optional.empty();
        IO.println("e == null          -> " + (e == null));          // false
        IO.println("e.equals(null)     -> " + e.equals(null));         // false
        IO.println("Serializable -> " + Serializable.class.isAssignableFrom(Optional.class));   // false
        IO.println("empty() cung object -> " + (Optional.empty() == Optional.empty()));   // true
        IO.println("of(\"a\") cung object -> " + (Optional.of("a") == Optional.of("a")));   // false
        IO.println("equals theo gia tri -> " + Optional.of("a").equals(Optional.of("a")));   // true
        IO.println("ofNullable(null)   -> " + Optional.ofNullable(null));      // Optional.empty
        IO.println("hashCode of empty  -> " + Optional.empty().hashCode());   // 0
    }
}
Optional là value-based class giống Integer/LocalDate — các lớp này được JDK chú thích @jdk.internal.ValueBased; lưu ý String không phải value-based class dù equals của nó cũng so theo giá trị (JDK không đảm bảo tráo đổi instance cho String; xem 2.6 equals / hashCode / toString). Với Optional, equals so theo giá trị bên trong, không so địa chỉ, nên Optional.of("a").equals(Optional.of("a")) là true. Vì vậy đừng bao giờ dùng == để so hai Optional, và đừng synchronized trên Optional.

4. Kiểm tra & truy xuất giá trị

Optional có hai trạng thái: present (có giá trị) hoặc empty. Nhóm API kiểm tra/đọc giá trị:

import java.util.Optional;

public class OptionalAccess {
    public static void main() {
        Optional<String> o = Optional.of("Java");

        IO.println(o.isPresent());   // true
        IO.println(o.isEmpty());     // false
        IO.println(o.get());         // Java

        o.ifPresent(v -> IO.println("Co gia tri: " + v));

        Optional<String> e = Optional.empty();
        e.ifPresentOrElse(
                v -> IO.println("Co: " + v),
                () -> IO.println("Khong co gia tri"));

        Optional<String> duPhong = e.or(() -> Optional.of("mac dinh"));
        IO.println(duPhong.get());   // mac dinh

        IO.println(e.or(() -> Optional.empty()));   // Optional.empty

        IO.println(e.isPresent());   // false
        IO.println(e.isEmpty());     // true
    }
}

5. orElse vs orElseGet vs orElseThrow Hay hỏi phỏng vấn

Ba method cùng mục đích "lấy giá trị ra khỏi Optional", khác nhau ở thời điểm tính giá trị mặc định và ở hành vi khi rỗng:

MethodNhận gìKhi Optional rỗngKhi Optional có giá trị
orElse(T other)Giá trị sẵnTrả otherTrả giá trị trong hộp — nhưng other đã được tính từ trước
orElseGet(Supplier<T>)Hàm sinh giá trịGọi supplier rồi trả kết quảTrả giá trị trong hộp — supplier không bao giờ được gọi
orElseThrow() (Java 10)—Ném NoSuchElementException("No value present")Trả giá trị
orElseThrow(Supplier<X>)Hàm sinh exceptionNém exception do supplier tạoTrả giá trị

Khác biệt eager/lazy không phải chuyện lý thuyết. Ví dụ dưới đây in ra dấu vết khi hàm mặc định được gọi; để ý orElse gọi hàm mặc định kể cả khi Optional đã có giá trị:

import java.util.Optional;

public class OptionalElse {
    static String macDinh() {
        IO.println("  -> macDinh() duoc goi");
        return "mac dinh";
    }

    static String tuDatabase() {
        IO.println("  -> tuDatabase() duoc goi");
        return "tu DB";
    }

    public static void main() {
        Optional<String> co = Optional.of("Java");
        Optional<String> rong = Optional.empty();

        IO.println("co.orElse(macDinh()):");
        IO.println("  ket qua = " + co.orElse(macDinh()));

        IO.println("co.orElseGet(OptionalElse::macDinh):");
        IO.println("  ket qua = " + co.orElseGet(OptionalElse::macDinh));

        IO.println("rong.orElseGet(OptionalElse::tuDatabase):");
        IO.println("  ket qua = " + rong.orElseGet(OptionalElse::tuDatabase));

        IO.println("rong.orElse(macDinh()):");
        IO.println("  ket qua = " + rong.orElse(macDinh()));
    }
}

Vì sao? co.orElse(macDinh()) tương đương co.orElse(giá trị-đã-tính): Java phải gọi macDinh() trước để có tham số truyền vào. Còn orElseGet nhận hàm Supplier, chỉ gọi khi cần. Hệ quả thực tế:

  • Mặc định rẻ và vô hại (hằng số, 0, chuỗi cố định) → orElse cho gọn.
  • Mặc định đắt hoặc có side effect (query DB, gọi API, đọc file, ghi log) → bắt buộc orElseGet, nếu không bạn trả tiền cho công việc bị vứt bỏ.
  • orElse(null) hợp lệ về cú pháp nhưng trả bạn về đúng vấn đề null ban đầu — hạn chế dùng.

Nhóm ném lỗi: orElseThrow() (không tham số) luôn dùng NoSuchElementException với message "No value present" — cùng exception như get(). Bản có Supplier cho phép tự chọn loại lỗi và message nghiệp vụ:

import java.util.NoSuchElementException;
import java.util.Optional;

public class OptionalThrow {
    static Optional<String> timTheoId(String id) {
        if ("U01".equals(id)) {
            return Optional.of("An");
        }
        return Optional.empty();
    }

    public static void main() {
        Optional<String> rong = Optional.empty();

        try {
            rong.orElseThrow();
        } catch (NoSuchElementException e) {
            IO.println("orElseThrow()            -> " + e.getMessage());
        }

        try {
            rong.orElseThrow(() -> new IllegalStateException("Khong tim thay nguoi dung"));
        } catch (IllegalStateException e) {
            IO.println("orElseThrow(supplier)    -> " + e.getMessage());
        }

        try {
            rong.get();
        } catch (NoSuchElementException e) {
            IO.println("get() tren empty         -> " + e.getMessage());
        }

        IO.println("timTheoId(U01)           -> " + timTheoId("U01").orElseThrow());
    }
}
orElseThrow()            -> No value present
orElseThrow(supplier)    -> Khong tim thay nguoi dung
get() tren empty         -> No value present
timTheoId(U01)           -> An
Nếu "không có giá trị" là lỗi thật theo hợp đồng method, orElseThrow(() -> new ...()) là cách nói rõ nhất. Nếu là luồng bình thường, hãy trả mặc định (orElse/orElseGet) hoặc để người gọi quyết định — đừng ném exception cho tình huống "không tìm thấy". Triết lý này học ở 3.1 Exceptions.

6. Biến đổi: map, flatMap, filter, stream

Optional mạnh nhất khi bạn không cần mở hộp: cứ biến đổi bên trong, đến cuối mới quyết định (mặc định / ném lỗi / trả Optional). Nhóm method:

map(Function<T, U>) → Optional<U>  ·  flatMap(Function<T, Optional<U>>) → Optional<U>  ·  filter(Predicate<T>) → Optional<T>  ·  stream() → Stream<T>
  • map — biến đổi nếu có giá trị. Optional rỗng thì trả luôn Optional rỗng (không gọi hàm). Đặc biệt: nếu hàm biến đổi trả về null, kết quả là Optional.empty() — map null-safe. Đây là điểm khác biệt với Stream.map: stream giữ nguyên phần tử null, Optional biến null thành rỗng.
  • flatMap — dùng khi hàm biến đổi trả về Optional. map sẽ bọc thêm một lớp (Optional<Optional<U>>), flatMap làm phẳng.
  • filter — giữ giá trị nếu thỏa predicate, ngược lại thành rỗng. Không bao giờ gọi predicate trên Optional rỗng.
  • stream — Java 9, biến Optional thành Stream có 0 hoặc 1 phần tử, chuyên dùng để nhúng vào pipeline (mục 9).
import java.util.List;
import java.util.Optional;

public class OptionalTransform {
    record User(String ten, String email) {}

    static Optional<String> emailCua(User u) {
        return Optional.ofNullable(u.email());
    }

    public static void main() {
        Optional<String> ten = Optional.of("  java  ");

        IO.println(ten.map(String::trim));                       // Optional[java]
        IO.println(ten.map(String::trim).map(String::toUpperCase)); // Optional[JAVA]
        IO.println(ten.map(String::trim).orElse("khong co"));     // java

        Optional<String> trong = Optional.empty();
        IO.println(trong.map(String::length));                   // Optional.empty

        IO.println(Optional.of("abc").map(s -> (String) null));  // Optional.empty

        IO.println(Optional.of(15).filter(n -> n > 10));         // Optional[15]
        IO.println(Optional.of(5).filter(n -> n > 10));          // Optional.empty

        Optional<User> u = Optional.of(new User("An", null));
        Optional<String> email = u.flatMap(OptionalTransform::emailCua);
        IO.println(email);                                        // Optional.empty

        Optional<User> u2 = Optional.of(new User("Binh", "binh@example.com"));
        IO.println(u2.flatMap(OptionalTransform::emailCua));      // Optional[binh@example.com]

        List<Optional<Integer>> ds = List.of(Optional.of(1), Optional.empty(), Optional.of(3));
        long dem = ds.stream().flatMap(Optional::stream).count();
        IO.println("dem = " + dem);                               // dem = 2

        Optional<Optional<String>> longNhau = u2.map(x -> emailCua(x));
        IO.println(longNhau);                                     // Optional[Optional[binh@example.com]]
    }
}

Bẫy map vs flatMap: dấu hiệu nhận biết là kiểu hàm. Hàm trả String, Integer, object thường → map. Hàm trả Optional<X> (ví dụ findById, emailCua) → flatMap. Dùng nhầm map bạn có Optional[Optional[...]] như dòng cuối ví dụ.

Optional cho kiểu nguyên thủy — tránh boxing

Với int/long/double, JDK cung cấp OptionalInt, OptionalLong, OptionalDouble. Lợi ích: không autobox mỗi giá trị (xem Biến trong Java — mục 12), và có API riêng getAsInt(), orElse(0):

import java.util.Optional;
import java.util.OptionalDouble;
import java.util.OptionalInt;
import java.util.OptionalLong;
import java.util.stream.IntStream;

public class OptionalPrimitive {
    public static void main() {
        OptionalInt max = IntStream.of(3, 7, 2).max();
        IO.println(max);                  // OptionalInt[7]
        IO.println(max.getAsInt());       // 7
        IO.println(max.orElse(-1));       // 7

        OptionalInt rong = OptionalInt.empty();
        IO.println(rong.isPresent());     // false
        IO.println(rong.orElse(-1));      // -1

        OptionalLong tong = OptionalLong.of(1_000_000_000L);
        IO.println(tong.getAsLong());     // 1000000000

        OptionalDouble tb = IntStream.of(1, 2, 3).average();
        IO.println(tb.getAsDouble());     // 2.0

        OptionalInt tuChuoi = Optional.of("42").stream()
                .mapToInt(Integer::parseInt)
                .findFirst();
        IO.println(tuChuoi.getAsInt());   // 42

        IO.println(OptionalInt.of(7).stream().sum());       // 7
        IO.println(OptionalLong.of(5).stream().sum());      // 5
        IO.println(OptionalDouble.of(2.5).stream().sum());  // 2.5
        IO.println(rong.stream().count());                  // 0

        Optional<Integer> boxing = Optional.of(1_000_000);
        IO.println(boxing);               // Optional[1000000]
    }

Bài toán kinh điển: lấy thành phố của user qua chuỗi User → Address → City, mỗi mắt xích đều có thể null. Đây là "null-hell" — kim tự tháp if:

public class NullHell {

    record Address(String duong, City city) {}
    record User(String ten, Address address) {}

8. Best practices & anti-patterns Production

Câu thần chú từ Javadoc: Optional chủ yếu dành cho kiểu trả về của method khi cần biểu diễn rõ "không có kết quả" (xem thêm Effective Java, item 55 — "Return optionals judiciously"). Mọi lạm dụng đều bắt nguồn từ việc quên câu này.

Anti-pattern 1 — isPresent() + get()

Đây là "null check đội lốt Optional": code chạy đúng nhưng cồng kềnh và không tận dụng gì cả, đặc biệt trong Stream:

// Khong nen
if (opt.isPresent()) {
    return opt.get().toUpperCase();
}
return "khong co";

// Nen
return opt.map(String::toUpperCase).orElse("khong co");

// Trong Stream - khong nen
list.stream().filter(Optional::isPresent).map(Optional::get).toList();

// Trong Stream - nen
list.stream().flatMap(Optional::stream).toList();

Anti-pattern 2 — Optional làm field / parameter

// Khong nen: Optional lam field trong domain model / DTO / entity
public class KhachHang {
    private Optional<String> email;   // khoi tao phuc tap, serialize loi, JPA khong ho tro
}

// Nen: field kieu thuong + validate o constructor, getter tra Optional NEU can
public class KhachHang {
    private final String email;       // co the null neu nghiep vu cho phep

    public Optional<String> email() {
        return Optional.ofNullable(email);
    }
}
  • Parameter: nhận Optional làm tham số ép caller bọc giá trị — phiền và không giải quyết vấn đề gì. Hãy nhận kiểu thường, hoặc tách overload (tim(ten) / tim(ten, email)) theo tinh thần Methods — mục 5.
  • Collection element: List<Optional<T>> thường là dấu hiệu bạn nên lọc bỏ rỗng hoặc dùng Map; mỗi Optional là một allocation.
  • Đừng lạm dụng: local variable, private method trong nội bộ class, hay trạng thái "đã set/đã gán" không cần Optional. Optional sinh ra cho ranh giới API công khai, nơi hai phía không biết nhau.

Allocation & hiệu năng — Optional có "đắt" không?

Optional là một object nhỏ: Optional.empty() là singleton dùng chung (đã kiểm ở mục 3), còn Optional.of(v) cấp phát một object gồm header + một reference tới giá trị bên trong. Với Optional<Integer> bạn còn tốn thêm một lần boxing. Trong hot loop hoặc collection, mỗi phần tử thêm một object là chi phí thật, không còn là "cho vui".

  • Escape analysis: JIT (C2) có thể loại bỏ allocation của Optional khi nó không "thoát" khỏi method/scope (scalar replacement). Nhờ vậy chain ngắn trong method thường không tốn gì sau khi JIT vào việc — nhưng đây là tối ưu của JVM, không phải bảo đảm, phụ thuộc phiên bản JVM và hình dạng code. Đừng dựa vào nó để viết hot loop.
  • Hot loop / dữ liệu lớn: tránh tạo Optional cho từng phần tử khi tính toán số học — dùng primitive/mảng, hoặc chỉ trả OptionalInt/Long/Double ở kết quả cuối. List<Optional<T>> vừa tốn bộ nhớ vừa rối (xem anti-pattern 2).
  • Record component cũng là field: record KhachHang(String ten, Optional<String> email) {} lưu thẳng Optional trong field y như khai báo field thường — cùng khuyến nghị "không nên". Muốn API trả Optional, để component là kiểu thường rồi thêm accessor:
// Khong nen: record component Optional -> luu Optional trong field
record KhachHang(String ten, Optional<String> email) {}

// Nen: component kieu thuong + accessor tra Optional khi can
record KhachHang(String ten, String email) {
    Optional<String> emailOptional() {
        return Optional.ofNullable(email);
    }
}

Anti-pattern 3 — serialize & framework

  • Optional không implement Serializable (đã kiểm chứng ở mục 3). Đừng để nó trong session, cache phân tán, RMI, DTO serialize nhị phân.
  • JPA/Hibernate: entity không nên có field Optional — JPA không ánh xạ được và bạn gặp lỗi mapping. Dùng getter trả Optional nếu muốn (như ví dụ trên).
  • Jackson (REST API): mặc định Jackson không hiểu Optional là container; cần đăng ký com.fasterxml.jackson.datatype.jdk8.Jdk8Module để nó serialize đúng giá trị bên trong (và bỏ qua rỗng tùy cấu hình). Nếu không, response có thể chứa cấu trúc lạ thay vì giá trị mong đợi — một trong những bug tích hợp phổ biến khi dùng Optional trong DTO. Cách an toàn hơn cho API: DTO dùng kiểu thường + @JsonInclude(NON_NULL).
  • Khi ghi log, đừng log Optional[...] trần — opt.orElse(null) hoặc opt.map(Object::toString).orElse("<empty>") dễ đọc hơn.
"Optional có thay thế null hoàn toàn không?" — Không. null vẫn tồn tại trong Java: field chưa gán, mảng, tham số, API cũ trả null, Map.get. Optional chỉ là quy ước ở tầng kiểu trả về để giảm NPE. Nó cũng không phải thuốc chữa mọi bệnh: lạm dụng Optional làm code rối, tốn allocation và che giấu lỗi thật — đôi khi null nội bộ hoặc một exception rõ nghĩa lại đúng hơn.

9. Optional trong Stream Junior+ Production

Stream và Optional là cặp bài trùng: nhiều terminal operation của Stream trả về Optional vì dữ liệu có thể rỗng — findFirst(), findAny(), max(), min(), reduce(BinaryOperator). Chi tiết Stream xem 3.8.

Bài toán thực tế: từ danh sách đơn hàng, mỗi đơn có maKhach; tra khách trong "DB" (Map) — khách có thể không tồn tại (dữ liệu mồ côi). Đây là chỗ map(::find) sinh ra Stream<Optional<Khach>> rồi flatMap(Optional::stream) làm phẳng, bỏ các empty:

import java.util.Comparator;
import java.util.List;
import java.util.Map;
import java.util.Optional;

public class OptionalStream {
    record DonHang(String ma, String trangThai, long tong, String maKhach) {}
    record Khach(String ma, String ten) {}

    static Map<String, Khach> db = Map.of(
            "K01", new Khach("K01", "An"),
            "K02", new Khach("K02", "Binh"));

    static Optional<Khach> timKhach(String ma) {
        return Optional.ofNullable(db.get(ma));
    }

    public static void main() {
        List<DonHang> don = List.of(
                new DonHang("DH01", "DA_GIAO", 250_000, "K01"),
                new DonHang("DH02", "DANG_GIAO", 120_000, "K02"),
                new DonHang("DH03", "DA_GIAO", 90_000, "K99"),
                new DonHang("DH04", "HUY", 0, "K01"));

        long tongDaGiao = don.stream()
                .filter(d -> "DA_GIAO".equals(d.trangThai()))
                .mapToLong(DonHang::tong)
                .sum();
        IO.println("tong da giao   = " + tongDaGiao);   // 340000

        Optional<DonHang> lonNhat = don.stream()
                .max(Comparator.comparingLong(DonHang::tong));
        IO.println("don lon nhat   = " + lonNhat.map(DonHang::ma).orElse("khong co"));   // DH01

        List<String> khachDaGiao = don.stream()
                .filter(d -> "DA_GIAO".equals(d.trangThai()))
                .map(d -> timKhach(d.maKhach()))
                .flatMap(Optional::stream)
                .map(Khach::ten)
                .toList();
        IO.println("khach da giao  = " + khachDaGiao);   // [An]

        long khongTimThay = don.stream()
                .map(d -> timKhach(d.maKhach()))
                .filter(Optional::isEmpty)
                .count();
        IO.println("khong tim thay = " + khongTimThay);   // 1

        List<String> maCoKhach = don.stream()
                .map(DonHang::maKhach)
                .distinct()
                .filter(ma -> timKhach(ma).isPresent())
                .toList();
        IO.println("ma co khach    = " + maCoKhach);     // [K01, K02]
    }
}

  • flatMap(Optional::stream) là idiom chuẩn để "vứt bỏ empty, giữ giá trị" — thay cho filter(isPresent).map(get) vừa dài vừa dễ sai.
  • Optional::stream chỉ là method reference của opt -> opt.stream(); mỗi Optional cho ra 0 hoặc 1 phần tử.
  • Stream lazy: không có gì chạy cho tới terminal operation (toList(), count(), sum()). Vì thế đừng đặt side effect trong map/filter (chi tiết ở 3.8).
  • Ngược lại, cần đếm "không tìm thấy" thì filter(Optional::isEmpty) lại đúng ý hơn cả.
Quy tắc nhớ nhanh: method tìm kiếm trả Optional → dùng map(::find) khi muốn giữ Optional để xử lý tiếp, dùng map(::find).flatMap(Optional::stream) khi muốn lọc sạch dữ liệu để đi tiếp pipeline.

  • ?. chỉ ngắn mạch với null/undefined, không phải mọi giá trị "rỗng": 0?.toString() chạy bình thường, nhưng a?.b.c vẫn nổ nếu a khác null mà b undefined — phải viết a?.b?.c. Java không có ?.; mỗi bước null phải là map hoặc check riêng.
  • ?? vs ||: ?? chỉ thay null/undefined, nên an toàn với 0, "", false, NaN; || thay mọi giá trị falsy — bug kinh điển khi số lượng/chuỗi rỗng là hợp lệ.
  • TypeScript strictNullChecks: khi bật, string | null buộc bạn kiểm tra trước khi dùng — gần với tinh thần Optional nhất. Toán tử non-null assertion x! là "lời hứa" với compiler rằng x không null; dùng bừa sẽ đổi compile error thành runtime crash, đúng kiểu get() bừa trong Java.
// TypeScript - minh hoa strictNullChecks (khong chay trong vi du Java)
interface Khach { ten: string; email: string | null; }
function guiMail(k: Khach) {
    // return k.email.toUpperCase();        // LOI compile: 'k.email' is possibly 'null'
    return (k.email ?? "khong-co@example.com").toUpperCase();   // OK
}
const k: Khach = { ten: "An", email: null };
console.log(guiMail(k));   // KHONG-CO@EXAMPLE.COM

11. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Optional là gì? Nó giải quyết vấn đề gì?
Optional<T> là container có thể chứa hoặc không chứa một giá trị non-null. Nó giải quyết vấn đề "trả null mơ hồ": thay vì trả null và hy vọng caller nhớ kiểm tra, method trả Optional nói rõ trong chữ ký rằng "có thể không có kết quả", buộc caller xử lý qua API của Optional (orElse, map, ifPresent…). Nó không loại bỏ null khỏi ngôn ngữ, chỉ giảm NPE ở ranh giới API.
Câu 2. Optional có thay thế null hoàn toàn không?
Không. (1) null vẫn tồn tại cho field, tham số, mảng, Map.get, API cũ; (2) Javadoc khuyến nghị Optional chỉ dùng làm kiểu trả về, không làm field/parameter/collection element; (3) lạm dụng Optional tạo thêm allocation và code rối hơn cả null check; (4) nhiều tình huống null hoặc exception rõ nghĩa vẫn hợp lý hơn (private method nội bộ, lỗi thật). Optional là quy ước thiết kế API, không phải hệ thống kiểu nullable.
Câu 3. Optional.of, ofNullable và empty khác nhau thế nào?
of(v) yêu cầu chắc chắn non-null, truyền null sẽ ném NullPointerException ngay (fail fast). ofNullable(v) nhận cả null và biến thành empty() — dùng cho nguồn có thể null như map.get(k). empty() trả Optional rỗng (singleton). Với Map, idiom đúng là Optional.ofNullable(map.get(k)).
Câu 4. Vì sao không nên gọi get()?
Vì get() trên Optional rỗng ném NoSuchElementException: No value present — chẳng khác gì dereference null, chỉ đổi tên lỗi, và không mang ngữ nghĩa nghiệp vụ. Hãy dùng orElse/orElseGet (mặc định), orElseThrow(() -> new ...) (lỗi có ngữ nghĩa), ifPresent/ifPresentOrElse (side effect) hoặc map (biến đổi).
Câu 5. orElse và orElseGet khác nhau ra sao? Cho ví dụ bị bug.
orElse(T) nhận giá trị nên tham số được tính trước khi gọi method (eager) — kể cả khi Optional có giá trị. orElseGet(Supplier) nhận hàm, chỉ gọi khi Optional rỗng (lazy). Bug điển hình: opt.orElse(loadFromDatabase()) vẫn query DB dù giá trị đã có; sửa thành opt.orElseGet(this::loadFromDatabase). Mặc định hằng số rẻ thì orElse tiện hơn.
Câu 6. get() và orElseThrow() không tham số khác gì nhau?
Cả hai ném cùng NoSuchElementException("No value present") khi rỗng. Khác ở tên gọi và ngữ nghĩa: orElseThrow nói rõ hành vi "ném nếu rỗng" và có bản nhận Supplier để chọn exception riêng; get() là API cũ, tên mơ hồ, dễ bị gọi bừa. Từ Java 10, orElseThrow() thay thế get() trong code mới.
Câu 7. ifPresent, ifPresentOrElse và or dùng khi nào?
ifPresent(Consumer): chỉ chạy hành động khi có giá trị (không có nhánh else). ifPresentOrElse(Consumer, Runnable) (Java 9): đủ hai nhánh, dùng cho logging/thông báo. or(Supplier<Optional<T>>) (Java 9): trả về Optional thay thế nếu rỗng — giữ được chain map/filter phía sau, khác hẳn orElse trả giá trị trần.
Câu 8. map và flatMap trên Optional khác nhau thế nào?
map(Function<T,U>) bọc kết quả thành Optional<U>; nếu hàm trả null thì kết quả là empty (null-safe). flatMap(Function<T, Optional<U>>) yêu cầu hàm đã trả Optional<U> và không bọc thêm — nhờ đó tránh Optional<Optional<U>>. Quy tắc: hàm trả object thường → map; hàm trả Optional → flatMap.
Câu 9. Optional.stream() là gì và dùng làm gì?
Method thêm từ Java 9, biến Optional thành Stream 0 hoặc 1 phần tử. Ứng dụng chính là stream().map(::find).flatMap(Optional::stream) để lọc bỏ kết quả rỗng trong pipeline, thay cho filter(Optional::isPresent).map(Optional::get). Ngoài ra còn dùng khi cần trộn Optional đơn lẻ vào stream khác.
Câu 10. Vì sao có OptionalInt/OptionalLong/OptionalDouble?
Để tránh autoboxing khi làm việc với primitive: Optional<Integer> bọc một object Integer, còn OptionalInt lưu trực tiếp int, có getAsInt(), orElse(int). Chúng sinh ra từ các terminal operation của IntStream/LongStream/DoubleStream: max(), min(), average(), findFirst(). Đổi lại chúng thiếu map/flatMap/filter (các method này sẽ boxing trở lại), nhưng vẫn có stream() từ Java 9 trả về IntStream/LongStream/DoubleStream — ví dụ OptionalInt.of(7).stream().sum() cho 7.

Nâng cao (Junior+)

Câu 11. Vì sao không nên dùng Optional cho field, parameter và phần tử collection?
Javadoc nói Optional chủ yếu dành cho kiểu trả về. Field Optional: constructor phải khởi tạo hộp, getter lồng getter, so sánh/equals phức tạp, JPA không map được, Jackson cần module, không Serializable. Parameter Optional: ép caller bọc giá trị, dễ nhầm giữa "không truyền" và "truyền rỗng"; hãy dùng overload. Collection element List<Optional<T>>: mỗi phần tử thêm một allocation; gần như luôn có cách biểu diễn tốt hơn (lọc bỏ rỗng, Map, sentinel).
Câu 12. Vì sao Optional<String> x = Optional.of(Optional.empty()); không compile, nhưng Optional<Optional<String>> x = Optional.of(Optional.empty()); thì được?
Vì Optional.of generic và Java dùng target typing để suy luận T. Ở vế đầu, compiler cố ép T = String nhưng tham số lại là Optional<T2> — mâu thuẫn nên báo lỗi "inference variable T has incompatible bounds". Ở vế sau, T được suy ra là Optional<String> nên hợp lệ. Điều này cũng cho thấy Optional lồng nhau là hợp lệ về kiểu nhưng hầu như luôn là dấu hiệu dùng sai map thay vì flatMap.
Câu 13. Optional có serialize được không? Vấn đề gì khi dùng trong DTO/API?
Optional không implement Serializable, nên không dùng trong session/RMI/cache nhị phân. Với REST API + Jackson, phải đăng ký Jdk8Module thì Jackson mới hiểu Optional là container; nếu không, JSON trả ra không như mong đợi (cấu trúc lạ hoặc lỗi serializer tùy phiên bản). Nhiều team chọn DTO dùng kiểu thường + @JsonInclude(NON_NULL) để API sạch và không phụ thuộc module.
Câu 14. Có nên dùng Optional để biểu diễn mọi trường hợp lỗi/không hợp lệ không?
Không. Optional phù hợp cho "không có kết quả" như một trạng thái bình thường (tìm không thấy, chưa cấu hình). Lỗi thật (sai định dạng, vi phạm ràng buộc, thao tác bất khả thi) nên là exception với message/ngữ cảnh — exception mang stack trace và lý do, Optional thì không. Ngoài ra Optional không nói được vì sao rỗng; nếu cần lý do, dùng record kết quả (ví dụ record KetQua<T>(T value, String lyDo) {}) theo tinh thần 3.1 Exceptions.

Checklist tự đánh giá trước phỏng vấn

  • Giải thích được "null là sai lầm tỷ đô" và Optional giải quyết phần nào của vấn đề.
  • Trả lời trôi chảy câu kinh điển: "Optional có thay thế null hoàn toàn không?" — Không, kèm 3 lý do.
  • Phân biệt of / ofNullable / empty và biết of(null) ném NPE lúc runtime.
  • Nhớ biến Optional không bao giờ null; không so == null; không lồng Optional ngoài ý muốn.
  • Kể được vì sao tránh get() và isPresent()+get(); nêu API thay thế.
  • Phân biệt orElse (eager) vs orElseGet (lazy) kèm ví dụ side effect.
  • Phân biệt map vs flatMap qua kiểu hàm; biết map null-safe.
  • Biến chuỗi truy cập a → b → c thành Optional.ofNullable(a).map(...).map(...).orElse(...).
  • Biết Optional::stream và idiom map(::find).flatMap(Optional::stream).
  • Nêu ít nhất 3 chỗ KHÔNG nên dùng Optional: field/param/collection, entity JPA, DTO serialize.
  • So sánh được với JS: null/undefined, ?., ?? vs ||, strictNullChecks.
