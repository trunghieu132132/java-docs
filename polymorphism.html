Polymorphism — đa hình trong Java

Polymorphism (đa hình) là khả năng cùng một lời gọi method cho ra hành vi khác nhau tuỳ theo object thật sự đứng sau lời gọi đó. Đây là trụ cột thứ ba của OOP bên cạnh encapsulation và inheritance, đồng thời là chủ đề phỏng vấn xuất hiện gần như trong mọi buổi phỏng vấn Java. Trang này tách bạch hai loại đa hình (compile-time và runtime), đi qua overloading, overriding, casting, field hiding, rồi tới pattern matching hiện đại (Java 21+) và ứng dụng trong production.

1. Tổng quan & cách học

Đa hình nghĩa đen là "nhiều hình thái". Bạn đã dùng nó từ ngày đầu học Java mà có thể chưa gọi tên: IO.println(...) có hàng chục phiên bản cho từng kiểu dữ liệu — đó là overloading (đa hình lúc compile). Còn khi bạn tạo new ArrayList<>() rồi gán cho biến kiểu List, lời gọi add(...) lúc chạy sẽ tìm tới implementation của ArrayList — đó là overriding (đa hình lúc runtime).

Hay hỏi phỏng vấn Junior+ Production

Mức độ bắt buộc của chủ đề 2.4 (phỏng vấn: rất cao · production: bắt buộc):

  • Phải làm được — viết overload đúng luật và đoán đúng bản được chọn; override đúng chữ ký kèm @Override; dùng biến kiểu cha gọi method của con; ép kiểu an toàn với instanceof; thay chuỗi if/else theo type bằng method ảo.
  • Phải hiểu — overload chọn theo static type của biến và argument lúc compile; override chọn theo runtime type của object lúc chạy; field và static không đa hình; bẫy null, widening và boxing khi overload; vì sao gọi method ảo trong constructor là nguy hiểm.
  • Nhận biết — pattern matching instanceof (Java 16), pattern matching for switch và record pattern (Java 21), sealed classes; bảng method ảo (vtable) và JIT; nguyên lý Liskov (LSP) ở GĐ2.

Cách học hiệu quả nhất với trang này:

  1. Đoán output của mỗi ví dụ trước khi nhìn comment kết quả — đặc biệt các ví dụ về chọn overload và field hiding.
  2. Làm mục Bài tập đoán output trước, chỉ mở đáp án sau khi đã đoán.
  3. Ôn nhanh bằng Cheat sheet & checklist trước buổi phỏng vấn.
  4. Gặp câu lạ, tra ở mục Interview Q&A.
Ví dụ dùng IO.println(...) — cách viết gọn của JDK 25 (JEP 512), tương đương System.out.println(...) mà bạn sẽ gặp trong đề phỏng vấn và tài liệu cũ. Mọi ví dụ Java trong trang là compact source file, chạy bằng java TenFile.java.

Một lời gọi, nhiều hành vi

Tưởng tượng một ứng dụng vẽ hình có nút "Vẽ". Cùng một lời gọi draw(), hình tròn vẽ đường tròn, hình chữ nhật vẽ bốn cạnh — code gọi không cần biết object đang là hình gì:

class Shape {
    void draw() {
        IO.println("Shape.draw");
    }
}

class Circle extends Shape {
    @Override
    void draw() {
        IO.println("Circle.draw");
    }
}

class Rectangle extends Shape {
    @Override
    void draw() {
        IO.println("Rectangle.draw");
    }
}

void main() {
    Shape a = new Circle();
    Shape b = new Rectangle();
    Shape c = new Shape();
    a.draw();   // Circle.draw
    b.draw();   // Rectangle.draw
    c.draw();   // Shape.draw
}
Circle.draw
Rectangle.draw
Shape.draw

Điểm mấu chốt: biến a có kiểu khai báo là Shape nhưng object thật là Circle. JVM gọi method theo object thật, không theo kiểu khai báo — đó chính là dynamic dispatch (mục 3).

Đừng nhầm: overload không phải là "đa hình OOP" theo nghĩa kinh điển — nó chỉ là tiện ích đặt tên của compiler. Muốn nói đến sức mạnh thật của đa hình (thêm class mới không phải sửa code cũ), người ta nói tới overriding + dynamic dispatch.

Góc Node.js — duck typing vs nominal typing

JavaScript không có khái niệm "kế thừa để đa hình": object nào có method draw() thì dùng được, bất kể nó được tạo ra thế nào. Kiểu này gọi là duck typing (structural typing): "nếu nó đi như vịt và kêu như vịt thì là vịt". Java thì ngược lại — nominal typing: muốn được coi là Shape, bạn phải khai báo extends Shape hoặc implements Shape, không quan trọng bạn có đủ method hay không.

// JavaScript - chi de so sanh, KHONG phai Java
// Duck typing: chi can co method draw, khong can ke thua
const circle = { draw: () => console.log("Circle.draw") };
const rectangle = { draw: () => console.log("Rectangle.draw") };

function ve(hinh) {
    hinh.draw();
}

ve(circle);
ve(rectangle);

// JS khong overload that: ham sau ghi de ham truoc
function chao(ten) {
    return "Xin chao " + ten;
}

function chao(ten, tuoi) {
    return ten + " (" + tuoi + ")";
}

console.log(chao("An"));        // An (undefined)
console.log(chao("An", 20));    // An (20)
Circle.draw
Rectangle.draw
An (undefined)
An (20)

Chạy thật bằng Node v22. Ba điểm cần nhớ:

  • JS gọi được hinh.draw() dù circle không kế thừa gì — Java bắt buộc Circle implements Shape.
  • JS không có overload thật: khai báo hai function chao cùng tên thì hàm sau ghi đè hàm trước, nên chao("An") in ra An (undefined). Java chọn bản theo kiểu/số lượng argument.
  • TypeScript có overload nhưng chỉ ở mức type-check; khi compile xong, thông tin đó biến mất và runtime không dispatch theo kiểu như JVM.

2. Overloading — đa hình lúc compile-time Hay hỏi phỏng vấn

Overload là nhiều method cùng tên trong cùng một class (hoặc giữa cha–con) nhưng khác danh sách tham số. Khác nhau có thể là số lượng tham số, kiểu tham số, hoặc thứ tự kiểu tham số. Tên parameter không tính vào chữ ký, và return type cũng vậy.

[modifiers] returnType ten(kieu1 a) | returnType ten(kieu1 a, kieu2 b) | returnType ten(kieu2 b, kieu1 a) 
void chao() {
    IO.println("Xin chao ban");
}

void chao(String ten) {
    IO.println("Xin chao " + ten);
}

void chao(String ten, int tuoi) {
    IO.println(ten + " (" + tuoi + " tuoi)");
}

void main() {
    chao();            // Xin chao ban
    chao("An");        // Xin chao An
    chao("Binh", 20);  // Binh (20 tuoi)
}
Xin chao ban
Xin chao An
Binh (20 tuoi)

Chỉ khác return type là không đủ để tạo overload — Java phân biệt method bằng tên + kiểu tham số (method descriptor). Đoạn sau lỗi ngay khi compile:

OverloadReturnErr.java:6: error: method moTa() is already defined in class Shape
    String moTa() {
           ^
1 error

Trong bytecode, tên method luôn được gắn kèm kiểu tham số; chạy javap bạn sẽ thấy các dòng như chao(String), chao(String, int) là các method hoàn toàn khác nhau.

Overload resolution — compiler chọn bản nào?

Khi nhiều bản cùng "vừa" với một lời gọi, compiler chọn qua 3 phase, phase trước thắng phase sau:

  1. Phase 1 — strict (không boxing): argument khớp chính xác, hoặc widening primitive (ví dụ int → long) / widening reference (ví dụ String → Object).
  2. Phase 2 — loose: cho phép boxing/unboxing (ví dụ int → Integer, Integer → int).
  3. Phase 3 — varargs: chỉ xét tới nếu hai phase trên không có bản nào phù hợp.

Trong mỗi phase, nếu có nhiều bản phù hợp, compiler chọn bản cụ thể nhất (most specific) — ví dụ argument int thì bản int thắng bản long.

void chon(long x) {
    IO.println("chon(long)");
}

void chon(Integer x) {
    IO.println("chon(Integer)");
}

void main() {
    chon(1);                   // chon(long) - widening (phase 1) thang boxing (phase 2)
    chon(1L);                  // chon(long)
    chon(Integer.valueOf(1));  // chon(Integer) - khop chinh xac (phase 1)
}
chon(long)
chon(long)
chon(Integer)

Chú ý: int → long là widening nên thuộc phase 1 và thắng int → Integer (boxing, phase 2). Đây là bẫy production phổ biến khi một API thêm bản long mà call site cũ đang truyền int — hành vi thay đổi âm thầm.

Bẫy widening với int/long/double và bẫy varargs:

void f(int x) {
    IO.println("f(int)");
}

void f(long x) {
    IO.println("f(long)");
}

void f(double x) {
    IO.println("f(double)");
}

void g(int a, int b) {
    IO.println("g(int, int)");
}

void g(int... xs) {
    IO.println("g(varargs) count=" + xs.length);
}

void main() {
    f(1);      // f(int) - khop chinh xac
    f(1L);     // f(long)
    f(1.5f);   // f(double) - float chi widening len double
    f('a');    // f(int) - char -> int la cu the nhat
    f(1.0);    // f(double)

    g(1, 2);   // g(int, int) - ban co dinh thang varargs
    g(1);      // g(varargs) count=1
    g();       // g(varargs) count=0
}
f(int)
f(long)
f(double)
f(int)
f(double)
g(int, int)
g(varargs) count=1
g(varargs) count=0

Bẫy boxing/unboxing khi cả hai kiểu nguyên thủy lẫn wrapper cùng tồn tại:

void h(int x) {
    IO.println("h(int)");
}

void h(Integer x) {
    IO.println("h(Integer)");
}

void p(int x) {
    IO.println("p(int)");
}

void p(long x) {
    IO.println("p(long)");
}

void p(double x) {
    IO.println("p(double)");
}

void r(Integer x) {
    IO.println("r(Integer)");
}

void r(int... xs) {
    IO.println("r(varargs) count=" + xs.length);
}

void main() {
    h(1);                   // h(int)
    h(Integer.valueOf(1));  // h(Integer) - identity (phase 1) thang unboxing (phase 2)

    Integer boxed = 5;
    p(boxed);               // p(int) - unbox dung kieu, cu the nhat trong phase 2

    r(1);                   // r(Integer) - boxing (phase 2) thang varargs (phase 3)
}
h(int)
h(Integer)
p(int)
r(Integer)

Overload quyết định theo static type, không theo runtime type

Đây là điểm khác biệt cốt lõi giữa overload và override. Compiler chỉ nhìn kiểu khai báo của argument:

void gui(String s) {
    IO.println("gui(String)");
}

void gui(Object o) {
    IO.println("gui(Object)");
}

void main() {
    gui("abc");          // gui(String)

    Object o = "abc";    // static type la Object, runtime van la String
    gui(o);              // gui(Object) - compiler chi nhin static type

    CharSequence cs = "abc";
    gui(cs);             // gui(Object)
}
gui(String)
gui(Object)
gui(Object)
Bẫy vận hành: thêm một overload mới có thể đổi method được chọn ở call site cũ mà không ai sửa gì. Vì vậy overload phải khác nhau rõ ràng về ngữ nghĩa, không chỉ để tiện tay. List.remove(int) và List.remove(Object) là ví dụ kinh điển: list.remove(1) xóa theo vị trí, muốn xóa theo giá trị phải viết list.remove(Integer.valueOf(1)) — xem lại Methods — mục 5.

Bẫy null — chọn bản cụ thể nhất

void xuLy(String s) {
    IO.println("xuLy(String)");
}

void xuLy(Object o) {
    IO.println("xuLy(Object)");
}

void main() {
    xuLy("abc");  // xuLy(String)
    xuLy(null);   // xuLy(String) - cu the nhat
}
xuLy(String)
xuLy(String)

null hợp lệ với mọi kiểu reference, nên compiler chọn bản most specific: String là subtype của Object. Nhưng nếu hai bản không có quan hệ cha–con (ví dụ Integer và Long), chương trình không compile:

OverloadNullErr.java:11: error: reference to xuLy is ambiguous
        xuLy(null);
        ^
  both method xuLy(Integer) in Shape and method xuLy(Long) in Shape match
1 error

Cách sửa: ép kiểu rõ ràng xuLy((Integer) null), hoặc tốt hơn là đừng để API rơi vào tình huống này — dùng tên method khác nhau cho hai ngữ nghĩa khác nhau.

3. Overriding & dynamic dispatch Hay hỏi phỏng vấn

Hai method là override của nhau khi lớp con định nghĩa lại instance method của lớp cha với cùng tên và cùng danh sách tham số. Quy tắc đầy đủ:

  • Return type phải giống, hoặc là subtype (covariant — mục 9).
  • Access modifier không được thu hẹp (public không được đổi thành protected/private).
  • Checked exception không được mở rộng (có thể thu hẹp hoặc bỏ).
  • static, private, final method không override được (xem mục 5).
  • Luôn viết @Override để compiler kiểm tra — nếu signature sai, bạn nhận lỗi ngay thay vì vô tình tạo overload mới.
@Override access returnType ten(kieu thamSo) { ... } 
class Shape {
    double area() {
        return 0;
    }

    String name() {
        return "Shape";
    }

    @Override
    public String toString() {
        return name() + "[area=" + area() + "]";
    }
}

class Circle extends Shape {
    final double r;

    Circle(double r) {
        this.r = r;
    }

    @Override
    double area() {
        return Math.PI * r * r;
    }

    @Override
    String name() {
        return "Circle";
    }
}

class Rectangle extends Shape {
    final double w;
    final double h;

    Rectangle(double w, double h) {
        this.w = w;
        this.h = h;
    }

    @Override
    double area() {
        return w * h;
    }

    @Override
    String name() {
        return "Rectangle";
    }
}

void main() {
    Shape[] shapes = { new Circle(1), new Rectangle(2, 3) };
    for (Shape s : shapes) {
        IO.println(s);   // toString -> name() + area() deu la method ao
    }
}
Circle[area=3.141592653589793]
Rectangle[area=6.0]

Trong vòng lặp, biến s có static type là Shape. Compiler chỉ đảm bảo Shape có các method name(), area(), toString(); còn implementation nào chạy là do JVM quyết định theo runtime type (Circle hay Rectangle). Ngay cả toString() bên trong Shape gọi name() và area() cũng được dispatch tiếp tới lớp con.

JVM làm điều đó thế nào?

Mỗi class khi nạp vào JVM có một bảng method ảo (vtable) trỏ tới implementation thực tế của từng chữ ký. Lời gọi được biên dịch thành lệnh invokevirtual ghi theo static type, nhưng JVM tra bảng của runtime class để lấy địa chỉ method:

9: aload_1
10: invokevirtual #12   // Method BytecodeDemo$Shape.area:()D

Dòng javap thật ở trên (file BytecodeDemo.java, in ra 3.14) trỏ tới Shape.area vì đó là static type — nhưng JVM nhìn object thật là Circle và gọi Circle.area. Interface dùng lệnh invokeinterface với cơ chế tương tự. JIT compiler còn tối ưu bằng inline caching: khi call site luôn nhận một loại object, lời gọi ảo gần như nhanh bằng lời gọi thường.

Bạn không cần thuộc bytecode, nhưng cần trả lời được câu phỏng vấn: "JVM chọn method lúc compile hay lúc runtime?" — với instance method bị override: lúc runtime, dựa trên object thật.

4. Upcasting, downcasting & instanceof Junior+

Upcast (đi lên: con → cha) là gán object của lớp con cho biến kiểu lớp cha. Java tự động làm, luôn an toàn vì mọi Circle đều là một Shape:

Shape s = new Circle();   // upcast - tu dong

Downcast (đi xuống: cha → con) phải ép tường minh, vì compiler không biết object thật là gì. Nếu object thật không phải kiểu đích (hoặc lớp con của nó), JVM ném ClassCastException lúc chạy:

class Shape {
    void draw() {
        IO.println("Shape.draw");
    }
}

class Circle extends Shape {
    void draw() {
        IO.println("Circle.draw");
    }

    void banKinh() {
        IO.println("banKinh()");
    }
}

void main() {
    Shape s = new Circle();   // upcast - tu dong, an toan
    s.draw();                 // Circle.draw - dynamic dispatch

    // s.banKinh();           // Loi compile: Shape khong co banKinh()
    if (s instanceof Circle c) {   // pattern matching (Java 16+)
        c.banKinh();               // banKinh()
    }

    Shape s2 = new Shape();
    try {
        Circle c2 = (Circle) s2;   // downcast sai
        IO.println("khong bao gio in dong nay: " + c2);
    } catch (ClassCastException e) {
        IO.println(e.getClass().getName());   // java.lang.ClassCastException
    }
}
Circle.draw
banKinh()
java.lang.ClassCastException

Ba điều rút ra:

  • Qua biến static type Shape, bạn chỉ gọi được method mà Shape khai báo (hoặc thừa hưởng). Muốn gọi banKinh() phải downcast hoặc thiết kế lại.
  • instanceof kiểm tra object có thuộc kiểu hay không (kể cả subclass) trước khi ép — tránh ClassCastException.
  • Từ Java 16, pattern matching instanceof cho phép khai báo luôn biến đã ép kiểu: s instanceof Circle c — không còn dòng ép thủ công.

Pattern matching for switch & record pattern (Java 21)

Kết hợp sealed + switch theo kiểu + record pattern, bạn có dạng đa hình "có kiểm soát" rất gọn. Compiler biết mọi subtype (nhờ permits) nên bắt buộc switch expression phải bao hết trường hợp:

sealed interface Shape permits Circle, Rectangle {
}

record Circle(double r) implements Shape {
}

record Rectangle(double w, double h) implements Shape {
}

double dienTich(Shape s) {
    return switch (s) {
        case Circle(double r) -> Math.PI * r * r;
        case Rectangle(double w, double h) -> w * h;
    };
}

void main() {
    IO.println(dienTich(new Circle(1)));       // 3.141592653589793
    IO.println(dienTich(new Rectangle(2, 3))); // 6.0
}
3.141592653589793
6.0

case Circle(double r) chính là record pattern: vừa kiểm tra kiểu vừa "tháo" component r ra biến mà không cần gọi c.r(). Record pattern là kiến thức nhận biết — chưa cần thành thạo, nhưng gặp trong codebase hiện đại phải đọc hiểu ngay.

Đừng dùng getClass() == Circle.class thay instanceof. Phép so sánh đó chỉ đúng khi object là chính xác lớp đó; subclass và proxy (Spring, Hibernate) sẽ trượt. instanceof kiểm tra theo quan hệ "là một" nên đúng với cả cây kế thừa.

5. Field hiding & static hiding — thứ KHÔNG đa hình Hay hỏi phỏng vấn

Method mới đa hình; field thì không. Nếu lớp con khai báo field trùng tên lớp cha, field cha bị che (hidden) chứ không bị override. Truy cập field luôn quyết định theo static type của biến:

class Shape {
    String ten = "Shape";

    String layTen() {
        return ten;
    }
}

class Circle extends Shape {
    String ten = "Circle";

    @Override
    String layTen() {
        return ten;
    }
}

void main() {
    Shape s = new Circle();
    IO.println(s.ten);           // Shape  - field theo static type
    IO.println(s.layTen());      // Circle - method theo runtime type

    Circle c = new Circle();
    IO.println(c.ten);           // Circle
    IO.println(((Shape) c).ten); // Shape  - ep len cha thi thay field cha
}
Shape
Circle
Circle
Shape

Cùng một object Circle mà s.ten in Shape còn s.layTen() in Circle — đây là câu hỏi phỏng vấn rất hay gặp. Lời khuyên production: field để private, truy cập qua getter/setter; khi đó mọi hành vi đi qua method và đa hình hoạt động đúng.

static method cũng vậy — nó bị hide, không override. Gọi static qua biến thực chất là compiler thay bằng tên class theo static type:

class Shape {
    static String loai() {
        return "Shape static";
    }
}

class Circle extends Shape {
    static String loai() {
        return "Circle static";
    }
}

void main() {
    Shape s = new Circle();
    IO.println(s.loai());       // Shape static - khong dispatch theo object
    IO.println(Shape.loai());   // Shape static
    IO.println(Circle.loai());  // Circle static
}
Shape static
Shape static
Circle static

Vì vậy không bao giờ dùng static method cho hành vi cần thay đổi theo từng loại object. Gọi static qua instance (s.loai()) là bad style — nên viết Shape.loai() hoặc Circle.loai() để ý định rõ ràng.

7. Đa hình với interface Junior+

Trong production, đa hình gần như luôn đi qua interface: code gọi làm việc với abstraction, implementation cụ thể được inject lúc chạy. Ví dụ bạn đã gặp mỗi ngày: List<String> ds = new ArrayList<>(); — biến là List, object là ArrayList; đổi sang LinkedList chỉ sửa một dòng.

interface Shape {
    double area();

    String ten();

    default boolean laHinhTron() {
        return ten().equals("Circle");
    }
}

class Circle implements Shape {
    final double r;

    Circle(double r) {
        this.r = r;
    }

    public double area() {
        return Math.PI * r * r;
    }

    public String ten() {
        return "Circle";
    }
}

class Rectangle implements Shape {
    final double w;
    final double h;

    Rectangle(double w, double h) {
        this.w = w;
        this.h = h;
    }

    public double area() {
        return w * h;
    }

    public String ten() {
        return "Rectangle";
    }
}

void inDienTich(Shape s) {
    IO.println(s.ten() + ": area=" + s.area() + ", laHinhTron=" + s.laHinhTron());
}

void main() {
    inDienTich(new Circle(1));
    inDienTich(new Rectangle(2, 3));
}
Circle: area=3.141592653589793, laHinhTron=true
Rectangle: area=6.0, laHinhTron=false

inDienTich(Shape s) là ví dụ của "lập trình theo abstraction": nó chỉ cần biết Shape làm được gì, không cần biết object là Circle hay Rectangle. Thêm một hình mới (ví dụ Triangle) không phải sửa inDienTich — miễn là hình đó implements Shape. default method (laHinhTron) cũng là method ảo, lớp con có thể override nếu muốn.

Abstract class vs interface — khi nào dùng cái nào — học ở 2.5 Abstract class vs Interface. Trước mắt hãy nhớ: interface cho phép một class "là nhiều hình thái" (implements Comparable, Serializable), còn abstract class phù hợp khi các lớp con chia sẻ state và code chung.

8. Ứng dụng production — Strategy & nguyên lý Open/Closed Production

Đa hình là công cụ chính để loại bỏ chuỗi if/else (hoặc switch) kiểm tra type. Mẫu refactor này có tên: Replace Conditional with Polymorphism, và nó phục vụ nguyên lý Open/Closed: mở cho mở rộng, đóng cho sửa đổi.

abstract class Shape {
    abstract double area();

    abstract String ten();
}

class Circle extends Shape {
    final double r;

    Circle(double r) {
        this.r = r;
    }

    @Override
    double area() {
        return Math.PI * r * r;
    }

    @Override
    String ten() {
        return "Circle";
    }
}

class Rectangle extends Shape {
    final double w;
    final double h;

    Rectangle(double w, double h) {
        this.w = w;
        this.h = h;
    }

    @Override
    double area() {
        return w * h;
    }

    @Override
    String ten() {
        return "Rectangle";
    }
}

// Cach cu: if/else theo type - them hinh moi phai sua method nay
double dienTichKieuCu(Shape s) {
    if (s instanceof Circle c) {
        return c.area();
    }
    if (s instanceof Rectangle r) {
        return r.area();
    }
    return 0;
}

// Cach dung da hinh: chi goi method ao, khong can biet type cu the
void inTatCa(Shape... shapes) {
    for (Shape s : shapes) {
        IO.println(s.ten() + " = " + s.area());
    }
}

void main() {
    Shape[] shapes = { new Circle(1), new Rectangle(2, 3) };
    IO.println("cach cu : " + dienTichKieuCu(shapes[0]));
    IO.println("cach cu : " + dienTichKieuCu(shapes[1]));
    inTatCa(shapes);
}
cach cu : 3.141592653589793
cach cu : 6.0
Circle = 3.141592653589793
Rectangle = 6.0

Nhìn thì hai cách cho cùng kết quả, nhưng khác nhau về chi phí bảo trì: cách if/else phải sửa mọi method có chuỗi kiểm tra type mỗi khi thêm hình mới, còn cách đa hình chỉ cần thêm class mới. Đây cũng chính là nền tảng của Strategy pattern: mỗi chiến lược là một implementation của cùng interface, chọn lúc runtime. Xem thêm 2.8 SOLID & design patterns.

Lưu ý thực dụng: nếu tập kiểu là đóng và nhỏ (ví dụ chỉ 2-3 loại trạng thái), một switch pattern với sealed classes (mục 4) lại dễ đọc và an toàn hơn ép mọi thứ thành class. Đa hình không phải cây búa vạn năng.

9. Covariant return type

Từ Java 5, method override được phép trả về kiểu hẹp hơn (subtype) so với lớp cha. Điều này giúp call site không phải ép kiểu:

class Shape {
    Shape copy() {
        return new Shape();
    }
}

class Circle extends Shape {
    final double r;

    Circle(double r) {
        this.r = r;
    }

    @Override
    Circle copy() {
        return new Circle(r);
    }
}

void main() {
    Shape s = new Circle(5);
    IO.println(s.copy().getClass().getSimpleName());  // Circle

    Circle c = new Circle(5);
    Circle c2 = c.copy();                              // khong can ep kieu
    IO.println(c2.getClass().getSimpleName() + " r=" + c2.r);  // Circle r=5.0
}
Circle
Circle r=5.0

Qua biến Shape, s.copy() vẫn khai báo trả về Shape; nhưng qua biến Circle, compiler biết c.copy() trả về Circle. Để giữ tương thích bytecode, compiler sinh thêm một bridge method có return type Shape gọi tới bản covariant — đây là chi tiết nhận biết, gặp khi đọc javap. JDK dùng nhiều: interface Appendable khai báo append(CharSequence) trả về Appendable, còn StringBuilder override trả về chính StringBuilder — nhờ vậy bạn chain được .append(...).append(...) (xem lại Methods — mục 10).

10. Bẫy gọi method ảo trong constructor Hay hỏi phỏng vấn

Gọi một method có thể bị override ngay trong constructor của lớp cha là bẫy kinh điển: override của lớp con chạy trước khi field của lớp con được khởi tạo. Thứ tự khởi tạo là: constructor lớp cha → field initializer/instance block của con → thân constructor con.

class Shape {
    Shape() {
        IO.println("Shape() goi moTa() -> [" + moTa() + "]");
    }

    String moTa() {
        return "Shape";
    }
}

class Circle extends Shape {
    String ten = "Circle";

    @Override
    String moTa() {
        return ten;
    }
}

void main() {
    new Circle();
    Circle c = new Circle();
    IO.println("sau khi tao xong: [" + c.moTa() + "]");
}
Shape() goi moTa() -> [null]
Shape() goi moTa() -> [null]
sau khi tao xong: [Circle]

Lúc Shape() chạy, JVM đã biết object thật là Circle, nên dispatch vào Circle.moTa() — nhưng field ten của Circle chưa được gán, nên trả về null. Nếu field là int, bạn sẽ nhận 0 thay vì giá trị mong đợi.

Quy tắc: constructor chỉ nên gọi method private, static hoặc final — những method không thể bị override. Nếu cần "hook" cho lớp con, hãy để việc đó ở method init() được gọi tường minh sau khi tạo object, hoặc dùng factory method.

11. Object methods dưới góc nhìn đa hình Junior+

Mọi class đều kế thừa Object, và các method như toString(), equals(), hashCode() đều là method ảo. Đây là lý do IO.println(object) in ra mô tả tuỳ object thật:

class Shape {
    @Override
    public String toString() {
        return "Shape";
    }
}

class Circle extends Shape {
    @Override
    public String toString() {
        return "Circle(r=1)";
    }
}

void main() {
    Object o = new Circle();
    IO.println(o);                 // Circle(r=1) - dynamic dispatch
    IO.println("x" + new Circle()); // xCircle(r=1) - cong chuoi cung goi toString
}
Circle(r=1)
xCircle(r=1)

Hệ quả production: List.contains, HashMap, logging, assertion đều dựa vào equals/hashCode/toString — tức là dựa vào đa hình. Override sai equals/hashCode (vi phạm contract) sẽ tạo bug rất khó tìm. Chi tiết ở 2.6 equals / hashCode / toString.

13. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Polymorphism (đa hình) là gì? Nêu lợi ích.
Là khả năng cùng một lời gọi method cho ra hành vi khác nhau tuỳ object thật sự nhận lời gọi. Ví dụ s.draw() vẽ hình tròn nếu object là Circle, vẽ chữ nhật nếu là Rectangle. Lợi ích: code gọi làm việc với abstraction thay vì từng type cụ thể; thêm loại mới không phải sửa code cũ (Open/Closed); dễ test nhờ mock implementation.
Câu 2. Hai loại đa hình chính trong Java, khác nhau ở thời điểm nào?
Compile-time (static): overloading — compiler chọn method theo static type của biến/argument, quyết định ngay khi biên dịch. Runtime (dynamic): overriding — JVM chọn implementation theo runtime type của object mỗi lần gọi (dynamic dispatch). Đa hình theo nghĩa OOP mạnh nhất là loại runtime.
Câu 3. Overloading là gì? Hai method là overload của nhau khi nào?
Cùng tên nhưng khác danh sách tham số: khác số lượng, khác kiểu, hoặc khác thứ tự kiểu — trong cùng class hoặc giữa cha–con. Tên parameter không tính; return type cũng không tính vào chữ ký.
Câu 4. Vì sao không thể overload chỉ bằng return type?
Method descriptor trong bytecode gồm tên + kiểu tham số; lời gọi m(x) chỉ mang tên và argument nên compiler không có cách nào phân biệt nếu hai bản chỉ khác return type. JLS cấm và báo lỗi "method ... is already defined".
Câu 5. Overload resolution chọn method theo thứ tự nào?
3 phase, phase trước thắng phase sau: (1) strict — khớp chính xác hoặc widening, không boxing; (2) loose — cho phép boxing/unboxing; (3) varargs. Trong mỗi phase, nếu nhiều bản cùng hợp lệ thì chọn bản "cụ thể nhất" (most specific).
Câu 6. Có m(long) và m(Integer), gọi m(1) chọn bản nào? Vì sao?
Bản m(long). int → long là widening nên thuộc phase 1, còn int → Integer là boxing thuộc phase 2. Muốn vào bản Integer phải viết m(Integer.valueOf(1)) (lúc đó identity phase 1 thắng).
Câu 7. Có gui(String) và gui(Object), gọi gui(null) chọn bản nào? Khi nào lỗi ambiguous?
Chọn gui(String): null hợp lệ với mọi reference type nên compiler chọn bản cụ thể nhất, String là subtype của Object. Nếu hai bản không có quan hệ cha–con (ví dụ Integer và Long) thì lỗi "reference to ... is ambiguous"; sửa bằng ép kiểu gui((Integer) null).
Câu 8. Overriding là gì? Điều kiện để override hợp lệ?
Lớp con định nghĩa lại instance method của lớp cha với cùng tên + cùng danh sách tham số. Return type giống hoặc covariant; access modifier không được thu hẹp; checked exception không được mở rộng. Chỉ override được method không static/private/final, và phải có quan hệ kế thừa/implements. Luôn dùng @Override.

Nâng cao (Junior+)

Câu 9. Dynamic dispatch hoạt động thế nào?
Lời gọi s.area() biên dịch thành lệnh invokevirtual ghi method theo static type (Shape.area). Lúc chạy, JVM tra bảng method ảo (vtable) của runtime class (Circle) và gọi implementation override. Interface dùng invokeinterface tương tự. JIT tối ưu call site ổn định bằng inline caching nên chi phí gần như lời gọi thường.
Câu 10. Field có đa hình không?
Không. Field không bị override mà bị hide: s.ten đọc theo static type của biến, dù object thật là lớp con. Muốn hành vi động phải dùng method (getter). Best practice: field private, truy cập qua method.
Câu 11. Static method có đa hình không?
Không. Static method thuộc class, bị hide chứ không override; gọi qua instance thực chất compiler thay bằng tên class theo static type. Static không có this nên không thể dispatch theo object.
Câu 12. Upcast và downcast khác nhau thế nào? Khi nào ném ClassCastException?
Upcast (con → cha) tự động và luôn an toàn. Downcast (cha → con) phải ép tường minh; nếu object thật không phải kiểu đích hoặc lớp con của nó thì JVM ném ClassCastException lúc runtime. Kiểm tra instanceof trước khi ép.
Câu 13. Pattern matching instanceof (Java 16) giải quyết vấn đề gì?
Thay vì if (s instanceof Circle) { Circle c = (Circle) s; ... }, viết gọn if (s instanceof Circle c) { ... } — vừa kiểm tra vừa khai báo biến đã ép kiểu, giảm lỗi copy-paste và tăng độ rõ. Biến pattern có scope trong nhánh điều kiện.
Câu 14. Pattern matching for switch (Java 21) — điều kiện để switch exhaustive?
Với switch expression theo kiểu, compiler yêu cầu bao hết mọi khả năng. Nếu kiểu là sealed với danh sách permits hữu hạn, compiler biết đủ mọi subtype và bắt lỗi thiếu case. Không dùng sealed thì phải thêm default.
Câu 15. Record pattern là gì?
Tính năng Java 21 cho phép "tháo" record ngay trong pattern: case Circle(double r) thay vì case Circle c rồi gọi c.r(). Có thể lồng nhiều tầng. Đây là kiến thức nhận biết để đọc code hiện đại; viết thành thạo sẽ hữu ích khi làm việc với dữ liệu dạng cây.
Câu 16. Gọi method ảo trong constructor gây ra vấn đề gì?
Override của lớp con chạy trước khi field của lớp con được khởi tạo (thứ tự: constructor cha → field initializer của con → thân constructor con). Kết quả là override đọc field còn null/0. Tránh gọi method overridable trong constructor; dùng private/static/final hoặc tách init().
Câu 17. Covariant return type là gì?
Từ Java 5, method override được trả về subtype của kiểu trả về ở lớp cha: Circle copy() override Shape copy(). Qua biến kiểu Circle, call site không cần ép kiểu. Compiler sinh bridge method để tương thích bytecode.
Câu 18. Nguyên lý Liskov (LSP) liên quan gì tới overriding?
LSP phát biểu: nơi dùng lớp cha phải thay được bằng object của mọi lớp con mà hành vi không vỡ. Override chỉ nên giữ hoặc củng cố ngữ nghĩa (precondition không chặt hơn, postcondition không lỏng hơn). Ví dụ kinh điển vi phạm: Square extends Rectangle — setWidth của hình vuông vô tình đổi cả chiều cao, làm code dùng Rectangle bị sai.

Production & Node.js

Câu 19. Tóm tắt khác biệt overload và override trong một câu cho mỗi loại?
Overload: cùng tên khác tham số, quyết định lúc compile theo static type, không cần kế thừa, static/private/final đều được. Override: cùng chữ ký, quyết định lúc runtime theo runtime type, bắt buộc kế thừa/implements, không áp dụng cho static/private/final. Bảng đầy đủ ở mục 6.
Câu 20. Đa hình được dùng thế nào trong production?
Thay chuỗi if/else instanceof bằng method ảo (Replace Conditional with Polymorphism, Strategy pattern) — thêm loại mới chỉ thêm class, không sửa code cũ (Open/Closed). Dependency injection (Spring) inject interface rồi runtime nhận implementation/proxy; mock khi test cũng nhờ đa hình. Xem mục 8.
Câu 21. Góc Node.js: JS có overload không? Duck typing vs nominal typing?
JS không có overload thật — khai báo hai function cùng tên thì hàm sau ghi đè hàm trước, tham số không có kiểu tĩnh. JS dùng duck typing (structural): object nào có method phù hợp là dùng được, không cần kế thừa. Java dùng nominal typing: muốn là Shape phải khai báo extends/implements. TypeScript có overload nhưng chỉ ở mức type-check, xoá khi compile; runtime không dispatch như JVM.

14. Bài tập đoán output

Bài 1 — widening thắng boxing 
void chon(long x)    { IO.println("chon(long)"); }
void chon(Integer x) { IO.println("chon(Integer)"); }

chon(1);
chon(1L);
chon(Integer.valueOf(1));
In ra chon(long), chon(long), chon(Integer). chon(1) chọn long vì widening thuộc phase 1 thắng boxing phase 2; Integer.valueOf(1) khớp chính xác bản Integer ngay phase 1.
Bài 2 — null chọn bản cụ thể nhất 
void gui(String s) { IO.println("String"); }
void gui(Object o) { IO.println("Object"); }

gui(null);
In ra String. null khớp cả hai, compiler chọn bản most specific; String là subtype của Object.
Bài 3 — int/long/double với char và float 
void f(int x)    { IO.println("int"); }
void f(long x)   { IO.println("long"); }
void f(double x) { IO.println("double"); }

f('a');
f(1.5f);
f(1L);
f(1);
In ra int, double, long, int. char → int là widening cụ thể nhất; float chỉ widening được lên double (không sang int/long); long khớp chính xác; int khớp chính xác.
Bài 4 — boxing và varargs 
void h(int x)     { IO.println("int"); }
void h(Integer x) { IO.println("Integer"); }

void r(Integer x) { IO.println("r(Integer)"); }
void r(int... xs) { IO.println("r(varargs) count=" + xs.length); }

h(1);
h(Integer.valueOf(1));
r(1);
In ra int, Integer, r(Integer). h(Integer.valueOf(1)) khớp identity phase 1 thắng unboxing phase 2; r(1) chọn bản Integer nhờ boxing phase 2, thắng varargs phase 3.
Bài 5 — bản cố định thắng varargs 
void g(int a, int b) { IO.println("g(int, int)"); }
void g(int... xs)    { IO.println("g(varargs) count=" + xs.length); }

g(1, 2);
g(1);
g();
In ra g(int, int), g(varargs) count=1, g(varargs) count=0. g(1, 2) khớp bản cố định (phase 1), chỉ khi không còn bản cố định nào phù hợp compiler mới xét varargs (phase 3).
Bài 6 — vì sao không compile? 
void xuLy(Integer x) { IO.println("Integer"); }
void xuLy(Long x)    { IO.println("Long"); }

xuLy(null);
Không compile: "reference to xuLy is ambiguous — both method xuLy(Integer) ... and method xuLy(Long) ... match". Integer và Long là hai nhánh độc lập, không bản nào cụ thể hơn. Sửa: xuLy((Integer) null), hoặc đổi tên một method.
Bài 7 — field hiding 
class Shape {
    String ten = "Shape";
    String layTen() { return ten; }
}

class Circle extends Shape {
    String ten = "Circle";
    @Override String layTen() { return ten; }
}

Shape s = new Circle();
IO.println(s.ten);
IO.println(s.layTen());
In ra Shape rồi Circle. Field ten đọc theo static type của biến s (Shape); method layTen() dispatch theo runtime type (Circle).
Bài 8 — static hiding 
class Shape {
    static String loai() { return "Shape static"; }
}

class Circle extends Shape {
    static String loai() { return "Circle static"; }
}

Shape s = new Circle();
IO.println(s.loai());
IO.println(Circle.loai());
In ra Shape static rồi Circle static. Static method không dispatch theo object: s.loai() bị compiler dịch thành Shape.loai() vì static type của s là Shape.
Bài 9 — dynamic dispatch qua Object 
class Shape {
    @Override public String toString() { return "Shape"; }
}

class Circle extends Shape {
    @Override public String toString() { return "Circle"; }
}

Object o = new Circle();
IO.println(o);
IO.println("x" + o);
In ra Circle rồi xCircle. Cả IO.println(Object) lẫn phép cộng chuỗi đều gọi toString(), và method này dispatch theo runtime type Circle dù biến có static type Object.
Bài 10 — dòng nào ném ClassCastException? 
Shape s = new Shape();
Circle c1 = (Circle) s;            // dong A
Shape s2 = new Circle();
Circle c2 = (Circle) s2;           // dong B
Dòng A ném ClassCastException: object thật là Shape, không phải Circle. Dòng B an toàn vì object thật là Circle (downcast hợp lệ). Kiểm tra instanceof trước nếu chưa chắc.
Bài 11 — refactor instanceof thành pattern matching 
double dienTich(Shape s) {
    if (s instanceof Circle) {
        Circle c = (Circle) s;
        return c.area();
    }
    if (s instanceof Rectangle) {
        Rectangle r = (Rectangle) s;
        return r.area();
    }
    return 0;
}
Dùng pattern matching (Java 16+): 
double dienTich(Shape s) {
    if (s instanceof Circle c) {
        return c.area();
    }
    if (s instanceof Rectangle r) {
        return r.area();
    }
    return 0;
}
Tốt hơn nữa: nếu mọi Shape đều biết tính diện tích, chuyển area() thành abstract method và bỏ hẳn chuỗi instanceof (mục 8).
Bài 12 — overload + override cùng lúc 
class Shape {
    void moTa(Shape s)   { IO.println("Shape.moTa(Shape)"); }
    void moTa(Circle c)  { IO.println("Shape.moTa(Circle)"); }
}

class Circle extends Shape {
    @Override
    void moTa(Shape s)   { IO.println("Circle.moTa(Shape)"); }
}

Shape s = new Circle();
Circle c = new Circle();
s.moTa(c);
c.moTa(c);
s.moTa(s);
In ra Shape.moTa(Circle), Shape.moTa(Circle), Circle.moTa(Shape). Hai dòng đầu: overload chọn moTa(Circle) theo static type của argument, nhưng Circle không override bản đó nên chạy implementation của Shape. Dòng ba: chọn moTa(Shape) rồi dispatch theo runtime type Circle.
Bài 13 — constructor gọi method ảo 
class Shape {
    Shape() {
        IO.println("[" + moTa() + "]");
    }
    String moTa() { return "Shape"; }
}

class Circle extends Shape {
    String ten = "Circle";
    @Override
    String moTa() { return ten; }
}

new Circle();
In ra [null]. Constructor Shape() gọi moTa() đã bị Circle override, nhưng field ten của Circle chỉ được gán sau khi constructor cha chạy xong, nên trả về null.

15. Cheat sheet & checklist

Cheat sheet

Việc cần nhớQuy tắc
Hai loại đa hìnhOverloading = compile-time (static type) · Overriding = runtime (runtime type, dynamic dispatch)
Overload hợp lệKhác số lượng/kiểu/thứ tự tham số; không tính return type và tên parameter
Thứ tự chọn overload(1) khớp chính xác/widening → (2) boxing/unboxing → (3) varargs; most specific thắng trong mỗi phase
m(1) với m(long)/m(Integer)Chọn m(long) — widening thắng boxing
gui(null) với String/ObjectChọn String; với Integer/Long thì lỗi ambiguous
Overload nhìn gì?Static type của biến/argument — Object o = "abc" thì gọi bản Object
Override hợp lệCùng chữ ký; return giống/covariant; access không hẹp hơn; checked exception không rộng hơn; luôn @Override
Dynamic dispatchStatic type quyết định gọi được method nào; runtime type quyết định implementation nào chạy
Upcast / downcastUpcast tự động, an toàn; downcast phải ép, sai → ClassCastException; dùng instanceof
Pattern matchinginstanceof Circle c (Java 16); switch theo kiểu + record pattern (Java 21) với sealed để exhaustive
Field & staticKhông đa hình: hide theo static type; field nên private + getter

ConstructorKhông gọi method overridable; field lớp con chưa khởi tạo
ProductionThay if/else instanceof bằng method ảo (Strategy, OCP); lập trình theo interface

Checklist tự đánh giá trước phỏng vấn

  • Giải thích được đa hình bằng một ví dụ đời thường, không dùng thuật ngữ khó.
  • Kể đúng hai loại đa hình và thời điểm quyết định của mỗi loại.
  • Viết được 3 phiên bản overload hợp lệ và giải thích vì sao chúng hợp lệ.
  • Giải thích vì sao khác return type không tạo overload.
  • Dự đoán đúng kết quả m(1) khi có m(long) và m(Integer).
  • Dự đoán đúng gui(null) và biết khi nào lỗi ambiguous.
  • Phân biệt overload (static type) và override (runtime type) bằng ví dụ Object o = "abc".
  • Viết override đúng chuẩn với @Override, kể cả covariant return type.
  • Giải thích field hiding và static hiding, không nhầm là đa hình.
  • Kể được điều kiện ném ClassCastException và cách phòng bằng instanceof.
  • Viết được pattern matching instanceof và switch pattern với sealed + record pattern.
  • Giải thích bẫy gọi method ảo trong constructor và cách tránh.
  • Nêu được một chỗ trong production nên thay if/else theo type bằng đa hình.
  • Trả lời được câu "JS có overload không?" kèm so sánh duck typing vs nominal typing.
