Đây là câu hỏi phỏng vấn kinh điển nhất của OOP Java: abstract class và interface khác gì nhau, khi nào chọn cái nào? 1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Trừu tượng hoá (abstraction) là nghệ thuật bỏ đi chi tiết implementation và chỉ giữ lại cái người gọi cần biết. Bạn đã gặp nó từ sớm: List chỉ hứa "tôi có add, get, size", bạn không cần biết nó là ArrayList hay LinkedList. Abstract class và interface là hai công cụ để tạo ra lời hứa đó, nhưng mạnh ở hai hướng khác nhau:

  • Abstract class = một class dở dang: vừa có hợp đồng (abstract method) vừa có tài sản (field, constructor, code dùng chung). Quan hệ là is-a: chó là một động vật.
  • Interface = bản hợp đồng thuần: chỉ quy định "làm được gì", không giữ state, một class ký được nhiều hợp đồng. Quan hệ là can-do / capability: thanh toán được, hoàn tiền được, sắp xếp được.

Mức độ bắt buộc của chủ đề 2.5 (phỏng vấn: rất cao · production: bắt buộc):

  • Phải làm được — khai báo abstract class/interface; implement nhiều interface; viết default/static method; sửa xung đột default bằng Interface.super.method(); viết functional interface và gán lambda; đọc hiểu lỗi compiler kinh điển của chủ đề này.
  • Phải hiểu — vì sao interface không có state và constructor; field trong interface thực chất là gì; thứ tự giải quyết xung đột default (class thắng → interface cụ thể hơn thắng → lỗi); vì sao Java cho đa implement interface nhưng không cho đa kế thừa class; khác biệt tư duy thiết kế is-a vs can-do.
  • Nhận biết — marker interface (Serializable, Cloneable); sealed interface (Java 17) + pattern matching switch (đào sâu ở 2.7 Enum, nested & sealed classes); functional interface là nền của lambda (học ở 3.6 Lambda); interface ở biên hệ thống để test/DI.

Cách học hiệu quả nhất:

  1. Đoán output hoặc đoán lỗi compile của ví dụ trước khi nhìn comment kết quả.
  2. Làm mục Bài tập đoán output trước, chỉ mở đáp án sau khi đã đoán.
  3. Ôn nhanh bằng Cheat sheet và bảng quyết định trước buổi phỏng vấn.
  4. Gặp câu lạ, tra ở mục Interview Q&A.

Góc Node.js — JS không có interface, TS có nhưng chỉ là kiểu tĩnh

JavaScript thuần không có khái niệm interface hay abstract class. Nó dùng duck typing: miễn object "có method cần dùng" là chạy, không ai kiểm tra tên class:

// JavaScript (Node 22) - khong co interface, chi can "co method pay"
class CardPayment {
  pay(amount) { return amount > 0; }
}

function checkout(gateway, amount) {
  console.log(gateway.pay(amount));
}

checkout(new CardPayment(), 100);
// true

TypeScript thêm interface, nhưng theo structural typing: chỉ cần cấu trúc (shape) khớp là được, không cần khai báo implements. Và interface TS bị xoá sạch khi biên dịch — runtime không hề biết nó tồn tại:

// TypeScript - structural typing: class khong he khai bao implements
interface Payment {
  pay(amount: number): boolean;
}

class CardPayment {
  pay(amount: number): boolean { return amount > 0; }
}

function checkout(p: Payment, amount: number): void {
  console.log("checkout", p.pay(amount));
}

checkout(new CardPayment(), 100);
// checkout true

2. Abstract class — class còn dở dang Junior+

Abstract class là class không thể tạo object trực tiếp, dùng làm nền cho các class con. Nó có thể chứa mọi thứ class thường có — field, constructor, method thường, static — cộng thêm method abstract (chỉ có chữ ký, không có body), buộc class con phải hoàn thiện.

[access] abstract class TenClass { abstract KieuTraVe lamGiDo(); KieuTraVe dungChung() { ... } }

Ví dụ dưới cho thấy abstract class giữ state dùng chung (biến đếm) và constructor — hai thứ interface không có. Class con ở đây là anonymous class cho gọn (cú pháp new DataProcessor() { ... } tạo class con vô danh ngay tại chỗ):

abstract class DataProcessor {
    private int soLanChay = 0;

    DataProcessor() {
        IO.println("Tao DataProcessor");
    }

    abstract String ten();

    String chay() {
        soLanChay++;
        return "lan " + soLanChay + ": " + ten();
    }
}

void main() {
    DataProcessor p = new DataProcessor() {
        String ten() {
            return "csv";
        }
    };
    IO.println(p.chay());
    IO.println(p.chay());
}
Tao DataProcessor
lan 1: csv
lan 2: csv

Ba điều cần nhớ:

  • Constructor vẫn tồn tại — nó chạy khi subclass được tạo, qua chuỗi super(). Nhưng không ai gọi new DataProcessor() trực tiếp được.
  • State là của abstract class — soLanChay nằm trong object subclass và tích luỹ qua từng lần gọi. Interface không làm được điều này.
  • Class con phải "trả nợ" — hoặc override hết abstract method, hoặc cũng khai báo abstract. Compiler ép bạn ngay lúc compile.

Hai lỗi kinh điển, đúng những gì compiler JDK 25 in ra:

Abstract method không được là private, static hay final — vì cả ba đều chống lại ý nghĩa "để subclass override". Ngược lại, method thường trong abstract class có thể final để chặn override. Một abstract class không bắt buộc phải có abstract method nào: đôi khi bạn chỉ cần nó để chặn new và gom code chung.

Khi nào dùng abstract class?

  • Các subclass chia sẻ state hoặc code chung thật sự (không chỉ chữ ký).
  • Cần constructor để ép subclass khởi tạo đúng cách, hoặc cần protected field/method cho con dùng.
  • Quan hệ là is-a rõ ràng và chỉ có một "trục" kế thừa: CsvDataProcessor là một DataProcessor.
  • Muốn dùng template method (mục 3): khung thuật toán cố định, vài bước cho con điền vào.

3. Template method với DataProcessor Production

Template method là pattern mạnh nhất của abstract class: class cha định nghĩa khung thuật toán và chốt nó bằng final, còn từng bước chi tiết là abstract method cho class con điền. Người gọi chỉ thấy một method xuLy(...); không thể vô tình phá thứ tự các bước.

3.1 Pattern Template Method — khung xương nằm ở lớp cha

Template method chia thuật toán thành hai phần: skeleton (khung cố định do class cha giữ) và các step (bước thay đổi được, class con điền). Khung được đặt final để không ai override; các bước khai báo abstract (bắt buộc con điền) hoặc là method có thân làm mặc định. Quyền điều khiển bị đảo ngược: class con không gọi cha, mà cha gọi class con — Hollywood principle: "Don't call us, we'll call you".

Mở rộng DataProcessor quen thuộc bằng log từng bước để thấy rõ thứ tự do khung quyết định:

abstract class DataProcessor {
    final String xuLy(String duLieu) {
        IO.println("[1] lam sach");
        String sach = lamSach(duLieu);
        IO.println("[2] bien doi");
        String ketQua = bienDoi(sach);
        IO.println("[3] ghi nhan");
        return ghiNhan(ketQua);
    }

    private String lamSach(String s) {
        return s.trim();
    }

    protected abstract String bienDoi(String s);

    protected abstract String ghiNhan(String s);
}

class CsvDataProcessor extends DataProcessor {
    protected String bienDoi(String s) {
        return s.toUpperCase();
    }

    protected String ghiNhan(String s) {
        return "CSV> " + s;
    }
}

void main() {
    DataProcessor csv = new CsvDataProcessor();
    IO.println(csv.xuLy("  don hang 42  "));

    DataProcessor dao = new DataProcessor() {
        protected String bienDoi(String s) {
            return new StringBuilder(s).reverse().toString();
        }

        protected String ghiNhan(String s) {
            return "TXT> " + s;
        }
    };
    IO.println(dao.xuLy("java"));
}

Hai class con — một class thật, một anonymous class — chỉ cung cấp đúng hai bước, cả hai chạy trên cùng bộ khung lam sach → bien doi → ghi nhan. Để ý cách chia vai: lamSach là private (chi tiết nội bộ, con không được chạm), xuLy là final (khung không cho đổi), còn bienDoi/ghiNhan là protected abstract (điểm mở rộng dành cho con). Đây chính là "Open for extension, closed for modification" trong thực tế.

3.2 Hook và abstract step — kiểm soát thứ tự, vì sao skeleton phải final

Có hai loại điểm mở rộng. Abstract step không có thân — compiler buộc mọi class con điền. Hook có thân mặc định (thường no-op hoặc xử lý hợp lý sẵn) — con có thể override nếu cần. Quy tắc thực dụng: bước nào bắt buộc thì để abstract, hành vi tùy chọn (log, audit, validate) thì làm hook.

abstract class ReportTemplate {
    final void xuat() {          // skeleton - thu tu do lop cha chot
        header();
        noiDung();
        footer();
    }

    void header() {              // hook - co san, con co the doi
        IO.println("=== BAO CAO ===");
    }

    abstract void noiDung();     // abstract step - bat buoc con dien

    void footer() {              // hook
        IO.println("--- het ---");
    }
}

class DoanhThu extends ReportTemplate {
    void noiDung() {
        IO.println("Doanh thu: 100 trieu");
    }
}

class KiemTon extends ReportTemplate {
    void noiDung() {
        IO.println("Ton kho: 42 san pham");
    }

    @Override
    void footer() {              // doi hook, khong doi thu tu
        IO.println("--- kiem ton xong ---");
    }
}

void main() {
    new DoanhThu().xuat();
    new KiemTon().xuat();
}
=== BAO CAO ===
Doanh thu: 100 trieu
--- het ---
=== BAO CAO ===
Ton kho: 42 san pham
--- kiem ton xong ---

DoanhThu dùng nguyên hook mặc định; KiemTon chỉ đổi footer(). Cả hai không thể chèn thêm bước hay bỏ header() — thứ tự nằm ở xuat() của lớp cha.

Nếu class con quên điền abstract step, javac chặn ngay từ lúc biên dịch:

class QuenBuoc extends DataProcessor {
^
1 error

Nhưng còn một lỗ hổng khác: nếu skeleton không final, class con "quên" bước bằng cách override thẳng xuLy. Bước cũ vẫn nằm đó nên compiler không báo gì, chỉ hành vi sai lúc chạy:

abstract class BadTemplate {
    String xuLy(String s) {              // KHONG final - ai cung override duoc
        return ghiNhan(bienDoi(s.trim()));
    }

    protected abstract String bienDoi(String s);

    protected abstract String ghiNhan(String s);
}

class QuenBuoc extends BadTemplate {
    protected String bienDoi(String s) {
        return s.toUpperCase();
    }

    protected String ghiNhan(String s) {
        return "OK> " + s;
    }

    @Override
    String xuLy(String s) {              // vo tinh bo qua trim + bienDoi + ghiNhan
        return "RAW> " + s;
    }
}

void main() {
    IO.println(new QuenBuoc().xuLy("don hang 42"));
}
RAW> don hang 42
Template method phải là final — đó là hợp đồng "khung này không được thay đổi". Bỏ final là mở đường cho lớp con phá vỡ thứ tự/các bước mà compiler không thể giúp gì. Tương tự, method nội bộ của khung nên private hoặc final để con không "vô tình" hook vào giữa thuật toán.

3.3 Template Method vs Strategy

Cả hai đều tách khung khỏi chi tiết, nhưng cơ chế đối lập nhau. Template method dùng kế thừa (biến thể chọn lúc compile); Strategy dùng composition — giữ một interface và thay implementation lúc runtime. Strategy đã học kỹ ở Polymorphism — mục 8 và SOLID & Patterns — mục 10:

  • Chọn Template Method khi khung các bước là cố định và nhiều biến thể chia sẻ state/code chung: pipeline xử lý dữ liệu, vòng đời servlet, đọc dữ liệu theo template.
  • Chọn Strategy khi muốn đổi thuật toán lúc chạy, tránh cây kế thừa sâu, hoặc thuật toán không cần state chung — đặc biệt khi interface chỉ một method thì lambda là đủ.
  • Hai pattern kết hợp được: khung template method nhận một Strategy cho bước biến đổi. JdbcTemplate là ví dụ: khung quản lý connection/exception, còn RowMapper là callback thay đổi theo từng query.

3.4 Template Method trong JDK và framework

  • java.io.InputStream: step abstract int read() đọc một byte; skeleton read(byte[], int, int) lặp gọi read(), còn skip/available là hook có default. Lớp con chỉ cần cài read() là có ngay hàng loạt method dùng được (có thể override skeleton để tối ưu, ví dụ ByteArrayInputStream).
  • java.util.AbstractList: step get(int) và size() là abstract; indexOf, lastIndexOf, iterator, subList, equals, hashCode đều là template method xây trên hai step đó. Chỉ cần cài get/size là có cả danh sách đọc được:
import java.util.AbstractList;

class BangSo extends AbstractList<Integer> {
    private final int[] data = {10, 20, 30};

    public Integer get(int i) {     // step 1
        return data[i];
    }

    public int size() {             // step 2
        return data.length;
    }
}

void main() {
    BangSo b = new BangSo();
    IO.println(b);                  // AbstractCollection.toString
    IO.println(b.indexOf(20));      // AbstractList.indexOf
    IO.println(b.contains(30));     // AbstractCollection.contains
    IO.println(b.subList(1, 3));    // AbstractList.subList
}

  • jakarta.servlet.http.HttpServlet: service(req, resp) là skeleton phân loại HTTP method rồi gọi doGet/doPost/doPut... — các hook mặc định trả lỗi 405. Bạn chỉ override đúng method mình hỗ trợ. Lưu ý chuyển dịch javax.servlet → jakarta.servlet (Jakarta EE 9+): Tomcat 10+ và Spring Boot 3 dùng jakarta.*, code cũ dùng javax.* sẽ không chạy.
  • Spring JdbcTemplate: execute/query/update giữ khung lấy connection, tạo statement, bắt SQLException, đóng tài nguyên; client truyền RowMapper/PreparedStatementSetter như các bước cắm vào. Đây là template method "lai" callback — vẫn là ví dụ được trích dẫn nhiều nhất khi nói về pattern này trong Java hiện đại.

Góc Node.js — middleware pipeline thay cho template

Node.js không có template method theo nghĩa kế thừa. Thứ tương đương là middleware pipeline (Express/Koa/NestJS) và function composition: khung là thứ tự các hàm, mỗi bước là một hàm nhận (req, next) và gọi next() để sang bước sau. Skeleton không nằm trong class cha mà nằm trong mảng pipeline:

// JavaScript - chi de so sanh, KHONG phai Java
const middleware = [];
function use(fn) { middleware.push(fn); }

use((req, next) => { req.sach = req.raw.trim();            console.log("1. lam sach"); next(); });
use((req, next) => { req.ketQua = req.sach.toUpperCase();  console.log("2. bien doi"); next(); });
use((req, next) => { console.log("3. ghi nhan: CSV> " + req.ketQua); next(); });

function chay(i, req) {
  if (i < middleware.length) middleware[i](req, () => chay(i + 1, req));
}
chay(0, { raw: "  don hang 42  " });

// function composition - skeleton chi con mot bieu thuc ghep ham
const lamSach = (s) => s.trim();
const bienDoi = (s) => s.toUpperCase();
const ghiNhan = (s) => "CSV> " + s;
const xuLy = (s) => ghiNhan(bienDoi(lamSach(s)));
console.log(xuLy("  don hang 42  "));
1. lam sach
2. bien doi
3. ghi nhan: CSV> DON HANG 42
CSV> DON HANG 42

Khác biệt cốt lõi: template method ép thứ tự và bắt buộc điền bước lúc compile-time; middleware chỉ là quy ước runtime — quên gọi next() hoặc đăng ký sai thứ tự thì chương trình vẫn chạy, chỉ sai kết quả. Bù lại, composition linh hoạt hơn: lắp/tháo/gắn điều kiện cho từng bước rất dễ.

Chốt gọn: template method = skeleton final ở cha gọi các bước của con (Hollywood principle) → abstract step để compiler ép điền, hook để tùy chọn đổi → skeleton phải final, nếu không con override và bỏ bước → so với Strategy: kế thừa compile-time vs composition runtime → JDK dùng đầy: InputStream.read, AbstractList.get/size, HttpServlet.service, JdbcTemplate.

4. Interface — hợp đồng thuần khiết Hay hỏi phỏng vấn

Interface chỉ mô tả "làm được gì". Trước Java 8 nó chỉ có method trắng và hằng số; nay có thêm default, static (Java 8) và private (Java 9) — nhưng vẫn không có state instance và không có constructor.

interface Payment { /* hang so + chu ky method */ }

6. default method — tiến hoá interface không phá code cũ Hay hỏi phỏng vấn

Trước Java 8, thêm một method vào interface đang được dùng chung nghĩa là mọi class implement đều gãy compile — không ai dám tiến hoá API. Default method (Java 8) giải quyết đúng bài toán đó: interface cung cấp implementation mặc định, class cũ không cần sửa vẫn chạy.

interface Payment {
    boolean pay(long amount);

    default String bienLai(long amount) {
        return "Bien lai " + amount + " " + currency();

    default String currency() {
        return "VND";

class CardPayment implements Payment {
    public boolean pay(long amount) {
        return true;

JDK dùng default method khắp nơi khi cần tiến hoá:

  • Iterable.forEach — thêm ở Java 8, mọi collection có sẵn forEach mà không class nào phải viết lại.
  • Comparator.thenComparing — thêm chuỗi so sánh cho comparator cũ.
  • Collection.stream / removeIf, Map.getOrDefault / putIfAbsent.
  • SequencedCollection.reversed() (Java 21) — thêm cả họ method mới cho List/Deque mà không phá implementer.

Default method tránh cả hai — đổi lại bạn phải cẩn thận xung đột default (mục 7) và thay đổi hành vi ngầm.

7. Xung đột default method & luật giải quyết Hay hỏi phỏng vấn

Khi một class nhận nhiều interface cùng có default method trùng chữ ký, Java giải quyết theo đúng thứ tự ưu tiên sau (JLS §9.4.1):

  1. Class thắng: method thật trong class (hoặc class cha) luôn thắng default của interface. Lý do: không phá code cũ từ thời trước Java 8.
  2. Interface cụ thể hơn thắng: nếu một interface là con của (extends) interface kia, default của interface con thắng.
  3. Còn lại là lỗi compile: hai default "ngang vai" không ai nhường ai — bạn phải override và chọn bằng tay qua Interface.super.method().

Trường hợp 3 — xung đột, phải override

interface Payment {
    default String status() {
        return "payment";

    default String status() {
        return "refundable";

    @Override
    public String status() {

void main() {
    IO.println(new CardPayment().status());
}

Ngoài ra, xung đột giữa một default và một method abstract trùng chữ ký cũng là lỗi compile — Java bắt bạn xác nhận rõ ràng rằng default đó thật sự đúng hợp đồng.

9. Functional interface & @FunctionalInterface Hay hỏi phỏng vấn

Functional interface là interface có đúng một abstract method (gọi là SAM — Single Abstract Method). Nó là "kiểu" cho lambda và method reference. Annotation @FunctionalInterface là tuỳ chọn, nhưng nên dùng để compiler chặn ngay lúc bạn lỡ thêm abstract method thứ hai.

10. Interface nhỏ — Interface Segregation (ISP) Production

Interface càng nhỏ càng dễ dùng đúng. Nguyên tắc Interface Segregation (chữ I trong SOLID) nói: đừng bắt client phụ thuộc vào method mà nó không dùng. Một "interface béo" như dưới đây là bẫy thiết kế kinh điển:

// FAT INTERFACE - dung nen lam
interface Payment {
    boolean pay(long amount);
    void refund(long amount);
    void inBaoCao();
    void guiEmail();
    void xuatExcel();
}

Mọi cổng thanh toán buộc phải implement cả 5 method dù chỉ cần 1; class nào không hỗ trợ hoàn tiền sẽ ném UnsupportedOperationException — dấu hiệu hợp đồng sai. Cách chữa: tách theo vai mà từng nhóm client thật sự cần, rồi class nào có đủ khả năng thì implements nhiều interface nhỏ:

  • Payment — chỉ pay, dành cho nơi thu tiền.
  • Refundable — chỉ refund, dành cho màn hình hoàn tiền.
  • Reportable — xuất báo cáo, tách hẳn khỏi luồng thanh toán.

Giống hệt JDK: List không gộp luôn khả năng truy cập ngẫu nhiên — thứ đó là interface riêng RandomAccess (marker). Đọc sâu về SOLID và pattern tại 2.8 SOLID & design patterns.

  1. Các implementation chia sẻ state hoặc code chung và quan hệ is-a rõ → abstract class.

  3. Cần cả hai → interface cho hợp đồng + abstract base class cho code chung (combo dưới đây).

12. Marker interface & sealed interface Junior+

Marker interface — interface không có method nào

Marker interface chỉ tồn tại để đánh dấu khả năng, không có method nào để implement. Ba ví dụ JDK bạn gặp nhiều nhất:

  • java.io.Serializable — "được phép serialize". Không có method nào; nếu quên đánh dấu, ghi object ra file sẽ ném NotSerializableException.
  • Cloneable — "được phép gọi clone()". Lạ lùng là method clone() nằm ở Object (protected), không nằm trong interface; thiếu marker là CloneNotSupportedException.
  • java.util.RandomAccess — "cấu trúc này truy cập theo index nhanh" (ArrayList có, LinkedList không).

    IO.println("abc" instanceof java.io.Serializable);

    IO.println(new Object() instanceof java.io.Serializable);

Nhiều marker cổ điển ngày nay được thay bằng annotation (@Deprecated, @FunctionalInterface) vì annotation gắn được metadata và không xâm chiếm danh sách interface cha. Chỉ tạo marker khi thư viện cố tình hỏi instanceof.

13. Production patterns — interface ở biên hệ thống Production

Trong code production, interface được dùng nhiều nhất ở biên hệ thống: nơi code nghiệp vụ nói chuyện với thế giới ngoài (HTTP, DB, email...). Nghiệp vụ chỉ biết hợp đồng; implementation thật (gọi mạng) nằm ở lớp ngoài. Nhờ vậy unit test có thể thay bằng fake implementation trong vài dòng — đặc biệt khi interface là functional:

interface Payment {
    boolean charge(long amount);
}

void thanhToan(Payment gateway, long amount) {
    if (gateway.charge(amount)) {
        IO.println("Thanh cong " + amount);
    } else {
        IO.println("That bai " + amount);
    }
}

void main() {
    Payment realGateway = amount -> {
        IO.println("[HTTP] goi cong thanh toan that " + amount);
        return true;
    };
    Payment fakeGateway = amount -> true;
    thanhToan(realGateway, 100_000);
    thanhToan(fakeGateway, 250_000);
}
[HTTP] goi cong thanh toan that 100000
Thanh cong 100000
Thanh cong 250000

Ba mẫu bạn sẽ gặp hằng ngày:

  • Port & adapter (hexagonal): nghiệp vụ định nghĩa Payment; adapter gọi cổng thanh toán thật implement nó. Đổi nhà cung cấp chỉ cần viết adapter mới.
  • Repository: interface OrderRepository nằm ở tầng nghiệp vụ; implementation JPA/DB nằm ở tầng hạ tầng. Test dùng implementation in-memory.
  • Dependency Injection: Spring tìm bean theo kiểu. @Service class CardPaymentService implements PaymentService được inject vào nơi cần PaymentService; trong test, Mockito thay bằng mock/proxy cùng interface.
Đây là Dependency Inversion Principle (chữ D trong SOLID): module cấp cao không phụ thuộc module cấp thấp, cả hai phụ thuộc abstraction. Abstract class ít dùng ở biên vì nó kéo theo state/code chung — thứ adapter không cần. Xem thêm 2.8 SOLID & design patterns.

15. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Abstract class và interface khác nhau ở những điểm cốt lõi nào?
Abstract class là class dở dang: có instance field, constructor, method thường, khối khởi tạo; đơn kế thừa; quan hệ is-a; abstract method không bắt buộc phải có. Interface là hợp đồng: không state instance, không constructor; đa kế thừa "vai"; method ngầm public abstract; từ Java 8/9 có thêm default/static/private; quan hệ can-do. Từ Java 8 ranh giới mờ dần nhưng khác biệt gốc vẫn là state + constructor: interface vĩnh viễn không có.
Câu 2. Khi nào chọn abstract class, khi nào chọn interface?
Chọn abstract class khi các subclass chia sẻ state/code chung thật sự, cần constructor ép khởi tạo, hoặc cần template method với vài bước mở cho con. Chọn interface khi chỉ cần hợp đồng hành vi cho nhiều loại implementation không liên quan, cần một object nhận nhiều vai, hoặc cần điểm thay thế để test/mock. Cần cả hai thì kết hợp: interface cho hợp đồng + abstract base cho code chung (mục 11).
Câu 3. Abstract class có constructor không? Có thì để làm gì?
Có. Constructor của abstract class chạy khi subclass được khởi tạo, qua chuỗi super(...), dùng để khởi tạo field chung và validate tham số. Bạn không new trực tiếp được abstract class, nên constructor thường để protected (hoặc package-private) thay vì public. Interface thì ngược lại: không có constructor, kể cả private.
Câu 4. Abstract class có bắt buộc phải có abstract method không?
Không. Một abstract class hoàn toàn có thể có 0 abstract method; nó vẫn hợp lệ và vẫn không new được. Người ta dùng trường hợp này để chặn khởi tạo trực tiếp và gom code chung. Chiều ngược lại mới bị luật: class chứa abstract method bắt buộc phải khai báo abstract, nếu không sẽ lỗi "is not abstract and does not override abstract method".
Câu 5. Interface có field không? Bản chất field trong interface là gì?
Có, nhưng mọi field đều ngầm là public static final và bắt buộc khởi tạo ngay khi khai báo. Đây là hằng số dùng chung, không phải biến instance: mọi object của mọi class implement đều thấy cùng một giá trị, và không gán lại được (cannot assign a value to static final variable). Vì thế interface không thể giữ state.
Câu 6. Interface có constructor không? Vì sao?
Không. Constructor tồn tại để khởi tạo state instance, mà interface không có state instance — nên ngôn ngữ cấm luôn constructor (khai báo Payment() { } trong interface là lỗi compiler). Object của interface không tồn tại; chỉ object của class implement interface tồn tại, và class đó tự lo constructor của mình.
Câu 7. Có new được abstract class hay interface không?
Không — cả hai đều lỗi compile ("is abstract; cannot be instantiated"). Nhưng bạn có thể viết new Payment() { ... } với anonymous class: đó thực chất là tạo object của một class con vô danh implement interface, không phải tạo interface. Với functional interface, lambda Payment p = amount -> true; cũng tạo ra một implementation như vậy.
Câu 8. Kết hợp abstract với final, private, static được không?
abstract final class là lỗi: "illegal combination of modifiers: abstract and final" — final cấm kế thừa, abstract sống nhờ kế thừa. Tương tự, abstract method không được private (không ai override được) và không được static (không gắn instance, không override theo đa hình). Ngược lại, một method thường trong abstract class hoàn toàn có thể final để chặn subclass override chính nó.
Câu 9. Vì sao Java cho đa implement interface nhưng không cho đa kế thừa class?
Vì state. Hai class cha đều có field instance sẽ nảy sinh diamond problem: object con chứa một hay hai bản của field trùng tên? Java cắt vấn đề bằng đơn kế thừa class. Interface không mang state instance (field là static final), nên đa implement an toàn; và nếu Java 8+ đưa ra diamond về default method, JLS có luật giải quyết dứt khoát (class thắng → interface cụ thể hơn thắng → lỗi compile), buộc lập trình viên chọn tường minh thay vì đoán mò như C++.
Câu 10. Method trong interface mặc định có modifier gì? Khai báo được những loại method nào?
Method không body ngầm là public abstract; field ngầm là public static final; nested type ngầm là public static. Từ Java 8 có thêm default và static; từ Java 9 có private và private static. Interface không có protected, không constructor, và không được có khối static { }. Khi implement method abstract, class con buộc ghi public.

Junior+

Câu 11. default method sinh ra để giải quyết vấn đề gì?
Để tiến hoá interface mà không phá implementation cũ. Trước Java 8, thêm method trắng vào interface đang dùng rộng rãi là phá vỡ mọi class implement. Default method cho interface một implementation mặc định, nên class cũ không cần sửa. JDK dùng nó ở Iterable.forEach, Comparator.thenComparing, Map.getOrDefault, SequencedCollection.reversed() (Java 21). Đây cũng là lý do interface từ Java 8 có thể chứa hành vi thật, làm ranh giới với abstract class mờ đi.
Câu 12. Xung đột default method được giải quyết theo thứ tự nào?
Ba bước, bước trước thắng: (1) class thắng interface — method trong class hoặc class cha override default; (2) nếu các default đến từ interface có quan hệ cha-con, interface con (cụ thể hơn) thắng; (3) nếu các default "ngang vai" không ai thắng ai, lỗi compile "inherits unrelated defaults". Muốn giải quyết xung đột ngang vai: override method đó trong class rồi tự chọn bằng InterfaceA.super.method() và/hoặc InterfaceB.super.method().
Câu 13. Interface.super.method() dùng khi nào? Điều kiện gì?
Dùng khi class override một method đang xung đột default (hoặc muốn tái dùng có chủ đích) và cần gọi lại implementation default của một interface cụ thể. Điều kiện: interface được gọi phải là direct superinterface của class đang viết (hoặc của interface đang viết), và method đó phải là default của chính interface này. Cú pháp đầy đủ là Payment.super.status(); không gọi được qualified super tới interface "ông nội" gián tiếp.
Câu 14. static method trong interface có được kế thừa không?
Không. Static method của interface không được class implement kế thừa, cũng không được interface con kế thừa — phải gọi qua tên interface: Payment.cash(). Gọi CardPayment.cash() là lỗi "cannot find symbol". Lý do: static gắn với kiểu khai báo chứ không tham gia đa hình; JLS khẳng định interface không thừa kế private/static method từ superinterface. Static method thường dùng làm factory/tiện ích gắn tên interface.
Câu 15. private method trong interface (Java 9) để làm gì?
Để chia sẻ code giữa các default/static method mà không biến helper thành API công khai. Trước Java 9, muốn tái sử dụng logic giữa hai default method bạn phải tạo một static helper public (ô nhiễm hợp đồng) hoặc class utility ngoài. Private method (và private static) chỉ code bên trong interface gọi được, không kế thừa, không override. Đây là chi tiết nhỏ nhưng hay được hỏi để phân biệt người theo dõi Java hiện đại.
Câu 16. Marker interface là gì? Cho ví dụ và nhược điểm.
Là interface không có method nào, chỉ dùng để đánh dấu khả năng. Ví dụ: Serializable (được serialize; thiếu nó ném NotSerializableException), Cloneable (được gọi Object.clone(), nếu không ném CloneNotSupportedException), RandomAccess (List truy cập index nhanh). Nhược điểm: không có method nào nên compiler không kiểm tra được gì về hành vi; class vẫn có thể "đánh dấu sai" và lỗi chỉ nổ lúc chạy. Ngày nay metadata thường dùng annotation; chỉ tạo marker khi có code chủ động instanceof nó.
Câu 17. Sealed interface là gì? Lợi ích khi kết hợp switch?
Sealed (Java 17) giới hạn interface/class chỉ được phép có đúng các subtype ghi trong permits. Vì compiler biết hết subtype, switch pattern matching trên nó trở nên exhaustive: không cần default, và khi thêm subtype mới mà quên nhánh switch, compiler báo "the switch expression does not cover all possible input values". Subtype phải là final, sealed hoặc non-sealed; record/enum hay dùng vì mặc định final. Đây là cách mô hình hoá union type an toàn của Java.
Câu 18. Functional interface là gì? @FunctionalInterface có bắt buộc không?
Là interface có đúng một abstract method (SAM) — nhờ đó có thể gán lambda hoặc method reference. Annotation @FunctionalInterface không bắt buộc: interface một abstract method vẫn dùng được lambda dù không ghi. Nhưng nên ghi để compiler chặn khi lỡ thêm abstract method thứ hai và để tài liệu hoá ý định. Default/static/private method, cùng method override-equivalent với public method của Object (như equals), không tính vào SAM.

Nâng cao

Câu 19. Interface extends interface được không? Abstract class implements interface thì sao?
Interface extends được nhiều interface cùng lúc: interface A extends B, C. Class thì implements nhiều interface nhưng extends tối đa một class. Khi abstract class implements một interface, nó không buộc implement hết abstract method — "món nợ" được chuyển cho class con cụ thể; nếu class con cũng không implement thì chính nó phải abstract. Đây là cách xây dựng abstract base class implements sẵn hợp đồng.
Câu 20. Thêm method mới vào interface đang được implement rộng rãi thì chuyện gì xảy ra?
Nếu method abstract: class cũ đã biên dịch vẫn load được (tương thích nhị phân), nhưng nếu gọi method mới trên implementation cũ sẽ ném AbstractMethodError lúc chạy; còn recompile thì lỗi compile "does not override abstract method". Nếu method default: an toàn hơn — implementer cũ chạy bình thường với hành vi mặc định. Nhưng coi chừng: class implement nhiều interface có thể vướng xung đột default sau này, và hành vi ngầm thay đổi (ví dụ method mới được gọi ở đâu đó từ trước). Vì vậy thiết kế API công khai cần tính trước chuyện versioning.
Câu 21. Vì sao không nên dùng interface chỉ để chứa hằng số (constant interface)?
Vì nó lạm dụng interface vào việc không phải hợp đồng hành vi: mọi class implement sẽ thừa hưởng hằng số mà không liên quan gì tới vai trò của mình, tên hằng "chảy" vào namespace của class (ô nhiễm), lộ chi tiết implementation vào API, và làm rối công cụ phân tích. Cách thay thế: hằng số gắn với enum (nhóm giá trị đóng), class utility với private constructor, hoặc static import khi thật sự cần. Effective Java gọi đây là constant interface antipattern.
Câu 22. Interface có thể khai báo default cho toString/equals/hashCode không?
Không — đó là lỗi compile: "default method toString in interface Payment overrides a member of java.lang.Object". Mọi class đã thừa hưởng implementation của Object, nên default đó sẽ không bao giờ được dùng và JLS cấm để tránh nhầm lẫn. Tuy vậy interface được phép khai báo abstract method trùng chữ ký với public method của Object (ví dụ boolean equals(Object o);) — nó không tính vào SAM nên interface vẫn có thể là functional. Đây là nền tảng để Comparator vẫn là functional interface.

In ra The 4242 rồi Chuyen khoan VCB. Switch không cần default vì sealed Payment chỉ có đúng hai subtype và compiler biết hết. Nếu mai thêm record MomoPayment(...) implements Payment mà quên thêm nhánh, compiler báo "does not cover all possible input values" ngay — đó là giá trị lớn nhất của sealed.

// Yeu cau: he thong thanh toan co nhieu kieu (the, chuyen khoan),
// moi kieu phai pay duoc; dong thoi moi giao dich deu di qua quy trinh:
// lam sach -> bien doi -> ghi nhan (khung co dinh).
// Hay chon abstract class / interface va viet code.

Chọn interface Payment cho hợp đồng "pay được" (can-do, nhiều implementation) và abstract class DataProcessor cho template method "làm sạch → biến đổi → ghi nhận" (is-a, code chung). Abstract class implements luôn interface để class con có cả hai. Kết quả:

interface Payment {
    boolean pay(long amount);

    default String currency() {
        return "VND";
    }
}

abstract class DataProcessor implements Payment {
    final String step(String raw) {
        return decorate(clean(raw));
    }

    private String clean(String s) {
        return s.trim();
    }

    protected abstract String decorate(String s);
}

class CardPayment extends DataProcessor {
    public boolean pay(long amount) {
        return amount > 0;
    }

    protected String decorate(String s) {
        return "CARD> " + s;
    }
}

void main() {
    CardPayment c = new CardPayment();
    IO.println(c.step("  pay now  "));
    IO.println(c.pay(10_000));
    IO.println(c.currency());
}

Output chạy thật: CARD> pay now, true, VND. Lý do không chọn abstract class cho Payment: nhiều loại thanh toán không chia sẻ state, và interface giữ slot extends cho abstract base. Lý do không chọn interface cho DataProcessor: cần private helper + method final khoá khung thuật toán — interface không có final method được.

Checklist tự đánh giá trước phỏng vấn

  • Trả lời trôi chảy câu "abstract class khác interface thế nào" trong 60 giây, kèm ví dụ.
  • Nêu được tiêu chí chọn: state/constructor/code chung → abstract; hợp đồng/đa vai → interface.
  • Giải thích được vì sao interface không có constructor và field là public static final.
  • Giải thích được vì sao Java cho đa implement interface nhưng không cho đa kế thừa class.
  • Thuộc 3 bước giải quyết xung đột default method và viết được Interface.super.m().
  • Phân biệt default/static/private method trong interface: ai gọi được, có kế thừa không.
  • Viết được một functional interface + gán lambda, và giải thích @FunctionalInterface có bắt buộc không.
  • Giải thích marker interface và nêu 2 ví dụ JDK kèm nhược điểm.
  • Viết được sealed interface + switch không cần default, và biết lỗi khi thiếu nhánh.
  • Nhận diện và sửa 4 lỗi compiler: new abstract, gán field interface, weaker access, unrelated defaults.
  • Biết cách dùng interface ở biên hệ thống: mock/fake cho unit test, DI trong Spring.
