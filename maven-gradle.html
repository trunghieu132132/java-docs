Maven & Gradle — build & quản lý dependency

Từ đầu khóa tới giờ bạn chạy code bằng java TenFile.java và tự tải từng thư viện bằng tay. Dự án thật không như vậy: hàng chục thư viện, hàng trăm file, nhiều người cùng sửa, CI chạy tự động. Build tool — Maven và Gradle — biến code rời rạc thành một project build được ở mọi máy, tự tải dependency, chạy test và đóng gói. Đây là chủ đề 4.3 trong lộ trình: project "quản lý đơn hàng" chính thức lên Maven trước khi học JUnit ở 4.4 Testing.

1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Build tool là gì? Là công cụ tự động hoá toàn bộ vòng đời của project: biên dịch, chạy test, đóng gói (.jar/.war), quản lý thư viện (tải cả thư viện của thư viện), và phát hành artifact. Trước khi có nó, bạn phải gõ javac từng file, tự tải jar, tự set -cp — làm vài lần là hết muốn làm. Maven ra đời 2004 và trở thành chuẩn; Gradle (2007) nhanh hơn, linh hoạt hơn, được Android và nhiều startup dùng. Cả hai đọc chung kho Maven Central.

Mức độ bắt buộc của chủ đề 4.3 (phỏng vấn: trung bình · production: bắt buộc):

  • Phải làm được — đọc và viết pom.xml có dependency + scope đúng; chạy mvn clean package, mvn test, mvn install; đọc mvn dependency:tree; dùng wrapper ./mvnw; đọc một build.gradle đơn giản.
  • Phải hiểu — dependency được resolve thế nào (transitive, mediation); scope ảnh hưởng classpath và file đóng gói ra sao; lifecycle gồm những phase nào; BOM/dependencyManagement giải quyết gì; vì sao lệch version gây lỗi runtime chứ không phải lỗi compile.
  • Nhận biết — multi-module, profile, deploy lên Nexus nội bộ, Gradle task tự viết, Maven 4 đang tới.

Cách học hiệu quả nhất:

  1. Đọc mục 2–4 rồi tự tay tạo project Maven nhỏ cho "quản lý đơn hàng" đã học ở GĐ1–3 (chỉ cần 2–3 class).
  2. Chạy từng lệnh mvn ... và quan sát thư mục target/ thay đổi — build tool học bằng tay, không học bằng mắt.
  3. Làm Bài tập (đọc pom, chọn scope, sửa conflict) trước khi mở đáp án.
  4. Ôn Cheat sheet trước buổi phỏng vấn.
  5. Câu lạ tra ở Interview Q&A; nếu công ty dùng Maven vẫn nên đọc lướt Gradle vì nhiều dự án mới chuyển sang.
Maven hay Gradle trước? Học Maven trước: XML dài nhưng tường minh, doanh nghiệp/ngân hàng và tài liệu Spring Boot ở Việt Nam dùng nhiều. Nắm khái niệm Maven (dependency, scope, lifecycle) rồi chuyển sang Gradle sẽ thấy mọi thứ ánh xạ gần 1-1 (mục 8 và 10).

3. pom.xml — khai báo project & dependency Junior+

pom.xml là Project Object Model — nguồn sự thật duy nhất về project: nó là gì (toạ độ GAV), dùng thư viện gì, build thế nào. File XML nhìn dài nhưng thực chất chỉ có mấy khối:

<project>                            # phan tu goc, kem xmlns
 ├── modelVersion                    # luon la 4.0.0 - phien ban schema pom
 ├── parent                          # (tuy chon) ke thua cau hinh tu pom cha
 ├── groupId / artifactId / version  # GAV - toa do cua project
 ├── packaging                       # jar (mac dinh) | war | pom
 ├── properties                      # bien ${...} dung lai nhieu noi
 ├── dependencyManagement            # ghim version, KHONG them dependency
 ├── dependencies                    # thu vien that su dung
 └── build/plugins                   # plugin + cau hinh build

GAV (groupId - artifactId - version) là "địa chỉ" của artifact trong mọi repository. Trùng GAV là trùng artifact — đây là lý do không được sửa nội dung một version đã phát hành:

  • groupId — tổ chức/dự án mẹ, viết ngược domain: vn.hocjava, org.springframework.boot.
  • artifactId — tên project/module: quan-ly-don-hang, spring-boot-starter-web.
  • version — 1.0-SNAPSHOT (đang phát triển) hoặc 1.0.0 (release).
  • packaging — jar (thư viện/app thường), war (deploy Tomcat), pom (project cha/aggregator, mục 7).

Dependency & scope

Scope quyết định dependency có mặt ở giai đoạn nào và có bị đóng gói vào artifact không. Chọn sai scope là lỗi production kinh điển:

providedCóCóKhôngKhôngjakarta.servlet-api — Tomcat cung cấp lúc chạy

Project "quản lý đơn hàng" với JUnit 5 (test) + SLF4J/Logback (log) — mẫu pom nên có trong đầu:

Vì sao gom version vào <properties>? Để nâng cấp một chỗ. Nhiều dependency cùng họ (Spring, Jackson...) nên dùng chung một property hoặc BOM. Hardcode version rải rác 30 dòng pom là nguồn gốc của lệch version (mục 12). Mẹo nhỏ: maven.compiler.release=25 là cách gọn nhất để compiler plugin dùng --release 25; project.build.sourceEncoding=UTF-8 tránh lỗi font tiếng Việt.

Plugins — phần "động cơ" của build

Maven bản thân chỉ là bộ khung; mọi việc thật do plugin làm: maven-compiler-plugin gọi javac, maven-surefire-plugin chạy test, maven-jar-plugin đóng gói... Bạn khai báo plugin trong <build><plugins> khi cần đổi cấu hình (ví dụ ép Java 25), hoặc gọi goal trực tiếp trên dòng lệnh (mvn dependency:tree) mà không cần khai báo trong pom.

4. Lifecycle & các lệnh Maven Hay hỏi phỏng vấn

Maven định nghĩa sẵn các bước build gọi là phase. Gọi một phase, Maven chạy lần lượt mọi phase đứng trước nó trong cùng lifecycle. Có 3 lifecycle: clean, default (build chính) và site (tài liệu). Chuỗi phase chính của default lifecycle:

validate → compile → test → package → verify → install → deploy

Plugin vs dependency & plugin goal

Phân biệt để trả lời phỏng vấn: dependency là thư viện được đưa vào classpath của code bạn (compile/runtime/test). Plugin là công cụ được Maven thực thi trong lúc build, chạy trong classloader riêng; nó có goal — đơn vị công việc nhỏ nhất. Phase chỉ là mốc, plugin goal mới là việc thật:

  • mvn clean package — chạy theo phase (đúng quy trình).
  • mvn compiler:compile, mvn dependency:tree — gọi thẳng plugin:goal (gọi tắt, không qua lifecycle).

Maven Wrapper — ./mvnw vì sao nên dùng

Wrapper gồm script mvnw (macOS/Linux) + mvnw.cmd (Windows) + thư mục .mvn/wrapper/ chứa version Maven và URL tải. Ai clone project chỉ cần chạy ./mvnw — không cần cài Maven, và luôn dùng đúng version mà team đã chọn:

$ mvn wrapper:wrapper -Dmaven=3.9.9
$ ./mvnw -v                 # tai + dung Maven 3.9.9 trong .mvn/wrapper
$ ./mvnw clean verify       # thay hon han cho 'mvn clean verify'
Vì sao quan trọng? Máy bạn Maven 3.6, CI Maven 3.9, đồng nghiệp Maven 3.8 — plugin mặc định và cách resolve có thể khác nhau, dẫn tới "máy tôi chạy được". Wrapper ghim version Maven theo project, commit lên git, ai clone cũng giống nhau. Gradle có cơ chế y hệt: ./gradlew.

5. Dependency & xung đột phiên bản Hay hỏi phỏng vấn Production

Đây là phần "đau đầu" nhất của build tool và cũng là câu hỏi phỏng vấn yêu thích. Hiểu bản chất trước: Maven không chỉ tải thư viện bạn khai báo, nó tải cả thư viện của thư viện — gọi là transitive dependency.

Scope của transitive dependency

Không phải mọi transitive đều giống nhau — scope của nó phụ thuộc scope của dependency trực tiếp kéo nó về. Bảng dưới theo tài liệu Maven (hàng = scope dependency bạn khai báo, cột = scope mà thư viện đó khai báo cho dependency con):

Bạn khai báo ↓ / nó khai báo →compileruntimeprovidedtest

Đọc bảng này giải thích được nhiều thứ: JUnit (scope test) không bao giờ lọt vào jar production; provided không truyền tiếp; dependency runtime của thư viện thành runtime của bạn.

Xung đột phiên bản — Maven chọn bản nào?

Hai thư viện khác nhau kéo về hai version của cùng một artifact (rất hay xảy ra với Guava, SLF4J, Jackson...). Maven giải quyết bằng nearest definition (a.k.a. mediation): bản gần project nhất thắng — độ sâu trên cây dependency nhỏ hơn. Nếu hai bản cùng độ sâu, bản khai báo trước trong pom thắng. Lưu ý: Maven không chọn bản mới nhất theo mặc định:

[INFO] --- dependency:3.8.1:tree (default-cli) @ quan-ly-don-hang ---
[INFO] vn.hocjava:quan-ly-don-hang:jar:1.0-SNAPSHOT
[INFO] +- com.example:company-utils:jar:1.0:compile
[INFO] |  \- org.slf4j:slf4j-api:jar:1.7.36:compile
[INFO] +- org.slf4j:slf4j-api:jar:2.0.16:compile
[INFO] \- ch.qos.logback:logback-classic:jar:1.5.16:runtime
[INFO]    \- org.slf4j:slf4j-api:jar:2.0.16:runtime
[INFO] ------------------------------------------------------------------------
[INFO] BUILD SUCCESS
[INFO] ------------------------------------------------------------------------

Ở đây SLF4J 2.0.16 (khai báo trực tiếp, độ sâu 1) thắng 1.7.36 (đi qua company-utils, độ sâu 2) — dù cả hai đều nằm trên cây. Gradle mặc định khác hẳn: chọn version cao nhất (highest version wins). Cùng một project, hai build tool có thể ra classpath khác nhau!

Exclusions — loại bỏ có chủ đích

Khi biết chắc một transitive không cần (hoặc kéo version cũ làm hại), loại nó ngay tại dependency cha:

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <version>4.0.0</version>
  <exclusions>
    <!-- bo logging mac dinh de tu chon implementation khac -->
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-logging</artifactId>
    </exclusion>
  </exclusions>
</dependency>
Exclusion là "dao mổ": loại nhầm có thể gây NoClassDefFoundError lúc chạy. Chỉ loại khi biết chắc thư viện đó không cần, và ghi comment giải thích ngay trong pom.

dependencyManagement & BOM — ghim version một chỗ

dependencyManagement khai báo version/scope "mặc định" cho dependency nhưng không thêm nó vào project — con/chính project chỉ cần khai báo groupId + artifactId. BOM (Bill of Materials) là một pom chỉ chứa dependencyManagement của cả bộ thư viện, import bằng type=pom + scope=import:

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.junit</groupId>
      <artifactId>junit-bom</artifactId>
      <version>5.14.4</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <!-- khong can version: lay tu BOM -->
  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
  </dependency>
</dependencies>

Spring Boot cũng phát hành BOM (spring-boot-dependencies) để mọi starter tương thích nhau mà không cần ghi version. Nếu bạn khai báo dependency không version mà không được quản lý bởi BOM/dependencyManagement, Maven dừng build ngay từ validate:

[ERROR] 'dependencies.dependency.version' for org.slf4j:slf4j-api:jar is missing. @ line 14, column 15

Đọc mvn dependency:tree

Đây là công cụ số 1 để gỡ rối dependency. Cây in theo thứ tự gốc → lá; mỗi dòng là groupId:artifactId:jar:version:scope:

[INFO] vn.hocjava:quan-ly-don-hang:jar:1.0-SNAPSHOT
[INFO] +- org.junit.jupiter:junit-jupiter:jar:5.14.4:test
[INFO] |  \- org.junit.jupiter:junit-jupiter-api:jar:5.14.4:test
[INFO] +- org.slf4j:slf4j-api:jar:2.0.16:compile
[INFO] \- ch.qos.logback:logback-classic:jar:1.5.16:runtime
[INFO]    +- ch.qos.logback:logback-core:jar:1.5.16:runtime
[INFO]    \- org.slf4j:slf4j-api:jar:2.0.16:runtime
  • +- là nhánh còn nữa, \- là nhánh cuối; đếm dấu | và khoảng cách để biết độ sâu.
  • Cùng artifact xuất hiện nhiều nhánh với version khác nhau → Maven chỉ dùng một bản (nearest). Muốn thấy các bản bị loại, thêm -Dverbose (tùy version plugin).
  • Lọc cho gọn: mvn dependency:tree -Dincludes=org.slf4j hoặc -Dincludes=com.google.guava:guava.
  • Muốn xem danh sách classpath đã resolve (không phải cây): mvn dependency:list; hoặc mvn help:effective-pom để xem pom sau khi merge BOM/parent.

Lỗi runtime do lệch version — vì sao compile qua mà chạy vẫn chết

Lúc compile, javac dùng một version của thư viện; lúc chạy, JVM có thể nạp version khác. Class/method không khớp chỉ nổ khi chạm tới, nên build xanh mà production vẫn sập. Ba lỗi phải phân biệt:

LỗiNghĩaNguyên nhân thường gặp
NoSuchMethodErrorClass có, nhưng bản đang chạy thiếu method đã compileHai version của cùng thư viện; bản chạy cũ hơn bản compile
NoClassDefFoundErrorClass từng có lúc compile, lúc chạy không tìm thấy (hoặc khởi tạo tĩnh đã fail trước đó)Thiếu jar do scope sai, exclusion quá tay, đóng gói thiếu dependency
ClassNotFoundExceptionCode chủ động load class theo tên (Class.forName, classloader) mà không thấyDriver DB khai provided thay vì runtime; thiếu jar trong fat jar
Quy trình gỡ conflict chuẩn: (1) mvn dependency:tree -Dverbose tìm artifact và version thực tế; (2) tìm thư viện nào kéo bản độc hại; (3) ưu tiên ghim version đúng bằng dependencyManagement (một chỗ, ảnh hưởng cả cây) hơn là exclusion lẻ tẻ; (4) chạy lại test + kiểm tra java -jar. Ghi nhớ: fix dependency không phải sửa code — sửa classpath.

7. Multi-module (mức nhận biết) Junior+

Khi project lớn dần, bạn tách thành nhiều module: order-core (domain + service), order-web (REST API), order-cli... Một parent pom đóng vai trò vừa là cha (chia sẻ cấu hình/version) vừa là aggregator (liệt kê module con):

<!-- pom.xml o thu muc goc: packaging=pom -->
<groupId>vn.hocjava</groupId>
<artifactId>quan-ly-don-hang</artifactId>
<version>1.0-SNAPSHOT</version>
<packaging>pom</packaging>

<modules>
  <module>order-core</module>
  <module>order-web</module>
</modules>
<!-- order-web/pom.xml: ke thua parent, phu thuoc module noi bo -->
<parent>
  <groupId>vn.hocjava</groupId>
  <artifactId>quan-ly-don-hang</artifactId>
  <version>1.0-SNAPSHOT</version>
</parent>

<artifactId>order-web</artifactId>

<dependencies>
  <dependency>
    <groupId>vn.hocjava</groupId>
    <artifactId>order-core</artifactId>
    <version>${project.version}</version>
  </dependency>
</dependencies>
  • Build từ thư mục gốc: Maven dựng reactor — sắp thứ tự module theo quan hệ phụ thuộc rồi build lần lượt.
  • Build chọn lọc: mvn -pl order-web -am package (-pl chọn module, -am build kèm các module nó phụ thuộc).
  • Module nội bộ dùng ${project.version} — version được quản lý ở parent.
Khi nào tách? Khi có code dùng chung giữa nhiều app/service, khi build một khối quá chậm, hoặc khi ranh giới team rõ ràng. Với project học 3–10 class thì một module là đủ — đừng tách sớm.

8. Gradle cơ bản Junior+

Gradle dùng script thay cho XML. Bạn cần biết 3 file: settings.gradle(.kts) (tên project + module), build.gradle(.kts) (cấu hình build), và thư mục gradle/wrapper/. Script là code Groovy hoặc Kotlin — mỗi dòng là một lời gọi API thật:

9. Gradle: task, Kotlin DSL & wrapper Production

Đơn vị công việc trong Gradle là task (tương tự goal của Maven plugin, nhưng bạn tự viết được bằng vài dòng). Ví dụ task in thông tin build:

tasks.register('inThongTin') {
    doLast {
        println "Project : ${project.name} ${project.version}"
        println "Gradle  : ${gradle.gradleVersion}"
        println "Java    : ${System.getProperty('java.version')}"
    }
}
$ ./gradlew inThongTin

> Task :inThongTin
Project : quan-ly-don-hang 1.0-SNAPSHOT
Gradle  : 8.11.1
Java    : 25

BUILD SUCCESSFUL in 1s
1 actionable task: 1 executed

Hai phase của một build Gradle cần phân biệt:

  • Configuration phase — Gradle đọc và "dựng" toàn bộ task graph (code trong build.gradle chạy ở đây).
  • Execution phase — task được thực thi; code trong doLast chạy lúc này.

Đặt logic vào doLast (hoặc task action) là quy tắc số 1 khi viết task; code nằm ngoài sẽ chạy mỗi lần cấu hình, kể cả khi bạn chỉ gõ ./gradlew tasks. Gradle còn có daemon (tiến trình nền giữ JVM ấm) và build cache — lý do build lần 2 nhanh hơn hẳn lần 1.

Cùng nội dung trên viết bằng Kotlin DSL (build.gradle.kts) — type-safe, được IDE gợi ý tốt, là mặc định của project mới:

plugins {
    java
    application
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("org.slf4j:slf4j-api:2.0.16")
    runtimeOnly("ch.qos.logback:logback-classic:1.5.16")
    testImplementation("org.junit.jupiter:junit-jupiter:5.14.4")
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }
}

tasks.test {
    useJUnitPlatform()
}

Wrapper của Gradle cũng giống Maven: tạo bằng gradle wrapper --gradle-version 8.11.1, sinh ra gradlew, gradlew.bat, gradle/wrapper/gradle-wrapper.jar + .properties. Tất cả các file này nên commit — trừ khi công ty có quy định riêng. Khi gỡ conflict trên Gradle, dùng:

$ ./gradlew dependencyInsight --dependency slf4j --configuration runtimeClasspath
$ ./gradlew dependencies --configuration runtimeClasspath
Góc Node.js: ./gradlew dependencies giống npm ls — cả hai cho xem cây tại sao một package có mặt, chỉ khác Gradle chia theo configuration (compile/runtime/test) còn npm chia theo dependency/devDependency.

11. Maven trong đời sống: IDE, CI, Spring Boot Production

11.1 IntelliJ IDEA

  • Mở thư mục có pom.xml → chọn "Open as Project"/"Maven project"; IDE tự đọc pom và tải dependency (dùng local repo chung).
  • Sau khi sửa pom, bấm nút Reload Maven Project (biểu tượng chữ M) — không reload thì IDE vẫn dùng classpath cũ dù dòng lệnh đã thấy dependency mới.
  • Tab Maven cho phép chạy lifecycle trực tiếp: nhấn đúp clean, package...; nên cấu hình IDE dùng wrapper (Settings → Build Tools → Maven → Maven home: chọn "Use Maven wrapper") để khớp CI.

11.2 CI — GitHub Actions chạy mvn

Pipeline tối thiểu cho Java 25 + Maven dùng wrapper (nhớ cache để không tải lại toàn bộ dependency mỗi lần chạy):

name: build

on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '25'
          cache: maven
      - run: ./mvnw --batch-mode --no-transfer-progress clean verify
  • --batch-mode — chế độ CI: không màu mè, log sạch, không chờ tương tác.
  • --no-transfer-progress — bỏ dòng tiến trình tải, log gọn (viết tắt -ntp).
  • clean verify — build sạch + test + kiểm tra; CI nên dùng verify thay vì package.
  • Vì dùng ./mvnw, CI không cần cài Maven — chỉ cần JDK do setup-java cung cấp.

11.3 Spring Boot parent & starter

Project Spring Boot thực tế bắt đầu bằng một parent đặc biệt: nó mang sẵn BOM (quản lý version của cả trăm thư viện), plugin và cấu hình mặc định. Vì thế các starter không cần version:

<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>4.0.0</version>
  <relativePath/>
</parent>

<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
</dependencies>

Version của parent minh hoạ ở đây — khi làm thật hãy lấy bản mới nhất từ start.spring.io. Project học của khóa (GĐ4) chỉ cần parent này + starter + plugin.

11.4 Fat jar / executable jar

mvn package mặc định tạo thin jar: chỉ chứa class của bạn, không chứa dependency — chạy java -jar sẽ lỗi vì thiếu classpath. Production cần fat jar (uber jar) gồm cả dependency, đóng gói bằng một trong (Spring Boot parent tự gắn sẵn repackage vào phase package; còn shade phải khai báo execution trong pom):

  • spring-boot-maven-plugin — repackage tạo jar chạy được của Spring Boot; mvn spring-boot:run chạy trực tiếp khi dev.
  • maven-shade-plugin — cho Java thuần, gộp dependency + đặt Main-Class trong manifest.
$ mvn clean package
$ java -jar target/quan-ly-don-hang-1.0-SNAPSHOT.jar
Vì sao thin jar vẫn hữu ích? Khi deploy lên Tomcat/container hoặc khi artifact là thư viện cho project khác, bạn không muốn gộp dependency vào. Fat jar là cho ứng dụng chạy độc lập.

13. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Build tool là gì? Maven giải quyết những việc gì?
Build tool tự động hoá vòng đời project: biên dịch, chạy test, đóng gói artifact, quản lý dependency (kể cả transitive), và phát hành lên repository. Maven còn chuẩn hoá cấu trúc thư mục và vòng đời build, nên bất kỳ dev nào mở project cũng hiểu ngay mà không cần tài liệu riêng.
Câu 2. pom.xml là gì? GAV là gì?
pom.xml (Project Object Model) là file XML mô tả project: toạ độ, dependency, properties, plugin, cách build. GAV là bộ ba groupId (tổ chức, viết ngược domain), artifactId (tên project/module), version — dùng để định danh artifact trong mọi repository. Trùng GAV nghĩa là cùng một artifact.
Câu 3. Transitive dependency là gì? Cho ví dụ thực tế.
Là dependency mà dependency của bạn kéo theo, ví dụ khai báo spring-web thì Maven tự thêm spring-core, spring-beans; khai báo jackson-databind thì có jackson-core, jackson-annotations. Bạn không phải khai báo chúng, nhưng chúng vẫn nằm trong classpath và có thể gây xung đột version.
Câu 4. Kể tên và giải thích các scope chính của Maven.
compile (mặc định) — có ở compile/test/runtime, được đóng gói, lan truyền transitive; provided — có ở compile/test, không runtime, không đóng gói (ví dụ jakarta.servlet-api do Tomcat cung cấp); runtime — không cần compile, có ở runtime/test, được đóng gói (driver DB); test — chỉ compile/test, không đóng gói (JUnit); system — như provided nhưng tự trỏ đường dẫn jar, nên tránh. import là scope đặc biệt chỉ dùng trong dependencyManagement với type=pom.
Câu 5. Lifecycle default của Maven gồm các phase nào? Gọi mvn package thì chạy gì?
Chuỗi chính: validate → compile → test → package → verify → install → deploy. Gọi một phase sẽ chạy lần lượt mọi phase trước nó trong cùng lifecycle, nên mvn package thực ra chạy validate, compile, test rồi mới đóng gói. Ngoài ra còn lifecycle clean (xoá target) và site (tài liệu).
Câu 6. package, install, deploy khác nhau thế nào?
package tạo artifact trong target/ — chỉ project hiện tại dùng được. install build rồi copy artifact + pom vào local repository ~/.m2/repository để các project khác trên máy bạn dùng. deploy upload lên remote repository (Nexus/Artifactory) cho cả team và CI. Nhớ: install không phải "cài dependency" — nó là bước publish vào local repo.
Câu 7. Maven wrapper là gì? Tạo bằng lệnh nào?
Là bộ script mvnw/mvnw.cmd + cấu hình trong .mvn/wrapper/ cho phép chạy Maven mà không cần cài sẵn, đồng thời ghim đúng version Maven của project. Tạo bằng mvn wrapper:wrapper -Dmaven=3.9.9, sau đó dùng ./mvnw clean verify thay cho mvn. Gradle tương tự với gradle wrapper --gradle-version ... và ./gradlew.
Câu 8. Dependency được tải về đâu? Phân biệt target/ và ~/.m2.
Dependency tải về local repository ~/.m2/repository, dùng chung cho mọi project và giữ lại vĩnh viễn (xoá đi thì Maven tải lại). Còn target/ là output của lần build hiện tại — class đã biên dịch, jar, báo cáo test — có thể xoá bằng mvn clean và không bao giờ commit. Gradle dùng cache riêng ở ~/.gradle/caches với vai trò tương tự local repo.
Câu 9. Plugin khác dependency thế nào?
Dependency là thư viện nằm trên classpath của code bạn (compile/runtime/test). Plugin là chương trình mở rộng chính Maven, được Maven thực thi trong lúc build (compiler, surefire, jar, shade...), mỗi plugin có các goal gắn vào phase. Cả hai đều tải từ repository dưới dạng jar, nhưng plugin chạy trong classloader riêng và khai báo ở <build><plugins>, không phải <dependencies>.
Câu 10. dependencyManagement khác dependencies thế nào? BOM là gì?
dependencies là thư viện thật sự được thêm vào project. dependencyManagement chỉ khai báo version/scope mặc định — không thêm gì vào classpath; khi dependency được khai báo ở dependencies mà thiếu version, Maven lấy từ đây. BOM (Bill of Materials) là một pom chỉ chứa dependencyManagement cho cả bộ thư viện (ví dụ junit-bom, spring-boot-dependencies), import bằng <type>pom</type> + <scope>import</scope> để mọi version tương thích nhau.

Nâng cao (Junior+)

Câu 11. Gradle khác Maven ở triết lý cốt lõi nào?
Maven là khai báo: XML mô tả project, Maven quyết định cách chạy theo lifecycle cố định. Gradle là lập trình: build script (Groovy/Kotlin) dựng task graph, bạn viết task tuỳ ý. Gradle có daemon + incremental + build cache nên build lại nhanh hơn; đổi lại build script trở thành code, có thể khó debug nếu lạm dụng. Cả hai đều dùng GAV và Maven Central, đều có wrapper.
Câu 12. Hai thư viện kéo hai version của cùng một artifact — Maven chọn bản nào? Gradle thì sao?
Maven dùng nearest definition: bản gần project nhất (độ sâu nhỏ nhất) thắng; cùng độ sâu thì bản khai báo trước thắng. Maven không chọn bản mới nhất tự động. Gradle mặc định ngược lại: version cao nhất thắng (có thể ép bằng resolutionStrategy/constraints). Vì vậy cùng dependency nhưng đổi build tool có thể ra classpath khác — nguyên nhân của những lỗi runtime "kỳ lạ".
Câu 13. Làm sao biết version nào đang thực sự được dùng và bị loại?
Chạy mvn dependency:tree xem cây; thêm -Dverbose để thấy node bị loại (tùy version plugin), thêm -Dincludes=groupId:artifactId để lọc. mvn dependency:list cho danh sách classpath đã resolve. Với Gradle: ./gradlew dependencies --configuration runtimeClasspath và ./gradlew dependencyInsight --dependency ten --configuration runtimeClasspath để biết chính xác ai kéo nó vào và version cuối cùng.
Câu 14. NoSuchMethodError, NoClassDefFoundError và ClassNotFoundException khác nhau thế nào?
NoSuchMethodError: class tìm thấy nhưng bản đang chạy thiếu method đã compile — thường do hai version lệch nhau. NoClassDefFoundError: class đã có lúc compile nhưng JVM không nạp được lúc chạy (thiếu jar, scope sai, exclusion quá tay, hoặc static initializer fail trước đó). ClassNotFoundException: code chủ động load theo tên (Class.forName) mà không thấy — ví dụ driver JDBC khai provided thay vì runtime. Cả ba đều là lỗi classpath, sửa bằng dependency:tree + ghim version/chỉnh scope.
Câu 15. Multi-module để làm gì? Parent pom và aggregator khác gì nhau?
Multi-module tách dự án lớn thành các module (core, web, cli...) để tái sử dụng code, build có thứ tự và giới hạn phụ thuộc giữa các phần. Parent pom chia sẻ cấu hình, version, dependencyManagement cho con qua <parent> (quan hệ kế thừa). Aggregator là vai trò của pom có <packaging>pom</packaging> + <modules>, cho phép build tất cả từ thư mục gốc qua reactor. Một pom có thể làm cả hai. Dự án nhỏ không cần tách.
Câu 16. Gradle: implementation, api, testImplementation khác nhau ra sao?
Chúng là các configuration (tương tự scope nhưng phức tạp hơn). implementation: dùng nội bộ module, không lộ ra compile classpath của module phụ thuộc bạn — mặc định nên dùng. api (cần plugin java-library): lộ ra ngoài, dùng khi public API của bạn tham chiếu type của thư viện đó. compileOnly ≈ provided, runtimeOnly ≈ runtime, testImplementation ≈ scope test. Che transitive bằng implementation giúp build nhanh và tránh vô tình phụ thuộc API nội bộ.
Câu 17. SNAPSHOT là gì? Vì sao không nên dùng trong production?
Version kết thúc bằng -SNAPSHOT là bản đang phát triển, có thể bị ghi đè mỗi lần build/publish. Maven coi snapshot là "động" và kiểm tra bản mới theo chính sách (mặc định mỗi ngày), nên cùng một version có thể là jar khác nhau giữa các lần build — build không tái lập được và không audit được. Production chỉ dùng version release cứng; snapshot để dành cho module nội bộ đang phát triển song song.
Câu 18. Vì sao commit file wrapper (mvnw, gradlew, gradle-wrapper.jar) nhưng không commit target/?
Wrapper là công cụ build: commit để mọi dev và CI dùng đúng một version Maven/Gradle mà không phải cài đặt gì — đảm bảo build tái lập. target//build/ là kết quả build: sinh lại được từ source, commit chỉ làm repo phình và gây conflict rác. Nguyên tắc: commit cấu hình và công cụ ghim version; ignore sản phẩm sinh ra.

Gradle & công cụ

Câu 19. Khi nào nên chọn Gradle thay vì Maven?
Khi build cần logic tuỳ biến phức tạp, khi cần tốc độ incremental/build cache cho project lớn hoặc đa ngôn ngữ, khi làm Android (bắt buộc Gradle), hoặc team đã quen Kotlin DSL. Chọn Maven khi muốn đơn giản, ổn định, tài liệu và cộng đồng doanh nghiệp VN dày, nhiều người đọc pom hơn đọc build script. Với project Spring Boot học tập, Maven là lựa chọn mặc định hợp lý; biết đọc Gradle vẫn cần vì nhiều dự án tuyển dụng dùng nó.
Câu 20. Vì sao chạy mvn install trên máy mình rồi mà đồng nghiệp vẫn không dùng được thư viện của mình?
install chỉ copy artifact vào local repository của máy bạn (~/.m2/repository). Đồng nghiệp và CI có local repo riêng nên không thấy. Muốn chia sẻ: (1) mvn deploy lên Nexus/Artifactory nội bộ, hoặc (2) để chung một multi-module build và build từ gốc (reactor dùng module ngay trong build, không qua repo).
Câu 21. mvn clean package khác mvn package thế nào? -DskipTests khác -Dmaven.test.skip=true ra sao?
mvn package có thể dùng lại output cũ trong target/ (build tăng dần); mvn clean package xoá target trước nên chậm hơn nhưng chắc chắn sạch — nên dùng khi nghi ngờ kết quả cũ hoặc trước khi phát hành. -DskipTests vẫn biên dịch test nhưng không chạy; -Dmaven.test.skip=true bỏ luôn cả biên dịch test (nhanh hơn, dùng khi test code đang hỏng nhưng vẫn cần đóng gói).
Câu 22. Maven có bắt buộc cấu trúc src/main/java không?
Không bắt buộc về mặt kỹ thuật — có thể đổi sourceDirectory/testSourceDirectory trong <build>. Nhưng thực tế nên giữ đúng convention: IDE, plugin, tài liệu, CI và mọi dev đều giả định cấu trúc chuẩn; đổi chỉ để "cho khác" là tự tạo gánh nặng bảo trì. Chỉ single-file java TenFile.java mới không cần cấu trúc này.

Bài 1. Đọc pom và trả lời 
<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>vn.hocjava</groupId>
  <artifactId>order-cli</artifactId>
  <version>2.1.0</version>
  <packaging>jar</packaging>

  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.14.4</version>
      <scope>test</scope>
    </dependency>
    <dependency>
      <groupId>ch.qos.logback</groupId>
      <artifactId>logback-classic</artifactId>
      <version>1.5.16</version>
      <scope>runtime</scope>
    </dependency>
  </dependencies>
</project>

artifactId: order-cli; version: 2.1.0; packaging: jar. JUnit có scope test — không vào jar. Logback scope runtime — không cần lúc compile nhưng có mặt lúc chạy và được đóng gói. Lưu ý cả hai dependency đều ghi version cứng, chưa dùng property/BOM.

Bài 2. Chọn scope đúng cho từng dependency

Điền scope hợp lý và giải thích một dòng:

  • org.junit.jupiter:junit-jupiter → test — chỉ chạy test, không đóng gói.
  • com.mysql:mysql-connector-j → runtime — code không gọi trực tiếp API driver, nhưng cần lúc chạy và khi đóng gói.
  • jakarta.servlet:jakarta.servlet-api → provided — Tomcat/container cung cấp lúc chạy, không đóng gói vào war.
  • org.slf4j:slf4j-api → compile (mặc định) — code import Logger/LoggerFactory nên cần lúc compile.
Bài 3. Ghim version bằng dependencyManagement

Hai thư viện kéo SLF4J 1.7.36 và 2.0.16; muốn chắc chắn dùng 2.0.16. Thêm vào pom (thường là pom cha):

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.slf4j</groupId>
      <artifactId>slf4j-api</artifactId>
      <version>2.0.16</version>
    </dependency>
  </dependencies>
</dependencyManagement>

Sau đó các dependency con có thể bỏ <version>. Kiểm chứng lại bằng mvn dependency:tree -Dincludes=org.slf4j — mọi nhánh phải hiện 2.0.16.

Bài 4. Loại một transitive dependency bằng exclusions

Một thư viện nội bộ kéo commons-logging làm trùng chức năng với SLF4J. Cách loại:

<dependency>
  <groupId>com.example</groupId>
  <artifactId>company-utils</artifactId>
  <version>1.0</version>
  <exclusions>
    <exclusion>
      <groupId>commons-logging</groupId>
      <artifactId>commons-logging</artifactId>
    </exclusion>
  </exclusions>
</dependency>

Kiểm tra bằng mvn dependency:tree: commons-logging phải biến mất. Nếu project dùng class của nó ở đâu đó thì sẽ lỗi NoClassDefFoundError lúc chạy — chỉ loại khi chắc chắn.

Bài 5. Viết dependency JUnit 5 đúng chuẩn

Dùng property cho version và scope test:

<properties>
  <junit.version>5.14.4</junit.version>
</properties>

<dependencies>
  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>${junit.version}</version>
    <scope>test</scope>
  </dependency>
</dependencies>

Nếu đã import org.junit:junit-bom thì bỏ luôn <version> cũng được. Test đặt ở src/test/java, chạy bằng mvn test.

Bài 6. Viết lệnh Maven theo mô tả
  • Build jar sạch, chạy đủ test: mvn clean package
  • Build jar không chạy test: mvn clean package -DskipTests
  • Chỉ chạy unit test: mvn test
  • Xem cây dependency, chỉ lọc SLF4J: mvn dependency:tree -Dincludes=org.slf4j
  • Cài artifact vào local repo: mvn install
  • Build khi không có mạng: mvn -o clean package
Bài 7. Phân tích lỗi NoSuchMethodError 
Exception in thread "main" java.lang.NoSuchMethodError:
 'java.lang.String com.example.utils.JsonUtil.toJson(java.lang.Object, boolean)'
    at vn.hocjava.order.OrderService.taoBaoCao(OrderService.java:42)

Class JsonUtil được tìm thấy nhưng bản đang chạy thiếu method toJson(Object, boolean) — code compile với company-utils 1.2 nhưng runtime lại nạp company-utils 1.0 (bị thư viện khác kéo vào). Cách sửa: (1) mvn dependency:tree -Dincludes=com.example:company-utils; (2) thấy nhánh nào kéo bản 1.0; (3) ghim 1.2 bằng dependencyManagement (ưu tiên) hoặc exclusion bản cũ; (4) build lại và test. Đây là lỗi classpath, không phải lỗi code.

Bài 8. Viết Gradle task in thông tin build 
tasks.register('inThongTin') {
    doLast {
        println "Project: ${project.name} ${project.version}"
        println "Gradle : ${gradle.gradleVersion}"
        println "Java   : ${System.getProperty('java.version')}"

Chạy ./gradlew inThongTin. Điểm quan trọng: logic nằm trong doLast để chỉ chạy ở execution phase; nếu đặt ngoài, nó chạy ở mọi lần cấu hình build (kể cả ./gradlew tasks).

Bài 9. Cùng một dependency, viết bằng Maven và Gradle

Maven:

<dependency>
  <groupId>com.fasterxml.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
  <version>2.18.2</version>
</dependency>

dependencies {

Bài 11. Đúng hay sai? Giải thích
  • "mvn install đẩy artifact lên Maven Central" — Sai. Install chỉ copy vào local repo; muốn lên remote phải mvn deploy và cấu hình distributionManagement.
  • "Dependency scope test không bị đóng gói vào jar" — Đúng. Nó chỉ có mặt trên test classpath.
  • "Gradle mặc định chọn version cao nhất khi xung đột" — Đúng. Khác Maven (nearest definition).
  • "dependencyManagement thêm dependency vào project, không cần khai báo lại" — Sai. Nó chỉ quản lý version/scope; muốn dùng phải khai báo trong dependencies.
  • "Dependency scope provided có mặt lúc runtime" — Sai. Nó có lúc compile/test, còn runtime do môi trường cung cấp.
Bài 12. Sửa multi-module pom còn thiếu

Parent pom thiếu <packaging>pom</packaging> và danh sách module:

<packaging>pom</packaging>
<modules>
  <module>order-core</module>
  <module>order-web</module>
</modules>

Child pom thiếu khối <parent> trỏ về pom gốc:

<parent>
  <groupId>vn.hocjava</groupId>
  <artifactId>quan-ly-don-hang</artifactId>

Build từ thư mục gốc; Maven tự sắp thứ tự (order-core trước order-web). Nếu chỉ muốn build web: mvn -pl order-web -am package.

Bài 13. Cấu hình Gradle: toolchain Java 25, JUnit, logback 
plugins {
    java
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("org.slf4j:slf4j-api:2.0.16")
    runtimeOnly("ch.qos.logback:logback-classic:1.5.16")
    testImplementation("org.junit.jupiter:junit-jupiter:5.14.4")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }
}

tasks.test {
    useJUnitPlatform()
}

Giải thích: toolchain yêu cầu Gradle dùng JDK 25 (tự tải nếu máy chưa có); useJUnitPlatform() bắt buộc để chạy JUnit 5; logback để runtimeOnly vì code chỉ gọi qua SLF4J; JUnit để testImplementation.
