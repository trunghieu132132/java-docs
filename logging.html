1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Mức độ bắt buộc của chủ đề 4.5 (phỏng vấn: cao · production: bắt buộc):

  • Phải làm được — tạo Logger bằng LoggerFactory.getLogger; dùng placeholder {}; chọn đúng 5 level; log exception kèm stack trace; viết logback.xml cơ bản (console + file + rolling); đặt requestId vào MDC.
  • Phải hiểu — vì sao production không dùng System.out.println; SLF4J chỉ là facade nên cần implementation; level theo môi trường; vì sao không log dữ liệu nhạy cảm; vì sao không vừa log vừa ném exception ở mọi tầng.
  • Nhận biết — structured logging (JSON), hệ thống log tập trung (ELK/Loki), async appender và đánh đổi, alert theo error rate, MDC với thread pool. MDC đặt trong filter servlet sẽ dùng lại khi làm REST API ở giai đoạn 5.

Cách học hiệu quả nhất:

  1. Đọc ngay code "trước/sau" bên dưới để thấy khác biệt System.out vs logger.
  2. Nhớ bảng level ở mục 3 — phỏng vấn gần như chắc chắn hỏi.
  3. Làm Bài tập (sửa log sai, chọn level, viết logback.xml) trước khi mở đáp án.
  4. Trước buổi phỏng vấn ôn Cheat sheet & checklist.
Khác các chương trước, ví dụ trong trang này không chạy single-file vì cần hai dependency Maven là slf4j-api và logback-classic. Cách thêm dependency vào pom.xml và chạy build học ở 4.3 Maven & Gradle; ở đây bạn chỉ cần hiểu nội dung file cấu hình.

Góc Node.js ngay từ đầu: nếu từng viết Node, console.log("Tạo đơn", orderId) chạy được nhưng cũng thiếu level, timestamp và ngữ cảnh y như System.out.println. Hệ sinh thái Node có pino/winston (thư viện logging) và morgan (log request HTTP) — Java tương ứng là SLF4J/Logback và servlet filter/interceptor. So sánh đầy đủ ở mục 13.

Trước và sau: một dòng log đơn hàng

Cách người mới thường viết — không level, không timestamp, không tắt/đổi đích được, và mỗi lần đổi format phải sửa code:

// SAI trong production: System.out.println
public class OrderService {
    public void taoDon(String orderId, String user) {
        System.out.println("Tao don " + orderId + " cho " + user);
    }
}

Cách thực tế — logger qua facade, level rõ ràng, placeholder, output do file cấu hình quyết định:

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    public void taoDon(String orderId, String user) {
        log.info("Tạo đơn {} cho {}", orderId, user);
    }
}

Với cấu hình Logback mặc định (chưa có logback.xml), dòng log.info in ra console theo đúng format chuẩn của Logback — thời gian + thread + level + tên logger + message:

14:32:07.512 [main] INFO  OrderService - Tạo đơn DH-1001 cho an

Bạn được thêm ngay 4 thứ: thời gian, level, tên logger và khả năng lọc/ghi file/xoay file mà không sửa một dòng code. Phần còn lại của trang mổ xẻ từng mảnh.

2. SLF4J + Logback — facade & implementation Hay hỏi phỏng vấn

import org.slf4j.Logger;

public class LoggingDemo {

3. Log levels — TRACE < DEBUG < INFO < WARN < ERROR Hay hỏi phỏng vấn

SLF4J có đúng 5 level, nghiêm trọng tăng dần. Khi đặt level X cho một logger, mọi log có level thấp hơn X bị tắt. Ví dụ root để INFO thì TRACE/DEBUG bị bỏ qua, còn WARN/ERROR vẫn in.

TRACEChi tiết cực mịn, từng bước nhỏ trong thuật toánGiá trị từng phần tử khi parse dữ liệuChỉ bật tạm khi điều tra
DEBUGThông tin giúp dev hiểu luồng xử lý: nhánh rẽ, giá trị biến, thời gian gọilog.debug("Phí vận chuyển = {} cho đơn {}", phi, id)Dev

WARNBất thường nhưng chương trình vẫn xử lý được: retry, fallback, dữ liệu hơi lạGọi API lỗi lần 1, sẽ retry; config thiếu nên dùng mặc địnhDev + Prod

Câu thần chú thực dụng: TRACE = "đang soi từng bước", DEBUG = "dev cần biết", INFO = "sếp cần biết", WARN = "có gì đó lạ nhưng tôi xử được", ERROR = "có người phải mở log ra xem ngay".

Đừng log ERROR cho lỗi nghiệp vụ đã xử lý

"Email đã tồn tại khi đăng ký" là lỗi dự đoán được và được trả về HTTP 409 cho người dùng — hệ thống không hỏng. Log ERROR cho ca này làm bảng điều khiển đỏ rực, alert kêu sai, và những ERROR thật bị chôn trong tiếng ồn:

// SAI: lỗi nghiệp vụ bình thường nhưng gắn ERROR
if (userRepository.existsByEmail(email)) {
    log.error("Email {} đã tồn tại", email);
    throw new IllegalArgumentException("Email đã được đăng ký");
}

// ĐÚNG: WARN (hoặc INFO tuỳ quy ước), message nói rõ đây là từ chối nghiệp vụ
if (userRepository.existsByEmail(email)) {
    log.warn("Từ chối đăng ký: email {} đã tồn tại", email);
    throw new IllegalArgumentException("Email đã được đăng ký");
}
Quy tắc chọn môi trường: dev để package của mình ở DEBUG (thấy hết luồng), thư viện framework ở INFO/WARN; prod để root ở INFO, chỉ hạ xuống DEBUG cho một package cụ thể khi đang điều tra — hạ cả hệ thống về DEBUG sẽ cực ồn và tốn I/O.

4. Placeholder logging — dùng {}, đừng cộng chuỗi Hay hỏi phỏng vấn

SLF4J dùng cặp ngoặc {} làm chỗ trống; giá trị truyền vào sau message theo đúng thứ tự. Đây là cách viết chuẩn thay cho cộng chuỗi:

// SAI: cộng chuỗi
log.info("Tạo đơn " + orderId + " cho " + user + " với " + items.size() + " mặt hàng");

// ĐÚNG: placeholder
log.info("Tạo đơn {} cho {} với {} mặt hàng", orderId, user, items.size());

Vì sao không cộng chuỗi?

Vì phép cộng luôn được thực hiện trước khi logger kịp kiểm tra level. Với một dòng DEBUG bị tắt (root đang INFO), bản cộng chuỗi vẫn xây xong String rồi mới bị vứt đi — tốn CPU và tạo rác cho GC:

// Root level = INFO -> DEBUG bị tắt.
// Bản cộng chuỗi vẫn nối và tạo String mới mỗi lần gọi.
log.debug("payload = " + payload);

// Placeholder: SLF4J kiểm tra level trước, DEBUG tắt thì bỏ qua việc nối chuỗi.
log.debug("payload = {}", payload);
Chú ý quan trọng: placeholder chỉ tránh việc nối chuỗi, còn tham số vẫn được tính trước khi gọi (Java đánh giá argument trước). Nếu bản thân giá trị đắt tiền — toJson(request), query DB, serialize — hãy chặn bằng isDebugEnabled():
if (log.isDebugEnabled()) {
    log.debug("payload = {}", toJson(request));
}

Ba đến mười tham số vẫn dùng bình thường; chỉ cần đếm đủ cặp {} khớp với số tham số. Nếu thiếu tham số, phần {} thừa bị giữ nguyên trong output — lỗi rất khó thấy:

log.info("Tạo đơn {} cho {}", orderId);
// 14:32:07.512 [main] INFO  OrderService - Tạo đơn DH-1001 cho {}

5. Log exception đúng cách Hay hỏi phỏng vấn

Exception có stack trace — chuỗi "dấu vết" cho biết lỗi nổ ở đâu, đi qua những method nào. Cách truyền đúng: đặt ex làm tham số cuối cùng, không gọi getMessage(), không cộng chuỗi:

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    public void taoDon(String orderId, PaymentService payment) {
        try {
            payment.charge(orderId);
            log.info("Đơn {} thanh toán xong", orderId);
        } catch (RuntimeException ex) {
            // ex là tham số CUỐI -> logback in kèm stack trace
            log.error("Không tạo được đơn {}", orderId, ex);
            throw ex;
        }
    }
}

Output thật với pattern mặc định (stack trace lược bớt):

14:33:10.002 [main] ERROR OrderService - Không tạo được đơn DH-1001
java.lang.IllegalStateException: Cổng thanh toán không phản hồi
    at PaymentService.charge(PaymentService.java:...)
    at OrderService.taoDon(OrderService.java:...)

Ba kiểu sai thường gặp

  1. Chỉ log getMessage(): log.error("Lỗi: " + ex.getMessage()) làm mất loại exception và toàn bộ stack trace — nhận được mỗi câu "Cổng thanh toán không phản hồi" mà không biết nổ ở dòng nào, method nào.
  2. Log rồi ném lại ở mọi tầng: service log ERROR, controller bắt được cũng log ERROR, global handler log thêm lần nữa — một lỗi thành ba dòng ERROR và alert đếm sai. Chọn đúng một tầng chịu trách nhiệm log (thường là tầng xử lý cuối); các tầng dưới chỉ ném tiếp.
  3. Nuốt lỗi sau khi log: catch (RuntimeException ex) { log.error("Lỗi", ex); } rồi không làm gì tiếp — caller tưởng thành công, dữ liệu rơi vào trạng thái nửa vời.

Log mà không mất dấu — chọn nơi log

Nguyên tắc: log ở nơi quyết định. Nếu tầng dưới vẫn muốn để lại dấu vết, log ở mức thấp hơn (DEBUG/WARN) hoặc thêm ngữ cảnh rồi ném tiếp:

try {
    payment.charge(orderId);
} catch (RuntimeException ex) {
    log.warn("Thanh toán lần 1 thất bại cho đơn {}, sẽ retry", orderId);
    throw ex;
}
Khi vừa có placeholder vừa có exception, exception vẫn phải nằm cuối cùng: log.error("Không tạo được đơn {}", orderId, ex). Nếu truyền ex ở giữa, nó bị coi là tham số thường và chỉ in toString() — mất stack trace.

Che dữ liệu (masking)

Masking biến giá trị nhạy cảm thành dạng vẫn đối chiếu được nhưng không đọc được toàn bộ. Hàm mask nên nằm cạnh DTO/tiện ích để không nơi nào quên:

static String maskCard(String card) {
    if (card == null || card.length() < 4) {
        return "***";
    }
    return "**** **** **** " + card.substring(card.length() - 4);
}

static String maskEmail(String email) {
    int at = email.indexOf('@');
    if (at <= 1) {
        return "***";
    }
    return email.charAt(0) + "***" + email.substring(at);
}

public static void main() {
    IO.println(maskCard("4111111111111111"));
    IO.println(maskEmail("an.nguyen@shop.vn"));
}
**** **** **** 1111
a***@shop.vn
  • Chỉ log ID thay vì dữ liệu: orderId, userId thay cho tên/email/số thẻ.
  • Che ngay tại nguồn gần nhất có thể (DTO/tiện ích) — đừng trông chờ người đọc log tự lọc.
  • Review log ngay trong code review: grep các từ khoá password, token, card, cvv trong diff.
  • Không log cả object DTO có toString() chứa field nhạy cảm — hoặc override toString() để che bớt. Xem 2.6 equals / hashCode / toString.
Bẫy toString(): log.info("user = {}", userDto) là cách rất nhanh để rò rỉ mọi field. Kiểm tra toString() của DTO trước khi log cả object.

7. Cấu hình logback.xml Production

Logback tự động tìm file cấu hình trên classpath theo thứ tự: logback-test.xml (thường ở src/test/resources) rồi logback.xml (ở src/main/resources). Không có file nào thì dùng cấu hình mặc định (console, DEBUG) đúng như output ở mục 2. Có thể chỉ định file khác bằng -Dlogback.configurationFile=.../logback-dev.xml.

Ba khối cần nhớ: appender → logger → root

  • Appender — "đích đến" của log: ConsoleAppender (màn hình), RollingFileAppender (file xoay vòng), AsyncAppender (bọc appender khác), appender JSON...
  • Logger — cấu hình theo tên/package: level riêng, appender riêng, độ kế thừa (additivity).
  • Root — logger gốc; mọi logger khác kế thừa từ đây nếu không có cấu hình riêng.

File cấu hình hoàn chỉnh mức cơ bản

<configuration>
    <property name="LOG_DIR" value="logs"/>
    <property name="PATTERN"
              value="%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n"/>

    <!-- 1. Log ra console -->
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>${PATTERN}</pattern>
        </encoder>
    </appender>

    <!-- 2. Log ra file, xoay vong theo ngay + dung luong -->
    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_DIR}/app.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
            <fileNamePattern>${LOG_DIR}/app.%d{yyyy-MM-dd}.%i.log</fileNamePattern>
            <maxFileSize>10MB</maxFileSize>
            <maxHistory>30</maxHistory>
            <totalSizeCap>1GB</totalSizeCap>
        </rollingPolicy>
        <encoder>
            <pattern>${PATTERN}</pattern>
        </encoder>
    </appender>

    <!-- 3. Level theo package: code cua minh DEBUG, framework WARN -->
    <logger name="com.shop" level="DEBUG"/>
    <logger name="org.hibernate" level="WARN"/>

    <!-- 4. Mac dinh cho toan bo ung dung -->
    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
        <appender-ref ref="FILE"/>
    </root>
</configuration>

Rolling policy — vì sao bắt buộc ở production

Nếu chỉ ghi mãi vào một file, file sẽ phình tới hàng GB, khó mở và có ngày đầy ổ đĩa. RollingFileAppender + SizeAndTimeBasedRollingPolicy tự cắt file theo ngày và theo dung lượng, đồng thời xoá bản cũ:

  • fileNamePattern ...%d{yyyy-MM-dd}.%i.log — ngày + số thứ tự khi vượt maxFileSize.
  • maxHistory 30 — giữ log 30 ngày rồi xoá dần.
  • totalSizeCap 1GB — trần tổng dung lượng cả thư mục log.
Level hoạt động theo cây tên logger: com.shop là cha của com.shop.OrderService, nên logger con kế thừa level DEBUG. Vì vậy đặt level theo package luôn linh hoạt hơn từng class — và đây chính là lý do nên lấy logger bằng getLogger(TenClass.class).
Đừng quên additivity khi tự gắn appender: nếu gắn appender cho logger com.shop mà không đặt additivity="false", log vẫn chảy tiếp lên root và bị ghi hai lần. Thấy file log trùng dòng thì kiểm tra chỗ này trước khi nghi ngờ code.

8. Structured logging — log cho máy đọc Production

Log text truyền thống tốt cho mắt người nhưng khó cho máy: muốn lọc "tất cả đơn của user X trong 1 giờ" bạn phải regex. Structured logging ghi mỗi sự kiện thành một object có khoá rõ ràng — thường là JSON mỗi dòng (JSON Lines) — để hệ thống tập trung (ELK, Loki, Datadog...) đánh index và truy vấn. Output thật là một dòng; ở đây xuống dòng cho dễ đọc:

{
  "@timestamp": "2026-10-03T14:32:07.512+07:00",
  "level": "INFO",
  "logger": "com.shop.OrderService",
  "thread": "main",
  "requestId": "req-a1b2c3",
  "message": "Tạo đơn DH-1001 cho an",
  "orderId": "DH-1001",
  "userId": "an",
  "total": 396000
}

Trong Java, structured logging thường làm bằng encoder JSON như logstash-logback-encoder (artifact net.logstash.logback:logstash-logback-encoder, bản 9.0 tại thời điểm viết), hoặc JSON layout của Log4j2. Mức tối thiểu cần biết — thêm appender JSON bên cạnh appender text:

<appender name="JSON_FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>logs/app.json</file>
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
        <customFields>{"service":"order-service"}</customFields>
    </encoder>
</appender>
  • Message ổn định, dữ liệu động vào field: message nên là câu cố định để nhóm/đếm; orderId, userId, requestId đưa vào MDC hoặc structured argument để filter chính xác.
  • Đừng nhồi mọi thứ vào message rồi lại phải regex — mất hết lợi ích của JSON.
  • Khi nào đáng làm: nhiều service, cần dashboard/alert theo field, truy vấn log thường xuyên. App nhỏ một service thì log text + grep là đủ.
  • Mức nhận biết là đủ cho Junior+ — biết nó là gì, vì sao dùng, và rằng dev vẫn thường giữ song song console text cho dễ đọc khi phát triển.

9. MDC & correlation id Production

MDC (Mapped Diagnostic Context) là một map gắn theo thread; mọi dòng log trong thread đó tự động mang theo các cặp key-value mà không phải truyền qua tham số. Pattern %X{key} sẽ in giá trị tương ứng. Dùng phổ biến nhất là requestId (correlation id / trace id): một request đi qua nhiều class, nhiều service — cùng một requestId giúp nối toàn bộ log của nó lại.

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    public void xuLy(String requestId, String orderId) {
        MDC.put("requestId", requestId);
        try {
            log.info("Bắt đầu xử lý đơn {}", orderId);
            log.info("Xử lý đơn {} xong", orderId);
        } finally {
            MDC.remove("requestId");
        }
    }
}

Với pattern có [%X{requestId}], hai dòng trên ra:

14:35:01.120 [http-nio-8080-exec-3] INFO  OrderService [req-a1b2c3] - Bắt đầu xử lý đơn DH-1001
14:35:01.450 [http-nio-8080-exec-3] INFO  OrderService [req-a1b2c3] - Xử lý đơn DH-1001 xong

Đặt requestId một lần ở filter servlet — nơi mọi request đều đi qua (học đầy đủ ở giai đoạn 5). Đoạn code trong doFilter trông như sau:

// Trong doFilter cua servlet filter (giai doan 5)
String requestId = request.getHeader("X-Request-Id");
if (requestId == null || requestId.isBlank()) {
    requestId = UUID.randomUUID().toString();
}
MDC.put("requestId", requestId);
response.setHeader("X-Request-Id", requestId);
try {
    chain.doFilter(request, response);
} finally {
    MDC.remove("requestId");
}

MDC và thread pool / bất đồng bộ

MDC là thread-local: khi công việc nhảy sang thread khác (ExecutorService, CompletableFuture, message listener), context không tự lan theo. Phải copy và đặt lại ở thread mới:

Map<String, String> context = MDC.getCopyOfContextMap();

executor.submit(() -> {
    if (context != null) {
        MDC.setContextMap(context);
    }
    try {
        log.info("Chạy trong thread khác, vẫn có requestId");
    } finally {
        MDC.clear();
    }
});
  • Luôn remove/clear trong finally: thread được tái sử dụng (đặc biệt trong web server), quên xoá thì request sau mang nhầm requestId của request trước — cực khó debug.
  • AsyncAppender của Logback: event log được tạo trên thread gọi nên đã "chụp" sẵn giá trị MDC lúc đó; vì vậy log vẫn đúng context dù việc ghi file diễn ra trên thread nền. Vấn đề MDC mất context chủ yếu là khi code nghiệp vụ chạy trên thread khác, không phải appender.
  • Correlation id còn được truyền giữa các service qua HTTP header (ví dụ X-Request-Id) để nối log liên service — hướng tới distributed tracing (OpenTelemetry) ở giai đoạn sau.

11. Production tips Production

11.1 Log phải có ngữ cảnh

"Đã tạo đơn" là dòng log vô dụng khi có sự cố. Người đọc log cần trả lời được: đơn nào, user nào, request nào:

// SAI: khong truy vet duoc gi
log.info("Đã tạo đơn");

// ĐÚNG: ngữ cảnh cụ thể
log.info("Đã tạo đơn {} cho user {} với tổng tiền {}", orderId, userId, total);

11.2 Không log trong vòng lặp dày

Một job xử lý 100.000 bản ghi mà log từng bản ghi sẽ tạo 100.000 dòng — chậm, ngốn đĩa, và không ai đọc. Log mốc đầu/cuối kèm số liệu tổng kết; chi tiết từng phần tử chỉ để DEBUG và nên lấy mẫu:

// SAI: 1 dong log cho moi phan tu
for (Order order : orders) {
    log.info("Đang xử lý đơn {}", order.id());
    xuLy(order);
}

// ĐÚNG: moc dau/cuoi + tong ket
log.info("Bắt đầu xử lý {} đơn", orders.size());
int ok = 0;
int failed = 0;
for (Order order : orders) {
    // ... xu ly, dem ok/failed ...
}
log.info("Xử lý xong: {} thành công, {} lỗi", ok, failed);

11.3 Đừng dùng log thay debugger

Debugger (breakpoint, step, watch) trả lời câu hỏi "tại sao giá trị này bằng 3" nhanh hơn hàng trăm dòng log. Log để lại dấu vết vận hành: sự kiện đã xảy ra ở production, khi bạn không ngồi trước máy. Khi điều tra, dùng debugger/test; khi chạy thật, dùng log có chủ đích.

11.4 Alert từ log phải "hành động được"

  • Alert nên dựa trên tỉ lệ/tần suất (error rate, số ERROR mỗi phút) chứ không phải từng dòng log.
  • Mỗi ERROR phải ứng với việc có người cần làm gì đó; lỗi nghiệp vụ đã xử lý để WARN/INFO (mục 3).
  • Đặt log message ổn định, có "mã" nhận dạng nếu cần (ORDER_PAYMENT_FAILED) để hệ thống alert đếm chính xác thay vì regex câu tiếng Việt.

11.5 Async appender — biết mình đánh đổi gì

Khi log I/O thành nút cổ chai, bọc appender trong AsyncAppender để thread nghiệp vụ không chờ ghi file:

<appender name="ASYNC_FILE" class="ch.qos.logback.classic.AsyncAppender">
    <queueSize>1024</queueSize>
    <discardingThreshold>0</discardingThreshold>
    <appender-ref ref="FILE"/>
</appender>
  • Lợi: throughput cao hơn, độ trễ ghi log không ảnh hưởng request.
  • Hại: khi process chết đột ngột, log còn trong queue có thể mất. Vì vậy đừng dùng async cho log audit/bảo mật/bắt buộc đầy đủ.
  • discardingThreshold 0 để không tự động vứt bớt message khi queue gần đầy; theo dõi cảnh báo "appender queue full".

11.6 Checklist vận hành

  • Log có rotation và trần dung lượng (mục 7) — ổ đĩa đầy là sự cố production kinh điển.
  • Sau mỗi deploy, thử một request và đọc log xem có đủ ngữ cảnh, đúng level, không lộ dữ liệu.
  • Đồng bộ format giữa các service để hệ thống log tập trung parse được.
  • Ghi cả duration cho các tác vụ dài (gọi API ngoài, job) để trả lời "chậm ở đâu".

14. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Logging là gì? Vì sao production không dùng System.out.println?
Logging là ghi lại sự kiện của chương trình (thời gian, mức độ, nguồn, nội dung) để đọc lại sau. System.out.println không có level để lọc, không timestamp/tên logger/thread, không cấu hình được đích ghi hay format, không xoay file, không tắt theo môi trường, và tuỳ tiện về luồng. Logger giải quyết tất cả và còn hỗ trợ MDC, rolling, appender. Trong production, log là công cụ điều tra chính vì không gắn được debugger.
Câu 2. SLF4J là gì? Vì sao dùng facade thay vì gọi trực tiếp Logback/Log4j2?
SLF4J là một facade (API) trung lập cho logging; nó không ghi log mà chuyển lời gọi tới implementation có trên classpath (Logback, Log4j2, JUL). Dùng facade giúp code không phụ thuộc implementation — đổi thư viện logging không phải sửa code; mọi thư viện trong hệ sinh thái cùng ghi về một chỗ với một định dạng.
Câu 3. Vì sao khai báo private static final Logger log = LoggerFactory.getLogger(TenClass.class)?
static vì logger dùng lại, không cần tạo theo từng object, và để gọi được từ static method; final để không bị gán đè. Truyền TenClass.class để tên logger là tên đầy đủ của class — nhờ đó cấu hình level theo package hoạt động và log biết nguồn phát sinh.
Câu 4. Kể tên 5 level của SLF4J theo thứ tự. Khi nào dùng từng level?
TRACE < DEBUG < INFO < WARN < ERROR. TRACE: chi tiết cực mịn để soi thuật toán. DEBUG: thông tin cho dev (giá trị biến, nhánh xử lý). INFO: sự kiện nghiệp vụ quan trọng đã hoàn tất. WARN: bất thường nhưng xử lý được (retry, fallback). ERROR: thao tác thất bại cần người xem. Đặt level X cho logger nghĩa là mọi log thấp hơn X bị tắt.
Câu 5. Nên đặt level gì cho dev và production?
Dev: package của mình DEBUG (thấy hết luồng), framework để INFO/WARN. Production: root INFO để ổn định và tiết kiệm I/O; khi điều tra thì hạ DEBUG cho một package cụ thể rồi trả lại. Bật DEBUG toàn hệ thống ở prod gây ồn, chậm và có thể lộ chi tiết nội bộ.
Câu 6. Khi nào KHÔNG nên log ERROR?
Khi lỗi là nghiệp vụ bình thường và đã được xử lý/từ chối có chủ đích — ví dụ email trùng khi đăng ký, hết hàng, sai OTP. Đây là tình huống dự đoán được, trả về lỗi rõ ràng cho người dùng; log WARN (hoặc INFO theo quy ước) là đủ. ERROR dành cho thứ cần người vận hành xem, nếu không alert sẽ nhiễu và ERROR thật bị chôn.
Câu 7. Placeholder {} của SLF4J là gì? Lợi ích chính?
Là chỗ trống trong message, được thay bằng tham số theo thứ tự: log.info("Tạo đơn {} cho {}", id, user). Lợi ích: tránh nối chuỗi khi level bị tắt (SLF4J kiểm tra level trước khi format), code gọn và an toàn hơn cộng chuỗi. Lưu ý: tham số vẫn được tính trước khi gọi — nếu tính toán đắt, chặn bằng isDebugEnabled().
Câu 8. Vì sao không nên cộng chuỗi khi log?
Vì phép cộng luôn chạy trước khi logger kiểm tra level: log.debug("x = " + tinhToan()) vẫn xây chuỗi (và gọi tinhToan) dù DEBUG đang tắt — tốn CPU, tạo rác cho GC. Placeholder giải quyết phần nối chuỗi; với tham số đắt còn cần isDebugEnabled().
Câu 9. Log exception đúng cách là thế nào?
Truyền exception làm tham số cuối cùng của lời gọi: log.error("Không tạo được đơn {}", orderId, ex). Logback/SLF4J nhận ra và in kèm stack trace. Không gọi getMessage(), không cộng chuỗi "Lỗi: " + ex, không truyền ex ở giữa các tham số.
Câu 10. Vì sao log.error(ex.getMessage()) là sai?
Vì message chỉ là một câu mô tả, còn stack trace mới cho biết lỗi nổ ở class/dòng nào và đi qua đường nào. Bỏ stack trace khiến điều tra gần như mất manh mối, đặc biệt với lỗi sâu trong framework. Ngoài ra còn mất loại exception (NullPointerException vs IllegalArgumentException...).
Câu 11. Có nên vừa log vừa ném lại exception (log and rethrow) không?
Không nên làm ở mọi tầng. Nếu mỗi tầng đều catch → log.error → throw, một lỗi sinh ra nhiều dòng ERROR trùng, alert đếm sai. Chọn một nơi log (thường là tầng xử lý cuối hoặc global exception handler); tầng dưới nếu cần dấu vết thì log WARN/DEBUG hoặc chỉ thêm ngữ cảnh rồi ném tiếp.
Câu 12. Những dữ liệu nào tuyệt đối không được log? Che thế nào?
Password, PIN/OTP, API key, JWT/token, số thẻ + CVV, số tài khoản đầy đủ, giấy tờ tuỳ thân và PII (số điện thoại, email, địa chỉ... tuỳ quy định). Cách làm: log ID nội bộ thay cho dữ liệu; nếu buộc phải đối chiếu thì masking (chỉ giữ 4 số cuối của thẻ, a***@shop.vn cho email); kiểm tra cả toString() của DTO trước khi log cả object; review diff để bắt các từ khoá nhạy cảm.

Nâng cao (Junior+)

Câu 13. logback.xml gồm những khối nào? Logback load file này thế nào?
Ba khối chính: appender (đích ghi: console, file rolling, async, JSON...), logger (cấu hình theo tên/package: level, appender, additivity), root (logger gốc, mặc định cho toàn ứng dụng). Logback tự tìm logback-test.xml rồi logback.xml trên classpath; không có thì dùng cấu hình mặc định. Có thể chỉ định file khác bằng -Dlogback.configurationFile=....
Câu 14. RollingFileAppender và rolling policy để làm gì? Cấu hình tối thiểu?
Để log không phình mãi một file và đầy ổ đĩa: cắt file theo thời gian/dung lượng và xoá bản cũ theo chính sách. Tối thiểu: fileNamePattern (ví dụ app.%d{yyyy-MM-dd}.%i.log), maxFileSize (10MB), maxHistory (giữ bao nhiêu ngày), totalSizeCap (trần tổng dung lượng).
Câu 15. Level theo package hoạt động thế nào? additivity là gì?
Tên logger tạo thành cây: com.shop là cha của com.shop.OrderService; logger con kế thừa cấu hình (level, appender) từ cha gần nhất nếu không tự đặt. Nhờ đó <logger name="com.shop" level="DEBUG"/> áp cho cả package. additivity="false" chặn log lan tiếp lên root — dùng khi logger con tự gắn appender để tránh ghi trùng hai lần.
Câu 16. MDC là gì? Vì sao cần correlation id?
MDC là map key-value gắn theo thread; mọi log trong thread đó in kèm giá trị qua pattern %X{key}. Correlation id (requestId/traceId) đặt một lần ở filter/entry point giúp nối toàn bộ log của cùng một request — kể cả khi nó đi qua nhiều class — và truyền qua header giữa các service. Nhờ đó grep một requestId là ra cả hành trình xử lý.
Câu 17. MDC có vấn đề gì với thread pool và bất đồng bộ?
MDC là thread-local nên không tự lan sang thread khác: khi submit việc cho ExecutorService/CompletableFuture, thread mới không có context. Phải MDC.getCopyOfContextMap() ở thread gọi rồi setContextMap ở thread mới và clear() khi xong. Với Logback AsyncAppender, event đã chụp MDC lúc tạo nên log vẫn đúng context dù việc ghi file chạy trên thread nền. Luôn remove/clear trong finally vì web server tái sử dụng thread.
Câu 18. Nên đặt log ở tầng nào trong ứng dụng?
Ở biên và nơi quyết định: entry point log request/response + requestId; service log mốc nghiệp vụ với orderId/userId; integration log retry/timeout khi tự xử lý; global exception handler log ERROR + stack trace đúng một lần. Tránh log trùng cùng một sự kiện ở nhiều tầng và tránh rắc log từng dòng nội bộ.
Câu 19. Structured logging là gì? Khi nào nên dùng?
Là ghi log dưới dạng có cấu trúc (thường JSON mỗi dòng) với các field rõ ràng — level, logger, requestId, orderId... — để hệ thống log tập trung (ELK, Loki, Datadog) index và truy vấn thay vì regex text. Nên dùng khi có nhiều service, cần dashboard/alert theo field hoặc truy vấn log thường xuyên; app nhỏ một service có thể chỉ cần log text.
Câu 20. Làm sao tránh log quá nhiều khi xử lý vòng lặp lớn?
Không log từng phần tử ở INFO. Log mốc bắt đầu và kết thúc kèm số liệu tổng kết (số thành công/lỗi, thời gian). Chi tiết từng phần tử chỉ để DEBUG, có thể lấy mẫu (log mỗi N phần tử) khi cần điều tra. Với job dài, log tiến độ theo lô thay vì từng bản ghi.
Câu 21. AsyncAppender đánh đổi điều gì?
Đổi độ trễ của thread nghiệp vụ lấy rủi ro mất log: log được đưa vào queue và ghi bởi thread nền nên request không chờ I/O; nhưng nếu process chết hoặc queue đầy, message trong queue có thể mất. Vì vậy không dùng async cho log audit/bảo mật; cấu hình queue hợp lý và theo dõi cảnh báo queue full.
Câu 22. Làm sao dùng log để alert hiệu quả?
Alert dựa trên tỉ lệ/tần suất (error rate, số ERROR mỗi phút theo message/pattern) thay vì từng dòng. Điều kiện tiên quyết là level đúng: lỗi nghiệp vụ đã xử lý để WARN/INFO, chỉ ERROR cho thứ cần hành động. Message nên ổn định, có mã nhận dạng để đếm chính xác; kết hợp metric để tránh alert trùng lặp.

15. Bài tập

Bài 1. Sửa log cộng chuỗi thành placeholder 
log.info("Tạo đơn " + orderId + " cho " + user + " tổng " + total + " VND");
log.debug("Số item = " + items.size());

log.info("Tạo đơn {} cho {} tổng {} VND", orderId, user, total); và log.debug("Số item = {}", items.size());. Placeholder tránh nối chuỗi khi level bị tắt; items.size() là tham số rẻ nên không cần isDebugEnabled.

Bài 2. Chọn level cho từng tình huống

1) Ứng dụng khởi động xong, lắng nghe cổng 8080 → INFO.
2) Gọi API đối tác timeout lần 1, sẽ retry → WARN.
3) Job đồng bộ chạy xong 12.000 bản ghi → INFO (kèm số liệu).
4) Không kết nối được DB sau 3 lần retry → ERROR.
5) Giá trị từng phần tử khi parse file cấu hình → TRACE (hoặc DEBUG).
6) User đăng ký email đã tồn tại, đã trả lỗi 409 cho người dùng → WARN, không phải ERROR.

Bài 3. Viết logback.xml mức cơ bản

Yêu cầu: console + file rolling theo ngày 10MB, giữ 14 ngày; package com.shop ở DEBUG, root INFO.

<configuration>
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>logs/app.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
            <fileNamePattern>logs/app.%d{yyyy-MM-dd}.%i.log</fileNamePattern>
            <maxFileSize>10MB</maxFileSize>
            <maxHistory>14</maxHistory>
        </rollingPolicy>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <logger name="com.shop" level="DEBUG"/>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
        <appender-ref ref="FILE"/>
    </root>
</configuration>
Bài 4. Tìm lỗi log dữ liệu nhạy cảm 
log.info("Đăng nhập: user={} pass={}", username, password);
log.info("Thanh toán thẻ {} cvv={}", cardNumber, cvv);
log.debug("Header Authorization: {}", authHeader);
log.info("User {} - CCCD {} - sdt {}", userId, cccd, phone);

Cả bốn dòng đều sai. Sửa: chỉ log sự kiện + định danh an toàn — log.info("Đăng nhập thành công user={}", username);; log.info("Thanh toán đơn {} bằng thẻ {}", orderId, maskCard(cardNumber));; không log Authorization/token (log.debug("Gọi API với token đã cấp cho user {}", userId);); CCCD/số điện thoại là PII — chỉ log userId, nếu buộc đối chiếu thì masking theo quy định công ty.

Bài 5. Sửa log exception 
try {
    paymentService.charge(order);
} catch (RuntimeException ex) {
    log.error("Thanh toán lỗi: " + ex.getMessage());
}

Hai lỗi: cộng chuỗi và chỉ lấy message (mất stack trace). Sửa tối thiểu:

try {
    paymentService.charge(order);
} catch (RuntimeException ex) {
    log.error("Thanh toán thất bại cho đơn {}", order.id(), ex);
    throw ex;   // hoac xu ly theo nghiep vu
}

Nếu tầng trên đã log rồi thì có thể chỉ log WARN ở đây để tránh trùng; nhưng tuyệt đối không nuốt lỗi im lặng.

Bài 6. Thêm ngữ cảnh vào log 
log.info("Đã tạo đơn");
log.info("Cập nhật trạng thái thất bại");

log.info("Đã tạo đơn {} cho user {} tổng {} VND", orderId, userId, total); và log.warn("Cập nhật trạng thái thất bại cho đơn {}: trạng thái hiện tại {}", orderId, currentStatus);. Ngoài ra nên có requestId trong MDC để nối các log cùng request.

Bài 7. Đoán log nào xuất hiện với cấu hình level 
root level = INFO
<logger name="com.shop" level="DEBUG"/>
<logger name="com.shop.db" level="WARN"/>
// com.shop.OrderService
log.debug("debug order");       // (1)
log.info("info order");         // (2)

// com.shop.db.OrderRepository
log.debug("debug db");          // (3)
log.info("info db");            // (4)
log.warn("warn db");            // (5)

In ra: (2), (5), (6). Giải thích: com.shop.OrderService kế thừa DEBUG từ com.shop nên (1) và (2) đều in. com.shop.db có level riêng WARN nên (3), (4) bị tắt, chỉ (5) in. com.other.PaymentService không có cấu hình riêng, kế thừa root INFO nên (6) in.

Bài 8. Đặt requestId bằng MDC (mô tả)

Viết trong filter (mọi request đi qua), đảm bảo luôn xoá trong finally:

String requestId = request.getHeader("X-Request-Id");
if (requestId == null || requestId.isBlank()) {
    requestId = UUID.randomUUID().toString();
}
MDC.put("requestId", requestId);
response.setHeader("X-Request-Id", requestId);
try {
    chain.doFilter(request, response);
} finally {
    MDC.remove("requestId");
}

Pattern cần có %X{requestId}, ví dụ: %d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{requestId}] - %msg%n. Nếu xử lý bất đồng bộ, phải copy MDC sang thread mới (mục 9).

Bài 9. Sửa log trong vòng lặp 
for (Order order : orders) {
    log.info("Đang xử lý đơn {}", order.id());
    xuLy(order);
}
log.info("Xong");

Giữ 2 dòng cho toàn bộ lô, thêm số liệu tổng kết và chuyển chi tiết sang DEBUG:

log.info("Bắt đầu xử lý {} đơn", orders.size());
int ok = 0;
int failed = 0;
for (Order order : orders) {
    log.debug("Xử lý đơn {}", order.id());
    if (xuLy(order)) {
        ok++;
    } else {
        failed++;
        log.warn("Xử lý đơn {} thất bại", order.id());
    }
}
log.info("Xử lý xong {} đơn: {} thành công, {} lỗi", orders.size(), ok, failed);

Log WARN cho từng đơn lỗi là hợp lý vì số lỗi thường ít và cần truy vết; log DEBUG chi tiết vẫn tắt ở prod.

Bài 10. Sửa double log 
// OrderService
try {
    payment.charge(orderId);
} catch (RuntimeException ex) {
    log.error("Thanh toán lỗi", ex);
    throw ex;
}

// Controller
try {
    orderService.taoDon(orderId);
} catch (RuntimeException ex) {
    log.error("Tạo đơn lỗi", ex);
    throw ex;
}

// GlobalExceptionHandler
log.error("Unhandled", ex);

Một lỗi đang bị log 3 lần. Giữ một nơi log ERROR — thường là global handler (nơi biết request đầy đủ ngữ cảnh) — và để các tầng dưới chỉ ném tiếp:

// OrderService
try {
    payment.charge(orderId);
} catch (RuntimeException ex) {
    throw ex; // hoac boc them context roi nem tiep
}

// Controller: chi goi service, khong catch

// GlobalExceptionHandler
log.error("Xử lý request thất bại cho đơn {}", orderId, ex);

Nếu service cần dấu vết retry thì log WARN ở đó, nhưng không log ERROR lặp lại.

Bài 11. Chọn cách log phù hợp

1) Ghi lại mã đơn trong mọi dòng log của một request → MDC (MDC.put("orderId", ...) + %X{orderId}).
2) In giá trị tạm total khi tính phí để debug → placeholder ở DEBUG: log.debug("Phí = {} cho đơn {}", phi, orderId).
3) Hệ thống log tập trung cần lọc theo userId, orderId, duration → structured logging (JSON) với các field đó (MDC/structured arguments).

Bài 12. Đoán output khi placeholder thiếu tham số, rồi sửa 
String orderId = "DH-1001";
log.info("Tạo đơn {} cho {}", orderId);

Output (Logback, pattern mặc định): ... INFO LoggingDemo - Tạo đơn DH-1001 cho {} — tham số thứ hai thiếu nên placeholder còn lại được giữ nguyên là {} (SLF4J không ném lỗi, nên bẫy này rất dễ lọt). Sửa: truyền đủ tham số log.info("Tạo đơn {} cho {}", orderId, user); — hoặc bỏ placeholder thừa nếu không cần.
