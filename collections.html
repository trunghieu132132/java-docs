Collections Framework — bộ sưu tập trong Java

Collections Framework là kiến trúc chuẩn trong java.util để lưu trữ, tìm kiếm và thao tác nhóm object. Đây là chủ đề phỏng vấn số 1 của Java: hầu như buổi phỏng vấn nào cũng hỏi ArrayList vs LinkedList, HashMap hoạt động thế nào, equals/hashCode liên quan gì tới Set, hay phân biệt Comparable và Comparator. Trang này đi từ hierarchy, Big-O, internals của HashMap, iterator fail-fast tới các bẫy production — mọi output đều chạy thật trên JDK 25.

1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Mức độ bắt buộc của chủ đề 3.3 (phỏng vấn: rất cao · production: bắt buộc):

  • Phải làm được — chọn đúng collection cho từng nhu cầu; dùng List, Set, Map, Deque thành thạo; duyệt và xóa an toàn bằng iterator/removeIf; sort bằng Comparable/Comparator; dùng các method hiện đại getOrDefault, computeIfAbsent, merge.

2. Hierarchy: Iterable → Collection → List/Set/Queue Hay hỏi phỏng vấn

Collections Framework chia làm hai "vũ trụ" tách biệt: Collection (một nhóm phần tử) và Map (cặp key–value). Map không kế thừa Collection — câu hỏi bẫy quen thuộc.

Iterable                        Map  (khong ke thua Collection)
  └── Collection                  ├── HashMap ── LinkedHashMap
        ├── List                  ├── SortedMap ── NavigableMap ── TreeMap
        │     ├── ArrayList       ├── EnumMap
        │     ├── LinkedList*     └── ConcurrentHashMap
        │     └── Vector ── Stack
        ├── Set
        │     ├── HashSet ── LinkedHashSet

        └── Queue
              ├── ArrayDeque* / LinkedList*
              └── PriorityQueue

* LinkedList vua la List vua la Deque (ke thua ca hai nhanh)
  • Iterable — hợp đồng duyệt: có iterator(), nhờ đó dùng được for-each. Mọi collection đều Iterable.
  • Collection — các thao tác chung: add, remove, contains, size, isEmpty, stream.
  • List — có thứ tự, truy cập theo index, cho phép trùng lặp.
  • Set — không trùng (theo equals/hashCode), không index.
  • Queue/Deque — hàng đợi một đầu/hai đầu, dùng để xử lý theo thứ tự.
  • Map — cặp key–value, key duy nhất; keySet(), values(), entrySet() là các view trên map.

Lập trình theo interface, khởi tạo bằng implementation

Quy tắc vàng: khai báo bằng interface, tạo object bằng class cụ thể. Đổi implementation không phải sửa code gọi:

import java.util.*;

void main() {
    List<String> list = new ArrayList<>();
    Set<String> set = new HashSet<>();
    Queue<Integer> queue = new ArrayDeque<>();
    Deque<Integer> deque = new ArrayDeque<>();
    Map<String, Integer> map = new HashMap<>();

    list.add("a");
    set.add("a");
    queue.offer(1);
    deque.push(2);
    map.put("a", 1);

    IO.println("List  -> " + list.getClass().getSimpleName());
    IO.println("Set   -> " + set.getClass().getSimpleName());
    IO.println("Queue -> " + queue.getClass().getSimpleName());
    IO.println("Map   -> " + map.getClass().getSimpleName());

    IO.println("deque instanceof Queue      : " + (deque instanceof Queue));
    IO.println("map instanceof Collection   : " + (map instanceof Collection));
    IO.println("ArrayList  instanceof RandomAccess : " + (list instanceof RandomAccess));
    IO.println("LinkedList instanceof RandomAccess : " + (new LinkedList<>() instanceof RandomAccess));

RandomAccess — marker interface

RandomAccess là marker interface: không có method nào, chỉ đánh dấu "class này truy cập index trong O(1)". Các thuật toán của Collections (binarySearch, shuffle, reverse…) kiểm tra instanceof RandomAccess để chọn cách duyệt: index nhanh cho ArrayList, iterator cho LinkedList. Nhờ vậy cùng một API chạy tối ưu cho cả hai.

3. List — ArrayList, LinkedList, Vector Hay hỏi phỏng vấn

List là collection có thứ tự, cho phép phần tử trùng nhau và truy cập theo index (bắt đầu từ 0). Ba implementation bạn cần nắm:

  • ArrayList — mặc định cho hầu hết trường hợp. Bên trong là mảng; mảng đầy thì tự tăng kích thước khoảng 1.5 lần (tạo mảng mới + copy). Vì vậy thêm cuối là O(1) khấu hao, nhưng thêm/xóa đầu hoặc giữa phải dịch phần còn lại nên O(n).
  • LinkedList — danh sách liên kết đôi, mỗi phần tử là một node giữ prev/next. Lấy theo index phải đi bộ từ đầu hoặc cuối nên O(n). Chỉ thắng khi bạn liên tục thêm/xóa ở hai đầu và không cần index — nhưng lúc đó ArrayDeque mới là lựa chọn đúng (mục 6).
  • Vector (và Stack kế thừa nó) — class từ Java 1.0, mọi method synchronized. Khóa toàn cục khiến chậm; ngày nay không dùng trong code mới: thay bằng ArrayList, ArrayDeque hoặc CopyOnWriteArrayList.

List.of — immutable, gọn và an toàn

Từ Java 9, List.of(...) tạo list bất biến (immutable). Mọi thao tác sửa đổi đều ném UnsupportedOperationException — kể cả set:

import java.util.*;

void main() {
    List<String> immutable = List.of("a", "b");
    IO.println("class    : " + immutable.getClass().getSimpleName());
    IO.println("noi dung : " + immutable);

    try {
        immutable.add("c");
    } catch (UnsupportedOperationException e) {
        IO.println("add    -> " + e);

    try {
        immutable.set(0, "z");
    } catch (UnsupportedOperationException e) {
        IO.println("set    -> " + e);
    }
    try {
        immutable.remove("a");
    } catch (UnsupportedOperationException e) {
        IO.println("remove -> " + e);
    }
}

Arrays.asList — fixed-size, không phải immutable

Arrays.asList(array) trả về list có kích thước cố định và dùng chung mảng gốc. set được (ghi thẳng vào mảng), nhưng add/remove thì không:

import java.util.*;

void main() {
    String[] arr = {"a", "b", "c"};
    List<String> fixed = Arrays.asList(arr);

    fixed.set(0, "A");
    IO.println("fixed : " + fixed);
    IO.println("arr[0]: " + arr[0]);

    try {
        fixed.add("d");
    } catch (UnsupportedOperationException e) {
        IO.println("add    -> " + e);
    }
    try {
        fixed.remove(0);
    } catch (UnsupportedOperationException e) {
        IO.println("remove -> " + e);
    }
}
fixed : [A, b, c]
arr[0]: A
add    -> java.lang.UnsupportedOperationException
remove -> java.lang.UnsupportedOperationException
Bẫy varargs với mảng nguyên thủy: Arrays.asList(new int[]{1, 2, 3}) trả về List<int[]> size 1 (một phần tử là cả mảng), không phải list 3 số. Vì generic không nhận primitive — dùng IntStream.of(...).boxed().toList() (học ở 3.8) hoặc tự thêm từng phần tử.

List.copyOf vs Collections.unmodifiableList — copy vs view

Hai API này khác nhau về bản chất. unmodifiableList là view: nó chỉ chặn bạn sửa, còn list gốc đổi thì nó đổi theo. List.copyOf là bản sao độc lập (nhưng sao chép nông — phần tử vẫn là cùng object):

import java.util.*;

void main() {
    List<String> goc = new ArrayList<>(List.of("a", "b"));
    List<String> view = Collections.unmodifiableList(goc);
    List<String> copy = List.copyOf(goc);

    goc.add("c");

    IO.println("goc  : " + goc);
    IO.println("view : " + view);
    IO.println("copy : " + copy);
}
goc  : [a, b, c]
view : [a, b, c]
copy : [a, b]
  • Muốn chụp ảnh dữ liệu tại thời điểm hiện tại (an toàn trước thay đổi sau đó) → List.copyOf.
  • Muốn chặn ghi trên chính list đang sống (ví dụ trả field ra ngoài) → Collections.unmodifiableList, nhưng nhớ list gốc vẫn sửa được ở nơi khác.
  • List.copyOf từ chối null (NPE nếu phần tử null); unmodifiableList cho phép null.

subList là view — bẫy kinh điển

subList(from, to) trả về view của đoạn [from, to). Sửa sublist là sửa list gốc, và ngược lại — thay đổi cấu trúc list gốc sẽ làm sublist "hết hạn":

import java.util.*;

void main() {
    List<Integer> nums = new ArrayList<>(List.of(0, 1, 2, 3, 4, 5));
    List<Integer> sub = nums.subList(1, 4);

    IO.println("sub               : " + sub);
    sub.set(0, 99);
    IO.println("nums sau sub.set  : " + nums);
    sub.clear();
    IO.println("nums sau sub.clear: " + nums);

    List<Integer> nums2 = new ArrayList<>(List.of(10, 20, 30, 40));
    List<Integer> sub2 = nums2.subList(1, 3);
    nums2.add(50);
    try {
        sub2.get(0);
    } catch (ConcurrentModificationException e) {
        IO.println("sub2.get sau nums2.add -> ConcurrentModificationException");
    }
}
sub               : [1, 2, 3]
nums sau sub.set  : [0, 99, 2, 3, 4, 5]
nums sau sub.clear: [0, 4, 5]
sub2.get sau nums2.add -> ConcurrentModificationException
Muốn cắt một đoạn độc lập, hãy copy: new ArrayList<>(nums.subList(1, 4)) hoặc List.copyOf(nums.subList(1, 4)).

remove(int) vs remove(Object) — bẫy overload nổi tiếng

List có hai method remove: xóa theo index trả về phần tử bị xóa, xóa theo giá trị trả về boolean. Truyền số nguyên vào sẽ luôn chọn bản remove(int):

import java.util.*;

void main() {
    List<Integer> nums = new ArrayList<>(List.of(10, 20, 30, 20));

    IO.println("nums                : " + nums);
    IO.println("remove(1)           = " + nums.remove(1));
    IO.println("nums                : " + nums);
    IO.println("remove(Integer(30)) = " + nums.remove(Integer.valueOf(30)));
    IO.println("nums                : " + nums);
    IO.println("indexOf(20)         = " + nums.indexOf(20));
    IO.println("contains(20)        = " + nums.contains(20));
    IO.println("contains(\"20\")      = " + nums.contains("20"));
}
nums                : [10, 20, 30, 20]
remove(1)           = 20
nums                : [10, 30, 20]
remove(Integer(30)) = true
nums                : [10, 20]
indexOf(20)         = 1
contains(20)        = true
contains("20")      = false

Nhớ quy tắc: remove(1) là xóa phần tử thứ 1; muốn xóa giá trị 1 phải remove(Integer.valueOf(1)). Bẫy overload này đã gặp ở Methods — Q14; khi làm việc với List<Integer> hãy luôn tự hỏi "mình muốn index hay value?".

Hai method tìm kiếm indexOf và contains đều dựa trên equals của phần tử (với contains thì so o.equals(elementData[i])), nên object muốn tìm đúng phải override equals — xem Object contract — mục 4. Ví dụ contains("20") trả false vì Integer(20) không equals String "20".

toArray — List ↔ mảng

Hai overload nghe giống nhau nhưng khác kiểu trả về: toArray() luôn trả Object[] (không cast được sang String[]); muốn mảng đúng kiểu hãy truyền mảng đích. Idiom hiện đại là toArray(new T[0]) — mảng rỗng để JVM tự cấp đúng kích thước (nhanh hơn new T[list.size()] trên JDK mới):

import java.util.*;

void main() {
    List<String> list = List.of("a", "b", "c");
    Object[] obj = list.toArray();
    String[] arr = list.toArray(new String[0]);
    IO.println("toArray()         : " + obj.getClass().getSimpleName());
    IO.println("toArray(new T[0]) : " + arr.getClass().getSimpleName() + " " + Arrays.toString(arr));

    arr[0] = "z";
    IO.println("sua mang, list    : " + list);
    List<String> view = Arrays.asList(arr);
    IO.println("Arrays.asList     : " + view);
    List<String> copy = new ArrayList<>(view);
    copy.add("d");
    IO.println("copy mutable      : " + copy);
}

5.1 HashMap hoạt động thế nào

Một lần map.get(key) đi qua 4 bước:

  1. Gọi key.hashCode().
  2. Trộn bit (spread): h ^ (h >>> 16) để các bit cao tham gia vào index — tránh dồn cục khi capacity nhỏ.
  3. Chọn bucket: (n - 1) & spread với n là số bucket (mặc định 16). Vì n là lũy thừa 2, phép & tương đương modulo nhưng nhanh hơn.
  4. Đi trong bucket, dùng equals tìm đúng key. Thấy → trả value; không → trả null.

Hai key khác nhau hoàn toàn có thể cùng hash — gọi là collision (va chạm), hoàn toàn bình thường. "Aa" và "BB" là ví dụ nổi tiếng cùng hash 2112:

import java.util.*;

void main() {
    IO.println("\"Aa\".hashCode() = " + "Aa".hashCode());
    IO.println("\"BB\".hashCode() = " + "BB".hashCode());

    int h = "Aa".hashCode();
    int spread = h ^ (h >>> 16);
    IO.println("spread          = " + spread);
    IO.println("bucket khi n=16 = " + (spread & 15));

    Map<String, Integer> map = new HashMap<>();
    map.put("Aa", 1);
    map.put("BB", 2);
    IO.println("map        : " + map);
    IO.println("map.size() : " + map.size());
}

"BB".hashCode() = 2112
spread          = 2112
bucket khi n=16 = 0
map        : {Aa=1, BB=2}
map.size() : 2

Hai key cùng bucket 0 nhưng equals là false nên cả hai vẫn được giữ — bucket chứa một chuỗi node (linked list). Phần demo đầy đủ về hash/equals và hậu quả khi vi phạm hợp đồng nằm ở Object contract — mục 9.

5.2 Resize, load factor & treeify

  • Capacity mặc định 16, load factor 0.75. Khi size > capacity × 0.75 (16 × 0.75 = 12 entry), map resize: nhân đôi capacity và phân bố lại toàn bộ entry. Chi phí một lần resize là O(n) nhưng chia đều ra vẫn O(1) khấu hao.
  • Capacity luôn là lũy thừa 2 để dùng mask (n - 1) & hash. Truyền capacity không phải lũy thừa 2 (ví dụ new HashMap<>(100)) thì map tự làm tròn lên lũy thừa 2 gần nhất (128).
  • Treeify: bucket 8 node vẫn là linked list; chỉ khi thêm node thứ 9 vào bucket đang có ≥ 8 node và capacity đạt ≥ 64 (MIN_TREEIFY_CAPACITY) thì bucket mới chuyển từ linked list sang cây đỏ-đen, tra cứu trong bucket còn ~O(log n) thay vì O(n). Nếu capacity còn < 64 thì map ưu tiên resize thay vì treeify — nên với map mặc định 16, bucket phải qua vài lần resize mới đủ điều kiện treeify.
  • Untreeify khi xóa: hằng số UNTREEIFY_THRESHOLD = 6 chỉ được dùng trong split() khi resize; còn khi xóa, việc bucket quay về linked list do removeTreeNode quyết định theo hình dạng cây, không phải đếm "còn ≤ 6 node". Đừng viết code dựa vào "bucket nhỏ là linked list".
  • Trường hợp xấu nhất khi bị tấn công hash (mọi key cùng hash): O(log n) nhờ cây đỏ-đen (từ Java 8); trước đó là O(n).
Vì vậy khi biết trước số phần tử, hãy tạo map đủ lớn để tránh resize: new HashMap<>((int) Math.ceil(soPhanTu / 0.75)) — nhớ cast (int) vì soPhanTu / 0.75 là double và HashMap không có constructor nhận double (new HashMap<>(soPhanTu / 0.75 + 1) không compile). Gọn hơn, dùng HashMap.newHashMap(soPhanTu) (JDK 19+): JDK tự tính capacity vừa đủ, không cần bạn nhớ công thức.

5.3 LinkedHashMap — LRU cache trong 10 dòng

Constructor LinkedHashMap(capacity, loadFactor, accessOrder) với accessOrder = true sẽ đưa phần tử vừa get hoặc put xuống cuối. Override removeEldestEntry để tự loại phần tử cũ nhất — đó chính là LRU (Least Recently Used):

import java.util.*;

void main() {
    LinkedHashMap<String, Integer> lru = new LinkedHashMap<>(16, 0.75f, true) {
        @Override
        protected boolean removeEldestEntry(Map.Entry<String, Integer> eldest) {
            return size() > 3;
        }
    };

    lru.put("a", 1);
    lru.put("b", 2);
    lru.put("c", 3);
    IO.println("sau put a,b,c : " + lru.keySet());

    lru.get("a");
    IO.println("sau get(a)    : " + lru.keySet());

    lru.put("d", 4);
    IO.println("sau put(d)    : " + lru.keySet());
}
sau put a,b,c : [a, b, c]
sau get(a)    : [b, c, a]
sau put(d)    : [c, a, d]

Đọc output theo trục thời gian: get("a") đẩy a ra cuối; put("d") vượt giới hạn 3 nên phần tử cũ nhất b bị loại. Trong production, LRU thật thường dùng thư viện cache (Caffeine, Guava) để có thêm TTL, thống kê, concurrency — nhưng cơ chế nền vẫn là LinkedHashMap access-order.

5.7 Bẫy key mutable

Key của HashMap phải ổn định hash trong suốt thời gian nằm trong map. Sửa field ảnh hưởng hashCode sau khi put sẽ khiến entry "mất tích" — vẫn nằm trong map nhưng không tra được:

import java.util.*;

final class Key {
    String ten;

    Key(String ten) {
        this.ten = ten;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof Key k && ten.equals(k.ten);
    }

    @Override
    public int hashCode() {
        return ten.hashCode();
    }

    @Override
    public String toString() {
        return "Key[" + ten + "]";
    }
}

void main() {
    Map<Key, String> map = new HashMap<>();
    Key k = new Key("a");
    map.put(k, "gia tri");

    IO.println("truoc khi doi : " + map.get(k));
    k.ten = "b";
    IO.println("sau khi doi   : " + map.get(k));
    IO.println("map van giu entry: " + map.size());
}
truoc khi doi : gia tri
sau khi doi   : null
map van giu entry: 1

Quy tắc production: key nên là immutable — String, số wrapper, enum, record, UUID, LocalDate. Nếu buộc dùng object mutable làm key, hãy copy giá trị tại thời điểm put hoặc "đóng băng" nó.

5.8 View: keySet(), entrySet(), values()

Ba method này trả view trỏ thẳng vào map, không phải bản sao: xóa qua view là xóa thẳng entry trong map, và map đổi thì view thấy ngay. Duyệt-xóa vẫn phải qua iterator/removeIf (không sửa map trực tiếp trong for-each):

import java.util.*;

void main() {
    Map<String, Integer> map = new HashMap<>();
    map.put("a", 1);
    map.put("b", 2);
    map.put("c", 3);

    Set<String> keys = map.keySet();
    Collection<Integer> values = map.values();
    Set<Map.Entry<String, Integer>> entries = map.entrySet();

    keys.remove("a");
    IO.println("sau keySet().remove(a) : " + new TreeMap<>(map));

5.9 WeakHashMap & IdentityHashMap

PriorityQueue — heap, không phải danh sách đã sort

PriorityQueue chỉ đảm bảo phần tử đầu là nhỏ nhất (theo natural ordering hoặc comparator). toString() in ra mảng heap bên trong — không phải thứ tự đã sort:

import java.util.*;

void main() {
    PriorityQueue<Integer> pq = new PriorityQueue<>();
    pq.addAll(List.of(30, 10, 20, 5));

    IO.println("heap array : " + pq);
    IO.println("peek()     : " + pq.peek());

    StringBuilder sb = new StringBuilder();
    while (!pq.isEmpty()) {
        sb.append(pq.poll()).append(' ');
    }
    IO.println("poll()     : " + sb.toString().trim());

    PriorityQueue<String> max = new PriorityQueue<>(Comparator.reverseOrder());
    max.addAll(List.of("b", "a", "c"));
    IO.println("max-heap   : " + max.poll() + " " + max.poll() + " " + max.poll());
}

  • PriorityQueue không stable: hai phần tử có cùng độ ưu tiên có thể ra theo thứ tự bất kỳ (heap không giữ thứ tự chèn). Cần stable thì thêm tie-breaker vào comparator (ví dụ số thứ tự tăng dần).
  • Không nhận null; không thread-safe. Bản concurrent là PriorityBlockingQueue.
  • Muốn lấy top-K từ dữ liệu lớn: giữ một PriorityQueue kích thước K (min-heap cho top-K lớn nhất), mỗi phần tử mới so với peek() — O(n log K) thay vì sort cả mảng.

7. Iterator & fail-fast Hay hỏi phỏng vấn

for-each thực chất được compiler dịch thành Iterator:

for (T x : collection) { ... }  ≡  Iterator<T> it = collection.iterator(); while (it.hasNext()) { T x = it.next(); ... }

Xóa phần tử an toàn trong lúc duyệt phải qua chính iterator (it.remove()), hoặc dùng removeIf — cả hai đều cập nhật đúng trạng thái nội bộ:

import java.util.*;

void main() {
    List<String> list = new ArrayList<>(List.of("a", "b", "c", "d"));

    Iterator<String> it = list.iterator();
    while (it.hasNext()) {
        if (it.next().equals("b")) {
            it.remove();
        }
    }
    IO.println("sau iterator.remove : " + list);

    list.removeIf(s -> s.equals("d"));
    IO.println("sau removeIf        : " + list);
}
sau iterator.remove : [a, c, d]
sau removeIf        : [a, c]

Sửa collection trực tiếp trong for-each (thay vì qua iterator) làm số lần sửa (modCount) lệch với bản ghi của iterator, lần next() kế tiếp sẽ ném ConcurrentModificationException — gọi tắt là fail-fast:

import java.util.*;

void main() {
    List<String> list = new ArrayList<>(List.of("a", "b", "c"));

    try {
        for (String s : list) {
            IO.println("duyet: " + s);
            if (s.equals("b")) {
                list.add("x");
            }
        }
    } catch (ConcurrentModificationException e) {
        IO.println("-> ConcurrentModificationException");
    }
    IO.println("list: " + list);
}
duyet: a
duyet: b
-> ConcurrentModificationException
list: [a, b, c, x]
Fail-fast chỉ là "best-effort": Javadoc ghi rõ nó không đảm bảo phát hiện mọi thay đổi đồng thời — code không được phép dựa vào exception này để đảm bảo đúng đắn. Với dữ liệu chia sẻ giữa thread, phải dùng collection concurrent, không dựa vào fail-fast.

ListIterator — duyệt hai chiều, sửa an toàn khi duyệt

List có thêm ListIterator: duyệt xuôi/ngược bằng hasNext/next và hasPrevious/previous, đồng thời cho phép set (ghi đè phần tử vừa đi qua) và add (chèn ngay trước vị trí con trỏ) an toàn — không ném CME vì thao tác qua chính iterator:

import java.util.*;

void main() {
    List<String> list = new ArrayList<>(List.of("a", "b", "c"));
    ListIterator<String> it = list.listIterator();
    while (it.hasNext()) {
        String s = it.next();
        if (s.equals("b")) {
            it.set("B");
            it.add("b2");
        }
    }
    IO.println("sau duyet xuoi : " + list);

    StringBuilder sb = new StringBuilder();
    ListIterator<String> rev = list.listIterator(list.size());
    while (rev.hasPrevious()) {
        sb.append(rev.previous()).append(' ');
    }
    IO.println("duyet nguoc    : " + sb.toString().trim());
}

Khác Iterator (chỉ có remove), ListIterator chỉ tồn tại trên List. Cách nhớ vị trí: con trỏ nằm giữa hai phần tử — add chèn vào ngay trước phần tử mà next() sẽ trả, còn set thay phần tử mà next()/previous() vừa trả.

Wrapper: synchronized & checked

Collections.synchronizedMap/Set (cùng họ với synchronizedList đã gặp ở mục 7) bọc collection thường thành bản khóa từng method. import java.util.*;

@SuppressWarnings({"unchecked", "rawtypes"})
void main() {
    Map<String, Integer> syncMap = Collections.synchronizedMap(new HashMap<>());
    syncMap.put("a", 1);
    synchronized (syncMap) {                 // bat buoc khi duyet
        StringBuilder sb = new StringBuilder();
        for (var e : syncMap.entrySet()) {
            sb.append(e);
        }
        IO.println("duyet trong synchronized: " + sb);
    }

    List<String> raw = new ArrayList<>();
    List<String> checked = Collections.checkedList(raw, String.class);
    checked.add("ok");
    try {
        ((List) checked).add(42);
    } catch (ClassCastException e) {
        IO.println("checkedList.add(42) -> ClassCastException");
    }
    IO.println("raw: " + raw);
}

synchronized wrapper khóa thô (toàn collection) và iterator vẫn fail-fast — code mới ưu tiên ConcurrentHashMap/CopyOnWriteArrayList. checked wrapper chỉ kiểm tra kiểu lúc ghi qua chính nó, hoàn toàn không phải cơ chế thread-safety hay bảo mật.

Bộ nhớ & hiệu năng

  • Boxing có giá: List<Integer> lưu reference tới object Integer (~16 byte) cộng slot trong mảng (4–8 byte), trong khi int[] chỉ 4 byte/ô. Với hàng triệu số, chênh lệch bộ nhớ và cache miss là đáng kể — dùng mảng hoặc IntStream cho đường nóng (hot path).
  • Pre-size khi biết trước số phần tử: new ArrayList<>(10_000) tránh nhiều lần copy mảng; new HashMap<>((int) Math.ceil(soPhanTu / 0.75)) tránh resize — hoặc HashMap.newHashMap(soPhanTu) (JDK 19+) cho rõ nghĩa. Lưu ý soPhanTu / 0.75 là double nên phải cast (int), nếu không sẽ không compile.
  • LinkedList tốn bộ nhớ: mỗi phần tử là một node với 2 reference + header object. Gần như mọi nhu cầu "chèn/xóa nhanh hai đầu" của LinkedList đều được ArrayDeque giải quyết tốt hơn (nhanh hơn, ít bộ nhớ hơn).
  • Load factor của HashMap: 0.75 là điểm cân bằng mặc định. Giảm xuống 0.5 → ít collision hơn nhưng tốn bộ nhớ; tăng lên 0.9 → tiết kiệm bộ nhớ nhưng nhiều collision, chậm hơn. Chỉ chỉnh khi đã đo đạc.
  • List.contains trong vòng lặp là O(n) mỗi lần, dễ biến thuật toán thành O(n²). Cần membership check nhiều lần → chuyển sang HashSet.
  • Duyệt LinkedList bằng iterator (for-each) là O(n); đừng bao giờ get(i) trong vòng lặp trên LinkedList — mỗi lần get lại đi bộ từ đầu.
  • Immutable collection như List.of có thể chia sẻ giữa các thread mà không cần đồng bộ — lựa chọn rẻ nhất cho dữ liệu chỉ đọc.

Production notes — concurrent collections (nhận biết)

  • ConcurrentHashMap — map chuẩn cho đa luồng: không khóa toàn cục, computeIfAbsent chạy atomic (khác HashMap + tự khóa), iterator weakly consistent. Không cho null key/value. Dùng cho cache, counter, registry.
  • CopyOnWriteArrayList — mỗi lần ghi copy toàn bộ mảng, đổi lại đọc và duyệt không cần khóa. Chỉ dùng khi ghi rất ít (danh sách listener, cấu hình). Ghi nhiều là thảm họa hiệu năng.
  • BlockingQueue — trái tim của producer–consumer: ArrayBlockingQueue (bounded, chống tràn bộ nhớ), LinkedBlockingQueue, PriorityBlockingQueue, SynchronousQueue. Học sâu ở Giai đoạn 4.
  • BlockingDeque — hàng đợi blocking hai đầu (LinkedBlockingDeque là implementation chính), thêm được putFirst/putLast, takeFirst/takeLast — dùng cho work-stealing hoặc deque producer–consumer hai chiều.
  • ConcurrentSkipListMap/ConcurrentSkipListSet — bản concurrent của TreeMap/TreeSet (skip list): giữ thứ tự sort, hỗ trợ range query, không khóa toàn cục. Dùng khi cần map/set có thứ tự chia sẻ giữa nhiều thread, vì ConcurrentHashMap không sort được.
  • Collections.synchronizedXxx — wrapper khóa từng method; duyệt vẫn phải tự synchronized (list) { ... }. Code mới ưu tiên concurrent collections thay vì wrapper này.
  • Không dùng Vector, Stack, Hashtable trong code mới — legacy, khóa thô, API lỗi thời. Thay bằng ArrayList/ArrayDeque/ConcurrentHashMap.
  • Đừng trả null cho collection — trả List.of() hoặc Collections.emptyList() để call site không phải null check. Ở biên API, dùng List.copyOf để phòng thủ (defensive copy).
  • Đóng gói collection nội bộ: field private final List<...>, getter trả List.copyOf hoặc unmodifiableList; không để lộ reference cho bên ngoài sửa (chi tiết ở 2.2 Encapsulation & Immutability).

ConcurrentHashMap internals (JDK 8+) & chuyện size()

Không khóa toàn cục như Hashtable: với bucket rỗng, put dùng CAS để gắn node đầu; khi bucket đã có node, nó synchronized trên chính head node của bucket đó (khóa mịn theo bin) — nhiều thread ghi vào các bucket khác nhau không chặn nhau. Đổi lại, size() chỉ là ước lượng (Javadoc nói rõ) vì được tổng hợp từ các CounterCell cập nhật phân tán; dưới concurrency hãy dùng mappingCount() (trả long, không tràn int):

import java.util.concurrent.*;

void main() {
    ConcurrentHashMap<String, Integer> chm = new ConcurrentHashMap<>();
    chm.put("a", 1);
    chm.computeIfAbsent("b", k -> 2);
    IO.println("size()         = " + chm.size());
    IO.println("mappingCount() = " + chm.mappingCount());
}

mappingCount() = 2
Không dùng size() để quyết định logic dưới concurrency (giá trị có thể là trung gian); cần đếm chính xác hãy dùng LongAdder hoặc tự quản lý. CHM cũng không nhận null key/value, và computeIfAbsent chạy atomic trên đúng bucket đó.

LRU bằng Map của JS — ý tưởng y hệt LinkedHashMap access-order: xóa rồi set lại để đẩy key xuống cuối, key cũ nhất nằm ở đầu:

class LRU {
  constructor(limit) {
    this.limit = limit;
    this.map = new Map();
  }
  get(key) {
    if (!this.map.has(key)) return undefined;
    const value = this.map.get(key);
    this.map.delete(key);
    this.map.set(key, value);
    return value;
  }
  set(key, value) {
    if (this.map.has(key)) this.map.delete(key);
    this.map.set(key, value);
    if (this.map.size > this.limit) {
      this.map.delete(this.map.keys().next().value);
    }
  }
}

const lru = new LRU(3);
lru.set("a", 1);
lru.set("b", 2);
lru.set("c", 3);
lru.get("a");
lru.set("d", 4);
console.log([...lru.map.keys()]);      // [ 'c', 'a', 'd' ]

Chốt: Java tách bạch "cấu trúc dữ liệu" (List/Set/Map/Deque) với "chiến lược bên trong" (hash, cây, heap). JS gộp nhiều thứ vào Array/Object/Map — tiện cho script nhỏ, nhưng dễ sai ngầm khi dữ liệu lớn (ép key, trùng reference, O(n) tìm kiếm).

12. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Collections Framework là gì? Kể hierarchy chính.
Là kiến trúc chuẩn trong java.util gồm interface + implementation + thuật toán để lưu và xử lý nhóm object. Hai nhánh chính: Collection (List, Set, Queue/Deque) và Map (key–value). Map không kế thừa Collection. Iterable là gốc của Collection, cho phép for-each.
Câu 2. ArrayList vs LinkedList — chọn cái nào?
Mặc định chọn ArrayList: get(i) O(1), bộ nhớ thấp, cache-friendly, thêm cuối O(1) khấu hao. LinkedList chỉ hơn ở thêm/xóa hai đầu O(1) nhưng lấy theo index O(n) và tốn bộ nhớ mỗi node. Khi cần thao tác hai đầu, ArrayDeque nhanh hơn cả LinkedList. Vậy LinkedList gần như không còn chỗ đứng trong code mới.
Câu 3. Vì sao ArrayList.get O(1) còn LinkedList.get O(n)?
ArrayList lưu trên mảng liên tục nên địa chỉ phần tử i = base + i × size — truy cập trực tiếp. LinkedList chỉ giữ node đầu/cuối, muốn tới vị trí i phải đi theo con trỏ next/prev (dù tối ưu đi từ đầu gần hơn), trung bình n/2 bước.
Câu 4. List.of, Arrays.asList và new ArrayList khác nhau thế nào?
List.of — immutable, cấm mọi sửa đổi kể cả set, không nhận null. Arrays.asList — fixed-size, set được và ghi thẳng vào mảng gốc, nhưng add/remove ném UnsupportedOperationException. new ArrayList<>(...) — bản sao mutable đầy đủ. Cần sửa thì luôn bọc: new ArrayList<>(List.of(...)).
Câu 5. Collections.unmodifiableList vs List.copyOf — khác gì?
unmodifiableList là view: thay đổi list gốc vẫn nhìn thấy qua view (chỉ chặn ghi qua view). List.copyOf là bản sao độc lập tại thời điểm gọi, không nhận null. Muốn chụp ảnh dữ liệu → copyOf; muốn chặn ghi trên collection đang sống → unmodifiable.
Câu 6. subList trả về gì? Bẫy là gì?
Trả về view của đoạn [from, to). Sửa qua sublist là sửa list gốc và ngược lại. Bẫy: sau khi list gốc bị sửa cấu trúc (add/remove), mọi truy cập sublist ném ConcurrentModificationException. Cần độc lập thì copy: new ArrayList<>(list.subList(a, b)).
Câu 7. remove(1) trên List<Integer> xóa gì?
Gọi remove(int index) — xóa phần tử ở vị trí 1 và trả về phần tử đó. Muốn xóa theo giá trị 1 phải remove(Integer.valueOf(1)) để chọn overload remove(Object) trả boolean. Với List<String> không có bẫy này vì không có overload int nhận String.
Câu 8. HashSet hoạt động thế nào? Vì sao cần equals + hashCode?
HashSet dùng HashMap bên trong: tính hash để chọn bucket, rồi dùng equals để phân biệt các phần tử cùng bucket. Nếu override equals mà không override hashCode, hai object "bằng nhau" rơi vào bucket khác → set giữ cả hai. Nếu override hashCode mà equals sai → có thể coi hai object khác nhau là một. Chi tiết ở Object contract — mục 7.

Nâng cao (Junior+)

Câu 9. HashMap hoạt động thế nào? Load factor và treeify là gì?
Mảng bucket; index = (n-1) & (h ^ (h >>> 16)); trong bucket dùng equals. Load factor 0.75: khi size vượt 75% capacity thì resize gấp đôi và rehash. Từ Java 8: bucket 8 node vẫn là linked list; chỉ khi thêm node thứ 9 vào bucket đang có ≥ 8 node và capacity ≥ 64 (MIN_TREEIFY_CAPACITY) mới treeify thành cây đỏ-đen để tra cứu ~O(log n); nếu capacity < 64 thì resize trước. Ngưỡng 6 (UNTREEIFY_THRESHOLD) chỉ dùng trong split() lúc resize; khi xóa, việc quay về linked list do removeTreeNode quyết định theo hình dạng cây, không đếm node ≤ 6.
Câu 10. Vì sao capacity của HashMap luôn là lũy thừa 2?
Để thay modulo bằng phép AND: hash % n chậm hơn hash & (n-1), và khi n là lũy thừa 2 thì (n-1) là mask toàn bit 1, phân bố đều nếu hash tốt. Constructor nhận capacity bất kỳ sẽ tự làm tròn lên lũy thừa 2 gần nhất. Đổi lại, phải "spread" bit cao xuống thấp (h ^ (h >>> 16)) vì mask chỉ dùng bit thấp.
Câu 11. LinkedHashMap làm LRU cache thế nào?
Constructor LinkedHashMap(capacity, 0.75f, true) với accessOrder=true: mỗi get/put đưa entry xuống cuối danh sách liên kết. Override removeEldestEntry trả true khi size() > limit để tự xóa entry cũ nhất (đầu danh sách). Kết quả là LRU. Demo chạy thật ở mục 5.3.
Câu 12. HashSet vs LinkedHashSet vs TreeSet?
HashSet O(1) trung bình, thứ tự không đảm bảo. LinkedHashSet O(1) trung bình, giữ thứ tự chèn (thêm linked list). TreeSet O(log n), luôn sorted theo compareTo/comparator, implement NavigableSet (floor/ceiling/subSet). Chọn theo nhu cầu thứ tự; mặc định HashSet.
Câu 13. Comparable vs Comparator?
Comparable (java.lang) định nghĩa thứ tự tự nhiên bên trong class qua compareTo — mỗi class chỉ có một. Comparator (java.util) là object so sánh bên ngoài, tạo được nhiều chiến lược (theo tên, theo điểm, đảo ngược) và là functional interface nên dùng lambda/method reference. Sort đa tiêu chí dùng thenComparing.
Câu 14. Vì sao compareTo nên nhất quán với equals? Cho ví dụ.
TreeSet/TreeMap dùng compareTo == 0 để coi là trùng, còn HashSet/HashMap dùng equals. Nếu không nhất quán, hai collection cùng dữ liệu cho kết quả khác nhau: BigDecimal("1.0") vs BigDecimal("1.00") equals false (khác scale) nhưng compareTo 0 → HashSet giữ 2, TreeSet giữ 1. Tương tự record so theo một field. Cách tránh: thêm tie-breaker để compareTo khớp equals, hoặc không dùng TreeSet cho class đó.
Câu 15. Fail-fast là gì? ConcurrentModificationException sinh ra thế nào?
Iterator của ArrayList/HashMap… ghi nhớ modCount lúc tạo; mỗi next() so với modCount hiện tại, lệch thì ném CME ngay. Sửa collection trực tiếp trong for-each là nguyên nhân phổ biến. Đây là cơ chế phát hiện bug sớm (best-effort), không phải để xử lý đồng thời. Xóa an toàn: it.remove() sau next() hoặc removeIf.
Câu 16. CopyOnWriteArrayList vs Collections.synchronizedList?
synchronizedList khóa từng method, iterator vẫn fail-fast, duyệt phải tự synchronized. CopyOnWriteArrayList copy mảng mỗi lần ghi nên iterator là snapshot — duyệt không khóa, không CME; đổi lại ghi rất đắt. Read-heavy (listener) chọn COW; ghi nhiều chọn cấu trúc khác (ConcurrentLinkedQueue, CHM…).
Câu 17. Queue: add/offer, remove/poll, element/peek khác gì?
Cùng hành vi nhưng khác cách báo lỗi: add/remove/element ném exception (IllegalStateException/NoSuchElementException); offer/poll/peek trả false/null. Code production thường dùng nhóm thứ hai trừ khi rỗng/đầy là lỗi lập trình. Với BlockingQueue, put/take còn block thay vì báo lỗi.
Câu 18. PriorityQueue có phải danh sách đã sort không? Có stable không?
Không. Nó là binary heap trên mảng, chỉ đảm bảo peek()/poll() trả phần tử nhỏ nhất (theo natural order hoặc comparator); toString() và for-each in theo thứ tự heap, không sorted. Không stable: hai phần tử cùng độ ưu tiên ra thứ tự bất kỳ — muốn stable phải thêm tie-breaker vào comparator.

Production

Câu 19. computeIfAbsent / merge giải quyết vấn đề gì?
Gộp thao tác "kiểm tra rồi mới sửa" thành một lời gọi atomic về mặt logic, ngắn và tránh null check lặp: computeIfAbsent để khởi tạo value (ví dụ list con), merge để đếm/cộng dồn (merge(k, 1, Integer::sum)). Trên ConcurrentHashMap, computeIfAbsent còn atomic giữa các thread — quan trọng hơn cả cú pháp.
Câu 20. Vì sao không nên dùng key mutable cho HashMap/HashSet?
Key được định vị theo hashCode tại thời điểm put. Nếu sửa field ảnh hưởng hashCode, lần get sau đó sẽ tính bucket khác và không tìm thấy entry (entry vẫn nằm trong map). Dùng key immutable: String, số wrapper, enum, record, UUID, LocalDate.
Câu 21. Vì sao hạn chế Vector, Stack, Hashtable?
Là class từ Java 1.0: mọi method synchronized (khóa toàn cục) nên chậm khi một thread; API lỗi thời (Stack kế thừa Vector nên vẫn cho phép chèn giữa như list); tên method không theo quy ước collection (Hashtable dùng elements()). Thay thế: ArrayList/ArrayDeque/ConcurrentHashMap hoặc concurrent collections.
Câu 22. Chọn collection nào cho: đếm tần suất, LRU, top-K, producer–consumer?
Đếm tần suất → HashMap + merge. LRU → LinkedHashMap access-order + removeEldestEntry. Top-K → PriorityQueue kích thước K. Producer–consumer → BlockingQueue (ArrayBlockingQueue bounded). Nếu phải kể thêm: unique giữ thứ tự → LinkedHashSet, range query → TreeMap.
