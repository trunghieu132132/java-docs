Generics — lập trình tổng quát trong Java

Generics (Java 5, 2004) cho phép viết class, interface, method làm việc với nhiều kiểu dữ liệu mà compiler vẫn kiểm tra kiểu chặt chẽ. Đây là nền tảng của toàn bộ Collections framework: hiểu generics là điều kiện bắt buộc trước khi học 3.3 Collections, 3.7 Optional và 3.8 Stream API. Trang này đi từ vấn đề "Object + cast" thời tiền generics tới bounded type, wildcard & PECS, type erasure, bridge method và các bẫy production.

2. Vì sao có generics Hay hỏi phỏng vấn

Trước Java 5, mọi collection chỉ chứa được Object: bạn bỏ gì vào cũng được, nhưng lấy ra phải tự ép kiểu về đúng loại. Compiler không thể giúp gì vì nó chỉ thấy Object. Ví dụ chạy thật với JDK 25 (code theo phong cách tiền generics):

import java.util.ArrayList;
import java.util.List;

public class KhongGenerics {
    public static void main() {
        List ds = new ArrayList();
        ds.add("hello");
        ds.add(42);

        String s = (String) ds.get(0);
        IO.println("s = " + s);

        try {
            String loi = (String) ds.get(1);
            IO.println("khong bao loi: " + loi);
        } catch (ClassCastException e) {
            IO.println("ClassCastException: " + e.getMessage());
        }
    }
}

Biên dịch bằng javac -Xlint:unchecked sẽ thấy cảnh báo unchecked (phân tích đầy đủ ở mục 7.6). Chương trình vẫn chạy, lỗi chỉ nổ khi tới dòng ép kiểu:

s = hello
ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')

Điểm chí mạng: dòng gây lỗi (ds.add(42)) và dòng nổ ((String) ds.get(1)) nằm xa nhau. Trong hệ thống lớn, stack trace chỉ vào nơi lấy dữ liệu, còn thủ phạm đã bỏ dữ liệu sai từ lâu. Generic ra đời để chuyển lỗi này về compile-time, ngay tại dòng gây lỗi.

Viết lại đúng cách generic:

import java.util.ArrayList;
import java.util.List;

public class GenericsBenefit {
    public static void main() {
        List<String> ds = new ArrayList<>();
        ds.add("hello");

        String s = ds.get(0);
        IO.println("s = " + s + ", length = " + s.length());
        IO.println("class = " + ds.getClass().getName());
    }
}
s = hello, length = 5
class = java.util.ArrayList

Không còn ép kiểu thủ công, và nhét sai kiểu bị chặn ngay lúc compile:

Generics mang lại hai thứ cùng lúc: type safety (compiler bắt lỗi kiểu) và tái sử dụng (một class generic dùng cho mọi type argument). Nhưng đừng quên: cả List<String> lẫn List<Integer> lúc runtime đều chỉ là ArrayList — type argument bị xóa, xem mục 7.

3. Generic class & interface Junior+

Type parameter (tham số kiểu) được khai báo trong ngoặc nhọn ngay sau tên class/interface, rồi dùng như một kiểu thật bên trong:

class Box<T> { T value; } 
public class BoxDemo {
    public static void main() {
        Box<String> ten = new Box<>();
        ten.set("Java");
        IO.println("Box<String> = " + ten.get());
        IO.println("length = " + ten.get().length());

        Box<Integer> so = new Box<>();
        so.set(42);
        IO.println("Box<Integer> = " + so.get());
        IO.println("so + 1 = " + (so.get() + 1));
    }
}

class Box<T> {
    private T value;

    void set(T value) {
        this.value = value;
    }

    T get() {
        return value;
    }
}
Box<String> = Java
length = 4
Box<Integer> = 42
so + 1 = 43

Đọc kỹ ví dụ: trong body của Box<T>, T là một kiểu chưa biết. Khi bạn viết Box<String>, compiler coi như mọi chỗ T đều là String; với Box<Integer> thì là Integer. Nhờ vậy ten.get().length() gọi được ngay mà không cần cast. Cú pháp new Box<>() gọi là diamond operator (Java 7): compiler tự suy type argument từ vế trái.

Type argument bắt buộc là kiểu reference; kiểu nguyên thủy không hợp lệ (dùng wrapper Integer, Double... thay thế):

PrimitiveTypeArgErr.java:3: error: unexpected type
        Box<int> b = new Box<>();
            ^
  required: reference
  found:    int
1 error

Nhiều type parameter

Class/interface có thể có nhiều type parameter, ngăn cách bằng dấu phẩy. Record cũng generic được — và equals/hashCode/toString do compiler sinh vẫn hoạt động đúng với mọi type argument (xem Object Contract — record):

public class PairDemo {
    record Pair<K, V>(K key, V value) {
        static <K, V> Pair<K, V> of(K key, V value) {
            return new Pair<>(key, value);
        }
    }

    public static void main() {
        Pair<String, Integer> tuoi = Pair.of("An", 30);
        Pair<Integer, String> ma = Pair.of(404, "Not Found");

        IO.println(tuoi);
        IO.println(ma);
        IO.println("key = " + tuoi.key() + ", value = " + tuoi.value());
    }
}
Pair[key=An, value=30]
Pair[key=404, value=Not Found]
key = An, value = 30

Generic interface & class implement

Interface cũng nhận type parameter. Class implement có hai lựa chọn: chốt cứng type argument, hoặc giữ generic và chuyển tiếp type parameter:

public class BoxInterfaceDemo {
    public static void main() {
        Box<String> box = new StringBox();
        box.set("hello");
        IO.println(box.get().toUpperCase());
    }
}

interface Box<T> {
    void set(T value);

    T get();
}

class StringBox implements Box<String> {
    private String value;

    @Override
    public void set(String value) {
        this.value = value;
    }

    @Override
    public String get() {
        return value;
    }
}
HELLO

Vì StringBox implements Box<String>, mọi T trong interface trở thành String — method override viết thẳng String, không cần generic lại. Muốn giữ tổng quát thì viết class NumberBox<N extends Number> implements Box<N>. Đây là ứng dụng trực tiếp của nguyên tắc "lập trình theo hợp đồng" trong 2.5 Abstract class vs Interface: interface generic mô tả năng lực, class quyết định kiểu cụ thể.

Nhớ nhanh: type parameter (T) xuất hiện ở phần khai báo; type argument (String) xuất hiện ở phần sử dụng. Một class generic có thể được dùng với vô số type argument nhưng chỉ tồn tại một class duy nhất trên đĩa.

4. Generic method & constructor Junior+

Method có thể có type parameter riêng, khai báo trước return type — không phụ thuộc class chứa nó có generic hay không:

[modifiers] <T> returnType tenMethod(T a, ...) 
import java.util.List;

public class GenericMethodDemo {
    static <T> T pick(T a, T b) {
        return a;
    }

    @SafeVarargs
    static <T> List<T> listOf(T... items) {
        return List.of(items);
    }

    public static void main() {
        String s = pick("a", "b");
        Integer i = pick(1, 2);
        IO.println(s + " / " + i);
        IO.println(listOf("x", "y", "z"));
        IO.println(listOf(1, 2, 3));
    }
}
a / 1
[x, y, z]
[1, 2, 3]

Compiler suy luận kiểu (type inference) từ arguments và ngữ cảnh: pick("a", "b") cho T = String; listOf(1, 2, 3) cho T = Integer. Khi ngữ cảnh không đủ, bạn chỉ định tường minh (explicit type witness): GenericMethodDemo.<String>pick("a", "b"), hoặc Collections.<String>emptyList(). Biến T của method độc lập hoàn toàn với T của class — trùng tên nhưng là hai chuyện khác nhau.

Generic constructor

Constructor cũng có thể khai báo type parameter riêng, thường dùng với bound buộc tham số phải "là một kiểu con" của class:

public class GenericCtorDemo {
    public static void main() {
        Wrapper<Object> w = new Wrapper<Object>("hello");
        IO.println("Object: " + w.get());

        Wrapper<Number> n = new Wrapper<>(42);
        IO.println("Number: " + n.get());
    }
}

class Wrapper<T> {
    private final T value;

    <U extends T> Wrapper(U value) {
        this.value = value;
    }

    T get() {
        return value;
    }
}

Number: 42

Static generic method & giới hạn của static

Static method khai báo type parameter riêng và gọi được độc lập với mọi instance:

public class StaticGenericDemo {
    static <T extends Comparable<T>> T max(T a, T b) {
        return a.compareTo(b) >= 0 ? a : b;
    }

    public static void main() {
        IO.println(max(3, 7));
        IO.println(max("apple", "orange"));
    }
}
7
orange

Nhưng static không được dùng type parameter của class, vì type parameter đó gắn với từng lần khởi tạo instance, còn static member dùng chung cho mọi instance:

Cách sửa đúng: khai báo type parameter cho chính method đó — static <T> T tao() — hoặc truyền Class<T> token (mục 8).

5. Bounded type parameters Hay hỏi phỏng vấn

Bound (giới hạn) thu hẹp tập type argument hợp lệ, đổi lại compiler cho phép gọi các method của bound. Từ khóa luôn là extends, dùng cho cả class lẫn interface:

import java.util.List;

public class BoundedDemo {
    static <T extends Number> double tong(List<T> ds) {
        double s = 0;
        for (T x : ds) {
            s += x.doubleValue();
        }
        return s;
    }

    static <T extends Comparable<T>> T lonNhat(List<T> ds) {
        T max = ds.get(0);
        for (T x : ds) {
            if (x.compareTo(max) > 0) {
                max = x;
            }
        }
        return max;
    }

    public static void main() {
        IO.println(tong(List.of(1, 2, 3)));
        IO.println(tong(List.of(1.5, 2.5)));
        IO.println(lonNhat(List.of("cam", "tao", "xoai")));
        IO.println(lonNhat(List.of(3, 1, 4, 1, 5)));
    }
}
6.0
4.0
xoai
5

Hai kiểu bound quan trọng:

  • <T extends Number> — chỉ nhận Integer, Double, BigDecimal... và nhờ vậy gọi được doubleValue().
  • <T extends Comparable<T>> — bound "tự tham chiếu" (self-referential), đảm bảo mọi T so sánh được với chính kiểu T. Đây chính là bound của Collections.max và Collections.sort trong JDK.

Multiple bounds

Một type parameter có thể có nhiều bound ngăn bằng &. Luật bắt buộc: class (nếu có) phải đứng đầu, sau đó mới tới các interface:

public class MultipleBoundsDemo {
    public static void main() {
        in(new Con());
    }

    static <T extends Cha & In> void in(T x) {
        IO.println(x.ma() + " - " + x.moTa());
    }
}

abstract class Cha {
    abstract int ma();
}

interface In {
    String moTa();
}

class Con extends Cha implements In {
    @Override
    int ma() {
        return 7;
    }

    @Override
    public String moTa() {
        return "Con";
    }
}
7 - Con

Viết sai thứ tự (interface trước class) bị chặn ngay khi compile:

MultipleBoundsErr.java:7: error: interface expected here
class MultipleBoundsErr<T extends InA & ChaB> {
                                        ^
1 error
Liên hệ với type erasure: bound không chỉ để kiểm tra compile — nó quyết định "hình dạng" sau khi xóa kiểu. Erasure của T extends Number là Number; của T extends Cha & In là Cha (bound trái nhất). Method PECS nhờ đó biết cần chèn cast về kiểu nào.

6. Wildcards & PECS Hay hỏi phỏng vấn Production

Generic trong Java bất biến (invariant): Integer là subtype của Number, nhưng List<Integer> không phải subtype của List<Number>. Gán trực tiếp là lỗi compile:

InvarianceErr.java:7: error: incompatible types: List<Integer> cannot be converted to List<Number>
        List<Number> nums = ints;
                            ^
1 error

Nếu Java cho phép dòng trên, đoạn code sau sẽ nhét 1.5 (Double) vào một danh sách thực ra chỉ chứa Integer — phá vỡ type safety mà không ai báo lỗi. Mảng thì khác: mảng covariant nhưng JVM kiểm tra từng lần ghi và ném ArrayStoreException lúc chạy (xem lại Polymorphism — mục 9):

    static double tong(List<? extends Number> ds) {
        double s = 0;
        for (Number n : ds) {
            s += n.doubleValue();
        }
        return s;
    }

    public static void main() {
        IO.println(tong(List.of(1, 2, 3)));
        IO.println(tong(List.of(1.5, 2.5)));

}

PECS — Producer Extends, Consumer Super

Mẫu method kinh điển vận dụng cả hai loại wildcard là Collections.copy — bản rút gọn chạy thật dưới đây:

import java.util.ArrayList;
import java.util.List;

public class CopyDemo {
    static <T> void copy(List<? super T> dest, List<? extends T> src) {
        for (T item : src) {
            dest.add(item);
        }
    }

    public static void main() {
        List<Integer> src = List.of(1, 2, 3);

        List<Number> destNumber = new ArrayList<>();
        copy(destNumber, src);
        IO.println(destNumber);

        List<Object> destObject = new ArrayList<>();
        copy(destObject, src);
        IO.println(destObject);
    }
}
[1, 2, 3]
[1, 2, 3]

Đọc src kiểu ? extends T (producer) rồi ghi vào dest kiểu ? super T (consumer). Nhờ vậy copy dùng được cho mọi cặp list hợp lý mà không mất an toàn kiểu. JDK áp dụng PECS khắp nơi: Collections.addAll, Collection.addAll, List.sort, Stream... — gặp lại ở 3.3 Collections.

Mẹo nhớ: Producer Extends, Consumer Super — nguồn dữ liệu (bạn đọc ra) dùng extends; đích dữ liệu (bạn ghi vào) dùng super. Nếu vừa đọc vừa ghi thì không dùng wildcard, hãy dùng type parameter T.

Wildcard capture — vì sao List<?> không add được

Khi bạn truyền List<String> vào List<?>, compiler tạo một kiểu ẩn gọi là capture (CAP#1) đại diện cho "kiểu nào đó không tên". Mọi thao tác ghi đều bất khả thi vì không thể chắc CAP#1 chính là kiểu bạn đưa:

"Wildcard capture" cũng là tên của kỹ thuật sửa lỗi này: gọi một helper generic để capture biến thành type parameter có tên, rồi thao tác bình thường:

import java.util.ArrayList;
import java.util.List;

public class CaptureHelperDemo {
    static void swap(List<?> ds, int i, int j) {
        swapHelper(ds, i, j);
    }

    static <T> void swapHelper(List<T> ds, int i, int j) {
        T tmp = ds.get(i);
        ds.set(i, ds.get(j));
        ds.set(j, tmp);
    }

    public static void main() {
        List<String> ds = new ArrayList<>(List.of("a", "b"));
        swap(ds, 0, 1);
        IO.println(ds);
    }
}
[b, a]

Khi nào dùng type parameter, khi nào dùng wildcard? Nếu biến kiểu chỉ xuất hiện một lần trong signature (như List<? extends Number>) thì wildcard gọn hơn. Nếu nó xuất hiện nhiều lần và các tham số có quan hệ với nhau (như dest với src trong copy, hay helper swapHelper), bắt buộc dùng type parameter để ràng buộc chúng cùng một kiểu.

7. Type erasure & hệ quả Hay hỏi phỏng vấn Junior+

Java chọn type erasure (xóa kiểu) để generics tương thích ngược với hàng triệu dòng code viết trước Java 5: compiler dùng type argument để kiểm tra, rồi xóa sạch chúng khỏi bytecode. Cụ thể: List<String> → List, T → bound trái nhất (mặc định Object), và compiler tự chèn các lệnh cast ở call site. Bằng chứng:

import java.util.ArrayList;
import java.util.List;

public class ErasureDemo {
    public static void main() {
        List<String> a = new ArrayList<>();
        List<Integer> b = new ArrayList<>();

        IO.println("cung class tai runtime: " + (a.getClass() == b.getClass()));
        IO.println("ten class: " + a.getClass().getName());
        IO.println("a instanceof List: " + (a instanceof List));
    }
}
cung class tai runtime: true
ten class: java.util.ArrayList
a instanceof List: true

Erasure là nguồn gốc của gần như mọi câu hỏi phỏng vấn khó về generics. Sáu hệ quả lớn:

7.1 Không tạo được thứ gì "mang theo" T lúc runtime

Vì T không còn tồn tại sau compile, JVM không biết khởi tạo cái gì:

Trong khi mảng raw thì vẫn tạo được, kèm cảnh báo (và mất an toàn kiểu): List<String>[] mang = new List[10]; — unchecked conversion. Ba cách thay thế đúng:

  • Dùng collection thay mảng: 99% trường hợp production nên là List<T>.
  • Truyền factory: Supplier<T> (học ở 3.6) hoặc IntFunction<T[]> để tạo mảng.
  • Truyền Class<T> token rồi dùng reflection: Array.newInstance(type, n) (mục 8).

7.2 instanceof không kiểm tra được type argument

Chỉ kiểm tra được phần "thô": o instanceof List hoặc o instanceof List<?> (unbounded wildcard được phép vì không khẳng định type argument cụ thể). Muốn kiểm tra chính xác phải mang theo Class<T> token.

7.3 Không overload được nếu erasure trùng nhau

ErasureOverloadErr.java:7: error: name clash: m(List<Integer>) and m(List<String>) have the same erasure
    void m(List<Integer> ds) {
         ^

Hai method này lúc runtime đều là m(List). Cùng lý do, không thể có hai method chỉ khác nhau ở type parameter hay return type generic. Sửa bằng cách đổi tên method cho rõ nghĩa (thường là lựa chọn tốt nhất) hoặc dùng tham số phân biệt.

7.4 Bridge method — chi tiết ẩn giữ compiler

Khi class/interface generic bị override với kiểu cụ thể, compiler sinh thêm một bridge method để giữ tương thích với bytecode gọi qua kiểu cha. Ví dụ HoSo implements Comparable<HoSo>:

public class BridgeGenericsDemo {
    public static void main() {
        HoSo a = new HoSo("An", 30);
        HoSo b = new HoSo("Binh", 25);
        IO.println("goi truc tiep: " + a.compareTo(b));

        Comparable<HoSo> c = a;
        IO.println("qua Comparable: " + c.compareTo(b));
    }
}

class HoSo implements Comparable<HoSo> {
    final String ten;
    final int tuoi;

    HoSo(String ten, int tuoi) {
        this.ten = ten;
        this.tuoi = tuoi;
    }

    @Override
    public int compareTo(HoSo other) {
        return Integer.compare(this.tuoi, other.tuoi);
    }
}
goi truc tiep: 1
qua Comparable: 1

Chạy javap -p HoSo sẽ thấy tận hai method compareTo; còn javap -v cho thấy cờ ACC_BRIDGE của bản nhận Object:

Compiled from "BridgeGenericsDemo.java"
class HoSo implements java.lang.Comparable<HoSo> {
  final java.lang.String ten;
  final int tuoi;
  HoSo(java.lang.String, int);
  public int compareTo(HoSo);
  public int compareTo(java.lang.Object);

Compiler sinh bridge ở mọi nơi generic bị "chốt kiểu": interface Comparable<T> khai báo compareTo(T), erasure thành compareTo(Object); class của bạn viết compareTo(HoSo); bridge đứng giữa nhận Object, cast và gọi method thật. Bridge cũng xuất hiện với covariant return type — cùng chủ đề với Polymorphism — mục 9.

7.5 Heap pollution & @SafeVarargs

Varargs generic (T... items) thực chất là mảng T[] — mà mảng generic không kiểm tra được kiểu phần tử, nên có thể "ô nhiễm heap" (heap pollution): mảng khai báo List<String>[] nhưng chứa List<Integer>. Compiler cảnh báo bằng -Xlint:unchecked:

GenericVarargsWarn.java:4: warning: [unchecked] Possible heap pollution from parameterized vararg type T
    static <T> List<T> listOf(T... items) {
                                   ^
  where T is a type-variable:
    T extends Object declared in method <T>listOf(T...)
1 warning

Nguy hiểm đến mức nào? Đây là hậu quả chạy thật — chú ý compiler hoàn toàn im lặng vì method được gắn @SafeVarargs (một lời hứa bị phá vỡ):

import java.util.List;

public class HeapPollutionDemo {
    @SafeVarargs
    static void nguyHiem(List<String>... ds) {
        Object[] mang = ds;
        mang[0] = List.of(42);
        String s = ds[0].get(0);
        IO.println("khong bao loi: " + s);
    }

    public static void main() {
        try {
            nguyHiem(java.util.List.of("a"));
        } catch (ClassCastException e) {
            IO.println("ClassCastException: " + e.getMessage());
        }
    }
}
ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')

Phiên bản an toàn — chỉ đọc/truyền mảng đi tiếp, không lưu trữ hay ghi đè phần tử — và gắn @SafeVarargs để tắt cảnh báo một cách trung thực:

import java.util.List;

public class SafeVarargsDemo {
    @SafeVarargs
    static <T> List<T> listOf(T... items) {
        return List.of(items);
    }

    public static void main() {
        IO.println(listOf("a", "b"));
    }
}
[a, b]
Luật @SafeVarargs: chỉ gắn được lên static method, final method, private instance method (Java 9+) hoặc constructor — nơi chắc chắn không bị override. Chỉ gắn khi method thực sự an toàn (không lưu mảng varargs ở đâu, không gán phần tử). Nếu không dám khẳng định, hãy để cảnh báo hiện ra và xử lý — JDK dùng @SafeVarargs cho List.of(E...), Arrays.asList(T...).

7.6 Raw type — kẻ phá hoại thầm lặng

Raw type là generic class dùng mà không có type argument: List thay vì List<String>. Chỉ cần một chỗ raw, mọi kiểm tra kiểu trên đường đi của dữ liệu đều có thể bị vô hiệu:

import java.util.ArrayList;
import java.util.List;

public class RawTypeDemo {
    public static void main() {
        List raw = new ArrayList();
        raw.add("hello");
        raw.add(42);

        String s = (String) raw.get(1);
        IO.println(s);
    }
}

Quy tắc production: không bao giờ dùng raw type trong code mới. Ba trường hợp buộc phải chấp nhận (và không sinh warning nếu dùng đúng):

  • Class literal không có generic: List.class (không viết được List<String>.class), dùng Class<?> nếu cần biến.
  • instanceof với raw: o instanceof List hoặc instanceof List<?>.
  • API cũ chưa generic (một số thư viện legacy); phải cô lập ở biên và ghi chú rõ.
Phân biệt: List (raw) tắt hết kiểm tra; List<Object> kiểm tra đầy đủ nhưng cho chứa mọi object; List<?> chỉ cho đọc ra Object và không cho ghi. Cần "chứa mọi thứ" thì dùng List<Object>, không dùng raw.

Bẫy "ép kiểu qua token" và cách dùng Class<T> cho đúng — lỗi hiện ra rõ ràng ngay tại dòng gọi, kèm thông báo của chính Class.cast:

import java.util.Map;

public class ClassTokenDemo {
    static <T> T lay(Map<String, Object> data, String key, Class<T> type) {
        return type.cast(data.get(key));
    }

    public static void main() {
        Map<String, Object> data = Map.of("ten", "An", "tuoi", 30);

        String ten = lay(data, "ten", String.class);
        Integer tuoi = lay(data, "tuoi", Integer.class);
        IO.println(ten + " - " + tuoi);

        try {
            Integer sai = lay(data, "ten", Integer.class);
            IO.println(sai);
        } catch (ClassCastException e) {
            IO.println("ClassCastException: " + e.getMessage());
        }
    }
}

Class<T> token là cầu nối duy nhất giữa generic lúc compile và kiểu thật lúc runtime: nó cho phép method generic biết type argument cụ thể để validate, tạo instance/mảng, hoặc parse. Đây cũng là cách các framework DI/serialization (Spring, Jackson) lấy được kiểu generic — đào sâu ở 2.9 Annotations & Reflection.

9. Góc Node.js — Generics trong TypeScript Junior+

Nếu bạn đến từ TypeScript, cú pháp generic trông rất quen: class Box<T>, <T extends Number>, type parameter trên method. Nhưng triết lý khác nhau ở ba điểm: hệ thống kiểu nominal (Java) vs structural (TS), cách xử lý variance, và mức độ kiểm tra lúc runtime.

Chạy thật trực tiếp bằng Node v22.23 (--experimental-strip-types chỉ xóa type rồi chạy JS, không kiểm tra kiểu — đúng tinh thần erasure):

// generics-node.ts - chay: node --experimental-strip-types generics-node.ts
function first<T>(arr: T[]): T {
  return arr[0];
}

const ten: string = first(["a", "b"]);
console.log("ten =", ten);

const ds: number[] = [1, 2, 3];

  • Type chỉ có trên giấy: dòng cuối nhét "x" vào mảng khai báo number[] mà chương trình vẫn chạy và in ra phần tử chuỗi. TS cố tình covariant number[] → unknown[] (giống Java cho mảng covariant), nhưng JS/Node không có JVM để kiểm tra — cái giá là hoàn toàn không có lưới an toàn runtime.
  • Java cần wildcard vì nominal + invariant; TS thường không cần "PECS" bởi kết hợp structural typing và variance annotation, nhưng cái giá là tính unsound cao hơn. Muốn an toàn trong TS, dùng readonly T[] (chặn push) và tránh cast qua any.
  • Không có bridge method trong TS/JS vì method call không bị ràng buộc bởi descriptor kiểu như bytecode Java.
  • Primitive: cả hai đều không cho type argument nguyên thủy — Java bắt dùng wrapper (Integer), TS chỉ có number nên không gặp vấn đề này.

10. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Generics là gì? Nó giải quyết vấn đề gì?
Generics (Java 5) cho phép class/interface/method tham số hóa theo kiểu dữ liệu: Box<T>, List<String>. Nó giải quyết hai vấn đề của thời dùng Object + cast: (1) chuyển lỗi sai kiểu từ runtime (ClassCastException) sang compile-time; (2) bỏ ép kiểu thủ công nhờ compiler biết kiểu. Lợi ích kèm theo là tái sử dụng: một class generic dùng cho mọi type argument.
Câu 2. Type parameter và type argument khác nhau thế nào?
Type parameter là biến kiểu trong phần khai báo — T trong class Box<T>, E trong interface List<E>. Type argument là kiểu cụ thể trong phần sử dụng — String trong Box<String>. Cùng quan hệ với parameter/argument của method.
Câu 3. Vì sao List<int> không hợp lệ? Dùng gì thay thế?
Type argument phải là kiểu reference; compiler báo error: unexpected type ... required: reference, found: int. Dùng wrapper tương ứng: List<Integer>, List<Double>... Autoboxing lo phần chuyển đổi giá trị, còn về bản chất trong list lưu reference tới object wrapper.
Câu 4. Generic method suy luận kiểu thế nào? Khi nào cần chỉ định tường minh?
Compiler suy T từ arguments và target type: pick("a", "b") → T = String; List<String> x = listOf() → T = String nhờ target typing (Java 8+). Khi ngữ cảnh không đủ (ví dụ Collections.emptyList() trong biểu thức mơ hồ), dùng explicit type witness: Collections.<String>emptyList().

Nâng cao (Junior+)

Câu 5. Vì sao không gán được List<Integer> cho biến List<Number>?
Vì generic invariant. Nếu cho phép, qua alias List<Number> ta có thể gọi nums.add(1.5) — nhét Double vào list thực ra chỉ chứa Integer, và lỗi chỉ nổ ở nơi khác lúc lấy phần tử ra. Java chặn ngay lúc compile. Khi cần linh hoạt, dùng List<? extends Number> (chỉ đọc) hoặc List<? super Integer> (chỉ ghi).
Câu 6. Mảng covariant khác generic invariant thế nào?
Mảng covariant từ thời trước generics: String[] gán được cho Object[], nhưng JVM kiểm tra mỗi lần ghi nên arr[0] = 42 ném ArrayStoreException lúc chạy. Generic chọn invariant để kiểm tra ngay lúc compile, đổi lại phải dùng wildcard khi cần quan hệ subtype. Xem demo tại Polymorphism — mục 9.
Câu 7. PECS là gì? Cho ví dụ.
Producer Extends, Consumer Super: nguồn dữ liệu chỉ đọc thì dùng ? extends T, đích dữ liệu chỉ ghi thì dùng ? super T. Ví dụ chuẩn: static <T> void copy(List<? super T> dest, List<? extends T> src) — đọc src ra T rồi ghi vào dest. JDK dùng PECS trong Collections.copy/addAll, Collection.addAll.
Câu 8. List<? extends Number> có add được không? List<? super Integer> đọc ra gì?
? extends: không add được gì ngoài null, vì compiler không biết list thực sự là List<Integer> hay List<Double>; add có thể phá vỡ kiểu. ? super: add Integer (và subtype) thoải mái, nhưng đọc ra chỉ dám chắc Object — muốn đọc Integer phải cast hoặc thiết kế lại signature.
Câu 9. Wildcard capture là gì? Xử lý thế nào?
Khi dùng List<?>, compiler tạo một kiểu ẩn CAP#1 đại diện "kiểu nào đó"; ghi vào list bị chặn vì không thể chứng minh giá trị thuộc CAP#1. Cách xử lý chuẩn là capture helper: một method generic static <T> void helper(List<T> ds) để compiler "đặt tên" cho kiểu bị capture rồi thao tác bình thường (ví dụ swap(List<?>, int, int) gọi swapHelper(List<T>, int, int)).
Câu 10. Type erasure là gì? Kể các hệ quả chính.
Erasure là việc compiler xóa type argument khi biên dịch để tương thích ngược: List<String> thành List, T thành bound trái nhất (Object nếu không bound); compiler chèn cast tại call site. Hệ quả: không new T(), không new T[]/new List<String>[], không instanceof List<String>, không overload nếu erasure trùng, không dùng type param của class trong static context, phát sinh bridge method và heap pollution với varargs generic.
Câu 11. Bridge method là gì? Tại sao phải sinh ra?
Khi override method generic bằng kiểu cụ thể (ví dụ compareTo(HoSo) thay cho compareTo(Object) sau erasure), compiler sinh thêm một method cầu nhận đúng kiểu đã xóa, cast rồi gọi method thật. Nhờ vậy bytecode cũ gọi qua interface/class cha vẫn chạy đúng. Kiểm chứng bằng javap -p: thấy hai compareTo, bản nhận Object có cờ ACC_BRIDGE, ACC_SYNTHETIC.
Câu 12. Heap pollution là gì? @SafeVarargs dùng khi nào?
Heap pollution là tình huống biến List<String>[] lại chứa List<Integer>, làm lỗi cast nổ lúc chạy. Varargs generic (T... args) là nguồn phổ biến vì mảng varargs không kiểm tra được kiểu phần tử. @SafeVarargs là lời hứa "method không lưu/ghi vào mảng varargs" — chỉ gắn lên static, final, private instance method hoặc constructor; gắn bừa lên method không an toàn có thể dẫn tới CCE lúc chạy.
Câu 13. Raw type là gì? Vì sao tránh? Khi nào buộc dùng?
Raw type là dùng generic class/interface không có type argument: List. Nó tắt mọi kiểm tra kiểu liên quan (unchecked warnings) nên lỗi chỉ nổ lúc chạy. Tránh dùng trong code mới; thay bằng List<Object> nếu thực sự cần chứa mọi thứ. Buộc dùng ở: class literal (List.class), instanceof (o instanceof List hoặc List<?>), và API legacy chưa generic.
Câu 14. Class<T> token dùng để làm gì?
Vì type argument bị xóa lúc runtime, muốn method generic biết kiểu cụ thể thì phải truyền Class<T> — "class object" còn giữ thông tin kiểu thật. Nó cho phép: validate/parse (type.cast(obj), type.isInstance(obj)), tạo instance (type.getDeclaredConstructor().newInstance()), tạo mảng (Array.newInstance(type, n)), và là nền tảng để framework reflection lấy generic type (xem 2.9).

In ra 2.5. T = Number nên set nhận cả Integer (boxing 1) lẫn Double (2.5). Lần set thứ hai ghi đè giá trị cũ, nên chỉ còn 2.5.
Bài 2 
public class Exercise02 {
    public static void main() {
        IO.println(hop(1, "x"));
        IO.println(hop("a", 2.5));
    }

    static <T> T hop(T a, T b) {
        IO.println(a.getClass().getSimpleName() + " / " + b.getClass().getSimpleName());
        return a;
    }
}
In ra bốn dòng: Integer / String, 1, String / Double, a. Compiler suy T thành kiểu chung (intersection) của các argument, nhưng lúc runtime object vẫn giữ class thật — getClass() cho biết chính xác Integer/String. Đây là minh họa "type bị xóa nhưng object thật vẫn còn".
Bài 3 
import java.util.List;

public class Exercise03 {
    public static void main() {
        List<? extends Number> ds = List.of(1, 2.5, 3);
        double tong = 0;
        for (Number n : ds) {
            tong += n.doubleValue();
        }
        IO.println(tong);
    }
}
In ra 6.5. List.of(1, 2.5, 3) suy kiểu chung của Integer và Double, gán được cho List<? extends Number>. Vòng for đọc từng phần tử như Number, cộng 1 + 2.5 + 3 = 6.5. Thử ds.add(...) sẽ lỗi compile (xem mục 6).
Bài 4 
static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (T x : src) {
        dest.add(x);
    }
}

// trong main:
List<Integer> src = List.of(1, 2);
List<Object> dest = new ArrayList<>();
copy(dest, src);
IO.println(dest);
In ra [1, 2]. T suy ra Integer; src khớp ? extends Integer, dest khớp ? super Integer. Đây là PECS: đọc từ producer src, ghi vào consumer dest.
Bài 5

In ra true rồi java.util.ArrayList. Type erasure xóa String/Integer, cả hai biến cùng trỏ tới một class runtime duy nhất. Vì vậy không thể phân biệt hai list này bằng instanceof hay getClass().

In ra a, sau đó chương trình dừng với Exception in thread "main" java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String .... Code compile kèm unchecked warning do raw type. Đây là lý do không dùng raw type: lỗi chỉ lộ lúc chạy, không ai chặn lúc viết.
Bài 7 
IO.println(lonNhat(List.of(3, 9, 4)));
IO.println(lonNhat(List.of("b", "a", "c")));

static <T extends Comparable<T>> T lonNhat(List<T> ds) {
    T max = ds.get(0);
    for (T x : ds) {
        if (x.compareTo(max) > 0) {
            max = x;
        }
    }
    return max;
}
In ra 9 rồi c. Bound T extends Comparable<T> cho phép gọi compareTo; so sánh chuỗi theo thứ tự từ điển nên max("b","a","c") = "c".
Bài 8 
List<Integer> a = Arrays.asList(1, 2, 3);
List<int[]> b = Arrays.asList(new int[] {1, 2, 3});
IO.println(a.size() + " / " + b.size());
IO.println(b.get(0)[1]);
In ra 3 / 1 rồi 2. Arrays.asList(1, 2, 3) nhận varargs Integer... nên có 3 phần tử. Còn Arrays.asList(new int[]{1,2,3}) nhận một argument kiểu int[] (mảng không tự bung ra), nên list có đúng 1 phần tử là cả mảng; b.get(0)[1] truy cập phần tử thứ hai của mảng đó.

12. Cheat sheet & checklist

Cheat sheet

Checklist tự đánh giá trước phỏng vấn

  • Viết được generic class, generic interface, generic method không cần tra cứu.
  • Phân biệt type parameter và type argument, diamond operator.
  • Giải thích được vì sao generic invariant và vì sao mảng covariant lại nguy hiểm.
  • Đọc thành thạo ? extends / ? super và phát biểu PECS.
  • Viết được method copy dạng PECS và giải thích từng wildcard.
  • Kể được ít nhất 5 hệ quả của type erasure kèm ví dụ.
  • Giải thích bridge method và chỉ ra nó bằng javap.
  • Giải thích heap pollution và luật dùng @SafeVarargs.
  • Biết vì sao tránh raw type, ba trường hợp buộc dùng, và phân biệt raw / List<Object> / List<?>.
  • Dùng Class<T> token để validate/tạo instance thay vì cast mù.
  • Nhận diện bẫy Arrays.asList với mảng nguyên thủy và list fixed-size.
  • So sánh được generics Java với TypeScript: erasure, covariance, any vs raw type.
