Exception Handling — xử lý lỗi trong Java

Exception (ngoại lệ) là cơ chế Java báo và xử lý lỗi khi chương trình đang chạy: một method "ném" lỗi lên, method gọi nó "bắt" và xử lý. Khác JavaScript/Node, Java phân biệt checked exception — compiler buộc bạn catch hoặc khai báo throws — và unchecked exception — thường là bug lập trình, không bị ép. Trang này đi từ Throwable, try/catch/finally, try-with-resources, chaining, custom exception tới cách xử lý lỗi trong project đơn hàng production.

2.2 Checked exception — compiler ép xử lý

Checked exception là mọi lớp con của Exception trừ RuntimeException và các lớp con của nó. Đặc điểm nhận dạng: nếu một method có thể ném checked exception, code gọi nó phải nằm trong try/catch hoặc method gọi phải khai báo throws. Đây là kiểm tra lúc biên dịch, không phải lúc chạy (JLS §11.2).

Quên xử lý sẽ không compile được — đúng nghĩa đen:

CheckedErr.java:9: error: unreported exception IOException; must be caught or declared to be thrown
        doc();
           ^
1 error

Hai cách sửa hợp lệ. Cách 1 — bắt tại chỗ:

import java.io.IOException;

public class CheckedOkDemo {
    static void doc() throws IOException {
        throw new IOException("khong doc duoc file");
    }

    public static void main() {
        try {
            doc();
        } catch (IOException e) {
            IO.println("da bat: " + e.getMessage());
        }
    }
}
da bat: khong doc duoc file

Cách 2 — khai báo throws để đẩy trách nhiệm lên caller (học ở mục 5).

2.3 Unchecked exception — lỗi lập trình, không bị ép

RuntimeException và các lớp con là unchecked. Compiler không kiểm tra và cũng không bắt buộc khai báo. Chúng đại diện cho bug hoặc vi phạm hợp đồng: tính toán trên null, index ngoài mảng, tham số sai, state sai.

Đoạn này chạy tốt dù chia(1, 0) chắc chắn ném lỗi — vì không cần try/catch bắt buộc:

public class UncheckedDemo {
    static int chia(int a, int b) {
        return a / b;
    }

    public static void main() {
        IO.println("chia(10, 2) = " + chia(10, 2));
        try {
            chia(1, 0);
        } catch (ArithmeticException e) {
            IO.println("bat ArithmeticException: " + e.getMessage());
        }
    }
}
chia(10, 2) = 5
bat ArithmeticException: / by zero
Đừng nhầm mọi lỗi số học đều thành exception: chia cho 0 ném ArithmeticException, còn tràn số nguyên lại âm thầm quay vòng (xem Biến trong Java — mục 9). Muốn chặn tràn phải tự kiểm tra trước khi tính.

2.4 Vì sao checked tồn tại — và chỉ trích

  • Lý do tồn tại — biến hợp đồng của API thành thứ compiler kiểm tra được: đọc file có thể thất bại, JDBC có thể mất kết nối; chữ ký throws IOException buộc người gọi ý thức được khả năng thất bại đó. Oracle tutorial gọi đây là lợi ích chính.
  • Chỉ trích — C# (thiết kế bởi Anders Hejlsberg) cố tình bỏ checked exception; Kotlin cũng không có. Lý do: exception lan qua nhiều tầng làm chữ ký method nào cũng phình to; lambda/Stream của Java 8 không tương thích tốt với checked nên sinh ra các "unchecked wrapper" như UncheckedIOException, CompletionException.
  • Java vẫn giữ chủ yếu vì tương thích ngược — đổi luật này sẽ phá vỡ hàng triệu dòng code và mọi thư viện. Vì vậy bạn vẫn phải hiểu checked dù phe "unchecked" đông hơn.

Nguyên tắc thực dụng khi tự thiết kế API:

  • Checked — khi caller thực sự có cách phục hồi hợp lý (retry, dùng file mặc định, báo người dùng chọn file khác), hoặc khi thất bại là một phần tự nhiên của tác vụ (I/O, mạng, DB).
  • Unchecked — khi lỗi là bug (NPE, index sai), vi phạm precondition (soLuong <= 0), và luật nghiệp vụ (hết hàng, đơn sai) theo trường phái hiện đại: caller không thể "xử lý cho qua", phải để lộ ra cho tầng biên dịch thành response.
  • Error — không bắt, không ném, không khai báo.
Chốt gọn: chỉ Throwable mới throw được. Compiler ép xử lý checked; không ép unchecked. Error là chuyện của JVM — sửa gốc, đừng bắt. Khi phân vân thiết kế custom exception: mặc định chọn unchecked; chỉ dùng checked khi caller chắc chắn phải recover.

2.5 JEP 358 — Helpful NullPointerException (mặc định từ JDK 15)

Từ JDK 15, message của NullPointerException không còn trống rỗng: JVM mô tả chính xác biểu thức nào null và vì sao. Tính năng bật mặc định (JEP 358); tắt bằng -XX:-ShowCodeDetailsInExceptionMessages, bật lại bằng -XX:+ShowCodeDetailsInExceptionMessages.

public class HelpfulNpeDemo {
    static class Khach {
        DiaChi diaChi;
    }

    static class DiaChi {
        String thanhPho;
    }

    static Khach khach = new Khach();

    public static void main() {
        try {
            IO.println(khach.diaChi.thanhPho);
        } catch (NullPointerException e) {
            IO.println("message: " + e.getMessage());
        }
        IO.println("tiep tuc chay");
    }
}
message: Cannot read field "thanhPho" because "HelpfulNpeDemo.khach.diaChi" is null
tiep tuc chay

Khi tắt bằng java -XX:-ShowCodeDetailsInExceptionMessages HelpfulNpeDemo.java, message trở về trống:

message: null
tiep tuc chay
Tên trong message lấy từ thông tin debug khi biên dịch: biến static/field hiện tên đầy đủ (HelpfulNpeDemo.khach.diaChi), còn biến local không có tên debug sẽ hiện dạng <local0>. Chi tiết này chỉ giúp debug — không nên parse message để xử lý logic.

2.6 NoClassDefFoundError vs ClassNotFoundException

Hai cái tên na ná nhau nhưng nằm ở hai tầng và hai họ khác nhau:

Do ai némCode của bạn qua reflection: Class.forName, ClassLoader.loadClassJVM khi bytecode đang chạy tham chiếu tới class không load được (thiếu classpath lúc chạy, lỗi static initializer...)
Ý nghĩa"Tìm class theo tên mà không thấy" — biết trước, có thể xử lý (plugin, JDBC driver)"Class chắc chắn phải có đã không load nổi" — thường là lỗi đóng gói/deploy, không nên bắt
Mẹo nhớ: ClassNotFoundException là bạn chủ động yêu cầu load class và nhận thông báo; NoClassDefFoundError là JVM nổ khi đang chạy code tham chiếu tới class đó. Cùng một class có thể ném NoClassDefFoundError vì lần load đầu tiên static initializer của nó đã ném lỗi — nguyên nhân production rất hay bị bỏ sót khi đọc log.
ExceptionInInitializerError — mắt xích còn thiếu: nếu static initializer (static block hoặc static field) ném exception ngay lần đầu class được dùng, JVM gói exception đó vào ExceptionInInitializerError. Class bị đánh dấu lỗi vĩnh viễn, nên mọi lần dùng lại sau đó JVM ném thẳng NoClassDefFoundError với cause chính là ExceptionInInitializerError của lần đầu. Cả hai đều là LinkageError, nên log production có thể chỉ hiện NoClassDefFoundError trong khi nguyên nhân gốc nằm ở lần init hỏng trước đó.
public class InitErrorDemo {
    static class CauHinh {
        static int giaTri;

        static {
            giaTri = docCauHinh();
        }

        static int docCauHinh() {
            throw new IllegalStateException("thieu file cau hinh");
        }
    }

    public static void main() {
        for (int lan = 1; lan <= 2; lan++) {
            try {
                IO.println("lan " + lan + ": " + CauHinh.giaTri);
            } catch (LinkageError e) {
                IO.println("lan " + lan + ": " + e.getClass().getSimpleName()
                        + " (cause: " + e.getCause().getClass().getSimpleName() + ")");
            }
        }
    }
}

3.2 Bẫy return trong finally nuốt exception

Nếu finally chứa return, nó không chỉ chạy trước khi thoát — nó ghi đè mọi exception đang bay. Exception biến mất không dấu vết:

public class FinallyReturnTrap {
    static int tinh() {
        try {
            throw new IllegalStateException("loi that su");
        } finally {
            return 42;          // nuot exception!
        }
    }

    public static void main() {
        IO.println("ket qua: " + tinh());
        IO.println("main ket thuc binh thuong");
    }
}
ket qua: 42
main ket thuc binh thuong

Chương trình không hề biết đã có IllegalStateException. javac mặc định im lặng; chỉ khi bật lint mới thấy cảnh báo:

$ javac -Xlint:finally FinallyReturnTrap.java
FinallyReturnTrap.java:7: warning: [finally] finally clause cannot complete normally
        }
        ^

Quy tắc: không bao giờ đặt return, break, continue hay throw trong finally. finally chỉ để giải phóng tài nguyên, ghi log kết thúc, phục hồi state. Từ Java 7, việc đóng tài nguyên nên giao hẳn cho try-with-resources ở mục 4.

3.3 Multi-catch — một catch cho nhiều loại lỗi

Khi nhiều exception được xử lý giống nhau, gộp bằng dấu |. Biến e trong multi-catch là implicitly final (JLS §14.20) — không phải "effectively final" như biến thường dùng trong lambda — và có kiểu chung nhất của các nhánh:

import java.io.IOException;

public class MultiCatchDemo {
    static void xuLy(String kieu) {
        try {
            switch (kieu) {
                case "io" -> throw new IOException("loi io");
                case "number" -> Integer.parseInt("abc");
                case "ok" -> IO.println("khong loi");
                default -> IO.println("khong biet");
            }
        } catch (IOException | NumberFormatException e) {
            IO.println("bat: " + e.getClass().getSimpleName() + " - " + e.getMessage());
        }
    }

    public static void main() {
        xuLy("io");
        xuLy("number");
        xuLy("ok");
    }
}
bat: IOException - loi io
bat: NumberFormatException - For input string: "abc"
khong loi

Ba ràng buộc của multi-catch:

  • Các nhánh không được có quan hệ cha-con với nhau — nếu không sẽ vô nghĩa vì nhánh cha đã bắt hết. Đây là lỗi compile:
MultiCatchSubclassErr.java:8: error: Alternatives in a multi-catch statement cannot be related by subclassing
        } catch (IOException | FileNotFoundException e) {
                               ^
  Alternative FileNotFoundException is a subclass of alternative IOException
1 error
  • Biến e là implicitly final — JLS nói rõ nó "is not considered effectively final" — nên gán lại e = ... bị javac chặn:
MultiCatchAssignErr.java:8: error: multi-catch parameter e may not be assigned
            e = new IOException("khac");
            ^
1 error
  • Ngược lại, biến của catch đơn (catch (IOException e)) gán lại được; chỉ khi muốn capture nó trong lambda mới cần nó effectively final.
  • Khi rethrow, compiler vẫn phân tích được tập exception có thể bay ra (precise rethrow, JLS §11.2.2): method khai báo throws IOException, SQLException thì trong multi-catch vẫn giữ đúng hai kiểu đó.

3.4 Thứ tự catch — subclass phải đứng trước

Java duyệt các nhánh catch từ trên xuống và chọn nhánh khớp đầu tiên. Nhánh cha bắt hết con, nên nhánh con đặt sau là code chết:

CatchOrderErr.java:7: error: exception RuntimeException has already been caught
        } catch (RuntimeException e) {
          ^
1 error

Ngược lại, catch một checked exception mà try không thể ném cũng là lỗi compile — hữu ích để phát hiện code vô nghĩa:

CatchNeverThrownErr.java:7: error: exception IOException is never thrown in body of corresponding try statement
        } catch (IOException e) {
          ^
1 error
Thứ tự chuẩn: exception cụ thể nhất trước (subclass), rồi tới cha, cuối cùng (nếu buộc phải) mới tới Exception. Mẹo nhớ: càng "rộng" càng nằm dưới.

3.5 Catch chung chung — dùng có kiểm soát

catch (Exception e) bắt mọi exception (trừ Error). Nó hợp lệ ở tầng biên — nơi mọi lỗi phải được biến thành log/response an toàn, không được để lộ stack trace ra người dùng: main, HTTP handler, message listener, task định kỳ.

Nhưng trong logic service/repository, catch chung chung là anti-pattern: bạn vô tình bắt cả NullPointerException do bug của chính mình, che mất lỗi và biến nó thành "trạng thái bình thường". Hãy bắt đúng thứ có thể xảy ra và xử lý được.

4. try-with-resources Hay hỏi phỏng vấn Production

Từ Java 7, tài nguyên (file, socket, connection...) được khai báo ngay trong try và được đóng tự động khi khối try kết thúc — dù bình thường, có exception, hay có return. Chính compiler sinh code gọi close() đúng thứ tự (JLS §14.20.3, pseudo-code ở mục 4.4); JVM chỉ thực thi bytecode đó. Không cần finally thủ công.

try (TaiNguyen a = ...; TaiNguyen b = ...) { ... }

4.1 AutoCloseable vs Closeable

Hai interface là điều kiện để một object đứng trong try (...):

public interface AutoCloseable { void close() throws Exception; }
public interface Closeable extends AutoCloseable { void close() throws IOException; }
  • AutoCloseable (Java 7) — close() cho phép ném mọi Exception; là hợp đồng tổng quát nhất.
  • Closeable (Java 5) — chuyên cho I/O, close() chỉ ném IOException, và hợp đồng yêu cầu gọi nhiều lần vẫn an toàn (idempotent).
  • Viết resource mới cho I/O thì implement Closeable; cho thứ khác (lock, transaction, timer) thì AutoCloseable là đủ.

4.2 Thứ tự đóng là NGƯỢC với thứ tự mở

public class TwrOrderDemo {
    static class TaiNguyen implements AutoCloseable {
        private final String ten;

        TaiNguyen(String ten) {
            this.ten = ten;
        }

        public void close() {
            IO.println("dong " + ten);
        }
    }

    public static void main() {

             TaiNguyen b = new TaiNguyen("B")) {

Thứ tự này quan trọng: nếu B dùng dữ liệu của A (ví dụ BufferedWriter bọc FileWriter), đóng theo thứ tự mở sẽ làm B flush vào writer đã đóng. Compiler sinh code đóng hộ bạn đúng thứ tự an toàn (JLS §14.20.3).

4.3 Suppressed exception — không đánh mất lỗi khi đóng

Câu hỏi khó: nếu thân try ném exception, rồi lúc đóng resource cũng ném exception, lỗi nào thắng? try-with-resources giữ cả hai: lỗi chính được ném ra, lỗi khi đóng bị "đính kèm" (suppressed) và đọc bằng getSuppressed().

public class SuppressedDemo {
    static class TaiNguyen implements AutoCloseable {
        private final String ten;

        TaiNguyen(String ten) {
            this.ten = ten;
        }

        void lamViec() {
            throw new RuntimeException("loi khi lam viec");
        }

        public void close() {
            throw new RuntimeException("loi khi dong " + ten);
        }
    }

    public static void main() {
        try (TaiNguyen a = new TaiNguyen("A");
             TaiNguyen b = new TaiNguyen("B")) {
            a.lamViec();
        } catch (RuntimeException e) {
            IO.println("bat      : " + e.getMessage());
            for (Throwable s : e.getSuppressed()) {
                IO.println("suppressed: " + s.getMessage());
            }
        }
    }
}
bat      : loi khi lam viec
suppressed: loi khi dong B
suppressed: loi khi dong A

Lỗi chính là "loi khi lam viec"; hai lỗi đóng resource bám theo đúng thứ tự đóng ngược (B rồi A). API dành cho bạn khi tự implement: Throwable.addSuppressed(Throwable) và getSuppressed().

4.4 Vì sao finally thủ công làm mất lỗi gốc

Cùng tình huống nhưng đóng bằng finally — exception khi đóng ghi đè exception của thân try và lỗi gốc mất tích (cause là null):

public class FinallyCloseOverwriteDemo {
    static class TaiNguyen implements AutoCloseable {
        public void close() {
            throw new RuntimeException("loi khi dong");
        }
    }

    public static void main() {
        try {
            TaiNguyen t = new TaiNguyen();
            try {
                throw new RuntimeException("loi khi lam viec");
            } finally {
                t.close();
            }
        } catch (RuntimeException e) {
            IO.println("bat   : " + e.getMessage());
            IO.println("cause : " + e.getCause());
        }
    }
}
bat   : loi khi dong
cause : null

Đây là lý do try-with-resources ra đời. Cơ chế gần đúng nó sinh ra phức tạp hơn finally một chút:

// pseudo-code: try-with-resources duoc dich gan nhu the nay
TaiNguyen t = new TaiNguyen();
Throwable primary = null;
try {
    ... than try ...
} catch (Throwable e) {
    primary = e;
    throw e;
} finally {
    if (t != null) {
        if (primary != null) {
            try {
                t.close();
            } catch (Throwable closeError) {
                primary.addSuppressed(closeError);
            }
        } else {
            t.close();        // khong co loi chinh -> loi dong noi len
        }
    }
}

4.6 Resource null thì sao?

Nếu biểu thức resource trả về null, close() bị bỏ qua và không có NullPointerException — hành vi này được JLS quy định rõ:

4.7 addSuppressed thủ công — gom lỗi ngoài try-with-resources

Throwable.addSuppressed(Throwable) không dành riêng cho try-with-resources. Khi một tác vụ chạy nhiều bước độc lập (cập nhật nhiều dòng, gửi nhiều request), bạn có thể gom hết lỗi con vào lỗi chính rồi ném một lần — thay vì nuốt các lỗi phía sau:

public class AddSuppressedDemo {
    static void capNhat(String ma) {
        throw new RuntimeException("khong cap nhat duoc " + ma);
    }

    static void xuLyLo() {
        RuntimeException chinh = new IllegalStateException("dong goi that bai");
        for (String ma : new String[] {"AO-01", "QUAN-02"}) {
            try {
                capNhat(ma);
            } catch (RuntimeException e) {
                chinh.addSuppressed(e);
            }
        }
        throw chinh;
    }

    public static void main() {
        try {
            xuLyLo();
        } catch (RuntimeException e) {
            IO.println("chinh: " + e.getMessage());
            for (Throwable s : e.getSuppressed()) {
                IO.println("suppressed: " + s.getMessage());
            }
        }
    }
}
chinh: dong goi that bai
suppressed: khong cap nhat duoc AO-01
suppressed: khong cap nhat duoc QUAN-02
Phân biệt cause và suppressed: mỗi Throwable chỉ có một cause (chuỗi nhân quả, in ra dưới dạng "Caused by") nhưng giữ được nhiều suppressed. Truyền null hoặc chính nó vào addSuppressed sẽ ném lỗi ngay. Chỉ dùng khi một thao tác tổng hợp thực sự cần báo cáo tất cả lỗi con.

5. throw, throws & exception chaining Hay hỏi phỏng vấn

throw bieuThucThrowable;   ·   kieuTraVe method(...) throws LoiA, LoiB { ... }
  • throw là câu lệnh ném một object lúc chạy. Biểu thức phải là Throwable (hoặc subclass).
  • throws là phần khai báo trong chữ ký method, cho compiler biết method có thể ném checked exception nào — trách nhiệm chuyển cho caller.
  • Unchecked exception có thể throw mà không cần throws; checked thì bắt buộc có (hoặc catch ngay bên trong).

Một ví dụ đủ cả hai: chia ném unchecked không khai báo, docCauHinh ném checked và buộc khai báo throws IOException:

import java.io.IOException;

public class ThrowThrowsDemo {
    static double chia(double a, double b) {
        if (b == 0) {
            throw new ArithmeticException("khong the chia cho 0");
        }
        return a / b;
    }

    static String docCauHinh() throws IOException {
        boolean loi = true;
        if (loi) {
            throw new IOException("khong tim thay config");
        }
        return "ok";
    }

    public static void main() {
        IO.println("6 / 3 = " + chia(6, 3));
        try {
            chia(1, 0);
        } catch (ArithmeticException e) {
            IO.println("loi runtime: " + e.getMessage());
        }
        try {
            IO.println(docCauHinh());
        } catch (IOException e) {
            IO.println("loi checked: " + e.getMessage());
        }
    }
}
6 / 3 = 2.0
loi runtime: khong the chia cho 0
loi checked: khong tim thay config

5.1 Override chỉ được thu hẹp throws

Method ghi đè không được phép ném "rộng" hơn method cha. Ba mức hợp lệ khi lớp cha khai báo throws IOException:

  • Khai báo y hệt throws IOException.
  • Khai báo hẹp hơn — subtype như FileNotFoundException.
  • Không khai báo gì cả (method con không ném hoặc tự xử lý bên trong).

Mở rộng throws bị chặn ngay khi compile, vì caller đang giữ reference kiểu cha sẽ không chuẩn bị cho exception mới:

OverrideThrowsErr.java:11: error: xuLy() in OverrideThrowsErr cannot override xuLy() in Cha
    void xuLy() throws Exception {
         ^
  overridden method does not throw Exception
1 error

Luật này áp dụng cả cho throws Exception khi cha chỉ ném checked hẹp, lẫn cho việc thêm checked exception hoàn toàn mới. Unchecked thì không bị ràng buộc — đó là một lý do nữa khiến chúng "dễ sống" hơn trong hệ thống phân tầng.

5.2 Exception chaining — giữ nguyên nhân gốc

Khi tầng trên wrap lỗi tầng dưới, bắt buộc truyền cause vào constructor để stack trace còn nguyên chuỗi nhân quả:

public class ChainCauseDemo {
    static void capNhatDon() {
        try {
            Integer.parseInt("khong-phai-so");
        } catch (NumberFormatException e) {
            throw new IllegalStateException("cap nhat don that bai", e);
        }
    }

    public static void main() {
        try {
            capNhatDon();
        } catch (IllegalStateException e) {
            IO.println("message: " + e.getMessage());
            IO.println("cause  : " + e.getCause().getClass().getSimpleName()
                    + " - " + e.getCause().getMessage());
        }
    }
}
message: cap nhat don that bai
cause  : NumberFormatException - For input string: "khong-phai-so"

Quy tắc của cause:

  • getCause() trả null nếu chỉ dùng super(message) mà không truyền cause — đây là lỗi production rất phổ biến.
  • Cause chỉ gán được một lần (qua constructor hoặc initCause). Không thể tự làm cause của chính mình; vòng lặp cause bị chặn.
  • Nhiều mức wrap tạo thành chuỗi, in ra nhờ "Caused by: ..." trong stack trace. Giữ tối đa 2–3 tầng cho dễ đọc.

Rethrow — bắt để ghi log rồi ném lại chính exception cũ — giữ nguyên stack trace gốc:

public class RethrowDemo {

6. Custom exception Junior+

JDK đã có sẵn gần đủ loại lỗi phổ biến. Chỉ tạo exception riêng khi:

  • Caller cần phân biệt lỗi bằng kiểu để xử lý khác nhau (hết hàng → gợi ý nhập thêm; đơn sai → báo lỗi form).
  • Lỗi mang dữ liệu nghiệp vụ cần cho handler: mã hàng, số lượng còn lại, mã đơn.
  • Tầng của bạn cần một "mã lỗi nội bộ" ổn định để log/metrics — NullPointerException không nói lên điều gì về nghiệp vụ.

Với nghiệp vụ, mặc định chọn unchecked (extends RuntimeException): không làm phình chữ ký mọi method trên đường đi, vẫn có thể bắt ở tầng biên. Chỉ kế thừa Exception khi bạn viết API mà caller chắc chắn phải recover — thường là code hạ tầng.

Cấu trúc constructor chuẩn nên có đủ message và cause:

public TenException(String message) { super(message); }
public TenException(String message, Throwable cause) { super(message, cause); }

Ví dụ đầy đủ cho project đơn hàng — một lớp cha OrderException, hai lớp con mang ngữ nghĩa khác nhau, kèm dữ liệu nghiệp vụ:

public class CustomExceptionDemo {
    static class OrderException extends RuntimeException {
        OrderException(String message) {
            super(message);
        }

        OrderException(String message, Throwable cause) {
            super(message, cause);
        }
    }

    static class InvalidOrderException extends OrderException {
        InvalidOrderException(String message) {
            super(message);
        }
    }

    static class InsufficientStockException extends OrderException {
        private final String maHang;
        private final int conLai;

        InsufficientStockException(String maHang, int conLai) {
            super("Het hang " + maHang + ", chi con " + conLai);
            this.maHang = maHang;
            this.conLai = conLai;
        }

        String maHang() {
            return maHang;
        }

        int conLai() {
            return conLai;
        }
    }

    static void datHang(String maHang, int soLuong) {
        int tonKho = maHang.equals("AO-01") ? 3 : 0;
        if (soLuong <= 0) {
            throw new InvalidOrderException("So luong phai > 0: " + soLuong);
        }
        if (soLuong > tonKho) {
            throw new InsufficientStockException(maHang, tonKho);
        }
        IO.println("Dat hang " + maHang + " x" + soLuong + " thanh cong");
    }

    static void thu(String maHang, int soLuong) {
        try {
            datHang(maHang, soLuong);
        } catch (OrderException e) {
            IO.println(e.getClass().getSimpleName() + ": " + e.getMessage());
            if (e instanceof InsufficientStockException ise) {
                IO.println("  ma hang: " + ise.maHang() + ", con lai: " + ise.conLai());
            }
        }
    }

    public static void main() {
        datHang("AO-01", 2);
        thu("AO-01", 10);
        thu("AO-02", 0);
    }
}

6.1 Không dùng exception cho control flow

Exception không phải công cụ rẽ nhánh. Dùng nó để thoát vòng lặp/method làm code khó đọc, chậm hơn (tạo stack trace) và che mất lỗi thật trong log. Cùng bài toán tìm vị trí số chẵn đầu tiên — cách "chuẩn" chỉ là một return:

public class ExceptionForFlowDemo {
    static class FoundEven extends RuntimeException {
        final int index;

        FoundEven(int index) {
            this.index = index;
        }
    }

    static int timSoChanDau(int[] ds) {
        try {
            for (int i = 0; i < ds.length; i++) {
                if (ds[i] % 2 == 0) {
                    throw new FoundEven(i);   // anti-pattern!
                }
            }
        } catch (FoundEven e) {
            return e.index;
        }
        return -1;
    }

    static int timSoChanDauChuan(int[] ds) {
        for (int i = 0; i < ds.length; i++) {
            if (ds[i] % 2 == 0) {
                return i;
            }
        }
        return -1;
    }

    public static void main() {
        int[] ds = {1, 3, 4, 7};
        IO.println("dung exception (anti-pattern): index " + timSoChanDau(ds));
        IO.println("cach chuan                    : index " + timSoChanDauChuan(ds));
    }
}
dung exception (anti-pattern): index 2
cach chuan                    : index 2
Dấu hiệu nhận biết: bạn tạo một exception class chỉ để throw ngay sau đó catch trong cùng method; hoặc dùng exception cho trạng thái bình thường như "không tìm thấy". Trường hợp "không tìm thấy" nên trả Optional (3.7) hoặc kết quả record, còn lỗi thật mới ném exception.

            return 0;               // nuot loi: khong log, khong bao
        }
    }

    public static void main() {

Nếu buộc phải "coi như thành công", hãy chọn cách có ghi dấu vết: dùng giá trị mặc định + log cảnh báo, hoặc ném IllegalArgumentException cho caller quyết định. Có đúng một trường hợp catch rỗng chấp nhận được: đóng tài nguyên trong finally của code rất cũ, khi bản thân lỗi đóng không quan trọng — và hiện đại hơn là dùng TWR.

7.2 Log-and-throw — log hai lần, alert ba lần

Ví dụ compile và chạy được ngay — để ý cùng một lỗi bị ghi log hai lần:

import java.io.IOException;

public class LogAndThrowDemo {
    static final Logger LOG = new Logger();

    static class Logger {
        void error(String message, Throwable e) {
            IO.println("[ERROR] " + message + " - " + e.getMessage());
        }
    }

    static class ServiceException extends RuntimeException {
        ServiceException(String message, Throwable cause) {
            super(message, cause);
        }
    }

    static void docFile() throws IOException {
        throw new IOException("file hong");
    }

    // Anti-pattern: vua log vua nem o tang trong, roi tang ngoai lai log tiep
    static void xuLy() {
        try {
            docFile();
        } catch (IOException e) {
            LOG.error("doc file that bai", e);   // log lan 1
            throw new ServiceException("khong doc duoc du lieu", e);
        }
    }

    public static void main() {
        try {
            xuLy();
        } catch (ServiceException e) {
            LOG.error("xu ly that bai", e);      // log lan 2 - trung lap
            IO.println("cause: " + e.getCause().getMessage());
        }
    }
}

cause: file hong

Cách đúng: wrap và ném ở tầng trong (không log), chỉ log ở nơi handle cuối cùng (tầng biên hoặc job). Ngoại lệ: log ở tầng trong với mục đích audit nghiệp vụ (ví dụ ghi rõ mã đơn vi phạm) — khi đó message log phải khác message exception.

7.4 UncaughtExceptionHandler — lưới an toàn cuối cùng cho thread

Exception không được bắt trong một thread sẽ làm thread đó chết và mặc định in stack trace ra System.err. Đặt Thread.setDefaultUncaughtExceptionHandler để log/telemetry tập trung cho mọi thread, hoặc gắn handler riêng qua thread.setUncaughtExceptionHandler(...). Đây là chỗ phù hợp để ghi nhận lỗi cuối cùng thay vì rải try/catch quanh mọi Runnable.

public class UncaughtHandlerDemo {
    public static void main() throws InterruptedException {
        Thread.setDefaultUncaughtExceptionHandler((t, e) ->
                IO.println("bat duoc: " + e.getMessage() + " tren thread " + t.getName()));

        Thread worker = new Thread(() -> {
            throw new IllegalStateException("no tren worker");
        }, "worker-1");
        worker.start();
        worker.join();

        IO.println("main van song");
    }
}

main van song
Thứ tự ưu tiên: handler gắn cho từng thread (nếu có) thắng handler mặc định. Handler không cứu thread — thread vẫn chết; nó chỉ đảm bảo lỗi được ghi nhận ở nơi bạn kiểm soát. worker.join() giữ output theo thứ tự cố định.

7.6 Checked exception trong lambda/Stream

Functional interface chuẩn như Function, Consumer không khai báo throws, nên gọi method checked bên trong lambda là lỗi compile unreported exception. Cách xử lý sạch: bọc ngay thành UncheckedIOException (giữ cause) rồi bắt ở ngoài — chi tiết thêm ở Stream API — mục 9.3.

import java.io.IOException;
import java.io.UncheckedIOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

public class LambdaCheckedDemo {
    static String xuLy(String dong) throws IOException {
        if (dong.isBlank()) {
            throw new IOException("gap dong rong");
        }
        return dong.toUpperCase();
    }

    public static void main() throws IOException {
        Path file = Files.createTempFile("lambda", ".txt");
        Files.writeString(file, "dong mot\n\n");
        try {
            List<String> ketQua = Files.readAllLines(file).stream()
                    .map(dong -> {
                        try {
                            return xuLy(dong);
                        } catch (IOException e) {
                            throw new UncheckedIOException(e);
                        }
                    })
                    .toList();
            IO.println("so dong: " + ketQua.size());
        } catch (UncheckedIOException e) {
            IO.println("wrap: " + e.getMessage());
            IO.println("cause: " + e.getCause().getClass().getSimpleName()
                    + " - " + e.getCause().getMessage());
        } finally {
            Files.deleteIfExists(file);
        }
    }
}
wrap: java.io.IOException: gap dong rong
cause: IOException - gap dong rong
Stream là lazy: để thấy lỗi, pipeline phải được kéo chạy thật — ví dụ qua toList(), forEach(). Một số thao tác như count() có thể tối ưu bỏ qua map() nên lỗi bên trong không nổ; đừng dựa vào tác dụng phụ trong map.

Ví dụ xuyên suốt: một OrderService đọc tồn kho từ file qua KhoRepository, validate nghiệp vụ, và xử lý đủ ba nhóm lỗi: lỗi hạ tầng (IOException), lỗi nghiệp vụ (hết hàng, số lượng sai), lỗi lập trình (không bắt vội).

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

public class OrderServiceDemo {
    static class OrderException extends RuntimeException {
        OrderException(String message) {
            super(message);
        }
    }

    static class DataAccessException extends RuntimeException {
        DataAccessException(String message, Throwable cause) {
            super(message, cause);
        }
    }

    static class KhoRepository {
        private final Path file;

        KhoRepository(Path file) {
            this.file = file;
        }

        int tonKho(String maHang) {
            try {
                for (String line : Files.readAllLines(file)) {
                    String[] phan = line.split("=");
                    if (phan[0].equals(maHang)) {
                        return Integer.parseInt(phan[1].trim());
                    }
                }
                return 0;
            } catch (IOException e) {
                throw new DataAccessException("khong doc duoc file ton kho: " + file.getFileName(), e);
            }
        }
    }

    static class OrderService {
        private final KhoRepository kho;

        OrderService(KhoRepository kho) {
            this.kho = kho;
        }

        void datHang(String maHang, int soLuong) {
            if (soLuong <= 0) {
                throw new OrderException("So luong phai lon hon 0: " + soLuong);
            }
            int ton = kho.tonKho(maHang);
            if (soLuong > ton) {
                throw new OrderException("Het hang " + maHang + ": can " + soLuong + ", con " + ton);
            }
            IO.println("Dat " + maHang + " x" + soLuong + " thanh cong");
        }
    }

    public static void main() throws IOException {
        Path file = Files.createTempFile("tonkho", ".txt");
        Files.writeString(file, "AO-01=5\nQUAN-02=0\n");
        try {
            OrderService service = new OrderService(new KhoRepository(file));
            service.datHang("AO-01", 3);
            thu(service, "AO-01", 9);
            thu(service, "QUAN-02", 1);
            thu(service, "AO-01", 0);
        } finally {
            Files.deleteIfExists(file);
        }
        docLoi();
    }

    static void thu(OrderService service, String maHang, int soLuong) {
        try {
            service.datHang(maHang, soLuong);
        } catch (OrderException e) {
            IO.println("OrderException: " + e.getMessage());
        }
    }

    static void docLoi() {
        try {
            new KhoRepository(Path.of("khong-ton-tai.txt")).tonKho("AO-01");
        } catch (DataAccessException e) {
            IO.println("DataAccessException: " + e.getMessage());
            IO.println("  cause: " + e.getCause().getClass().getSimpleName());
        }
    }
}
Dat AO-01 x3 thanh cong
OrderException: Het hang AO-01: can 9, con 5
OrderException: Het hang QUAN-02: can 1, con 0
OrderException: So luong phai lon hon 0: 0

Đọc hiểu luồng lỗi:

  • Repository bắt IOException của Files.readAllLines, wrap thành DataAccessException kèm cause NoSuchFileException — caller không cần biết chi tiết NIO. File I/O đào sâu ở 3.4 I/O & Files.
  • Service chỉ quan tâm luật nghiệp vụ: số lượng dương, đủ tồn kho. Hai lỗi này là business exception — tầng trên có thể map thành response cho người dùng.
  • main là tầng biên của ví dụ: bắt đúng OrderException; lỗi hạ tầng cố ý không bắt để lộ ra ngoài (trong app thật sẽ có handler ở tầng biên).
  • Files.deleteIfExists nằm trong finally vì file tạm không phải resource kiểu stream; nếu mở stream thì phải dùng try-with-resources.
Khi nào trả lỗi nghiệp vụ thay vì ném? Nếu "thất bại" là kết quả bình thường của luồng (tìm kiếm không thấy, import có dòng lỗi), hãy trả kết quả record/Optional để caller đọc dễ hơn. Chỉ ném exception khi thao tác không thể hoàn thành theo hợp đồng — như đặt hàng khi hết tồn.
Nối tiếp REST API: ở giai đoạn 5, tầng controller sẽ map exception sang HTTP status: InvalidOrderException → 400, InsufficientStockException → 409, DataAccessException → 500 (kèm log đầy đủ, không lộ chi tiết nội bộ trong response). Một @ExceptionHandler tập trung thay cho try/catch rải rác. Stream API cũng sẽ học ở 3.8 — lưu ý exception trong lambda phải là unchecked hoặc wrapped.

10. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Vẽ cây kế thừa Throwable. Error và Exception khác nhau thế nào?
Object → Throwable → { Error, Exception }. Error là sự cố hệ thống/JVM (OutOfMemoryError, StackOverflowError) — không nên bắt vì chương trình không thể xử lý. Exception là lỗi của chương trình, chia tiếp thành checked và unchecked (nhánh RuntimeException). Chỉ object Throwable mới throw được.
Câu 2. Checked exception và unchecked exception khác nhau thế nào? Cho ví dụ.
Checked: mọi lớp con của Exception trừ RuntimeException; compiler buộc catch hoặc khai báo throws — ví dụ IOException, SQLException, InterruptedException. Unchecked: RuntimeException và con của nó; không bị compiler kiểm tra — ví dụ NullPointerException, IllegalArgumentException, IllegalStateException, ClassCastException, NumberFormatException.
Câu 3. Vì sao Java có checked exception? Khi nào nên dùng checked cho custom exception?
Checked biến khả năng thất bại thành phần của hợp đồng API mà compiler kiểm tra được — người gọi buộc phải ý thức và xử lý. Nhiều ngôn ngữ khác (C#, Kotlin) bỏ checked vì làm chữ ký phình to và vướng lambda/async. Nguyên tắc: dùng checked khi caller thực sự có cách phục hồi hợp lý hoặc thất bại là thuộc tính tự nhiên của tác vụ (I/O, DB); nghiệp vụ thuần thường dùng unchecked. Khi phân vân, chọn unchecked.
Câu 4. finally có luôn chạy không? Có ngoại lệ nào?
finally chạy khi: try kết thúc bình thường, có exception (được bắt hay không), có return/break/continue. Không chạy khi: JVM thoát bằng System.exit hoặc Runtime.getRuntime().halt(...) (halt là instance method, phải gọi qua getRuntime()); thread còn kẹt/treo trong try (finally chưa tới lượt); process bị kill từ ngoài (SIGKILL/taskkill) hoặc native crash. Lưu ý: Thread.stop() (deprecated for removal) từ JDK 20 ném UnsupportedOperationException chứ không còn kill thread; kể cả thời còn hoạt động, nó chỉ ném ThreadDeath vào thread nên finally vẫn chạy — đừng dùng nó như cách "bỏ qua finally".
Câu 5. Vì sao không nên viết return trong finally?
Vì return trong finally không chỉ chạy trước khi thoát — nó ghi đè mọi exception đang bay và ghi đè luôn giá trị return của try. Exception biến mất không dấu vết, bug trở nên cực khó tìm. javac mặc định không cảnh báo (chỉ -Xlint:finally mới báo "finally clause cannot complete normally"), nên đừng trông chờ compiler nhắc.
Câu 6. Nếu cả try và finally đều ném exception thì exception nào được ném ra?
Exception của finally thắng. Exception trong try bị "nuốt" (không có suppressed, không thành cause) — đây chính là lý do try-with-resources được sinh ra để xử lý bài toán này đúng cách. Trong khi đó, nếu thân try ném trước và resource trong try-with-resources ném khi đóng, exception chính được ném ra còn lỗi đóng nằm trong getSuppressed().

Nâng cao (Junior+)

Câu 7. try-with-resources hoạt động thế nào? Thứ tự đóng resource ra sao?
Resource phải implement AutoCloseable (hoặc Closeable). Compiler sinh code gọi close() theo thứ tự ngược với thứ tự khai báo (mở A rồi B thì đóng B rồi A) — JVM chỉ thực thi bytecode đó — đảm bảo resource bọc ngoài còn sống khi resource bọc trong flush/đóng. close được gọi cả khi try kết thúc bình thường, có exception, hay có return.
Câu 8. Suppressed exception là gì? Đọc chúng thế nào?
Là exception phụ bị "đính kèm" vào exception chính thay vì thay thế nó. try-with-resources dùng cơ chế này: lỗi khi đóng resource được addSuppressed vào lỗi chính. Đọc bằng Throwable.getSuppressed(); stack trace in ra các dòng "Suppressed: ...". Tự dùng khi bạn cần chạy nhiều tác vụ và muốn báo hết lỗi phụ mà không mất lỗi chính.
Câu 9. try-with-resources khác finally thủ công ở điểm nào quan trọng nhất?
Không đánh mất lỗi gốc. finally thủ công: nếu try ném lỗi A rồi close ném lỗi B, B ghi đè A và A mất hút (cause null). TWR: A được ném ra, B vào suppressed của A. Ngoài ra TWR tự xử lý null resource, không cần check null, code ngắn và khó quên close hơn.
Câu 10. throw và throws khác nhau thế nào?
throw là câu lệnh ném exception tại thời điểm chạy: throw new IOException("..."). throws là khai báo trong chữ ký method, chỉ ra các checked exception method có thể ném để compiler kiểm tra caller. Một method có thể throw nhiều lần nhưng chỉ throws một danh sách.
Câu 11. Method override được thay đổi danh sách throws thế nào?
Chỉ được thu hẹp: giữ nguyên, dùng subtype, hoặc bỏ hẳn. Không được thêm checked exception mới hay dùng kiểu cha rộng hơn. Ví dụ cha throws IOException thì con có thể throws FileNotFoundException hoặc không throws, nhưng throws Exception là lỗi compile "overridden method does not throw Exception". Unchecked không bị ràng buộc.
Câu 12. Exception chaining là gì? getCause() và initCause() khác gì nhau?
Chaining là wrap lỗi tầng dưới vào lỗi tầng trên nhưng giữ nguyên nhân: new ServiceException("...", e). getCause() đọc nguyên nhân; constructor có cause hoặc initCause(e) để gán. Cause chỉ gán được một lần, không thể là chính nó, và getCause() trả null nếu quên truyền — lỗi production phổ biến làm mất gốc khi debug.
Câu 13. Custom exception nên checked hay unchecked? Constructor cần gì?
Mặc định unchecked (extends RuntimeException) cho lỗi nghiệp vụ/bug; checked chỉ khi caller phải recover. Constructor chuẩn: (String message) và (String message, Throwable cause); thêm field + accessor nếu handler cần dữ liệu (mã hàng, số lượng còn lại). Nên có một lớp cha chung cho miền nghiệp vụ để tầng biên bắt một lần.
Câu 14. Vì sao không nên dùng exception cho control flow?
Vì nó làm code khó đọc (logic ẩn trong catch), tốn chi phí tạo stack trace, và trộn lẫn "lỗi thật" với "trạng thái bình thường" khiến log/alert nhiễu. Trường hợp "không tìm thấy", "hết phần tử", "không hợp lệ nhẹ" nên trả về Optional, giá trị mặc định, hoặc record kết quả. Chỉ ném exception khi thao tác không thể hoàn thành theo hợp đồng.
Câu 15. Nuốt exception (catch rỗng) và log-and-throw sai ở đâu? InterruptedException xử lý thế nào?
Catch rỗng biến lỗi thành im lặng: dữ liệu sai âm thầm, không ai debug được. Log-and-throw gây log trùng ở nhiều tầng: hãy wrap (không log) ở tầng trong và log một lần ở nơi handle cuối. Với InterruptedException: không được nuốt — gọi Thread.currentThread().interrupt() để phục hồi cờ ngắt rồi thoát/đẩy tiếp, vì nuốt cờ ngắt làm hỏng cơ chế shutdown của thread pool.

}

IO.println(tinh());
In ra 1. finally chạy trước khi method trả về, nhưng giá trị return đã được "chốt" (copy) từ trước khi x bị đổi. Gán x = 99 trong finally không ảnh hưởng kết quả. Đừng suy luận từ đây rằng finally vô hại: return trong finally mới là thứ ghi đè giá trị/exception (xem mục 3.2).
Bài 2 
try {
    IO.println("A");
    throw new RuntimeException("boom");
} catch (RuntimeException e) {
    IO.println("B");
} finally {
    IO.println("C");
}
IO.println("D");
In ra A, B, C, D theo đúng thứ tự. Exception ném ở try → catch khớp chạy B → finally chạy C → exception đã được xử lý nên luồng tiếp tục tới D.
Bài 3 
class Res implements AutoCloseable {
    private final String ten;
    Res(String ten) { this.ten = ten; }
    public void close() { IO.println("dong " + ten); }
}

try (Res a = new Res("A");
     Res b = new Res("B")) {
    IO.println("than try");
} finally {
    IO.println("finally ngoai");
}
In ra than try, dong B, dong A, finally ngoai. TWR đóng resource ngược thứ tự mở (B rồi A) ngay khi thân try kết thúc; finally bên ngoài chạy sau cùng, khi cả hai resource đã đóng.
Bài 4 
RuntimeException e = new RuntimeException("ngoai");
IO.println(e.getCause());
IO.println(e.getMessage());
In ra null rồi ngoai. Exception mới tạo bằng constructor một tham số không có cause; getCause() trả null, không phải chính nó và không phải exception rỗng.
Bài 5 
class AppException extends RuntimeException {
    AppException(String message) { super(message); }
}

class NotFoundException extends AppException {
    NotFoundException(String id) { super("khong thay: " + id); }
}

try {
    throw new NotFoundException("DH-42");
} catch (AppException e) {
    IO.println(e.getClass().getSimpleName() + ": " + e.getMessage());
}
In ra NotFoundException: khong thay: DH-42. Catch theo kiểu cha AppException vẫn bắt được con; getClass().getSimpleName() trả tên lớp thật lúc chạy. Đây là lý do chỉ cần một catch ở tầng biên cho cả họ exception nghiệp vụ.
Bài 6 
static void chay() {
    try {
        throw new RuntimeException("goc");
    } finally {
        throw new IllegalStateException("tu finally");
    }
}

try {
    chay();
} catch (RuntimeException e) {
    IO.println(e.getClass().getSimpleName() + ": " + e.getMessage());
    IO.println("cause: " + e.getCause());
}
In ra IllegalStateException: tu finally rồi cause: null. Exception ném trong finally thay thế hoàn toàn exception "goc" — nó không tự động trở thành cause của nhau. Đây là lý do quy tắc "không throw trong finally".
Bài 7 
import java.io.IOException;

class DocDemo {
    static void doc() throws IOException {
        throw new IOException("loi doc file");
    }

    public static void main() {
        doc();
    }
}
Không compile. Lỗi: "unreported exception IOException; must be caught or declared to be thrown" tại dòng doc();. Sửa bằng một trong hai cách: bọc try/catch (IOException e), hoặc khai báo public static void main() throws IOException.
Bài 8 
try {
    IO.println("chay");
} catch (Exception e) {
    IO.println("Exception");
} catch (RuntimeException e) {
    IO.println("RuntimeException");
}
Không compile. Lỗi: "exception RuntimeException has already been caught". RuntimeException là lớp con của Exception; nhánh cha phía trên đã bắt hết nên nhánh con không bao giờ tới. Đảo thứ tự (con trước, cha sau) là hợp lệ.

Checklist tự đánh giá trước phỏng vấn

  • Vẽ được cây Throwable và xếp đúng vị trí IOException, NullPointerException, StackOverflowError.
  • Giải thích được vì sao compiler bắt lỗi với checked nhưng bỏ qua unchecked.
  • Nêu được lý do checked tồn tại và chỉ trích phổ biến nhất.
  • Dự đoán đúng thứ tự chạy khi try có return và finally có in/log.
  • Giải thích vì sao return trong finally nuốt exception.
  • Kể được ít nhất hai trường hợp finally không chạy.
  • Viết được multi-catch và nêu ràng buộc subclassing.
  • Giải thích thứ tự đóng resource và suppressed exception bằng ví dụ getSuppressed().
  • So sánh TWR với finally thủ công về khả năng giữ lỗi gốc.
  • Phân biệt throw và throws; phát biểu luật thu hẹp throws khi override.
  • Viết custom exception đủ constructor và truyền cause đúng chỗ.
  • Nêu 3 anti-pattern: nuốt exception, log-and-throw, catch Exception quá rộng — kèm cách thay thế.
  • Biết cách phục hồi cờ ngắt khi gặp InterruptedException.
