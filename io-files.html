I/O & Files — đọc ghi dữ liệu trong Java

Backend không chỉ tính toán — nó còn đọc file cấu hình, ghi log, xử lý CSV, ảnh upload, file nén… Trang này đi từ bản chất byte stream vs character stream, qua NIO.2 (Path/Files) hiện đại, tới các bẫy encoding tiếng Việt và cách ghi file an toàn trong production. Mọi ví dụ tự tạo file tạm trong thư mục hệ thống rồi tự dọn, chạy được ngay bằng java TenFile.java trên JDK 25.

1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Mức độ bắt buộc của chủ đề 3.4 (phỏng vấn: cao · production: bắt buộc):

  • Phải làm được — đọc/ghi file text với UTF-8 tường minh; đọc file theo dòng; dùng Path/Files thay File; tạo/đọc/ghi trong thư mục tạm; copy/move/delete; duyệt cây thư mục và đóng Stream đúng cách.
  • Phải hiểu — vì sao file trên đĩa luôn là byte còn String trong RAM được lưu bằng compact strings (từ JDK 9: Latin-1, 1 byte/char khi mọi ký tự biểu diễn được, ngược lại UTF-16) nhưng API như length()/charAt() vẫn tính theo UTF-16 code unit; charset là "hợp đồng" giữa hai bên; try-with-resources đóng resource theo thứ tự nào; vì sao Files.lines/Files.list/Files.walk bắt buộc phải đóng.
  • Nhận biết — NIO.2 (Java 7) và tiện ích JDK 11+ (readString/writeString); JEP 400 (JDK 18 — UTF-8 mặc định); atomic write; BOM; symbolic link; deserialization không an toàn.

Cách học hiệu quả nhất:

  1. Đoán output của ví dụ trước khi nhìn comment kết quả — đặc biệt các ví dụ encoding.
  2. Tự gõ lại ví dụ, đổi tên file/thư mục, thêm dòng tiếng Việt có dấu để tự kiểm chứng.
  3. Làm mục Bài tập đoán output trước, chỉ mở đáp án sau khi đã đoán.
  4. Ôn nhanh bằng Cheat sheet trước buổi phỏng vấn.
Ví dụ dùng IO.println(...) — cách viết gọn của JDK 25 (JEP 512), tương đương System.out.println(...). Các ví dụ là compact source file: không cần khai báo class, nhưng vẫn cần void main() (JDK 25 không cho câu lệnh trần). Compact file tự import mọi class public của module java.base, nên ví dụ không cần dòng import; khi viết trong class thường bạn phải tự import java.io.*, java.nio.file.*, java.nio.charset.*.

2. Byte stream vs Character stream

Ổ đĩa, socket, mạng — tất cả chỉ biết byte. Còn String trong RAM được lưu bằng compact strings (Latin-1 khi đủ, UTF-16 nếu không — từ JDK 9), nhưng API như length()/charAt() tính theo UTF-16 code unit. Để chuyển giữa hai thế giới đó cần một bảng mã — gọi là charset (UTF-8, ISO-8859-1, windows-1252…). Nhánh byte stream vận chuyển byte thô, không diễn giải; nhánh character stream có bước encode/decode qua charset giúp bạn làm việc với ký tự.

3. Byte streams thực chiến

3.1 Ghi/đọc file nhị phân với File* + Buffered*

write(int) chỉ dùng 8 bit thấp, nên write(-1) ghi byte 0xFF; còn read() trả về 0..255 hoặc -1 khi hết file. Vì vậy -1 vừa là "EOF", vừa không bao giờ là giá trị byte hợp lệ:

void main() throws IOException {
    Path dir = Files.createTempDirectory("iolab-");
    Path f = dir.resolve("raw.bin");

    try (var out = new FileOutputStream(f.toString())) {
        out.write(new byte[] {1, 2, 3, 127, -1});
    }

    try (var in = new FileInputStream(f.toString())) {
        int b;
        while ((b = in.read()) != -1) {
            IO.print(b + " ");
        }
        IO.println();
    }

    try (var in = new FileInputStream(f.toString())) {
        byte[] buf = new byte[4];
        int n;
        while ((n = in.read(buf)) != -1) {
            IO.print("[" + n + "]");
        }
        IO.println();
    }

    Files.delete(f);
    Files.delete(dir);
}
1 2 3 127 255 
[4][1]

Đọc bằng read(byte[]) nhanh hơn hẳn read() từng byte vì mỗi lần gọi tốn một syscall. Lần đọc đầu đầy buffer ([4]), lần sau chỉ còn 1 byte ([1]). Luôn nhớ: read(byte[]) có thể trả về ít hơn độ dài buffer — đừng giả định nó đọc đầy.

3.2 DataInputStream/DataOutputStream — đọc ghi primitive

Muốn ghi int xuống file đúng 4 byte thay vì 4 ký tự text thì dùng data streams. Chúng mã hoá cố định, độc lập nền tảng (big-endian), kèm writeUTF ghi chuỗi theo định dạng riêng (2 byte độ dài + modified UTF-8):

void main() throws IOException {
    Path dir = Files.createTempDirectory("iolab-");
    Path f = dir.resolve("data.bin");

    // ghi: int -> UTF -> double -> boolean, buffer cho nhanh
    try (var out = new DataOutputStream(new BufferedOutputStream(Files.newOutputStream(f)))) {
        out.writeInt(42);
        out.writeUTF("Xin chao");
        out.writeDouble(19.99);
        out.writeBoolean(true);
    }

    // doc phai dung thu tu va dung kieu da ghi
    try (var in = new DataInputStream(new BufferedInputStream(Files.newInputStream(f)))) {
        IO.println(in.readInt());
        IO.println(in.readUTF());
        IO.println(in.readDouble());
        IO.println(in.readBoolean());
    }

    IO.println("size=" + Files.size(f));

    Files.delete(f);
    Files.delete(dir);
}

19.99
true
size=23

File nặng 23 byte = 4 (int) + 2 + 8 (UTF dài 8 ký tự) + 8 (double) + 1 (boolean). Không có ký tự phân cách nào — đó là lý do thứ tự ghi và đọc phải khớp tuyệt đối. Đọc lệch kiểu sẽ không báo lỗi ngay mà trả về giá trị rác:

void main() throws IOException {
    Path dir = Files.createTempDirectory("iolab-");
    Path f = dir.resolve("mixed.bin");

    try (var out = new DataOutputStream(Files.newOutputStream(f))) {
        out.writeInt(7);
        out.writeDouble(2.5);
    }

    // doc sai thu tu: double truoc
    try (var in = new DataInputStream(Files.newInputStream(f))) {
        IO.println("readDouble truoc: " + in.readDouble());
    }

    // doc dung thu tu
    try (var in = new DataInputStream(Files.newInputStream(f))) {
        IO.println("readInt truoc: " + in.readInt());
        IO.println("readDouble sau: " + in.readDouble());
    }

    Files.delete(f);
    Files.delete(dir);
}
readDouble truoc: 1.5384599001E-313
readInt truoc: 7
readDouble sau: 2.5

readDouble() đọc 8 byte đầu tiên (4 byte của int 7 + 4 byte đầu của double) và diễn giải thành một double rác 1.5384599001E-313 — không exception, chỉ sai âm thầm. Vì vậy data streams chỉ hợp với định dạng do chính bạn kiểm soát cả hai đầu (cache nội bộ, protocol riêng), không hợp làm API trao đổi dữ liệu giữa các hệ thống. Giao tiếp liên hệ thống hãy dùng JSON/protobuf; ObjectInputStream thì càng phải tránh vì lỗ hổng deserialization.

3.3 read() vs read(byte[]) vs readAllBytes() vs transferTo()

Bốn cách đọc, chọn theo kích thước và mục đích:

void main() throws IOException {
    Path dir = Files.createTempDirectory("iolab-");
    Path src = dir.resolve("src.txt");
    Files.writeString(src, "Hello NIO", StandardCharsets.UTF_8);

    try (var in = Files.newInputStream(src)) {
        int b = in.read();
        IO.println("read()          -> " + (char) b);
    }

    try (var in = Files.newInputStream(src)) {
        byte[] buf = new byte[5];
        int n = in.read(buf);
        IO.println("read(byte[5])   -> " + n + " + " + new String(buf, 0, n, StandardCharsets.UTF_8));
    }

    try (var in = Files.newInputStream(src)) {
        byte[] all = in.readAllBytes();
        IO.println("readAllBytes()  -> " + all.length + " + " + new String(all, StandardCharsets.UTF_8));
    }

    Path copy = dir.resolve("copy.txt");
    try (var in = Files.newInputStream(src); var out = Files.newOutputStream(copy)) {
        in.transferTo(out);
    }
    IO.println("transferTo()    -> " + Files.readString(copy));

    Files.delete(copy);
    Files.delete(src);
    Files.delete(dir);
}
read()          -> H
read(byte[5])   -> 5 + Hello
readAllBytes()  -> 9 + Hello NIO
transferTo()    -> Hello NIO
  • read() — 1 byte một lần, trả 0..255 hoặc -1. Chỉ dùng khi cần đọc từng byte (parse định dạng nhị phân).
  • read(byte[]) — đọc tối đa buf.length byte, trả số byte thực đọc (có thể nhỏ hơn) hoặc -1. Muốn đọc đủ phải lặp; khi biết trước số byte cần đọc, dùng readNBytes(in, n) cho gọn.
  • readAllBytes() — đọc tới hết vào byte[]. Tiện cho file nhỏ; file lớn sẽ ngốn RAM gấp đôi (mảng byte + String khi decode).
  • transferTo(out) — chuyền dữ liệu sang OutputStream khác, tự quản buffer, dùng để copy nhị phân mà không cần tự viết vòng while đọc/ghi.

3.4 Nén & giải nén — GZIP, ZIP

Nén là thao tác byte thuần, không cần charset cho nội dung (chỉ cần khi ghi tên entry trong ZIP). GZIPOutputStream/GZIPInputStream nén một luồng dữ liệu (thường dùng cho file log, HTTP body); ZipOutputStream/ZipInputStream/ZipFile quản lý nhiều entry có tên trong một file ZIP. Cả hai đều bọc quanh OutputStream/InputStream nên ghép được với Files.newInputStream/newOutputStream và transferTo:

void main() throws IOException {
    Path dir = Files.createTempDirectory("gzip-");
    Path txt = dir.resolve("log.txt");
    Path gz = dir.resolve("log.txt.gz");
    String data = "2026-01-03 Giao don A01\n".repeat(1000);
    Files.writeString(txt, data, StandardCharsets.UTF_8);

    try (var out = new GZIPOutputStream(Files.newOutputStream(gz));
         var in = Files.newInputStream(txt)) {
        in.transferTo(out);
    }
    IO.println("goc      = " + Files.size(txt) + " byte");
    IO.println("gz       = " + Files.size(gz) + " byte");

    try (var in = new GZIPInputStream(Files.newInputStream(gz))) {
        String s = new String(in.readAllBytes(), StandardCharsets.UTF_8);
        IO.println("giai nen khop = " + s.equals(data));
        IO.println("so dong  = " + s.lines().count());
    }

    Files.delete(gz);
    Files.delete(txt);
    Files.delete(dir);
}

gz       = 123 byte
giai nen khop = true
so dong  = 1000

ZIP cần gọi putNextEntry/closeEntry cho từng file. Khi tạo ZIP nhớ truyền charset (ví dụ UTF-8) để tên file tiếng Việt không bị hỏng; khi đọc lại, ZipFile cho tra cứu entry theo tên còn ZipInputStream duyệt tuần tự:

import java.util.zip.*;
void main() throws IOException {
    Path dir = Files.createTempDirectory("zip-");
    Path zip = dir.resolve("bundle.zip");
    Path a = dir.resolve("a.txt");
    Path b = dir.resolve("b.txt");
    Files.writeString(a, "noi dung A", StandardCharsets.UTF_8);
    Files.writeString(b, "noi dung B", StandardCharsets.UTF_8);

    try (var zos = new ZipOutputStream(Files.newOutputStream(zip), StandardCharsets.UTF_8)) {
        zos.putNextEntry(new ZipEntry("a.txt"));
        Files.copy(a, zos);
        zos.closeEntry();
        zos.putNextEntry(new ZipEntry("b.txt"));
        Files.copy(b, zos);
        zos.closeEntry();
    }
    IO.println("zip size = " + Files.size(zip));

    try (var zf = new ZipFile(zip.toFile(), StandardCharsets.UTF_8)) {
        var en = zf.entries();
        while (en.hasMoreElements()) {
            var e = en.nextElement();
            IO.println("entry " + e.getName() + " size=" + e.getSize());
        }
        try (var in = zf.getInputStream(zf.getEntry("a.txt"))) {
            IO.println("a.txt = " + new String(in.readAllBytes(), StandardCharsets.UTF_8));
        }
    }

    try (var zis = new ZipInputStream(Files.newInputStream(zip), StandardCharsets.UTF_8)) {
        ZipEntry e;
        while ((e = zis.getNextEntry()) != null) {
            IO.println("giai " + e.getName() + " = " + new String(zis.readAllBytes(), StandardCharsets.UTF_8));
        }
    }

    Files.delete(zip);
    Files.delete(a);
    Files.delete(b);
    Files.delete(dir);
}

giai a.txt = noi dung A
giai b.txt = noi dung B
Zip Slip: không bao giờ giải nén thẳng new File(dir, entry.getName()) — entry có thể chứa ../ để ghi đè file ngoài thư mục đích. Hãy resolve rồi kiểm tra normalize().startsWith(base) như cảnh báo path traversal ở mục 9. Ngoài ra đừng nạp cả file nén lớn vào RAM; ZIP bomb có thể làm cạn bộ nhớ/đĩa.

3.5 RandomAccessFile — đọc/ghi theo vị trí

Khi cần nhảy tới vị trí bất kỳ (đọc record thứ N, sửa giữa file) thay vì đọc tuần tự, RandomAccessFile cho seek() kèm đọc/ghi primitive. Mấu chốt là bản ghi kích thước cố định để tính offset = index × recordSize:

record Sv(int id, String ten) {}

void main() throws IOException {
    Path dir = Files.createTempDirectory("raf-");
    Path f = dir.resolve("sv.dat");
    int tenDai = 8;
    int recordSize = Integer.BYTES + tenDai * Character.BYTES;

    try (var raf = new RandomAccessFile(f.toString(), "rw")) {
        for (Sv sv : List.of(new Sv(1, "An"), new Sv(2, "Binh"), new Sv(3, "Cuong"))) {
            raf.writeInt(sv.id());
            raf.writeChars(String.format("%-" + tenDai + "s", sv.ten()));
        }
    }

    try (var raf = new RandomAccessFile(f.toString(), "r")) {
        IO.println("so record = " + raf.length() / recordSize);
        raf.seek(1L * recordSize);
        int id = raf.readInt();
        StringBuilder ten = new StringBuilder();
        for (int i = 0; i < tenDai; i++) ten.append(raf.readChar());
        IO.println("record 2  = " + id + " " + ten.toString().trim());
        raf.seek(2L * recordSize);
        IO.println("record 3 id = " + raf.readInt());
    }

    Files.delete(f);
    Files.delete(dir);
}
so record = 3
record 2  = 2 Binh
record 3 id = 3
Ví dụ dùng writeChars (mỗi char đúng 2 byte) để record cố định kích thước; writeUTF ghi độ dài biến đổi nên không seek theo index được. Code mới hãy ưu tiên FileChannel + ByteBuffer; RandomAccessFile vẫn phổ biến khi đọc file nhị phân legacy hoặc định dạng tự quy định.

3.6 FileChannel & memory-mapped file

FileChannel (NIO) thay thế mạnh hơn cho RandomAccessFile: hỗ trợ position/read/write, khóa file, transferTo/From zero-copy và map() để ánh xạ file vào bộ nhớ. MappedByteBuffer đọc/ghi như mảng byte nhưng dữ liệu nằm ở page cache của OS — rất nhanh cho file lớn truy cập ngẫu nhiên:

import java.nio.channels.*;
void main() throws IOException {
    Path dir = Files.createTempDirectory("mmap-");
    Path f = dir.resolve("data.bin");

    try (var ch = FileChannel.open(f, StandardOpenOption.CREATE, StandardOpenOption.READ, StandardOpenOption.WRITE)) {
        MappedByteBuffer buf = ch.map(FileChannel.MapMode.READ_WRITE, 0, 26);
        for (int i = 0; i < 26; i++) buf.put(i, (byte) ('A' + i));
        buf.force();
    }

    try (var ch = FileChannel.open(f, StandardOpenOption.READ)) {
        MappedByteBuffer buf = ch.map(FileChannel.MapMode.READ_ONLY, 0, ch.size());
        byte[] out = new byte[(int) ch.size()];
        buf.get(out);
        IO.println("noi dung = " + new String(out, StandardCharsets.US_ASCII));
        IO.println("size     = " + ch.size() + " byte");
    }

    Files.delete(f);
    Files.delete(dir);
}
noi dung = ABCDEFGHIJKLMNOPQRSTUVWXYZ
size     = 26 byte
Mapping không copy dữ liệu vào heap: OS quản lý trang bộ nhớ, ghi vào buffer là ghi vào file (khi flush). Cẩn thận với file thay đổi kích thước/bị truncate trong lúc map (có thể gây lỗi bus), và trên Windows không xoá được file đang map cho tới khi GC giải phóng buffer. Muốn ép xuống đĩa dùng buf.force(); file nhỏ chỉ cần Files.readString/readAllBytes.

4. Character streams & encoding Hay hỏi phỏng vấn Production

4.1 Charset — hợp đồng giữa byte và ký tự

UTF-8 mã hoá mỗi code point thành 1–4 byte; tiếng Việt có dấu thường 2–3 byte mỗi ký tự, còn ASCII 1 byte. Khi đọc/ghi text mà không chỉ định charset, chương trình dùng Charset.defaultCharset() — trên JDK 18+ (JEP 400) mặc định là UTF-8 không phụ thuộc locale/OS; chỉ bị đổi khi truyền -Dfile.encoding=... (hoặc -Dfile.encoding=COMPAT để quay về hành vi theo OS) hay chạy trên JDK cũ. Đó là lý do quy tắc số 1 của I/O text: luôn chỉ định charset ở biên.

FileReader/FileWriter dùng charset mặc định nếu bạn gọi constructor không có charset — constructor đó lấy Charset.defaultCharset(). Từ JDK 11 đã có constructor nhận Charset (new FileWriter(path, UTF_8), new FileReader(path, UTF_8)), nhưng Files.newBufferedWriter(path, UTF_8) / Files.newBufferedReader(path, UTF_8) vẫn gọn hơn vì nhận thẳng Path. Chỉ cần JVM chạy với -Dfile.encoding=ISO-8859-1 (CI, tùy chọn legacy) là ký tự tiếng Việt bị thay bằng ? âm thầm khi ghi nếu bạn quên charset. Code production hãy chỉ định charset tường minh.

4.2 Demo: FileWriter ghi mất dấu mà không báo lỗi

Chạy file sau hai lần — lần đầu bình thường, lần sau ép charset mặc định thành ISO-8859-1. Chuỗi dùng escape \u1EBF để source chỉ chứa ASCII, tránh việc -Dfile.encoding còn ảnh hưởng cả cách javac đọc source:

void main() throws IOException {

    IO.println("Dang UTF-8 can : " + text.getBytes(StandardCharsets.UTF_8).length + " byte");

Ghép từ các lớp gốc; InputStreamReader chính là cầu byte→char và là nơi khai báo charset:

void main() throws IOException {

  • BufferedWriter.newLine() ghi đúng dấu xuống dòng của hệ điều hành (\n trên Unix/macOS, \r\n trên Windows). printf("%n") cũng vậy; còn "\n" luôn là LF.

4.4 Scanner — parse token/kiểu dữ liệu

Scanner tiện khi cần tách token và parse sẵn kiểu (nextInt, nextDouble…) với delimiter tuỳ biến — thay vì tự split rồi parse. Đổi lại nó chậm hơn BufferedReader và xử lý lỗi kém rõ ràng, nên đọc file lớn vẫn ưu tiên Files.lines/BufferedReader:

void main() throws IOException {
    Path dir = Files.createTempDirectory("scan-");
    Path f = dir.resolve("nums.txt");
    Files.writeString(f, "10 20\n30 40", StandardCharsets.UTF_8);

    try (var sc = new Scanner(f, StandardCharsets.UTF_8)) {
        int tong = 0;
        while (sc.hasNextInt()) tong += sc.nextInt();
        IO.println("tong  = " + tong);

    try (var sc = new Scanner("An,20;Binh,22").useDelimiter("[,;]")) {
        StringBuilder sb = new StringBuilder();
        while (sc.hasNext()) sb.append(sc.next()).append(' ');
        IO.println("token = " + sb.toString().trim());
    }

    Files.delete(f);
    Files.delete(dir);
}

5.4 Duyệt cây — Files.list vs walk vs find

Cả ba đều trả Stream<Path> được hỗ trợ bởi handle của hệ điều hành, nên phải đóng bằng try-with-resources. Files.list chỉ liệt kê mục con trực tiếp; Files.walk duyệt đệ quy tới độ sâu cho trước; Files.find như walk kèm predicate lọc ngay (đỡ đọc attribute hai lần):

void main() throws IOException {
    Path dir = Files.createTempDirectory("tree-");
    Files.createDirectories(dir.resolve("2025"));
    Files.createDirectories(dir.resolve("2026/thang-01"));
    Files.writeString(dir.resolve("root.txt"), "r", StandardCharsets.UTF_8);
    Files.writeString(dir.resolve("2025/old.txt"), "o", StandardCharsets.UTF_8);
    Files.writeString(dir.resolve("2026/a.txt"), "a", StandardCharsets.UTF_8);
    Files.writeString(dir.resolve("2026/thang-01/b.txt"), "b", StandardCharsets.UTF_8);
    Files.writeString(dir.resolve("2026/thang-01/c.md"), "c", StandardCharsets.UTF_8);

    IO.println("Files.list (chi muc con truc tiep), sap xep:");
    try (var list = Files.list(dir)) {
        list.sorted().forEach(p -> IO.println("  " + dir.relativize(p)));
    }

    IO.println("Files.walk depth 2:");
    try (var walk = Files.walk(dir, 2)) {
        walk.sorted().forEach(p -> IO.println("  " + (p.equals(dir) ? "." : dir.relativize(p))));
    }

    IO.println("Files.find: file .txt nam sau nhat 3 cap:");
    try (var find = Files.find(dir, 3,
            (p, attr) -> attr.isRegularFile() && p.getFileName().toString().endsWith(".txt"))) {
        find.sorted().forEach(p -> IO.println("  " + dir.relativize(p)));
    }

    try (var walk = Files.walk(dir)) {
        walk.sorted(Comparator.reverseOrder()).forEach(p -> {
            try { Files.delete(p); } catch (IOException e) { throw new UncheckedIOException(e); }
        });
    }
}

5.5 Files.lines — đọc dòng kiểu Stream

Files.lines mở file và trả Stream các dòng, đọc lazy: mỗi dòng chỉ được đọc khi pipeline cần. Đổi lại, Stream này giữ file handle nên bắt buộc try-with-resources:

void main() throws IOException {
    Path dir = Files.createTempDirectory("lines-");
    Path f = dir.resolve("log.txt");
    Files.writeString(f, """
            2026-01-03 Giao don A01
            2026-01-04 Huy don A02
            2026-01-05 Giao don A03
            """, StandardCharsets.UTF_8);

    try (var lines = Files.lines(f, StandardCharsets.UTF_8)) {
        lines.filter(l -> l.contains("Giao"))
             .forEach(IO::println);
    }

    long soDong;
    try (var lines = Files.lines(f, StandardCharsets.UTF_8)) {
        soDong = lines.count();
    }
    IO.println("Dem dong: " + soDong);

    Files.delete(f);
    Files.delete(dir);
}

2026-01-05 Giao don A03

Stream API đầy đủ (map/filter/collect/parallel) học ở 3.8 Stream API; ở đây chỉ cần nhớ Files.lines là cầu nối I/O ↔ Stream, và stream từ I/O luôn phải đóng. Với file rất lớn, pipeline lazy giúp xử lý mà không nạp cả file vào RAM — nhưng nếu gọi collect(toList()) thì lại nạp hết; đừng nhầm "lazy" với "tiết kiệm bộ nhớ luôn luôn".

5.6 DirectoryStream — duyệt thư mục kiểu Iterator

Files.newDirectoryStream trả DirectoryStream<Path> — duyệt bằng for-each (không phải Stream API) và nhận glob pattern để lọc tên ngay từ OS. Hợp khi chỉ cần liệt kê một cấp thư mục mà không muốn kéo cả Stream pipeline:

void main() throws IOException {
    Path dir = Files.createTempDirectory("ds-");
    Files.writeString(dir.resolve("a.txt"), "a", StandardCharsets.UTF_8);
    Files.writeString(dir.resolve("b.txt"), "b", StandardCharsets.UTF_8);
    Files.writeString(dir.resolve("c.md"), "c", StandardCharsets.UTF_8);

    try (DirectoryStream<Path> ds = Files.newDirectoryStream(dir, "*.txt")) {
        List<String> names = new ArrayList<>();
        for (Path p : ds) names.add(p.getFileName().toString());
        Collections.sort(names);
        IO.println("glob *.txt = " + names);
    }

    try (var walk = Files.walk(dir)) {
        walk.sorted(Comparator.reverseOrder()).forEach(p -> {
            try { Files.delete(p); } catch (IOException e) { throw new UncheckedIOException(e); }
        });
    }
}
glob *.txt = [a.txt, b.txt]
DirectoryStream cũng giữ file handle của OS nên phải đóng (try-with-resources). Nó không phải java.util.stream.Stream: không có map/filter/collect — muốn pipeline thì dùng Files.list, còn lọc glob thì newDirectoryStream gọn hơn.

5.7 readAttributes, mismatch & metadata

Files.readAttributes trả một lượt nhiều metadata (thay vì gọi Files.size, Files.isDirectory… nhiều lần — mỗi lần một syscall). Files.mismatch(p1, p2) so nội dung hai file và trả vị trí byte khác nhau đầu tiên, -1 nếu giống hệt — nhanh hơn đọc cả hai vào RAM để so:

void main() throws IOException {
    Path dir = Files.createTempDirectory("attr-");
    Path a = dir.resolve("a.txt");
    Path b = dir.resolve("b.txt");
    Files.writeString(a, "abc", StandardCharsets.UTF_8);
    Files.writeString(b, "abd", StandardCharsets.UTF_8);

    BasicFileAttributes attrs = Files.readAttributes(a, BasicFileAttributes.class);
    IO.println("isRegularFile = " + attrs.isRegularFile());
    IO.println("size          = " + attrs.size());
    IO.println("lastModified  = " + (attrs.lastModifiedTime().toMillis() > 0));
    IO.println("mismatch(a,b) = " + Files.mismatch(a, b));

    Files.writeString(b, "abc", StandardCharsets.UTF_8);
    IO.println("sau khi giong = " + Files.mismatch(a, b));

    Files.delete(a);
    Files.delete(b);
    Files.delete(dir);
}

sau khi giong = -1
Cần thêm quyền/owner/chủ sở hữu POSIX thì dùng view riêng: Files.readAttributes(p, PosixFileAttributes.class) hoặc DosFileAttributes trên Windows; kiểm tra supportedFileAttributeViews() trước. Với symlink, nhớ LinkOption.NOFOLLOW_LINKS nếu muốn đọc thuộc tính của chính link.

6. Bẫy encoding & tiếng Việt Hay hỏi phỏng vấn Production

6.1 Mojibake — đọc UTF-8 bằng charset sai

Tiếng Việt có dấu là "máy dò" encoding tốt nhất. Cùng một dãy byte, decode bằng charset khác nhau cho ra chuỗi khác nhau — hiện tượng này gọi là mojibake (chữ hỏng). Ví dụ kinh điển: đọc UTF-8 bằng windows-1252 (mặc định một thời của Windows):

void main() throws IOException {
    String goc = "Tiếng Việt có dấu";
    byte[] utf8 = goc.getBytes(StandardCharsets.UTF_8);
    IO.println("So byte UTF-8: " + utf8.length);

    // co tinh doc sai charset
    String sai = new String(utf8, Charset.forName("windows-1252"));
    IO.println("Doc sai       : " + sai);

    // sua: ma hoa lai dung charset da doc sai, roi decode UTF-8
    String sua = new String(sai.getBytes(Charset.forName("windows-1252")), StandardCharsets.UTF_8);
    IO.println("Doc lai dung  : " + sua);

    Path dir = Files.createTempDirectory("enc-");
    Path f = dir.resolve("utf8.txt");
    Files.write(f, utf8);

    IO.println("readString UTF-8: " + Files.readString(f, StandardCharsets.UTF_8));
    IO.println("readAllBytes    : " + Files.readAllBytes(f).length + " byte");

    Files.delete(f);
    Files.delete(dir);
}

Chuỗi "Tiếng Việt có dấu" dài 17 ký tự nhưng chiếm 24 byte UTF-8. Khi thấy dữ liệu hiển thị dạng Tiáº¿ng Viá»‡t, gần như chắc chắn đâu đó đang decode UTF-8 bằng một charset single-byte (windows-1252/ISO-8859-1). Cách sửa đúng là tìm và chỉnh đúng chỗ decode, không phải "sửa chuỗi" lung tung. Chuỗi mojibake trong ví dụ là CP1252 → đảo ngược hoàn hảo vì các byte đã dùng đều được windows-1252 định nghĩa. Đừng nhầm chiều mất dữ liệu: ISO-8859-1 ánh xạ đủ cả 256 byte nên round-trip 0 mất; còn windows-1252 có 5 byte không định nghĩa (0x81, 0x8D, 0x8F, 0x90, 0x9D) — gặp chúng sẽ decode thành U+FFFD, rồi encode lại bị thay bằng 0x3F (?) và mất dữ liệu thật.

6.2 Byte hỏng và hai kiểu phản ứng

Cùng gặp chuỗi byte không hợp lệ, hai API phản ứng khác nhau — đây là bẫy âm thầm:

void main() throws IOException {

        Files.readString(f, StandardCharsets.UTF_8);

        IO.println("readString: " + e.getClass().getSimpleName());

    Files.delete(dir);

6.3 BOM — ký tự vô hình đầu file

UTF-8 BOM là 3 byte EF BB BF mà một số công cụ (điển hình là Excel khi lưu CSV) chèn đầu file. Java không tự bỏ BOM, nên nó biến thành ký tự U+FEFF đầu dòng, làm so sánh chuỗi trượt:

void main() throws IOException {
    Path dir = Files.createTempDirectory("bom-");
    Path f = dir.resolve("bom.csv");

    byte[] bom = {(byte) 0xEF, (byte) 0xBB, (byte) 0xBF};
    Files.write(f, bom);
    Files.write(f, "ma,ten\nA01,Ghe".getBytes(StandardCharsets.UTF_8), StandardOpenOption.APPEND);

    String s = Files.readString(f, StandardCharsets.UTF_8);
    IO.println("startsWith ma    = " + s.startsWith("ma"));
    IO.println("startsWith BOM   = " + s.startsWith("\uFEFF"));
    IO.println("char dau (int)   = " + (int) s.charAt(0));
    IO.println("dong dau tho     = " + s.lines().findFirst().orElse(""));
    String sach = s.startsWith("\uFEFF") ? s.substring(1) : s;
    IO.println("sau khi bo BOM   = " + sach.lines().findFirst().orElse(""));

    Files.delete(f);
    Files.delete(dir);
}

Hai quy tắc thực dụng: (1) đọc file do người dùng/Excel tạo thì strip U+FEFF ở đầu trước khi parse — nhớ xử lý cả trường hợp chỉ đọc dòng đầu; (2) khi ghi CSV cho Excel mở đúng tiếng Việt trên Windows, có thể phải thêm BOM thủ công.

    IO.println("native.encoding = " + System.getProperty("native.encoding"));
    IO.println("Charset.default = " + Charset.defaultCharset());

  • System.out.charset() là charset mà terminal/console đang chờ, có thể khác Charset.defaultCharset(). Trên Windows cmd cũ thường là CP1258/CP437 — tiếng Việt in ra hỏng dù file ghi đúng; sửa bằng chcp 65001 hoặc set -Dstdout.encoding=UTF-8.

Nguyên tắc vàng: bên trong chương trình, String là Unicode — không có encoding. Encoding chỉ tồn tại ở biên I/O: đọc file, ghi file, đọc socket, đọc HTTP request, ghi DB, in console, nhận tham số dòng lệnh. Hãy khai báo UTF-8 ở mọi biên đó và kiểm tra ở cả hai đầu hệ thống (client gửi gì — server đọc nấy).

6.5 CharsetDecoder/CharsetEncoder & CodingErrorAction

Đằng sau mọi new String(bytes, charset)/getBytes(charset) là một CharsetDecoder/CharsetEncoder. Khi cần kiểm soát chi tiết cách xử lý byte/char hỏng, bạn cấu hình trực tiếp qua CodingErrorAction: REPORT (ném CharacterCodingException), REPLACE (thay bằng ký tự thay thế — mặc định khi decode) và IGNORE (bỏ qua — thường chỉ hợp khi encode):

import java.nio.charset.*;
void main() {
    Charset utf8 = StandardCharsets.UTF_8;
    byte[] bad = {(byte) 0xE1, (byte) 0xBA};

    CharsetDecoder replace = utf8.newDecoder()
            .onMalformedInput(CodingErrorAction.REPLACE)
            .onUnmappableCharacter(CodingErrorAction.REPLACE);
    try {
        CharBuffer cb = replace.decode(ByteBuffer.wrap(bad));
        IO.println("REPLACE -> char=" + (int) cb.charAt(0));
    } catch (CharacterCodingException e) {
        IO.println("REPLACE -> " + e.getClass().getSimpleName());
    }

    CharsetDecoder report = utf8.newDecoder()
            .onMalformedInput(CodingErrorAction.REPORT)
            .onUnmappableCharacter(CodingErrorAction.REPORT);
    try {
        report.decode(ByteBuffer.wrap(bad));
    } catch (CharacterCodingException e) {
        IO.println("REPORT  -> " + e.getClass().getSimpleName());
    }

    try {
        CharsetEncoder ignore = utf8.newEncoder()
                .onMalformedInput(CodingErrorAction.IGNORE)
                .onUnmappableCharacter(CodingErrorAction.IGNORE);
        ByteBuffer out = ignore.encode(CharBuffer.wrap("a\uD800b"));
        IO.println("IGNORE  -> " + new String(out.array(), 0, out.remaining(), utf8) + " (" + out.remaining() + " byte)");
    } catch (CharacterCodingException e) {
        IO.println("IGNORE  -> " + e.getClass().getSimpleName());
    }
}
REPLACE -> char=65533
REPORT  -> MalformedInputException
IGNORE  -> ab (2 byte)
Decoder/encoder "trần" mặc định là REPORT (thử StandardCharsets.UTF_8.newDecoder().decode(...) với byte hỏng sẽ thấy MalformedInputException). Chính new String(bytes, charset) và String.getBytes(charset) (qua StringCoding) mới cấu hình REPLACE — vì vậy chúng âm thầm ra U+FFFD/? thay vì ném lỗi. Các API NIO như Files.readString/newBufferedReader dùng REPORT nên lỗi dữ liệu lộ ra sớm — xem mục 6.2.

7. try-with-resources, flush & close Hay hỏi phỏng vấn

7.1 try-with-resources đóng theo thứ tự ngược

Mọi resource implement AutoCloseable đều dùng được trong try-with-resources (Java 7+). Resource được đóng theo thứ tự ngược với lúc mở (LIFO), kể cả khi body return hoặc ném exception. Chi tiết exception suppression học ở exceptions.html; phần I/O chỉ cần nhớ thứ tự đóng quyết định dữ liệu có được flush đúng hay không:

class Res implements AutoCloseable {
    private final String ten;

    Res(String ten) {
        this.ten = ten;
        IO.println("mo  " + ten);
    }

    @Override
    public void close() {
        IO.println("dong " + ten);
    }
}

void main() throws Exception {
    IO.println("truoc try");
    try (var a = new Res("A"); var b = new Res("B")) {
        IO.println("trong try");
    }
    IO.println("sau try");
}
truoc try
mo  A
mo  B
trong try
dong B
dong A
sau try

Bọc nhiều lớp cũng theo nguyên tắc đó: đóng BufferedWriter trước, nó tự flush rồi mới đóng FileOutputStream bên trong. Bạn không cần gọi close() thủ công cho từng lớp — chỉ cần đóng lớp ngoài cùng. Ngược lại, đóng lớp trong trước rồi mới dùng lớp ngoài sẽ lỗi, nên hãy để try-with-resources lo trọn gói.

7.2 flush() vs close() — dữ liệu mất ở đâu

void main() throws IOException {
    Path dir = Files.createTempDirectory("flush-");
    Path f = dir.resolve("out.txt");

    var w = new BufferedWriter(Files.newBufferedWriter(f, StandardCharsets.UTF_8));
    w.write("dữ liệu");
    IO.println("size truoc flush = " + Files.size(f));

    w.flush();
    IO.println("size sau flush   = " + Files.size(f));

    w.write(" them");
    IO.println("size sau ghi tiep= " + Files.size(f));
    w.close();
    IO.println("size sau close   = " + Files.size(f));
    IO.println("noi dung         = " + Files.readString(f, StandardCharsets.UTF_8));

    Files.delete(f);
    Files.delete(dir);
}
size truoc flush = 0
size sau flush   = 11
size sau ghi tiep= 11
size sau close   = 16
noi dung         = dữ liệu them
  • flush() đẩy dữ liệu từ buffer trong RAM xuống hệ điều hành; sau đó bạn vẫn ghi tiếp bình thường.
  • close() flush rồi trả tài nguyên (file handle) về cho OS. Sau close() không dùng lại được resource.
  • Buffered stream chưa flush/close thì dữ liệu còn nằm trong RAM — size bằng 0 như ví dụ. Với socket, quên flush còn khiến phía kia chờ vô hạn.
  • try-with-resources gọi close() giúp bạn, nên hiếm khi cần flush() thủ công — ngoại lệ là socket/stream trước khi đọc phản hồi ngay (request/response trên cùng kết nối).

7.3 Exception khi close

Nếu body try ném exception và close() cũng ném, exception của close() được gắn vào exception chính qua getSuppressed() — bạn không mất thông tin gốc. Nếu chỉ close() ném (body chạy bình thường), exception đó trở thành exception chính. Vì vậy đừng viết close() có logic nghiệp vụ phức tạp, và đừng "nuốt" exception trong close().

8. Mini project — quản lý đơn hàng CSV

Ghép mọi thứ đã học: tạo thư mục tạm, ghi CSV UTF-8, đọc bằng Files.readAllLines, parse bằng split + Integer.parseInt/Long.parseLong, tính tổng, lọc theo ngưỡng, ghi file kết quả và tự dọn. List/ArrayList đã học ở 3.3 Collections; chỗ này cố tình dùng vòng lặp thay vì Stream (3.8 học sau) để bạn thấy rõ từng bước:

record DonHang(String ma, String ten, int soLuong, long donGia) {
    long tongTien() {
        return soLuong * donGia;
    }
}

void main() throws IOException {
    Path dir = Files.createTempDirectory("donhang-");
    Path csv = dir.resolve("don-hang.csv");

    Files.writeString(csv, """
            A01,Bàn phím cơ,2,890000
            A02,Chuột không dây,1,450000
            A03,Màn hình 27 inch,1,3200000
            A04,Tai nghe,3,250000
            """, StandardCharsets.UTF_8);

    List<DonHang> donHangs = new ArrayList<>();
    for (String line : Files.readAllLines(csv, StandardCharsets.UTF_8)) {
        if (line.isBlank()) {
            continue;
        }
        String[] parts = line.split(",");
        donHangs.add(new DonHang(
                parts[0],
                parts[1],
                Integer.parseInt(parts[2]),
                Long.parseLong(parts[3])));
    }

    long tong = 0;
    for (DonHang d : donHangs) {
        tong += d.tongTien();
    }
    IO.println("Tong tien: " + tong);

    long nguong = 1_000_000;
    List<String> ketQua = new ArrayList<>();
    for (DonHang d : donHangs) {
        if (d.tongTien() > nguong) {
            ketQua.add(d.ma() + "," + d.ten() + "," + d.tongTien());
        }
    }

    Path out = dir.resolve("ket-qua.csv");
    Files.write(out, ketQua, StandardCharsets.UTF_8);
    IO.println("Ghi " + ketQua.size() + " don vao " + out.getFileName());

    for (String line : Files.readAllLines(out, StandardCharsets.UTF_8)) {
        IO.println(line);
    }

    Files.delete(csv);
    Files.delete(out);
    Files.delete(dir);
}

  • split(",") đủ cho CSV đơn giản, nhưng CSV thật có dấu phẩy trong tên, dấu ngoặc kép, xuống dòng trong ô — lúc đó cần parser chuẩn (RFC 4180) hoặc thư viện như OpenCSV. Đây là bẫy phỏng vấn rất hay gặp.
  • Integer.parseInt/Long.parseLong ném NumberFormatException khi ô rỗng/sai định dạng — production phải validate từng dòng và thông báo kèm số dòng lỗi, đừng để cả file fail vì một dòng.
  • Tiền nên là long theo đơn vị nhỏ nhất (VND) hoặc BigDecimal cho USD — xem Biến trong Java — mục 13. long tính bằng * có thể tràn nếu số lượng/đơn giá lớn; kiểm tra hoặc dùng Math.multiplyExact.
  • Files.write(path, Iterable<CharSequence>, charset) tự thêm dấu xuống dòng sau mỗi phần tử. Muốn kiểm soát hoàn toàn, dùng BufferedWriter và newLine().
  • Thư mục tạm của OS được dọn tự động theo thời gian nhưng đừng ỷ lại — code mẫu vẫn delete để ví dụ chạy lại được nhiều lần.

9.1 Atomic write, quyền file, symbolic link

void main() throws IOException {
    Path dir = Files.createTempDirectory("prod-");
    Path target = dir.resolve("config.properties");
    Files.writeString(target, "version=1", StandardCharsets.UTF_8);

    Path tmp = Files.createTempFile(dir, "config-", ".tmp");
    try {
        Files.writeString(tmp, "version=2", StandardCharsets.UTF_8);
        Files.move(tmp, target, StandardCopyOption.ATOMIC_MOVE, StandardCopyOption.REPLACE_EXISTING);
        IO.println("noi dung moi = " + Files.readString(target));
    } finally {
        Files.deleteIfExists(tmp);
    }

    Path link = dir.resolve("link.properties");
    Files.createSymbolicLink(link, target.getFileName());
    IO.println("isSymbolicLink           = " + Files.isSymbolicLink(link));
    IO.println("isRegularFile (follow)   = " + Files.isRegularFile(link));
    IO.println("isRegularFile NOFOLLOW   = " + Files.isRegularFile(link, LinkOption.NOFOLLOW_LINKS));
    IO.println("readSymbolicLink         = " + Files.readSymbolicLink(link));

    Files.setPosixFilePermissions(target, PosixFilePermissions.fromString("rw-------"));
    IO.println("quyen                    = " + Files.getPosixFilePermissions(target));

    Files.delete(link);
    Files.delete(target);
    Files.delete(dir);
}

  • Atomic write — ghi ra file tạm cùng thư mục rồi Files.move(..., ATOMIC_MOVE). Người đọc chỉ thấy bản cũ hoặc bản mới, không bao giờ thấy file dở dang; dùng cho file cấu hình/state mà tiến trình khác có thể đọc đồng thời. Trên POSIX, rename cùng filesystem là atomic. Lưu ý Javadoc: khi có ATOMIC_MOVE thì mọi option khác bị bỏ qua (kể cả REPLACE_EXISTING), và nếu đích đã tồn tại thì việc thay thế hay ném lỗi là implementation-specific (trên Unix provider mặc định, rename thay thế đích). Cần bền vững qua mất điện thì thêm FileChannel.force(true) trước khi move.
  • Quyền file — PosixFilePermissions chỉ chạy trên hệ thống POSIX; trên Windows ném UnsupportedOperationException, phải kiểm tra FileSystems.getDefault().supportedFileAttributeViews().contains("posix"). File chứa bí mật nên để rw-------; đừng đặt quyền mở cho tiện.
  • Symbolic link — nhiều method như Files.isRegularFile, Files.size, Files.readAttributes mặc định đi theo link (thao tác trên đích); thêm LinkOption.NOFOLLOW_LINKS để thao tác trên chính link. Riêng Files.delete không đi theo link và không nhận LinkOption: nó luôn xoá chính link, không xoá đích — muốn xoá đích phải trỏ thẳng tới đường dẫn đích.
Path traversal: không bao giờ ghép đường dẫn từ input người dùng bằng phép cộng chuỗi hay resolve trần. Input "../../etc/passwd" hoặc đường dẫn tuyệt đối có thể thoát khỏi thư mục cho phép — xem Q&A 15 để biết cách chặn.

9.2 Checklist production cho I/O

  • Không hardcode path — nhận base directory từ cấu hình/biến môi trường, ghép bằng Path.of(base).resolve(...). Đừng dùng "data/orders.csv" trần vì working directory khi chạy service khác khi chạy test.
  • File lớn thì đọc theo dòng — Files.lines hoặc BufferedReader, tuyệt đối không readAllLines/readString cho file GB. Ghi cũng vậy, dùng BufferedWriter thay vì dựng cả String khổng lồ.
  • Luôn chỉ định UTF-8 ở mọi biên; đừng phụ thuộc Charset.defaultCharset(). Kiểm tra cả phía nhận dữ liệu (DB collation, HTTP charset header).
  • Đóng resource bằng try-with-resources; với Stream từ Files.list/walk/find/lines càng bắt buộc vì giữ file handle của OS.
  • Atomic write cho file trạng thái/cấu hình; ATOMIC_MOVE chỉ hiệu lực khi nguồn và đích cùng filesystem — file tạm phải nằm cùng thư mục với đích. Nhớ: option khác đi kèm bị bỏ qua và việc ghi đè đích là implementation-specific, nên đừng dựa vào REPLACE_EXISTING khi đã có ATOMIC_MOVE.
  • Không dùng File trong code mới; chuyển dần bằng toPath(). Ưu tiên Files vì exception nói rõ lý do (không tồn tại, bị chiếm, hết quyền…).
  • Kiểm tra quyền trước khi ghi — Files.isWritable; thư mục cha phải tồn tại, tạo bằng createDirectories. Ghi file secret với quyền hạn chế.
  • Xử lý IOException có ngữ cảnh — log kèm đường dẫn và thao tác ("Khong ghi duoc " + path), giữ nguyên exception gốc làm cause. Không catch rồi bỏ qua.
  • Cẩn thận symlink và TOCTOU — kiểm tra tồn tại rồi mới mở là hai bước có thể bị thay đổi ở giữa; với thư mục do người khác ghi, ưu tiên thao tác trực tiếp và bắt exception.
  • Đặt tên file theo thời gian — log/backup nên có timestamp trong tên; dùng java.time (LocalDate, DateTimeFormatter) thay vì SimpleDateFormat cũ — xem 3.5 java.time.
  • Dọn file tạm trong finally/try-with-resources; đặt tên có prefix dễ nhận biết (createTempFile(dir, "upload-", ".tmp")).

9.3 Khoá file & WatchService (nhận biết)

Khoá file qua FileChannel.lock() (block tới khi lấy được khoá) hoặc tryLock() (trả null nếu đang bị khoá) — dùng cho nhiều tiến trình cùng ghi một file (ví dụ chống chạy 2 instance ghi cùng log). Lưu ý khoá là advisory ở tầng OS: tiến trình không tuân thủ vẫn ghi được, và khoá có thể là exclusive (ghi) hoặc shared (đọc). Trong cùng một JVM, khoá chồng lấn trên cùng file sẽ ném OverlappingFileLockException.

WatchService (FileSystems.getDefault().newWatchService()) theo dõi thư mục và nhận event CREATE/MODIFY/DELETE qua WatchKey — nền tảng để tự động reload config, theo dõi thư mục upload. Là API event-driven, có thể bỏ lỡ event khi overload, và trên một số OS chỉ báo "có thay đổi" chứ không chi tiết từng file — production thường dùng thư viện (ví dụ directory-watcher) thay vì tự viết.

11. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Byte stream và character stream khác nhau thế nào? Khi nào dùng loại nào?
Byte stream (InputStream/OutputStream) vận chuyển byte thô, không diễn giải nội dung — dùng cho ảnh, zip, PDF, audio, protocol nhị phân. Character stream (Reader/Writer) làm việc với char và có bước encode/decode qua charset — dùng cho text: CSV, JSON, log, properties. File trên đĩa luôn là byte; character stream chỉ là lớp bọc thêm charset. Dùng nhầm (đọc text bằng FileInputStream rồi tự cắt byte[]) sẽ chẻ đôi ký tự UTF-8 nhiều byte.
Câu 2. Có những cách nào đọc file text? Chọn cách nào cho trường hợp nào?
Files.readString — file nhỏ, cần cả nội dung một lần (UTF-8 mặc định). Files.readAllLines — cần List<String> và file vừa. Files.lines — cần pipeline Stream, file lớn, lazy, phải đóng. BufferedReader.readLine — vòng lặp cổ điển, kiểm soát tốt, file rất lớn. Scanner — parse token/kiểu dữ liệu nhanh gọn nhưng chậm hơn và ít dùng cho production I/O. Quy tắc: file lớn thì không readString/readAllLines; xử lý theo dòng để bộ nhớ không tăng theo kích thước file.
Câu 3. Vì sao "ế".length() == 1 nhưng ghi UTF-8 lại mất 3 byte?
Trong RAM, Java lưu String bằng compact strings (từ JDK 9): Latin-1 1 byte/char khi mọi ký tự biểu diễn được, ngược lại UTF-16; nhưng API như String.length()/charAt() luôn đếm code unit 16 bit, không phải byte. Ký tự ế (U+1EBF) nằm trong BMP nên chỉ 1 char, nhưng UTF-8 cần 3 byte để mã hoá. Với ký tự ngoài BMP (emoji), một code point cần 2 char (surrogate pair) nên length() = 2 và codePointCount = 1. Hệ quả: đừng dùng length()/substring() để cắt chuỗi theo "ký tự người dùng"; dùng codePointCount/offsetByCodePoints.
Câu 4. FileReader/FileWriter dùng charset gì? Vì sao production nên tránh?
Constructor không truyền charset dùng Charset.defaultCharset(). Từ JDK 11 đã có constructor nhận Charset (new FileWriter(path, UTF_8), new FileReader(path, UTF_8)); còn Files.newBufferedReader/newBufferedWriter(path, UTF_8) gọn hơn vì nhận thẳng Path. Từ JDK 18 (JEP 400), mặc định là UTF-8 không phụ thuộc locale/OS — chỉ đổi bằng -Dfile.encoding hoặc chạy trên JDK cũ. Khi ghi bằng charset không chứa ký tự tiếng Việt, Java thay bằng ? âm thầm (xem demo mục 4.2: 14 byte thành 10 byte, hex chứa 3f) — không exception, close() cũng im lặng. Vì vậy hãy luôn chỉ định charset tường minh.
Câu 5. readLine() có trả ký tự xuống dòng không? File có \r\n thì sao?
Không. readLine() trả nội dung dòng đã bỏ ký tự kết thúc (\n, \r\n, hoặc \r), trả "" cho dòng trống và null khi hết file. Nhờ vậy while ((line = r.readLine()) != null) phân biệt được dòng rỗng với hết file. Khi ghi, dùng BufferedWriter.newLine() hoặc printf("%n") để ghi đúng dấu của hệ điều hành; "\n" cố định là LF.
Câu 6. Phân biệt read(), read(byte[]) và readAllBytes().
read() đọc 1 byte, trả 0..255 hoặc -1. read(byte[]) đọc tối đa buf.length byte, trả số byte thực đọc (có thể nhỏ hơn độ dài buffer, không bao giờ là 0 khi buf.length > 0) hoặc -1 — phải lặp tới -1 và dùng đúng n. readAllBytes() đọc tới hết vào một mảng — tiện nhưng nạp toàn bộ vào RAM, chỉ dùng file nhỏ. Muốn đọc đủ n byte đã biết, dùng readNBytes(n).
Câu 7. Vì sao cần charset tường minh khi làm việc với text? Bên trong String có encoding không?
Bên trong JVM, String được lưu tối ưu bằng compact strings (Latin-1 khi đủ, UTF-16 nếu không — JDK 9+), nhưng API (length(), charAt()) tính theo UTF-16 code unit — và không có encoding. Encoding chỉ xuất hiện ở biên I/O khi chuyển String ↔ byte[]. Nếu hai đầu biên không thống nhất charset: ghi UTF-8 đọc windows-1252 ra mojibake; ghi bằng charset thiếu ký tự có thể ra ? âm thầm. Nguyên tắc: khai báo UTF-8 ở mọi biên (file, socket, HTTP, DB, console, args) và kiểm tra cả phía gửi lẫn phía nhận.

Nâng cao (Junior+)

Câu 8. try-with-resources hoạt động thế nào? Thứ tự đóng và exception suppression ra sao?
Cú pháp try (R1 a = ...; R2 b = ...) { } yêu cầu resource implement AutoCloseable. Khi thoát khối try (bình thường, return, hay exception), các resource được đóng theo thứ tự ngược lúc khai báo (b rồi a). Nếu body ném exception chính và close() cũng ném, exception của close() được suppress (gắn vào exception chính, đọc bằng getSuppressed()) để không che mất lỗi gốc; nếu chỉ close() ném, nó là exception chính. Chi tiết ở exceptions.html.
Câu 9. flush() và close() khác gì nhau? Khi nào dữ liệu bị mất?
flush() đẩy buffer từ RAM xuống OS nhưng chưa giải phóng tài nguyên — sau đó vẫn ghi tiếp được. close() flush rồi giải phóng file handle; sau đó không dùng lại resource. Buffered stream không flush/close thì dữ liệu vẫn nằm trong RAM (ví dụ mục 7.2: size = 0 trước flush) — chương trình kết thúc hoặc mất điện là mất. Với socket, thiếu flush có thể làm bên kia chờ vô hạn. try-with-resources tự gọi close(), nên hiếm khi cần flush() thủ công — ngoại lệ là giao thức request/response trên cùng kết nối.
Câu 10. Vì sao Files.list/walk/find/lines phải đóng? Không đóng thì sao?
Chúng trả Stream nhưng bên dưới là tài nguyên I/O: Files.lines giữ file handle, Files.list/walk/find tựa trên DirectoryStream cũng mở handle của hệ điều hành. Không đóng → rò rỉ file descriptor; đủ nhiều sẽ gặp Too many open files, trên Windows file còn bị khoá không xoá/ghi được. Vì Stream implement AutoCloseable, hãy luôn đặt trong try-with-resources dù chỉ gọi findFirst() rồi thoát.
Câu 11. Vì sao code mới nên dùng Path thay vì File?
File từ Java 1.0 nhiều hạn chế: method trả boolean không cho biết lý do thất bại, thao tác path thủ công bằng chuỗi dễ sai dấu phân cách, chỉ hỗ trợ file system mặc định. Path (NIO.2, Java 7) immutable, tạo bằng factory Path.of, có resolve/normalize/relativize chuẩn hoá, hỗ trợ nhiều provider (zip file system, in-memory), và Files ném exception cụ thể (NoSuchFileException, AccessDeniedException…). Cầu nối với API cũ: file.toPath() / path.toFile().
Câu 12. BOM là gì? Vì sao đọc CSV do Excel tạo ra hay bị lỗi dòng đầu?
BOM (Byte Order Mark) là vài byte đánh dấu encoding ở đầu file; riêng UTF-8 BOM là EF BB BF. Excel khi lưu CSV thường chèn BOM để nhận diện UTF-8. Java không tự bỏ BOM: sau khi decode UTF-8, nó thành ký tự U+FEFF (char 65279) ở đầu chuỗi, khiến "ma".equals(header) trượt dù mắt thường nhìn giống hệt. Cách xử lý: kiểm tra và cắt U+FEFF đầu nội dung trước khi parse (chú ý cả dòng đầu). Khi ghi CSV cho Excel trên Windows, có thể cần chủ động thêm BOM.
Câu 13. Atomic write là gì? Viết file an toàn cho production như thế nào?
Là kỹ thuật ghi sao cho người đọc khác không bao giờ thấy file dở dang: ghi nội dung mới ra file tạm cùng thư mục, flush/fsync nếu cần, rồi Files.move(tmp, target, ATOMIC_MOVE). Trên POSIX, rename cùng filesystem là thao tác nguyên tử nên người đọc chỉ thấy bản cũ hoàn chỉnh hoặc bản mới hoàn chỉnh. Lưu ý Javadoc: khi có ATOMIC_MOVE, mọi option khác (kể cả REPLACE_EXISTING) bị bỏ qua, và thay thế đích khi đã tồn tại là implementation-specific; ATOMIC_MOVE cũng không hỗ trợ khi vượt filesystem. Cần bền vững qua mất điện thì gọi FileChannel.force(true) trước khi move; luôn dọn file tạm trong finally.
Câu 14. DataInputStream dùng khi nào? Vì sao phải khớp thứ tự ghi/đọc?
Dùng để đọc/ghi primitive và chuỗi theo định dạng nhị phân cố định, độc lập nền tảng (big-endian; writeUTF dùng 2 byte độ dài + modified UTF-8). Vì định dạng không có nhãn/độ dài phân cách kiểu, reader phải gọi đúng chuỗi method theo đúng kiểu: lệch một kiểu là mọi byte sau đó bị diễn giải sai (giá trị rác như 1.5384599001E-313) hoặc EOFException. Chỉ dùng khi cả hai đầu do bạn kiểm soát; giao tiếp giữa các hệ thống dùng JSON/protobuf. Tuyệt đối không dùng ObjectInputStream với dữ liệu không tin cậy vì rủi ro deserialization.
Câu 15. Vì sao ghép đường dẫn từ input người dùng là lỗ hổng? Chặn thế nào?
Vì resolve với input tuyệt đối sẽ thay thế path gốc (Path.of("uploads").resolve("/etc/passwd") → /etc/passwd), còn input chứa .. có thể thoát khỏi thư mục cho phép — gọi là path traversal. Cách chặn: chuẩn hoá rồi kiểm tra nằm trong gốc, ví dụ Path base = Path.of(uploadDir).toAbsolutePath().normalize(); Path target = base.resolve(userInput).normalize(); if (!target.startsWith(base)) throw new IllegalArgumentException(...). Không ghép bằng phép +, không tin tên file do client gửi, và cẩn thận thêm với symbolic link trong thư mục ai cũng ghi được.

Checklist tự đánh giá trước phỏng vấn

  • Phân biệt byte stream và character stream, nêu 3 tình huống dùng mỗi loại.
  • Giải thích vì sao file luôn là byte còn String chỉ là chuỗi code unit UTF-16 (compact strings từ JDK 9), và charset nằm ở đâu trong đường đi.
  • Biết read() trả 0..255/-1 và read(byte[]) có thể trả ít hơn buffer.
  • Tự tay đọc/ghi được file UTF-8 chỉ với Files.newBufferedReader/newBufferedWriter.
  • Giải thích được demo FileWriter mất dấu với -Dfile.encoding=ISO-8859-1 (14 byte → 10 byte, hex 3f).
  • Nhớ Files.readString ném MalformedInputException còn new String thay bằng U+FFFD.
  • Nhận diện mojibake windows-1252 của tiếng Việt và biết cách điều tra đúng chỗ decode.
  • Giải thích BOM EF BB BF và cách strip U+FEFF.
  • Trả lời trôi chảy try-with-resources: LIFO, suppressed exception, resource phải AutoCloseable.
  • Phân biệt flush() và close(), kể được ca dữ liệu mất do thiếu flush.
  • Dùng thành thạo Path.of/resolve/normalize/relativize/getFileName/parent.
  • Phân biệt Files.list/walk/find, biết walk tính cả thư mục gốc và Stream phải đóng.
  • Viết được atomic write và giải thích vì sao file tạm phải cùng thư mục.
  • Nhận diện path traversal và viết được đoạn kiểm tra startsWith(base).
  • Kể được vì sao không dùng readAllLines/readString cho file lớn.
  • Nén/giải nén được GZIP và ZIP; nhớ truyền charset cho tên entry và chống Zip Slip khi giải nén.
  • Phân biệt đọc tuần tự với RandomAccessFile/FileChannel/memory-mapped; biết DirectoryStream cũng phải đóng.
