1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Bạn không cần biết JVM ở mức đọc mã C++ của HotSpot. Nhưng khi production có sự cố — service chậm, CPU cao, bị kill đột ngột, log chỉ có một dòng OutOfMemoryError — người hiểu JVM sẽ biết ngay phải xem gì: heap hay metaspace đầy? GC pause hay thread treo? Container thiếu RAM hay code giữ reference? Mức độ bắt buộc của chủ đề 4.1 (phỏng vấn: trung bình–cao · production: nên biết):

  • Phải làm được — phân biệt JDK/JRE/JVM; chạy java TenFile.java; đọc được stack trace để tìm class + dòng lỗi; hiểu -Xmx đang đặt bao nhiêu; phân biệt lỗi stack với lỗi heap.
  • Phải hiểu — bytecode và vai trò JVM; classloader và delegation; stack (per-thread) vs heap (dùng chung) vs metaspace; GC roots; minor/full GC và stop-the-world; vì sao giữ reference trong static collection gây leak.
  • Nhận biết — các flag tuning, container awareness; bộ công cụ jps/jstack/jcmd/jmap/jstat, VisualVM, JFR; khi nào cần heap dump. Các phần này trang chỉ giới thiệu đủ để biết tên và khi nào dùng — không đào sâu tuning GC.

Cách học hiệu quả nhất:

  1. Đoán output của ví dụ trước khi nhìn kết quả (kết quả thật, chạy bằng JDK 25 trên máy này).
  2. Làm mục Bài tập đoán output trước, chỉ mở đáp án sau khi đã đoán.
  3. Ôn nhanh bằng Cheat sheet trước buổi phỏng vấn.
  4. Gặp câu lạ, tra ở mục Interview Q&A.
Ví dụ dùng IO.println(...) — cách viết gọn của JDK 25 (JEP 512, lớp java.lang.IO), tương đương System.out.println(...) mà bạn sẽ thấy trong đề phỏng vấn và codebase cũ. Stack của thread và pass-by-value đã học ở Biến trong Java — mục 7; trang này đi sâu vào phía JVM.

Góc Node.js — V8 vs JVM, event loop vs thread

Bạn đã quen Node.js: một process có event loop chạy JS trên một thread, việc nặng đẩy cho libuv worker pool. Java thì khác căn bản: một JVM process có thể chạy nhiều thread cùng lúc, mỗi thread có stack riêng và chia sẻ heap — đó là lý do phải học concurrency (xem Concurrency — mục 2). Về bộ nhớ, cả hai đều có GC và đều có giới hạn heap riêng:

Điểm chung đáng nhớ: GC chỉ thu hồi được object không còn ai tham chiếu tới. Trong Node, biến module-level giữ reference là leak; trong Java, static field/collection giữ reference cũng leak y hệt. Phần còn lại của trang sẽ cho bạn bộ từ vựng và công cụ để nói về chuyện đó một cách chính xác.

Nhưng đừng nói "JVM là JRE" trong phỏng vấn: JVM chỉ là cỗ máy thực thi, JRE là JVM + thư viện, JDK là JRE + công cụ.

3. Class loading — class được nạp thế nào Junior+

Trước khi chạy được, class phải được classloader tìm, đọc file .class và định nghĩa thành một Class<?> trong bộ nhớ. Có 3 classloader chính trong JDK hiện đại:

    static {
        IO.println("  >> static block cua Init chay (initialize)");

  • String trả về null — không phải lỗi: bootstrap loader không có Java object đại diện, quy ước trả null. Đây là câu hỏi phỏng vấn quen thuộc.
  • Chuỗi cha-con cho thấy Application → Platform → Bootstrap là một cây. Loader cha của AppClassLoader là PlatformClassLoader; cha của PlatformClassLoader là null (bootstrap).
  • Load vs initialize: lấy Init.class (class literal) chỉ nạp class, không chạy static block. Đọc hằng số compile-time Init.NHAN cũng không — giá trị đã bị compiler nội suy (inlined) từ trước. Chỉ tới lúc gọi method Init.tang() class mới được khởi tạo và static block chạy. Quy tắc này ở JLS §12.4.1, và có ví dụ liên quan ở Biến trong Java — mục 10, Classes & Objects — mục 6.

Delegation model — luôn hỏi cha trước

Khi bạn gọi ClassLoader.loadClass("X"), loader không tự tìm ngay mà theo trình tự:

  1. Kiểm tra class đã được loader này nạp chưa; nếu rồi thì trả lại.
  2. Nhờ loader cha nạp trước (đệ quy lên tới bootstrap).
  3. Cha thất bại thì loader mới tự tìm trong classpath/nguồn của mình.

Mục đích là an toàn và nhất quán: bạn không thể "tráo" java.lang.String bằng class của mình, vì mọi request đều bị đẩy lên bootstrap. Đổi lại, các hệ sinh thái như Servlet container (Tomcat) hay plugin có thể cố tình phá thứ tự "parent-first" để mỗi webapp có bản thư viện riêng — đó cũng là nguồn gốc của classloader leak khi redeploy (metaspace không được thu hồi, xem mục 6).

Classpath là danh sách thư mục/JAR để Application classloader tìm class. Khi trùng tên class ở nhiều nơi, thứ tự classpath quyết định bản nào được dùng — lý do lỗi "NoSuchMethodError" sau khi nâng cấp thư viện thường là class cũ còn sót trên classpath. Từ JDK 9, code JDK được tổ chức thành module, nhưng code thường của bạn vẫn chạy theo cơ chế classpath quen thuộc.

Vì vậy truyền primitive vào method là sao chép giá trị, truyền object là sao chép địa chỉ. Bốn câu trong ví dụ sau minh hoạ trực tiếp:

public class MemoryDemo {
    record DonHang(int id, String ten) {}

    public static void main() {
        Runtime rt = Runtime.getRuntime();
        long mb = 1024 * 1024;
        IO.println("Xmx (maxMemory) = " + rt.maxMemory() / mb + " MB");

        DonHang a = new DonHang(1, "DH-1");
        DonHang b = a;
        IO.println("a == b          = " + (a == b));
        IO.println("a.equals(b)     = " + a.equals(b));

        int x = 10;
        tang(x);
        IO.println("x sau tang()    = " + x);
    }

    static void tang(int n) {
        n++;
        IO.println("n trong method  = " + n);
    }
}

Chạy mặc định và chạy với -Xmx256m (máy 16 GB RAM nên mặc định là 25% = 4096 MB):

$ java MemoryDemo.java

a == b          = true
a.equals(b)     = true
n trong method  = 11
x sau tang()    = 10

$ java -Xmx256m MemoryDemo.java

a == b          = true
a.equals(b)     = true
n trong method  = 11

  • maxMemory() trả về -Xmx hiệu dụng — 4096 MB mặc định, 256 MB khi chỉnh flag. Đây là cách nhanh nhất để kiểm tra flag có ăn hay không lúc vận hành.
  • a == b là true vì b = a chỉ sao chép reference — cả hai biến trỏ tới một object trên heap.
  • n++ trong method sửa bản sao trên stack frame mới, không ảnh hưởng x. Đúng tinh thần pass-by-value.
Metaspace không nằm trong heap: tăng -Xmx không giúp gì nếu OOM là Metaspace. Từ JDK 8 vùng này thay cho PermGen cũ, nằm trong bộ nhớ native của process, mặc định không giới hạn — nhưng trong container nó vẫn tính vào tổng RAM.

5. Heap & GC cơ bản Hay hỏi phỏng vấn

Bạn không cấp phát/giải phóng bộ nhớ bằng tay: JVM cấp phát object trên heap và Garbage Collector (GC) tự thu hồi object không còn được tham chiếu. Heap theo mô hình generational — chia theo tuổi thọ object:

  • Young generation — gồm Eden và hai Survivor (S0, S1). Object mới sinh ra ở Eden; phần lớn object chết trẻ.
  • Old generation (tenured) — object sống qua nhiều lần dọn young sẽ được "thăng cấp" lên đây.
  • Minor GC dọn young: copy object còn sống từ Eden sang Survivor, thường rất nhanh. Full GC dọn cả old: nặng hơn nhiều.

GC roots — bắt đầu từ đâu để biết object còn sống

GC không "đếm reference" thủ công; nó duyệt đồ thị object bắt đầu từ các GC root. Object nào reachable (đi tới được) từ root thì còn sống. Các root chính:

  • Biến local và tham số đang nằm trong stack frame của các thread đang chạy.
  • static field của class đã nạp — ví dụ một static final List cache.
  • Thread đang sống, đối tượng JNI, classloader đang hoạt động.
Đây là lời giải thích cho "memory leak trong ngôn ngữ có GC": nếu bạn giữ reference tới object trong static collection không bao giờ clear, object đó vẫn reachable từ root — GC không thể thu hồi. Leak trong Java hầu như luôn là "còn tham chiếu", không phải "quên free".

Stop-the-world và G1

Ở một số pha, GC phải dừng toàn bộ thread ứng dụng — gọi là stop-the-world (STW). Minor GC thường chỉ vài ms; Full GC có thể hàng trăm ms tới vài giây, gây spike latency. Từ JDK 9, G1 là GC mặc định (JEP 248, thay cho Parallel GC trước đó): G1 chia heap thành các region nhỏ và ưu tiên dọn region "rác nhiều" trước, cho phép nhắm mục tiêu thời gian pause. Các collector khác vẫn tồn tại cho mục đích riêng: ZGC/Shenandoah cho độ trễ cực thấp (mức nhận biết), Parallel/Serial cho batch nhỏ, ZGC là lựa chọn phổ biến cho service yêu cầu p99 thấp ở JDK 21+.

Đừng tối ưu GC sớm: G1 mặc định đủ tốt cho phần lớn service. Chỉ tuning khi có bằng chứng: log GC cho thấy full GC thường xuyên, pause vượt mục tiêu latency, hoặc heap liên tục gần đầy sau full GC (dấu hiệu leak). Chỉnh flag mù không làm nhanh hơn — thường chỉ che triệu chứng.

6. Lỗi bộ nhớ: StackOverflowError & OutOfMemoryError Hay hỏi phỏng vấn

Cả hai đều là Error (không phải Exception), nhưng nguyên nhân và cách xử lý hoàn toàn khác nhau. Phân biệt đúng là kỹ năng production cơ bản.

StackOverflowError — stack của thread đầy

Mỗi lời gọi method đẩy thêm một frame lên stack. Đệ quy không có base case (hoặc sâu quá giới hạn) làm stack đầy — JVM ném lỗi thay vì treo máy:

public class StackOverflowDemo {
    static int dem = 0;

    static int truoc(int n) {
        dem++;
        return sau(n + 1);
    }

    static int sau(int n) {
        return truoc(n);
    }

    public static void main() {
        IO.println("bat dau");
        truoc(0);
    }
}

Chạy thật — JVM in ra stack trace bắt đầu bằng Exception in thread "main" rồi lặp hai frame mãi (lần chạy này tổng cộng 1026 dòng):

$ java StackOverflowDemo

	at StackOverflowDemo.sau(StackOverflowDemo.java:10)
	at StackOverflowDemo.truoc(StackOverflowDemo.java:6)

  • Top frame cho biết method nào đang chạy lúc stack đầy; các frame lặp lại chỉ ra vòng đệ quy. Ở đây truoc ↔ sau gọi nhau không điểm dừng.
  • Trong production không bắt Error để "chữa cháy" — phải sửa thuật toán (thêm base case, chuyển vòng lặp, giới hạn độ sâu). -Xss tăng stack chỉ làm lỗi chậm tới, không sửa gốc. Xem thêm Methods — mục 7.

OutOfMemoryError: Java heap space — hết chỗ chứa object

Heap đầy vì object vẫn được giữ reference. Ví dụ kinh điển: một collection static tích lũy mãi không xóa (cache không giới hạn, buffer không clear):

import java.util.ArrayList;
import java.util.List;

public class HeapOomDemo {
    static final List<byte[]> CACHE = new ArrayList<>();

    public static void main() {
        try {
            while (true) {
                CACHE.add(new byte[1_000_000]);
            }
        } catch (OutOfMemoryError e) {
            int soMb = CACHE.size();
            CACHE.clear();
            IO.println("class  : " + e.getClass().getName());
            IO.println("message: " + e.getMessage());
            IO.println("giu lai : " + soMb + " MB");
        }
    }
}

Chạy với heap nhỏ -Xmx64m để thấy lỗi nhanh (số MB giữ được thay đổi đôi chút mỗi lần chạy):

$ java -Xmx64m HeapOomDemo
class  : java.lang.OutOfMemoryError
message: Java heap space
giu lai : 62 MB

Dấu hiệu nhận biết: log có OutOfMemoryError: Java heap space, GC chạy liên tục mà heap sau full GC vẫn gần đầy, service chậm dần rồi chết. Cách điều tra: lấy heap dump (mục 9) và tìm ai đang giữ nhiều object nhất — thường là cache, collection, session map (Collections — mục 5).

OutOfMemoryError: Metaspace — hết chỗ chứa metadata class

Metaspace đầy khi chương trình định nghĩa class mới liên tục và không cho class cũ được unload. Ví dụ thực tế: sinh proxy/class động mỗi request, hoặc hot-redeploy trong app server để lại classloader cũ. Demo dưới tạo liên tục dynamic proxy class qua các classloader mới và giữ reference để class không bị thu hồi:

import java.lang.reflect.Proxy;
import java.util.ArrayList;
import java.util.List;

public class MetaspaceOomDemo {
    public interface XuLy {
        void chay();
    }

    public static void main() {
        List<Object> giu = new ArrayList<>();
        long dem = 0;
        OutOfMemoryError loi = null;
        try {
            while (true) {
                ClassLoader parent = MetaspaceOomDemo.class.getClassLoader();
                ClassLoader loader = new ClassLoader(parent) {};
                Object proxy = Proxy.newProxyInstance(
                        loader, new Class<?>[] {XuLy.class}, (p, m, a) -> null);
                giu.add(proxy);
                dem++;
            }
        } catch (OutOfMemoryError e) {
            loi = e;
        }
        giu.clear();
        System.gc();
        IO.println("class  : " + loi.getClass().getName());
        IO.println("message: " + loi.getMessage());
        IO.println("so class: " + dem);
    }
}
$ java -XX:MaxMetaspaceSize=32m MetaspaceOomDemo
class  : java.lang.OutOfMemoryError
message: Metaspace
so class: 5260

Một lần chạy thật giới hạn metaspace 32 MB: sau khoảng 5260 class động thì hết chỗ (số này phụ thuộc máy và phiên bản JDK). Chú ý sau khi giu.clear() và System.gc(), chương trình mới in được message — vì lúc metaspace đầy thì cả việc nội suy chuỗi cũng có thể thất bại nếu chưa giải phóng. Đây là lý do trong code thật, sau khi bắt OutOfMemoryError nên giải phóng reference trước khi log.

Container awareness — chỗ hay chết production

Từ JDK 10+, JVM tự đọc giới hạn bộ nhớ của container (cgroup) thay vì nhìn RAM của host (UseContainerSupport mặc định bật). Nếu container limit 1 GB thì heap mặc định khoảng 25% × 1 GB = 256 MB, chứ không phải 25% × RAM của server vật lý. Tuy nhiên heap không phải toàn bộ bộ nhớ process: metaspace, stack các thread, code cache, direct buffer, thư viện native đều nằm ngoài -Xmx. Vì vậy đặt -Xmx bằng đúng container limit gần như chắc chắn bị kernel kill, chứ chưa kịp thấy OutOfMemoryError.

-XX:MaxRAMPercentage=75.0 (an toàn hơn hardcode -Xmx khi chạy đa môi trường)
Không tune mù: đừng copy các bộ flag dài trên mạng vào service của bạn. Thứ tự đúng: (1) quan sát — GC log, p99 latency, RSS; (2) tìm nguyên nhân — leak hay chỉ thiếu heap; (3) thay đổi một thứ, đo lại. JVM mặc định của JDK 25 đã rất tốt cho đa số workload.

8. Đọc stack trace như thế nào Production

Stack trace là "ảnh chụp" các lời gọi method tại thời điểm lỗi. Đọc đúng giúp bạn nhảy tới dòng gây lỗi trong vài giây. Cấu trúc một trace chưa bắt lỗi:

import java.util.List;

    static int tinhTong(List<Integer> tien) {
        int tong = 0;
        for (int x : tien) {
            tong += x;
        }
        return tong;
    }

    static void inTong() {
        IO.println(tinhTong(null));
    }

    public static void main() {
        inTong();
    }
}

Đọc từng phần:

  • Dòng đầu — loại lỗi + message. Ở đây NullPointerException với message "helpful NPE" của JDK hiện đại: nói luôn biến nào null (parameter1) và method nào bị gọi trên nó (List.iterator()).
  • Frame đầu tiên — at StackTraceDemo.tinhTong(StackTraceDemo.java:6) chỉ đúng dòng 6 (vòng lặp for) ném lỗi. Đây là nơi bắt đầu điều tra.
  • Các frame tiếp theo — chuỗi lời gọi dẫn tới đó: main (dòng 17) gọi inTong (dòng 13) gọi tinhTong. Đọc từ dưới lên là đường đi của chương trình; frame của code thư viện (bắt đầu java.base/..., jdk...) thường bỏ qua cho tới frame đầu tiên thuộc code của bạn.

Đây là cặp khái niệm dễ gây chết service nhất khi lên container/Kubernetes:

Quy tắc an toàn: để heap chiếm khoảng 60–75% limit, chừa phần còn lại cho metaspace, stack, code cache và native. Nếu thấy app bị kill mà log trống trơn, nghĩ ngay tới OOMKilled — đừng chỉ nhìn OutOfMemoryError.

GC pause ảnh hưởng latency thế nào

Mỗi lần GC stop-the-world, mọi request đang xử lý đều đứng im. Minor GC vài ms hầu như không ai thấy; Full GC vài trăm ms tạo spike p99 rõ rệt — đúng lúc traffic cao lại càng tệ. Vì vậy ở production nên bật log GC với rotation, để khi có sự cố latency còn dữ liệu phân tích:

java '-Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=10M' TenFile.java

Log này overhead thấp, ghi ra file xoay vòng 5 file × 10 MB. Khi cần đào sâu, Java Flight Recorder (jcmd <pid> JFR.start) ghi lại sự kiện GC, allocation, thread — mức nhận biết ở giai đoạn này.

Checklist khi service có sự cố bộ nhớ

  1. Xác định ai giết: exit code 137 + không có log OOM → nghi OOMKilled (mục này); có log OOM → đọc message (mục 6).
  2. Đọc stack trace và GC log; xác định vùng đầy (heap hay metaspace).
  3. Lấy heap dump nếu kịp (đã bật flag từ trước thì luôn kịp).
  4. Phân tích bằng MAT/VisualVM: object nào chiếm nhiều nhất, ai giữ reference (thường là static collection).
  5. Tạm thời: tăng limit/hạ Xmx hợp lý để hồi phục; dài hạn: sửa leak hoặc giới hạn cache.
  6. Thêm giám sát: RSS, heap sau full GC, tần suất full GC, p99 latency.

12. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. JVM, JRE và JDK khác nhau thế nào?
JVM là máy ảo thực thi bytecode (interpreter + JIT + GC + classloader). JRE = JVM + thư viện chuẩn, đủ để chạy app. JDK = JRE + công cụ phát triển (javac, javap, jcmd...). Từ JDK 9 không còn bản JRE phát hành riêng; muốn runtime gọn thì dùng jlink.
Câu 2. Bytecode là gì? Vì sao Java độc lập nền tảng?
Bytecode là tập lệnh trung gian trong file .class, không gắn với CPU cụ thể (khác mã máy). javac dịch source thành bytecode; mỗi nền tảng có bản JVM riêng đọc cùng bytecode đó — nên "write once, run anywhere". Xem thật bằng javap -c.
Câu 3. JVM thông dịch hay biên dịch?
Cả hai. HotSpot bắt đầu bằng interpreter (khởi động nhanh), đồng thời theo dõi method "nóng"; method chạy nhiều được JIT biên dịch thành mã máy tối ưu (C1/C2), có thể deoptimize nếu giả định sai. Nhờ vậy vừa khởi động nhanh vừa đạt hiệu năng cao về sau.
Câu 4. Kể 3 classloader chính và mỗi loại nạp gì?
Bootstrap (native, nạp lõi java.base như String; getClassLoader() trả null), Platform (các module JDK khác như java.sql), và Application/System (classpath: code của bạn + thư viện). Chúng tạo thành cây cha-con App → Platform → Bootstrap.
Câu 5. Delegation model của classloader là gì? Vì sao cần?
Khi nạp class, loader hỏi loader cha trước, chỉ tự nạp khi cha thất bại (parent-first). Mục đích: đảm bảo class lõi như java.lang.String luôn do bootstrap nạp — không thể bị "tráo" bởi class của ứng dụng, và tránh nạp trùng class trong cùng hệ thống. App server đôi khi cố tình đảo ngược để cô lập thư viện giữa các webapp.
Câu 6. Load và initialize class khác nhau thế nào? Static block chạy khi nào?
Load là đọc và định nghĩa class trong bộ nhớ; initialize (chạy <clinit> + static block) xảy ra ở lần dùng chủ động đầu tiên: tạo instance, gọi static method, ghi/đọc static field không phải hằng, hoặc reflection có yêu cầu init. Class literal (X.class) và hằng số compile-time static final (đã inline) không kích hoạt init — JLS §12.4.1.
Câu 7. Classpath là gì? Vì sao thứ tự quan trọng?
Là danh sách thư mục/JAR để Application classloader tìm class (qua -cp hoặc biến CLASSPATH). Khi nhiều nguồn có cùng tên class, nguồn xuất hiện trước thắng — nguyên nhân kinh điển của NoSuchMethodError khi có hai phiên bản thư viện trên classpath.
Câu 8. Stack và heap khác nhau thế nào?
Stack: mỗi thread một cái, chứa frame với biến local primitive và reference; tự giải phóng khi method return; đầy → StackOverflowError; điều chỉnh bằng -Xss. Heap: dùng chung mọi thread, chứa object/mảng; GC quản lý; đầy → OutOfMemoryError: Java heap space; điều chỉnh bằng -Xms/-Xmx. Object luôn nằm trên heap, biến giữ object chỉ là reference trên stack.
Câu 9. Metaspace là gì? Khác gì heap?
Metaspace chứa metadata class (tên class, method, bytecode, constant pool), thay PermGen từ JDK 8, nằm trong bộ nhớ native chứ không phải heap Java. Vì vậy tăng -Xmx không giúp lỗi OutOfMemoryError: Metaspace. Mặc định không giới hạn; production nên đặt -XX:MaxMetaspaceSize để phát hiện classloader leak sớm.

Nâng cao (Junior+)

Câu 10. GC roots gồm những gì?
Các điểm bắt đầu để GC duyệt đồ thị object: biến local/tham số trong stack frame của thread đang chạy, static field của class đã nạp, thread đang sống, tham chiếu JNI/native, và classloader đang hoạt động. Object reachable từ root là còn sống; ngược lại mới bị thu hồi.
Câu 11. Minor GC và Full GC khác nhau thế nào? Young/Old generation là gì?
Heap chia young (Eden + 2 Survivor) và old. Object mới ở Eden; minor GC dọn young, object sống sót được copy qua Survivor rồi thăng cấp lên old sau vài lần. Full GC dọn cả old (và thường cả young) — nặng hơn hẳn, pause dài. Nếu sau Full GC heap vẫn gần đầy, nhiều khả năng có object bị giữ (leak).
Câu 12. Stop-the-world là gì? G1 mặc định từ khi nào?
STW là pha GC dừng toàn bộ thread ứng dụng để dọn an toàn — dài thì request bị treo. Từ JDK 9 (JEP 248), G1 là GC mặc định: chia heap thành region, ưu tiên vùng nhiều rác, hướng tới mục tiêu pause. Các collector khác: ZGC/Shenandoah cho độ trễ rất thấp, Parallel/Serial cho workload nhỏ hoặc batch.
Câu 13. StackOverflowError và OutOfMemoryError khác nhau ra sao?
StackOverflowError: stack của một thread đầy, thường do đệ quy vô hạn/quá sâu; message null; chỉ thread đó chết. OutOfMemoryError: một vùng nhớ dùng chung hết chỗ; message cho biết vùng (Java heap space, Metaspace...); ảnh hưởng cả ứng dụng. Cả hai là Error — sửa nguyên nhân, không bắt để chạy tiếp.
Câu 14. -Xms và -Xmx là gì? Nên đặt thế nào?
-Xms là heap ban đầu, -Xmx là heap tối đa. Mặc định JVM tính theo 25% RAM (MaxRAMPercentage) và tự resize; production thường đặt -Xmx rõ ràng (hoặc MaxRAMPercentage) để tránh bất ngờ, và phải để headroom cho metaspace/stack/native. Đặt -Xms = -Xmx giúp tránh chi phí resize nhưng không bắt buộc.
Câu 15. Vì sao -Xmx phải nhỏ hơn container limit? OOMKilled là gì?
Vì process còn dùng bộ nhớ ngoài heap: metaspace, stack các thread, code cache, direct buffer, thư viện native. Nếu tổng RSS vượt limit cgroup, kernel giết process — container exit code 137, gọi là OOMKilled, và log ứng dụng thường không có dòng OutOfMemoryError nào. Vì vậy để heap ~60–75% limit hoặc dùng -XX:MaxRAMPercentage phù hợp.
Câu 16. Đọc stack trace: cần nhìn những gì?
Dòng đầu (loại exception + message), frame đầu tiên (nơi lỗi phát sinh, có tên file + dòng), và khối Caused by cuối cùng (nguyên nhân gốc). Các frame java.base/... là thư viện — tìm frame đầu tiên thuộc code của bạn. ... N more chỉ là viết gọn, không phải lỗi.
Câu 17. Khi nào dùng jstack, khi nào dùng jcmd?
jstack để lấy thread dump khi app treo, nghi deadlock hoặc CPU cao — xem thread nào đang chạy/chờ gì. jcmd là dao đa năng: xem flags (VM.flags), heap (GC.heap_info, GC.heap_dump), thread (Thread.print), JFR. Thực tế chỉ cần jcmd là làm được phần lớn việc của bộ tool cũ.

Production

Câu 18. System.gc() có ép GC chạy ngay không? Có nên gọi?
Không đảm bảo — chỉ là gợi ý, JVM có thể bỏ qua (nhất là khi bật -XX:+DisableExplicitGC). Nếu chạy, nó thường kích hoạt Full GC gây pause lớn. Không gọi trong code production; chỉ dùng trong demo/đo đạc có kiểm soát.
Câu 19. Vì sao static collection gây memory leak dù Java có GC?
Vì static field là GC root: mọi object được collection đó tham chiếu vẫn reachable mãi, GC không thu hồi được. Cache/session map/list "tạm" không giới hạn size sẽ phình heap tới OutOfMemoryError: Java heap space. Cách tránh: giới hạn size/TTL, dùng cache có eviction, hoặc WeakHashMap khi phù hợp.
Câu 20. Heap dump là gì? Lấy thế nào và đọc bằng gì?
Là file ảnh chụp toàn bộ object trên heap (định dạng .hprof). Lấy bằng -XX:+HeapDumpOnOutOfMemoryError (tự động lúc OOM) hoặc jcmd <pid> GC.heap_dump <path> lúc đang chạy. Phân tích bằng Eclipse MAT hoặc VisualVM để tìm loại object chiếm nhiều nhất và chuỗi reference đang giữ chúng. Lưu ý file lớn và chứa dữ liệu nhạy cảm.
Câu 21. Vì sao không nên tối ưu GC/flags sớm?
Vì default của JDK hiện đại (G1, ergonomics theo RAM) đã tốt cho phần lớn service; tuning mù dựa trên cảm giác có thể làm chậm, tăng pause hoặc che leak. Quy trình đúng: đo (GC log, latency, RSS) → xác định nguyên nhân (thiếu heap hay leak) → sửa một thứ → đo lại. Tối ưu chỉ khi có số liệu chứng minh.
Câu 22. Từ Node.js nhìn sang: V8 và JVM khác nhau ở điểm nào quan trọng nhất?
V8 chạy JS trên event loop một thread (thêm worker pool cho I/O), còn JVM là nền tảng đa luồng thật — nhiều thread chia sẻ heap nên phải học race condition. Về bộ nhớ, cả hai đều có giới hạn heap riêng và GC phân thế hệ: V8 chỉnh bằng --max-old-space-size, JVM chỉnh bằng -Xmx (mặc định 25% RAM). Debug bộ nhớ cũng tương tự: bên Node là heap snapshot, bên JVM là heap dump.
