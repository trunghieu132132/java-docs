2. 5 ngữ cảnh chuyển kiểu của JLS

Chuyện "khi nào Java tự chuyển kiểu" không phải ngẫu nhiên — JLS (Java Language Specification, chương 5) định nghĩa 5 ngữ cảnh, mỗi ngữ cảnh cho phép một bộ chuyển đổi khác nhau. Hiểu 5 ngữ cảnh này là hiểu toàn bộ phần còn lại:

Góc Node.js: JS không có kiểu tĩnh — mọi số thường đều là number (double 64-bit), chỉ có thêm BigInt khi cần, và == tự ép kiểu. Java tách int/long/float/double và kiểm tra kiểu chặt chẽ: chuyển an toàn (widening, unboxing) thì tự động, còn lại phải ép tường minh hoặc bị compiler từ chối.

Vì sao cần biết? Cùng một phép chuyển kiểu có thể hợp lệ ở ngữ cảnh này nhưng bị từ chối ở ngữ cảnh khác. Ví dụ int → byte tự động trong b += 1 (compound assignment) nhưng phải ép tường minh trong b = b + 1.

3. Widening — "an toàn" nhưng không tuyệt đối

Widening primitive conversion là chuyển từ kiểu nhỏ sang kiểu lớn hơn theo chuỗi:

byte → short → int → long → float → double
                  ↑
                char → int

Chuyển ngầm (không cần ép) và nhìn chung an toàn với số nguyên. Nhưng có hai trường hợp mất chữ số vì float chỉ giữ 24 bit phần định trị, double giữ 53 bit:

public class WideningDemo {
    public static void main() {
        char c = 'A';
        int ci = c;                  // char -> int
        IO.println("char 'A' -> int          : " + ci);  // 65

        int i = 16_777_217;          // 2^24 + 1
        float f = i;                 // int -> float: mat chu so!
        IO.println("int 16_777_217 -> float  : " + f);   // 1.6777216E7

        long big = 9_007_199_254_740_993L;  // 2^53 + 1
        double d = big;              // long -> double: mat chu so!
        IO.println("long ...993 -> double     : " + d);   // 9.007199254740992E15
    }
}
Bẫy phỏng vấn: widening không đồng nghĩa "không mất gì". float biểu diễn chính xác đến 2^24, double đến 2^53. ID long lớn đi qua double (ví dụ serialize qua JSON không cẩn thận) có thể hụt 1 đơn vị — đây là lý do thật khiến hệ thống production lệch ID.

4. Narrowing — ép tường minh và mất dữ liệu

Narrowing (lớn → nhỏ) bắt buộc ép tường minh (type) vì có thể mất dữ liệu. Java từ chối ngầm chuyển:

int x = 3.9;
        ^
error: incompatible types: possible lossy conversion from double to int

float g = 1.5;
          ^
error: incompatible types: possible lossy conversion from double to float

Khi đã ép, Java cắt theo luật xác định trước — không ném lỗi:

IO.println("(byte) 130       : " + (byte) 130);       // -126
IO.println("(int) 3.99       : " + (int) 3.99);       // 3    - cat ve 0
IO.println("(int) -3.99      : " + (int) -3.99);      // -3   - cat ve 0, khong lam tron
IO.println("(char) 65        : " + (char) 65);        // A
IO.println("(int) Double.NaN : " + (int) Double.NaN); // 0
IO.println("(int) 1e20       : " + (int) 1e20);       // 2147483647
IO.println("(long) 1e20      : " + (long) 1e20);      // 9223372036854775807
  • (byte) 130 = -126: 130 vượt 127 nên quay vòng theo bù hai.
  • Ép double → int cắt phần thập phân, không làm tròn: 3.99 thành 3.
  • NaN → 0; số quá lớn bị kẹp về MAX_VALUE (khác wraparound của số nguyên).

Ngoại lệ đáng nhớ: hằng số (constant) trong khoảng đích được phép ngầm chuyển, nên đoạn sau compile bình thường:

final int y = 3;
byte z = y;        // hang so vua khoang -> duoc
char ch = 65;      // hang so vua khoang char -> duoc
IO.println(z + " " + ch);   // 3 A

Nhưng byte b = 200; hay char ch = -1; vẫn bị từ chối:

byte b = 200;
         ^
error: incompatible types: possible lossy conversion from int to byte

char ch = -1;
          ^
error: incompatible types: possible lossy conversion from int to char

5. Numeric promotion — vì sao byte + byte ra int

Trước khi tính toán, Java "nâng" toán hạng theo luật numeric promotion:

  • Unary promotion: byte, short, char được nâng lên int trước khi tính (kể cả -b, b++).
  • Binary promotion: nếu một toán hạng là double → cả hai thành double; nếu là float → cả hai thành float; nếu là long → cả hai thành long; còn lại → cả hai thành int.
byte b1 = 1, b2 = 2;
IO.println("byte + byte     : " + (b1 + b2));      // 3    - nhung kieu la int
IO.println("char + int      : " + ('a' + 1));       // 98
IO.println("'a' + 'b'       : " + ('a' + 'b'));     // 195
IO.println("long + float    : " + (1L + 1.5f));     // 2.5

Hệ quả thực tế: byte b = b1 + b2; không compile vì vế phải là int — dù giá trị nhỏ. Phải viết byte b = (byte) (b1 + b2);.

6. Compound assignment và ++/--

+=, -=, *=... chứa sẵn một phép ép kiểu ngầm về kiểu của biến bên trái. Đây là lý do b += 5 chạy được còn b = b + 5 thì không:

byte b3 = 10;
b3 += 5;                       // tuong duong b3 = (byte) (b3 + 5)
IO.println("byte += 5       : " + b3);   // 15

int i2 = 5;
i2 += 3.9;                     // tuong duong i2 = (int) (i2 + 3.9)
IO.println("int += 3.9      : " + i2);   // 8  - 5 + 3.9 = 8.9 -> cat thanh 8

long l2 = 1;
l2 += 1.0;                     // long += double -> ngam ep ve long
IO.println("long += 1.0     : " + l2);   // 2
Bẫy production: i2 += 3.9 không báo lỗi, không cảnh báo — chỉ âm thầm cắt phần thập phân. Với tiền bạc, luôn dùng BigDecimal (xem Biến trong Java — mục 13) thay vì tin vào compound assignment.

++ và -- trên byte/short/char

b++ với byte b hợp lệ vì phép tăng chứa sẵn ép kiểu ngầm — khác với b = b + 1:

byte b = 10;
b++;                       // ok - khac b = b + 1
IO.println("b++            : " + b);   // 11

Dòng b = b + 1; không qua được compiler:

b = b + 1;
      ^
error: incompatible types: possible lossy conversion from int to byte

7. Ternary, nối chuỗi và các ngữ cảnh ngầm

Ternary promotion

Hai nhánh của toán tử ?: được đưa về cùng một kiểu trước khi trả kết quả:

boolean flag = true;
IO.println(flag ? 1 : 2.0);    // 1.0  - int duoc nang thanh double
long mixed = flag ? 1 : 2L;    // int duoc nang thanh long
IO.println("ternary int/long   : " + mixed);   // 1

Bẫy unboxing trong ternary

Đây là bẫy phỏng vấn rất hay gặp: nếu một nhánh là primitive, nhánh còn lại là wrapper, kiểu của cả biểu thức là primitive — nên nhánh nào được chọn sẽ bị unbox. Wrapper null chỉ nổ khi chính nhánh đó được chọn:

Integer boxed = null;

boolean flag = true;
try {
    int x = flag ? boxed : 0;   // nhanh boxed duoc chon -> unbox null -> NPE
} catch (NullPointerException e) {
    IO.println("flag=true  : NullPointerException");
}

boolean flag2 = false;
int y = flag2 ? boxed : 0;      // nhanh 0 duoc chon -> khong dung toi boxed
IO.println("flag=false : " + y);  // 0

// Nhanh wrapper co the duoc chon: kiem tra null truoc
int safe = flag ? (boxed == null ? 0 : boxed) : 0;
IO.println("ternary an toan : " + safe);   // 0

Còn nếu cả hai nhánh đều là wrapper thì Java không unbox — kết quả có thể là null mà không ném gì:

Integer a = null;
Integer b = 1;
Integer c = true ? a : b;
IO.println("ca hai wrapper : " + c);   // null

String concatenation

Toán tử + xử lý trái sang phải; khi gặp String, mọi thứ sau đó được chuyển thành chuỗi:

IO.println(1 + 2 + "x");    // 3x   - cong so truoc
IO.println("x" + 1 + 2);    // x12  - noi chuoi truoc
IO.println('A' + "1");      // A1

8. Chuyển đổi boxing/unboxing

Boxing/unboxing có luật riêng, không đối xứng:

long b = Integer.valueOf(5);     // OK: unbox Integer -> int, roi widening int -> long
double d = Integer.valueOf(5);   // OK: unbox + widening
IO.println("long tu Integer : " + b);   // 5
IO.println("double tu Integer: " + d);  // 5.0

Long e = (long) Integer.valueOf(1);   // OK: unbox -> int -> long roi boxing Long
IO.println("Long tu (long)  : " + e);   // 1

Nhưng không có chuyện widening rồi boxing tự động trong assignment. Đây là câu hỏi phỏng vấn kinh điển:

Long a = 10;
         ^
error: incompatible types: int cannot be converted to Long

Double c = 1;
           ^
error: incompatible types: int cannot be converted to Double

Vì sao? 10 là int literal; muốn thành Long phải qua hai bước (int → long → Long) mà assignment context không cho phép chuỗi đó. Cách viết đúng: Long a = 10L;.

Tương tự, wrapper không tự chuyển sang wrapper khác dù primitive tương ứng widening:

Integer i = 10;
Long f = i;
         ^
error: incompatible types: Integer cannot be converted to Long
Các ví dụ cache wrapper (127 == 127 vs 128 == 128) và NPE unbox đã có ở Biến trong Java — mục 12; ở đây chỉ bàn luật chuyển đổi.

9. Method invocation conversion và overload

Khi chọn method overload, Java xét theo 3 phase theo thứ tự, phase trước thắng phase sau:

  1. Không boxing/unboxing, không varargs — chỉ widening.
  2. Cho phép boxing/unboxing.
  3. Cho phép varargs.
static void pick(int x)     { IO.println("pick(int)     -> " + x); }
static void pick(long x)    { IO.println("pick(long)    -> " + x); }
static void pick(Integer x) { IO.println("pick(Integer) -> " + x); }
static void pick(Object x)  { IO.println("pick(Object)  -> " + x); }

static void onlyLong(long x)    { IO.println("onlyLong(long)    -> " + x); }
static void onlyLong(Integer x) { IO.println("onlyLong(Integer) -> " + x); }

public static void main() {
    byte b = 1;
    pick(b);                    // pick(int)      - widening thang int
    pick(1);                    // pick(int)
    pick(1L);                   // pick(long)
    pick(Integer.valueOf(1));   // pick(Integer)
    pick("text");               // pick(Object)

    onlyLong(1);                // onlyLong(long) - phase 1 (widening) thang phase 2 (boxing)
    onlyLong(Integer.valueOf(1)); // onlyLong(Integer)
    pick(null);                 // pick(Integer)  - Integer cu the hon Object
}
Hệ quả production: API nhận long mà bạn truyền int thì không sao; nhưng nếu class có cả method(long) lẫn method(Integer), giá trị int sẽ đi vào bản long. Hai bản này mà xử lý khác nhau (ví dụ Integer chấp nhận null) là nguồn bug rất khó thấy.

10. Ép kiểu reference và ClassCastException

Với object, upcast (lên cha) luôn ngầm được, downcast (xuống con) phải ép tường minh — compiler chỉ tin bạn, còn JVM kiểm tra lúc chạy:

Object o = "abc";
String s = (String) o;                    // downcast hop le
IO.println("downcast ok   : " + s);       // abc

Object num = Integer.valueOf(5);
try {
    String s2 = (String) num;             // sai kieu thuc te
} catch (ClassCastException e) {
    IO.println("CCE message   : " + e.getMessage());
}

Object o2 = 5;                            // boxing thanh Integer
IO.println("instanceof    : " + (o2 instanceof Integer));   // true

Number n = 5;                             // upcast ngam
IO.println("upcast double : " + n.doubleValue());          // 5.0

Message thật của JVM (JDK 25):

class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')

Trước khi downcast, luôn kiểm tra bằng instanceof (hoặc pattern matching instanceof, Java 16+). Nội dung này được đào sâu ở 2.4 Polymorphism.

12. BigInteger — khi long không đủ

long tràn là quay vòng âm thầm (xem Biến trong Java — mục 9). Khi cần số nguyên lớn hơn 64-bit chính xác tuyệt đối (mã giao dịch, hash, tính toán khoa học), dùng BigInteger:

long maxL = Long.MAX_VALUE;
IO.println("long max     : " + maxL);                     // 9223372036854775807
IO.println("long max + 1 : " + (maxL + 1));                // -9223372036854775808

BigInteger big = BigInteger.valueOf(maxL).add(BigInteger.ONE);
IO.println("BigInteger   : " + big);                     // 9223372036854775808

BigInteger n = new BigInteger("123456789012345678901234567890");
IO.println("multiply 2   : " + n.multiply(new BigInteger("2")));
// 246913578024691357802469135780
IO.println("2^100        : " + BigInteger.TWO.pow(100));
// 1267650600228229401496703205376

13. Production patterns

13.1 Parse cấu hình an toàn — không để app chết vì env sai

static int pageSize(String raw, int fallback) {
    if (raw == null || raw.isBlank()) {
        return fallback;
    }
    try {
        return Integer.parseInt(raw.trim());
    } catch (NumberFormatException e) {
        return fallback;
    }
}

IO.println("pageSize(null, 20) : " + pageSize(null, 20));   // 20
IO.println("pageSize(\" 50 \")   : " + pageSize(" 50 ", 20)); // 50
IO.println("pageSize(\"abc\")    : " + pageSize("abc", 20));  // 20

Dữ liệu từ input người dùng thì ngược lại: không fallback âm thầm, phải báo lỗi rõ ràng (IllegalArgumentException với message cụ thể) để API trả về 400 thay vì chạy sai.

13.2 ID và timestamp: long, và cẩn thận khi qua JavaScript

long id = Long.parseLong("9007199254740993");   // 2^53 + 1
IO.println("long id > 2^53     : " + id);        // 9007199254740993

JavaScript chỉ giữ chính xác số nguyên đến 2^53, nên ID long gửi dạng number trong JSON sẽ bị làm tròn ở client (2^53 + 1 → 9007199254740992). Production thường serialize ID thành string trong JSON — nhớ khi viết DTO ở giai đoạn 5 (Jackson, mục 5.2 của lộ trình).

13.3 Validate trước khi cast

long id = Long.parseLong("123");
if (id <= 0) {
    throw new IllegalArgumentException("orderId phai > 0: " + id);
}

15. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. JLS định nghĩa mấy ngữ cảnh chuyển kiểu? Kể tên.
5 ngữ cảnh: assignment, method invocation, casting, numeric promotion, string concatenation. Mỗi ngữ cảnh cho phép bộ chuyển đổi khác nhau — cùng phép chuyển có thể hợp lệ ở ngữ cảnh này nhưng bị từ chối ở ngữ cảnh khác.
Câu 2. Widening conversion có luôn an toàn không?
Không. Với số nguyên nhìn chung an toàn, nhưng int → float và long → double có thể mất chữ số vì float chỉ giữ 24 bit định trị, double giữ 53 bit. Ví dụ (float) 16_777_217 ra 1.6777216E7.
Câu 3. Vì sao byte b = 100; hợp lệ nhưng byte b = 200; thì không?
100 là hằng số nằm trong khoảng của byte (-128..127) nên được ngầm narrowing; 200 vượt khoảng nên bị từ chối với lỗi "possible lossy conversion". Cùng luật đó cho phép final int y = 3; byte z = y;.
Câu 4. Vì sao byte + byte lại ra int?
Numeric promotion: byte, short, char được nâng lên int trước khi tính toán (unary promotion), nên kết quả là int. Muốn gán lại vào byte phải ép: (byte) (b1 + b2).
Câu 5. b += 1 khác b = b + 1 thế nào khi b là byte?
b += 1 tương đương b = (byte) (b + 1) — có ép kiểu ngầm nên compile được. b = b + 1 thất bại vì b + 1 là int.
Câu 6. (int) 3.99 và (int) -3.99 cho gì?
3 và -3. Narrowing từ số thực cắt phần thập phân (làm tròn về 0), không làm tròn số học. Muốn làm tròn dùng Math.round().
Câu 7. (byte) 130 bằng bao nhiêu? Giải thích.
-126. 130 vượt 127 nên quay vòng theo bù hai: 130 - 256 = -126. Ép kiểu số nguyên không ném lỗi tràn, chỉ giữ 8 bit thấp nhất.
Câu 8. true ? 1 : 2.0 có kiểu gì?
double — int được nâng lên double trước. Kết quả in ra 1.0 chứ không phải 1.
Câu 9. 1 + 2 + "x" và "x" + 1 + 2 khác nhau thế nào?
Toán tử + chạy trái sang phải. 1 + 2 + "x" = "3x" (cộng số trước); "x" + 1 + 2 = "x12" (nối chuỗi trước, sau đó mọi thứ thành chuỗi).

Nâng cao (Junior+)

Câu 10. Khi nào flag ? boxed : 0 ném NPE, khi nào không?
Biểu thức có một nhánh primitive (0) nên kiểu kết quả là primitive, và chỉ nhánh được chọn mới bị unbox. Với flag == true và boxed == null: NPE. Với flag == false: trả về 0, không đụng tới boxed nên không lỗi. Nếu cả hai nhánh đều là wrapper thì không có unbox — kết quả có thể là null.
Câu 11. Vì sao Long a = 10; không compile, nhưng long b = Integer.valueOf(5); compile?
Assignment context không cho phép "widening rồi boxing" (int → long → Long). Chiều ngược lại thì được: unboxing trước rồi widening (Integer → int → long) là chuỗi hợp lệ. Nếu cần Long từ literal int, viết Long a = 10L;.
Câu 12. Overload resolution xét theo thứ tự nào? Cho ví dụ.
3 phase: (1) chỉ widening/không boxing, (2) cho phép boxing/unboxing, (3) cho phép varargs. Ví dụ có onlyLong(long) và onlyLong(Integer), gọi onlyLong(1) sẽ chọn bản long vì phase 1 thắng phase 2.
Câu 13. (int) Double.NaN và (int) 1e20 cho gì?
NaN → 0; 1e20 → Integer.MAX_VALUE (2147483647). Luật JLS: NaN thành 0, giá trị quá lớn kẹp về MAX, quá nhỏ kẹp về MIN — khác wraparound của ép kiểu số nguyên.
Câu 14. parseInt và valueOf khác nhau thế nào?
Integer.parseInt trả int primitive; Integer.valueOf trả Integer và dùng cache -128..127 nên cùng giá trị nhỏ sẽ trả cùng object. Cả hai đều ném NumberFormatException khi chuỗi sai định dạng hoặc vượt khoảng.
Câu 15. Integer.parseInt(null) ném gì?
NumberFormatException với message "Cannot parse null string" — không phải NullPointerException. Đây là bẫy khi code parse dữ liệu chưa kiểm tra null.
Câu 16. Khi nào cần BigInteger? Nó khác BigDecimal ở đâu?
Khi số nguyên cần vượt 64-bit hoặc phải chính xác tuyệt đối (hash, mã hóa, toán lớn). BigInteger là số nguyên chính xác; BigDecimal là số thập phân với scale — dùng cho tiền tệ. Cả hai đều bất biến, mọi phép tính trả object mới.
Câu 17. Vì sao ID kiểu long nên gửi dạng string trong JSON?
JavaScript chỉ biểu diễn chính xác số nguyên đến 2^53. ID long lớn hơn (snowflake ID, ID từ DB lớn dần) sẽ bị làm tròn khi client parse JSON number. Serialize thành string tránh mất mát — thường cấu hình ở tầng Jackson/Jackson 3.

Câu hỏi khó

Câu 18. Vì sao float f = 16_777_217; lại mất 1 đơn vị?
16_777_217 = 2^24 + 1. float có 24 bit phần định trị nên chỉ biểu diễn chính xác số nguyên đến 2^24; vượt ngưỡng sẽ làm tròn về bội số gần nhất. Kết quả in ra 1.6777216E7.
Câu 19. Kể 3 trường hợp hàng ngày mà Java chuyển kiểu ngầm mà không cần ép.
(1) widening khi gán (int i = 'a'); (2) boxing/unboxing (Integer x = 5; int y = x;); (3) numeric promotion khi tính (byte + int → int). Ngoài ra còn nối chuỗi và hằng số vừa khoảng.
Câu 20. Trong method invocation, khi nào int được truyền vào tham số Integer mà không cần boxing tường minh?
Luôn được — đó là boxing conversion tự động (assignment context và invocation context đều cho phép). Nhưng nếu overload có cả long lẫn Integer, bản long sẽ được chọn vì widening thuộc phase 1, boxing thuộc phase 2.

17. Cheat sheet & checklist

Cheat sheet

Việc cần làmCách viết
Widening (tự động)byte → short → int → long → float → double; char → int
NarrowingÉp tường minh: (byte) 130, (int) 3.99
Constant narrowingfinal int y = 3; byte z = y; (hằng số vừa khoảng)
Promotion khi tínhbyte/short/char → int; có long → long; có float → float; có double → double
Compound assignmentb += 1 = b = (byte)(b + 1); b = b + 1 lỗi
Ép số thực sang intCắt phần thập phân; NaN → 0; quá lớn → MAX/MIN
Boxing an toànLong a = 10L; · long b = Integer.valueOf(5); (unbox + widen OK)
OverloadWidening (phase 1) thắng boxing (phase 2), thắng varargs (phase 3)
TernaryHai nhánh về cùng kiểu; coi chừng unbox null
Parse chuỗiInteger.parseInt (int) · Integer.valueOf (Integer, có cache) · bọc try/catch NFE
Số cực lớnBigInteger cho số nguyên; BigDecimal cho tiền
JSON + longSerialize ID thành string (JS chỉ chính xác đến 2^53)

Checklist tự đánh giá trước phỏng vấn

  • Kể được 5 ngữ cảnh chuyển kiểu và ví dụ mỗi loại.
  • Giải thích được vì sao int → float có thể mất chữ số.
  • Giải thích (byte) 130 = -126 và luật kẹp của NaN/quá lớn.
  • Phân biệt b += 1 với b = b + 1.
  • Chỉ ra bẫy unboxing trong ternary bằng ví dụ tự viết.
  • Giải thích vì sao Long a = 10; lỗi còn long b = Integer.valueOf(5); chạy được.
  • Nêu thứ tự 3 phase của overload resolution và cho ví dụ.
  • Viết hàm parse cấu hình có fallback và hàm parse input ném lỗi rõ ràng.
  • Biết khi nào cần BigInteger thay long.
  • Biết vì sao ID long phải gửi dạng string trong JSON.
