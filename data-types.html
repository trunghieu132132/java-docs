2. 5 ngữ cảnh chuyển kiểu của JLS

Chuyện "khi nào Java tự chuyển kiểu" không phải ngẫu nhiên — JLS (Java Language Specification, chương 5) định nghĩa 5 ngữ cảnh, mỗi ngữ cảnh cho phép một bộ chuyển đổi khác nhau. Hiểu 5 ngữ cảnh này là hiểu toàn bộ phần còn lại:

Góc Node.js: JS không có kiểu tĩnh — mọi số thường đều là number (double 64-bit), chỉ có thêm BigInt khi cần, và == tự ép kiểu. Java tách int/long/float/double và kiểm tra kiểu chặt chẽ: chuyển an toàn (widening, unboxing) thì tự động, còn lại phải ép tường minh hoặc bị compiler từ chối.

3. Widening — "an toàn" nhưng không tuyệt đối Hay hỏi phỏng vấn

Widening primitive conversion (JLS 5.1.2) là chuyển từ kiểu nhỏ sang kiểu lớn hơn không cần ép tường minh. Chuỗi quen thuộc là byte → short → int → long → float → double, còn char nhập cuộc tại int. Nhìn chung an toàn — nhưng "nhìn chung" là từ khoá quan trọng: int → float và long → double vẫn có thể mất chữ số, âm thầm, không cảnh báo.

3.1 Sơ đồ widening primitive

Java có 19 phép widening primitive, tất cả nằm gọn trong bảng sau — không nhảy cóc, không rẽ nhánh ngoài bảng:

TừCó thể widening tới

  • boolean không có bất kỳ chuyển đổi số nào: không widening, không narrowing, không cast sang số. Đây là kiểu primitive duy nhất tách khỏi hệ số học.
  • char là 16-bit không dấu (0..65535) nên chỉ widening từ int trở lên — nó không đi về short/byte dù cùng 16/8 bit (mục 3.5).
  • Widening primitive không "bắc cầu": bảng định nghĩa từng phép trực tiếp, compiler không tự đi qua trung gian.

3.2 Hai chỗ mất chính xác: int → float và long → double

float chỉ giữ 24 bit phần định trị, double giữ 53 bit. Số nguyên vượt ngưỡng tương ứng (224, 253) bị làm tròn về bội số gần nhất — đúng luật IEEE 754, không lỗi, không cảnh báo, và ép ngược lại không khôi phục được:

int i = 16_777_217;          // 2^24 + 1
float f = i;                 // int -> float
IO.println("int 16_777_217 -> float  : " + f);       // 1.6777216E7
IO.println("ep nguoc lai thanh int   : " + (int) f); // 16777216

long big = 9_007_199_254_740_993L;   // 2^53 + 1
double d = big;              // long -> double
IO.println("long ...993 -> double     : " + d);       // 9.007199254740992E15
IO.println("ep nguoc lai thanh long  : " + (long) d); // 9007199254740992

Bẫy production: float chính xác đến 224, double đến 253. ID long lớn đi qua double — ví dụ serialize JSON thành number rồi client JS đọc lại — có thể hụt 1 đơn vị: 9_007_199_254_740_993 thành ...992. Đây là lý do thật khiến hệ thống production lệch ID, và cũng là lý do ID lớn phải gửi dạng String (mục 13.2).

3.3 Widening xảy ra ở đâu

Cùng một luật, ba ngữ cảnh hay gặp — assignment, method invocation và numeric promotion:

static void takeLong(long x) {
    IO.println("takeLong(long) : " + x);
}

int i = 'a';             // char -> int             (assignment)
long l = i;              // int -> long             (assignment)
double d = l;            // long -> double          (assignment)
IO.println("i, l, d        : " + i + " " + l + " " + d);   // 97 97 97.0

takeLong('Z');           // char -> int -> long     (method invocation)
takeLong(7);             // int -> long
IO.println("i + 1L         : " + (i + 1L));   // 98      (numeric promotion)
  • Assignment: long l = i; — vế phải widening được tới kiểu vế trái là gán hợp lệ.
  • Method invocation: tham số long nhận char, int, short... Không có overload takeLong(int) nên compiler widening; nếu có cả hai bản, bản khớp chính xác thắng (mục 9).
  • Numeric promotion: i + 1L — chỉ cần một toán hạng long, cả biểu thức thành long (mục 5).

3.4 Widening reference và array covariance

Với reference cũng có widening: String → Object, Integer → Number → Object luôn ngầm được vì quan hệ kế thừa. Và mảng "covariant": String[] là một Object[]:

String s = "java";
Object o = s;               // String -> Object        (widening reference)
CharSequence cs = s;        // String -> CharSequence
IO.println("String -> Object       : " + o);   // java
IO.println("String -> CharSequence : " + cs);  // java

Object[] objs = new String[2];   // mang covariant: String[] la Object[]
objs[0] = "ok";
try {
    objs[1] = 5;                 // runtime type la String[]
} catch (ArrayStoreException e) {
    IO.println("ArrayStoreException    : " + e.getMessage());   // java.lang.Integer
}
  • Widening reference chỉ đổi kiểu tĩnh; object runtime không đổi. Đây là nền của upcast + dynamic dispatch — xem Polymorphism — mục 4.
  • Mảng covariant cho compiler, nhưng JVM kiểm tra từng lần ghi: gán Integer vào String[] ném ArrayStoreException lúc chạy. Chi tiết ở Arrays — mục 7; đây là lý do List<String> cố tình không covariant để bắt lỗi ngay lúc compile.

3.5 char không widening về byte/short

char chứa 0..65535, không nằm trong khoảng byte (−128..127) hay short (−32768..32767), nên đó là narrowing — và Java từ chối ngầm chuyển:

WideningError.java:4: error: incompatible types: possible lossy conversion from char to byte
        byte b = c;
                 ^
WideningError.java:5: error: incompatible types: possible lossy conversion from char to short
        short s = c;
                  ^
2 errors

Muốn đổi phải ép tường minh (byte) c và tự chịu trách nhiệm với ký tự > 127 — ví dụ (byte) 'é' ra số âm. Cùng lý do, short s = 65; char c = s; cũng không compile.

Góc Node.js

  • JS chỉ có một kiểu số thường — number = double 64-bit — nên không có "widening": 16_777_217 chính xác, nhưng literal 9_007_199_254_740_993 đã in ra 9007199254740992 ngay từ lúc parse, và 2 ** 53 === 2 ** 53 + 1 là true.
  • Java tách int/long chính xác tuyệt đối khỏi float/double xấp xỉ; JS gộp hết vào double. TypeScript khai báo number cũng chỉ là double — không có cách nào "widening" vì không có gì để widen.
  • Cần số nguyên lớn chính xác trong JS phải dùng BigInt (9007199254740993n), tương ứng BigInteger bên Java (mục 12).
Chốt gọn: widening primitive tự động nhưng không bảo toàn tuyệt đối: int → float (quá 224) và long → double (quá 253) làm tròn âm thầm → char chỉ widening từ int trở lên, về byte/short là lỗi compile → widening reference luôn an toàn, còn array covariance trả giá bằng ArrayStoreException lúc chạy → cần chính xác số nguyên lớn: giữ long/BigInteger, đừng để lọt qua double.

4. Narrowing — ép tường minh và mất dữ liệu Hay hỏi phỏng vấn

Narrowing (lớn → nhỏ) là chiều ngược lại: compiler luôn từ chối ngầm chuyển vì biết có thể mất dữ liệu, bạn phải tự ép (type) để nhận trách nhiệm. Khi đã ép, Java áp luật xác định trước — không ném exception, không cảnh báo, chỉ có kết quả có thể "sai" một cách lặng lẽ.

4.1 Luật cắt khi ép số

IO.println("(int) 2.9            : " + (int) 2.9);        // 2
IO.println("(int) -2.9           : " + (int) -2.9);       // -2
IO.println("(int) Double.NaN     : " + (int) Double.NaN); // 0
IO.println("(int) +Infinity      : " + (int) Double.POSITIVE_INFINITY);  // 2147483647
IO.println("(int) -Infinity      : " + (int) Double.NEGATIVE_INFINITY);  // -2147483648
IO.println("(int) 1e20           : " + (int) 1e20);       // 2147483647
IO.println("(long) 1e20          : " + (long) 1e20);      // 9223372036854775807
IO.println("(byte) 130           : " + (byte) 130);       // -126
IO.println("(short) 65535        : " + (short) 65535);    // -1
IO.println("(int) (char) -1      : " + (int) (char) -1); // 65535
IO.println("(int) 0x1_0000_0001L : " + (int) 0x1_0000_0001L);  // 1
IO.println("(int) 4_294_967_296L : " + (int) 4_294_967_296L);  // 0

  • long → int giữ 32 bit thấp: 0x1_0000_0001L → 1, còn 4_294_967_296L (232) → 0.
  • char là 16-bit không dấu: (char) -1 = 65535; in trực tiếp là ký tự không nhìn thấy nên phải ép ngược (int) (char) -1 mới thấy số.
  • Hai luật "quá lớn" khác hẳn nhau: số dấu phẩy động bị kẹp về MAX/MIN, còn số nguyên bị quay vòng. Đừng đoán theo thói quen của phép này sang phép kia.
  • Ép double → int rồi ép ngược không khôi phục dữ liệu; muốn làm tròn số học dùng Math.round (trả long), muốn kẹp dùng Math.clamp (Java 21+).
Bẫy production: narrowing là chỗ duy nhất JVM im lặng khi bạn mất dữ liệu. Ép long ID/thời gian về int, ép double tiền về int... đều chạy trơn tru rồi sai âm thầm. Ở biên dữ liệu, validate trước khi ép (so khoảng) thay vì ép rồi hy vọng.

4.2 Constant narrowing — ngoại lệ cho hằng số vừa khoảng

Assignment context có ngoại lệ (JLS 5.2): nếu vế phải là constant expression kiểu int — literal hoặc biến final khởi tạo bằng constant expression — và giá trị nằm trong khoảng kiểu đích, Java cho phép ngầm narrowing:

final int y = 100;
byte z = y;                 // hang so vua khoang
char ch = 65;               // 65 -> 'A'
char next = 'A' + 1;        // bieu thuc hang so
byte b3 = 50 + 50;          // 100, vua byte
IO.println(z + " " + ch + " " + next + " " + b3);   // 100 A B 100

Chỉ cần "quá khoảng" hoặc "không còn là constant expression" là compiler chặn ngay:

NarrowingError.java:3: error: incompatible types: possible lossy conversion from int to byte
        byte b = 200;
                 ^
NarrowingError.java:4: error: incompatible types: possible lossy conversion from int to char
        char ch = -1;
                  ^
NarrowingError.java:6: error: incompatible types: possible lossy conversion from int to byte
        byte z = y;
                 ^
3 errors
  • byte b = 100; hợp lệ, byte b = 200; không: 200 vượt 127. final int y = 1000; byte z = y; cũng không — vẫn là hằng số nhưng ngoài khoảng.
  • 'A' + 1 là constant expression (char + int literal) → gán thẳng vào char ra 'B'. Nhưng int code = 1; char c = 'A' + code; thì lỗi vì code không phải hằng số.
  • Ngoại lệ này chỉ tồn tại ở assignment context. Method invocation không có đặc quyền đó: void m(byte b) rồi gọi m(100) vẫn lỗi "possible lossy conversion" dù 100 vừa byte — muốn truyền phải ép m((byte) 100).

4.3 Narrowing ngầm trong compound assignment

Compound assignment là ngữ cảnh duy nhất khác được phép narrowing ngầm (kể cả với giá trị không phải hằng số). s += 2.5 tương đương s = (short) (s + 2.5):

short s = 1;
s += 2.5;                    // s = (short) (s + 2.5)
IO.println("short += 2.5 : " + s);   // 3

byte b = 127;
b += 1;                      // (byte) 128
IO.println("byte 127 += 1: " + b);   // -128

Đây chính là cơ chế ở mục 6 — hữu ích nhưng cũng là nguồn bug âm thầm lớn nhất của Java.

Góc Node.js

  • JS không có cast; phép bitwise | 0 là ToInt32 (ép về int 32-bit có dấu): 2.9 | 0 = 2, -2.9 | 0 = -2, NaN | 0 = 0.
  • Khác Java ở chỗ quá lớn: Infinity | 0 = 0 và 1e20 | 0 = 1661992960 — JS lấy modulo 232, Java kẹp về 2147483647. (2147483647 + 1) | 0 = -2147483648 thì giống wraparound của Java.
  • Math.trunc(2.9) = 2 cắt về 0 giống (int) 2.9; còn new Int8Array([130])[0] = -126 mô phỏng đúng (byte) 130.
Chốt gọn: narrowing luôn cần (type) tường minh → double → int cắt về 0, NaN → 0, ±∞/quá lớn kẹp MAX/MIN → số nguyên giữ N bit thấp (wraparound bù hai) → ngoại lệ duy nhất: constant expression vừa khoảng và compound assignment → production: validate khoảng trước khi ép, không tin vào giá trị sau ép.

5. Numeric promotion — vì sao byte + byte ra int Hay hỏi phỏng vấn

Trước khi tính toán, Java "nâng" toán hạng theo luật numeric promotion (JLS 5.6). Đây không phải widening khi gán — nó là quy tắc riêng của biểu thức, và giải thích gần hết các lỗi "possible lossy conversion" mà người mới hay gặp.

5.1 Luật promotion

Với phép hai ngôi (+ - * / %, bitwise, shift), xét từ trên xuống và dừng ở dòng đầu tiên đúng; phép một ngôi (-b, ~b, b++) cũng nâng byte/short/char lên int trước:

Nếu một toán hạng làCả hai được nâng thành
doubledouble
floatfloat
longlong
còn lại: byte, short, char, intint
 
byte b1 = 1, b2 = 2;
IO.println("byte + byte    : " + (b1 + b2));   // 3
char c1 = 'a', c2 = 'b';
IO.println("'a' + 1        : " + ('a' + 1));    // 98
IO.println("'a' + 'b'      : " + (c1 + c2));    // 195
IO.println("int + long     : " + (1 + 2L));     // 3
IO.println("float + double : " + (1.5f + 2.5)); // 4.0
IO.println("int + float    : " + (16_777_217 + 0.0f));             // 1.6777216E7
IO.println("long + float   : " + (9_007_199_254_740_993L + 0.0f)); // 9.007199E15
  • b1 + b2 in ra 3 nhưng kiểu kết quả là int, không phải byte — muốn gán ngược vào byte phải ép: byte sum = (byte) (b1 + b2);.
  • 'a' + 'b' là phép cộng số: 97 + 98 = 195, không phải "ab". Muốn nối ký tự phải dính tới String: "" + 'a' + 'b'.
  • long + float nâng cả hai thành float — nghĩa là long lớn có thể mất chữ số ngay trong biểu thức, trước cả khi bạn kịp gán (mục 3.2).
  • int + float nâng int thành float: 16_777_217 thành 1.6777216E7.

Hệ quả compile hay gặp nhất:

PromotionError.java:4: error: incompatible types: possible lossy conversion from int to byte
        byte sum = b1 + b2;
                      ^
1 error

5.2 Chia số nguyên và tràn trước khi gán

IO.println("1 / 2          : " + (1 / 2));    // 0
IO.println("1.0 / 2        : " + (1.0 / 2));  // 0.5
IO.println("-7 / 2         : " + (-7 / 2));   // -3
IO.println("-7 % 2         : " + (-7 % 2));   // -1

long bad = 1 * 1000 * 1000 * 1000 * 5;    // int * int tran truoc
long good = 1L * 1000 * 1000 * 1000 * 5;  // long ngay tu dau
IO.println("int * int      : " + bad);     // 705032704
IO.println("1L * ...       : " + good);    // 5000000000
  • int / int luôn là chia nguyên: 1 / 2 = 0. Chỉ cần một toán hạng double (1.0 / 2) là ra 0.5. Đây là nguồn bug tính trung bình/tỷ lệ kinh điển; cẩn thận hơn nữa với 0 / 0 (int ném ArithmeticException, double ra NaN).
  • Chia lấy dư giữ dấu số bị chia: -7 / 2 = -3, -7 % 2 = -1 — khác Python (làm tròn xuống, dư dương).
  • Tràn xảy ra theo kiểu của biểu thức, không theo kiểu biến nhận: 1 * 1000 * 1000 * 1000 * 5 tính trong int, tràn thành 705032704 rồi mới widening sang long. Chỉ cần viết 1L ở đầu là cả biểu thức thành long. Xem thêm Biến trong Java — mục 9 (Tràn số).

5.3 Nối chuỗi vs cộng số

Toán tử + kết hợp trái sang phải và đổi sang nối chuỗi ngay khi một toán hạng (đã tính) là String. Vì vậy thứ tự toán hạng quyết định kết quả:

IO.println(1 + 2 + "3");     // 33
IO.println("1" + 2 + 3);     // 123
IO.println(1 + (2 + "3"));   // 123
IO.println(1 + 2 + 3 + "x"); // 6x
  • 1 + 2 + "3": cộng số trước (1 + 2 = 3) rồi mới nối → "33".
  • "1" + 2 + 3: gặp String ngay từ đầu → "123". Muốn cộng trước thì thêm ngoặc: "1" + (2 + 3) = "15".
  • Nối chuỗi trong vòng lặp tạo nhiều object trung gian — dùng StringBuilder (xem Strings chuyên sâu).

5.4 Ternary và so sánh cũng promotion

Hai nhánh ternary và hai vế so sánh cũng được đưa về cùng kiểu theo đúng luật trên:

boolean flag = true;
IO.println(flag ? 1 : 2.0);   // 1.0
IO.println(flag ? 1 : 2L);    // 1
IO.println(1 == 1L);          // true
IO.println(1 == 1.0f);        // true
  • flag ? 1 : 2.0 có kiểu double nên in 1.0; flag ? 1 : 2L có kiểu long nên in 1. Bẫy unboxing khi nhánh là wrapper nằm ở mục 7.2.
  • So sánh == giữa các kiểu số cũng promotion trước khi so — 1 == 1L, 1 == 1.0f đều true. Riêng so sánh wrapper với nhau bằng == chỉ so reference, không promotion (Biến trong Java — mục 12).

Góc Node.js

  • JS chỉ có một kiểu số nên 1 / 2 luôn ra 0.5; không có chuyện chia nguyên ngoài ý muốn — nhưng cũng không có int để tràn. Muốn chia nguyên phải Math.trunc(1 / 2) hoặc (1 / 2) | 0.
  • Nối chuỗi giống Java về thứ tự: "1" + 2 + 3 = "123", 1 + 2 + "3" = "33". Khác ở chỗ JS còn tự ép cho -: "5" - 1 = 4 (Java không compile).
  • 9007199254740993 là literal double nên in ra 9007199254740992 — đúng kiểu mất chính xác của long → double bên Java.
Chốt gọn: biểu thức luôn được nâng theo thứ tự double > float > long > int; byte/short/char tự lên int → byte + byte ra int, gán ngược phải ép → int / int cắt về 0, tràn tính theo kiểu biểu thức chứ không theo kiểu biến nhận (nhớ hậu tố L) → + chạy trái sang phải, gặp String là nối từ đó về sau.

6. Compound assignment và ++/-- Hay hỏi phỏng vấn Production

JLS 15.26.2 định nghĩa E1 op= E2 tương đương E1 = (T) ((E1) op (E2)), trong đó T là kiểu của E1 và E1 chỉ được đánh giá một lần. Chính phép ép (T) ngầm này khiến b += 5 chạy được còn b = b + 5 thì không.

6.1 Cơ chế ép ngầm về kiểu bên trái

byte b = 10;
b += 5;                      // b = (byte) (b + 5)
IO.println("byte += 5  : " + b);   // 15

int i = 5;
i += 3.9;                    // i = (int) (i + 3.9)
IO.println("int += 3.9 : " + i);   // 8

long l = 1;
l += 1.0;                    // l = (long) (l + 1.0)
IO.println("long += 1.0: " + l);   // 2

Bỏ ép ngầm đi là compiler chặn ngay — cùng phép tính, khác ngữ cảnh:

CompoundAssignError.java:4: error: incompatible types: possible lossy conversion from int to byte
        b = b + 5;
              ^
1 error
Bẫy production: i += 3.9 không báo lỗi, không cảnh báo — chỉ âm thầm cắt phần thập phân. Với tiền bạc, luôn dùng BigDecimal (Biến trong Java — mục 13) thay vì tin vào compound assignment.

6.2 Toán hạng trái chỉ được đánh giá MỘT lần

Đây là điểm người mới hay hiểu sai khi "khai triển" += thành phép gán thường. JLS bảo đảm biểu thức bên trái (reference mảng, chỉ số, field) được tính đúng một lần:

int[] arr = {10, 20, 30};
int idx = 0;
arr[idx++] += 5;             // idx++ chi chay MOT lan
IO.println("arr : " + Arrays.toString(arr));   // [15, 20, 30]
IO.println("idx : " + idx);                    // 1
  • Nếu khai triển ngây thơ thành arr[idx++] = arr[idx++] + 5; thì idx bị tăng hai lần: lần đầu ở vế trái, lần sau lại được chọn phần tử — kết quả hoàn toàn khác. Compiler sinh code đúng luật, không sinh hai lần tăng.
  • Luật này áp dụng cho mọi vế trái là "variable" theo JLS: phần tử mảng (a[i] *= 2) và field (obj.count += 1) — mỗi cái chỉ được định vị một lần. Lưu ý biểu thức như map.get(k) không phải variable nên map.get(k) += v không compile.

6.3 Ba bẫy production

long x = 0;
x += 0.1;                    // (long) 0.1 = 0
IO.println("long += 0.1       : " + x);   // 0

int y = 5;
y = y++;                     // tra gia tri cu, tang ban sao
IO.println("y = y++           : " + y);   // 5

Integer box = null;
try {
    box += 1;                // box.intValue() -> NPE
} catch (NullPointerException e) {
    IO.println("Integer null += 1 : NullPointerException");
}
box = 1;
box += 1;
IO.println("Integer 1 += 1    : " + box);   // 2
  • x += 0.1 với long mãi bằng 0: phép cộng ra 0.1 (double), rồi bị ép ngầm về long — lần nào cũng cắt thành 0. Cộng thêm bao nhiêu lần cũng vô nghĩa; đây là bug im lặng đúng nghĩa.
  • i = i++ giữ giá trị cũ: hậu tố trả về giá trị trước khi tăng, phép gán ghi lại chính giá trị cũ đó rồi giá trị tăng bị bỏ. Dòng này compile, chạy, và ra 5 — không ai báo lỗi. Đừng viết x = x++ hay x = ++x; muốn tăng thì viết x++ hoặc x += 1.
  • Integer null += 1 ném NPE: compound assignment trên wrapper desugar thành box = Integer.valueOf((int) (box.intValue() + 1)) — unbox ngầm gọi intValue() trên null. Wrapper không null (box = 1; box += 1;) thì chạy bình thường.

6.4 += với String, >>>= và biến thể

String s = "a";
s += 1;
s += 'b';
IO.println("s += 1; s += 'b' : " + s);   // a1b

int u = -1;
u >>>= 1;                    // u = (int) (u >>> 1)
IO.println("-1 >>>= 1        : " + u);   // 2147483647

byte b2 = -1;
b2 >>>= 1;                   // (byte) (0xFFFFFFFF >>> 1)
IO.println("byte -1 >>>= 1   : " + b2);  // -1
  • String += là ngoại lệ duy nhất không cần ép ngầm: phép + đã là nối chuỗi, kết quả vẫn là String. s += 1; s += 'b'; ra "a1b" — char được nối như ký tự, không thành số.
  • >>>= vẫn theo công thức chung: byte được nâng lên int khi dịch (-1 → 0xFFFFFFFF), >>> 1 được 0x7FFFFFFF, rồi ép ngược (byte) nên kết quả lại là -1. Dịch luận lý không "cứu" được byte vì phép ép ngược về byte mới là bước quyết định.
  • Các toán tử += -= *= /= %= &= |= ^= <<= >>= >>>= đều đúng một công thức chung như trên; riêng >>>= hay bị quên vì ít gặp trong code nghiệp vụ.

6.5 ++/-- trên byte/short/char

b++ với byte b hợp lệ vì phép tăng cũng chứa sẵn ép kiểu ngầm — khác với b = b + 1 (errblock ở mục 6.1):

byte b = 10;
b++;                         // ok - khac b = b + 1
IO.println("b++ : " + b);    // 11

char c = 'A';
c++;                         // char cung tang duoc
IO.println("c++ : " + c);    // B

Lưu ý byte b = 127; b++; quay vòng thành -128 — luật wraparound vẫn áp dụng, chỉ khác là không cần ép tay.

Góc Node.js

  • JS không có kiểu biến cố định nên += không bao giờ bị compiler từ chối: let s = "a"; s += 1; ra "a1"; let n = 1; n += "2"; ra "12" (đổi kiểu luôn!); nhưng let m = "5"; m -= 1; ra 4 vì - ép về number.
  • Kiểu "lỏng" đó khiến bug kiểu dữ liệu khó thấy hơn cả compound assignment của Java: Java ít nhất chặn b = b + 5 với byte, JS nuốt hết rồi để lỗi nổ ở tận tầng render.
  • x = x++ trong JS cũng giữ giá trị cũ y hệt Java — bẫy này chung cho mọi ngôn ngữ có hậu tố tăng.
Chốt gọn: E1 op= E2 = E1 = (T)((E1) op (E2)), vế trái đánh giá đúng một lần → b += 5 chạy còn b = b + 5 lỗi compile → xem chừng ba bẫy: long += 0.1 mãi bằng 0, i = i++ giữ giá trị cũ, wrapper null += 1 NPE → String += là ngoại lệ, >>>= vẫn ép về kiểu trái.

7. Ternary, nối chuỗi và các ngữ cảnh ngầm Hay hỏi phỏng vấn

Toán tử điều kiện ?: là toán tử ba ngôi duy nhất của Java. Nó tưởng dễ vì giống JavaScript, nhưng có luật kiểu riêng (JLS 15.25) và một bẫy unboxing nổi tiếng.

7.1 Cú pháp và kết hợp phải

dieuKien ? giaTriDung : giaTriSai

?: kết hợp phải, nên chuỗi lồng nhau không cần ngoặc theo nghĩa khác đi: a ? b : c ? d : e chính là a ? b : (c ? d : e):

static String pick(int n) {
    return n < 0 ? "am" : n == 0 ? "khong" : "duong";
}

IO.println(pick(-5) + " " + pick(0) + " " + pick(7));   // am khong duong
  • Chỉ đúng một nhánh được thực thi: dieuKien ? f() : g() gọi f() hoặc g(), không gọi cả hai. Vì vậy ternary là biểu thức (trả giá trị), khác if (câu lệnh).
  • Lồng nhau quá 2 tầng làm code khó đọc; ưu tiên if/else hoặc switch expression (Java 14+) cho logic nhiều nhánh. Ternary chỉ nên dùng cho chọn giá trị đơn giản.

7.2 Kiểu của ternary (JLS 15.25)

Hai nhánh không cần cùng kiểu — JLS quy định kiểu chung theo từng nhóm. Nhóm numeric trước:

boolean flag = true;
IO.println(flag ? 'a' : 1);      // a  - hang so 1 bieu dien duoc trong char
IO.println(flag ? 'a' : 70000);  // 97 - hang so ngoai khoang char -> int
int code = 1;
IO.println(flag ? 'a' : code);   // 97 - bien int -> ca hai thanh int
IO.println(flag ? 1 : 2.0);      // 1.0
IO.println(flag ? 1 : 2L);       // 1
  • numeric conditional: 1 : 2.0 → double nên in 1.0; 1 : 2L → long (mục 5.4).
  • Ngoại lệ tinh tế: nếu một nhánh là char và nhánh kia là hằng số int biểu diễn được trong char, kiểu kết quả là char — nên flag ? 'a' : 1 in ra a, còn đổi thành 70000 hoặc một biến int thì in ra 97.

Nhóm wrapper/primitive mới là chỗ gây bug — nếu một nhánh là primitive thì Java buộc cả biểu thức về primitive, và chỉ nhánh được chọn mới bị unbox:

Integer boxed = null;

try {
    int x = true ? boxed : 0;     // nhanh boxed bi unbox
    IO.println(x);
} catch (NullPointerException e) {
    IO.println("true ? boxed : 0   : NullPointerException");
}

Integer ok = false ? boxed : 0;   // nhanh 0 duoc chon
IO.println("false ? boxed : 0  : " + ok);   // 0

Integer a = null, b = 1;
IO.println("ca hai wrapper     : " + (true ? a : b));   // null

Integer one = true ? 1 : null;    // primitive + null -> Integer
Integer nil = false ? 1 : null;
IO.println("true ? 1 : null    : " + one);   // 1
IO.println("false ? 1 : null   : " + nil);   // null
  • true ? boxed : 0 có kiểu int (vì nhánh 0 là primitive) nên nhánh boxed bị unbox khi được chọn → NPE. Với false, nhánh 0 được chọn nên boxed không bị đụng tới — lỗi phụ thuộc dữ liệu, rất khó tái hiện.
  • Nếu cả hai nhánh đều là wrapper (true ? a : b), kiểu kết quả vẫn là wrapper, không unbox — kết quả có thể là null mà không ném gì.
  • Ngoại lệ "cứu" được null: nhánh kia là null literal thì kết quả là wrapper (true ? 1 : null kiểu Integer), nên false ? 1 : null trả null an toàn.
  • Trộn wrapper khác nhóm với primitive, ví dụ Integer với 2L, cho kết quả primitive long — nhánh wrapper bị unbox. Cách phòng chung: đừng để nhánh nào có thể null, hoặc chuẩn hoá bằng Objects.requireNonNullElse trước khi đưa vào ternary.

7.3 Nối chuỗi — precedence, null và char

Một khi một toán hạng là String, phép + chuyển thành nối chuỗi và mọi giá trị sau đó được "string hoá". Dấu ngoặc đổi hoàn toàn kết quả:

IO.println("1" + 1 + 2);     // 112
IO.println(1 + 1 + "2");     // 22
IO.println(null + "x");      // nullx
IO.println("" + null);       // null
IO.println('A' + "1");       // A1
IO.println("x" + 'A');       // xA
  • null + "x" compile bình thường và in ra "nullx": JLS coi null literal như giá trị có thể string hoá. Nhưng cẩn thận — null với phép - hay == là chuyện hoàn toàn khác.
  • 'A' + "1" = "A1" (char nối ký tự), nhưng 'A' + 'B' = 195 (cộng số) và "" + 'A' + 'B' = "AB" — đặt String ở đâu quyết định tất cả (mục 5.3).
  • Chuỗi nối bằng + trong vòng lặp tạo object mới mỗi lần; dùng StringBuilder cho khối lượng lớn (Strings chuyên sâu).

Góc Node.js

  • ?: cú pháp giống hệt, nhưng JS không có luật kiểu chung: mỗi nhánh giữ nguyên kiểu của nó, nên không bao giờ có NPE unbox. Đổi lại, kiểu kết quả có thể "nhảy" giữa number/string/null tuỳ nhánh — TypeScript mới là bên cảnh báo.
  • JS có thêm hai toán tử trả về toán hạng: 0 || "x" = "x" (falsy đầu tiên bị bỏ) còn 0 ?? "x" = 0 (chỉ bỏ null/undefined). Không có tương đương trực tiếp trong Java — gần nhất là ternary với kiểm tra null.
  • Nối chuỗi giống Java: null + "x" = "nullx", "" + null = "null"; nhưng 1 + null = 1 (JS ép null thành 0) trong khi Java 1 + null không compile.
Chốt gọn: ?: kết hợp phải, chỉ chạy một nhánh → hai nhánh được đưa về cùng kiểu: numeric chuẩn, char + hằng int vừa khoảng ra char → hễ có nhánh primitive thì nhánh wrapper được chọn bị unbox (NPE nếu null), cả hai wrapper thì giữ được null → + trái sang phải, gặp String là nối, null thành "null", char thành ký tự.

8. Chuyển đổi boxing/unboxing Hay hỏi phỏng vấn Junior+

Boxing (JLS 5.1.7) là bọc primitive thành wrapper: int → Integer. Unboxing (JLS 5.1.8) là chiều ngược lại: Integer → int. Hai chiều này không đối xứng khi ghép thêm widening — và gần như mọi câu hỏi phỏng vấn về wrapper đều xoay quanh chỗ đó.

8.1 Hai chiều chuyển đổi hợp lệ

Assignment/invocation context cho phép ghép hai bước theo đúng thứ tự: boxing rồi widening reference, hoặc unboxing rồi widening primitive:

Object o = 1;                    // boxing int -> Integer, roi widening reference
Number n = 1;                    // Integer -> Number
IO.println("Object o = 1     : " + o);   // 1
IO.println("Number n = 1     : " + n);   // 1

long l = Integer.valueOf(5);     // unbox int -> widening long
double d = Integer.valueOf(5);   // unbox + widening
IO.println("long tu Integer  : " + l);   // 5
IO.println("double tu Integer: " + d);   // 5.0

Long e = (long) Integer.valueOf(1);   // unbox -> int -> long -> boxing Long
IO.println("Long tu (long)   : " + e);   // 1

Long ok = 10L;
IO.println("Long ok = 10L    : " + ok);  // 10
  • Object o = 1; hợp lệ vì đi int → Integer → Object: boxing trước, widening reference sau. Đây không phải "int thành Object" mà là hai phép chuyển nối tiếp.
  • long l = Integer.valueOf(5); hợp lệ vì Integer → int → long: unboxing trước, widening primitive sau. Chiều này cực kỳ hay gặp khi API trả Optional<Integer> hay field nullable.
  • Long e = (long) Integer.valueOf(1); cần ép tường minh để chỉ rõ đích: unbox → widening int→long → boxing Long. Không có ép thì lỗi (mục 8.2).

8.2 int → Long không hợp lệ — vì sao Long a = 10 lỗi

BoxingError.java:3: error: incompatible types: int cannot be converted to Long
        Long a = 10;
                 ^
BoxingError.java:4: error: incompatible types: int cannot be converted to Double
        Double c = 1;
                   ^
BoxingError.java:6: error: incompatible types: Integer cannot be converted to Long
        Long f = i;
                 ^
3 errors
  • Long a = 10; đòi chuỗi int → long → Long: widening primitive rồi mới boxing — tổ hợp này assignment context không cho phép. Cách đúng: viết literal đúng kiểu Long a = 10L; chỉ còn một bước boxing.
  • Đối xứng của nó thì được: long b = Integer.valueOf(5); (unbox rồi widening). Quy tắc dễ nhớ: boxing đi trước widening reference, unboxing đi trước widening primitive; widening primitive rồi boxing thì không.
  • Wrapper khác wrapper cũng không tự chuyển dù primitive tương ứng widening: Integer i = 10; Long f = i; lỗi — Integer không phải cha của Long. Muốn đổi: Long f = i.longValue();.

8.3 Unbox null và autobox trong switch/ternary

Unboxing là nơi NPE ẩn núp nhiều nhất vì cú pháp không hề gợi ý có lời gọi method:

Integer x = null;
try {
    long l = x;              // x.longValue() ngam
    IO.println(l);
} catch (NullPointerException e) {
    IO.println("long l = x       : NullPointerException");
}

switch (Integer.valueOf(2)) {    // switch tu unbox
    case 2 -> IO.println("switch Integer 2 : hai");
    default -> IO.println("khac");
}
  • long l = x tương đương x.longValue(); x == 1, x + 1, x > 0... đều unbox ngầm. switch trên wrapper cũng unbox — wrapper null ném NPE ngay khi vào switch.
  • Ternary với một nhánh primitive cũng unbox — bẫy ở mục 7.2. Đây là lý do các check null tưởng thừa lại quan trọng ở biên dữ liệu.
  • Cache -128..127, == giữa wrapper, equals khác class... không nhắc lại ở đây — bảng đầy đủ ở Biến trong Java — mục 12. Mục này chỉ bàn luật chuyển đổi.

Góc Node.js

  • JS không phân biệt primitive và object cho số thường: typeof 1 là "number", không có boxing ngầm — cũng không có NPE unbox. Đổi lại JS không có generics, nên vấn đề "collection chỉ chứa reference" mà wrapper sinh ra để giải quyết không tồn tại.
  • new Number(1) là object thật: new Number(1) === 1 là false nhưng new Number(1) == 1 là true (nhờ coercion). Đừng bao giờ tạo new Number/new String/new Boolean — giống tinh thần "đừng dùng wrapper làm toán" trong Java.
  • 1 + null trong JS ra 1 (null → 0) — không lỗi; Java thì không compile. TypeScript với strictNullChecks mới chặn được kiểu bẫy này ở mức compile.
Chốt gọn: boxing rồi widening reference OK (Object o = 1;) → unboxing rồi widening primitive OK (long l = Integer.valueOf(5);) → widening primitive rồi boxing không OK (Long a = 10; lỗi; viết 10L) → unbox null ném NPE ở mọi ngữ cảnh (gán, so sánh, switch, ternary) → chi tiết cache/so sánh xem mục 12.

9. Method invocation conversion và overload Hay hỏi phỏng vấn Junior+

Khi bạn gọi m(1) mà class có nhiều bản m, compiler phải chọn đúng một bản. JLS 15.12.2 quy định xét theo 3 pha theo thứ tự, dừng ngay khi pha nào tìm được bản phù hợp nhất — không bao giờ "nhảy" xuống pha sau dù bản ở pha sau có vẻ khớp hơn.

9.1 Ba pha chọn overload

  1. Pha 1 — strict invocation: chỉ widening primitive (không narrowing), widening reference. Không boxing/unboxing, không varargs.
  2. Pha 2 — loose invocation: thêm boxing/unboxing, vẫn không varargs.
  3. Pha 3 — variable arity: mới xét method varargs (int...), sau khi đã loại các bản cố định.

Trong mỗi pha, nếu có nhiều bản cùng "vừa", compiler chọn bản most specific — kiểu tham số "hẹp" nhất không cần ép thêm. Nội dung đa hình của overload (static dispatch) nằm ở Polymorphism — mục 2; ở đây tập trung vào phần chuyển kiểu.

9.2 Ví dụ — widening (pha 1) đánh bại boxing (pha 2)

static void f(long x)    { IO.println("f(long)"); }
static void f(Integer x) { IO.println("f(Integer)"); }
static void f(Object x)  { IO.println("f(Object)"); }

static void g(Object x)  { IO.println("g(Object)"); }
static void g(Integer x) { IO.println("g(Integer)"); }

f(1);                    // f(long)    - phase 1 widening
f(Integer.valueOf(1));   // f(Integer) - khop chinh xac
f("text");               // f(Object)
g(null);                 // g(Integer) - cu the hon Object
  • f(1) chọn f(long) vì int → long là widening ở pha 1, còn Integer/Object cần boxing (pha 2). Dù f(Integer) trông "gần" hơn về mặt khái niệm, nó thua ngay từ pha.
  • f("text") rơi vào f(Object) bằng widening reference — không có bản nào khác nhận String.
  • g(null) không lỗi vì có bản most specific: Integer là con của Object, nên g(Integer) thắng.
  • Hệ quả production: class có cả method(long) lẫn method(Integer) thì mọi lời gọi bằng số nguyên sẽ vào bản long. Nếu hai bản xử lý khác nhau (ví dụ bản Integer chấp nhận null), bug rất khó thấy — xem thêm Methods.

9.3 Bẫy null mơ hồ

Nếu hai bản nằm ở hai nhánh kế thừa không liên quan nhau, null không chọn được bản nào "cụ thể hơn" — compile error ngay:

OverloadAmbiguous.java:6: error: reference to m is ambiguous
        m(null);
        ^
  both method m(String) in OverloadAmbiguous and method m(Integer) in OverloadAmbiguous match
1 error
  • String và Integer là hai class lá của hai cây khác nhau, không bản nào specific hơn → ambiguous. Cách sửa: ép tường minh m((String) null) hoặc m((Integer) null) để nói rõ ý bạn.
  • Khác biệt tinh tế: m(Object) và m(Integer) thì m(null) chọn m(Integer) (Integer là con). Chỉ khi hai nhánh không quan hệ cha–con mới ambiguous.
  • Với giá trị int chứ không phải null: m(long) và m(Integer) → chọn m(long) (pha 1). Cùng cặp bản đó, truyền Integer thì chọn m(Integer) vì khớp chính xác pha 1.

9.4 varargs — luôn xét cuối

static void h(int x)     { IO.println("h(int)"); }
static void h(int... x)  { IO.println("h(int...) - " + x.length + " tham so"); }

h(1);                    // h(int) - phase 1 thang varargs
h(1, 2);                 // h(int...) - 2 tham so
h();                     // h(int...) - 0 tham so
  • h(1) chọn bản fixed-arity h(int): pha 3 chỉ được xét khi pha 1–2 thất bại. Bản varargs không bao giờ "cướp" lời gọi của bản cố định.
  • Method varargs tạo mảng mỗi lần gọi khi tham số rời rạc (h(1, 2) → new int[]{1, 2}) — chi phí nhỏ nhưng có thật; đừng lạm dụng trong vòng lặp nóng. Chi tiết ở Arrays — mục 9.
  • Cẩn thận overload giữa h(int...) và h(long...): h(1) không chọn bản fixed-arity (không có), cả hai đều vào pha 3 và bản int... thắng vì specific hơn — nhưng code đọc rất dễ nhầm.

Góc Node.js

  • JS không có overload theo kiểu: khai báo hai function cùng tên thì bản sau ghi đè bản trước, không có "3 phase" nào cả. Muốn hành xử theo kiểu, bạn tự kiểm tra typeof/arguments.length bên trong.
  • TypeScript hỗ trợ khai báo overload signature nhưng chỉ là gợi ý compile-time; runtime vẫn chạy đúng một function — tương tự giới hạn của generic erasure bên Java.
  • Vì không có overload, JS cũng không có bẫy widening-vs-boxing; nhưng bù lại bug "truyền null/undefined rơi vào nhánh mặc định" lại phổ biến không kém.
Chốt gọn: chọn overload theo 3 pha strict → loose (boxing) → varargs, dừng ở pha đầu tiên có bản phù hợp và most specific → f(1) với f(long)+f(Integer) chọn long → m(null) hai nhánh không liên quan (String/Integer) là lỗi compile, còn Object/Integer chọn Integer → cẩn thận API có cả bản primitive lẫn wrapper.

10. Ép kiểu reference và ClassCastException Junior+

Với primitive, ép kiểu đổi giá trị. Với reference, ép kiểu không đổi object — nó chỉ đổi cách compiler nhìn object đó. Đây là nguồn của cả upcast tự động lẫn ClassCastException lúc chạy.

10.1 Upcast ngầm — downcast tường minh

Object o = "abc";
String s = (String) o;                    // downcast
IO.println("downcast        : " + s);     // abc

Number n = Integer.valueOf(5);            // upcast ngam
IO.println("upcast Number   : " + n);     // 5

Object num = Integer.valueOf(5);
try {
    String s2 = (String) num;
    IO.println(s2);
} catch (ClassCastException e) {
    IO.println("CCE             : " + e.getMessage());
}

Object nil = null;
String s3 = (String) nil;                 // cast null: OK
IO.println("cast null       : " + s3);     // null

Message thật của JVM (JDK 25) khi downcast sai:

class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')
  • Upcast (Integer → Number → Object) luôn ngầm được vì mọi Integer đều là Number. Downcast (Object → String) chỉ là lời hứa với compiler; JVM kiểm tra lại lúc chạy và ném ClassCastException nếu sai.
  • Cast null luôn hợp lệ — (String) null ra null, không ném gì. Vì vậy CCE thường xuất hiện ở nơi dữ liệu "bỗng nhiên" khác kiểu, còn null thì lặng lẽ đi qua rồi nổ ở chỗ khác.
  • Luôn kiểm tra trước khi downcast: instanceof cổ điển hoặc pattern matching Java 16+ if (o instanceof String s) { ... } — vừa kiểm tra vừa gán tên, không cần ép lại. Đào sâu ở Polymorphism — mục 4.

Có những cặp cast compiler từ chối thẳng vì chắc chắn vô nghĩa:

ReferenceCastError.java:4: error: incompatible types: Integer cannot be converted to String
        String s = (String) i;
                            ^
1 error
  • Hai class final không có quan hệ cha–con (như Integer và String) thì không object nào vừa là cái này vừa là cái kia → compiler chặn ngay, tốt hơn để nổ runtime.
  • Nhưng cast qua interface thường vẫn compile: Comparable<String> cs = "x"; String s = (String) cs; hợp lệ vì biết đâu object runtime là class implements cả hai. Compiler chỉ cho qua khi còn khả năng đúng.

10.2 Cast chỉ đổi kiểu tĩnh — object không đổi

Object o = "abc";
String s = (String) o;
IO.println("cung object     : " + (s == o));          // true
IO.println("runtime class   : " + o.getClass());      // class java.lang.String

Object arr0 = new String[] {"a", "b"};
String[] arr = (String[]) arr0;            // mang covariant
IO.println("mang cast duoc  : " + Arrays.toString(arr));   // [a, b]

Object badArr = new Object[] {"a"};
try {
    String[] x = (String[]) badArr;
    IO.println(x);
} catch (ClassCastException e) {
    IO.println("Object[] -> String[] : ClassCastException");
}

Comparable<String> cs = "class.cast";
String sc = String.class.cast(cs);
IO.println("Class.cast      : " + sc);      // class.cast
  • (String) o không tạo object mới, không copy gì: s == o vẫn true, getClass() vẫn là String. Chỉ có kiểu tĩnh của biến đổi, mở ra method nào được gọi trên biến đó.
  • Cast mảng phụ thuộc runtime component type: Object arr0 = new String[]{...} cast về String[] được; nhưng new Object[]{...} cast về String[] ném CCE vì mảng thật sự là Object[]. Cùng cơ chế với ArrayStoreException ở mục 3.4.
  • Cast interface ↔ class cũng theo luật runtime: String.class.cast(cs) trả về chính object "class.cast" (không copy), hữu ích khi kiểu chỉ biết qua Class<T>.

10.3 Class.cast() và unchecked cast

Class.cast hành xử y hệt ép kiểu thường: trả object gốc nếu đúng kiểu, ném ClassCastException nếu sai — nhưng gọi được khi bạn có đối tượng Class<T> trong tay (reflection, generic API). Còn ép kiểu sang type variable thì compiler chỉ cảnh báo, vì erasure xoá mất thông tin generic:

static <T> T cast(Object o) {
    return (T) o;                 // unchecked cast
}

Object o = "x";
String s = cast(o);               // T suy ra String nhung khong kiem tra runtime
IO.println(s);                    // x
UncheckedCast.java:3: warning: [unchecked] unchecked cast
        return (T) o;                 // unchecked cast
                   ^
  required: T
  found:    Object
  where T is a type-variable:
    T extends Object declared in method <T>cast(Object)
1 warning
  • Mặc định javac chỉ in dòng Note: ... uses unchecked or unsafe operations; bật javac -Xlint:unchecked mới thấy chi tiết như trên.
  • Unchecked cast không sai nếu bạn chứng minh được object đúng kiểu (ví dụ sau khi validate bằng reflection); khi đó bọc @SuppressWarnings("unchecked"), kèm comment lý do. Nếu không chắc, đó là heap pollution: danh sách khai báo List<String> nhưng chứa Integer, lỗi chỉ nổ ở nơi khác khi lấy phần tử ra.
  • Trong code nghiệp vụ, ưu tiên thiết kế tránh cast hẳn: dùng polymorphism, generic đúng kiểu, hoặc pattern matching switch (Java 21). Cast chỉ nên xuất hiện ở biên tích hợp (JSON, reflection, thư viện cũ).

Góc Node.js

  • JavaScript thuần không có cast; TypeScript có x as number nhưng đó là ép kiểu tĩnh hoàn toàn compile-time — không sinh kiểm tra runtime nào. Gán sai kiểu vẫn chạy tới khi gọi method không tồn tại mới nổ (TypeError), muộn hơn hẳn CCE của Java.
  • Muốn kiểm tra thật trong JS dùng instanceof, typeof, Array.isArray — tương ứng tinh thần instanceof + pattern matching của Java.
  • Downcast "an toàn" của Java nhờ kiểm tra runtime là lợi thế thật của nền tảng có JVM; đổi lại bạn phải viết thêm instanceof ở nơi TS chỉ cần as.
Chốt gọn: upcast ngầm, downcast tường minh và JVM kiểm tra runtime (ClassCastException) → cast null OK, cast hai class không liên quan là lỗi compile, cast interface có thể vẫn compile → cast chỉ đổi kiểu tĩnh, object và == reference không đổi → mảng cast theo runtime component type → (T) o sinh cảnh báo unchecked, chỉ @SuppressWarnings khi đã chứng minh an toàn → ưu tiên instanceof/pattern matching thay vì cast.

11. parseXxx / valueOf chuyên sâu — dữ liệu từ bên ngoài Hay hỏi phỏng vấn Production

Mọi dữ liệu từ HTTP request, file, biến môi trường đều là chuỗi. Chuyển chuỗi thành số tưởng đơn giản nhưng là nguồn lỗi production hàng đầu: parseInt ném NumberFormatException thay vì trả giá trị mặc định, còn tràn khoảng thì cũng ném. Mục này đi từ API cơ bản tới message lỗi thật của JDK 25, locale, và cách xử lý ở biên hệ thống.

11.1 parse vs valueOf vs decode

MethodTrả vềĐặc điểm
Integer.parseInt("255")intPrimitive; tính toán nhanh; ném NFE khi sai
Integer.valueOf("255")IntegerObject; cache sẵn -128..127; dùng khi cần null/collection
Integer.decode("0xFF")IntegerTự hiểu tiền tố 0x/# (hex), 0 (bát phân), dấu +/-
 
IO.println(Integer.parseInt("255"));    // 255
IO.println(Integer.valueOf("255"));     // 255
IO.println(Integer.decode("0xFF"));     // 255
IO.println(Integer.decode("#FF"));      // 255
IO.println(Integer.decode("010"));      // 8   - he bat phan!
IO.println(Integer.decode("-0x10"));    // -16

Integer a = Integer.valueOf(127), b = Integer.valueOf(127);
Integer c = Integer.valueOf(128), d = Integer.valueOf(128);
IO.println(a == b);                     // true  - nam trong cache
IO.println(c == d);                     // false - ngoai cache, hai object khac nhau
Bẫy "010": decode theo luật literal cũ — chuỗi bắt đầu bằng 0 là bát phân, nên "010" = 8 chứ không phải 10. Nó tiện cho mã hex có tiền tố, nhưng đừng dùng cho dữ liệu người dùng nếu không chắc định dạng.

Constructor new Integer(5) đã bị deprecated từ Java 9; javac chỉ cảnh báo khi bật -Xlint:deprecation:

DeprecatedDemo.java:3: warning: [deprecation] Integer(int) in Integer has been deprecated
        Integer x = new Integer(5);
                    ^
1 warning

11.2 Radix — hệ đếm 2..36

Mọi wrapper số đều có bản parseXxx(String, int radix). Radix hợp lệ từ Character.MIN_RADIX (2) tới Character.MAX_RADIX (36); chữ số dùng 0-9 rồi a-z, không phân biệt hoa thường.

IO.println(Integer.parseInt("FF", 16));     // 255
IO.println(Integer.parseInt("1010", 2));    // 10
IO.println(Integer.parseInt("z", 36));      // 35
IO.println(Character.MIN_RADIX);            // 2
IO.println(Character.MAX_RADIX);            // 36
IO.println(Integer.parseInt("+5"));         // 5   - dau + duoc phep
IO.println(Integer.parseInt("-0"));         // 0

try {
    Integer.parseInt("0x1F");
} catch (NumberFormatException e) {
    IO.println(e.getMessage());             // For input string: "0x1F"
}

try {
    Integer.parseInt("1", 37);
} catch (NumberFormatException e) {
    IO.println(e.getMessage());             // radix 37 greater than Character.MAX_RADIX
}

Chú ý parseInt("0x1F") không tự hiểu tiền tố hex — radix phải truyền tường minh; muốn tự nhận 0x/# thì dùng decode (mục 11.1). Radix ngoài khoảng 2..36 cũng ném NFE với message riêng.

Unsigned: JDK có parseUnsignedInt/parseUnsignedLong đọc được giá trị vượt MAX_VALUE nhưng vẫn trong 32/64 bit — kết quả là bit pattern, in ra có thể âm:

IO.println(Integer.parseUnsignedInt("4294967295"));          // -1
IO.println(Integer.toUnsignedString(-1));                    // 4294967295
IO.println(Long.parseUnsignedLong("18446744073709551615"));  // -1
IO.println(Long.toUnsignedString(-1L));                      // 18446744073709551615
Unsigned trong Java chỉ là cách nhìn trên cùng bit pattern, không phải kiểu mới. Hợp cho dữ liệu nhị phân/protocol (IPv4, checksum); tính toán nghiệp vụ thường ngày nên tránh để khỏi nhầm dấu.

11.3 Lỗi thật và message của JDK 25

Gần như mọi lỗi parse đều là NumberFormatException (NFE) — kể cả null. Chạy thật từng trường hợp bằng helper nhỏ:

static void show(String label, Runnable r) {
    try {
        r.run();
    } catch (NumberFormatException e) {
        IO.println(label + " : " + e.getMessage());
    }
}

show("null", () -> Integer.parseInt(null));                // null : Cannot parse null string
show("12a", () -> Integer.parseInt("12a"));                // 12a : For input string: "12a"
show("12G radix 16", () -> Integer.parseInt("12G", 16));   // 12G radix 16 : For input string: "12G" under radix 16
show("overflow", () -> Integer.parseInt("999999999999"));  // overflow : For input string: "999999999999"
show("space", () -> Integer.parseInt(" 5"));               // space : For input string: " 5"
show("trailing", () -> Integer.parseInt("5 "));            // trailing : For input string: "5 "
show("underscore", () -> Integer.parseInt("1_000"));       // underscore : For input string: "1_000"
show("decimal", () -> Integer.parseInt("3.14"));           // decimal : For input string: "3.14"
show("plus", () -> Integer.parseInt("+"));                 // plus : For input string: "+"
  • parseInt(null) ném NumberFormatException Cannot parse null string, không phải NPE — code bắt NPE sẽ hụt. Ngược lại Double.parseDouble(null) lại ném NPE — API không đồng nhất, đừng đoán.
  • Message mặc định chỉ có "For input string: ..."; chỉ khi radix khác 10 mới thêm "under radix N". Đừng hardcode message để phân loại lỗi — hãy kiểm tra dữ liệu trước.
  • Tràn khoảng cũng là NFE, không kẹp giá trị: "999999999999" vượt Integer.MAX_VALUE. Giá trị lớn hơn chuyển sang Long.parseLong hoặc BigInteger (mục 12).
  • parseXxx không trim: khoảng trắng đầu/cuối đều gây lỗi, trong khi Double.parseDouble lại tự trim (mục 11.4) — càng thêm lý do luôn trim() dữ liệu người dùng trước khi parse (mục 11.6).
  • Dấu gạch dưới 1_000 chỉ hợp lệ trong literal (int x = 1_000;), còn trong chuỗi parse là NFE. Đừng nhầm hai ngữ cảnh.

11.4 Các kiểu khác: double, boolean, enum

IO.println(Double.parseDouble("3.14"));       // 3.14
IO.println(Double.parseDouble("NaN"));        // NaN
IO.println(Double.parseDouble("Infinity"));   // Infinity
IO.println(Double.parseDouble("-Infinity"));  // -Infinity
IO.println(Double.parseDouble("0x1.8p1"));    // 3.0
IO.println(Double.parseDouble("1e3"));        // 1000.0
IO.println(Double.parseDouble(" 1.5 "));      // 1.5  - tu trim
IO.println(Boolean.parseBoolean("TRUE"));     // true
IO.println(Boolean.parseBoolean("yes"));      // false
IO.println(Character.digit('F', 16));         // 15
IO.println(Character.digit('G', 16));         // -1
IO.println(Character.valueOf('a'));           // a
  • Double.parseDouble hào phóng hơn parseInt: nhận "NaN", "Infinity" (phân biệt hoa thường — "nan" ném NFE), ký pháp khoa học 1e3, cả hex float 0x1.8p1 = 3.0, và tự trim khoảng trắng. Vì vậy "parseDouble không lỗi" không đồng nghĩa "số hợp lệ" — còn phải loại NaN/Infinity nữa.
  • Boolean.parseBoolean chỉ trả true khi chuỗi là "true" (không phân biệt hoa thường); mọi thứ khác — kể cả null, " true" — trả false và không bao giờ ném lỗi. Lỗi chính tả trong config sẽ âm thầm thành false.
  • Không có Character.parseCharacter; dùng Character.digit(c, radix) (trả -1 nếu không hợp lệ) hoặc charAt(0) kèm validate độ dài chuỗi.

enum có valueOf riêng, nghiêm hơn hẳn:

enum Color { RED, GREEN }

IO.println(Color.valueOf("RED"));   // RED

Color.valueOf("red");
// IllegalArgumentException: No enum constant Color.red

Color.valueOf(null);
// NullPointerException: Name is null
Enum valueOf phân biệt hoa thường: sai tên → IllegalArgumentException, null → NullPointerException. Giá trị đọc từ API/DB vì vậy cần bọc try/catch hoặc map tường minh (thường viết helper fromString trong enum) — đừng để một chuỗi sai làm nổ 500.

11.5 Locale & định dạng số

parseXxx của JDK chỉ hiểu dạng "máy" (1234567.89, dấu chấm thập phân, không grouping). Chuỗi người dùng nhập theo từng nước — 1,234.5 (US) hay 1.234,5 (Đức/Việt) — phải qua NumberFormat:

NumberFormat us = NumberFormat.getInstance(Locale.US);
NumberFormat de = NumberFormat.getInstance(Locale.GERMANY);
NumberFormat vi = NumberFormat.getInstance(Locale.of("vi", "VN"));

IO.println(us.format(1234567.89));    // 1,234,567.89

  • Locale.of("vi", "VN") (Java 19+) tạo locale tường minh; đừng dựa vào Locale.getDefault() cho dữ liệu client — locale server có thể khác máy người dùng và đổi giữa các môi trường deploy.
  • NumberFormat.parse lenient: gặp ký tự lạ thì dừng và trả phần đã đọc, không ném lỗi. Muốn bắt buộc đọc hết chuỗi, dùng ParsePosition và kiểm tra getIndex():
ParsePosition pos = new ParsePosition(0);

DecimalFormat khi cần pattern tường minh (số chữ số, kiểu tiền tệ) — nhớ chỉ định DecimalFormatSymbols để không phụ thuộc locale mặc định của máy chạy:

DecimalFormat fmt = new DecimalFormat("#,##0.00",
        DecimalFormatSymbols.getInstance(Locale.US));
IO.println(fmt.format(1234.5));   // 1,234.50
Nhớ: Integer.parseInt("1,000") luôn ném NFE vì parseXxx của JDK không biết grouping. Grouping chỉ là chuyện hiển thị/nhập liệu; trong DB/API vẫn lưu dạng số 1000 và format ở tầng biên.

11.6 Production pattern: parse ở biên

Nguyên tắc: parse một lần ở biên (controller, config loader) rồi truyền kiểu đã sạch vào trong; không rải parseInt trong business logic. Cấu hình sai thì fallback, input người dùng sai thì báo lỗi rõ:

static Optional<Integer> parseIntSafe(String raw) {
    if (raw == null || raw.isBlank()) {
        return Optional.empty();
    }
    try {
        return Optional.of(Integer.parseInt(raw.trim()));
    } catch (NumberFormatException e) {
        return Optional.empty();
    }
}

static int port(String raw) {
    int p = parseIntSafe(raw).orElse(8080);
    if (p < 1 || p > 65535) {
        throw new IllegalArgumentException("port khong hop le: " + p);
    }
    return p;
}

IO.println(parseIntSafe("42"));     // Optional[42]
IO.println(parseIntSafe("abc"));    // Optional.empty
IO.println(parseIntSafe(null));     // Optional.empty
IO.println(parseIntSafe("  "));     // Optional.empty
IO.println(port(" 9090 "));         // 9090
IO.println(port(""));               // 8080
port("70000");
// IllegalArgumentException: port khong hop le: 70000
  • Đừng catch rỗng (catch (NumberFormatException e) {}) — nuốt lỗi khiến dữ liệu sai chạy tiếp. Trả Optional/giá trị mặc định có chủ đích, hoặc ném IllegalArgumentException kèm tên field và giá trị sai.
  • Validate khoảng ngay sau parse: parse thành công chưa chắc hợp lệ nghiệp vụ (tuổi âm, port > 65535, page size quá lớn).
  • Config từ env: fallback + log cảnh báo; input API: trả 400. Hai ngữ cảnh, hai chiến lược — xem thêm Production patterns (mục 13.1).
  • Vượt 32-bit dùng Long.parseLong; vượt 64-bit hoặc cần chính xác tuyệt đối dùng BigInteger (mục 12). Cẩn thận tràn int khi cộng dồn (Biến trong Java — mục 9).

Góc Node.js

  • Number.parseInt("12px") = 12 (đọc tới ký tự lạ rồi dừng); Integer.parseInt("12px") ném NFE. JS "dễ tính" nên lỗi hay bị bỏ qua; Java nghiêm nên buộc phải xử lý.
  • Number("") = 0 và Number(" ") = 0 (!), Number("12px") = NaN; Java cả ba đều NFE. JS kiểm tra bằng Number.isNaN, Java dùng try/catch.
  • Number("0x1F") = 31 (tự nhận hex); Java parseInt("0x1F") ném NFE — phải dùng decode hoặc radix 16.
  • Cả hai ngôn ngữ đều cho gạch dưới trong literal (1_000 = 1000) nhưng không trong chuỗi parse: Number.parseInt("1_000") = 1, Java NFE.
  • BigInt("42") cho số nguyên lớn; BigInt("12.5") ném SyntaxError; BigInt không trộn được với Number (xem mục 12).
Chốt gọn: tính toán → parseInt/parseLong; cần object/null → valueOf; chuỗi tự mô tả hệ đếm (0x, #, 0 bát phân) → decode → luôn bọc try/catch NFE (kể cả null) → trim() trước parse, validate khoảng sau parse → chuỗi có grouping/locale phải qua NumberFormat, không qua parseXxx.

12. BigInteger chuyên sâu — khi long không đủ Hay hỏi phỏng vấn Production

long chỉ chứa đến 263 − 1 ≈ 9.22×1018, và tràn thì quay vòng âm thầm (xem Biến trong Java — mục 9). Khi số nguyên cần vượt ngưỡng đó, hoặc cần chính xác tuyệt đối cho hash/crypto, dùng BigInteger. Mục này song song với BigDecimal chuyên sâu (Biến trong Java — mục 13): cùng bất biến, cùng bẫy "quên gán lại", nhưng khác hẳn chuyện equals.

12.1 Khi nào long không đủ

Bốn nhóm tình huống thực tế:

  • Vượt 263 − 1: giai thừa, tổ hợp, dãy Fibonacci, lũy thừa lớn.
  • Hash/checksum: MD5 (128-bit), SHA-1 (160-bit), SHA-256 (256-bit) — đều dài hơn 64-bit.
  • Crypto: RSA, Diffie-Hellman tính trên số vài trăm tới vài nghìn bit; một khóa 2048-bit không lọt vào long.
  • ID và tính toán dài: định danh 128-bit, tổng/tích dồn cần đúng từng chữ số.
long maxL = Long.MAX_VALUE;
IO.println(maxL);            // 9223372036854775807
IO.println(maxL + 1);        // -9223372036854775808  - tran quay vong

IO.println(BigInteger.TWO.pow(63).subtract(BigInteger.ONE));   // 9223372036854775807
IO.println(BigInteger.TWO.pow(100));   // 1267650600228229401496703205376

BigInteger f = BigInteger.ONE;
for (int i = 2; i <= 50; i++) {
    f = f.multiply(BigInteger.valueOf(i));
}
IO.println(f);
// 30414093201713378043612608166064768844377641568960512000000000000

BigInteger f100 = BigInteger.ONE;
for (int i = 2; i <= 100; i++) {
    f100 = f100.multiply(BigInteger.valueOf(i));
}
IO.println(f100.toString().length());   // 158 - 100! co 158 chu so

BigInteger c50 = BigInteger.ONE;
for (int i = 1; i <= 25; i++) {
    c50 = c50.multiply(BigInteger.valueOf(50 - i + 1)).divide(BigInteger.valueOf(i));
}
IO.println(c50);             // 126410606437752 - C(50,25)
Đừng "phòng thủ" quá sớm: BigInteger chậm hơn long hàng chục lần và tạo nhiều object. Chỉ dùng khi thật sự vượt 64-bit hoặc cần chính xác tuyệt đối; phần lớn nghiệp vụ tiền tệ VN chỉ cần long theo đơn vị đồng.

12.2 Tạo và chuyển đổi

Ba cách tạo, cùng các chuyển đổi hai chiều giữa BigInteger với long/byte[]/String:

BigInteger a = BigInteger.valueOf(100);         // tu long: nhanh nhat
BigInteger b = new BigInteger("123456789012345678901234567890");
BigInteger c = new BigInteger("ff", 16);        // 255
BigInteger d = new BigInteger("1010", 2);       // 10
BigInteger e = new BigInteger("zz", 36);        // 1295
IO.println(c + " " + d + " " + e);              // 255 10 1295
IO.println(b.multiply(BigInteger.TWO));
// 246913578024691357802469135780

byte[] raw = BigInteger.valueOf(255).toByteArray();
IO.println(Arrays.toString(raw));    // [0, -1] - them byte 0 de giu dau
IO.println(new BigInteger(raw));     // 255
IO.println(new BigInteger(new byte[] { (byte) 0xFF }));   // -1 - doc co dau!

BigInteger tooBig = new BigInteger("9223372036854775808");   // 2^63
IO.println(tooBig.longValue());      // -9223372036854775808 - tran am tham
try {
    tooBig.longValueExact();
} catch (ArithmeticException ex) {
    IO.println(ex.getMessage());     // BigInteger out of long range
}
try {
    tooBig.intValueExact();
} catch (ArithmeticException ex) {
    IO.println(ex.getMessage());     // BigInteger out of int range
}
IO.println(BigInteger.valueOf(42).intValueExact());   // 42

IO.println(BigInteger.valueOf(255).toString(16));     // ff
IO.println(BigInteger.valueOf(255).toString(2));      // 11111111
IO.println(BigInteger.valueOf(255).toString(36));     // 73
IO.println(BigInteger.valueOf(-255).toString(16));    // -ff
  • toByteArray() dùng bù hai (two's complement) và có thể thêm một byte 0x00 ở đầu để giữ dấu — nên 255 thành [0, -1], không phải [-1]. Khi đọc lại, nếu chắc chắn là số không âm (hash), dùng new BigInteger(1, bytes) — byte dấu bị bỏ và luôn ra số dương.
  • intValue()/longValue() cắt bit thấp và không báo tràn; ở biên API/DB hãy dùng intValueExact()/longValueExact() để ném ArithmeticException thay vì nhận giá trị sai.
  • BigInteger.valueOf(long) nhanh hơn parse chuỗi; constructor nhận String + radix theo đúng luật ở mục 11.2 (không nhận tiền tố 0x, chuỗi rỗng/sai ném NFE).
  • toString(radix) in hệ đếm 2..36, số âm có dấu trừ đứng trước (-ff).
Parse lỗi khác Integer: new BigInteger("12a") ném NFE For input string: "12a"; chuỗi rỗng ném NFE Zero length BigInteger; new BigInteger(null) ném NullPointerException (không phải NFE); radix ngoài 2..36 ném NFE Radix out of range.

12.3 Số học — method, không toán tử

Không có +, * cho object; mọi phép tính là method và trả object mới (bất biến):

BigInteger a = BigInteger.valueOf(100);
BigInteger b = BigInteger.valueOf(7);
IO.println(a.add(b));        // 107
IO.println(a.subtract(b));   // 93
IO.println(a.multiply(b));   // 700
IO.println(a.divide(b));     // 14
IO.println(a.remainder(b));  // 2

BigInteger[] qr = a.divideAndRemainder(b);
IO.println(qr[0] + " du " + qr[1]);   // 14 du 2

IO.println(BigInteger.TWO.pow(100));  // 1267650600228229401496703205376
IO.println(BigInteger.valueOf(3).modPow(BigInteger.valueOf(100), BigInteger.valueOf(7)));   // 4
IO.println(BigInteger.valueOf(3).modInverse(BigInteger.valueOf(7)));   // 5
IO.println(BigInteger.valueOf(48).gcd(BigInteger.valueOf(36)));        // 12
IO.println(BigInteger.valueOf(1000000).sqrt());   // 1000 - Java 9+
IO.println(BigInteger.valueOf(2).sqrt());         // 1

IO.println(BigInteger.valueOf(-7).divide(BigInteger.valueOf(2)));      // -3
IO.println(BigInteger.valueOf(-7).remainder(BigInteger.valueOf(2)));   // -1
IO.println(BigInteger.valueOf(-5).abs());        // 5
IO.println(BigInteger.valueOf(5).negate());      // -5

BigInteger total = BigInteger.TEN;
total.add(BigInteger.ONE);                       // quen gan
IO.println(total);                               // 10
total = total.add(BigInteger.ONE);               // gan lai
IO.println(total);                               // 11
  • Chia cắt về 0 giống int/long: -7 / 2 = -3, -7 % 2 = -1 — khác Python (làm tròn xuống, dư dương).
  • divideAndRemainder trả [thương, dư] trong một lần tính, hiệu quả hơn gọi divide rồi remainder.
  • modPow tính lũy thừa modular không tạo số trung gian khổng lồ — trái tim crypto ở mục 12.6. modInverse ném ArithmeticException: BigInteger not invertible. khi không tồn tại nghịch đảo (ví dụ 4 và 10).
  • sqrt (Java 9+) là căn nguyên, làm tròn xuống: sqrt(2) = 1. Còn abs/negate trả object mới như mọi method khác.
  • Quên gán lại là bug im lặng y hệt BigDecimal — total.add(...) không làm gì với total.

12.4 Thao tác bit

BigInteger xử lý bit như số nguyên dài vô hạn theo bù hai — tiện cho bitmask, cờ trạng thái, subnet:

BigInteger n = BigInteger.valueOf(180);   // 1011 0100
IO.println(n.bitLength());   // 8   - so bit toi thieu (khong tinh dau)
IO.println(n.bitCount());    // 4   - so bit 1
IO.println(n.testBit(2));    // true
IO.println(n.testBit(3));    // false
IO.println(n.setBit(0));     // 181
IO.println(n.clearBit(2));   // 176
IO.println(n.flipBit(2));    // 176
IO.println(n.shiftLeft(2));  // 720
IO.println(n.shiftRight(2)); // 45

BigInteger p = BigInteger.valueOf(12);   // 1100
BigInteger q = BigInteger.valueOf(10);   // 1010
IO.println(p.and(q));   // 8
IO.println(p.or(q));    // 14
IO.println(p.xor(q));   // 6
IO.println(p.not());    // -13 - bu hai tren vo han bit

IO.println(BigInteger.valueOf(40).getLowestSetBit());   // 3
IO.println(BigInteger.ZERO.getLowestSetBit());          // -1

BigInteger low4 = n.and(BigInteger.ONE.shiftLeft(4).subtract(BigInteger.ONE));
IO.println(low4);            // 4 - lay 4 bit thap nhat
IO.println(n.testBit(0));    // false - n chan
  • Bit đánh số từ 0 (thấp nhất). not cho số âm vì bù hai vô hạn — đừng so với đảo bit kiểu cố định 32/64 bit.
  • getLowestSetBit() trả số bit 0 đứng trước bit 1 đầu tiên (số mũ của 2 chia hết n), -1 nếu n = 0. Kiểm tra chẵn/lẻ bằng testBit(0) nhanh hơn remainder(TWO).
  • Mask k bit thấp: x.and(BigInteger.ONE.shiftLeft(k).subtract(BigInteger.ONE)). Bitmask, cờ quyền, subnet... đều gói trong vài dòng.

12.5 So sánh — equals theo giá trị (khác BigDecimal!)

BigInteger a = new BigInteger("1000");
BigInteger b = new BigInteger("1000");
IO.println(a.equals(b));     // true  - so theo gia tri
IO.println(a == b);          // false - hai object khac nhau
IO.println(a.compareTo(b));  // 0
IO.println(a.compareTo(new BigInteger("999")));   // 1

IO.println(BigInteger.valueOf(-7).signum());   // -1
IO.println(BigInteger.ZERO.signum());          // 0
IO.println(BigInteger.valueOf(7).signum());    // 1

Map<BigInteger, String> map = new HashMap<>();
map.put(a, "a");
map.put(b, "b");
IO.println(map.size());      // 1 - equals consistent voi compareTo

Map<BigInteger, String> tree = new TreeMap<>();
tree.put(a, "a");
tree.put(b, "b");
IO.println(tree.size());     // 1 - compareTo = 0 nen gop lam mot

Đây là điểm BigInteger dễ thở hơn BigDecimal: equals so theo giá trị (không có scale) và consistent với compareTo, nên dùng làm key HashMap hay TreeMap đều cho cùng kết quả — khác bẫy 1.0 vs 1.00 của BigDecimal (mục 13.6). Quy tắc vẫn là: == luôn sai, so bằng dùng .equals(), cần thứ tự dùng compareTo. Lưu ý nhỏ: BigInteger.valueOf(5) == BigInteger.valueOf(5) là true nhờ cache −16..16 của JDK, nhưng đừng bao giờ dựa vào đó.

12.6 Số nguyên tố & crypto

BigInteger mang sẵn các phép nguyên tố và modular dùng cho mật mã:

BigInteger p = BigInteger.valueOf(97);
IO.println(p.isProbablePrime(100));                       // true
IO.println(BigInteger.valueOf(91).isProbablePrime(100));  // false
IO.println(p.nextProbablePrime());                        // 101

Random rnd = new Random(42);
BigInteger r = BigInteger.probablePrime(64, rnd);
IO.println(r.isProbablePrime(100) + " " + r.bitLength()); // true 64

// Demo RSA nho: n = 61 * 53, e = 17, d = 2753
BigInteger m = BigInteger.valueOf(65);     // ky tu 'A'
BigInteger c = m.modPow(BigInteger.valueOf(17), BigInteger.valueOf(3233));
IO.println(c);                             // 2790
IO.println(c.modPow(BigInteger.valueOf(2753), BigInteger.valueOf(3233)));   // 65
  • isProbablePrime(certainty): xác suất "thực ra là hợp số" < 2-certainty. Dùng làm ước lượng nhanh; số nguyên tố cho khóa phải sinh bằng probablePrime với SecureRandom, không tự chế.
  • nextProbablePrime() trả số nguyên tố kế tiếp lớn hơn n — tiện chọn kích thước hash table.
  • modPow(base, exp, mod) là phép tính trung tâm của RSA/Diffie-Hellman: demo chỉ minh hoạ công thức c = me mod n, không phải code mã hoá thật. Production dùng JCA/BouncyCastle, đừng tự viết crypto.

12.7 Performance & bẫy

  • Chỉ dùng khi cần: BigInteger chậm hơn primitive hàng chục lần và tạo nhiều rác. Cộng dồn triệu phần tử bằng BigInteger là anti-pattern; nếu giá trị chắc chắn trong 64-bit, dùng long (kèm Math.addExact để phát hiện tràn — xem Biến trong Java — mục 9).
  • Bất biến: luôn gán lại kết quả; method không sửa object hiện tại (giống BigDecimal).
  • Parse: lỗi định dạng/độ dài/radix đều là NFE; null lại là NPE — message thật ở mục 12.2, cách xử lý an toàn ở mục 11.6.
  • So sánh: == so reference, luôn dùng equals/compareTo (mục 12.5). Ngoài ra longValue() không báo tràn — dùng longValueExact() ở biên.

13. Production patterns

13.1 Parse cấu hình an toàn — không để app chết vì env sai

static int pageSize(String raw, int fallback) {
    if (raw == null || raw.isBlank()) {
        return fallback;
    }
    try {
        return Integer.parseInt(raw.trim());
    } catch (NumberFormatException e) {
        return fallback;
    }
}

IO.println("pageSize(null, 20) : " + pageSize(null, 20));   // 20
IO.println("pageSize(\" 50 \")   : " + pageSize(" 50 ", 20)); // 50
IO.println("pageSize(\"abc\")    : " + pageSize("abc", 20));  // 20

Dữ liệu từ input người dùng thì ngược lại: không fallback âm thầm, phải báo lỗi rõ ràng (IllegalArgumentException với message cụ thể) để API trả về 400 thay vì chạy sai.

13.2 ID và timestamp: long, và cẩn thận khi qua JavaScript

long id = Long.parseLong("9007199254740993");   // 2^53 + 1
IO.println("long id > 2^53     : " + id);        // 9007199254740993

JavaScript chỉ giữ chính xác số nguyên đến 2^53, nên ID long gửi dạng number trong JSON sẽ bị làm tròn ở client (2^53 + 1 → 9007199254740992). Production thường serialize ID thành string trong JSON — nhớ khi viết DTO ở giai đoạn 5 (Jackson, mục 5.2 của lộ trình).

15. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. JLS định nghĩa mấy ngữ cảnh chuyển kiểu? Kể tên.
5 ngữ cảnh: assignment, method invocation, casting, numeric promotion, string concatenation. Mỗi ngữ cảnh cho phép bộ chuyển đổi khác nhau — cùng phép chuyển có thể hợp lệ ở ngữ cảnh này nhưng bị từ chối ở ngữ cảnh khác.
Câu 2. Widening conversion có luôn an toàn không?
Không. Với số nguyên nhìn chung an toàn, nhưng int → float và long → double có thể mất chữ số vì float chỉ giữ 24 bit định trị, double giữ 53 bit. Ví dụ (float) 16_777_217 ra 1.6777216E7.
Câu 3. Vì sao byte b = 100; hợp lệ nhưng byte b = 200; thì không?
100 là hằng số nằm trong khoảng của byte (-128..127) nên được ngầm narrowing; 200 vượt khoảng nên bị từ chối với lỗi "possible lossy conversion". Cùng luật đó cho phép final int y = 3; byte z = y;.
Câu 4. Vì sao byte + byte lại ra int?
Numeric promotion: byte, short, char được nâng lên int trước khi tính toán (unary promotion), nên kết quả là int. Muốn gán lại vào byte phải ép: (byte) (b1 + b2).
Câu 5. b += 1 khác b = b + 1 thế nào khi b là byte?
b += 1 tương đương b = (byte) (b + 1) — có ép kiểu ngầm nên compile được. b = b + 1 thất bại vì b + 1 là int.
Câu 6. (int) 3.99 và (int) -3.99 cho gì?
3 và -3. Narrowing từ số thực cắt phần thập phân (làm tròn về 0), không làm tròn số học. Muốn làm tròn dùng Math.round().
Câu 7. (byte) 130 bằng bao nhiêu? Giải thích.
-126. 130 vượt 127 nên quay vòng theo bù hai: 130 - 256 = -126. Ép kiểu số nguyên không ném lỗi tràn, chỉ giữ 8 bit thấp nhất.
Câu 8. true ? 1 : 2.0 có kiểu gì?
double — int được nâng lên double trước. Kết quả in ra 1.0 chứ không phải 1.
Câu 9. 1 + 2 + "x" và "x" + 1 + 2 khác nhau thế nào?
Toán tử + chạy trái sang phải. 1 + 2 + "x" = "3x" (cộng số trước); "x" + 1 + 2 = "x12" (nối chuỗi trước, sau đó mọi thứ thành chuỗi).

Nâng cao (Junior+)

Câu 10. Khi nào flag ? boxed : 0 ném NPE, khi nào không?
Biểu thức có một nhánh primitive (0) nên kiểu kết quả là primitive, và chỉ nhánh được chọn mới bị unbox. Với flag == true và boxed == null: NPE. Với flag == false: trả về 0, không đụng tới boxed nên không lỗi. Nếu cả hai nhánh đều là wrapper thì không có unbox — kết quả có thể là null.
Câu 11. Vì sao Long a = 10; không compile, nhưng long b = Integer.valueOf(5); compile?
Assignment context không cho phép "widening rồi boxing" (int → long → Long). Chiều ngược lại thì được: unboxing trước rồi widening (Integer → int → long) là chuỗi hợp lệ. Nếu cần Long từ literal int, viết Long a = 10L;.
Câu 12. Overload resolution xét theo thứ tự nào? Cho ví dụ.
3 phase: (1) chỉ widening/không boxing, (2) cho phép boxing/unboxing, (3) cho phép varargs. Ví dụ có onlyLong(long) và onlyLong(Integer), gọi onlyLong(1) sẽ chọn bản long vì phase 1 thắng phase 2.
Câu 13. (int) Double.NaN và (int) 1e20 cho gì?
NaN → 0; 1e20 → Integer.MAX_VALUE (2147483647). Luật JLS: NaN thành 0, giá trị quá lớn kẹp về MAX, quá nhỏ kẹp về MIN — khác wraparound của ép kiểu số nguyên.
Câu 14. parseInt và valueOf khác nhau thế nào?
Integer.parseInt trả int primitive; Integer.valueOf trả Integer và dùng cache -128..127 nên cùng giá trị nhỏ sẽ trả cùng object. Cả hai đều ném NumberFormatException khi chuỗi sai định dạng hoặc vượt khoảng.
Câu 15. Integer.parseInt(null) ném gì?
NumberFormatException với message "Cannot parse null string" — không phải NullPointerException. Đây là bẫy khi code parse dữ liệu chưa kiểm tra null.
Câu 16. Khi nào cần BigInteger? Nó khác BigDecimal ở đâu?
Khi số nguyên cần vượt 64-bit hoặc phải chính xác tuyệt đối (hash, mã hóa, toán lớn). BigInteger là số nguyên chính xác; BigDecimal là số thập phân với scale — dùng cho tiền tệ. Cả hai đều bất biến, mọi phép tính trả object mới.
Câu 17. Vì sao ID kiểu long nên gửi dạng string trong JSON?
JavaScript chỉ biểu diễn chính xác số nguyên đến 2^53. ID long lớn hơn (snowflake ID, ID từ DB lớn dần) sẽ bị làm tròn khi client parse JSON number. Serialize thành string tránh mất mát — thường cấu hình ở tầng Jackson/Jackson 3.

Câu hỏi khó

Câu 18. Vì sao float f = 16_777_217; lại mất 1 đơn vị?
16_777_217 = 2^24 + 1. float có 24 bit phần định trị nên chỉ biểu diễn chính xác số nguyên đến 2^24; vượt ngưỡng sẽ làm tròn về bội số gần nhất. Kết quả in ra 1.6777216E7.
Câu 19. Kể 3 trường hợp hàng ngày mà Java chuyển kiểu ngầm mà không cần ép.
(1) widening khi gán (int i = 'a'); (2) boxing/unboxing (Integer x = 5; int y = x;); (3) numeric promotion khi tính (byte + int → int). Ngoài ra còn nối chuỗi và hằng số vừa khoảng.
Câu 20. Trong method invocation, khi nào int được truyền vào tham số Integer mà không cần boxing tường minh?
Luôn được — đó là boxing conversion tự động (assignment context và invocation context đều cho phép). Nhưng nếu overload có cả long lẫn Integer, bản long sẽ được chọn vì widening thuộc phase 1, boxing thuộc phase 2.
