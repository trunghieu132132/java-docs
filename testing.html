1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Mức độ bắt buộc của chủ đề 4.4 (phỏng vấn: rất cao · production: bắt buộc):

  • Phải làm được — viết test JUnit 5 với @Test, assertion, @BeforeEach; parameterized test; mock dependency bằng Mockito và verify tương tác; chạy test bằng Maven trong IDE/CI.
  • Phải hiểu — vì sao mỗi test phải độc lập; AAA; vòng đời test instance; test double (mock/stub/spy/fake); unit test vs integration test; coverage nói gì và không nói gì; TDD.
  • Nhận biết — AssertJ nâng cao, JaCoCo, Testcontainers, Spring Boot slice test, @MockitoBean thay @MockBean, Awaitility cho test bất đồng bộ.

Vì sao phải viết test?

  • Bắt regression — sửa chỗ này làm vỡ chỗ khác là chuyện thường ngày; test chạy trong vài giây sẽ chỉ ra ngay thay vì để bug ra production.
  • Tự tin refactor — không có test, "dọn code" là canh bạc. Có test, bạn đổi cấu trúc bên trong thoải mái miễn hành vi không đổi.
  • Tài liệu sống — test mô tả chính xác method nhận gì, trả gì, ném lỗi khi nào; khác comment, test cũ đi là fail ngay nên không thể "nói dối".
  • Cổng chất lượng cho CI — pipeline chạy mvn test; test đỏ thì không cho merge. Đây là cách duy nhất để một nhóm nhiều người giữ chất lượng.
  • Thiết kế tốt hơn — code khó test thường là code dính chặt (hard-coded new, static, thời gian hệ thống). Viết test trước buộc bạn tách dependency ra, thường là thiết kế tốt hơn.

Ba tầng test với tỷ lệ và chi phí rất khác nhau. Viết nhiều test ở tầng rẻ, nhanh; chỉ giữ một ít test đầu-cuối:

Vì không có project thật trong trang nên không có output chạy thật; chỗ nào ghi Tests run: … là mô tả dạng dòng tổng kết của Maven Surefire khi mọi test pass.

Cách học hiệu quả nhất

  1. Đọc mục 2–3 rồi tự viết test cho đúng những method bạn từng viết ở các chủ đề trước (Calculator, tính tiền đơn hàng).
  2. Làm mục Bài tập theo thứ tự; mỗi bài tự viết trước khi mở đáp án.
  3. Học Mockito (mục 5) bằng cách lấy chính OrderService của dự án "quản lý đơn hàng" ra mock repository.
  4. Trước phỏng vấn, ôn Cheat sheet và các câu ở Interview Q&A.
  5. Bật coverage (mục 8) một lần để thấy chỗ trống — nhưng đừng lấy nó làm mục tiêu.

2. JUnit 5 cơ bản — @Test & assertions Junior+

JUnit 5 là thư viện test chuẩn của Java hiện đại, gồm 3 phần: JUnit Platform (nền tảng chạy test), JUnit Jupiter (API mới với @Test, assertions — phần bạn dùng hằng ngày) và JUnit Vintage (chạy test JUnit 4 cũ, mức nhận biết). Maven chỉ cần đúng artifact tổng junit-jupiter là có đủ.

Một test method có dạng tối giản sau — không cần main, không cần in ra gì:

@Test @DisplayName("mô tả") void tenMethod() { /* Arrange - Act - Assert */ }

Test đầu tiên — Calculator & CalculatorTest

Quy ước: code cần test nằm ở src/main/java, test nằm ở src/test/java cùng package (chi tiết ở mục 12). Class dưới test:

import java.math.BigDecimal;

class Calculator {
    int add(int a, int b) {
        return a + b;
    }

    int divide(int a, int b) {
        if (b == 0) {
            throw new ArithmeticException("chia cho 0");
        }
        return a / b;
    }

    BigDecimal giaSauGiam(BigDecimal gia, int phanTramGiam) {
        if (gia == null || gia.signum() < 0) {
            throw new IllegalArgumentException("gia khong hop le");
        }
        if (phanTramGiam < 0 || phanTramGiam > 100) {
            throw new IllegalArgumentException("phan tram giam khong hop le: " + phanTramGiam);
        }
        BigDecimal giam = gia.multiply(BigDecimal.valueOf(phanTramGiam))
                .divide(BigDecimal.valueOf(100));
        return gia.subtract(giam);
    }
}

Và test tương ứng. Chú ý test class để package-private, tên method là câu mô tả hành vi:

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import java.math.BigDecimal;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

class CalculatorTest {
    private final Calculator calculator = new Calculator();

    @Test
    @DisplayName("2 + 3 = 5")
    void add_haiSoDuong_traVeTong() {
        assertEquals(5, calculator.add(2, 3));
    }

    @Test
    void divide_chiaChoKhong_nemArithmeticException() {
        ArithmeticException ex = assertThrows(
                ArithmeticException.class,
                () -> calculator.divide(10, 0));
        assertEquals("chia cho 0", ex.getMessage());
    }

    @Test
    void giaSauGiam_10PhanTram_traVe180000() {
        BigDecimal ketQua = calculator.giaSauGiam(new BigDecimal("200000"), 10);
        assertEquals(0, new BigDecimal("180000").compareTo(ketQua));
    }
}
// mvn test -> Tests run: 3, Failures: 0, Errors: 0, Skipped: 0

Ba điều cần nhớ ngay từ ví dụ:

  • assertEquals(expected, actual) — expected đứng trước. Đặt ngược vẫn pass/fail đúng nhưng khi fail message sẽ ngược (expected: giá trị thực tế), gây hoang mang.
  • Với BigDecimal, assertEquals so sánh cả scale: 180000 không equals 180000.0. Cách đúng là so bằng compareTo(...) == 0, hoặc dùng AssertJ isEqualByComparingTo (mục 6).
  • assertThrows(LoạiLỗi.class, lambda) trả về exception để bạn kiểm tra tiếp getMessage(). Lambda phải là biểu thức không trả về gì (kiểu Executable) — đừng truyền method có return.

assertAll đặc biệt hữu ích khi một kết quả có nhiều thứ để kiểm tra: nếu không gộp, assertion đầu fail sẽ dừng test ngay và bạn phải sửa rồi chạy lại mới thấy lỗi tiếp theo.

@Test

Vòng đời test: @BeforeEach, @AfterEach, @BeforeAll, @AfterAll

Bốn annotation lo phần setup/cleanup. Điểm phải nhớ: @BeforeAll/@AfterAll chạy một lần cho cả class nên phải là static (trừ khi dùng @TestInstance(PER_CLASS)); còn @BeforeEach/@AfterEach chạy quanh từng test.

class LifecycleTest {
    @BeforeAll
    static void chayMotLanTruocTatCa() {
        // mo tai nguyen dung chung: connection, file mau, server test (phai static)
    }

    @BeforeEach
    void chayTruocMoiTest() {
        // tao du lieu sach cho tung test: list rong, object moi
    }

    @AfterEach
    void chaySauMoiTest() {
        // don dep: xoa file tam, reset state
    }

    @AfterAll
    static void chayMotLanSauTatCa() {
        // dong tai nguyen dung chung
    }

    @Test
    void testThuNhat() { }

    @Test
    @Disabled("Cho tinh nang moi, bat lai khi lam xong")
    void testChuaLam() { }
}

Vòng đời mặc định: mỗi test một instance mới

Đây là điều nhiều bạn mới học JUnit bất ngờ: JUnit không dùng chung một object test. Mặc định (PER_METHOD), mỗi test method JUnit tạo một instance mới của test class. Vì vậy field instance luôn là dữ liệu sạch cho từng test — bạn không cần "reset" gì cả:

class FreshInstanceTest {
    List<String> items = new ArrayList<>();

    @Test
    void test1_themPhanTu() {
        items.add("a");
        assertEquals(1, items.size());
    }

    @Test
    void test2_khongThayDuLieuCuaTestKhac() {
        // JUnit tao instance MOI cho moi test -> items luon rong
        assertEquals(0, items.size());
    }
}
// mvn test -> Tests run: 2, Failures: 0, Errors: 0, Skipped: 0

Hệ quả thực chiến: đừng dùng field static mutable trong test class — nó phá vỡ cơ chế cách ly này và tạo ra test phụ thuộc thứ tự (xem mục 11). Muốn chia sẻ state tốn kém giữa các test (hiếm khi cần), dùng @TestInstance(TestInstance.Lifecycle.PER_CLASS) — khi đó @BeforeAll không cần static nữa.

3. Parameterized test — một test, nhiều bộ dữ liệu Junior+

Khi nhiều case chỉ khác nhau ở dữ liệu mà logic kiểm tra giống hệt, đừng copy-paste nhiều test method — hãy dùng @ParameterizedTest. Mỗi bộ dữ liệu là một lần chạy riêng, fail ở case nào Surefire chỉ đúng case đó, và tên test hiển thị đủ tham số để bạn biết ngay.

Ba nguồn dữ liệu dùng nhiều nhất:

  • @ValueSource — một danh sách giá trị cùng kiểu (int, long, String, char, boolean...). Hợp với kiểm tra "mọi giá trị X đều chạy êm/đúng tính chất".
  • @CsvSource — nhiều cột, mỗi dòng một case; giá trị được tự chuyển kiểu sang tham số method (String → int, BigDecimal nếu bạn khai báo BigDecimal...). Tiện nhất cho bảng dữ liệu nhỏ. Dùng nháy đơn '...' nếu giá trị chứa dấu phẩy.
  • @MethodSource — trỏ tới một method static trả về Stream/Collection các Arguments. Dùng khi dữ liệu phức tạp, cần tính toán, hoặc muốn đặt tên case.

Ví dụ với chính Calculator.giaSauGiam — dùng bảng giá/giảm giá, đúng tinh thần "tính tiền đơn hàng":

import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.Arguments;
import org.junit.jupiter.params.provider.CsvSource;
import org.junit.jupiter.params.provider.MethodSource;
import org.junit.jupiter.params.provider.ValueSource;

import java.math.BigDecimal;
import java.util.stream.Stream;

import static org.junit.jupiter.api.Assertions.assertDoesNotThrow;
import static org.junit.jupiter.api.Assertions.assertEquals;

class CalculatorTest {
    private final Calculator calculator = new Calculator();

    @ParameterizedTest(name = "giam {0}% khong nem loi")
    @ValueSource(ints = {0, 1, 50, 100})
    void giaSauGiam_phanTramHopLe_chayEm(int phanTram) {
        assertDoesNotThrow(() ->
                calculator.giaSauGiam(new BigDecimal("100000"), phanTram));
    }

    @ParameterizedTest(name = "{0} giam {1}% = {2}")
    @CsvSource({
            "200000, 10, 180000",
            "120000, 25,  90000",
            "100000,  0, 100000",
            "100000, 100, 0"
    })
    void giaSauGiam_traVeDung(String gia, int phanTram, String mongDoi) {
        BigDecimal ketQua = calculator.giaSauGiam(new BigDecimal(gia), phanTram);
        assertEquals(0, new BigDecimal(mongDoi).compareTo(ketQua));
    }

    @ParameterizedTest
    @MethodSource("duLieuChia")
    void divide_traVeThuong(int a, int b, int mongDoi) {
        assertEquals(mongDoi, calculator.divide(a, b));
    }

    static Stream<Arguments> duLieuChia() {
        return Stream.of(
                Arguments.of(10, 2, 5),
                Arguments.of(7, 2, 3),
                Arguments.of(-10, 2, -5),
                Arguments.of(0, 5, 0));
    }
}
// mvn test -> Tests run: 12, Failures: 0, Errors: 0, Skipped: 0
// (4 lan @ValueSource + 4 dong @CsvSource + 4 case @MethodSource)

Vài chi tiết thực chiến:

  • name = "{0} ..." là display name template: {index} là số thứ tự, {0}, {1}... là tham số. Đặt tên tốt giúp nhìn báo cáo biết ngay case nào sai.
  • @MethodSource("duLieuChia") bắt buộc method static (trừ khi class dùng PER_CLASS), và nếu method trùng tên với test method thì có thể bỏ chữ ("duLieuChia").
  • Chuyển kiểu của @CsvSource dùng conversion service của JUnit: int, long, boolean, enum... đều được. Nếu khai báo tham số là BigDecimal thì không tự convert — nên nhận String rồi new BigDecimal(...) như ví dụ, tường minh hơn.
  • Còn @EnumSource, @NullSource, @EmptySource (nhận biết) cho enum và case null/empty.
Đừng tham parameterized: nếu mỗi case cần logic kiểm tra khác nhau (case này assert message, case kia verify call), hãy viết test riêng — nhồi if/else trong parameterized test sẽ khó đọc hơn nhiều lần so với vài method tách biệt.

4. Viết test tốt — AAA & F.I.R.S.T. Hay hỏi phỏng vấn

Test chạy được chưa đủ; test còn phải dễ đọc, dễ sửa và đáng tin. Ba quy tắc dưới đây áp dụng cho mọi ngôn ngữ, và là thứ nhà tuyển dụng soi khi đọc test của bạn.

AAA — Arrange, Act, Assert

Một test tốt có 3 phần rõ ràng, nên cách nhau bằng dòng trống:

@Test
void giaSauGiam_10PhanTram_truDung() {
    // Arrange: chuan bi du lieu, khong chua logic nghiep vu
    Calculator calculator = new Calculator();
    BigDecimal gia = new BigDecimal("200000");

    // Act: MOT dong goi dung method can test
    BigDecimal sauGiam = calculator.giaSauGiam(gia, 10);

    // Assert: kiem tra ket qua mong doi
    assertEquals(0, new BigDecimal("180000").compareTo(sauGiam));
}
  • Arrange — dựng dữ liệu, mock, object. Nếu Arrange dài hơn 10 dòng, đó là tín hiệu nên tách builder/helper hoặc thiết kế lại API.
  • Act — gọi đúng một hành vi. Nếu phải gọi 2-3 method nghiệp vụ để test một thứ, bạn đang test quá nhiều trong một test.
  • Assert — kiểm tra kết quả, không kiểm tra cách làm (xem bên dưới).

5. Mockito — mock & verify Hay hỏi phỏng vấn

Unit test muốn nhanh và độc lập thì không được gọi DB, HTTP, file, đồng hồ hệ thống thật. Mockito tạo object giả cho các dependency đó: giả lập kết quả trả về (stub) và kiểm tra tương tác (verify).

Lấy đúng project "quản lý đơn hàng". Domain tối giản bằng record:

import java.math.BigDecimal;
import java.util.List;
import java.util.Optional;

record User(String email, String ten) { }

record Product(String ten, BigDecimal gia) { }

record Order(User user, List<Product> sanPham, BigDecimal tongTien) { }

interface OrderRepository {
    Order save(Order order);
    Optional<Order> findById(long id);
}

class OrderService {
    private final OrderRepository repository;

    OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    Order taoDon(User user, List<Product> sanPham) {
        if (user == null) {
            throw new IllegalArgumentException("Thieu nguoi mua");
        }
        if (sanPham == null || sanPham.isEmpty()) {
            throw new IllegalArgumentException("Don hang phai co san pham");
        }
        BigDecimal tong = sanPham.stream()
                .map(Product::gia)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
        return repository.save(new Order(user, List.copyOf(sanPham), tong));
    }

    Order layDon(long id) {
        return repository.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Khong tim thay don " + id));
    }
}

Test với đầy đủ vũ khí: @Mock, @InjectMocks, @ExtendWith(MockitoExtension.class), when/thenAnswer, verify và ArgumentCaptor:

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.ArgumentCaptor;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.math.BigDecimal;
import java.util.List;
import java.util.Optional;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertSame;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.ArgumentMatchers.anyLong;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.verifyNoInteractions;
import static org.mockito.Mockito.verifyNoMoreInteractions;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    OrderRepository repository;

    @InjectMocks
    OrderService service;

    @Test
    void taoDon_duLieuHopLe_luuVaTraVeDon() {
        User user = new User("an@example.com", "An");
        List<Product> sanPham = List.of(
                new Product("Ao thun", new BigDecimal("120000")),
                new Product("Quan jean", new BigDecimal("240000")));
        when(repository.save(any(Order.class)))
                .thenAnswer(invocation -> invocation.getArgument(0));

        Order order = service.taoDon(user, sanPham);

        assertEquals(0, new BigDecimal("360000").compareTo(order.tongTien()));
        ArgumentCaptor<Order> captor = ArgumentCaptor.forClass(Order.class);
        verify(repository).save(captor.capture());
        assertSame(user, captor.getValue().user());
        verifyNoMoreInteractions(repository);
    }

    @Test
    void taoDon_gioHangRong_nemLoi_vaKhongGoiRepository() {
        User user = new User("an@example.com", "An");

        IllegalArgumentException ex = assertThrows(IllegalArgumentException.class,
                () -> service.taoDon(user, List.of()));

        assertEquals("Don hang phai co san pham", ex.getMessage());
        verifyNoInteractions(repository);
    }

    @Test
    void layDon_khongTimThay_nemIllegalArgumentException() {
        when(repository.findById(99L)).thenReturn(Optional.empty());

        IllegalArgumentException ex = assertThrows(IllegalArgumentException.class,
                () -> service.layDon(99L));

        assertEquals("Khong tim thay don 99", ex.getMessage());
        verify(repository).findById(99L);
    }
}
// mvn test -> Tests run: 3, Failures: 0, Errors: 0, Skipped: 0

Giải mã các annotation

  • @ExtendWith(MockitoExtension.class) — kích hoạt Mockito cho class test: tự khởi tạo @Mock, tự tiêm vào @InjectMocks (theo constructor trước, rồi setter/field), và bật strict stubs. Không có extension thì @Mock vẫn null — phải gọi MockitoAnnotations.openMocks(this) trong @BeforeEach.
  • @Mock — tạo instance giả của interface/class, mọi method trả về mặc định (null, 0, false, list rỗng).
  • @InjectMocks — tạo object OrderService thật và tiêm các mock vào.
  • Strict stubs — stub mà test không dùng sẽ làm test fail bằng UnnecessaryStubbingException. Đây là feature, không phải bug: nó giúp bạn xoá stub chết khi code đổi. Cần nới lỏng cục bộ thì @MockitoSettings(strictness = Strictness.LENIENT) (nhận biết).

6. AssertJ — assertion dễ đọc Junior+

Assertions của JUnit đủ dùng cho kiểm tra đơn giản, nhưng khi so sánh collection, object lồng nhau hay exception thì rất khó đọc. AssertJ cho chuỗi method fluent bắt đầu bằng assertThat, gợi ý method theo kiểu dữ liệu và in diff chi tiết khi fail — gần với cảm giác expect(...) của Jest.

import org.assertj.core.api.SoftAssertions;
import org.junit.jupiter.api.Test;

import java.math.BigDecimal;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatCode;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class CalculatorTest {
    private final Calculator calculator = new Calculator();

    @Test
    void giaSauGiam_traVeDung_voiAssertJ() {
        BigDecimal sauGiam = calculator.giaSauGiam(new BigDecimal("200000"), 10);

        // isEqualByComparingTo: so BigDecimal bang compareTo (bo qua scale)
        assertThat(sauGiam).isEqualByComparingTo("180000");
    }

    @Test
    void danhSachSanPham_extracting() {
        List<Product> sanPham = List.of(
                new Product("Ao thun", new BigDecimal("120000")),
                new Product("Quan jean", new BigDecimal("240000")));

        assertThat(sanPham)
                .hasSize(2)
                .extracting(Product::ten)
                .containsExactly("Ao thun", "Quan jean");

        assertThat(sanPham).allSatisfy(p -> assertThat(p.gia()).isPositive());
    }

    @Test
    void chiaChoKhong_nemLoi_voiAssertJ() {
        assertThatThrownBy(() -> calculator.divide(10, 0))
                .isInstanceOf(ArithmeticException.class)
                .hasMessage("chia cho 0");
    }

    @Test
    void kiemTraMem_softAssertions() {
        User user = new User("an@example.com", "An");

        SoftAssertions softly = new SoftAssertions();
        softly.assertThat(user.ten()).isEqualTo("An");
        softly.assertThat(user.email()).contains("@");
        softly.assertAll();   // bat buoc: khong goi thi loi bi bo qua
    }
}
// mvn test -> Tests run: 4, Failures: 0, Errors: 0, Skipped: 0

Chạy hết assertion, báo đủ lỗiassertAll(...)SoftAssertions / assertSoftly
  • containsExactly vs containsOnly vs containsExactlyInAnyOrder — lần lượt: đúng thứ tự, đủ phần tử không cần thứ tự, đủ phần tử bất kỳ thứ tự. Dùng containsOnly/containsExactlyInAnyOrder khi thứ tự không phải hợp đồng.
  • Ngoại lệ: assertThatCode(() -> ...).doesNotThrowAnyException(), assertThatExceptionOfType(...) là biến thể hay dùng.
  • So sánh object lồng nhau: assertThat(actual).usingRecursiveComparison().isEqualTo(expected) so từng field đệ quy, bỏ qua việc class chưa cài equals. Tên cũ isEqualToComparingFieldByFieldRecursively đã bị loại bỏ ở các bản AssertJ mới — gặp tên cũ này thì chuyển sang usingRecursiveComparison().
  • Soft assertions chạy tiếp dù assertion trước fail, gom hết lỗi rồi báo một lần — nhưng quên softly.assertAll() thì mọi lỗi bị nuốt im lặng. Đừng lạm dụng: một test vẫn nên tập trung một hành vi.
Kết hợp cả hai: nhiều dự án dùng JUnit Assertions cho kiểm tra đơn giản và AssertJ cho list/exception. Chỉ cần thống nhất trong team — trộn lẫn mỗi test một kiểu sẽ khó review.

7. TDD — red-green-refactor Hay hỏi phỏng vấn

TDD (Test-Driven Development) là viết test trước code, theo vòng lặp 3 bước rất ngắn:

  1. Red — viết một test nhỏ cho hành vi chưa có; chạy cho chắc là nó fail (chưa compile hoặc assert sai). Test đỏ chứng minh test thực sự kiểm tra được điều cần kiểm tra.
  2. Green — viết code đơn giản nhất đủ để test xanh. Chưa cần đẹp, chưa cần tối ưu.
  3. Refactor — dọn code khi toàn bộ test vẫn xanh: đổi tên, tách method, bỏ lặp. Test là lưới an toàn.

Ví dụ chu trình cho Calculator.giaSauGiam — giả sử method chưa tồn tại. Bước 1, viết test trước (đỏ vì chưa compile):

// RED: chua co method giaSauGiam -> khong compile, dung la mong doi
@Test
void giaSauGiam_10PhanTram_traVe180000() {
    BigDecimal ketQua = calculator.giaSauGiam(new BigDecimal("200000"), 10);
    assertEquals(0, new BigDecimal("180000").compareTo(ketQua));
}

Bước 2 — code tối thiểu để xanh (chưa validate gì cả):

// GREEN: phien ban don gian nhat chay qua test
BigDecimal giaSauGiam(BigDecimal gia, int phanTramGiam) {
    BigDecimal giam = gia.multiply(BigDecimal.valueOf(phanTramGiam))
            .divide(BigDecimal.valueOf(100));
    return gia.subtract(giam);
}

Bước 3, thêm một test mới cho case lỗi — lại đỏ vì chưa validate, rồi bổ sung validation để xanh:

// RED lan 2: percent ngoai 0..100 phai nem loi
@Test
void giaSauGiam_phanTramNgoaiKhoang_nemIllegalArgumentException() {
    assertThrows(IllegalArgumentException.class,
            () -> calculator.giaSauGiam(new BigDecimal("100000"), 150));
}

// GREEN lan 2: them guard clause (khong doi test cu)
BigDecimal giaSauGiam(BigDecimal gia, int phanTramGiam) {
    if (phanTramGiam < 0 || phanTramGiam > 100) {
        throw new IllegalArgumentException("phan tram giam khong hop le: " + phanTramGiam);
    }
    BigDecimal giam = gia.multiply(BigDecimal.valueOf(phanTramGiam))
            .divide(BigDecimal.valueOf(100));
    return gia.subtract(giam);
}
// REFACTOR: tach hang so, dat ten bien ro -> chay lai toan bo test, van xanh

Điểm cốt lõi: code chỉ được coi là "xong" khi có test chứng minh. TDD cũng là cách học thiết kế API — bạn đóng vai người gọi method trước khi viết nó, nên tên và tham số tự nhiên dễ dùng hơn.

Đừng giáo điều. TDD là công cụ, không phải tôn giáo. Trong thực tế nhiều team viết code trước rồi test sau (test-after) cho phần đã rõ, và dùng TDD cho phần logic phức tạp. Điều bắt buộc là có test — thứ tự viết linh hoạt.

8. Coverage & JaCoCo Production

Coverage (độ bao phủ) là tỷ lệ code được test chạy qua, đo tự động bởi công cụ. Hai chỉ số cần phân biệt:

  • Line coverage — bao nhiêu % dòng code đã được chạy ít nhất một lần.
  • Branch coverage — bao nhiêu % nhánh (if/else, switch, toán tử 3 ngôi, &&/||) đã được chạy. Một if không có else cần cả 2 nhánh mới đạt 100% branch.

Ví dụ line coverage có thể 100% mà branch chỉ 50%: dòng if có chạy nhưng nhánh điều kiện sai chưa bao giờ được thử.

JaCoCo trong Maven

JaCoCo chuẩn của Java: chạy cùng mvn test, sinh báo cáo HTML ở target/site/jacoco/index.html:

<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.12</version>
  <executions>
    <execution>
      <goals>
        <goal>prepare-agent</goal>
      </goals>
    </execution>
    <execution>
      <id>report</id>
      <phase>test</phase>
      <goals>
        <goal>report</goal>
      </goals>
    </execution>
  </executions>
</plugin>
Version plugin chỉ là ví dụ — tra bản mới trên Maven Central. Dùng Spring Boot thì thêm plugin là đủ, dependency JUnit/Mockito/AssertJ đã có trong spring-boot-starter-test.

Coverage là chỉ số hỗ trợ, không phải mục tiêu

Coverage trả lời câu hỏi "chỗ nào chưa được test" — nó không trả lời "test có tốt không". Đoạn test sau làm coverage tăng mà không bảo vệ gì cả:

// Anti-pattern: "test" chi de du coverage, khong assert gi
@Test
void goiChoCoCoverage() {
    calculator.giaSauGiam(new BigDecimal("100000"), 10);   // chay nhung khong kiem tra
}

Dòng code trên đã "được test" theo báo cáo, nhưng nếu method trả sai, nếu quên validate — test vẫn xanh. Vài lời khuyên thực dụng:

  • Đừng đặt KPI kiểu "phải 90% coverage" — team sẽ viết test rác cho đủ số. Nếu công ty bắt buộc ngưỡng, hãy chặn ở mức thấp (ví dụ 60–70%) và tăng dần theo vùng code mới.
  • Ưu tiên coverage cho logic nghiệp vụ (tính tiền, chính sách giảm giá, validate) và branch coverage — nơi bug ẩn. Code generated, getter/setter, DTO thuần không cần ép coverage.
  • Khi đọc báo cáo, soi các dòng đỏ (chưa chạy) và các nhánh chưa đi qua — thường là case lỗi, case biên mà bạn quên. Đó mới là giá trị thật của công cụ.
  • Mức nhận biết: mutation testing (PIT) — công cụ tự sửa code (đảo điều kiện, đổi toán tử) rồi xem test có bắt được không; đây mới là thước đo test chất lượng, nhưng chạy chậm nên ít dùng hằng ngày.

9. Unit test vs Integration test Hay hỏi phỏng vấn

Hai loại test khác nhau ở phạm vi và cái gì là thật, kéo theo tốc độ và độ tin cậy khác nhau:

Tiêu chíUnit testIntegration test
Phạm viMột class/methodNhiều tầng: service + repository + DB/HTTP
DependencyMock hết (Mockito)Thật phần lớn (DB thật/in-memory, HTTP server giả)
Tốc độMili-giây — chạy nghìn test vài giâyGiây đến phút — cần dựng context, DB

Nhớ lại test pyramid (mục 1): nhiều unit test vì nhanh và rẻ; integration test đủ để bắt các lỗi mà mock không thể tạo ra (SQL sai, mapping sai, transaction sai); e2e rất ít vì chậm và dễ flaky.

Spring Boot — slice test & full context (nhận biết, học sâu ở GĐ5)

Spring Boot cho chọn đúng "lát" cần load thay vì dựng cả ứng dụng, giúp integration test nhanh hơn nhiều:

  • @SpringBootTest — dựng cả ApplicationContext; dùng cho integration test quan trọng, đừng dùng tràn lan vì rất chậm.
  • Slice test (@WebMvcTest, @DataJpaTest, @JsonTest) — chỉ load phần liên quan, dependency ngoài được mock/thay bằng H2.
  • Testcontainers (nhận biết) — chạy DB/Redis/Kafka thật trong Docker ngay từ test. Chậm hơn H2 nhưng loại bỏ khác biệt "H2 chạy được, PostgreSQL production lại lỗi". Đánh đổi: cần Docker trong máy/CI.
  • @MockitoBean thay @MockBean — Spring Framework 6.2 (Spring Boot 3.4+) đánh dấu @MockBean/@SpyBean deprecated và khuyến nghị chuyển sang @MockitoBean/@MockitoSpyBean; các bản Spring Boot 4 về sau dùng @MockitoBean là chuẩn. Đọc đề cũ thấy @MockBean thì biết ngay đó là tài liệu trước 3.4.

10. Testing trong production Production

Unit test hằng ngày khác bài tập ở chỗ: người đọc test là đồng nghiệp (và chính bạn 6 tháng sau). Vài thói quen tạo khác biệt lớn:

  • Test đọc như tài liệu. Tên test + dữ liệu Arrange + assertion chính là đặc tả. Một người mới đọc CalculatorTest phải hiểu method làm gì mà không cần mở Calculator.
  • Test cả exception, không chỉ happy path. Hỏi "dữ liệu xấu nhất là gì?" — null, rỗng, âm, 0, quá lớn, sai định dạng, phần tử trùng. Mỗi case lỗi quan trọng nên có một test (assertThrows, thường kèm kiểm tra message để chắc đúng lỗi).
  • Test chạy trong CI. Test chỉ chạy trên máy bạn thì gần như vô giá trị. Pipeline gọi mvn -B test, test đỏ chặn merge.
  • Test phải chạy ổn định (deterministic). Không phụ thuộc thời gian, mạng, thứ tự chạy. Xem 2 mục dưới.

Loại bỏ phụ thuộc thời gian & random

Đây là nguồn flaky test số một. Code gọi LocalDate.now() hoặc new Random() bên trong không thể test ổn định — hãy tiêm (inject) phụ thuộc vào. Với thời gian, JDK có sẵn Clock (học ở 3.5 java.time):

// Code production: nhan Clock tu ngoai
class OrderService {
    private final Clock clock;

    OrderService(Clock clock) {
        this.clock = clock;
    }

    LocalDate ngayGiaoDuKien() {
        return LocalDate.now(clock).plusDays(3);
    }
}

// Test: Clock co dinh -> ket qua co dinh, chay nam nao cung vay
@Test
void ngayGiaoDuKien_cong3Ngay() {
    Clock coDinh = Clock.fixed(Instant.parse("2026-10-03T00:00:00Z"), ZoneOffset.UTC);
    OrderService service = new OrderService(coDinh);

    assertEquals(LocalDate.of(2026, 10, 6), service.ngayGiaoDuKien());
}

Flaky test — test lúc xanh lúc đỏ

Flaky test là test fail ngẫu nhiên dù không ai sửa code. Nguy hiểm hơn test không có: team bắt đầu "chạy lại cho xanh" và bỏ qua tín hiệu đỏ thật. Bốn nguyên nhân phổ biến và cách xử lý:

Nguyên nhânDấu hiệuCách sửa
Phụ thuộc thứ tự / state dùng chungChạy một mình thì pass, chạy cả class thì failBỏ field static, dựng dữ liệu trong @BeforeEach
Thời gian / timezone / randomFail theo giờ trong ngày, khác máyInject Clock, seed cố định, chỉ định timezone trong test
Thread.sleep chờ việc bất đồng bộMáy chậm là fail, máy nhanh thì passChờ theo điều kiện (Awaitility), dùng CompletableFuture.get(timeout), không sleep
Mạng / service ngoài / portFail khi CI chậm hoặc service bên kia chếtMock ở biên hoặc Testcontainers; không gọi production trong test
Quy tắc vàng với flaky test: tìm nguyên nhân gốc, không rerun cho tới khi xanh. Nếu chưa sửa được ngay, quarantine (tạm @Disabled("flaky -> ticket #123")) và coi đó là bug P1 — vì mỗi lần rerun là một lần bạn dạy cả team phớt lờ đèn đỏ.

13. Ví dụ đầy đủ — Calculator & OrderService Production

Ghép mọi thứ đã học vào một test class hoàn chỉnh: @BeforeEach, JUnit assertions, AssertJ, parameterized và exception. Giả định Calculator ở mục 2 nằm trong src/main/java:

import org.assertj.core.api.SoftAssertions;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

import java.math.BigDecimal;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

class CalculatorTest {
    private Calculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new Calculator();
    }

    @Test
    @DisplayName("cong hai so")
    void add_haiSoDuong_traVeTong() {
        assertThat(calculator.add(2, 3)).isEqualTo(5);
    }

    @Test
    void divide_chiaChoKhong_nemArithmeticException() {
        assertThatThrownBy(() -> calculator.divide(10, 0))
                .isInstanceOf(ArithmeticException.class)
                .hasMessage("chia cho 0");
    }

    @ParameterizedTest(name = "{0} giam {1}% = {2}")
    @CsvSource({
            "200000, 10, 180000",
            "120000, 25,  90000",
            "100000,  0, 100000"
    })
    void giaSauGiam_traVeDung(String gia, int phanTram, String mongDoi) {
        BigDecimal ketQua = calculator.giaSauGiam(new BigDecimal(gia), phanTram);
        assertThat(ketQua).isEqualByComparingTo(mongDoi);
    }

    @Test
    void giaSauGiam_phanTramNgoai0Den100_nemIllegalArgumentException() {
        IllegalArgumentException ex = assertThrows(IllegalArgumentException.class,
                () -> calculator.giaSauGiam(new BigDecimal("100000"), 150));

        SoftAssertions softly = new SoftAssertions();
        softly.assertThat(ex.getMessage()).contains("khong hop le");
        softly.assertThat(ex.getCause()).isNull();
        softly.assertAll();
        assertTrue(ex.getMessage().contains("150"));
    }
}
// mvn test -> Tests run: 6, Failures: 0, Errors: 0, Skipped: 0
// (3 @Test + 3 lan chay cua @ParameterizedTest)

14. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Unit test là gì? Vì sao phải viết?
Unit test là test tự động kiểm tra một đơn vị nhỏ (thường là một method/class), chạy nhanh và không phụ thuộc hệ thống ngoài. Viết test để bắt regression khi sửa code, tự tin refactor, làm tài liệu sống mô tả hành vi, và làm cổng chất lượng trong CI. Cần nhớ: test không làm code đúng — nó chỉ giúp bạn biết code đúng hay sai; thiết kế vẫn là việc của bạn.
Câu 2. JUnit 5 khác JUnit 4 ở điểm nào?
JUnit 5 gồm Platform (nền chạy), Jupiter (API mới) và Vintage (chạy test JUnit 4 cũ). Khác biệt chính: annotation chuyển từ org.junit.Test sang org.junit.jupiter.api.Test; @Before/@After đổi thành @BeforeEach/@AfterEach; mở rộng bằng @ExtendWith thay cho @RunWith; assertions rõ ràng hơn; hỗ trợ lambda, @ParameterizedTest, @Nested. Về dependency, Maven chỉ cần artifact tổng junit-jupiter.
Câu 3. @BeforeEach khác @BeforeAll thế nào?
@BeforeEach chạy trước mỗi test method — nơi dựng dữ liệu sạch cho từng test, không cần static. @BeforeAll chạy một lần trước tất cả test — dùng cho tài nguyên đắt (mở kết nối, dựng server test), bắt buộc static trừ khi class dùng @TestInstance(PER_CLASS). @AfterEach/@AfterAll đối xứng để dọn dẹp. Quy tắc thực dụng: mặc định dùng @BeforeEach; chỉ @BeforeAll khi thật sự tốn kém.
Câu 4. JUnit tạo instance test class như thế nào? Vì sao điều này quan trọng?
Mặc định (PER_METHOD), mỗi test method được chạy trên một instance mới của test class. Vì vậy field instance luôn sạch, các test độc lập và chạy theo thứ tự nào cũng được. Điều này cũng có nghĩa: field static mutable sẽ phá vỡ cách ly và gây test phụ thuộc thứ tự — đừng dùng. Muốn giữ state giữa các test (hiếm), dùng @TestInstance(TestInstance.Lifecycle.PER_CLASS).
Câu 5. assertEquals(expected, actual) — đặt sai thứ tự có sao không?
Pass/fail vẫn đúng vì so sánh đối xứng, nhưng khi fail JUnit in expected: <...> but was: <...> theo đúng thứ tự bạn truyền. Đặt actual trước expected sẽ khiến message đảo ngược, người debug hiểu sai. Luôn truyền expected trước, actual sau. JUnit còn nhận tham số message thứ ba, hoặc Supplier<String> để tránh tạo chuỗi khi test pass.
Câu 6. Test exception thế nào? assertThrows hoạt động ra sao?
Dùng assertThrows(LoaiException.class, () -> ...): JUnit chạy lambda, pass nếu ném đúng loại exception, fail nếu không ném hoặc ném loại khác. Nó trả về exception đã ném để bạn assert tiếp getMessage()/getCause(). Với trường hợp phải chạy êm, dùng assertDoesNotThrow. Không dùng try/catch + cờ boolean trong test — vừa dài vừa dễ bỏ sót khi exception không được ném.
Câu 7. assertAll để làm gì?
Gộp nhiều assertion vào một test và chạy hết thay vì dừng ở lỗi đầu tiên, sau đó báo cáo tất cả lỗi cùng lúc. Hữu ích khi kiểm tra nhiều field của cùng một kết quả (message, cause, mã lỗi). Tuy nhiên vẫn phải giữ tinh thần "một hành vi một test" — assertAll không phải giấy phép nhồi nhiều hành vi khác nhau vào một test.
Câu 8. @ParameterizedTest là gì? Kể các nguồn dữ liệu chính.
Là test chạy cùng logic với nhiều bộ dữ liệu; mỗi bộ là một lần chạy riêng và được báo fail riêng. Nguồn dữ liệu: @ValueSource (danh sách một kiểu), @CsvSource (bảng nhiều cột, tự chuyển kiểu cơ bản), @MethodSource (method static trả Stream/Collection các Arguments), ngoài ra @EnumSource, @NullSource, @EmptySource. Dùng name = "...{0}..." để tên case dễ đọc. Nếu mỗi case cần logic kiểm tra khác nhau thì viết test riêng.
Câu 9. AAA là gì? Có bắt buộc viết comment không?
AAA = Arrange (chuẩn bị dữ liệu/mock), Act (gọi đúng một hành vi), Assert (kiểm tra kết quả). Comment AAA không bắt buộc, nhưng nên tách 3 phần bằng dòng trống để mắt nhận ra ngay. Nếu phần Arrange chiếm quá nhiều dòng hoặc có nhiều Act, đó là tín hiệu test quá lớn — tách test hoặc tách helper.
Câu 10. Đặt tên test thế nào cho tốt?
Tên nói rõ hành vi + điều kiện + kết quả mong đợi: taoDon_gioHangRong_nemIllegalArgumentException, giaSauGiam_10PhanTram_traVe180000. Tránh test1, testOrder, shouldWork. Vì test fail sẽ hiện tên method, tên tốt giúp chẩn đoán mà không cần mở code. Tên dài/tiếng Việt có dấu thì để trong @DisplayName, tên method giữ ASCII.

Test double & Mockito

Câu 11. mock, stub, spy, fake, dummy khác nhau thế nào?
Đều là test double (object giả thay cho object thật): dummy — object rỗng chỉ để đủ tham số; stub — trả dữ liệu đã định (when...thenReturn); mock — stub + ghi lại tương tác để verify; spy — bọc quanh object thật, method không stub chạy code thật; fake — cài đặt đơn giản nhưng hoạt động thật (repository in-memory). Mockito tạo mock/stub/spy; fake do bạn tự viết.
Câu 12. when/thenReturn hoạt động ra sao? Khi nào dùng doReturn().when()?
when(mock.method(args)).thenReturn(x) đăng ký stub: gọi method trên mock để Mockito ghi nhận lời gọi, rồi trả x cho các lần gọi sau. Với spy hoặc method void, cách này nguy hiểm vì when(spy.method()) gọi luôn code thật (có thể gây side effect) — phải dùng doReturn(x).when(spy).method(), doThrow(...), doNothing(). Cần kết quả động theo tham số thì dùng thenAnswer.
Câu 13. verify dùng khi nào? Khi nào verify là dấu hiệu test tồi?
verify dùng khi tương tác chính là hành vi cần bảo vệ: bắt buộc gọi repository.save, bắt buộc gửi email, không được gọi API khi validate fail (verifyNoInteractions). Verify trở thành dấu hiệu tồi khi test dính vào triển khai nội bộ — verify số lần gọi helper, thứ tự gọi nội bộ — vì refactor không đổi hành vi vẫn làm test đỏ. Nguyên tắc: ưu tiên assert kết quả/trạng thái, chỉ verify ở biên hệ thống.
Câu 14. @Mock, @InjectMocks, @ExtendWith(MockitoExtension.class) làm gì? Thiếu extension thì sao?
@Mock tạo object giả và gán vào field; @InjectMocks tạo object thật cần test rồi tiêm các mock vào (constructor trước, sau đó setter/field); @ExtendWith(MockitoExtension.class) kích hoạt cả hai và kiểm tra strict stubs. Thiếu extension thì @Mock vẫn là null — phải tự gọi MockitoAnnotations.openMocks(this) trong @BeforeEach. Strict stubs giúp phát hiện stub thừa qua UnnecessaryStubbingException.
Câu 15. ArgumentCaptor dùng khi nào?
Khi cần kiểm tra sâu giá trị argument mà code đã truyền cho mock — đặc biệt object được tạo bên trong method nên test không có tham chiếu. Cách dùng: ArgumentCaptor<Order> captor = ArgumentCaptor.forClass(Order.class); verify(repository).save(captor.capture()); rồi assert trên captor.getValue(). Nếu chỉ cần biết "có gọi hay không" thì verify thường đủ; đừng lạm dụng captor cho mọi thứ.
Câu 16. Khi nào KHÔNG nên mock?
Không mock value object/record/DTO (User, Product, Order, Money) — tạo thật rẻ và tránh null bất ngờ. Không mock thư viện JDK (List, BigDecimal, Optional). Không mock class thuần logic không có dependency. Không mock thư viện bên thứ ba trực tiếp — hãy bọc sau interface của bạn rồi mock interface đó. Mock chỉ nên xuất hiện ở biên hệ thống: repository/DB, HTTP, file, message queue, Clock, nguồn random. Mockito 5 mock được final class và static (inline mock maker), nhưng càng mock sâu test càng dính triển khai.
Câu 17. Test private method thế nào?
Không test trực tiếp — hãy test qua public API đã gọi nó. Nếu một private method phức tạp đến mức cần test riêng, đó là tín hiệu thiết kế: tách nó thành class/package-private helper rồi test trực tiếp (test cùng package truy cập được package-private). Dùng reflection để gọi private là giải pháp bị bỏ qua nhanh chóng vì cực dễ vỡ khi refactor và không mang lại giá trị.

Nâng cao (Junior+)

Câu 18. AssertJ hơn JUnit Assertions ở điểm nào? So BigDecimal ra sao?
AssertJ cho chuỗi assertion fluent, method gợi ý theo kiểu dữ liệu (list có hasSize, containsExactly, extracting; exception có assertThatThrownBy) và message lỗi chi tiết, dễ chẩn đoán hơn. Với BigDecimal phải dùng isEqualByComparingTo("180000") thay vì isEqualTo: isEqualTo dùng equals nên phân biệt scale (180000 khác 180000.0). AssertJ còn có soft assertions và usingRecursiveComparison() để so object lồng nhau không cần equals.
Câu 19. TDD là gì? Lợi ích và giới hạn?
TDD là viết test trước code theo vòng lặp red → green → refactor: viết test đỏ, viết code tối thiểu cho xanh, dọn code khi test vẫn xanh. Lợi ích: test luôn tồn tại, thiết kế API từ góc người dùng, tự tin refactor, bug fix kèm test tái hiện. Giới hạn: không hợp khi đang khám phá công nghệ (spike), UI, prototype; legacy code phải viết characterization test trước. Thực tế nhiều team kết hợp test-first cho logic phức tạp và test-after cho phần đã rõ.
Câu 20. Coverage bao nhiêu là đủ? 100% có nghĩa là hết bug?
Không có con số "đủ" tuyệt đối. Coverage chỉ cho biết dòng/nhánh nào chưa được chạy, không chứng minh assertion có ý nghĩa — test không assert gì vẫn đạt 100%. Branch coverage có giá trị hơn line coverage. Thực dụng: đặt ngưỡng thấp cho toàn dự án (60–70%) và tập trung test kỹ logic nghiệp vụ, case biên, case lỗi. Đừng lấy coverage làm KPI vì sẽ sinh "test rác cho đủ số". Công cụ sâu hơn là mutation testing (PIT) — nhận biết.
Câu 21. Unit test khác integration test thế nào? Spring Boot hỗ trợ gì?
Unit test kiểm tra một class/method với mọi dependency được mock — nhanh (mili-giây), fail khoanh vùng hẹp. Integration test kiểm tra nhiều tầng thật (service + DB/HTTP) — chậm hơn (giây), độ tin cậy cao hơn vì không phụ thuộc mock, nhưng fail khó điều tra. Test pyramid: nhiều unit, vừa integration, ít e2e. Spring Boot có slice test (@WebMvcTest, @DataJpaTest, @JsonTest) load đúng phần cần thiết, @SpringBootTest load full context, và Testcontainers để chạy DB thật bằng Docker (nhận biết). Từ Spring Boot 3.4 dùng @MockitoBean thay @MockBean đã deprecated.
Câu 22. Flaky test là gì? Nguyên nhân và cách xử lý?
Flaky test là test lúc pass lúc fail dù code không đổi. Nguyên nhân thường gặp: phụ thuộc thứ tự/state dùng chung (static mutable), thời gian/timezone/random, Thread.sleep chờ bất đồng bộ, mạng/port/service ngoài, race condition. Cách xử lý: tìm nguyên nhân gốc — tuyệt đối không "rerun cho xanh"; cô lập dữ liệu mỗi test, inject Clock/seed, chờ theo điều kiện (Awaitility) thay vì sleep, mock hoặc Testcontainers thay vì gọi service thật. Nếu chưa sửa ngay, @Disabled kèm ticket và coi là bug ưu tiên cao — vì test flaky phá hỏng lòng tin vào cả bộ test.

Nếu muốn kiểm tra kiểu số nguyên, chọn dữ liệu chia hết; còn với tiền tệ hãy giữ BigDecimal và so bằng compareTo.

Bài 12. AssertJ exception: assertThatThrownBy + assertThatCode

Hai biến thể hay dùng của AssertJ: một cái khẳng định ném đúng lỗi + message, một cái khẳng định chạy êm ở case hợp lệ:

import org.junit.jupiter.api.Test;

import java.math.BigDecimal;

import static org.assertj.core.api.Assertions.assertThatCode;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class CalculatorTest {
    private final Calculator calculator = new Calculator();

    @Test
    void giaSauGiam_phanTramNgoaiKhoang_nemLoi() {
        assertThatThrownBy(() -> calculator.giaSauGiam(new BigDecimal("100000"), 150))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessageContaining("khong hop le")
                .hasMessageContaining("150");
    }

    @Test
    void giaSauGiam_phanTram0_chayEm() {
        assertThatCode(() -> calculator.giaSauGiam(new BigDecimal("100000"), 0))
                .doesNotThrowAnyException();
    }
}
// mvn test -> Tests run: 2, Failures: 0, Errors: 0, Skipped: 0

Quy tắc phải nhớ

  • Một hành vi một test; tên test nói rõ hành vi — điều kiện — kết quả.
  • Test độc lập: không static mutable, dữ liệu dựng lại mỗi test.
  • Assert kết quả trước, verify tương tác sau (và chỉ ở biên hệ thống).
  • Không mock value object; mock repository/HTTP/Clock.
  • Matcher Mockito phải dùng cho tất cả tham số của một lời gọi.
  • BigDecimal so bằng compareTo/isEqualByComparingTo, không equals.
  • Không Thread.sleep; inject thời gian/random.
  • Coverage là đèn soi chỗ trống, không phải KPI; test đỏ không được rerun cho xanh.
  • Test fail: kiểm tra code trước, đừng sửa test để che bug.

Checklist tự đánh giá trước phỏng vấn

  • Viết được test JUnit 5 với @Test, @DisplayName, assertions mà không cần tra cứu.
  • Giải thích được vòng đời: mỗi test một instance; @BeforeEach vs @BeforeAll.
  • Test được exception bằng assertThrows và kiểm tra cả message.
  • Viết parameterized test với @CsvSource và @MethodSource.
  • Nêu và áp dụng AAA; đặt tên test theo hành vi.
  • Phân biệt mock/stub/spy/fake/dummy và biết khi nào không mock.
  • Mock repository, stub when/thenReturn, verify tương tác, bắt argument bằng ArgumentCaptor.
  • Giải thích @Mock, @InjectMocks, @ExtendWith(MockitoExtension.class) và strict stubs.
  • Dùng AssertJ cho list/exception; biết bẫy BigDecimal scale.
  • Trình bày TDD red-green-refactor kèm ví dụ.
  • Phân biệt line vs branch coverage và vì sao cover 100% chưa chắc hết bug.
  • Phân biệt unit vs integration test; kể được slice test Spring Boot + Testcontainers.
  • Xử lý flaky test: nêu nguyên nhân và cách sửa, không rerun cho xanh.
