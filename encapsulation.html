Encapsulation & Immutability — đóng gói & bất biến

Encapsulation (đóng gói) là giấu ruột của object, chỉ mở ra những gì bên ngoài thật sự cần. Immutability (bất biến) là làm object không thể đổi state sau khi tạo. Hai ý này đi cùng nhau: muốn bảo vệ dữ liệu thì vừa phải đóng (private), vừa phải chặn sửa (immutable). Trang này đi từ private/getter/setter, 5 bước tạo immutable class, copy phòng thủ, record, tới pattern production và các cạm bẫy hay gặp.

1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Hãy bắt đầu bằng hình ảnh cây ATM. Bạn chỉ thấy màn hình, bàn phím, khe tiền — đó là API công khai. Bạn không thấy và không chạm được ruột máy, két tiền, hệ thống đếm — đó là implementation bị giấu. Ngân hàng có thể thay ruột máy, nâng cấp phần mềm, miễn giữ nguyên cách dùng bên ngoài thì bạn vẫn rút tiền như cũ. Code cũng vậy: field để private, chỉ lộ ra vài method nghiệp vụ; muốn đổi cách lưu trữ bên trong thì đổi, client không hề biết.

Đóng gói tồn tại để bảo vệ invariant — điều kiện luôn phải đúng của object: số dư không được âm, số lượng đặt hàng phải > 0, email phải chứa @, createdAt không được đổi. Nếu field là public, mọi nơi trong chương trình đều có thể phá invariant, và bạn không có cách nào kiểm soát:

user.balance = -500_000;              // khong ai kiem tra duoc
user.balance = user.balance - 100_000; // quy tac trừ tiền copy khap noi
user.balance -= 100_000;              // ba noi viet ba kieu, mot noi quen validate

Ba lợi ích cốt lõi của đóng gói:

  • Bảo vệ invariant — mọi thay đổi phải đi qua method có validate, object không bao giờ rơi vào trạng thái vô lý.
  • Giấu implementation — đổi kiểu dữ liệu bên trong (ví dụ long sang BigDecimal) mà không phá code bên ngoài, miễn giữ API.
  • Kiểm soát điểm thay đổi — logic nằm một chỗ, sửa một lần; không phải đi tìm mọi nơi đã copy quy tắc.

Còn immutable là mức bảo vệ cao hơn: object sinh ra xong thì không đổi được nữa. Ai đang giữ reference cũng yên tâm vì không ai sửa lén được state. Bạn đã gặp nhiều object bất biến của JDK: String, Integer, BigDecimal, LocalDate — và record được sinh ra chính để chở dữ liệu theo kiểu này.

Góc Node.js: JavaScript hiện đại cũng có field #private (từ ES2022) để giấu dữ liệu thật, nhưng đa số code quen dùng public field và object tự do; còn "khóa" object kiểu Object.freeze chỉ có tác dụng một lớp. Mục 12 so sánh chi tiết.

Mức độ bắt buộc của chủ đề 2.2 (phỏng vấn: rất cao · production: bắt buộc):

  • Phải làm được — khai báo field private + getter/setter có validate; viết immutable class đủ 5 bước; defensive copy cho List/Map; viết method withX()/plus() trả object mới; đọc và viết record có validate.
  • Phải hiểu — vì sao final chưa đủ để bất biến; record chỉ bất biến nông; vì sao immutable thread-safe và an toàn khi làm key HashMap; khác nhau giữa unmodifiable và immutable; khi nào nên bỏ setter (tell-don't-ask).
  • Nhận biết — copy nông vs copy sâu cho cấu trúc lồng; JPA entity không immutable (học ở giai đoạn backend); builder khi có nhiều field (2.8 SOLID & design patterns).

2. private, getter & setter — giấu dữ liệu

Cơ chế đầu tiên của đóng gói là access modifier (mức truy cập). Java có 4 mức, chọn đúng mức là quyết định thiết kế chứ không phải chi tiết vặt:

MứcAi truy cập đượcDùng khi nào
privateChỉ code trong cùng classMặc định cho mọi field; helper method nội bộ
không ghi gì (package-private)Các class cùng packagePhối hợp nội bộ một package, test cùng package
protectedCùng package + subclassMethod dành cho subclass override (học ở 2.3 Inheritance)
publicMọi nơiAPI công khai — càng ít càng tốt

Quy tắc thực dụng: field luôn private, method mặc định để hẹp nhất có thể rồi mở dần khi cần. Khi field private, bên ngoài chỉ đọc/ghi qua getter/setter hoặc method nghiệp vụ:

public long getBalance() { return balance; }    public void setBalance(long value) { validate; this.balance = value; }

Ví dụ đầy đủ: User có balance private, mọi lối vào đều validate, bên ngoài không chạm được vào field:

public class User {
    private final String email;
    private long balance;

    User(String email, long balance) {
        if (email == null || !email.contains("@")) {
            throw new IllegalArgumentException("email khong hop le: " + email);
        }
        if (balance < 0) {
            throw new IllegalArgumentException("balance khong duoc am: " + balance);
        }
        this.email = email;
        this.balance = balance;
    }

    String getEmail() {
        return email;
    }

    long getBalance() {
        return balance;
    }

    void setBalance(long newBalance) {
        if (newBalance < 0) {
            throw new IllegalArgumentException("balance khong duoc am: " + newBalance);
        }
        this.balance = newBalance;
    }

    void deposit(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("amount phai duong: " + amount);
        }
        balance += amount;
    }

    void withdraw(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("amount phai duong: " + amount);
        }
        if (amount > balance) {
            throw new IllegalArgumentException("so du khong du: " + amount);
        }
        balance -= amount;
    }

    public static void main() {
        User an = new User("an@example.com", 100_000);
        an.deposit(50_000);
        IO.println("sau deposit    : " + an.getBalance());   // 150000
        an.withdraw(30_000);
        IO.println("sau withdraw   : " + an.getBalance());   // 120000
        an.setBalance(200_000);
        IO.println("sau setBalance : " + an.getBalance());   // 200000
        try {
            an.withdraw(500_000);
        } catch (IllegalArgumentException e) {
            IO.println("loi: " + e.getMessage());            // loi: so du khong du: 500000
        }
        try {
            an.setBalance(-1);
        } catch (IllegalArgumentException e) {
            IO.println("loi: " + e.getMessage());            // loi: balance khong duoc am: -1
        }
        IO.println("so du cuoi     : " + an.getBalance());   // 200000
    }
}

Kết quả chạy thật java User.java:

sau deposit    : 150000
sau withdraw   : 120000
sau setBalance : 200000
loi: so du khong du: 500000
loi: balance khong duoc am: -1
so du cuoi     : 200000

Thử truy cập thẳng field từ class khác sẽ bị chặn ngay khi compile — đây là hàng rào cứng, không phải quy ước:

User.java:8: error: balance has private access in User
        u.balance = -100;
         ^
1 error
private là theo class, không theo object: hai object cùng class vẫn đọc/ghi private của nhau thoải mái, và main nằm trong chính class đó cũng truy cập được. Vì vậy ví dụ lỗi trên phải đặt lời gọi trong một class khác. Điều này giải thích vì sao equals của một class so sánh private field của object khác cùng class được (xem 2.6 equals / hashCode / toString).
Có private + getter/setter chưa chắc là đóng gói tốt. Nếu getter/setter chỉ chuyển tiếp field, bạn vừa giấu dữ liệu lại vừa mở nó ra ở dạng khác — client vẫn phụ thuộc cấu trúc nội bộ. Mục tiếp theo bàn kỹ hơn.

3. Khi nào KHÔNG nên có setter Production

Setter là API nguy hiểm nhất trong một class nghiệp vụ vì nó cho phép "đặt object vào bất kỳ trạng thái nào". Ba trường hợp dưới đây setter gần như luôn là mùi code.

3.1. Object bất biến thì không có setter

Nếu mục tiêu là object không đổi (mục 4), setter mâu thuẫn trực tiếp với mục tiêu đó. Muốn "sửa" thì method trả về object mới.

3.2. Tell, don't ask — bảo object làm việc thay vì hỏi dữ liệu

Kiểu "ask rồi set" đẩy quy tắc nghiệp vụ ra ngoài class; ai gọi cũng phải nhớ và copy quy tắc đó. Kiểu "tell" giao việc cho object, quy tắc nằm một chỗ:

// Ask roi set: quy tac nam o ngoai, phai nho va lap lai o moi call site
if (user.getBalance() >= 100_000) {
    user.setBalance(user.getBalance() - 100_000);
}

// Tell: giao viec cho object, class tu giu invariant
user.withdraw(100_000);

3.3. Setter cho id, createdAt, status là mùi code

  • id là định danh — đổi id nghĩa là object khác, đừng cho setter.
  • createdAt là thời điểm sinh ra — bất biến theo định nghĩa.
  • status nên đổi qua hành động nghiệp vụ để class kiểm tra luật chuyển trạng thái, thay vì gán thô:
order.setStatus(OrderStatus.CANCELLED); // ai cung set duoc, ke ca tu trang thai da giao
order.cancel();                         // ro nghiep vu, class tu kiem tra trang thai hop le

Còn getter trả về collection nội bộ là lỗi kinh điển — client sửa được list ruột của object. Ví dụ và cách sửa nằm ở mục 6.

Bối cảnhSetterLý do
Value object (Money, Email...), entityKhông nênInvariant và hành vi nghiệp vụ phải được giữ; dùng method có tên hành động
DTO / config cần framework (Jackson, JPA)Chấp nhận đượcFramework cần set field; DTO gần như chỉ chở dữ liệu — nhưng entity (JPA) thì cẩn thận
Field có invariant (số dư, số lượng)Chỉ khi validateSetter không validate = cửa mở phá invariant (bài tập 8)
Field định danh, thời gian tạo, trạng tháiTránhĐổi qua method nghiệp vụ để kiểm soát luật
Nguyên tắc nhớ nhanh: setter chỉ hợp lệ khi "gán giá trị bất kỳ" thật sự là một hành vi hợp lệ của object. Nếu không, hãy viết method nghiệp vụ — tên method cũng tự tài liệu hóa ý nghĩa.

4. Immutable class — 5 bước tạo Hay hỏi phỏng vấn

Object bất biến (immutable) là object mà sau khi constructor chạy xong, nhìn từ bên ngoài không có cách nào đổi state. Tạo một immutable class chuẩn gồm 5 bước:

  1. Đánh dấu class final — chặn subclass thêm field mutable hoặc override method phá tính bất biến. Nếu không muốn final class, có thể giữ constructor private + static factory.
  2. Mọi field private final — không có đường ghi sau constructor.
  3. Không viết setter — mọi thao tác "thay đổi" trả về object mới (withAmount, plus...).
  4. Validate trong constructor — fail fast, object sinh ra là đã đúng invariant, không có cửa sổ thời gian nào object ở trạng thái hỏng.
  5. Defensive copy mọi field mutable — khi nhận trong constructor và khi trả trong getter (chi tiết ở mục 6).
public final class Money {  private final long amount; private final String currency;  // khong setter; method tra object moi }

final — khóa reference, không khóa nội dung

Đây là hiểu lầm tốn kém nhất. final chỉ đảm bảo biến được gán một lần; nếu biến trỏ tới object mutable thì nội dung object vẫn đổi bình thường:

import java.util.ArrayList;
import java.util.List;

public class VariablesDemo {
    public static void main() {
        final List<String> items = new ArrayList<>();
        items.add("ao");
        items.add("quan");
        IO.println(items);       // [ao, quan]
        IO.println(items.size()); // 2
    }
}

Đoạn trên chạy bình thường, thêm phần tử thoải mái. Nhưng gán lại biến thì không compile:

VariablesDemo.java:8: error: cannot assign a value to final variable items
        items = new ArrayList<>();
        ^
1 error
Kết luận: final là điều kiện cần nhưng chưa đủ. Muốn immutable phải khóa cả reference và nội dung object (dùng object immutable, hoặc copy phòng thủ). Chi tiết final bạn đã học ở Biến trong Java — mục 10.

5. Class Money — ví dụ bất biến đầy đủ

Ghép đủ 5 bước vào một value object thật: Money với amount + currency. Mọi thao tác trả object mới, không bao giờ sửa object cũ:

public class ProductionDemo {
    static final class Money {
        private final long amount;
        private final String currency;

        Money(long amount, String currency) {
            if (amount < 0) {
                throw new IllegalArgumentException("amount khong hop le: " + amount);
            }
            if (currency == null || currency.isBlank()) {
                throw new IllegalArgumentException("currency khong hop le");
            }
            this.amount = amount;
            this.currency = currency;
        }

        long amount() {
            return amount;
        }

        String currency() {
            return currency;
        }

        Money plus(Money other) {
            checkSameCurrency(other);
            return new Money(amount + other.amount, currency);
        }

        Money minus(Money other) {
            checkSameCurrency(other);
            return new Money(amount - other.amount, currency);
        }

        Money withAmount(long newAmount) {
            return new Money(newAmount, currency);
        }

        private void checkSameCurrency(Money other) {
            if (!currency.equals(other.currency)) {
                throw new IllegalArgumentException("khac currency: " + currency + " vs " + other.currency);
            }
        }

        @Override
        public String toString() {
            return amount + " " + currency;
        }
    }

    public static void main() {
        Money gia = new Money(250_000, "VND");
        Money ship = new Money(30_000, "VND");
        Money tong = gia.plus(ship);

        IO.println("gia      : " + gia);                                // 250000 VND
        IO.println("tong     : " + tong);                               // 280000 VND
        IO.println("giam gia : " + tong.minus(new Money(50_000, "VND"))); // 230000 VND
        IO.println("amount 0 : " + tong.withAmount(0));                // 0 VND
        IO.println("gia sau tat ca phep tinh: " + gia);                 // 250000 VND

        try {
            new Money(-1, "VND");
        } catch (IllegalArgumentException e) {
            IO.println("loi: " + e.getMessage());                     // loi: amount khong hop le: -1
        }

        try {
            gia.plus(new Money(1, "USD"));
        } catch (IllegalArgumentException e) {
            IO.println("loi: " + e.getMessage());                     // loi: khac currency: VND vs USD
        }
    }
}

Kết quả chạy thật:

gia      : 250000 VND
tong     : 280000 VND
giam gia : 230000 VND
amount 0 : 0 VND
gia sau tat ca phep tinh: 250000 VND
loi: amount khong hop le: -1
loi: khac currency: VND vs USD
  • gia không bao giờ đổi sau plus, minus, withAmount — mỗi method trả object mới. Đây là khác biệt cốt lõi so với setter.
  • Validate ngay trong constructor — không tồn tại Money âm hay sai currency. Vì vậy mọi method khác không cần kiểm tra lại.
  • Tên method không có tiền tố get — amount(), currency() theo phong cách value object/record (giống BigDecimal.scale(), LocalDate.getYear() thì cũ vẫn dùng get).
  • Phép tính khác loại tiền bị chặn — đây là invariant nghiệp vụ được mã hóa vào class, client không thể cộng VND với USD.
Tiền tệ production thường dùng BigDecimal thay long khi cần phần thập phân; nguyên tắc bất biến và validate giữ nguyên. Xem Data Types — mục 12 và Biến trong Java — mục 13.

6. Copy phòng thủ (defensive copy) Hay hỏi phỏng vấn

Defensive copy là sao chép dữ liệu mutable tại biên của object — lúc nhận vào (constructor) và lúc trả ra (getter) — để bên ngoài không bao giờ giữ được reference tới state nội bộ. Không có bước này, "immutable" chỉ là danh nghĩa.

Xem lỗ hổng kinh điển: getter trả thẳng list nội bộ.

import java.util.ArrayList;
import java.util.List;

public class Order {
    private final String code;
    private final List<String> items = new ArrayList<>();

    Order(String code) {
        this.code = code;
    }

    void addItem(String item) {
        items.add(item);
    }

    List<String> getItems() {
        return items;
    }

    public static void main() {
        Order don = new Order("DH-001");
        don.addItem("ao thun");
        List<String> tuBenNgoai = don.getItems();
        tuBenNgoai.add("hang la");
        IO.println("items cua don: " + don.getItems()); // [ao thun, hang la]
        IO.println("ai do da chen duoc vao list noi bo!");
    }
}

Kết quả chạy thật — object Order bị sửa từ bên ngoài mà nó không hề hay biết:

items cua don: [ao thun, hang la]
ai do da chen duoc vao list noi bo!

Sửa bằng copy phòng thủ ở cả hai đầu: constructor nhận List.copyOf, getter cũng trả List.copyOf:

import java.util.ArrayList;
import java.util.List;

public class Order {
    private final String code;
    private final List<String> items;

    Order(String code, List<String> items) {
        this.code = code;
        this.items = List.copyOf(items);
    }

    List<String> getItems() {
        return List.copyOf(items);
    }

    public static void main() {
        List<String> goc = new ArrayList<>(List.of("ao thun"));
        Order don = new Order("DH-001", goc);

        goc.add("hang la tu ben ngoai");
        IO.println("sau khi sua list goc : " + don.getItems()); // [ao thun]

        List<String> tuBenNgoai = don.getItems();
        try {
            tuBenNgoai.add("hang la");
        } catch (Exception e) {
            IO.println("khong sua duoc list tra ve: " + e.getClass().getSimpleName()); // UnsupportedOperationException
        }
        IO.println("items cua don van     : " + don.getItems()); // [ao thun]
    }
}
sau khi sua list goc : [ao thun]
khong sua duoc list tra ve: UnsupportedOperationException
items cua don van     : [ao thun]

List.copyOf — công cụ chính

  • Trả về snapshot bất biến: list gốc đổi sau đó không ảnh hưởng gì (dòng "sau khi sửa list gốc" vẫn là [ao thun]).
  • Mọi thao tác sửa trên list trả về ném UnsupportedOperationException (đã kiểm chứng thật ở trên).
  • Ném NullPointerException nếu collection hoặc bất kỳ phần tử nào là null — vừa là điểm cần biết, vừa là lá chắn dữ liệu bẩn (bài tập 12).
  • Muốn bản mutable để tự do sửa: new ArrayList<>(items) — nhưng khi đó bạn tự chịu trách nhiệm copy đúng chỗ.

Về bản chất, đây cũng là câu chuyện reference đã học ở Biến trong Java — mục 7: gán this.items = items chỉ copy địa chỉ, hai bên cùng trỏ một list. Copy phòng thủ tạo một object mới thật sự.

Copy nông vs copy sâu: List.copyOf chỉ copy một lớp ngoài cùng. Nếu phần tử là object mutable (ví dụ List<List<String>>, List<int[]>), bên ngoài vẫn sửa được ruột của từng phần tử. Cách xử lý: copy sâu từng phần tử, hoặc tốt hơn — làm phần tử cũng immutable. So sánh shallow/deep copy ở Biến trong Java — mục 17.

7. Record & bất biến nông Hay hỏi phỏng vấn

Record (Java 16+, JEP 395) là cú pháp gọn để khai báo data carrier. Compiler tự sinh: field private final cho từng component, accessor cùng tên, equals/hashCode/toString. Không có setter — record mặc định bất biến.

Nhưng chỉ bất biến nông (shallowly immutable): field là final, còn nếu field trỏ tới list/array/object mutable thì ruột của chúng vẫn sửa được. Đúng như tài liệu JDK mô tả: record là "shallowly immutable, transparent carrier".

import java.util.ArrayList;
import java.util.List;

public class ProductionDemo {
    record Order(String code, List<String> items) {}

    public static void main() {
        List<String> goc = new ArrayList<>(List.of("ao thun", "quan jean"));
        Order don = new Order("DH-001", goc);
        goc.add("giay");
        IO.println("items cua don: " + don.items()); // [ao thun, quan jean, giay]
        IO.println("record 'bat bien' nhung da bi doi!");
    }
}
items cua don: [ao thun, quan jean, giay]
record 'bat bien' nhung da bi doi!

Cách sửa chuẩn: copy phòng thủ trong compact constructor. Record cho phép viết constructor rút gọn không cần danh sách tham số; bạn validate và chuẩn hóa, compiler tự gán field ở cuối:

import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

        Order {

            lay.add("mu");

                + new Order("DH-001", List.of("ao", "quan")).equals(new Order("DH-001", List.of("ao", "quan")))); // true
    }
}

8. Lợi ích của immutable Production

Vì sao production ưu tiên immutable cho value object/DTO? Bốn lợi ích lớn:

  1. Thread-safe mặc định — không ai sửa được state thì nhiều thread chỉ đọc cùng lúc không đụng độ. Không cần lock, không cần lo thứ tự truy cập; đây là lý do String, Integer, LocalDate an toàn khắp nơi. (Concurrency học ở 4.2 Threads & concurrency.)
  2. Làm key HashMap an toàn — key mutable là bẫy chết người (xem ngay dưới).
  3. Cache/chia sẻ thoải mái — một hằng như BigDecimal.ZERO, List.of() có thể chia sẻ cho mọi nơi vì không ai phá được.
  4. Dễ suy luận và test — nhìn constructor là biết toàn bộ state tồn tại mãi; không cần dựng lại ngữ cảnh chuỗi gọi method.

Vì sao key HashMap phải immutable?

HashMap tìm bucket theo hashCode tại thời điểm put. Nếu key đổi state sau đó, hashCode đổi theo và map "mất" entry dù dữ liệu vẫn nằm đâu đó. Record làm key lý tưởng vì bất biến + tự sinh equals/hashCode (chi tiết ở 2.6 equals / hashCode / toString):

import java.util.HashMap;
import java.util.Map;

public class ProductionDemo {
    record User(String email, String name) {}

    public static void main() {
        Map<User, String> quyen = new HashMap<>();
        quyen.put(new User("an@example.com", "An"), "ADMIN");
        IO.println("tra cuu bang object moi cung gia tri: "
                + quyen.get(new User("an@example.com", "An"))); // ADMIN
        IO.println("immutable key: hash khong bao gio doi");
    }
}
tra cuu bang object moi cung gia tri: ADMIN
immutable key: hash khong bao gio doi

Đổi sang key mutable — setter đổi email, hashCode đổi — và entry biến mất khỏi tầm tra cứu:

import java.util.HashMap;
import java.util.Map;

public class User {
    private String email;

    User(String email) {
        this.email = email;
    }

    void setEmail(String email) {
        this.email = email;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof User other && email.equals(other.email);
    }

    @Override
    public int hashCode() {
        return email.hashCode();
    }

    public static void main() {
        Map<User, String> quyen = new HashMap<>();
        User an = new User("an@example.com");
        quyen.put(an, "ADMIN");

        IO.println("truoc khi doi: " + quyen.get(new User("an@example.com"))); // ADMIN
        an.setEmail("an2@example.com");
        IO.println("sau khi doi   : " + quyen.get(new User("an@example.com"))); // null
        IO.println("sau khi doi   : " + quyen.get(an));                         // null
    }
}

9. Đánh đổi & khi nào không nên immutable

Immutable không phải viên đạn bạc. Các đánh đổi cần biết để chọn đúng chỗ:

  • Tạo nhiều object — mỗi lần "sửa" là một object mới, tăng áp lực GC. Với value object nhỏ (Money, DTO) chi phí này thường không đáng kể so với lợi ích an toàn và dễ đọc.
  • Cập nhật liên tục trong vòng lặp — cộng dồn hàng triệu lần bằng object mới là lãng phí; dùng biến local mutable rồi "chốt" thành immutable object khi xong.
  • API/build tool cần mutable — StringBuilder tồn tại để nối chuỗi trong vòng lặp, thay vì tạo vô số String.
  • Framework cần set field — JPA/Hibernate cần entity mutable: chúng tạo proxy, set field qua reflection, theo dõi dirty state. Đừng cố ép entity immutable; hãy giữ entity trong tầng persistence và trả DTO immutable ra ngoài (mục 10). Nội dung này học ở giai đoạn backend (5 Backend stack).
  • Cấu trúc lồng sâu — copy sâu tốn kém và dễ viết thiếu; ưu tiên thiết kế phần tử cũng immutable để copy nông là đủ.

10. Patterns trong production Production

Các pattern dưới đây gặp hàng ngày trong codebase thật:

  • Value object — object nhỏ, bất biến, so sánh theo giá trị: Money, Email, PhoneNumber, DateRange. Đây là nơi immutability + validate + defensive copy tỏa sáng nhất.
  • DTO bằng record — request/response của API là record immutable; Jackson hiện đại (2.12+) deserialize record được, không cần setter. Đừng dùng Map<String, Object> mơ hồ làm DTO.
  • Không trả entity ra ngoài — entity mutable, gắn với persistence context (lazy loading, proxy); serialize thẳng vừa lộ cấu trúc DB, vừa cho client cơ hội sửa state ngoài ý muốn. Hãy map sang DTO record rồi trả.
  • Builder khi nhiều field — immutable object có 5-10 field khó dựng bằng constructor (nhiều tổ hợp, boolean khó đọc). Builder cho "named arguments" rồi build() ra object immutable. Chi tiết ở 2.8 SOLID & design patterns.
  • Static factory + withX() — Money.vnd(250_000) rõ nghĩa hơn constructor; withAmount(...) tạo bản sao có một field đổi — đúng phong cách java.time (plusDays, withYear).
Quy tắc thực dụng: dữ liệu băng qua nhiều tầng (API → service → repository) nên immutable; state sống trong một tầng hẹp có thể mutable. Càng ít nơi sửa được state, càng ít bug "ai đổi cái này?".

Field #private thật sự kín: in trực tiếp không thấy, truy cập bằng tên động không được (chạy thật bằng Node v22):

class User {
  #balance = 0;

  deposit(amount) {
    if (amount <= 0) throw new Error("amount phai duong");
    this.#balance += amount;
  }

  getBalance() {
    return this.#balance;
  }

const u = new User();
u.deposit(100);
console.log(u.getBalance());  // 100
console.log(u["#balance"]);   // undefined - khong truy cap duoc tu ngoai

Object.freeze chỉ nông — thuộc tính của object bị khóa, nhưng mảng/object bên trong vẫn sửa bình thường (chạy thật, chế độ strict nên gán field ném TypeError):

"use strict";

const order = Object.freeze({ code: "DH-01", items: ["ao thun"] });

try {
  order.code = "DH-02";
} catch (e) {
  console.log("strict mode: " + e.constructor.name); // TypeError
}

order.items.push("quan jean"); // items la object rieng, freeze chi khoa lop ngoai
console.log(order.code);       // DH-01
console.log(order.items);      // [ 'ao thun', 'quan jean' ]

Spread copy cũng nông y hệt List.copyOf cho một lớp, nhưng spread còn không ngăn được sửa bản copy. Muốn bất biến thật trong JS phải copy sâu (structuredClone) hoặc dùng object lồng immutable:

const goc = { code: "DH-01", items: ["ao thun"] };
const copy = { ...goc };

copy.code = "DH-02";           // copy doi, goc khong doi
copy.items.push("quan jean");  // items chi duoc copy reference

console.log(goc.code);  // DH-01
console.log(goc.items); // [ 'ao thun', 'quan jean' ]
Điểm chung của cả hai ngôn ngữ: copy một lớp chưa đủ. Java có lợi thế record + List.copyOf + final cấp ngôn ngữ để làm immutable rẻ hơn; JS phải tự kỷ luật hoặc dùng thư viện.

13. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Encapsulation và abstraction khác nhau thế nào?
Encapsulation là cơ chế giấu chi tiết bên trong (private field, method công khai, validate); abstraction là cách chọn mức trừu tượng phù hợp để lộ ra bên ngoài. Ví dụ: vô lăng và bàn đạp là abstraction của việc lái xe; nắp ca-pô đóng kín, không cho bạn chọc vào động cơ là encapsulation. Hai khái niệm bổ trợ chứ không thay thế nhau.
Câu 2. Chỉ cần private field + getter/setter là đã đóng gói tốt chưa?
Chưa. Nếu getter/setter chỉ chuyển tiếp thẳng field, client vẫn phụ thuộc cấu trúc nội bộ và invariant vẫn bị phá nếu setter không validate. Đóng gói tốt là lộ ra hành vi nghiệp vụ (deposit, withdraw, cancel) và bảo vệ dữ liệu; setter chỉ tồn tại khi "gán giá trị bất kỳ" thật sự là hành vi hợp lệ (DTO/config).
Câu 3. Vì sao field nên private?
Ba lý do: chặn truy cập/sửa tùy tiện để giữ invariant; cho phép đổi implementation bên trong (kiểu dữ liệu, cache, cách tính) mà không phá client; và giới hạn điểm thay đổi logic vào một chỗ. Nhớ thêm: private trong Java là theo class, nên hai object cùng class vẫn truy cập private của nhau.
Câu 4. Các bước tạo một immutable class?
Năm bước: (1) class final; (2) mọi field private final; (3) không setter — method "sửa" trả object mới; (4) validate mọi thứ trong constructor; (5) defensive copy field mutable khi nhận (constructor) và khi trả (getter). Thiếu bước 5 là lỗ hổng phổ biến nhất.
Câu 5. Biến final đã đảm bảo object bất biến chưa? Vì sao?
Chưa. final khóa reference — biến chỉ gán một lần — nhưng không khóa nội dung object. final List<String> items = new ArrayList<>() vẫn add/remove bình thường; chỉ khi gán lại items = ... mới lỗi compile. Muốn bất biến phải dùng object immutable hoặc defensive copy.
Câu 6. Defensive copy là gì? Khi nào cần?
Là sao chép dữ liệu mutable ở biên của object — trong constructor khi nhận vào và trong getter khi trả ra — để bên ngoài không giữ được reference tới state nội bộ. Cần khi field là mutable: List, Map, mảng, object mutable. Với field immutable (String, record...), copy là dư thừa.
Câu 7. Record có bất biến hoàn toàn không?
Không. Record bất biến nông: các component là field final và không có setter, nhưng nếu component là List, mảng hay object mutable thì nội dung vẫn sửa được từ bên ngoài. Cần defensive copy trong compact constructor (và override accessor nếu muốn chặn cả đường trả ra).
Câu 8. Vì sao immutable object thread-safe?
Vì sau khi tạo không có thao tác nào thay đổi state, nên nhiều thread chỉ đọc đồng thời không tranh chấp gì — không cần lock, không có race condition. Đây là lý do String, Integer, LocalDate dùng an toàn ở khắp nơi, kể cả chia sẻ giữa các thread.
Câu 9. Vì sao String immutable?
Bốn lý do chính: an toàn khi chia sẻ qua string pool (nhiều biến cùng trỏ một chuỗi không sợ ai sửa); hashCode được cache nên dùng làm key HashMap rất hiệu quả; thread-safe; và an toàn bảo mật — path, URL, tên class, mật khẩu không bị sửa lén sau khi kiểm tra. Chi tiết ở Biến trong Java — mục 14.
Câu 10. Vì sao key HashMap phải immutable?
Vì HashMap chọn bucket theo hashCode tại thời điểm put. Key mutable đổi state → hashCode đổi → lần get sau tìm sai bucket và trả null dù entry vẫn còn. Record, String, wrapper class là key lý tưởng (kèm equals/hashCode đúng — xem 2.6).
Câu 11. Tell-don't-ask là gì? Liên hệ gì tới encapsulation?
Thay vì "hỏi" dữ liệu rồi tự xử lý bên ngoài (getBalance rồi setBalance), hãy "bảo" object làm việc (withdraw). Cách này giữ quy tắc nghiệp vụ và invariant bên trong class, tránh mỗi call site copy lại một phiên bản logic — đúng tinh thần encapsulation.
Câu 12. Copy constructor là gì? Java có tự sinh không?
Là constructor nhận một object cùng loại và sao chép state của nó, ví dụ new ArrayList<>(otherList). Java không tự sinh copy constructor (khác C++); muốn phải tự viết, và nếu object có field mutable thì cần copy sâu để tránh chia sẻ reference.
Câu 13. Unmodifiable collection và immutable collection khác nhau thế nào?
Unmodifiable thường là view: chặn sửa qua nó nhưng collection gốc đổi thì view đổi theo. Immutable là snapshot độc lập, không bao giờ đổi — List.copyOf và List.of cho snapshot như vậy. Muốn chia sẻ an toàn giữa các nơi, dùng bản immutable.
Câu 14. Vì sao class immutable nên được đánh dấu final?
Nếu cho phép kế thừa, subclass có thể thêm field mutable, override method để thay đổi hành vi, hoặc phá invariant mà class cha không kiểm soát được. final chặn con đường đó. Cách thay thế: giữ constructor private và cung cấp static factory.
Câu 15. Validate trong constructor có phải là một phần của encapsulation?
Có. Encapsulation không chỉ là giấu field mà còn là đảm bảo object luôn ở trạng thái hợp lệ. Validate trong constructor (fail fast) nghĩa là object sinh ra đã đúng invariant; mọi method sau đó không cần kiểm tra lại và không có "cửa sổ" object ở trạng thái hỏng.

Nâng cao (Junior+)

Câu 16. Khi nào nên có setter?
Khi "gán giá trị bất kỳ" thật sự hợp lệ: DTO/request object cho framework deserialize, config đơn giản, hoặc field không có invariant. Kể cả vậy, setter phải validate nếu field có điều kiện ràng buộc. Với entity/value object, ưu tiên method nghiệp vụ thay vì setter.
Câu 17. Nhược điểm của immutable object là gì?
Mỗi thay đổi tạo object mới nên tăng lượng rác cho GC; cập nhật nhiều field liên tục phải "copy rồi sửa", có thể dùng builder cho gọn; một số framework (JPA) bắt buộc entity mutable. Với value object nhỏ, chi phí này thường nhỏ hơn nhiều so với lợi ích an toàn và dễ đọc.
Câu 18. List.copyOf khác List.of và new ArrayList<>(...) thế nào?
List.of tạo list bất biến từ các phần tử truyền vào; List.copyOf tạo snapshot bất biến từ một collection có sẵn. Cả hai đều unmodifiable và đều ném NullPointerException khi gặp null. new ArrayList<>(...) là bản sao mutable — dùng khi cần tiếp tục sửa.
Câu 19. Vì sao không nên trả entity trực tiếp ra API?
Entity thường mutable, gắn với persistence context (lazy loading, proxy) và phản ánh cấu trúc DB — serialize thẳng dễ lộ schema, lỗi lazy initialization, và client có thể gửi ngược entity đã bị sửa. Chuẩn production là map sang DTO immutable (record) rồi trả ra ngoài.
Câu 20. Pattern withX() là gì? Vì sao object bất biến cần nó?
withX(value) trả về object mới giống hệt bản cũ nhưng field X đổi giá trị, các field khác giữ nguyên (kiểu LocalDate.withYear, Money.withAmount). Vì object bất biến không có setter, đây là cách "cập nhật" hợp lệ — dùng nội bộ để tái sử dụng logic tạo object và giữ validate ở một chỗ.

Bài 1 — getter trả collection nội bộ 
import java.util.ArrayList;
import java.util.List;

public class Order {
    private final List<String> items = new ArrayList<>(List.of("ao"));

    List<String> getItems() {
        return items;
    }

    public static void main() {
        Order don = new Order();
        don.getItems().add("quan");
        IO.println(don.getItems());
    }
}
In ra [ao, quan]. getItems() trả thẳng reference của list nội bộ, nên add("quan") bên ngoài sửa chính state của Order. Sửa bằng return List.copyOf(items); — khi đó lời gọi add sẽ ném UnsupportedOperationException thay vì âm thầm phá object.

Bài 3 — final List vẫn sửa được nội dung 
import java.util.ArrayList;
import java.util.List;

public class VariablesDemo {

In ra [ao, quan] rồi 2. Không có lỗi nào vì final chỉ khóa reference; nội dung list vẫn mutable. Muốn list thật sự bất biến phải dùng List.of/List.copyOf (và khi đó add ném UnsupportedOperationException).
Bài 4 — viết Money.plus và đoán output 
public class ProductionDemo {
    record Money(long amount, String currency) {
        Money plus(Money other) {
            return new Money(amount + other.amount, currency);
        }
    }

    public static void main() {
        Money a = new Money(100_000, "VND");
        Money b = new Money(50_000, "VND");
        Money c = a.plus(b);
        IO.println(a);
        IO.println(c);
        IO.println(a.equals(c));
    }
}
In ra:
Money[amount=100000, currency=VND]
Money[amount=150000, currency=VND]
false
plus trả object mới nên a không đổi; a.equals(c) là false vì amount khác nhau. Nếu so hai object cùng amount + currency, record trả true.
Bài 5 — tìm chỗ thiếu defensive copy 
public class Order {
    private final List<String> items;

    Order(List<String> items) {
        this.items = items;
    }

    List<String> getItems() {
        return items;
    }
}
Thiếu copy ở cả hai đầu: constructor nhận thẳng list của bên ngoài (họ sửa sau khi tạo cũng ảnh hưởng object), và getter trả thẳng list nội bộ. Sửa: this.items = List.copyOf(items); và return List.copyOf(items);.
Bài 6 — chọn record hay class thường? 
// (a) Du lieu toa do 2D chi doc, so sanh theo gia tri
// (b) Tai khoan game co mau/level thay doi lien tuc khi choi
// (c) Money can validate trong constructor + plus/withAmount tra object moi
(a) record — chỉ chở dữ liệu, so sánh giá trị, bất biến. (b) class thường — state thay đổi liên tục theo nghiệp vụ, cần method cập nhật. (c) record — record vẫn validate được trong compact constructor và viết được method trả object mới; chỉ chuyển sang class khi cần kế thừa hoặc logic phình to.
Bài 7 — phương thức withAmount() 
public class ProductionDemo {
    record Money(long amount, String currency) {
        Money withAmount(long newAmount) {
            return new Money(newAmount, currency);
        }
    }

    public static void main() {
        Money m = new Money(100_000, "VND");
        Money m2 = m.withAmount(0);
        IO.println(m);
        IO.println(m2);

}
In ra:
Money[amount=100000, currency=VND]
Money[amount=0, currency=VND]
false
m == m2 là false vì withAmount tạo object mới — đúng bản chất bất biến. Muốn so giá trị phải dùng equals (và ở đây cũng false vì amount khác).
Bài 8 — setter phá invariant 
public class User {
    private long balance;

    User(long balance) {
        this.balance = balance;
    }

    long getBalance() {
        return balance;
    }

    void setBalance(long balance) {
        this.balance = balance;
    }

    public static void main() {
        User u = new User(100_000);
        u.setBalance(-50_000);
        IO.println(u.getBalance());
    }
}
In ra -50000. Setter không validate đã phá invariant "số dư không âm"; object rơi vào trạng thái vô lý mà không báo lỗi. Sửa: validate trong setter (như mục 2) hoặc bỏ setter, thay bằng withdraw/deposit.
Bài 9 — record + copy phòng thủ trong compact constructor 
import java.util.ArrayList;
import java.util.List;

public class ProductionDemo {
    record Order(String code, List<String> items) {
        Order {
            items = List.copyOf(items);
        }
    }

    public static void main() {
        List<String> goc = new ArrayList<>(List.of("ao"));
        Order o = new Order("DH-01", goc);
        goc.add("quan");
        IO.println(o.items());
    }
}
In ra [ao]. Compact constructor đã copy list lúc nhận, nên việc goc.add("quan") sau đó không ảnh hưởng record. Nếu bỏ dòng items = List.copyOf(items); thì in ra [ao, quan].
Bài 10 — record chứa mảng mutable 
public class ProductionDemo {
    record Order(String code, int[] quantities) {}

    public static void main() {
        int[] soLuong = {1, 2};
        Order don = new Order("DH-01", soLuong);
        soLuong[0] = 99;
        IO.println(don.quantities()[0]);
        IO.println(java.util.Arrays.toString(don.quantities()));
    }
}
In ra 99 rồi [99, 2]. Mảng không bao giờ bất biến, nên bên ngoài sửa lọt vào record — bất biến nông. Sửa: quantities = quantities.clone(); trong compact constructor và override accessor trả quantities.clone(); khi đó in ra 1 rồi [1, 2].
Bài 11 — mutable key của HashMap 
import java.util.HashMap;
import java.util.Map;

public class User {
    private String email;

    User(String email) {
        this.email = email;
    }

    void setEmail(String email) {
        this.email = email;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof User other && email.equals(other.email);
    }

    @Override
    public int hashCode() {
        return email.hashCode();
    }

    public static void main() {
        Map<User, String> quyen = new HashMap<>();
        User an = new User("an@example.com");
        quyen.put(an, "ADMIN");
        IO.println(quyen.get(new User("an@example.com")));
        an.setEmail("an2@example.com");
        IO.println(quyen.get(new User("an@example.com")));
        IO.println(quyen.get(an));
    }
}
In ra ADMIN, rồi null, rồi null. Sau khi đổi email, hashCode của key thay đổi nên cả key mới cùng giá trị cũ lẫn chính object key đều tìm sai bucket. Đây là lý do key HashMap phải immutable.
Bài 12 — List.copyOf gặp phần tử null 
import java.util.Arrays;
import java.util.List;

public class ProductionDemo {
    public static void main() {
        try {
            List<String> items = List.copyOf(Arrays.asList("ao", null));
            IO.println(items);
        } catch (NullPointerException e) {
            IO.println("NPE: " + e.getMessage());
        }
    }
}
In ra NPE: null — List.copyOf ném NullPointerException ngay khi thấy phần tử null (không tạo ra list chứa null). Nếu đây là dữ liệu đầu vào, hãy validate trước khi copy và báo lỗi rõ nghĩa hơn.

Checklist tự đánh giá trước phỏng vấn

  • Giải thích được encapsulation và immutability khác nhau thế nào, kèm ví dụ ATM.
  • Kể đủ 4 mức access modifier và mặc định field nên là gì.
  • Viết được immutable class đủ 5 bước không cần tra cứu.
  • Giải thích vì sao final chưa đủ, kèm ví dụ final List vẫn add được.
  • Viết được defensive copy ở cả constructor lẫn getter bằng List.copyOf.
  • Giải thích vì sao record chỉ bất biến nông và sửa được bằng compact constructor.
  • Nhớ bẫy không được gán this.field trong compact constructor — gán lại parameter.
  • Trả lời được vì sao immutable thread-safe và vì sao key HashMap phải immutable.
  • Nêu được 3 trường hợp không nên có setter (immutable, tell-don't-ask, id/createdAt/status).
  • Phân biệt copy nông và copy sâu, biết khi nào cần cái nào.
  • Biết unmodifiable view khác immutable snapshot ở điểm nào.
  • Liệt kê được 2-3 pattern production dùng immutable (value object, DTO record, config).
