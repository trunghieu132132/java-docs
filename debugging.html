Debugging — tìm và sửa bug trong Java

Viết code chạy được là chuyện thường; tìm ra vì sao code chạy sai mới là kỹ năng được trả lương cao nhất của lập trình viên. Debugging không phải là ngồi đoán mò rồi sửa thử — đó là một quy trình có phương pháp: tái hiện, khoanh vùng, sửa gốc, kiểm chứng, phòng ngừa. 1. Tổng quan & cách học

Hay hỏi phỏng vấn Junior+ Production

Mức độ bắt buộc của chủ đề 4.7 (phỏng vấn: cao · production: bắt buộc):

  • Phải làm được — đặt breakpoint và step qua code trong IntelliJ; đọc stack trace tìm đúng dòng gây lỗi; tái hiện bug bằng một ví dụ nhỏ; sửa một thứ rồi chạy lại kiểm chứng; viết test tái hiện trước khi fix.
  • Phải hiểu — quy trình 5 bước reproduce → isolate → fix → verify → prevent; conditional breakpoint/logpoint/exception breakpoint; vì sao println rải khắp nơi là cách debug tồi; vì sao race condition "không thấy" khi chạy máy mình; helpful NullPointerException (JEP 358) đọc thế nào.
  • Nhận biết — thread dump/heap dump và các lệnh jps/jstack/jcmd; remote debug (JDWP) và lý do không bật trên production; debugger của Node.js (node --inspect + Chrome DevTools) để so sánh.

Quy trình chuẩn mà mọi kỹ sư giỏi đều dùng (chi tiết ở mục 2):

  1. Reproduce — làm bug xuất hiện lại một cách ổn định, với ví dụ nhỏ nhất có thể.
  2. Isolate — thu hẹp phạm vi: dòng code nào, điều kiện nào, dữ liệu nào gây ra.
  3. Fix — sửa nguyên nhân gốc, mỗi lần chỉ đổi một thứ.
  4. Verify — chạy test tái hiện + toàn bộ test cũ để chắc không làm vỡ chỗ khác.
  5. Prevent — thêm test, thêm validate/log, rút ra bài học để bug không quay lại.

Cách học hiệu quả nhất:

  1. Đọc xong mục 6 — Đọc stack trace rồi quay lại thử đọc mọi trace trong trang này trước khi xem phần giải thích.
  2. Tự chạy lại các ví dụ trong IDE/terminal, cố tình tạo lỗi rồi sửa — debug là kỹ năng tay chân, không phải lý thuyết.
  3. Làm Bài tập tìm bug trước, chỉ mở đáp án sau khi đã đoán.
  4. Ôn nhanh Cheat sheet (shortcut + lệnh dòng lệnh) trước buổi phỏng vấn.
Ví dụ dùng IO.println(...) — cách viết gọn của JDK 25 (JEP 512), tương đương System.out.println(...) mà bạn sẽ thấy trong tài liệu cũ. Output trong trang là kết quả chạy thật: stack trace lấy từ class biên dịch với javac -g (đủ debug info), các ví dụ khác chạy bằng java TenFile.java.

2. Quy trình tìm bug: reproduce → isolate → fix → verify → prevent Junior+

Người mới thường nhảy thẳng vào bước "fix" khi chưa hiểu bug. Người có kinh nghiệm đi tuần tự qua 5 bước — mỗi bước trả lời một câu hỏi cụ thể:

BướcCâu hỏi cần trả lờiCông cụ / cách làm
1. ReproduceLàm sao lỗi xuất hiện lại? Có ổn định không?Chạy lại đúng input; viết test nhỏ; đọc bug report; giảm input về mức tối thiểu
2. IsolateDòng nào, điều kiện nào, dữ liệu nào gây lỗi?Breakpoint/step; chia đôi dữ liệu; comment bớt code; git bisect; so sánh với code chạy đúng
3. FixNguyên nhân gốc là gì? Sửa chỗ nào?Sửa một thay đổi mỗi lần; ưu tiên sửa gốc thay vì che triệu chứng
4. VerifyBug hết chưa? Có làm vỡ chỗ khác không?Chạy test tái hiện + toàn bộ test cũ; thử các ca biên; chạy lại nhiều lần với bug race
5. PreventLàm sao để bug này không tái diễn?Giữ test tái hiện làm regression test; thêm validate/log; review lại thiết kế

Ví dụ thực tế với project "quản lý đơn hàng": khách báo phí vận chuyển của đơn 600.000đ bị tính sai.

  • Reproduce: tạo đơn có tổng tiền đúng 600.000đ, chạy lại — luôn ra 30.000đ, có thể tái hiện 100%.
  • Isolate: breakpoint ở OrderService.tinhPhi; thấy biến tongTien = 600000 nhưng điều kiện miễn phí không kích hoạt — vì code viết if (tongTien > 500_000) (sai: phải là >=).
  • Fix: sửa một ký tự: > thành >=. Không sửa gì thêm.
  • Verify: chạy lại 600.000đ → 0đ; thử 499.999đ → 30.000đ; chạy các test cũ của OrderService.
  • Prevent: thêm test biên tinhPhi(500_000) == 0 và tinhPhi(499_999) == 30_000 để lần sau sửa code không âm thầm phá mốc này.
Bug không reproduce được là bug chưa hiểu. Nếu bạn không làm lỗi xuất hiện lại, mọi "fix" chỉ là đoán. Trường hợp xấu nhất — bug production không tái hiện ở local — hãy đọc tiếp mục 9 (log, metrics, dump) thay vì sửa mù.

3. Debug với IntelliJ debugger Junior+

Nếu chưa quen project IntelliJ, xem trước Giai đoạn 0 — Chuẩn bị môi trường (mục 0.2 IntelliJ IDEA). Dưới đây là vòng lặp debug cơ bản mà bạn sẽ dùng hằng ngày.

3.1 Đặt breakpoint và chạy Debug

  1. Click vào gutter (lề trái cạnh số dòng) để đặt breakpoint — chấm đỏ xuất hiện. Phím tắt: Ctrl+F8 (Windows/Linux) / Cmd+F8 (macOS).
  2. Chạy chương trình bằng nút Debug (con bọ) thay vì Run: Shift+F9 (Win/Linux) / Ctrl+D (macOS).
  3. Chương trình dừng trước khi dòng có breakpoint được thực thi. Dòng hiện tại được tô sáng.
  4. Cửa sổ Debug mở ra với các panel: Frames (call stack), Variables (biến của frame đang chọn), Watches, Console.

Breakpoint dòng là loại đơn giản nhất: cứ chạy tới dòng đó là dừng. Nhược điểm: nếu dòng nằm trong vòng lặp 1 triệu lần, bạn phải bấm Resume 1 triệu lần — đó là lý do có breakpoint nâng cao ở mục sau.

4. Breakpoint nâng cao Junior+

Ba loại breakpoint sau giải quyết 90% tình huống mà breakpoint dòng thường bó tay. Mở hộp thoại quản lý bằng Ctrl+Shift+F8 (Win/Linux) / Cmd+Shift+F8 (macOS) — View Breakpoints.

4.1 Conditional breakpoint — chỉ dừng khi điều kiện đúng

Chuột phải vào breakpoint → gõ vào ô Condition một biểu thức boolean. Debugger chỉ dừng khi biểu thức trả true. Ví dụ cho vòng lặp for (int i = 0; i < 1_000_000; i++):

i == 987_654                  // chi dung o lan lap thu 987.654
donHang.size() > 100          // chi dung khi gio hang lon
"DH-001".equals(don.getCode()) // chi dung voi don hang dich
tongTien % 1000 == 0          // chi dung khi tong la boi so cua 1000
  • Điều kiện được đánh giá mỗi lần chạy qua dòng — đừng viết biểu thức có side effect (ví dụ list.add(x) == 5), vì nó sẽ chạy cả triệu lần và làm hỏng chương trình.
  • Biểu thức chạy trong ngữ cảnh frame hiện tại nên gọi được method của object: don.getTongTien() > 1_000_000.
  • Dùng khi bug chỉ xảy ra với một dòng dữ liệu đặc biệt giữa hàng nghìn dòng bình thường.

4.2 Logpoint — in log mà không dừng chương trình

Chuột phải breakpoint → bỏ tick Suspend → tick Evaluate and log và nhập message. Cách nhanh khác: giữ Shift và click gutter. Logpoint in ra Console đúng như println nhưng không dừng chương trình, nên vòng lặp 1 triệu lần chạy hết tốc lực. Trong ô message có thể chèn biểu thức bằng cặp ngoặc nhọn:

i = {i}, tong = {tongTien}, don = {don.getCode()}

Logpoint là cách "trung dung" giữa println (phải sửa code, xóa sau khi xong) và breakpoint thường (dừng quá nhiều). Nhớ tắt/xóa logpoint trước khi commit — nó chỉ là công cụ debug, không phải logging production (xem 4.5 Logging).

4.3 Exception breakpoint — dừng tại nơi exception được ném

Vào View Breakpoints → + → Java Exception Breakpoint, chọn:

  • Any Exception — dừng ở mọi exception, kể cả những exception bị nuốt im lặng trong try/catch. Rất mạnh nhưng ồn (JDK ném exception nội bộ liên tục), nên dùng khi bí.
  • Exception cụ thể — ví dụ NullPointerException, IllegalStateException. Cân bằng nhất, dùng thường xuyên.
  • Caught / Uncaught — chọn chỉ dừng ở exception bị bắt (caught) hay chỉ ở exception thoát ra ngoài (uncaught). Bug production thường là exception bị catch rồi nuốt — khi đó exception breakpoint với "Caught exception" là công cụ duy nhất tìm ra.
  • On throw / On catch — dừng ngay lúc ném (thấy được cả stack lúc tạo exception, tốt nhất để truy nguồn) hay lúc bắt.

So sánh nhanh khi nào dùng loại nào:

5. Watch & Evaluate Expression

Khi chương trình đã dừng, bạn có ba cách quan sát dữ liệu, mỗi cách hợp một việc:

  • Variables — toàn bộ biến của frame đang chọn, cập nhật sau mỗi bước. Click mũi tên để mở object tree; Collection (List/Set/Map) có chế độ xem dạng bảng (gõ tên class vào ô search để tìm phần tử, xem size).
  • Watches — ghim một biểu thức để xem lại ở mọi lần dừng. Ví dụ watch don.getItems().size(), tong % 100, list.contains(don). Biến ở frame khác vẫn xem được nếu còn trong scope.
  • Evaluate Expression (Alt/⌥+F8) — chạy biểu thức tùy ý trong ngữ cảnh frame hiện tại, kể cả gọi method. Đây là cách nhanh nhất để trả lời "nếu gọi method này ngay bây giờ thì kết quả là gì?".
Evaluate Expression có thể thay đổi chương trình. Biểu thức bạn gõ chạy thật trong process đang debug: list.remove(0), don.setTrangThai(...), hay gọi một API HTTP đều gây tác dụng phụ và làm sai lệch điều tra. Muốn xem giá trị thuần túy thì ưu tiên getter không side effect. Tương tự, chức năng Set Value (sửa biến ngay lúc debug) rất tiện để thử nhánh khác, nhưng nhớ restart trước khi kết luận kết quả.

Thứ tự thực hành tốt khi vừa dừng ở một điểm nghi ngờ:

  1. Nhìn Frames — mình đang ở đâu, ai gọi mình tới đây (xem mục 6).
  2. Nhìn Variables — so giá trị thực tế với giá trị bạn kỳ vọng khi đọc code.
  3. Điểm khác biệt đầu tiên giữa "kỳ vọng" và "thực tế" chính là bug hoặc nằm ngay trước đó.

6. Đọc stack trace thành thạo Hay hỏi phỏng vấn

Stack trace không đáng sợ — nó là bản đồ chỉ đường có sẵn mà nhiều người mới chỉ đọc mỗi dòng đầu rồi... bỏ qua. Quy tắc đọc:

  1. Dòng đầu: loại exception + message — đọc kỹ, message thường nói thẳng vấn đề.
  2. Các dòng at ...: chuỗi lời gọi từ nơi ném exception đi ra ngoài. Dòng trên cùng là nơi exception phát sinh.
  3. Tìm frame đầu tiên thuộc code của bạn (bỏ qua java.base/..., org.springframework...). Đó là điểm bắt đầu điều tra.
  4. Nếu có nhiều khối, khối "Caused by" bên dưới mới là nguyên nhân gốc; exception phía trên chỉ là lớp bọc.
  5. ... N more nghĩa là N frame bị lặp lại so với khối trên — không phải lỗi.

Ví dụ chạy thật (class BugDemo biên dịch với javac -g):

public class BugDemo {
    static int chia(int a, int b) {
        return a / b;
    }

    static int tinhTrungBinh(int tong, int soMon) {
        return chia(tong, soMon);
    }

    public static void main() {
        IO.println(tinhTrungBinh(10, 0));
    }
}
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at BugDemo.chia(BugDemo.java:3)
	at BugDemo.tinhTrungBinh(BugDemo.java:7)
	at BugDemo.main(BugDemo.java:11)

Đọc trace này trong 10 giây: lỗi chia cho 0 tại BugDemo.java:3 (method chia), được gọi từ dòng 7 (tinhTrungBinh), rồi từ dòng 11 (main). Bạn biết chính xác cần xem dòng 3 và câu hỏi tiếp theo: "vì sao b lại bằng 0?" — câu trả lời nằm ở dòng 7 và 11, nơi truyền tham số.

Đừng dừng ở IllegalStateException — đó chỉ là thông điệp nghiệp vụ. Dòng Caused by: NumberFormatException: For input string: "12a" mới nói sự thật: chuỗi "12a" không parse được thành số, ném từ dòng 4. 6.2 Helpful NullPointerException — JEP 358

Từ JDK 14 (JEP 358, bật mặc định từ JDK 15), NullPointerException nói rõ cái gì null thay vì chỉ có chữ "null". Ví dụ chạy thật — mã nguồn:

public class BugDemo {
    static class Order {
        String code;
    }

    static int doDaiMa(Order don) {
        return don.code.length();
    }

    public static void main() {
        Order don = null;
        IO.println(doDaiMa(don));
    }
}
Exception in thread "main" java.lang.NullPointerException: Cannot read field "code" because "don" is null
	at BugDemo.doDaiMa(BugDemo.java:7)
	at BugDemo.main(BugDemo.java:12)

Message Cannot read field "code" because "don" is null chỉ đích danh biến don — không cần debugger cũng biết thủ phạm. Ba dạng message thường gặp (chạy thật, bắt exception để in message):

1: Cannot read field "code" because "don" is null
2: Cannot invoke "String.length()" because "ten" is null
3: Cannot read the array length because "a" is null

Vài lưu ý thực chiến:

  • Tắt được: chạy java -XX:-ShowCodeDetailsInExceptionMessages BugDemo sẽ chỉ còn java.lang.NullPointerException trần — hữu ích khi bạn muốn message gọn, nhưng đừng tắt trong lúc debug.
  • Thấy <local0>/<parameter1>? Nghĩa là class thiếu debug info về tên biến. Chế độ chạy file đơn java BugDemo.java hoặc javac mặc định (không có -g) sẽ hiển thị tên slot thay vì tên biến; biên dịch với javac -g (IntelliJ luôn bật) sẽ hiện đúng tên như ví dụ trên.
  • ArrayIndexOutOfBoundsException cũng có message chi tiết từ JDK 9: Index 3 out of bounds for length 3 — thấy ngay index nào vượt biên (dùng ở mục 7.2).
Tự luyện: với mỗi trace bạn gặp trong công việc, viết ra giấy 3 câu trả lời — (1) exception gì, (2) frame đầu tiên thuộc code mình ở dòng nào, (3) câu hỏi cần trả lời tiếp theo. Sau vài chục lần, bạn sẽ đọc trace nhanh như đọc tiêu đề báo.

7. Các lỗi kinh điển khi debug Hay hỏi phỏng vấn

Sáu nhóm lỗi dưới đây chiếm phần lớn thời gian debug của một Java backend developer. Nhận diện được chúng từ triệu chứng sẽ tiết kiệm cho bạn rất nhiều giờ.

7.1 NullPointerException — vẫn là "vua" của mọi bug

NPE xảy ra khi bạn gọi method/đọc field trên reference đang là null. Các nguồn null phổ biến:

  • Method trả null: map.get(key) không có key, findById(...) không tìm thấy, API trả null.
  • Field chưa khởi tạo (object tạo ra nhưng field còn null) — khác JavaScript, field object mặc định là null, còn field primitive mặc định là 0/false.
  • Autoboxing: Integer null bị unbox thành int (ví dụ cộng vào biến int) → NPE ngay tại phép toán.
  • Chuỗi method: một mắt xích trả null làm cả chain nổ (xem Methods — mục 10).

Cách xử lý theo thứ tự ưu tiên: validate sớm bằng guard clause, dùng Objects.requireNonNull để fail fast, trả collection rỗng thay vì null, và chỉ dùng Optional cho giá trị "có thể không có" ở return type — không lạm dụng Optional cho field/tham số. Chi tiết ở 3.1 Exception Handling và 3.7 Optional. NPE helpful message đã học cách đọc ở mục 6.2.

7.2 Off-by-one — sai lệch đúng một đơn vị

Triệu chứng kinh điển: ArrayIndexOutOfBoundsException với message "Index N out of bounds for length N". Đoạn code chạy thật:

public class BugDemo {
    static int tong(int[] a) {
        int s = 0;
        for (int i = 0; i <= a.length; i++) {
            s += a[i];
        }
        return s;
    }

    public static void main() {
        IO.println(tong(new int[] {1, 2, 3}));
    }
}
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 3 out of bounds for length 3
	at BugDemo.tong(BugDemo.java:5)
	at BugDemo.main(BugDemo.java:11)

Mảng có index hợp lệ 0..length-1, nên điều kiện đúng là i < a.length. Nhưng tai hại nhất là off-by-one không hề crash — chỉ trả kết quả sai. Ví dụ chạy thật, tính tổng 1..n với điều kiện i < n (thiếu số cuối):

public class BugDemo {
    static int tongTu1Den(int n) {
        int s = 0;
        for (int i = 1; i < n; i++) {
            s += i;
        }
        return s;
    }

    public static void main() {
        IO.println("tongTu1Den(10) = " + tongTu1Den(10));
    }
}
tongTu1Den(10) = 45

Đáp án đúng phải là 55 (1+2+...+10). Bug kiểu này lọt qua mọi buổi review vì code "chạy được". Các dạng off-by-one bạn sẽ gặp: truy cập mảng bằng <= length; tính tổng 1..n bằng < n; substring(0, s.length() - 1) mất ký tự cuối; vòng lặp cần chạy hi - lo + 1 lần (fencepost — số hàng rào nhiều hơn số khoảng một đơn vị). Cách debug hiệu quả: đặt conditional breakpoint ở lần lặp cuối (i == a.length - 1, i == n - 1) và kiểm tra giá trị ngay trước/sau biên. Link ôn mảng: 1.6 Arrays.

7.3 ConcurrentModificationException — sửa collection giữa lúc đang duyệt

Đoạn code chạy thật — định xóa số chẵn khỏi danh sách:

import java.util.ArrayList;
import java.util.List;

public class BugDemo {
    public static void main() {
        List<Integer> nums = new ArrayList<>(List.of(1, 2, 3, 4));
        for (int n : nums) {
            if (n % 2 == 0) {
                nums.remove(Integer.valueOf(n));
            }
        }
        IO.println(nums);
    }
}
Exception in thread "main" java.util.ConcurrentModificationException
	at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1096)
	at java.base/java.util.ArrayList$Itr.next(ArrayList.java:1050)
	at BugDemo.main(BugDemo.java:7)

Vòng for-each thực chất dùng Iterator nội bộ. Khi nums.remove(...) thay đổi danh sách, Iterator phát hiện modCount thay đổi và ném CME ở lần next() kế tiếp. Cách sửa đúng — chạy thật cho kết quả [1, 3]:

List<Integer> nums = new ArrayList<>(List.of(1, 2, 3, 4));
nums.removeIf(n -> n % 2 == 0);   // dung: xoa qua removeIf
IO.println(nums);
// [1, 3]

Ba cách sửa hợp lệ: removeIf(...) (gọn nhất), iterator.remove() khi đang duyệt bằng Iterator, hoặc duyệt trên bản copy. Chi tiết Iterator/collection và bẫy này ở 3.3 Collections Framework.

7.4 Race condition — bug "tuần trăng" chỉ hiện khi đúng thời điểm

Race condition xảy ra khi nhiều thread đọc/ghi cùng state mà không đồng bộ. Đặc trưng: kết quả thay đổi giữa các lần chạy, càng ít thread/CPU càng khó thấy, và bug thường biến mất khi bạn... gắn debugger (vì debugger làm chậm mọi thứ, đổi thứ tự thực thi). Ví dụ chạy thật dùng CountDownLatch để cả hai thread cùng đọc số dư trước khi ghi:

import java.util.concurrent.CountDownLatch;

public class BugDemo {
    static int balance = 1000;
    static final CountDownLatch DA_DOC = new CountDownLatch(2);

    static void rut(int soTien) throws InterruptedException {
        int hienTai = balance;     // ca hai cung doc 1000
        DA_DOC.countDown();
        DA_DOC.await();
        balance = hienTai - soTien; // ghi de len nhau
    }

    public static void main() throws InterruptedException {
        Thread t1 = new Thread(() -> {
            try { rut(100); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        Thread t2 = new Thread(() -> {
            try { rut(200); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        IO.println("balance = " + balance);
    }
}
balance = 900

Đúng ra phải rút được 300 và còn 700. Thực tế mỗi thread tính từ 1000 rồi ghi đè: kết quả là 900 hoặc 800 tùy thread nào ghi sau (8 lần chạy thử đều ra 900) — không bao giờ đúng 700. Cách điều tra: không tin một lần chạy, hãy chạy lặp nhiều lần/ nhiều thread; dùng thread dump khi treo (mục 10); khoanh vùng shared mutable state. Cách sửa: synchronized/khóa, lớp atomic (AtomicInteger, LongAdder), bất biến, hoặc concurrent collections. Toàn bộ chủ đề ở 4.2 Concurrency.

Bug race còn có anh em sinh đôi là visibility: thread A ghi balance nhưng thread B vẫn mãi đọc giá trị cũ do không có volatile/happens-before. Triệu chứng cũng là "lúc được lúc không" — debug y hệt bằng cách chạy lặp và đọc thread dump. Đừng "sửa" bằng cách thêm Thread.sleep.

7.5 equals/hashCode sai — Set/Map "mất" phần tử

Bug này rất hay gặp khi bạn tạo class nghiệp vụ (ví dụ Order) rồi đưa vào HashSet/HashMap. Chạy thật — class Order chưa override equals/hashCode:

import java.util.HashSet;
import java.util.Set;

public class BugDemo {
    static class Order {
        final String code;

        Order(String code) {
            this.code = code;
        }
    }

    public static void main() {
        Set<Order> donHang = new HashSet<>();
        donHang.add(new Order("DH-001"));
        IO.println("contains: " + donHang.contains(new Order("DH-001")));
        IO.println("remove  : " + donHang.remove(new Order("DH-001")));
        IO.println("size    : " + donHang.size());
    }
}
contains: false
remove  : false
size    : 1

Hai object có cùng code = "DH-001" nhưng equals mặc định so sánh địa chỉ, nên HashSet coi là hai object khác nhau — phần tử tưởng chừng "biến mất". Sửa bằng record (tự sinh equals/hashCode), chạy thật cho kết quả đúng:

record Order(String code) {}
// contains: true
// remove  : true
// size    : 0

Quy tắc hợp đồng: equals bằng nhau thì hashCode bắt buộc bằng nhau (ngược lại không cần). hashCode quyết định bucket, equals quyết định phần tử trong bucket — thiếu một trong hai là bug âm thầm. Nếu không dùng record, IntelliJ có generator (Code → Generate → equals() and hashCode()) nhưng hãy chọn đủ field đúng nghiệp vụ. Đào sâu ở 2.6 equals / hashCode / toString.

7.6 Logic sai — code chạy hoàn hảo nhưng cho kết quả sai

Loại khó debug nhất vì không có exception nào chỉ đường. Hai thủ phạm phổ biến:

So sánh bằng == thay vì equals — chạy thật:

public class BugDemo {
    public static void main() {
        String a = new String("DH-001");
        String b = new String("DH-001");
        IO.println("a == b          : " + (a == b));
        IO.println("a.equals(b)     : " + a.equals(b));

        Integer x = Integer.valueOf(127);
        Integer y = Integer.valueOf(127);
        IO.println("127 == 127      : " + (x == y));

        Integer m = Integer.valueOf(128);
        Integer n = Integer.valueOf(128);
        IO.println("128 == 128      : " + (m == n));
    }
}
a == b          : false
a.equals(b)     : true
127 == 127      : true
128 == 128      : false

== so sánh reference (địa chỉ), còn equals so sánh giá trị. Riêng wrapper có cache −128..127 nên 127 == 127 đúng nhưng 128 == 128 sai — cực kỳ dễ lừa. Quy tắc: luôn dùng equals cho object (và nhớ null: gọi "DH-001".equals(code) thay vì code.equals("DH-001")).

Điều kiện boolean sai — nhầm && với ||. Ví dụ soLuong > 0 || soLuong < 100 luôn true với mọi giá trị (vì không số nào vừa ≤0 vừa ≥100 — một trong hai vế luôn đúng); điều kiện đúng phải là &&. Xem bài tập Bài 5 để thấy test tái hiện phát hiện lỗi này. Cách debug logic sai: đừng đọc code thêm — hãy cho chương trình in ra giá trị thật tại điểm quyết định, so với giá trị bạn kỳ vọng, hoặc viết test nhỏ với bảng giá trị.

8.2 Chia đôi dữ liệu — binary search bug

Khi bug chỉ xuất hiện với dữ liệu lớn (1000 đơn hàng, file 2GB), đừng debug cả tập dữ liệu. Hãy chia đôi liên tục để khoanh vùng:

  1. Chạy với 1000 bản ghi → lỗi xuất hiện? Nếu có, thử 500 bản ghi đầu tiên.
  2. Nếu 500 đầu không lỗi, bug nằm ở nửa sau → thử 250 bản ghi tiếp theo, cứ thế.
  3. Sau ~10 lần chia, bạn tìm ra bản ghi (hoặc tổ hợp bản ghi) gây lỗi — nhanh hơn nhiều so với đọc code mò.

Kỹ thuật này áp dụng được cho cả code: comment/disable một nửa số method để xem lỗi còn không (đừng quên bật lại), và cho cả lịch sử git bằng git bisect — git tự tìm commit gây bug qua các lần chia đôi.

8.3 Viết test nhỏ tái hiện

Một test 5 dòng tái hiện bug có giá trị hơn 30 phút đọc code. Nguyên tắc: dùng input nhỏ nhất làm lỗi xuất hiện. Ví dụ bug off-by-one chỉ cần mảng 3 phần tử; bug equals/hashCode chỉ cần 1 phần tử. Khi đã có test tái hiện, mỗi lần sửa code bạn chạy test để biết ngay đã hết bug chưa — đây chính là quy trình red → fix → green ở mục 11. Cách viết test bằng JUnit: 4.4 Testing (JUnit).

8.4 So sánh với code chạy đúng

Khi khó hiểu vì sao một đoạn code cho kết quả sai, hãy đặt cạnh một đoạn code tương tự đã chạy đúng (phiên bản cũ, module khác, code mẫu) rồi so từng dòng. Kỹ thuật differential debugging: chạy cùng input trên hai phiên bản, log ra điểm khác biệt đầu tiên — bug nằm ngay đó. Với code trong git, git log -p -- file.java và git bisect thường chỉ ra commit làm hỏng hành vi nhanh đến mức ngạc nhiên.

8.5 Rubber duck — giải thích cho... con vịt nhựa

Nhiều bug biến mất ngay khi bạn phải diễn đạt thành lời: "method này nhận danh sách đơn, nếu... à, mình đang sửa danh sách gốc thay vì bản copy!". Hãy giải thích code từng dòng cho đồng nghiệp (hoặc một món đồ vô tri) trước khi gọi trợ giúp. Nếu không ai nghe, viết lại luồng chạy ra giấy — làm chậm quá trình suy nghĩ chính là mục đích.

9. Debug production không có debugger Production

Trên production bạn không có breakpoint, không step được, và mọi hành động đều ảnh hưởng người dùng thật. Thứ tự ưu tiên khác hẳn local: ổn định hệ thống trước, tìm nguyên nhân sau.

  1. Giảm thiệt hại trước: rollback phiên bản vừa deploy, tắt tính năng lỗi bằng feature flag, mở rộng tài nguyên nếu nghẽn — rồi mới điều tra. Không có gì tệ hơn vừa sập vừa loay hoay tìm bug.
  2. Đọc log có cấu trúc: tìm theo requestId/correlationId để gom toàn bộ log của một request; xem timestamp để biết bắt đầu từ đâu (thường ngay sau một deploy/ thay đổi cấu hình). Log tốt được ghi từ trước — nếu hệ thống không có correlation id, đó là việc cần bổ sung ngay (4.5 Logging).
  3. Nhìn metrics: error rate, latency p95/p99, số request, CPU/RAM, kích thước queue, GC. Metrics cho biết cái gì và từ khi nào; log cho biết vì sao.
  4. Reproduce ở local với dữ liệu thật đã che: lấy payload/request thật (đã loại bỏ thông tin cá nhân), replay lại ở môi trường dev. Nếu không replay được, dựng test từ dữ liệu đó hoặc từ log.
  5. Thu thập dump khi cần: thread dump (treo, deadlock), heap dump (OOM, memory leak) — xem mục 10.

Những điều không được làm trên production:

  • Bọc try/catch mù để "hết lỗi": lỗi chỉ bị nuốt, dữ liệu có thể sai âm thầm. Catch phải đi kèm xử lý hoặc log đầy đủ.
  • Bật remote debug (JDWP) trên production: mở cổng debug là rủi ro bảo mật; dừng chương trình tại breakpoint có thể treo cả hệ thống.
  • Sửa file/thay cấu hình bằng tay không qua quy trình: lần sau không ai biết đã sửa gì ("configuration drift").
  • Restart mù: restart có thể "hết bệnh" tạm thời nhưng xóa sạch bằng chứng (dump, trạng thái) — hãy thu thập dump trước nếu nghi treo/leak.

Ví dụ một dòng log có cấu trúc (minh hoạ định dạng, không phải output chạy):

2026-10-03T14:21:07.412Z ERROR [order-service,trace=9f2c1a] orderId=DH-001 step=tinhPhi msg="tinh phi that bai" total=600000 ex="ArithmeticException: / by zero"

10.2 Thread dump — chụp ảnh mọi thread

Thread dump là danh sách toàn bộ thread kèm trạng thái và call stack tại một thời điểm. Lấy bằng jstack <pid> hoặc jcmd <pid> Thread.print (jcmd hiện đại hơn, cùng định dạng). Ví dụ với chương trình có một worker đang ngủ:

                    Thread.sleep(120_000);

                    Thread.currentThread().interrupt();

        };
        Thread worker = new Thread(congViec, "worker-xu-ly-don");
        worker.start();
        IO.println("pid: " + ProcessHandle.current().pid());
        Thread.sleep(120_000);
    }
}

10.3 Heap dump — tìm memory leak và OOM

Heap dump là ảnh chụp toàn bộ object trên heap. Lấy bằng:

jcmd <pid> GC.heap_info                                  # xem nhanh heap dang dung bao nhieu
jcmd <pid> GC.heap_dump /tmp/heap.hprof                  # ghi heap dump ra file
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>      # lua chon nang cao (live: ep Full GC)

Phân tích file .hprof bằng Eclipse MAT hoặc VisualVM (xem retained size, dominator tree, tìm class nhiều instance bất thường). Dùng khi: OutOfMemoryError, memory tăng dần đều không giảm, GC chạy liên tục. Cảnh báo production: file dump có thể nặng bằng vài lần heap thật, jmap -dump:live gây Full GC (dừng ứng dụng một nhịp), và heap dump chứa dữ liệu nhạy cảm — phải xoá/chuyển an toàn sau khi phân tích. Đọc thêm về heap, GC và OOM ở 4.1 JVM cơ bản.

10.4 jstat và JFR — nhìn nhanh sức khỏe JVM

jstat -gcutil <pid> 1000 in mỗi giây tỷ lệ sử dụng các vùng heap và số lần GC — thấy ngay GC có đang bất thường. Muốn chẩn đoán sâu hơn (latency, allocation, lock), dùng Java Flight Recorder: jcmd <pid> JFR.start duration=60s filename=/tmp/record.jfr rồi mở bằng JDK Mission Control. Đây là bộ ba kinh điển khi production "chậm mà không lỗi": thread dump + heap dump + JFR.

11. Reproduce bug & viết test tái hiện Production

Quy tắc vàng: viết test làm bug tái hiện TRƯỚC khi sửa (red → fix → green). Test đỏ chứng minh bạn đã hiểu bug và sẽ chuyển thành test xanh để chứng minh đã sửa đúng — đồng thời trở thành regression test chặn bug tái phát. Ví dụ chạy thật với validator đơn hàng có bug điều kiện:

public class OrderValidator {
    static boolean hopLe(int soLuong) {
        return soLuong > 0 || soLuong < 100;   // BUG: || luon dung
    }

    static void check(int soLuong, boolean mongDoi) {
        boolean thucTe = hopLe(soLuong);
        IO.println((thucTe == mongDoi ? "PASS" : "FAIL")
                + " soLuong=" + soLuong
                + " -> " + thucTe
                + " (mong doi " + mongDoi + ")");
    }

    public static void main() {
        check(10, true);
        check(0, false);
        check(-5, false);
        check(150, false);
    }
}

Chạy lần đầu — test đỏ (1 PASS, 3 FAIL) cho thấy bug thật sự tồn tại:

PASS soLuong=10 -> true (mong doi true)
FAIL soLuong=0 -> true (mong doi false)
FAIL soLuong=-5 -> true (mong doi false)
FAIL soLuong=150 -> true (mong doi false)

Sửa đúng một chỗ — đổi || thành && — rồi chạy lại; tất cả PASS:

PASS soLuong=10 -> true (mong doi true)
PASS soLuong=0 -> false (mong doi false)
PASS soLuong=-5 -> false (mong doi false)
PASS soLuong=150 -> false (mong doi false)

Đây chính là chu trình red → fix → green mà JUnit chuẩn hoá: viết assertEquals(false, hopLe(0)) làm test đỏ, sửa code đến khi xanh, giữ test lại mãi mãi. Sang 4.4 Testing (JUnit) bạn sẽ viết đúng những test này bằng JUnit thay vì check thủ công.

13. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Quy trình debug của bạn gồm những bước nào?
Năm bước: (1) Reproduce — tái hiện lỗi ổn định với ví dụ nhỏ nhất; (2) Isolate — khoanh vùng dòng code/điều kiện/dữ liệu gây lỗi; (3) Fix — sửa nguyên nhân gốc, mỗi lần một thay đổi; (4) Verify — chạy test tái hiện và test cũ; (5) Prevent — giữ regression test, thêm validate/log. Nếu chưa reproduce được thì chưa được phép sửa.
Câu 2. Step Over, Step Into, Step Out khác nhau thế nào? Khi nào dùng cái nào?
Step Over (F8): chạy hết dòng hiện tại mà không đi vào method được gọi — dùng khi tin method đó đúng. Step Into (F7): nhảy vào bên trong method — dùng khi nghi method trả sai và muốn xem chi tiết. Step Out (Shift+F8): chạy nốt method hiện tại rồi quay về caller — dùng khi đã hiểu method hoặc lỡ step vào quá sâu. Bổ sung: Smart Step Into (Shift+F7) khi dòng có nhiều lời gọi, Run to Cursor (Alt/⌥F9) khi chỉ muốn tới một dòng cụ thể.
Câu 3. Conditional breakpoint là gì? Cho ví dụ thực tế.
Là breakpoint chỉ dừng khi một biểu thức boolean trả true. Chuột phải breakpoint → nhập Condition. Ví dụ: bug chỉ xảy ra với đơn hàng mã "DH-001" → condition "DH-001".equals(don.getCode()); vòng lặp 1 triệu lần mà bug ở lần 987.654 → i == 987_654. Lưu ý condition được đánh giá mỗi lần qua dòng nên tuyệt đối không viết biểu thức có side effect.
Câu 4. Logpoint là gì, khác gì println và breakpoint thường?
Logpoint là breakpoint không dừng chương trình: bỏ tick Suspend, tick Evaluate and log (hoặc Shift+click gutter), rồi nhập message, có thể chèn biểu thức bằng {...}. So với println: không cần sửa code, không sợ commit nhầm, đổi/xóa dễ. So với breakpoint thường: chương trình chạy hết tốc lực nên hợp với vòng lặp lớn. Logpoint chỉ để debug local — production dùng logging framework có cấu trúc.
Câu 5. Exception breakpoint là gì? "Any Exception" khác exception cụ thể thế nào, caught và uncaught khác gì?
Là breakpoint dừng ngay khi exception được ném, thêm qua View Breakpoints → + → Java Exception Breakpoint. Any Exception bắt mọi exception (kể cả cái bị nuốt trong try/catch) nhưng rất ồn vì JDK ném exception nội bộ liên tục; nên chọn exception cụ thể như NullPointerException. Tùy chọn Caught chỉ dừng ở exception bị bắt — cực hữu ích khi bug là exception bị nuốt im lặng; Uncaught chỉ dừng ở exception thoát ra ngoài; On throw dừng tại nơi ném (thấy đủ stack lúc tạo), On catch dừng tại nơi bắt.
Câu 6. Watch khác Variables thế nào?
Variables tự động hiển thị mọi biến trong frame đang chọn, cập nhật sau mỗi bước. Watches là danh sách biểu thức bạn tự ghim, xem lại ở mọi lần dừng, kể cả biến không còn trong frame scope (nếu object còn sống) — ví dụ don.getItems().size() hoặc list.contains(don). Thực hành tốt: dùng Variables để khảo sát nhanh, ghim các giá trị then chốt vào Watches để so sánh giữa các lần dừng.
Câu 7. Evaluate Expression dùng làm gì? Nguy hiểm ở đâu?
Evaluate Expression (Alt/⌥+F8) chạy một biểu thức Java tùy ý trong ngữ cảnh frame hiện tại — trả lời nhanh câu hỏi "gọi method này thì ra gì?". Nguy hiểm vì nó chạy thật trong process đang debug: gọi method có side effect có thể sửa state (list.remove, setter), gọi API/IO gây chậm hoặc sai lệch dữ liệu. Chỉ nên evaluate getter/biểu thức thuần túy; nhớ rằng chức năng Set Value cũng tương tự — dùng xong nên restart trước khi kết luận.
Câu 8. Đọc stack trace bắt đầu từ đâu? Frame nào là code của bạn?
Đọc dòng đầu để biết loại exception + message, sau đó đọc các frame at ... từ trên xuống: frame đầu tiên là nơi exception phát sinh. Bỏ qua các frame thư viện (java.base/..., org.springframework...) và tìm frame đầu tiên thuộc package của bạn — đó là điểm bắt đầu điều tra. Số sau tên file (ví dụ BugDemo.java:3) là số dòng chính xác, dùng ngay được thay vì dò tay.
Câu 9. "Caused by" nghĩa là gì? Vì sao phải đọc khối bên dưới?
"Caused by" xuất hiện khi exception được gói kèm nguyên nhân gốc (exception chaining). Exception in phía trên là lớp bọc nghiệp vụ (ví dụ IllegalStateException: du lieu khong hop le), còn khối dưới mới chứa nguyên nhân kỹ thuật thật (ví dụ NumberFormatException: For input string: "12a"). Bỏ qua khối dưới là nguyên nhân phổ biến của việc sửa sai chỗ. Dòng ... N more chỉ là N frame lặp lại, không phải lỗi.
Câu 10. Helpful NullPointerException (JEP 358) cho biết gì? Khi nào thấy <local0> thay vì tên biến?
JEP 358 (JDK 14, bật mặc định từ JDK 15) làm NPE nói rõ phần tử nào null: Cannot read field "code" because "don" is null, Cannot invoke "String.length()" because "ten" is null, Cannot read the array length because "a" is null. Tắt bằng -XX:-ShowCodeDetailsInExceptionMessages. Nếu thấy <local0>/<parameter1>, class thiếu debug info về tên biến — thường do chạy file đơn hoặc javac không có -g; biên dịch với javac -g (IntelliJ mặc định) sẽ hiện tên thật.

Nâng cao (Junior+)

Câu 11. Vì sao không nên debug bằng cách rải println khắp nơi?
Vì phải sửa code (dễ commit nhầm, quên xóa), chỉ thấy được giá trị đơn giản, không xem được object tree/collection, không dừng được ở đúng thời điểm, và hoàn toàn vô dụng ở production. Thay thế: breakpoint/logpoint ở local; logging có cấu trúc (có ngữ cảnh, mức log) ở mọi nơi. Nếu buộc phải in, hãy in giá trị đang nghi ngờ kèm ngữ cảnh thay vì "chạy tới đây".
Câu 12. Làm sao tìm race condition? Vì sao nó khó?
Khó vì phụ thuộc thời điểm: càng ít thread/CPU càng khó thấy, và gắn debugger (làm chậm mọi thứ) thường làm bug biến mất. Cách tìm: chạy lặp rất nhiều lần với nhiều thread; kiểm tra mọi shared mutable state không đồng bộ; đọc thread dump khi treo (jstack, tìm BLOCKED/deadlock); dùng công cụ stress test. Cách sửa: synchronized/khóa, atomic, bất biến, concurrent collections — tuyệt đối không "sửa" bằng Thread.sleep. Chi tiết ở 4.2 Concurrency.
Câu 13. Debug production không có debugger thì làm thế nào?
Ưu tiên ổn định hệ thống trước (rollback, tắt feature flag), rồi mới điều tra: đọc log có cấu trúc theo correlationId, xem metrics (error rate, latency, GC) để biết thời điểm bắt đầu, reproduce ở local bằng dữ liệu thật đã che, và thu thập thread dump/heap dump khi cần. Không bọc try/catch mù, không bật remote debug JDWP trên production, không restart mù trước khi thu thập bằng chứng.
Câu 14. Vì sao phải viết test tái hiện TRƯỚC khi fix?
Vì test đỏ chứng minh bạn đã hiểu bug (reproduce được), test xanh sau fix chứng minh đã sửa đúng, và test đó ở lại làm regression test chặn bug tái phát. Nếu viết test sau khi fix, bạn có thể vô tình viết test "khớp" với hành vi mới mà không biết hành vi nào là đúng. Đây là chu trình red → fix → green của TDD, áp dụng cho riêng việc sửa bug.
Câu 15. Một bug report tốt gồm những thành phần nào?
(1) Bước tái hiện cụ thể (từng bước, dữ liệu); (2) mong đợi vs thực tế; (3) môi trường (phiên bản, JDK, OS, trình duyệt); (4) bằng chứng runtime: log, stack trace, traceId, screenshot; (5) mức ảnh hưởng. Người nhận bug report tốt có thể tái hiện trong vài phút thay vì hỏi lại mười câu. Khi bạn là người báo bug cũng nên viết đủ những mục này.
Câu 16. Bug không reproduce được thì làm gì?
Đừng sửa mù. Tìm thêm dữ liệu: log xung quanh thời điểm lỗi, metrics, dump, khác biệt môi trường (phiên bản, cấu hình, dữ liệu, tải). Thử replay request/dữ liệu thật ở local, bật thêm log có mục tiêu, hoặc viết test giả lập đúng điều kiện nghi ngờ. Hỏi người báo bug thêm bước tái hiện. Nếu vẫn không được, đặt "bẫy" quan sát (log/metric) để lần sau bug nổ thì có đủ dữ liệu.
Câu 17. Thread dump dùng khi nào, đọc thế nào?
Dùng khi ứng dụng treo, chậm bất thường, deadlock, hoặc CPU cao. Lấy bằng jstack <pid> hoặc jcmd <pid> Thread.print. Đọc: tên thread + trạng thái (RUNNABLE, BLOCKED, WAITING, TIMED_WAITING) + stack. Nhiều thread BLOCKED trên cùng một monitor → lock contention; chu trình chờ nhau → deadlock (jstack tự báo "Found one Java-level deadlock"); thread RUNNABLE trong vòng lặp/query lâu → điều tra logic.
Câu 18. Heap dump dùng khi nào và cần chú ý gì?
Dùng khi OutOfMemoryError, nghi memory leak (bộ nhớ tăng đều không giảm), hoặc GC chạy quá nhiều. Lấy bằng jcmd <pid> GC.heap_dump file hoặc jmap -dump:live,format=b,file=... <pid>, phân tích bằng Eclipse MAT/VisualVM (retained size, dominator tree). Chú ý: file có thể rất nặng, -dump:live ép Full GC (dừng ứng dụng một nhịp), và dump chứa dữ liệu nhạy cảm — phải bảo vệ và xóa an toàn sau khi dùng.
Câu 19. Off-by-one là gì? Kể các dạng thường gặp.
Là lỗi sai lệch đúng một đơn vị ở biên. Dạng thường gặp: duyệt mảng bằng i <= a.length (phải là <) → ArrayIndexOutOfBoundsException; tính tổng 1..n bằng i < n (thiếu số cuối) → kết quả sai âm thầm; substring(0, s.length() - 1) mất ký tự; fencepost — số lần lặp/số hàng rào nhiều hơn số khoảng một đơn vị; mid = (lo + hi) / 2 trong binary search khi hi = a.length. Debug bằng cách kiểm tra giá trị ngay trước và tại biên (conditional breakpoint ở lần lặp cuối).
Câu 20. Tại sao "đổi nhiều thứ cùng lúc" khi debug là sai lầm?
Vì bạn không biết thay đổi nào sửa được bug — nếu hết bug thì không rõ cái nào có tác dụng (có thể cái đúng lẫn cái sai), nếu còn bug thì càng rối. Quy tắc: một giả thuyết — một thay đổi — chạy test — kết luận; sau đó mới sang thay đổi tiếp theo. Cách này còn giúp bạn hiểu vì sao bug được sửa, chứ không chỉ "thấy hết lỗi".

Bài 9 — Đặt conditional breakpoint
Tình huống: vòng lặp for (int i = 0; i < 1_000_000; i++) xử lý đơn hàng, bug chỉ xảy ra ở lần lặp thứ 987.654, và chỉ khi đơn có tổng tiền lớn hơn 1.000.000. Cách làm: chuột phải breakpoint → Condition nhập i == 987_654 && don.getTongTien() > 1_000_000. Debugger chạy qua ~987 nghìn lần lặp trong nháy mắt và chỉ dừng ở đúng lần cần xem. Nếu muốn xem giá trị qua nhiều lần lặp mà không dừng, chuyển sang logpoint với message i = {i}, tong = {don.getTongTien()}.

Bài 11 — Off-by-one trong binary search 
static int timKiem(int[] a, int x) {
    int lo = 0;
    int hi = a.length;          // sai
    while (lo <= hi) {
        int mid = (lo + hi) / 2;
        if (a[mid] == x) return mid;
        if (a[mid] < x) lo = mid + 1;
        else hi = mid - 1;
    }
    return -1;
}

IO.println(timKiem(new int[] {10, 20, 30}, 99));
Ném ArrayIndexOutOfBoundsException: Index 3 out of bounds for length 3 tại dòng if (a[mid] == x) (chạy thật). Với hi = a.length, khi tìm số lớn hơn mọi phần tử thì lo đạt 3 và mid = (3 + 3) / 2 = 3 → truy cập a[3]. Sửa: hi = a.length - 1 (giữ lo <= hi), hoặc giữ hi = a.length nhưng dùng vòng lặp nửa mở while (lo < hi) với cách cập nhật khác.
Bài 12 — Race condition: giá trị nào có thể xảy ra? 
static int balance = 1000;
static final CountDownLatch DA_DOC = new CountDownLatch(2);

static void rut(int soTien) throws InterruptedException {
    int hienTai = balance;
    DA_DOC.countDown();
    DA_DOC.await();
    balance = hienTai - soTien;
}
// t1 rut 100, t2 rut 200, cung doc 1000 truoc khi ghi
IO.println("balance = " + balance);
Kết quả in ra có thể là 900 hoặc 800 (chạy thử 8 lần đều ra 900), tùy thread nào ghi sau — vì cả hai đều tính từ 1000. Không bao giờ ra 700 dù đúng ra phải là 700 (1000 − 100 − 200). Đây là dấu hiệu kinh điển của lost update; sửa bằng synchronized hoặc AtomicInteger. Xem 4.2 Concurrency.
Bài 13 — Cấu hình logpoint
Muốn xem tongTien và maDon qua 1 triệu lần lặp mà không dừng chương trình: đặt breakpoint ở dòng cần xem → chuột phải → bỏ tick Suspend → tick Evaluate and log → nhập maDon = {maDon}, tongTien = {tongTien}. Chương trình chạy hết tốc lực và in ra Console từng dòng log — giống hệt logging nhưng không cần sửa code. Nhớ xóa logpoint trước khi commit.

Checklist tự đánh giá trước phỏng vấn

  • Nêu được quy trình 5 bước reproduce → isolate → fix → verify → prevent kèm ví dụ.
  • Đọc một stack trace bất kỳ: chỉ ra exception, frame code mình, dòng cụ thể, và "Caused by".
  • Giải thích 3 dạng NPE helpful message và cách tắt/mở JEP 358.
  • Phân biệt Step Over / Step Into / Step Out và biết dùng khi nào.
  • Viết được condition cho conditional breakpoint trong vòng lặp lớn.
  • Giải thích logpoint khác println và breakpoint thường ở đâu.
  • Cấu hình exception breakpoint cho exception bị nuốt trong catch.
  • Biết nguy cơ side effect của Evaluate Expression và Set Value.
  • Nhận diện off-by-one im lặng (kết quả sai nhưng không crash).
  • Giải thích vì sao ConcurrentModificationException xảy ra và 2 cách sửa.
  • Nêu cách điều tra race condition và vì sao không được sửa bằng Thread.sleep.
  • Giải thích hợp đồng equals/hashCode và vì sao thiếu hashCode làm mất phần tử trong HashSet.
  • Kể được 4 lệnh chẩn đoán jps/jstack/jcmd/jmap và dùng khi nào.
  • Viết test tái hiện trước khi fix theo chu trình red → fix → green.
