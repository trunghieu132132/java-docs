2. if/else, nested if và guard clause

if là cấu trúc rẽ nhánh cơ bản nhất: đúng thì chạy, sai thì bỏ qua. Chuỗi else if kiểm tra lần lượt từ trên xuống, nhánh nào đúng đầu tiên thì dừng — nên thứ tự điều kiện quan trọng.

public class IfElseDemo {
    public static void main() {
        int score = 72;

        if (score >= 90) {
            IO.println("Xuat sac");
        } else if (score >= 80) {
            IO.println("Gioi");
        } else if (score >= 70) {
            IO.println("Kha");
        } else {
            IO.println("Can co gang");
        }
    }
}
// Kha
Điểm khác JS đầu tiên: điều kiện của Java bắt buộc là boolean thật sự. Java không có truthy/falsy — không có chuyện số khác 0, chuỗi khác rỗng hay object tồn tại được coi là "đúng" như JavaScript. JLS định nghĩa điều kiện if là biểu thức kiểu boolean (hoặc Boolean — sẽ tự unbox).

2.1. Bẫy JS: if (1) và if ("a")

Đoạn code sau chạy ngon trong Node.js nhưng không compile được trong Java:

        if (1) {
            ^
error: incompatible types: int cannot be converted to boolean

        if ("a") {
            ^
error: incompatible types: String cannot be converted to boolean

Muốn kiểm tra "khác rỗng" phải viết tường minh: if (count != 0), if (!name.isEmpty()), if (obj != null). Dài hơn một chút nhưng người đọc biết chính xác đang kiểm tra gì — đây là lý do Java chọn boolean bắt buộc.

Cẩn thận khi điều kiện là wrapper Boolean: nó tự unbox, và unbox null ném NPE (xem thêm Biến trong Java — mục 12).

Boolean enabled = null;
if (enabled) {          // tuong duong enabled.booleanValue()
    IO.println("bat");
}
// NullPointerException: Cannot invoke "java.lang.Boolean.booleanValue()" because "<local0>" is null

Cách viết an toàn: if (Boolean.TRUE.equals(enabled)).

2.2. Nested if vs guard clause

Nested if (if lồng trong if) hoạt động đúng, nhưng khi lồng 3-4 tầng thì nhánh "thành công" bị đẩy sâu vào trong, người đọc phải giữ nhiều điều kiện trong đầu. Guard clause là kỹ thuật đảo ngược: kiểm tra điều kiện sai trước và return/throw sớm, để phần còn lại của method chỉ còn "happy path" phẳng.

// Cach 1: nested if - happy path bi chon 3 tang
static String shippingLabelNested(long orderId, String customer, boolean paid) {
    if (orderId > 0) {
        if (customer != null && !customer.isBlank()) {
            return paid ? "Gui hang - DH" + orderId + " - " + customer
                        : "Cho thanh toan - DH" + orderId;
        } else {
            throw new IllegalArgumentException("customer khong duoc rong");
        }
    } else {
        throw new IllegalArgumentException("orderId phai > 0");
    }
}

// Cach 2: guard clause - kiem tra loi truoc, happy path phang
static String shippingLabelGuard(long orderId, String customer, boolean paid) {
    if (orderId <= 0) {
        throw new IllegalArgumentException("orderId phai > 0");
    }
    if (customer == null || customer.isBlank()) {
        throw new IllegalArgumentException("customer khong duoc rong");
    }
    if (!paid) {
        return "Cho thanh toan - DH" + orderId;
    }
    return "Gui hang - DH" + orderId + " - " + customer;
}
// shippingLabelGuard(101, "An", true)    -> Gui hang - DH101 - An
// shippingLabelGuard(102, "Binh", false) -> Cho thanh toan - DH102
// shippingLabelGuard(0, "Chi", true)     -> IllegalArgumentException: orderId phai > 0

Hai bản cho cùng kết quả (đã chạy thật), nhưng bản guard clause dễ đọc hơn vì: điều kiện lỗi nằm ngay gần đầu method, mỗi guard kiểm tra đúng một việc, và không cần else. Quy tắc thực dụng khi review code: method không nên có quá 2 tầng lồng; thấy tầng thứ 3 là dấu hiệu nên tách method hoặc dùng guard clause.

3. switch truyền thống và fall-through

switch sinh ra để thay chuỗi if/else if dài khi cùng kiểm tra một biểu thức với nhiều giá trị rời rạc. Bản truyền thống (kiểu C, JavaScript cũng vậy) có một đặc điểm phải hiểu rõ: fall-through — sau khi khớp một case, chương trình chạy tiếp xuống các lệnh bên dưới cho tới khi gặp break hoặc hết switch.

int day = 3;

switch (day) {
    case 1:
        IO.println("Thu Hai");
    case 2:
        IO.println("Thu Ba");
    case 3:
        IO.println("Thu Tu");
    case 4:
        IO.println("Thu Nam");
    default:
        IO.println("Cuoi tuan");
}
// Thu Tu
// Thu Nam
// Cuoi tuan

Vào case 3 in "Thu Tu", thiếu break nên rơi (fall through) xuống case 4 in "Thu Nam", rơi tiếp vào default in "Cuoi tuan". Không có lỗi nào được báo — đây là nguồn bug kinh điển. Viết đúng:

static String dayType(int day) {
    String result;
    switch (day) {
        case 1:
        case 2:
        case 3:
        case 4:
        case 5:
            result = "Ngay lam viec";
            break;
        case 6:
        case 7:
            result = "Cuoi tuan";
            break;
        default:
            result = "Ngay khong hop le: " + day;
    }
    return result;
}
// dayType(3) -> Ngay lam viec
// dayType(6) -> Cuoi tuan
// dayType(9) -> Ngay khong hop le: 9

Hai ý cần nhớ:

  • Nhiều case chung một khối lệnh: xếp các case liền nhau, chỉ case cuối có thân lệnh. Đây là fall-through được dùng có chủ đích — khác hẳn fall-through do quên break.
  • default không bắt buộc và không nhất thiết nằm cuối, nhưng nên đặt cuối cho dễ đọc. Với dữ liệu từ bên ngoài, luôn có default để xử lý giá trị lạ.

Còn đây là lỗi thật khi switch trên chuỗi null — message là helpful NPE của JDK hiện đại:

String mode = null;

4. switch expression (Java 14+) Hay hỏi phỏng vấn Junior+

Java 14 (JEP 361) biến switch thành expression — tức là nó trả về một giá trị, dùng cú pháp mũi tên ->, không fall-through, và compiler bắt buộc phải bao hết mọi trường hợp (exhaustive). Đây là cách viết switch được khuyến nghị trong code mới.

enum OrderStatus { PENDING, PAID, SHIPPED, CANCELLED }

// enum: khong can default vi compiler biet het cac hang
static String message(OrderStatus status) {
    return switch (status) {
        case PENDING -> "Cho thanh toan";
        case PAID -> "Da thanh toan";
        case SHIPPED -> "Dang giao";
        case CANCELLED -> "Da huy";
    };
}

// nhieu label chung, block nhieu dong thi dung yield
static String classify(int score) {
    return switch (score / 10) {
        case 10, 9 -> "A";
        case 8 -> "B";
        case 7 -> "C";
        case 6 -> "D";
        default -> {
            if (score < 0) {
                yield "INVALID";
            }
            yield "F";
        }
    };
}
// message(PAID) -> Da thanh toan
// classify(85)  -> B
// classify(-5)  -> INVALID
// classify(61)  -> D

Các điểm phải nắm:

  • Mũi tên -> không fall-through — mỗi nhánh độc lập, không cần break, hết nhánh là thoát.
  • yield — trả giá trị cho switch expression khi thân nhánh là block nhiều dòng. Nó khác return: return thoát khỏi cả method, yield chỉ thoát khỏi switch. Trong nhánh một dòng, -> đã là yield ngầm.
  • Nhiều label một nhánh: case 10, 9 -> — gọn hơn xếp chồng case của bản cũ.
  • Exhaustive: switch expression với int/String phải có default; với enum chỉ cần liệt kê đủ các hằng (hoặc có default). Thiếu là lỗi compile:
        int code = switch (s) {
                   ^
error: the switch expression does not cover all possible input values

Cú pháp -> dùng được cả trong switch statement (không trả giá trị), khi đó không cần exhaustive:

switch (x) {
    case 1 -> IO.println("mot");
    case 2 -> {
        IO.println("hai");
        IO.println("hai trong block");
    }
    default -> IO.println("khac");
}
// voi x = 2: hai
//            hai trong block

5. Pattern matching for switch (Java 21) — mức nhận biết

Java 21 (JEP 441) cho phép case khớp theo kiểu dữ liệu thay vì chỉ theo giá trị hằng: case Integer i -> vừa kiểm tra object có phải Integer, vừa gán nó vào biến i để dùng luôn trong nhánh — khỏi phải viết instanceof rồi ép kiểu. Có thể thêm guard bằng when để lọc thêm điều kiện.

sealed interface Payment permits CardPayment, BankTransfer, CashPayment {}

record CardPayment(String last4, long amountCents) implements Payment {}
record BankTransfer(String bankCode, long amountCents) implements Payment {}
record CashPayment(long amountCents) implements Payment {}

// sealed + record: compiler biet het cac kha nang -> khong can default
static String describe(Payment payment) {
    return switch (payment) {
        case CardPayment c -> "The " + c.last4() + ": " + c.amountCents() + " cents";
        case BankTransfer b -> "Chuyen khoan " + b.bankCode();
        case CashPayment c -> "Tien mat: " + c.amountCents() + " cents";
    };
}

// type pattern + guard + case null
static String classify(Object obj) {
    return switch (obj) {
        case null -> "null";
        case Integer i when i < 0 -> "So nguyen am: " + i;
        case Integer i -> "So nguyen: " + i;
        case String s when s.isBlank() -> "Chuoi rong";
        case String s -> "Chuoi: " + s;
        default -> "Khong biet";
    };
}
// describe(new CardPayment("4242", 199_000L)) -> The 4242: 199000 cents
// describe(new BankTransfer("VCB", 500_000L)) -> Chuyen khoan VCB
// describe(new CashPayment(50_000L))          -> Tien mat: 50000 cents
// classify(-3)      -> So nguyen am: -3
// classify(42)      -> So nguyen: 42
// classify("hello") -> Chuoi: hello
// classify("  ")    -> Chuoi rong
// classify(null)    -> null

Khi nào dùng (mức nhận biết — chưa cần thành thạo):

  • Khi cần rẽ nhánh theo kiểu thực tế của object và muốn compiler kiểm tra đủ nhánh — thay cho chuỗi if (x instanceof A) rồi ép kiểu thủ công.
  • Kết hợp sealed hierarchy (sealed interface/class + record) thì switch không cần default và thêm subtype mới là compiler báo lỗi ngay. Sealed/records học ở 2.4 Polymorphism.
  • Record pattern (cũng Java 21) cho phép bóc tách component ngay trong case, ví dụ case CardPayment(String last4, long cents) — đọc thêm khi cần.
  • Nhớ: tính năng này chỉ dùng được khi runtime/compiler từ Java 21; project cũ dùng Java 17 thì không có.

6. for, while, do-while, for-each

Java có đúng 4 loại vòng lặp, mỗi loại hợp một tình huống. Cả bốn đều hỗ trợ break/continue.

// for: biet truoc so lan lap, can bien dem
for (int i = 1; i <= 3; i++) {
    IO.println("for i = " + i);
}
// for i = 1
// for i = 2
// for i = 3

// while: kiem tra dieu kien truoc, co the khong chay lan nao
int count = 3;
while (count > 0) {
    IO.println("while count = " + count);
    count--;
}
// while count = 3
// while count = 2
// while count = 1

// do-while: than chay it nhat 1 lan vi kiem tra dieu kien SAU
int retries = 0;
do {
    retries++;
    IO.println("do-while chay lan " + retries);
} while (retries < 0);
// do-while chay lan 1   <- dieu kien sai ngay tu dau nhung van chay 1 lan

// for-each: duyet toan bo mang/collection, khong can index
int[] prices = {100, 200, 300};
int sum = 0;
for (int price : prices) {
    sum += price;
}
IO.println("for-each sum = " + sum);
// for-each sum = 600

6.1. Scope của biến trong for

Biến khai báo trong phần đầu của for chỉ sống trong thân vòng lặp — hết vòng lặp là biến biến mất (block scope, xem Biến trong Java — mục 6):

        IO.println(i);
                   ^
error: cannot find symbol
  symbol:   variable i
  location: class ForScopeError

Vì scope hẹp nên hai vòng for liên tiếp có thể cùng đặt tên i mà không đụng nhau. Ngược lại, for (int i = ...) mà muốn dùng i sau vòng lặp thì phải khai báo i bên ngoài — nhưng khi đó nhớ rằng nếu vòng lặp không chạy lần nào, i giữ giá trị ban đầu.

6.2. Vòng lặp vô hạn

Vòng lặp vô hạn không phải lúc nào cũng là bug — với server, event loop hay retry loop, nó là chủ ý. Hai cách viết phổ biến:

int attempts = 0;
while (true) {              // tuong minh, de doc hon for (;;)
    attempts++;
    if (attempts == 3) {
        IO.println("thoat vong lap vo han tai attempts = " + attempts);
        break;              // luon co duong thoat
    }
}
// thoat vong lap vo han tai attempts = 3

while (true) là cách viết được khuyến nghị; for (;;) tương đương nhưng khó đọc hơn. Điều bắt buộc: bên trong phải có break, return, throw hoặc điều kiện dừng rõ ràng.

7. for-each và chuyện không sửa được phần tử

Đây là bẫy rất hay gặp với người từ JS sang: trong for-each, biến vòng lặp là bản sao giá trị của phần tử, không phải tham chiếu tới ô mảng. Gán vào nó chỉ đổi bản sao — mảng giữ nguyên.

int[] prices = {100, 200, 300};

for (int p : prices) {
    p = p * 2;                  // chi doi bien cuc bo p
}
IO.println("sau for-each : " + prices[0] + " " + prices[1] + " " + prices[2]);
// sau for-each : 100 200 300

for (int i = 0; i < prices.length; i++) {
    prices[i] = prices[i] * 2;  // sua truc tiep qua index
}
IO.println("sau for-index: " + prices[0] + " " + prices[1] + " " + prices[2]);
// sau for-index: 200 400 600

Với object thì khác một nửa: biến vòng lặp vẫn là bản sao, nhưng bản sao đó là bản sao reference — trỏ cùng object. Gọi method làm thay đổi nội dung object thì có hiệu lực (giống pass-by-value trong Biến trong Java — mục 7):

StringBuilder[] names = {new StringBuilder("an"), new StringBuilder("binh")};
for (StringBuilder name : names) {
    name.append("!");           // sua noi dung object -> OK
}
IO.println("sua noi dung object: " + names[0] + " " + names[1]);
// sua noi dung object: an! binh!

Quy tắc nhớ nhanh: gán lại biến vòng lặp = vô hiệu; gọi method trên object = có hiệu lực. Muốn thay phần tử primitive thì dùng for với index. Ngoài ra for-each không duyệt ngược được, không biết vị trí hiện tại, và không nên xóa phần tử khỏi collection trong lúc duyệt (sẽ học ở Collections).

8. break, continue và label

  • break — thoát hẳn vòng lặp gần nhất (hoặc thoát switch).
  • continue — bỏ phần còn lại của lần lặp hiện tại, nhảy sang lần lặp kế tiếp.
  • label — đặt tên cho vòng lặp để break/continue tác động lên vòng ngoài, dùng khi có vòng lặp lồng nhau.
int[][] matrix = {
    {1, 2, 3},
    {4, 5, 6},
    {7, 8, 9}
};
int target = 5;
boolean found = false;

outer:
for (int row = 0; row < matrix.length; row++) {
    for (int col = 0; col < matrix[row].length; col++) {
        if (matrix[row][col] == target) {
            IO.println("Tim thay " + target + " tai [" + row + "][" + col + "]");
            found = true;
            break outer;            // thoat CA HAI vong lap
        }
    }
}
if (!found) {
    IO.println("Khong tim thay " + target);
}
// Tim thay 5 tai [1][1]

skip:
for (int i = 1; i <= 3; i++) {
    for (int j = 1; j <= 3; j++) {
        if (j == 2) {
            continue skip;      // bo qua phan con lai cua vong ngoai hien tai
        }
        IO.println("i=" + i + " j=" + j);
    }
}
// i=1 j=1
// i=2 j=1
// i=3 j=1

Không có label, break trong ví dụ tìm kiếm chỉ thoát vòng trong, vòng ngoài chạy tiếp — phải thêm biến cờ found và kiểm tra ở mỗi tầng. Label xử lý gọn hơn hẳn.

Best practices cho label:

  • Chỉ dùng cho vòng lặp lồng nhau khi cần thoát/continue vòng ngoài; không dùng label cho khối if hay câu lệnh thường.
  • Đặt tên có nghĩa (search, rows) và viết ngay trước vòng lặp ngoài, thụt lề cùng cấp.
  • Lồng quá 2 tầng thì ưu tiên tách method con và return sớm — vừa thoát đúng chỗ, vừa dễ test.
  • Lint của công ty có thể cấm label; hỏi trước khi dùng trong code base lạ.

9. Pitfalls tổng hợp Hay hỏi phỏng vấn

9.1. Dangling else — else treo

else luôn gắn với if gần nhất chưa có else, bất kể thụt lề thế nào:

int a = -1, b = -1, x = 0;
if (a > 0)
    if (b > 0)
        x = 1;
    else
        x = 2;
IO.println("dangling else x = " + x);
// dangling else x = 0

Đọc thụt lề tưởng else thuộc if (a > 0), nhưng thực tế nó thuộc if (b > 0). Vì a = -1 nên cả hai if đều không chạy, x giữ 0. Luôn dùng ngoặc nhọn cho mọi thân if/else.

9.2. Quên ngoặc nhọn và thụt lề đánh lừa

int total = 0;
for (int k = 0; k < 3; k++)
    total += k;
    IO.println("dong thut le chay 1 lan, total = " + total);
// dong thut le chay 1 lan, total = 3

Dòng IO.println thụt lề như nằm trong vòng lặp nhưng thực tế nằm ngoài (for chỉ có một câu lệnh). Code chạy "đúng" theo cú pháp, sai theo ý người viết. Ngoặc nhọn là bắt buộc trong convention production.

9.3. Gán nhầm = trong điều kiện

Trong JavaScript, if (x = 1) chạy được (gán xong lấy giá trị 1 làm điều kiện). Java tách bạch phép gán và so sánh nên đoạn này không compile:

        if (x = 1) {
              ^
error: incompatible types: int cannot be converted to boolean

Đây là lỗi compile tốt cho sức khỏe — không bao giờ lọt vào bản build như JS. Muốn so sánh viết ==, muốn so sánh giá trị object viết equals.

9.4. Dấu chấm phẩy thừa sau if

int stock = 5;
if (stock > 0);
    IO.println("con hang - luon in du dieu kien dung hay sai");
// con hang - luon in du dieu kien dung hay sai

if (stock > 0); là một câu lệnh rỗng — điều kiện được tính rồi vứt đi, còn dòng println luôn chạy. Compiler không báo gì. Đây là biến thể của pitfall 9.2.

9.5. So sánh số thực trong điều kiện

double sum = 0.1 + 0.2;
IO.println("0.1 + 0.2 == 0.3           : " + (sum == 0.3));            // false
IO.println("Math.abs(sum - 0.3) < 1e-9 : " + (Math.abs(sum - 0.3) < 1e-9));  // true

Vì biểu diễn nhị phân của double, 0.1 + 0.2 không bằng chính xác 0.3. So sánh float/double bằng == trong điều kiện hầu như luôn sai về mặt logic — dùng epsilon (Math.abs(a - b) < 1e-9) hoặc chuyển sang BigDecimal khi là tiền tệ (xem Biến trong Java — mục 13).

9.6. Vòng lặp vô hạn do cập nhật sai biến

int i = 0;
int j = 0;
while (i < 3) {
    j++;                // cap nhat nham bien: i khong bao gio tang
    if (j == 3) {
        IO.println("i van = " + i + " sau 3 lan lap -> vong lap vo tan");
        break;          // them break chi de minh hoa
    }
}
// i van = 0 sau 3 lan lap -> vong lap vo tan

Biến điều khiển không bao giờ tiến tới điều kiện dừng. Cách phòng: đặt tên biến đếm rõ ràng, và với vòng lặp while luôn tự hỏi "cái gì làm điều kiện này sai đi?".

11. Production patterns Production

11.1. Validate input bằng guard clause + record

Convention: validate ngay khi tạo object, throw IllegalArgumentException với message nói rõ sai gì — fail fast, không để dữ liệu bẩn đi sâu vào hệ thống. Record với compact constructor là chỗ đặt validation gọn nhất:

record CreateOrderRequest(long customerId, BigDecimal totalAmount) {
    CreateOrderRequest {
        if (customerId <= 0) {
            throw new IllegalArgumentException("customerId phai > 0");
        }
        if (totalAmount == null || totalAmount.signum() <= 0) {
            throw new IllegalArgumentException("totalAmount phai > 0");
        }
    }
}
// new CreateOrderRequest(42L, new BigDecimal("199000.00"))
//   -> CreateOrderRequest[customerId=42, totalAmount=199000.00]
// new CreateOrderRequest(0L, ...) -> IllegalArgumentException: customerId phai > 0

Chú ý convention: ID dùng long, tiền dùng BigDecimal (không dùng double), trạng thái dùng enum.

11.2. Mapping enum sang message bằng switch expression

Không dùng magic string rải rác; gom mapping vào một chỗ bằng switch expression exhaustive. Khi thêm hằng enum mới, compiler ép bạn cập nhật mọi switch — đây là lợi ích production lớn nhất so với if/else if:

enum PaymentMethod { CARD, BANK_TRANSFER, COD }

static final int MAX_RETRY = 3;   // hang so: static final + UPPER_SNAKE_CASE

static String paymentHint(PaymentMethod method) {
    return switch (method) {
        case CARD -> "Thanh toan bang the (ho tro 3D Secure)";
        case BANK_TRANSFER -> "Chuyen khoan trong 24h";
        case COD -> "Thanh toan khi nhan hang";
    };
}

static int retryLimit(PaymentMethod method) {
    return switch (method) {
        case CARD -> MAX_RETRY;
        case BANK_TRANSFER -> 1;
        case COD -> 0;
    };
}
// CARD | Thanh toan bang the (ho tro 3D Secure) | retry=3
// BANK_TRANSFER | Chuyen khoan trong 24h | retry=1
// COD | Thanh toan khi nhan hang | retry=0

11.3. Tránh lồng quá 2 tầng

Quy tắc thực dụng được nhiều team áp dụng: tối đa 2 tầng lồng trong một method. Cách xử lý theo thứ tự ưu tiên:

  1. Guard clause + return sớm cho các trường hợp lỗi/biên (mục 2.2).
  2. Gộp điều kiện bằng &&/|| khi chúng cùng ý nghĩa.
  3. Tách đoạn lồng sâu thành method riêng có tên mô tả việc nó làm.
  4. Dùng switch expression thay chuỗi if/else if so sánh cùng một biến.
  5. Đảo điều kiện: xử lý trường hợp hiếm trước, happy path sau cùng.

Lợi ích không chỉ là đọc dễ: method phẳng hơn thì tách test dễ hơn, và mỗi method con có thể test độc lập (bước chuẩn bị cho JUnit ở giai đoạn 4).

12. Interview Q&A Hay hỏi phỏng vấn

Cơ bản

Câu 1. Điều kiện của if trong Java khác gì JavaScript?
Java bắt buộc điều kiện là boolean (hoặc Boolean — tự unbox). Không có truthy/falsy như JS, nên if (1), if ("a"), if ([]) đều là compile error. Phải viết tường minh if (n != 0), if (!s.isEmpty()).
Câu 2. Fall-through trong switch là gì? Vì sao phải break?
Khi một case khớp, chương trình chạy từ đó xuống hết các câu lệnh phía dưới, kể cả của case khác, cho tới khi gặp break hoặc hết switch. Đây là hành vi cố ý của JLS (cho phép nhiều case chung một thân), nhưng nếu quên break thì chạy sai nhánh mà compiler không báo. Switch expression không có fall-through.
Câu 3. Làm sao cho nhiều case dùng chung một khối lệnh?
Switch cũ: xếp các label liền nhau, chỉ case cuối có thân — case 1: case 2: case 3: ... break;. Switch expression: case 1, 2, 3 -> ....
Câu 4. Switch expression khác switch statement ở đâu?
Switch expression trả về giá trị (dùng được trong gán, return, truyền tham số), dùng cú pháp ->, không fall-through, và bắt buộc exhaustive. Switch statement chỉ chạy lệnh, có fall-through, không cần bao hết trường hợp.
Câu 5. yield khác return thế nào?
yield trả giá trị cho switch expression rồi thoát khỏi switch, còn method chạy tiếp. return thoát khỏi cả method. yield chỉ dùng trong block của nhánh -> khi cần nhiều dòng.
Câu 6. do-while khác while thế nào?
do-while kiểm tra điều kiện sau khi chạy thân, nên thân luôn chạy ít nhất một lần — kể cả điều kiện sai ngay từ đầu. while kiểm tra trước, có thể không chạy lần nào. Dùng do-while cho menu, retry, đọc input đến khi hợp lệ.
Câu 7. Khi nào không nên dùng for-each?
Khi cần index (duyệt ngược, so sánh phần tử kề, in vị trí), cần sửa phần tử mảng primitive, cần xóa/tìm theo vị trí trong collection, hoặc cần duyệt có bước nhảy khác 1. for-each vẫn break/continue được bình thường.
Câu 8. Vì sao for-each không sửa được phần tử mảng int?
Biến vòng lặp là bản sao giá trị của phần tử (giống tham số truyền vào method). Gán vào nó chỉ đổi bản sao, không đổi ô mảng. Với mảng object, bản sao là bản sao reference nên gọi method làm thay đổi nội dung object vẫn có hiệu lực, nhưng gán lại biến vòng lặp thì không.
Câu 9. break và continue khác nhau thế nào?
break thoát hẳn vòng lặp (hoặc switch) gần nhất. continue chỉ bỏ phần còn lại của lần lặp hiện tại rồi sang lần kế tiếp. Cả hai đều bị ảnh hưởng bởi label nếu có.

Nâng cao (Junior+)

Câu 10. switch nhận những kiểu selector nào?
Các kiểu nguyên thủy byte, short, char, int và wrapper tương ứng; String (Java 7+); enum. Không nhận long, float, double, boolean. Từ Java 21, pattern switch mở rộng cho reference type bất kỳ.
Câu 11. Vì sao case label phải là hằng số compile-time?
Compiler sinh bảng nhảy/tra cứu từ các giá trị case, phải biết trước lúc compile — biến thường chỉ biết lúc runtime. Hợp lệ: literal, static final hằng, enum constant. case target: với biến thường báo "constant expression required".
Câu 12. Vì sao switch expression với enum không cần default, nhưng với int thì bắt buộc?
Vì tính exhaustive: compiler biết chính xác tập hằng của enum nên kiểm tra đủ nhánh được. Với int/String, tập giá trị không hữu hạn (theo góc nhìn compiler) nên phải có default để bao các trường hợp còn lại. Thiếu exhaustive báo lỗi "the switch expression does not cover all possible input values".
Câu 13. Thêm một hằng enum mới thì code switch bị ảnh hưởng gì?
Với switch expression liệt kê đủ hằng (không default): compile error ngay tại mọi chỗ switch — buộc dev cập nhật, tránh bỏ sót. Đây là lợi ích production lớn; nếu lạm dụng default thì hằng mới rơi vào default âm thầm và logic có thể sai.
Câu 14. if (x = 1) trong Java có chạy không?
Không compile: "incompatible types: int cannot be converted to boolean". Java tách phép gán (trả về giá trị) khỏi ngữ cảnh điều kiện (cần boolean), nên bẫy kinh điển của C/JavaScript không tồn tại. Muốn so sánh viết ==.
Câu 15. Pattern matching for switch là gì? Cho ví dụ.
Java 21: case có thể khớp theo kiểu — case Integer i -> "so " + i vừa kiểm tra kiểu vừa gán vào biến. Kèm guard when để lọc thêm điều kiện (case Integer i when i < 0 ->) và case null. Kết hợp sealed hierarchy thì không cần default; record pattern còn bóc tách được component của record.
Câu 16. Dangling else là gì và tránh thế nào?
else luôn gắn với if gần nhất chưa có else, bất kể thụt lề. Trong if (a) if (b) ... else ..., else thuộc if (b). Luôn dùng ngoặc nhọn cho mọi thân if/else để loại bỏ hoàn toàn nhập nhằng.
Câu 17. So sánh float/double trong điều kiện thế nào cho đúng?
Không dùng == vì sai số biểu diễn nhị phân (0.1 + 0.2 != 0.3). Dùng epsilon: Math.abs(a - b) < 1e-9. Với tiền tệ, không dùng số thực từ đầu — dùng BigDecimal và so sánh bằng compareTo.
Câu 18. Làm sao giảm if lồng nhau sâu?
Guard clause + return/throw sớm cho trường hợp lỗi; gộp điều kiện cùng ý nghĩa; tách method con đặt tên mô tả; dùng switch expression khi nhiều nhánh so sánh cùng biến; đảo điều kiện để happy path ở cuối. Mục tiêu: tối đa 2 tầng lồng.

Câu hỏi khó

Câu 19. Vì sao if (booleanWrapper) có thể ném NPE?
Điều kiện cần boolean nên compiler chèn unboxing (booleanValue()). Wrapper null thì unbox ném NPE — dù code đọc như đang "kiểm tra object có tồn tại hay không". An toàn: Boolean.TRUE.equals(b).
Câu 20. switch trên chuỗi null ném gì? Vì sao?
NullPointerException ngay khi tính selector. javac hiện thực switch String bằng hashCode() trước rồi mới equals từng case khớp hash — gọi method trên null là nổ. Phải kiểm tra null trước; pattern switch Java 21 có thể bắt bằng case null ->.
Câu 21. Label có phải bad practice không? Khi nào nên dùng, thay thế bằng gì?
Label bị xem là khó đọc nên nhiều team hạn chế. Dùng khi cần thoát/continue vòng ngoài từ trong vòng lồng 2 tầng. Thay thế: tách method con và return sớm, dùng biến cờ (dài dòng hơn), hoặc cấu trúc dữ liệu phẳng hơn. Nếu dùng, đặt tên có nghĩa và chỉ cho vòng lặp.
Câu 22. Vì sao switch trên String hoạt động được?
Java 7 thêm switch String. JLS quy định so sánh bằng equals; javac sinh code: tính hashCode() của selector, nhảy theo bảng hash, rồi gọi equals cho từng case khớp hash (tránh collision). Vì vậy selector null nổ ở bước hashCode.

In ra so 42. Guard when i > 100 không thỏa vì 42 < 100, nên rơi xuống type pattern case Integer i phía sau.
Bài 12 
int x = 9;
int result = 0;
switch (x) {
    default:
        result = 100;
    case 1:
        result += 1;
        break;
    case 2:
        result += 2;
}
IO.println(result);
In ra 101. x = 9 không khớp case nào nên vào default (đặt trước case 1): result = 100, thiếu break nên fall through xuống case 1: result += 1 thành 101 rồi gặp break. Đây là ví dụ cho thấy fall-through và vị trí default đều có thể gây bất ngờ.

  • Giải thích fall-through của switch cũ bằng ví dụ tự viết, và chỉ ra lỗi khi quên break.

  • Giải thích vì sao switch expression với enum không cần default, và vì sao điều đó hữu ích khi thêm hằng mới.
  • Phân biệt 4 loại vòng lặp và chọn đúng cho từng tình huống.
  • Giải thích vì sao for-each không sửa được phần tử mảng primitive, nhưng sửa được nội dung object.
